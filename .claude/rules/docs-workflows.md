# docs-workflows — invariants, workflow map, agent callers

Loaded when a file under `plugins/docs-workflows/` is read, or `/epics`'s command, agent or docs page. Repo-wide rules are in `CLAUDE.md`; evidence is in `docs/maintainers/rationale.md`.

This file also loads with `/epics`'s command, agent and docs page, because the *Key invariants for `/document` (keyed mode) and `/epics`* section's bullets bind both commands; keep them here and never copy them into `product-workflows.md`, where two copies would drift.

Split out to keep this file under 20,000 characters: `/docs-serve`'s map line and run state → `.claude/rules/docs-serve.md`; `/release-notes`' map line, invariants and the `release-note-types` authority → `.claude/rules/release-notes.md`; `$DOCS_PATH` docs grounding, whose rules bind consumers in three plugins → `.claude/rules/docs-grounding.md`.

## Plugin facts

`/document`, `/docs-profile` and `/release-notes` all assume documentation already exists and work against a delta. The cold-start trio is `/docs-init` (scaffold a docs repository for a project that has none), `/docs-brand` (logo and colours out of the product's own code, contrast-checked) and `/docs-serve` (run the site's dev server). `/docs-audit` enumerates the documentation surfaces a product's own code and the specs tree imply, crosses each with the page types it earns, and writes a prioritised backlog and a coverage grid — it writes no documentation content.

The subagents are `diff-summarizer`, `doc-location-finder`, `doc-planner`, `doc-reviewer`, `doc-writer`, `docs-audit-reviewer`, `docs-auditor`, `docs-scaffold-reviewer`, `docs-style-checker`, `ia-planner` and `release-notes-writer`. The reference files are twenty-one markdown pages plus `default-owners.txt` and `docs-profile.default.yml`, which are read as data.

`docs-workflows` declares `workflows-core` and `prose-style` as dependencies, both by bare name, as `workflows-core:dependencies` requires — `/release-notes` hands `prose-style-checker` the `repo_root` input 0.4.0 added and checks the checker's echo of it, so an older `prose-style` gives a stated `DEGRADED` style check rather than a silent one.

`docs-style-checker` **always dispatches `prose-style-checker`**, in one of three roles its own step 5 names — *complementary* beside a primary linter that produced a result, *FALLBACK* where rungs were detected and every one failed, and *SOLE* where the repository configures none. What stays genuinely conditional is the **repo linter**, never `prose-style-checker` itself. `plugins/prose-style/README.md` says the same in as many words, and `docs-style-checker`'s own step 5 is the authority. ([why](../../docs/maintainers/rationale.md#prose-style-roles))

## Docs tree

`docs-workflows` carries 20 pages — `README.md`, `getting-started.md`, `workflow.md` and `docs-workflow.md` (the route page, which states the whole procedure from an empty repository to a populated portal, manual steps written out), 7 command pages and 9 reference pages.

## Authorities

`plugins/docs-workflows/references/gate-ledger.md` is the **single source of truth** for verification-gate accounting — the six outcomes (`RAN` / `DEGRADED` / `FAILED` / `UNAVAILABLE` / `SKIPPED_BY_USER` / `NOT_APPLICABLE`), the rule that **no outcome is orchestrator-assignable to mean "I decided not to run this"**, the `/document` gate registry, the `UNAVAILABLE` conversion prompt, and the reviewer contract. Consumed by `/document` (both modes), plus `doc-reviewer` and `docs-style-checker`, which read the ledger it produces; written generically for other commands to adopt.

`plugins/docs-workflows/references/repo-verification-gates.md` is the **single source of truth** for extracting a docs repo's own pre-PR checklist into the `repo_verification_gates` block — the heading patterns, what counts as checkable against the written files, and the augment-never-override rule. Applied by `doc-planner` in `/document` keyed mode and by the orchestrator itself in direct mode, which has no planner.

`plugins/docs-workflows/references/toolchain-preflight.md` is the **single source of truth** for the environment check a run makes before it writes anything — deriving the required tool set from the resolved profile, the repo's config signals, and the repo's own documented `Prerequisites`; the `toolchain` block with its tool→gate map; and the missing-tool prompt (Cancel recommended, silence when everything resolves). Its §2, source 2, is also where the plugin defines the five names Vale reads its configuration from and how every Vale run in the plugin — a lint and `vale sync` alike — runs over one: a form chosen by whether that configuration sets `StylesPath`, since `--no-global` drops Vale's default StylesPath along with the global configuration. Consumed by `/document` (both modes) at Phase 0, and by `/docs-init` at Phase 2 — which derives nothing, since there is no profile yet, and hands the check a fixed set of its own. `/docs-brand` and `/docs-serve` run no toolchain preflight, though `/docs-serve` Phase 4 takes its §2 definition of a command's tool, and §3's test for one, before it starts a server, and Phase 2 takes §2's set-aside of a leading `cd <dir> &&` and `VAR=value` words when it matches a recorded command to a process's command line. Its §3 chooses each tool's test, once, by running `command -v` in the shell — and from the directory — that will run it, never by emulating either: a tool the plugin runs through `bash -c` or as `command <name>` — `bash`, `curl`, `lsof`, `ps`, `vale` and every dev server's tool — is asked of that same child shell, which expands no alias of the user's and takes no unexported function of theirs, where a bare `command -v` in the Bash tool's own shell passes on both; a tool the gates run in the Bash tool's own shell — a build or lint command's — is asked of that shell, where the user's aliases and functions apply exactly as they will at run time; either test runs from the directory the command runs from, which is what resolves a path-valued tool such as `node_modules/.bin/vitepress`; an alias that resolves to something absent passes and fails at the gate, recorded there as any environmental failure is; and a tool that serves both takes both. `/docs-serve`'s Mode dispatch and Phase 4, `/document`'s render check and `docs-style-checker`'s third rung cite that split for their own tools.

## Workflow map

The `docs-workflows` commands' lines of the family workflow map, and the caller lines of the agents `plugins/docs-workflows/agents/` ships that have one (`diff-summarizer`, `doc-writer` and `release-notes-writer` have no tree line).

```
/document (direct)   → [docs-style-checker] → [doc-fixer] → impl-maintenance → commit-artifacts   (with no PRD folder — the ordinary case, this mode taking no address — its cost and feedback land under $SPECS_PATH/documentation/<docs-repo-slug>/ for the repository it edited, ahead of pending — D19; report-only if misrooted)
/docs-profile        → [resolve-docs-repo (signal-positive)] → scans docs repo → writes/refreshes .dev-workflows/docs-profile.yml + CLAUDE.md guidance → PR
/docs-init           → [resolve-scaffold-target — the *inverted* ladder: a $DOCS_PATH carrying a docs signal is a stop, not a match (D23)] → [source repos + toolchain preflight] → branch → scaffold the tree (a stub in every section; public + internal build over one content root; nav generated from frontmatter order) → Vale + seeded vocabulary → [/docs-brand --inline, unless --no-brand] → write .dev-workflows/docs-profile.yml → verify (public build, internal build, vale, the output-level visibility gate — a failure is reported and left unfixed) → [docs-scaffold-reviewer@Opus] → [triage: verify each finding; the orchestrator applies survivors — no fixer and no re-review (D25)] → commit + a drafted PR it never pushes → impl-maintenance → commit-artifacts   (its cost and feedback land under $SPECS_PATH/documentation/<docs-repo-slug>/, ahead of pending, because this run has no PRD and never will — D19; report-only if misrooted)
/docs-brand          → [resolve-docs-repo (signal-positive) + resolve the code repo to extract from] → extract colour by fixed precedence (Tailwind, CSS custom properties, MUI, web-app manifest, SCSS/LESS) → extract logo by fixed search order → print every value with its file and line → confirm (never applies silently) → [contrast check against the WCAG 2.2 SC 1.4.3 / 1.4.11 threshold pair — D24] → branch → apply → [docs-scaffold-reviewer@Opus] → [triage; orchestrator applies survivors] → commit + a drafted PR it never pushes → impl-maintenance → commit-artifacts   (--inline from /docs-init runs none of the branch/review/finish/emitter tail: its diff and its contrast finding go into that command's single review and single PR — and any stop or Cancel under --inline returns "no branding applied: <reason>", on which /docs-init continues as if --no-brand rather than aborting the scaffold; it validates the EFFECTIVE theme, following INHERIT, and writes theme/extra_css only into the config that inherits nothing)
/docs-audit          → [resolve-docs-repo (signal-positive)] → resolve <top> + read the profile → [confirm/record source_repos[] where the key is absent — recorded only where a profile exists] → [require nothing on main: this command gates on no prior phase] → [code-scanner×N over the recorded repos (parallel, cap 4, default branch) + the caller's own $SPECS_PATH read for the `decision` and `release` kinds] → [§8.5 seeded round 2; a theme still unresolved is named, never flattened into a gap] → [docs-auditor: surfaces[] with volatility from git log density] → [ia-planner@Opus: cross each surface with the types it earns, rank on four signals, propose tutorial candidates] → [mint a picked tutorial candidate — --refresh only] → write .dev-workflows/docs-backlog.yml + reconcile existing pages by their `unit:` frontmatter key → [docs-audit-reviewer@Opus] → [triage: verify each finding; the orchestrator applies survivors — no fixer and no re-review (D25)] → impl-maintenance → commit-artifacts   (no branch and no commit in the docs repo: the backlog is left in the working tree for the operator to review and commit; resolves no docs grounding (see the docs-grounding bullet); its cost and feedback land under $SPECS_PATH/documentation/<docs-repo-slug>/, ahead of pending, because this run has no PRD and never will — D19; report-only if misrooted)
/document (keyed)    → read the resolved PRD folder → [diff-summarizer×N (parallel)] → [doc-location-finder] → [doc-planner] → [discrepancy-escalation (Phase 5.8)] → writing → [docs-style-checker, which always also runs prose-style-checker — complementary / FALLBACK / SOLE] → [doc-fixer] → [doc-reviewer] → [triage: verify each finding] → [doc-fixer] → impl-maintenance → commit-artifacts   (Phase 0 hint: prefers ${DOCS_PATH:-/workspace/docs} as a docs-repo discovery hint — write-target only, no docs-grounder consumption)
                      └── doc-reviewer (docs-workflows)         (used by /document keyed mode)
                      └── doc-location-finder (docs-workflows)  (used by /document keyed mode)
                      └── doc-planner (docs-workflows)          (used by /document keyed mode)
                      └── docs-style-checker (docs-workflows)   (used by /document, both modes)
                      └── docs-scaffold-reviewer (docs-workflows) (used by /docs-init, and by /docs-brand on its standalone path — an --inline /docs-brand contributes to its caller's review instead of running a second one)
                      └── docs-auditor (docs-workflows)       (used by /docs-audit)
                      └── ia-planner (docs-workflows)         (used by /docs-audit)
                      └── docs-audit-reviewer (docs-workflows) (used by /docs-audit)
```

## Invariants

### Key invariants for `/document` (direct mode)

- **No branch and no commit, ever** — not "not by default", and there is no user-request escape: `document.md`'s Phase 3 step 7 says *"Do NOT create a branch, and do NOT commit the doc edits"* flatly, and the direct-mode page says the mode "creates no branch and no commit, ever". It works on the current branch and leaves its edits uncommitted; the user manages git by hand for a doc edit. The terminal `commit-artifacts` step is a **different repository** — it stages only `$SPECS_PATH`'s bounded artifact paths (`workflows-core:specs-repo-git` §2.1) and never the files edited here
- **No `test-baseliner`, no `test-writer`, no `code-review`** — docs-only phases only
- **No `doc-reviewer` gate** — direct mode is deliberately lightweight: a mandatory style check (Phase 3.5) and `doc-fixer`, but no Opus review. Two rules in `document.md`'s direct-mode section depend on that absence — the redirect to keyed mode or `/epics` when the task reads as SIGNIFICANT/HIGH-RISK (never to `/implement`, which that array does not offer), and the parenthetical stating there is no Phase 2B, Phase 3B or Opus review here (cited by content rather than by line, because a line number goes stale on the next edit above it)
- Style-check findings are fixed via `doc-fixer`; with no reviewer gate there is no BLOCKER fix cycle, no re-review, and no finding triage in this mode — a linter violation is a deterministic match with nothing to trace, so `workflows-core:finding-triage` explicitly excludes this path
- Mixed code + docs changes must use `/implement` instead

### Key invariants for `/document` (keyed mode) and `/epics`

The rule that a phase's `choices:` array is presented verbatim binds every command and is in `CLAUDE.md`.

- `/document` (keyed mode) and `/epics` are distinct top-level commands, each invoked explicitly
- **Zero direct API calls** — neither command calls a forge's REST API **directly over HTTPS**, on any host, or has a forge URL to resolve: `/document` (keyed mode) hands `diff-summarizer` only `refs[]` (its Phase 4 step 6), built from `implementation.md` and the commit scan, and `/epics` scans present-day code. All resolution runs against clones discovered under `$REPOS_PATH` (default `/workspace`), matched by `git remote get-url origin` slug. `gh`, which wraps the API, runs only for key discovery's optional, read-only `gh search prs` and `gh pr view` (`references/key-discovery.md`) and the `gh pr create` `/document` Phase 8.5 offers the **user** for the run's own pull request
- Parallel agent invocation: all diff summarizers (docs flow) or code scanners (epics flow) are launched in a **single response**
- Branch setup happens **before** writing output files — never after — in `/document`; `/epics` branches only at its Phase 7.5 handoff, after writing
- Branch policy: `/document` classifies its write context against the resolved `docs_repo_path` (not necessarily cwd: the git top level of the directory its ladder resolved — that directory itself outside any work tree — which is where the profile lives) — walk up from that resolved directory for `.obsidian/` → `obsidian` (never branch); else `git rev-parse` plus docs signals, or an in-repo `docs-profile.yml` → `docs_repo` (branch opt-in, confirmed at plan approval) or `non_docs_repo` (user confirmation promotes it to `docs_repo` behaviour); else `plain_dir` (never branch)
- `doc-location-finder` (docs flow) identifies write targets before writing begins
- `doc-planner` (docs flow) synthesizes PRD content + diffs into a documentation checklist
- `docs-style-checker` + `doc-fixer` lint prose after writing, before the review gate; style check is mandatory, and `prose-style-checker` runs on every dispatch — complementary beside a repo linter that produced a result, FALLBACK where every detected rung failed, SOLE where the repo configures no linter at all. `prose-style` is a declared dependency of `docs-workflows`, so it has no absent case; `style_check` records `UNAVAILABLE` only when every repo rung AND `prose-style-checker` fail
- For epics, `prose-style-checker` is the sole style checker and runs unconditionally as a non-gating quality pass; `prose-style` is a declared dependency of `product-workflows`, so there is no absent case to skip
- Description-vs-source discrepancies are escalated in Phase 5.8 (never auto-resolved); `doc-planner` records `prd_phrasing` / `spec_phrasing` alongside `source_phrasing` without choosing
- A bug-report draft (`<KEY>-implementation-gaps.md`) is written to the resolved PRD folder for `document-as-spec` / `skip-and-report` decisions, and for a `document-as-code` decision where the source document's phrasing asserts a specific value the code contradicts (`workflows-core:source-truth` §7.5)
- Review gate is `doc-reviewer` (docs flow) or `epic-reviewer@Opus` (epics flow); the reviewer's findings are triaged by the orchestrator before `doc-fixer` sees them (`workflows-core:finding-triage` — each finding verified at the location it names; kept, marked unverified, or dismissed with a reason that disposes of its own claim; survivors only, and a survivor failing the patch gate surfaced rather than patched); `doc-fixer` resolves surviving BLOCKERs; cap at one fix cycle plus one re-review. Both flows dispatch `doc-fixer` more than once — the triage attaches to the **reviewer-fed dispatch only**, never to the style-checker-fed one
- The re-review is handed the `doc-fixer` Fix Report as `claims_file`, and the reviewer reads it ONLY after every other dimension is complete — the deferral is what makes the falsification independent, and it is bought structurally (a path, read late) rather than by instruction
- Sub-agents return `DIRTY_TREE` / `REFRESH_BLOCKED` when a **writable** repo cannot be refreshed; a read-only mount returns neither and scans at `prep.scanned_ref` — never fail silently
- Every written claim must be traceable to the originating key plus the `diff-summarizer` ref that backs it (docs flow) or a file path (epics flow) — docs-flow attribution goes in the run handoff and the commit message, never onto the rendered page, and the `[[KEY]]` wikilink form is the epics flow's alone, `epic.md` being a specs-tree document (`workflows-core:doc-structure-conventions` §1)
- Writes never touch `_archive/`, and neither command confines its writes to cwd. `/document` (keyed mode) writes product documentation only inside the resolved `docs_repo_path` — the git top level of the directory its Phase 0 step 2 ladder answered with (that directory itself outside any work tree): cwd's own work tree where that carries a docs signal (a), else `${DOCS_PATH:-/workspace/docs}` where that carries a docs signal or an in-repo `.dev-workflows/docs-profile.yml` (a.5), else a repository found by the same test under `${REPOS_PATH:-/workspace}` (b), else cwd or an absolute path the user confirms (c) — so rung (a.5) writes into `$DOCS_PATH` from any working directory, and every Phase 6.3 write consumes `docs_repo_path`, not cwd. Its bug-report draft (`<KEY>-implementation-gaps.md`) and `pr-draft.md` go to the resolved PRD folder, and a screenshot staged for manual upload goes under `<screenshot_staging_dir>` — the resolved PRD folder's screenshot subfolder, or a persistent directory the operator names — never `/tmp` and never the docs repo. `/epics` writes each Epic inside the resolved PRD folder, in its own `EPIC-` subfolder, and never into cwd. Both file their session bookkeeping under `$SPECS_PATH` (`workflows-core:specs-repo-git` §2.1)
- (docs flow) Phase 0 runs the toolchain preflight after profile resolution; it prompts **only** when a required tool is missing, and Cancel is the recommended option
- (docs flow) Every gate in the `gate-ledger.md` registry appends its row **when the gate completes**; a missing row, an unconverted `UNAVAILABLE`, or an unattributed skip is a `doc-reviewer` BLOCKER
