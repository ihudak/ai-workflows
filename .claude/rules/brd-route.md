# BRD route — map lines and folder-kind invariants

Loaded for every file under `plugins/product-workflows/`, plus the named files outside it that carry a kind or container gate these invariants bind — `dev-workflows`' `/design`, `/ready` and `/implement`, `docs-workflows`' `/document` and `/release-notes`, `workflows-core`'s `/frames`, and `workflows-core:addressing`. That cross-plugin list is not a census: a kind gate added elsewhere needs its file added to these `paths:`. Find them with two greps and add every file outside `plugins/product-workflows/` that either returns: `grep -l '_BRD_NOT_SLICED: <' plugins/*/commands/*.md` (the container refusals) and `grep -lE 'kind it asserts|asserted kind|asserts .kind: brd|asserting .brd' plugins/*/commands/*.md plugins/*/references/*.md` (every file that places a folder by prefix rather than by its asserted kind, or reads the asserted kind on purpose). The rest of `product-workflows`' rules are in `.claude/rules/product-workflows.md`; repo-wide rules are in `CLAUDE.md`; evidence is in `docs/maintainers/rationale.md`.

## Workflow map

The BRD-to-PRD route's lines of the family workflow map, and the caller lines of the route's own agents.

```
/brd-intake          → [walk every link read-only, wikilinks included (product-workflows:linked-sources); the operator decides on files outside the folder and on files neither markdown nor an image] → copy what was taken — `brd/source/` verbatim, the customer's document **and every file Phase 1 took from its own directory**, byte-for-byte at the same relative paths, and outside files into `brd/source-external/` — with `brd/brd-link-log.md` naming every link in a captured file whose target was not copied, and why, and mapping each captured link that does not resolve as written → [figure-reader@Opus ×N (parallel) → brd/brd-figures.md] → brd-reader@Opus (document + linked markdown + transcriptions) → [docs-grounder (grill-rank over the defect walk)] → (defect confirmation with a human) → write `brd/brd-inventory.md` + `brd/brd-defect-log.md` + `coverage-ledger.md` (every row `unallocated`) → [handoff-to-main: intake artifacts] → impl-maintenance → commit-artifacts
/brd-split           → [require-on-main: grounding/code-grounding.md, `allocate-only` only — a root is never ground] → [on a slice: gate, four tests: code grounding non-empty; design grounding on main covering every design/ frame set on disk, where any exist; every finding carries a verifier outcome; and every finding block well-formed against `workflows-core:grounding-format` §2.1's **closed** field set — §2's fields plus `outcome` and `notes`, so a block carrying the verifier's `own_verdict` return field, and therefore two verdicts at once, is refused where the outcome test passes it] → [`<instruction>` — mandatory on a root with a row still `unallocated` (`BRD_SPLIT_NEEDS_INSTRUCTION` if absent, stopped on late in Phase 0 so a root run that proposes nothing stays reachable without one), optional on a slice: resolve it against this BRD's rows, then a bounded grill (≤5) on the residue, gated on one answer placing more than one row — seeds the grouping and the walk's `<recommended>`, decides nothing] → propose + key slices (`full` mode only) → walk every `unallocated` ledger row to a recorded fate — **or, on a fully-allocated root carrying an instruction, the sibling re-cut** (Phase 0 step 9a builds the candidate set, step 10 tests it before the no-op, Phase 4's Step 2R walks it in place of Step 2): each row this BRD delegated to a child whose own ledger records `deferred-to` against it may be re-pointed onto a sibling that has not been interviewed, `covered-by: <B>` written on this ledger and then on the donor's → reconcile every standing child's `claims:`, inventory and ledger against this ledger's `covered-by` rows, writing nothing for a child already in step (a bare run on a fully-allocated root reaches this too, where a stopped carve left a child out of step) → write slices.md → [resolve every standing empty child: remove, or keep against a recorded `reason:`] → [handoff-to-main: ledger + slices + each surviving child's `brd-link.md`, `brd/brd-inventory.md` and `coverage-ledger.md` — the route's seed files are written by nothing here] → impl-maintenance → commit-artifacts   (on a slice: `allocate-only` — no child, and a *different* four: `covered-here` where the parent's walk offers `covered-by`; runs once on the root to carve slices, once more on each slice — after `/prd-ground` — to allocate it, and again on the root, with an instruction, to re-cut)
/prd-ground          → [require-on-main: coverage-ledger.md, then brd/brd-inventory.md] → [on a slice: its `claims:`, its inventory and the parent's `covered-by` rows for it agree, else `PRD_GROUND_SLICE_UNRECONCILED`] → resolve repos + baseline-integrity gate → [docs-grounder (lead-only)] → [code-grounder@Opus ×N (parallel, cap 4)] → [design-grounder@Opus ×N (parallel, cap 4, after the code batch returns — its fourth class cites a `[CG#n]`)] → [grounding-verifier@Opus, batched ≤25 per repository or frame set, two dispatches each — a blind derive handed no finding's answer, then a compare: independent re-derivation, no outcome ⇒ not evidence; settles whether a finding owes a `control` by the closed-set rule, then runs any it owes rather than reading it; a missing one is `contradict`, and a failed one is too **except** where the finding already reads `NOT-PROVABLE` with that failed control recorded, which is agreement] → [sweep every class-4 `[DG#n]` whose cited `[CG#n]` this run rewrote] → write findings → [handoff-to-main: grounding findings] → impl-maintenance → commit-artifacts   (a resolved root stops with `PRD_GROUND_ROOT_LEVEL`: a root BRD is never ground — grounding happens at a `PRD-` folder, a slice or an idea-route PRD folder)
/brd-interview       → [require-on-main: grounding/code-grounding.md] → [gates: every finding verified; no ledger row `unallocated`] → resolve/open the round → tag every question → answer each `[G]` from the findings → decide each `[V]` with the operator → hold each `[C]` for the customer → write, in this order, code-defect-log.md (where a decision turns on a [CDF#n]) → decisions.md → interview/customer-questions.md → interview/round-N.md last, the commit point: an item no round record names is a torn write no reader counts (`product-workflows:decision-register-format` §8) → apply each [CDF#n] re-disposition the round record names → [handoff-to-main: register + round record + `[C]` question set] → impl-maintenance → commit-artifacts   (a resolved root stops with `BRD_INTERVIEW_ROOT_LEVEL`: deciding is slice-only)

/brd-reconcile       → [require-on-main: the sent customer-review-prompt — unless --sent names what was actually sent for a package this route did not build] → canonicalise + commit the returned review, and any --sent material beside it, before anything reads either → customer-review-reader → confirm every candidate with the operator → freeze `[CD#n]` → corrections, banners, defect resolutions, ledger rows → [propagation sweep across dependent BRDs] → [stale cross-reference sweep under the parent] → write the reconciliation record → [handoff-to-main: reconciliation] → impl-maintenance → commit-artifacts   (a resolved root stops with `BRD_RECONCILE_ROOT_LEVEL`: reconciling is slice-only)

Each of the three writes `consumed_by: PRD|ARD|specification` on what it drew on and reports, by id, what at its own altitude is still `consumed_by: none`. **The three altitude seeds are written by nothing on the route** — `prd-seed.md`, `ard-seed.md` and `spec-seed.md` have exactly one creator, `/brd-intake --sort-existing`, a migration path for a package authored by hand before the route existed — so a reconciled BRD normally holds none and each consumer says so rather than reporting a gap. What actually carries every altitude is `decisions.md`, which all three read and filter by the `altitude` field, plus the grounding files (and, for `/specify`, the derivation matrix appended to `code-grounding.md`). The design's altitude-router table (§7.2 of the BRD-to-PRD workflow design spec, removed from the tree 2026-09-23 — `git show 62e791e8:docs/superpowers/specs/2026-08-29-brd-to-prd-workflow-design.md`) names a seed file per altitude; treat that as the unbuilt half of §7.2, not as a description of what runs, and do not write "routed to its seed" into any command — a reader sent after that file finds nothing and concludes the content was lost. A BRD key addresses a folder, never a record in any tracker; no tracker key is minted anywhere, and a user's own tracker identity, where they keep one, lives in the reserved `workitem_key` the plugin never writes into frontmatter (its value is carried into a code commit's `Work-Item:` trailer). The PRD's `key` is written by `/create-prd` on **both** routes, set to the resolved folder's own key — the `PRD-` slice's on the BRD route (`workflows-core:prd-format`); `/update-prd` carries it forward and mints nothing. **Every downstream command reads the same tree.** `/epics`, `/release-notes`, `/design` and `/ready` each resolve a folder with `resolve-address` and read what is in it; none needs a key minted anywhere else, and none can be unreachable for want of an import. The PRD's `brd_key`, `brd_parent` and `depends_on` record committed BRD provenance, and **no command of the build ladder reads any of the three**: `brd_key` and `brd_parent` are acted on by no command (`prd-reviewer` only checks that the pair is present together), and `depends_on`'s one reader is `/brd-proposal`, which takes slice order from it to compute peak concurrency — an estimate, gating nothing. So do not justify them by naming a build-ladder consumer; they exist because provenance captured at authoring time is the precondition for any future one.

## Invariants

- **A slice folder is `PRD-`-prefixed and asserts `kind: brd`, and that contradiction is load-bearing.** `/brd-split` writes `brd-link.md` with `kind: brd` into the `PRD-` folder it carves, and `workflows-core:addressing` §4 reads a folder's kind off the first top-level artifact, in byte-wise order of name, whose frontmatter carries `key:` and a `kind:` naming a folder kind — of a slice's files that qualify, `brd-link.md` sorts first — so the slice *asserts* `brd` while being exactly the folder a PRD, an ARD, a specification and every `EPIC-` folder belong in. That is why a container refusal tests the **directory prefix** — every `*_BRD_NOT_SLICED` stop does (`grep -l '_BRD_NOT_SLICED: <' plugins/*/commands/*.md`; `/create-prd` step 5a, `/create-ard` step 1a and `/epics` step 1a among them), each taken before a single ledger row is read, and `/epics`'s accept gate tests **`prd.md`'s own `kind: prd`** one file down. A prefix is the name beginning `<KIND>-<the resolved key>-`, as `workflows-core:addressing` §4.1 defines one, so a legacy folder whose key begins with a kind token is not taken for a prefixed one. An asserted-kind gate would refuse every slice and accept nothing, which is the single most likely way to get this wrong. `/create-prd` is the one command that cannot use the `prd.md` test at all — it is the run that writes the file — which is why its refusal is structural and its data refusals are slice-only.
- **PRD-eligibility is a folder-kind question now, not a ledger question.** D5 makes a BRD a container that is never implementable, so the question "may a PRD be authored here?" is answered by *which kind of folder this is* — a `BRD-` container never, a `PRD-` slice yes — and only then, on a slice, by the two ledger tests (`no row still unallocated`, `at least one covered-here`). `product-workflows:coverage-ledger-format` §5 is the authority all three refusals cite; do not re-express D5 as a sixth disposition or as a new ledger rule. On a folder with no prefix — one §5's legacy unprefixed fallback resolved, or an unprefixed folder an `@<path>` names (`workflows-core:addressing` §4.1) — there is no prefix to test, so the container question is answered by **positive evidence that it is a BRD** — `coverage-ledger.md` or `brd/brd-inventory.md` present and no `brd-link.md` naming a `parent:` — never by the *absence* of a file, which would refuse a legacy idea-route PRD folder and then offer `/brd-split` on a folder with no ledger to walk.
- **The sibling re-cut is the one place `/brd-split` re-allocates a row that already carries a fate by the owner's choice, and its precondition is the whole of it.** (Phase 4.5's removal repair also rewrites fated rows — a removed child's `covered-by` — but that is the key repair a removal forces, not a re-allocation.) On a fully-allocated **root** carrying an `<instruction>` — the one run on which that argument is otherwise free, which is why it takes no flag — a row whose parent ledger reads `covered-by: <A>` while A's **own** ledger reads `deferred-to: <A>` may be re-pointed onto a sibling under the same parent that has not been interviewed (no `decisions.md` holding a `[VD#n]`/`[CD#n]`, no `interview/round-*.md`), one already standing or one that same run carves. Both halves are read off the `disposition` column at both levels, never off `claims:` or an inventory. **What relaxes is only the weaker rule** that this command never re-allocates a settled row, and it relaxes against the owner's own written refusal and against nothing else. **What survives, and a reader needs to see that it survived: no row ever returns to `unallocated`** — every write here replaces one terminal disposition with another, so §4's allocation gate is never reopened — and the one-level nesting cap is untouched, because a re-cut carves a *sibling*, never a child. `product-workflows:coverage-ledger-format` §3.2 is the authority, and the rule is changed there. **Its readers are not a set a glob expresses, so no recipe stands here.** Sweep a §3.2 change from §3.2's own citations across `plugins/`, never from a command-name pattern — a recipe that returns a wrong answer is worse than no recipe, because the next reader trusts what it returns. ([why](../../docs/maintainers/rationale.md#brd-recut-readers))
- **The BRD route is detected, never declared.** `/create-prd`, `/create-ard` and `/specify` each take one positional address; where it resolves to a folder carrying `brd-link.md`, the run is on the BRD route and says so before doing anything. There is no flag: one that could disagree with the folder it names is one more disagreement to have. The seeds are altitude-partitioned and non-interchangeable — `prd-seed.md` is `/create-prd`'s, `ard-seed.md` `/create-ard`'s, `spec-seed.md` `/specify`'s — and `prd-format.md`'s no-implementation-detail rule is **not** relaxed on that route: sub-product-altitude content is what the ARD and specification seeds exist to carry. `/create-prd` may fill what a seed leaves open and may **never** reopen a `[VD#n]` or `[CD#n]`; a customer signed those. `--from-prd` survives as a flag and is not symmetric with what was removed: it names a *different* PRD to seed from, which no folder can decide on the operator's behalf.
- **`/prd-ground`'s verification is blind by construction, batched, and never weakened per finding.** The derive dispatch carries a finding's premise and source and never its `verdict`, `evidence`, `control` or `cites` (`workflows-core:grounding-format` §8); a batch's composition never depends on a finding's answer; and every finding in Phase 7's verification set gets its own Opus re-derivation on every run — no cheaper tier, no sample, no repository-scope finding standing in for the ones under it, and no outcome carried forward from an earlier run; a finding this run could not verify keeps the outcome it had and is reported as not verified by this run — it is never reported as verified. Read the rationale before proposing any of those as a saving. ([why](../../docs/maintainers/rationale.md#verifier-blind-batched))
