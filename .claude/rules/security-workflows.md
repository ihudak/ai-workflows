# security-workflows — plugin facts, workflow map, invariants

Loaded when a file under `plugins/security-workflows/`, the register format it writes (`workflows-core:security-register-format`) or the family map that draws its lane is read. Repo-wide rules are in `CLAUDE.md`; the shared authorities its command consumes are in `.claude/rules/workflows-core.md` and `.claude/rules/workflows-core-git.md`; the design and its decisions (D1–D19, cited below as spec D*n*) are in `docs/superpowers/specs/2026-10-15-security-workflows-scan-design.md`.

## Plugin facts

`security-workflows` provides one command, `/security-workflows:scan` (`ls plugins/security-workflows/commands | wc -l`), and no agents, hooks, skills or reference files: the orchestrator triages inline, and Claude Security does every scan and every patch. It ships two scripts (`ls plugins/security-workflows/scripts/*.py | wc -l`): `register.py`, the register's one writer, whose `--selftest` CI runs, and `bounded.py`, the copy of `workflows-core`'s that CI holds byte-identical (`.claude/rules/workflows-core-bounded-run.md`).

It has two dependencies, in `plugin.json`'s `dependencies`: `workflows-core`, by bare name, and `claude-security@claude-plugins-official`, Anthropic's Claude Security, from another marketplace. Claude Code installs that one only because `.claude-plugin/marketplace.json` allowlists its marketplace in `allowCrossMarketplaceDependenciesOn` — without that line the install completes without Claude Security and this plugin fails to load. Neither carries a version pin: a pin would disable the plugin whenever Claude Security moved past it (spec *Risks*). No other family plugin depends on it (`grep -l security-workflows plugins/*/.claude-plugin/plugin.json` lists its own manifest alone), so removing Claude Security costs this one command and nothing else (spec D1).

Its docs tree carries 8 pages (`find plugins/security-workflows/docs -name '*.md' | wc -l`) — `docs/README.md` (the index), `getting-started.md`, `workflow.md` and `roles-and-phases.md`, 1 command page under `docs/commands/` (`ls plugins/security-workflows/docs/commands | wc -l`) and 3 reference pages under `docs/reference/` (`ls plugins/security-workflows/docs/reference | wc -l`).

## Authority

`plugins/workflows-core/references/security-register-format.md` is the **single source of truth** for the findings register `/security-workflows:scan` keeps per code repository in `$SPECS_PATH/security/<repo-slug>/`: where it lives and how it reaches the default branch (§1), the run record, numbering and renumbering (§2), a finding's fields and the structured-fields rule for anything built from one (§3), the statuses and the two roles (§4), and the rules `register.py` applies — matching, closure on evidence and only on evidence, an `ID_VERSION` change, ancestry, unverified scans, a file gone, idempotence (§5). It lives in `workflows-core` because a reference does not cross a plugin boundary (spec D2). `scripts/register.py` implements it, and its readers are what `grep -l 'args: "security-register-format' plugins/*/commands/*.md plugins/*/agents/*.md` lists (§6).

## Workflow map

```
/security-workflows:scan → [strip-run-flags; one address — a key, or a repository path; SPECS_PATH required] → [resolve-address on a key; no folder created] → specs-preflight → [the repository: the session's own on a key run without --import, else the one the path or --import names; its slug, a best-effort fetch, its default ref] → [change scan (a key alone): fetch the block's branch by refspec → unit-branch — none stops] → [reservations: run records other session/* branches hold] → [leftover worktrees: an idle one offered for removal] → [prerequisites: python3 3.9, the Workflow tool] → [model-routing: SIGNIFICANT; on Sonnet or lower asks Cancel / Scan anyway] → (a change scan: checked-out in place, local/remote after a switch question, merged/missing stop | a path: in place | --verify-fixes: register.py verify-scope → a temporary worktree at the default branch's head | --triage: register.py plan, no scan | --import: no scan) → (a scan: [one confirmation] → claude-security, the change job over the block's base or the codebase job) → (a scan or --import: [redaction check] → copy the products to security/<repo-slug>/scans/ → register.py plan) → [triage, one batch: fix / decide later / false positive with evidence / accepted risk with an owner and a review-by date; a possibly-same row always asked; a dev run's decisions awaiting security review] → register.py ids → [patches: claude-security suggest patches, the session's repository only] → [refresh the reservations] → register.py commit → _security.md unit note → worktree removed → report → impl-maintenance → feedback → follow-ups → cost → resume.md → commit-artifacts   (no agent of its own; no handoff-to-main and no require-on-main: the register is bookkeeping)
```

It is offered by `/dev-workflows:implement` and `/dev-workflows:conformance` on an Epic before its pull request merges, and among the offers it prints in turn are `/dev-workflows:implement <KEY>`, which continues on the Epic's branch while its pull request is open (`.claude/rules/dev-workflows-implement.md`), `--verify-fixes` once a fix has merged and `--triage` for the Security Engineer, and, after a change scan, the scan from each other repository the unit names and the Product Engineer's `/dev-workflows:conformance <PRD-KEY>` (`workflows-core:next-phase-offer`; the list is Phase 7's `### Next step`). Its offers carry no `<merge-clause>`: the run hands nothing off by pull request.

## Invariants

- **`register.py` is the register's only writer.** The command never writes `register.json`, `register.md` or a run record by hand, and a scan folder holds Claude Security's products unchanged; `workflows-core:security-register-format` and `register.py` change together, in the same commit (that reference's opening, and §1). The one read of a derived file as state is §1's *Confirm*, from a `register.json` the run has just rebuilt
- **The register is bookkeeping, and nothing waits.** `$SPECS_PATH/security/<repo-slug>/` and a unit's `_security.md` are among `workflows-core:specs-repo-git` §2.1's bounded paths, so `commit-artifacts` commits and pushes them with the run's session files — on `session/<identity>` in §8's session-branch mode — and nothing hands them off by pull request. No run stops or waits because another run's register changes are unmerged (`security-register-format` §1, spec D12). `security/` holds the register and a keyless run's cost entries, and nothing else
- **A finding is named by its origin, and a published number stays.** Every run record names a finding by `origin`, never by number, so a renumbering cannot point a record's decisions at another finding. A new finding takes the next number past every number any record published — allocated, or written as a move's `to` — the records other `session/*` branches hold included: Phase 0 step 6 reserves them and Phase 7.1 refreshes them, the specs default branch included. Every number an allocation was published under stays held for it; the one way a `[SEC#n]` changes is §2's move, of an allocation whose number another finding was published under first, to the lowest number nobody published, and two records that allocated one finding twice name one finding, the later number giving way the same way. A run that meets a move reports it, naming the record it came from and the follow-up lines that still cite the old number. The first run that records anything after it writes the move into its own record, so no later run reports it again; a run that records nothing reports it as provisional, with no line to correct yet, and leaves it for the next one to record (`security-register-format` §2)
- **Follow-ups carry structured fields only.** `register.py commit` builds every follow-up line, and on a path every `/implement` prompt line, from the `[SEC#n]`, a CWE number, a plain `path:line` (or a pointer to `register.md`) and the patch path — never from a finding's text, which is scan output and is quoted under its own heading wherever it is shown (`security-register-format` §3, spec D10)
- **A change scan never closes a finding, and a closure through a squash is only proposed.** Only a covering codebase scan, later than the finding's last sighting and over a changed file, closes a `fixing` finding by itself; one the scan reaches only through a squash merge, which names the unit and not the fix, is proposed fixed, as is an `open`, `fix`, `reopened` or `accepted-risk` one, and changes on a person's confirmation. An unverified or dirty scan closes nothing, a low-effort one covers nothing, and the command never asks for `low` (`security-register-format` §5 rules 2 and 5)
- **A Dev is never blocked.** A `dev` run's false positive or accepted risk takes effect at once, recorded `confirmed: false`, *awaiting security review*; a `sec` run confirms it by deciding the same status again, or overrules it. Nothing the Dev does waits for that review, and their pull request is reviewed and merged as usual (`security-register-format` §4)
- **Only a change scan runs `unit-branch`** — a key with none of `--import`, `--triage` and `--verify-fixes`, which first fetches the block's branch by its explicit refspec on a writable clone, best effort; `--triage` and `--verify-fixes` with a key never run it, and never meet its states (`workflows-core:implementation-format` §5)
- **The scan root is the session's repository on a key run (spec D5).** Claude Security's change job scans the repository the session is open in, so a key run without `--import` takes `git rev-parse --show-toplevel` from the working directory, and another repository the unit's `implementation.md` names is scanned from there; a path scans that repository in place; `--verify-fixes` scans a temporary worktree at the default branch's head, removed on every path. The user's checkout is never switched without Phase 1's question
- **Patches run only in the session's own repository.** *Suggest patches* builds against the working directory's repository at the scanned commit, so Phase 6 asks only where the scan ran there, over a clean stamp at the session's HEAD — never on `--verify-fixes` — and elsewhere each follow-up says it has no patch. The command never applies a patch: `/dev-workflows:implement` starts from it
- **The session model is the scan's model (spec D6).** Claude Security's agents inherit it, and nothing inside a running command can change it: on Opus nothing is asked, on Sonnet or lower Phase 0 asks before scanning, on Fable nothing is asked and the confirmation says Fable's filters re-run some requests on Opus; the scan never escalates to Fable. `--enforce-model` reaches the run's own dispatches only — the Phase 7.6 maintenance agents — and under it the Sonnet question does not fire (`workflows-core:model-routing/classification` §10)
- **Follow-ups are written after the report.** `register.py commit` builds them at Phase 7.2. On a key run the report lists them as pending and Phase 7.6 previews and writes them in the emitter tail (`workflows-core:followup-emission` §7); on a path run they are prompt lines in the report's `### Next step` and nothing is written. A line the preview cancels returns its finding to `fix` with a second, small run record, and a `fix` decision clears the finding's follow-up link. `register.py plan` offers every `fix` finding again as `pending_fix`, and, given the unit's `follow-ups.md`, every `fixing` one no line there carries — a run cut off before its follow-up write (`security-register-format` §4). `followup-emission` §5 matches a line carrying a `[SEC#n]` only against an open line carrying the same `[SEC#n]` for the same repository and unit, so neither a ticked line nor another caller's line stands for it
- The command never scans by itself, never runs anything against a deployed system and never writes exploit code: it records, triages and routes what Claude Security reports
