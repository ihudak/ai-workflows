# dev-workflows — `/implement` invariants

Loaded with `.claude/rules/dev-workflows.md`, whose `paths:` it shares. Split out of `.claude/rules/dev-workflows.md` to keep that file under 20,000 characters; the plugin's other rules are there, and the test-writing requirement for code changes is in `.claude/rules/dev-workflows-tests.md`; repo-wide rules are in `CLAUDE.md`; evidence is in `docs/maintainers/rationale.md`.

## Invariants

### Key invariants for `/implement` specifically

- A keyed run whose working directory is in the specs repository — `$SPECS_PATH` that repository's top level — stops before the preflight: the specs repository is no code repository. A direct run there runs on with a notice, its session files committed on its code branch, which `commit-artifacts` does not push unless the branch's name carries a plugin prefix (`workflows-core:specs-repo-git` §4 step 5) — on a run that stops before it cuts that branch, on the branch HEAD then stands on, the default branch after Phase 1.4's fresh start, which it pushes (§4.1) — or, in session-branch mode, sent to `session/<identity>` and never onto that branch, or left uncommitted where no identity names one (`workflows-core:specs-repo-git` §8) — and where `$SPECS_PATH` is a specs tree inside a larger repository, the run goes on as it did
- Phase 4.6 (`finish-code-branch`) runs **after** Phase 4, never before it — Phase 4's maintenance agents write `README.md`, `CHANGELOG.md`, `docs/`, `CLAUDE.md` and any project-level memory entry into the same repository, so a commit ahead of them ships a partial run. A multi-source run changes code only in the repository it branched; a change another code repository needs is a follow-up (Phase 6's, or named in the stop), never an uncommitted edit there
- **The branch is settled before the first read of the code.** Phase 1.4 — run from Phase 1 after its read-back and its stops, before its look — holds the clean-tree check and the HEAD question, so every move of HEAD an answer makes (the switch to the unit's branch, its fast-forward, a fresh start's switch to the default branch) comes before Phase 1's look, Phase 1.7's scan, Phase 2A's and 2B's exploration and `risk-planner`'s repro, all of which read the tree; no move is made that would change a spec input Phase 0 read inside the repository. Pre-Phase 3 then cuts the branch from where Phase 1.4 left HEAD, or none where the run continues on the unit's own, and every stop from Phase 1.4 to Phase 4.6 names `stash_ref` and the branch HEAD stands on
- **`/implement` keeps its run state in a file it re-reads every phase**: `$(git rev-parse --git-path dev-workflows/implement-run.json)` in the code repository — per worktree, inside the git directory, never staged, one `/implement` run per worktree at a time being its precondition, as it is the working tree's — holding every fact a later phase, a stop or the Phase 5 report reads, the `## Test Baseline` block and the task description through temp files it names. Phase 1.4 opens by creating it — `init` handed only the facts the run holds by then, every other key taking the default the script's `KEYS` gives it, and a slip it names corrected and the call made once more — moving aside unread any file an earlier run left there (`implement-run.json.stale-<UTC compact stamp>`, named once in `### Assumptions & limitations`, at most one kept); every key is written the moment the run learns it, `phase` on every entry into a phase, through `plugins/dev-workflows/scripts/run-state.py` alone (`init`, `open`, `read`, `set`, `append`, `remove`, with a `--selftest` CI runs), which refuses a key the file does not hold and whose every write, under a lock, replaces the file whole, as UTF-8 with non-ASCII written as itself, so a path comes back as git's `-z` record gave it — each write and each read named at its site; every phase from Phase 1.5 to Phase 7 opens with `Read the run-state file first.` and acts on its keys, never on memory — Phase 4.6 takes `run_flags` (`no_commit` included), `branch`, `pre_existing_dirty`, `stash_ref`, `unit_key`, `workitem_key` and `clean_finish` from it, and every stop names `stash_ref` and the branch from it; and its end-of-run removal — the temp files it names, then the file — runs once, as the run's last action before the terminal `commit-artifacts` and in every stop once its message is out, never at Phase 4.6, which Phases 4.7 to 7 follow. A file the run cannot reach (`run-state.py`'s exit `4`) stops it with the work uncommitted, the one exception besides the secret scan's to the commit `.claude/rules/dev-workflows.md` keeps: Phase 4.6 takes `pre_existing_dirty` and `stash_ref` from that file, and without them its commit could carry the user's own uncommitted work
- On a keyed run whose default branch resolves (`dev-workflows:code-handoff` §2.8), Phase 1.4 step 2 fetches `origin` and then finds the unit's own recorded branch with `workflows-core:implementation-format` §5's `unit-branch`. Where its pull request has not merged (no `merged` state, no `after_merge`), `/implement` offers *Continue on this branch* where HEAD is that branch and carries commits the default branch lacks, or, on a tree with no uncommitted change to a tracked file, *Switch and continue* where it is `local` or `remote`, wherever HEAD stands — each question naming `<branch>` in its text and saying that the work joins its open pull request, which the step probes for first, or that it has none — so the work joins its pull request where one is open. A tree with tracked changes is told why the switch is not offered, and asked whether to stop so the user can commit or stash first (recommended) or to cut a fresh branch here, one without the unit's commits. It never cuts a second branch carrying the first one's commits, unless the user asks, and where the state is `merged` and HEAD is still on that branch, it recommends the fresh start
- **A keyed run starts from the scan's patch where it still applies.** Phase 1's read-back resolves a `/security-workflows:scan` follow-up's `security/<repo-slug>/scans/<folder>/patches/F<n>.patch` under `$SPECS_PATH` — the worktree, else `<default-ref>` through a temporary file — never under the code repository, and hands its absolute path to the planner. It is a starting point the plan checks against the unit's specification, ARD and design like any change, a shortfall being a Phase 1 question. Before any other edit, on the branch Phase 1.4 settled or Pre-Phase 3 cut from there (Phase 3A/3B step 1, which a re-plan re-enters and which then checks only a patch not yet checked), each task's patch is checked and applied in task order, `git apply --check` deciding: a pass applies it and that fix goes on through the run's own tests and review; a failure — the first patch's, or one's after an earlier patch applied — or a patch that could not be read goes into `### Assumptions & limitations` and that fix is derived afresh, with no re-plan. A temporary copy is removed once its patch is applied or refused. A direct run reads no follow-up, so it resolves no patch: `/security-workflows:scan`'s path run prints each patch's absolute path beside its prompt line instead
- Test baseline captured **before** any source edits, using `test-baseliner`
- **`/implement`'s orchestrator writes no source code in Phase 3A, 3B or 3.5**: `code-writer` codes the approved plan, one dispatch per step group — a step, or up to ten consecutive steps naming exactly the same files, a Phase 2A plan's Steps naming them as `risk-planner`'s do — in plan order, each dispatched once the one before it returned `done`; and `review-fixer` applies the review's fixes. Both run on `workflows-core:model-routing/classification` §4's `implementation_model` — `current_model` at `SIMPLE`; from `MODERATE` up, `current_model` where it is an Opus or Fable model, else the §2 Opus chain's first available row; `--enforce-model` over both — re-resolved at every class change for the dispatches after it. The orchestrator's own working-tree actions there are the mechanical ones: a plan's bisect step, a scan's patch applied, a `[DEBUG-xxxx]` probe stripped, a diff captured, a step 7.5 note written and Phase 3.5's checks run. `code-writer` runs no lint, build, type-check or test against the working tree at any class, writes no git state, never asks the user and returns `done`, `needs_decision`, `trigger` (at `SIMPLE` or `MODERATE` only) or `blocked`: a `blocked` step is put as `Revise the plan (you'll be prompted)` — the run's one re-plan, `risk-planner`'s at `SIGNIFICANT` or `HIGH-RISK`, a Phase 2A revision re-tested for its class below — or `Stop here`, and once that re-plan is spent the run stops through Phase 4.6 unasked. On `task_shape: bug`, at every class, it runs the repro and its probes only in a scratch checkout of `HEAD`, and a repro step that does not go red there is `blocked`, save where the plan's ranking reads `Ranking withheld`
- **`MODERATE` work is reviewed by the Opus `code-review` gate before any test**, as `SIGNIFICANT` and `HIGH-RISK` work is: Phase 3A step 6 runs Phase 3B's steps 4a to 8 at `MODERATE`, with no `risk-planner` — `test-writer`, the review diff, the review, triage, `review-fixer`, then Phase 3.5 from its step 3 — and `code-review` returns no `### Re-classification` on a `MODERATE` brief, naming only `SIMPLE` on a higher one, the one class `/implement` leaves unreviewed. Every Phase 3.5 fix — the failing lint, build and other checks of its step 3 together in one attempt, a regression or a new failure at its step 6 — is a `code-writer` dispatch in `mode: fix`, two automated attempts in all, after each of which the orchestrator's own run of the check is the only run; a lint failure is the run's unless the same lint command, run on a scratch checkout of `HEAD` (`bug-diagnosis.md`'s recipe, only when a lint check fails), reports it at the same file with the same message — such a pre-existing failure is named in `### Assumptions & limitations`, never sent to the loop, never asked about and never a reason for `clean_finish: false`; a failing build always goes to the loop
- The test-writing requirement — what `test-writer` must write, its one bound, and what a completion must name — is in `.claude/rules/dev-workflows-tests.md` § Test-writing requirement
- If no test framework is detected — or if every suite the capture actually ran aborted with no parseable pass/fail counts, the other capture that asks — surface that explicitly at Pre-Phase 3.5; test-writing is never silently skipped. **`RUN_FAILED` is about the suites that were *run*, not the ones that were *detected***, which are two different sets wherever a `command_hint` narrowed the run (`dev-workflows:test-baseliner` capture step 4), and a suite that started, finished, and printed output the parse table does not recognise is `RUN_FAILED` without having failed to start at all
- Phase 3.5 verifies against the captured baseline before the workflow is considered complete, and **names what it did not cover rather than assuming it**: a suite that could not run at either end (verify `PARTIAL`) is recorded in `### Deferred items` and the run continues; a comparison that could not be made at all (`RUN_FAILED` / `COMMAND_NOT_FOUND`) is surfaced, never read as a pass, and accepting it finishes `clean_finish: false`, so any pull request it opens carries the DO-NOT-MERGE banner; and a run whose Pre-Phase 3.5 capture returned `COMMAND_NOT_FOUND` **or `RUN_FAILED`** carries a `test_decision: skip` from that prompt, taken before any edit and while a baseline could still have been taken — **the gate being the recorded decision, never the baseline's `Framework` field**, which is why a `RUN_FAILED` capture (whose `Framework` names the suites it could not run) reaches this completion too. **That skip has two provenances and they finish differently**, stated in `.claude/rules/dev-workflows-tests.md` § Test-writing requirement (the Pre-Phase 3.5 skip bullet). Either way it is scoped to steps 4–6: the lint and build of step 3 still run, because "Skip tests for this run" is what was asked. A test the run itself wrote and that fails is in **none** of those: it is a New failure, which moves no `test-baseliner` status, and Phase 3.5 reads that list beside the status precisely so it cannot pass as one ([why](../../docs/maintainers/rationale.md#implement-phase-3-5))
- Multi-source input (more than one distinct repo, counted by top level, or any folder input — a specs folder or a spec/design folder) floors classification at SIGNIFICANT (overridable at plan approval) and triggers the Phase 1.7 fan-out scan
- The fan-out reads the resolved folder and runs per-repo `code-scanner` (single response, cap 4 concurrent); its synthesized summary feeds the planner instead of the single Explore subagent. A companion run, and a tasks-only run — a keyed run whose only work is its Phase 1 read-back tasks: no prose or spec token of its own, and a block of the unit's `implementation.md` already naming this repository — take the scan's themes from those tasks' changes alone, the folder still read as their context, and a tasks-only run prints one line naming that narrowing and its opt-out, a description of the run's own
- A theme round 1 leaves inconclusive — `partial`/`absent`/`error`, or two scanners each naming the other's repo — gets ONE narrow round 2 seeded with round 1's verified anchors (`classification.md` §8.5, cap 4, no round 3). A theme still unresolved after round 2 is named in the summary's `## Unresolved` section and carried into the plan's risks; it is NEVER flattened into an ordinary gap, because a gap asserts absence while an unresolved theme asserts only that the scan could not tell
- A referenced directory that is missing or unrecognized is surfaced, never silently skipped
