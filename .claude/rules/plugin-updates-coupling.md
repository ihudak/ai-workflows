# Plugin updates — which plugins to update together

Loaded when a plugin's `plugin.json`, the marketplace catalog or a plugin's `CHANGELOG.md` is read — where a release's version is bumped and its coupling bullet written — and read before writing an update command for someone to run (`.claude/rules/plugin-updates.md`, which holds the rest of the update rules). Split out of that file to keep it under 20,000 characters; evidence is in `docs/maintainers/rationale.md`. The bullets up to `workflows-core` 1.45.0 continue in `.claude/rules/plugin-updates-coupling-history.md`, which shares these `paths:` and loads with this file; read both.

**A release that relies on another plugin's newer text gets a bullet here**, naming the versions to install together and what each side does wrong beside an older other side, in both directions where both mislead. A batch that changes a `workflows-core` reference a dependent cites adds one (`docs/superpowers/reviews/2026-10-26-fix-batches.md`, *How to run a batch* step 6).

## Releases to update together

- **Update `workflows-core` 1.47.0 with `security-workflows` 0.4.0**: the reference states the checks and the follow-up clause only 0.4.0's `register.py` applies, so either one alone leaves the two disagreeing.
- **Update `workflows-core` 1.48.0 with `product-workflows` 3.38.1**: 1.48.0 describes 3.37.0's lanes and 3.38.0's picker and archives; 3.38.1's label cites 1.48.0's picker rule.
- **Update `workflows-core` 1.51.0 with `dev-workflows` 4.34.0 and `product-workflows` 3.42.0**: `/design`'s and `/specify`'s new overlap reads before their play-backs, and the inline-fix steps of `/design`, `/specify`, `/create-prd`, `/create-ard`, `/prd-proposal` and `/brd-proposal`, cite `grilling-technique`'s *What a requirement overlaps*, which 1.50.0 lacks — though each new read states its own first kind and runs that part all the same. The reverse leaves two live instructions at odds: 1.51.0 reads every inline edit and every gate against five kinds, where an older fix step of those six commands names a narrower set.
- **Update `workflows-core` 1.52.0 with `product-workflows` 3.43.0 and `dev-workflows` 4.35.0**: `/epics` makes the offer to apply open findings that only 1.52.0's `escalation-rules` lists it for, and `/specify` and `/implement` restate 1.52.0's `epic-picker` cap, so a mixed install holds two caps that disagree on a PRD of two to four Epics.
- **Update `workflows-core` 1.56.0 with `docs-workflows` 1.24.0**: `/document` carries its own copy of `source-truth` §7.3's per-discrepancy array, and `/release-notes` presents it, so beside an older `workflows-core` the two commands recommend *Document as actual (code)* and hold the release on *Document as intended (spec)* while the reference they load recommends the intended phrasing and holds nothing — two live instructions that disagree. The reverse is the same disagreement the other way: 1.56.0 tells an older `/document` and `/release-notes` to hold a release they never mention, beside a copy that still recommends the intended phrasing; and an older `/document` asks a `(not verifiable)` row the actual-code choice, which has nothing to write.
- **Update `workflows-core` 1.57.0 with `product-workflows` 3.46.0**: 1.57.0's `grounding-format` makes `consumed_by` an add-only list and fixes the `baselines.md` layout, its `pre-lint` gains a specs-tree branch 2 (1.56.0's branch 2 is the tracker's), and its `code-scanner` a coupling list; 3.46.0's commands add to the list, write that layout, wrap a BRD key under the new branch and ask for the coupling list. Mixed, one side writes or wraps what the other's reference forbids, asks for a field the scanner does not return, or overwrites the list with one name.
- **Update `workflows-core` 1.58.0 with `product-workflows` 3.46.1 and `dev-workflows` 4.39.1**: 1.58.0's row B′ also stops where the run's own branch changed the path too, which the B′ register stops of an older `/create-prd`, `/create-ard` or `/specify` misstate. An older `/conformance` says a squash near a change reads unmerged, false under 1.58.0's content test; 4.39.1's describes that test, which an older `workflows-core` lacks.
- **Update `workflows-core` 1.59.0 with `dev-workflows` 4.39.2, `product-workflows` 3.47.0 and `docs-workflows` 1.25.0**: 1.59.0's `followup-emission` §7 presents *Select some (you'll be prompted for the row numbers)* where an older `/implement`, `/ready`, `/epics`, `/document` or `/release-notes` restates the option as `select`, and the reverse pairs an older §7's bare `select` with a newer command's relabelled restatement — two live instructions that disagree either way. And the newer commands' *Cancel ends the run* sentences, and the missing-reason picker's way back lean on 1.59.0's §0, which keeps a two-option array whose other option the prose handles, and on its stop rules' stated *Cancel*: beside 1.58.0, whose §0 says a text answer is never asked through a picker built for it, those arrays contradict their reference; beside older commands, 1.59.0's §0 asks for handling an older command's `Cancel` does not state, and its closed-vocabulary list describes a missing-reason `Cancel` that returns to the four options where the older `/brd-reconcile` leaves it unhandled.
- **Update `workflows-core` 1.59.1 with `dev-workflows` 4.40.0 and `product-workflows` 3.48.0**: 1.59.1's *Required path environment variable unset* names `/epics` Phase 0 step 0a and seven other *Set SPECS_PATH* sites as its citers and says no command carries a typed path on its own terms, which an older `/design`, `/ready`, `/conformance`, `/create-prd`, `/update-prd`, `/create-ard` or `/specify` still does, and an older `/epics` has no such step. The newer commands cite a rule 1.59.0 already holds.
- **Update `workflows-core` 1.60.0 with `security-workflows` 0.5.0**: 1.60.0's `security-register-format` §2 states the `reserved_moves` key that only 0.5.0's `register.py plan` prints, so beside 0.4.0 the format names a key no plan carries and a run reports no reserved move. The reverse pairs 0.5.0's `register.py` and its scan's 7.1, which report `reserved_moves`, with an older §2 that says nothing of them — the format and its only writer disagreeing on what `plan --reserve-dir` reports.
- **Update `prose-style` with `docs-workflows` past 1.1.3** (`claude plugin update prose-style@shipwright`): beside a `prose-style` older than 0.4.0, `/release-notes` records its style check `DEGRADED`.
