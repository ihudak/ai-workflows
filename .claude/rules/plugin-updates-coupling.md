# Plugin updates — which plugins to update together

Loaded when a plugin's `plugin.json`, the marketplace catalog or a plugin's `CHANGELOG.md` is read — where a release's version is bumped and its coupling bullet written — and read before writing an update command for someone to run (`.claude/rules/plugin-updates.md`, which holds the rest of the update rules). Split out of that file to keep it under 20,000 characters; evidence is in `docs/maintainers/rationale.md`. The bullets up to `workflows-core` 1.95.1 continue in `.claude/rules/plugin-updates-coupling-history-5.md` (1.92.0 to 1.95.1), `.claude/rules/plugin-updates-coupling-history-4.md` (1.84.0 to 1.91.1), `.claude/rules/plugin-updates-coupling-history-3.md` (1.75.0 to 1.83.1), `.claude/rules/plugin-updates-coupling-history-2.md` (1.59.0 to 1.74.0) and `.claude/rules/plugin-updates-coupling-history.md` (1.39.0 to 1.58.0), which share these `paths:` and load with this file; read all six.

**A release that relies on another plugin's newer text gets a bullet here**, naming the versions to install together and what each side does wrong beside an older other side, in both directions where both mislead. A batch that changes a `workflows-core` reference a dependent cites adds one (`docs/superpowers/reviews/2026-10-26-fix-batches.md`, *How to run a batch* step 6).

## Releases to update together

- **Update `workflows-core` 1.96.0 with `product-workflows` 3.84.0**: beside an older `workflows-core`, which holds no `threat-intake` reference, 3.84.0's `/create-ard` fails closed: on every run that checks the model its folder holds, at Phase 4.3 step 3, it reads no design and no record, prints `Threat model: threats sent back not read — update workflows-core`, and asks the question it asked before, so no threat sent back reaches the architect. Update `workflows-core`.
- **Update `product-workflows` 3.84.0 with `dev-workflows` 4.70.0 or `workflows-core` 1.96.0**: beside an older `product-workflows`, 4.70.0's `/conformance` and 1.96.0's Dev lane send the architect to `/product-workflows:create-ard <KEY>` for a threat returned, taken by no design or open on a decision, with no caveat, and 4.70.0's Phase 6 prints `/product-workflows:create-ard reads this record only on the default branch — …`, naming a read the older `/create-ard` does not make: it lists none of those threats — the misleading direction, which nothing detects. And 1.96.0's `threat-model-format`, which that command loads, says a refine lists them, and its `phase-handoff` that the command reads each record and design — two live instructions at odds. Update `product-workflows` with either.
- **Update `dev-workflows` 4.70.0 with `product-workflows` 3.84.0 and `workflows-core` 1.96.0**: beside an older `dev-workflows`, `/conformance` still ends its line for each of those three states `No command re-disposes a live threat that is not stale yet: …`, though 3.84.0's refine re-disposes them; still sends a stand-alone `Returned` entry behind a threat the architect re-disposed, superseded or withdrawn to `/create-ard`, whose refine lists nothing for it, where 4.70.0 sends it to the Dev's `/dev-workflows:design`, which proposes the entry's withdrawal; and prints no line above its array for a declined record a refine reads, where 1.96.0's `phase-handoff` says it does. Its routes and 1.96.0's Dev lane, which it loads, disagree — two live instructions at odds — as do 4.70.0's and an older `workflows-core`'s lane and `_conformance.md` register row. Update `dev-workflows`.
- **Update `workflows-core` 1.96.1 with `docs-workflows` 1.41.0**: beside an older `workflows-core`, 1.41.0's `/document` and `/release-notes` read the repository that holds the documentation by path, while the `implementation-format` §4 they load says the scan never reads the docs repository and counts as scanned every non-merge commit — two live instructions at odds, the command's own text and `key-discovery.md` deciding what the run passes. The reverse: an older `docs-workflows` beside 1.96.1 leaves that repository out whole where `implementation.md` does not name it — and `/release-notes` reads a subfolder root's repository whole — while 1.96.1's §4 describes a path rule the installed script does not apply: wording at odds, and no run breaks that did not before. 1.96.1 carries 1.96.0 and everything before it, and 1.41.0 carries 1.40.0, so the 1.95.1 bullet applies to this pair too — never `docs-workflows` 1.41.0 beside a `workflows-core` below 1.94.0 — and the three bullets naming 1.96.0 apply to 1.96.1: beside a `product-workflows` older than 3.84.0 or a `dev-workflows` older than 4.70.0, update that plugin with it. `dev-workflows` 4.70.1 changes one page sentence, which describes 1.41.0's scan: it needs neither release, nor they it, and it carries 4.70.0, so the two bullets naming 4.70.0 apply to it.
- **Update `workflows-core` 1.97.0 with `docs-workflows` 1.43.0**: beside an older `workflows-core`, 1.43.0's `doc-reviewer` row excepts `unit:` and `evidence:` by a `doc-structure-conventions` §1 paragraph that core lacks — two live instructions at odds, so a review may grade a `/docs-write` page's `unit:` MAJOR; its `cost-emission` §8 and `feedback-emission` §2 name no `/docs-write`, so the cost entry waits in pending; and its `command-namespaces.json` lacks the command. Update both. The reverse names a command not installed: harmless. `dev-workflows` 4.70.2, `product-workflows` 3.84.1 and `prose-style` 0.8.4 change prose and pages only: none needs these releases, nor they it.
- **Update `prose-style` to 0.8.0 or later with `product-workflows` 3.57.0**: 3.57.0's `/epics` passes `prose-style-checker` a `dialect_files` input, which only 0.8.0's step 1e reads; an older checker infers no dialect at all and holds the Epics to the baseline's American spelling, raising every house British spelling the PRD uses as a violation — the NITs 3.57.0 set out to stop. An older `/epics` beside 0.8.0 passes no `dialect_files`, and 0.8.0 infers from the drafts alone, as before.
- **Update `prose-style` with `docs-workflows` past 1.1.3** (`claude plugin update prose-style@shipwright`): beside a `prose-style` older than 0.4.0, `/release-notes` records its style check `DEGRADED`.
