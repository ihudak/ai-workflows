# workflows-core — plugin facts, shared authorities, workflow map

Loaded when a file under `plugins/workflows-core/`, or any plugin's command or agent file, is read: the consumer sets of the core authorities below and the core agents' caller lines change when a command or agent in another plugin does. Repo-wide rules are in `CLAUDE.md`; evidence is in `docs/maintainers/rationale.md`.

Split out for the 20,000-character budget: the git authorities (`specs-repo-git`, `phase-handoff`) and the specs-repo git invariants → `.claude/rules/workflows-core-git.md`, with `read-only-repos` and the `phase-handoff` authority split out of that in turn → `.claude/rules/workflows-core-read-only.md` and `.claude/rules/workflows-core-handoff.md`, all of which also load with every command, reference and agent file: every `$SPECS_PATH` writer, its references and its agents invoke those entry points. `instruction-file-maintenance` binds hand edits to `CLAUDE.md` and is stated there, in § Editing discipline.

Split out for the same budget: the `finding-triage` authority → `.claude/rules/workflows-core-triage.md`, which loads with that reference and with every command and agent that cites it; the `bounded-run` authority and the copied-scripts rule → `.claude/rules/workflows-core-bounded-run.md`, which loads with every copy of `scripts/bounded.py`, `scripts/tree-snapshot.py` or `scripts/run-folder.py` and every command, agent and reference file; the `run-folder` authority and its invariants → `.claude/rules/workflows-core-run-folder.md`, which loads with every copy of `scripts/run-folder.py` and every command, agent and reference file; the `model-routing/classification` authority and its callers → `.claude/rules/workflows-core-model-routing.md`, which shares this file's `paths:`, since its callers change when a command or agent in another plugin does; and the `implementation-format` authority → `.claude/rules/workflows-core-implementation-format.md`, which loads with this file's `paths:` and every reference file, since commands, agents and references in other plugins cite it.

## Plugin facts

`workflows-core` carries forty-four reference files (`find plugins/workflows-core/references -type f | wc -l`), the parts of those that load by part, and `phase-handoff`'s three entry-point files, `require-on-main`'s, `branch-check`'s and `handoff-to-main`'s, generated under `reference-parts/` and never edited (`.claude/rules/gates-reference-parts.md`), thirteen agents (`adr-drafter`, `answer-applier`, `architecture-grounder`, `code-scanner`, `defect-reporter`, `doc-fixer`, `docs-grounder`, `frame-describer`, `impl-maintenance`, `overlap-reader`, `promotion-scout`, `question-planner`, `session-analyst`; `ls plugins/workflows-core/agents | wc -l`), five bundled skills (`ls -d plugins/workflows-core/skills/*/ | wc -l`: `model-routing`; `agent-file`, which prints a `workflows-core` agent's file for another plugin's command to save its dispatch (`run-folder`); `specs-git`, which runs `scripts/specs-git.py` for `specs-repo-git`'s `specs-preflight` and `commit-artifacts`, a run's start and end, and keeps the state the two share in a record outside every repository (`.claude/rules/workflows-core-git.md`); `weakness-classes`, which runs `scripts/weakness-classes.py` for a command, never an agent, and hands back the path of its JSON — the security registers' weakness classes, `security-register-format` §7 — passing no argument value that holds a character outside `[A-Za-z0-9._:/@+=-]`, and its flags only in one order, origins last; and the `reference` loader, which reads a whole reference — executing any entry point its caller names — or, on one that loads by part, the part its caller names, or, for `phase-handoff require-on-main`, `phase-handoff branch-check` and `phase-handoff handoff-to-main`, that entry point's own generated file, which also serves a citation of a section it holds from its text or the whole reference's wherever the run has read either, else by being read in a `##` section requesting it; anywhere else the loader reads the whole reference — its entry-point rules kept out of its body, in `skills/reference/entry-files.md`, which a request on `phase-handoff` reads with or before its other reads — save its one routing exception: `specs-repo-git specs-preflight` and `specs-repo-git commit-artifacts` go to `specs-git`, reading no reference, and a citation of `specs-repo-git` in a command's own start or end step, or of its §3.2 run key set, §5 notices or §6 outcome lines anywhere in a command's own text, is served by that skill's text and the script's output, every other request on it — that skill's fallback among them — reading the whole reference, as a request on any other reference does; the loader's paragraph on `specs-repo-git` holds that scope), the cost, status-line, session-branch, specs-git (with its two modules, `specs_git_state.py` and `specs_git_lines.py`), lineage, bounded-run, tree-snapshot, run-folder and weakness-classes scripts under `scripts/` (with their two JSON maps), and seven family-meta commands — `/feedback`, `/prompt`, `/prompt-brainstorm`, `/prompt-grill-me`, `/statusline`, `/frames` and `/diagnose-session` (`ls plugins/workflows-core/commands | wc -l`).

It ships three hooks — `notify-done`, `test-notify` and `statusline-refresh`, all session-wide rather than command-scoped, which is why they live in `workflows-core`: every family plugin declares `workflows-core`, so one copy serves everyone.

The host installs `workflows-core` alongside any of the four family plugins that name it, and every pipeline command loads at least one core reference in its first phase — the reason the tier-1 dependency rule is what the family wants.

## Docs tree

`workflows-core` carries 19 pages (`find plugins/workflows-core/docs -name '*.md' | wc -l`) — `docs/README.md` (the index), `getting-started.md`, `workflow.md`, `family-map.md` and `roles-and-phases.md`, 7 command pages under `docs/commands/` (`ls plugins/workflows-core/docs/commands | wc -l`) and 7 reference pages under `docs/reference/` (`ls plugins/workflows-core/docs/reference | wc -l`). Only `frames.md` and `diagnose-session.md` draw a flow: the other five commands log or set up.

## Authorities

`plugins/workflows-core/references/run-flags.md` is the **single source of truth** for the three run flags every applicable command accepts — `--skip-costs`, `--skip-feedback`, `--enforce-model=<model>` — their `$WORKFLOWS_SKIP_COSTS` / `$WORKFLOWS_SKIP_FEEDBACK` / `$WORKFLOWS_ENFORCE_MODEL` environment defaults, the model-alias table with the Haiku rows its `haiku` alias resolves against, the `strip-run-flags` entry point that resolves each flag's applicability and builds the `run_flags` record a command's later steps read, and the `skip-cost` entry point that advances the cost checkpoint and drops any deferred claim without ever loading `cost-emission.md` — and §7's rule that every `mktemp` a run executes runs with `TMPDIR` set to the session's scratchpad directory, where the session names one that exists, save for a file a process outliving the session goes on writing, such as a server's log — and §8's `$WORKFLOWS_FABLE_ESCALATION`, the setting for `classification` §4's `HIGH-RISK` Fable escalation, which is no run flag: `/implement` alone reads it, at its Fable escalation guard and on a resume, and `strip-run-flags` never does, so it adds no `run_flags` member and no `Run flags:` line. It owns the three flags' consumer sets, each re-derived from the running command's own body rather than by a runtime grep (§3 step 3), and re-counted with the maintainer recipe beside each: `--skip-feedback` applies to 31 commands (`grep -l 'workflows-core:impl-maintenance' plugins/*/commands/*.md`), `--skip-costs` to 33 (`grep -l 'emit-cost' plugins/*/commands/*.md`, 31, plus `prompt-brainstorm.md` and `prompt-grill-me.md`), and `--enforce-model` to 32 (`grep -l 'workflows-core:model-routing' plugins/*/commands/*.md`).

`plugins/workflows-core/references/source-truth.md` is the **single source of truth** for the Implementation-vs-Description discrepancy-escalation protocol. It is consulted by `doc-planner`, `doc-writer`, `doc-reviewer`, `release-notes-writer`, `risk-planner`, `claim-reader` — which applies §3 and §4.2's step 4 as `/docs-verify` hands them over, holding no `Skill` tool of its own — and `/release-notes`, which runs the discrepancy escalation itself to verify user-visible claims (option lists, UI labels, menu paths, defaults, counts, mode names) against the shipped source code, and defines the escalation protocol when a written description and the source disagree (Phase 5.8 in `/document` (keyed mode)). **Its §7.8 is the one authority on a decision a `/dev-workflows:conformance` record already holds**: which records a run reads (from the working tree, as data; a malformed one set aside like an unreadable one), which entries are open (never one whose `document:` names `design.md`, a mitigation the design owns), the exact-identity match of a claim to an entry, which of two entries on one claim wins (`final` over `proposed`; between equals `fix-code`), the mapping (`amend-document` or `accept` → `document-as-code`, an open `fix-code` → `skip-and-report`, none of them drafting a gap or holding a release), and how far the code has moved since. `/document` (Phase 3, and Phase 5.8 step 0) and `/release-notes` take a recorded decision by it in place of asking; `dev-workflows:conformance-format` §6 and `docs-workflows:release-note-types` §8 cite it rather than keep a copy; and `/dev-workflows:ready`'s *Delivery verified* test, which maps no decision, is its own (`.claude/rules/dev-workflows-conformance.md`), as is `/product-workflows:create-ard`'s test for a threat open on a decision, which maps none either (`workflows-core:threat-intake`; `.claude/rules/threat-model.md` invariant 11).

`plugins/workflows-core/references/prose-formatting.md` is the **single source of truth** for output line-wrapping — never hard-wrap prose; write each paragraph/prose block as one unbroken line, so Obsidian and IntelliJ Idea soft-wrap it for reading and a straight copy-paste into a tracker, a review tool or a chat needs no manual cleanup. Consumed by every authoring command/agent that writes prose — `grep -l prose-formatting plugins/*/commands/*.md plugins/*/agents/*.md` lists them. ([why](../../docs/maintainers/rationale.md#recipe-returns-wrong-answer))

`plugins/workflows-core/references/doc-structure-conventions.md` is the **single source of truth** for three product-docs authoring conventions: the traceability boundary (a rendered page carries no key, PR URL, or provenance comment — that lives in the commit message and the run handoff only), callout scope and adjacency (a callout sits with the option it qualifies, in the lead-in only when it spans the whole set), and component-pattern fidelity (reuse an area's established content component for a recurring content shape instead of an ad-hoc structure). Consumed by `/document`, `/docs-write`, `/docs-verify` and `/epics`, and by `doc-planner`, `doc-writer`, and `doc-reviewer`.

`plugins/workflows-core/references/document-lineage.md` is the **single source of truth** for the lineage record — the class its paths and blobs are held to before a command is built from one (§1) included — when an upstream counts as moved, the kind table (`scripts/lineage-kinds.json`) and the `record` and `upstream-check` entry points; `scripts/lineage.py` runs them.

`plugins/workflows-core/references/components.md` is the **single source of truth** for what a **component** is — a repository, or a set of paths inside one — and its id; `enumerate-components`, which proposes a repository's modules from what it declares and nothing else; the **multi-component test** and its three sources, of which the ARD's `components:` and an `/epics` run's confirmed set are sets a target can be checked *in*; the **ride-along** rule for same-repository deploy components; the ARD `components:` entry; and `multi-component-prereqs`, the read-only check `/epics` (at `epics` scope), `/implement` and `/ready` share, which writes nothing, asks nothing and never stops. Its citing files are what `grep -l 'workflows-core:components\|args: "components\|references/components\.md' plugins/*/commands/*.md plugins/*/agents/*.md plugins/*/references/*.md` lists; `epic-reviewer`, `design-reviewer` and `readiness-reviewer` apply its rules from their briefs without loading it.

`plugins/workflows-core/references/question-budget.md` is the **single source of truth** for how the BRD route asks people questions — the value test, the budget, the question shape, merging, ranking, strategic sittings, applying answers forward, the tail table, the end-of-sitting list, the account, the registry — and for §13's plain-text block for the customer's prompt. `question-planner` and `answer-applier` follow it, reading it by path.

## Workflow map

The `workflows-core` command's line of the family workflow map, the logging commands' note, and the caller lines of the agents `plugins/workflows-core/agents/` ships. In the `## Workflow map` blocks of `.claude/rules/*.md`, agents marked `(workflows-core)`, `(docs-workflows)`, or `(product-workflows)` ship from a plugin other than `dev-workflows`, invoked as `subagent_type: "<plugin>:<agent>"`.

```
/diagnose-session (core) → [problem intake: one question at a time; nothing is read before the user answers] → locate the session's transcripts (`workflows-core:session-diagnosis` §2) → case.md → [session-analyst×1 per dimension (all seven, or those named), in parallel; repeated-work, stumbles, claims-and-evidence split past 20,000 lines, where run] → report.md, outside every repository → a ready-to-run /feedback line where the family was involved   (its only specs-repo write is its cost entry; no maintenance agent, never a fix)
/frames (core)       → [resolve-address on the specs tree — any kind: design/ is reserved in BRD, PRD and Epic folders] → list each design/<frame-set>/ → [frame-describer×1 per set, cap 40 frames per run] → rebuild each index.md per `workflows-core:grounding-format` §6.2 (preserve verbatim / append / drop / one of **two** placeholders — `_no description on record_` where the run never looked, which the next run retries, and `_could not be read: <reason>_` where the describer looked and failed, which it does not, because retrying a frame that cannot be read spends budget a reachable one would have used and never converges) → [handoff-to-main: each index.md, one literal path] → impl-maintenance → commit-artifacts   (indexing only: no design-grounder, no [DG#n], no verifier)
                      └── doc-fixer (workflows-core)            (used by /document, /docs-write, /docs-verify, /epics)
                      └── code-scanner (workflows-core)         (used by /epics, /implement multi-source fan-out, /create-ard, /specify, /update-spec, /design, /idea, /docs-audit, /docs-write, /docs-verify)
                      └── frame-describer (workflows-core)      (used by /frames)
                      └── session-analyst (workflows-core)      (used by /diagnose-session)
                      └── docs-grounder (workflows-core)        (used by /idea, /create-prd, /update-prd, /create-ard, /specify, /update-spec, /epics, /release-notes, /brd-intake, /prd-ground)
                      └── architecture-grounder (workflows-core) (used by /create-ard, /specify, /update-spec, /design)
                      └── overlap-reader (workflows-core)       (used by /design, /specify, /update-spec — the whole-artifact read before the play-back that precedes the first review, and the read after the last review; and /specify's Stage 4 Rule read, scope: rules, before that stage's gate)
                      └── promotion-scout, adr-drafter (workflows-core) (used by /promote-decisions)
                      └── question-planner (workflows-core)     (used by /brd-intake in mode intake, and /brd-interview in modes merge, plan and strategic)
                      └── answer-applier (workflows-core)       (used by /brd-interview)
                      └── impl-maintenance (workflows-core)     (used by 31 of the 40 commands — `grep -l 'workflows-core:impl-maintenance' plugins/*/commands/*.md | wc -l` against `find plugins/dev-workflows/commands plugins/product-workflows/commands plugins/docs-workflows/commands plugins/workflows-core/commands plugins/security-workflows/commands -maxdepth 1 -name '*.md' | wc -l` — all but /docs-profile, /docs-serve, /harvest-decisions, /statusline, /feedback, /prompt, /prompt-brainstorm, /prompt-grill-me and /diagnose-session — replaced by defect-reporter under --skip-feedback)
                      └── defect-reporter (workflows-core)      (used under --skip-feedback by the same commands as impl-maintenance)
```

`/feedback`, `/prompt`, `/prompt-brainstorm`, and `/prompt-grill-me` run `specs-preflight` and `commit-artifacts` like every other command that writes into `$SPECS_PATH` (`CLAUDE.md` § Hard constraints), and have no line of their own in the workflow map because they are single-purpose logging commands rather than pipelines. All four emit a session-cost entry unless `--skip-costs` (`workflows-core:run-flags` §5), inheriting the phase and role of whatever they are correcting (`workflows-core:cost-emission` §7) — but `/prompt-brainstorm` and `/prompt-grill-me` cede the session before they could write one, so each records its labels and the next cost-emitting run in the session writes the entry on its behalf, splitting its own window at the transcript's record of where that run began (§13). In `/prompt-brainstorm` and `/prompt-grill-me` the terminal step runs immediately before their Phase 3, which cedes the session (`workflows-core:specs-repo-git` §4). `/diagnose-session` runs both for its cost entry alone, charged to `plugin-feedback`/`n/a` outright, and has a map line because it dispatches an agent.
