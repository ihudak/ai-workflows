# dev-workflows — `/implement` invariants and the test-writing requirement for code changes

Loaded when `/implement`'s command or docs page, a `test-*` agent or its handoff file, `references/code-handoff.md`, or the test-suite-detection reference page is read. The rest of the `dev-workflows` rules are in `.claude/rules/dev-workflows.md`; repo-wide rules are in `CLAUDE.md`; evidence is in `docs/maintainers/rationale.md`.

The `/implement`-specific invariants, under § Invariants below, were split out of `.claude/rules/dev-workflows.md` to keep that file under 20,000 characters; this file's `paths:` already reach `/implement`'s command file and docs page.

## Test-writing requirement

Any `/implement` invocation that touches source code **must** write at least one test for each new or changed behaviour, **must never complete silently on one that fails**, and **must name in the Phase 5 `### Deferred items` section every test it could not write, could not run, or left failing**. **Only the first clause is bounded, and only by what `test-writer` could not write** — Pre-Phase 3.5's skip on a `COMMAND_NOT_FOUND` capture, where `test-writer` returns its "not detected" report and writes nothing, and every behaviour its `### Notes` names as untested: one it cannot test in isolation (its step 5), or each one, in a changed file no other suite's tests live alongside, where a `hinted` or `declared` command gives it no test to follow (its step 1). `/implement` names each of those in `### Deferred items`. The second and third hold on every **completion**, which is narrower than every path and deliberately so: every `/implement` exit that stops *after* the branch exists produces no Phase 5 report at all — its Phase 4.6 *"Every run"* paragraph enumerates the ones that stop after files were written and says as much in as many words, and the one it deliberately leaves out, Pre-Phase 3.5's **Cancel**, is named in Phase 4.6's own *"Two Cancels are not in that set"* paragraph as stopping after the branch and before the first edit, where the run stops and summarizes and no such report is produced either — so on those there is no `### Deferred items` section for the third clause to hold in, and nothing has completed for the second to be silent about. (No count here on purpose, and not because a count went wrong: the set is `implement.md`'s to enumerate, and a second copy of it in these rules is exactly how two lists come to disagree.) What the section is about is wider than those exceptions, though: the completions that leave **no passing test** behind, and those are **three kinds, exhaustive by construction** — a test is written or it is not; written, it runs or it does not; run, it passes or it does not — so this section needs no census of completions and keeps none. The kinds are: **no test written** (that same `COMMAND_NOT_FOUND` skip, and every behaviour `test-writer`'s `### Notes` names as untested); **a test written but never run** — **four members**, each disposed of in the bullets below: the same skip on a `RUN_FAILED` capture, an accepted unverified run at Phase 3.5 step 5, a suite that could not run at either end, and a runner that silently narrows its own run past the new test; and **a test written, run and still failing**. That last is the one this section was built around: a test the run wrote and that is still failing after the Phase 3.5 fix loop's two attempts is surfaced, and the run continues only on the user's own *"Accept the remaining failures and proceed"*, recorded with their rationale and setting `clean_finish: false` — so any pull request the run opens is a draft carrying the DO-NOT-MERGE banner. The first clause is not made unqualified: that would have to remove **both** escapes a user can choose — that option and Pre-Phase 3.5's *"Skip tests for this run"* — and would leave the clause unmeetable on whatever `test-writer` names as untested, which is the code's or the repository's answer rather than anybody's choice; do not re-propose it without new evidence ([why](../../docs/maintainers/rationale.md#test-writing-requirement)).

- Prefer unit tests; use integration or end-to-end tests only if that is the project's established pattern
- Tests must be meaningful (assert specific behaviour), deterministic, and follow existing project conventions
- **Pre-Phase 3.5's skip is where kind 1's first member and the first of kind 2's four members come from, and it is never a silent one.** Where that capture returns `COMMAND_NOT_FOUND` (no framework detected and no test command the repository declares) **or `RUN_FAILED`** (every suite the capture actually ran aborted with no parseable counts), the run surfaces it and asks before the first edit — while a baseline can still be taken. `test_decision: skip` is that question's logged answer **or the run's own record after two `command_hint` attempts that also failed**, and the two are different decisions: the operator's is typed, carries their rationale, and is honoured without penalty, while the run's carries the last capture failure and sets `clean_finish: false`, because nobody consented to shipping unverified work — nothing was typed and nothing was declined there (`dev-workflows:code-handoff` §2.9). On `COMMAND_NOT_FOUND` `test-writer` returns its "not detected" report and **writes nothing**; on `RUN_FAILED` it writes against the suites the baseline named and those tests are then never run. Either way the Final Report says so
- **Kind 2's third member is environmental and nobody picks it: a Phase 3.5 verify `PARTIAL` whose unrunnable suite is the one this run's tests were written into.** `test-writer` writes against every suite the diff touches, so on a multi-suite repository whose broken stack is that stack, the new tests sit in a suite that produced no counts at either end. Phase 3.5 step 5's `PARTIAL` arm records that suite in `### Deferred items` and the run continues; `clean_finish` stays `true` and no banner is raised, because every suite the baseline *did* cover is green. **Population: narrow** — it needs a multi-suite baseline, one suite unrunnable at both ends, and a diff touching only that stack. It is named because the three kinds above are a closed set and this is one of that kind's four members, not because it is common. **The other three are not read off this one, and they differ exactly where it matters**: the accepted unverified run at step 5 *does* flip the flag, since there the comparison was attempted and failed rather than merely being incomplete; the bullet above's `RUN_FAILED`-capture skip flips it on the run's own record and not on the operator's typed answer; and the fourth is the bullet below. The **third kind** is the one the user *does* pick — a test written, run and still failing, accepted at Phase 3.5 step 6 — and it both flips the flag and raises the banner, which is what the headline paragraph says of it
- **Kind 2's fourth member is the silent one, and it is the reason that kind is spelled out member by member: a runner that narrows its own run past the test `test-writer` just wrote.** The new test never ran and is named nowhere — capture and verify report identically, so `Status: OK` with `### New failures` and `### Missing from run` both empty, and the run completes `clean_finish: true` with an empty `### Deferred items`. **It is the one member of this kind the third clause above cannot catch**, because nothing in the run knows a test was dropped: `/implement`'s `### Deferred items` template has a line for each of the other three and none that this state would fill. **Population: narrow** — it needs an exclusive test committed in the repository *and* a runner that skips rather than aborts on one. Recorded rather than fixed: catching it needs a per-runner guard (`--forbid-only` and its siblings) that `test-baseliner` does not pass today, and passing one would change what the baseline measures ([why](../../docs/maintainers/rationale.md#test-writing-requirement))
- Docs-only changes (`/document`) are exempt from this requirement

## Invariants

### Key invariants for `/implement` specifically

- A keyed run whose working directory is in the specs repository — `$SPECS_PATH` that repository's top level — stops before the preflight: the specs repository is no code repository. A direct run there runs on with a notice, its session files committed on its code branch, which `commit-artifacts` does not push unless the branch's name carries a plugin prefix (`workflows-core:specs-repo-git` §4 step 5), and a specs tree inside a larger repository is left as it was
- Phase 4.6 (`finish-code-branch`) runs **after** Phase 4, never before it — Phase 4's maintenance agents write `README.md`, `CHANGELOG.md`, `CLAUDE.md`, and in-repo memory files into the same repository, so a commit ahead of them ships a partial run. A multi-source run changes code only in the repository it branched; a change another code repository needs is a follow-up (Phase 6's, or named in the stop), never an uncommitted edit there
- Test baseline captured **before** any source edits, using `test-baseliner`
- The test-writing requirement — what `test-writer` must write, its one bound, and what a completion must name — is in `.claude/rules/dev-workflows-tests.md` § Test-writing requirement
- If no test framework is detected — or if every suite the capture actually ran aborted with no parseable pass/fail counts, the other capture that asks — surface that explicitly at Pre-Phase 3.5; test-writing is never silently skipped. **`RUN_FAILED` is about the suites that were *run*, not the ones that were *detected***, which are two different sets wherever a `command_hint` narrowed the run (`dev-workflows:test-baseliner` capture step 4), and a suite that started, finished, and printed output the parse table does not recognise is `RUN_FAILED` without having failed to start at all
- Phase 3.5 verifies against the captured baseline before the workflow is considered complete, and **names what it did not cover rather than assuming it**: a suite that could not run at either end (verify `PARTIAL`) is recorded in `### Deferred items` and the run continues; a comparison that could not be made at all (`RUN_FAILED` / `COMMAND_NOT_FOUND`) is surfaced, never read as a pass, and accepting it finishes `clean_finish: false`, so any pull request it opens carries the DO-NOT-MERGE banner; and a run whose Pre-Phase 3.5 capture returned `COMMAND_NOT_FOUND` **or `RUN_FAILED`** carries a `test_decision: skip` from that prompt, taken before any edit and while a baseline could still have been taken — **the gate being the recorded decision, never the baseline's `Framework` field**, which is why a `RUN_FAILED` capture (whose `Framework` names the suites it could not run) reaches this completion too. **That skip has two provenances and they finish differently**, stated in `.claude/rules/dev-workflows-tests.md` § Test-writing requirement (the Pre-Phase 3.5 skip bullet). Either way it is scoped to steps 4–6: the lint and build of step 3 still run, because "Skip tests for this run" is what was asked. A test the run itself wrote and that fails is in **none** of those: it is a New failure, which moves no `test-baseliner` status, and Phase 3.5 reads that list beside the status precisely so it cannot pass as one ([why](../../docs/maintainers/rationale.md#implement-phase-3-5))
- Multi-source input (more than one distinct repo, counted by top level, or any folder input — a specs folder or a spec/design folder) floors classification at SIGNIFICANT (overridable at plan approval) and triggers the Phase 1.7 fan-out scan
- The fan-out reads the resolved folder and runs per-repo `code-scanner` (single response, cap 4 concurrent); its synthesized summary feeds the planner instead of the single Explore subagent
- A theme round 1 leaves inconclusive — `partial`/`absent`/`error`, or two scanners each naming the other's repo — gets ONE narrow round 2 seeded with round 1's verified anchors (`classification.md` §8.5, cap 4, no round 3). A theme still unresolved after round 2 is named in the summary's `## Unresolved` section and carried into the plan's risks; it is NEVER flattened into an ordinary gap, because a gap asserts absence while an unresolved theme asserts only that the scan could not tell
- A referenced directory that is missing or unrecognized is surfaced, never silently skipped
