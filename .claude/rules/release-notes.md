# docs-workflows — `/release-notes`

Loaded when `/release-notes`' command file or docs page is read, `release-notes-writer`, or `docs-workflows:release-note-types`. Split out of `.claude/rules/docs-workflows.md` to keep that file under 20,000 characters; the plugin's other rules are there.

## Authority

`plugins/docs-workflows/references/release-note-types.md` is the **single source of truth** for the release-note **section map** — the three destinations as three sections, `## Breaking changes` / `## Feature updates` / `## Fixes`, of one `release-notes.md` in the resolved PRD folder, under a heading for the release version, each draft under a scope comment naming the PRD or Epic it was drafted for and every commit its run read — the per-section **draft shape** (label + title + prose, vs one or two bare sentences for `## Fixes`), the per-section prose rules, the deprecation-note rule (end-of-life date required, end-of-support optional), the effective-version rule (§6 — a release named only where the heading cannot say it: a breaking change taking effect in a later release, or a far-off deprecation's date; never invented, never taken from the heading), Change Type sourcing (the PRD's `change_type` → infer), and what a `/dev-workflows:conformance` entry does to the draft (§8 — `fix-code` leaves the claim out, `amend-document` and `accept` word it as shipped). It is consulted by `release-notes-writer`; `/release-notes` cites it for its own invariants but never re-derives the writer's decision. The Change Type is never rendered as text.

## Workflow map

```
/release-notes       → [document-lineage upstream-check per unit, Phase 0, shown before the diff-grounding question — reported, never asks or records] → [run_phase and the `_conformance.md` records in scope, Phase 0 — the stage picks the diff-grounding array, the diffs recommended on a dev run] → read the resolved PRD folder → [each record's open entries, diff grounding on or off — never asked, never re-checked as a discrepancy] → [diff-summarizer×N (parallel, optional)] → [docs-grounder] → [release-notes-writer: resolve destination + shape per destination + source the **Category:** label + detect deprecation + resolve a breaking note's later effective release] → [prose-style-checker → prose-fixer (optional), on a scratch copy, the checker handed the specs repository as the repo whose house-style rules apply] → append the draft to the PRD folder's release-notes.md, under its version and Change Type section, never rewriting an earlier section (destination-shaped Summary; yours to paste wherever release notes are published) → [handoff-to-main: the draft, `prd/` prefix] → impl-maintenance → commit-artifacts
```

## Invariants

### Key invariants for `/release-notes`

- **Zero direct API calls** — the run has no forge URL to resolve in the first place: Phase 3 builds `refs[]` from `implementation.md` and the commit scan, and the opt-in diff grounding reuses `diff-summarizer`, which takes a ref's diff with pure local `git`; all resolution runs against clones under `$REPOS_PATH`; key discovery's optional, read-only `gh search prs` and `gh pr view`, with its own login check (`plugins/docs-workflows/references/key-discovery.md`), and the draft's handoff, on the operator's consent — its authentication check, open-pull-request probe and `gh pr create` (`workflows-core:phase-handoff` §2.6–§2.7) — are its only `gh` calls, and `gh` wraps the API
- The draft is the **authored body only** — for a titled destination a **Category:** label, `### title`, and customer-facing prose; for `fixes` one bare past-tense sentence (two at most). NEVER a key or issue ID, a PR link, a `Change type:` line, or a `{{#internal-note}}` block (the docs automation adds the metadata wrapper)
- The **Category:** label IS the PRD's own `release_notes_category`, used verbatim; absent ⇒ the line is omitted. Change Type is sourced from the PRD's `change_type` → infer, drives destination + shape only, and is confirmed with the user only on a low-confidence inference — by shape and destination, never by enum label
- The Summary is shaped per its destination (breaking → present tense, what breaks, remediation under a literal `**Action plan:**` label; feature update → benefit-led, plus a docs/blog link on a dev-phase run only; fixes → one or two past-tense sentences opening with a past-tense verb, no hedging, no internal terms); exactly ONE Summary per run. No title names a release version, and only a breaking note that takes effect in a later release than its heading names one in its prose — from the source or the user, never invented — or a far-off deprecation's date (`release-note-types.md` §6). A Change Type switch at the Phase 6 prompt re-dispatches the writer
- The run has **no worthiness gate**, and that is a retirement rather than an omission: `relevant_for_release_notes` is retired from `workflows-core:prd-format`, no command reads it, and a value left in an existing PRD is inert ([why](../../docs/maintainers/rationale.md#release-notes-worthiness)). The command refuses only on its address and on what that address needs — `RELEASE_NOTES_NEEDS_KEY` where the prompt carries no positional address at all or one that fails the key grammar, an unset `$SPECS_PATH` on a `<KEY>` (an `@<path>` needs no specs tree and runs on), a stop naming every match where one resolves ambiguously, `SPECS_PATH_INSIDE_TREE` on either address form where `$SPECS_PATH` is set inside the specs tree, the shared re-enter/cancel escalation where one resolves to nothing, and a Phase 0 named stop where an address resolves but leads to no `prd.md` the run can read, or to a PRD folder carrying no key — `RELEASE_NOTES_BRD_NOT_SLICED` on a BRD container, `RELEASE_NOTES_FOLDER_NOT_PLACED` on a folder placed at no level, `RELEASE_NOTES_PRD_NO_KEY` on a PRD folder carrying no key, `RELEASE_NOTES_NO_PRD` on a PRD folder with no `prd.md` or one it cannot read, its remedy following a BRD-route slice's ledger state
- A deprecation carries a deprecation note in the Summary — end-of-life date (required) + end-of-support date (optional); a missing required date becomes a `deprecation_eol` gap the command asks about (never invented)
- NEVER writes into a docs repo; the draft's one destination, `release-notes.md` in the resolved PRD folder, is persistent (never `/tmp`), and the draft is appended to it, never overwriting an earlier section
- Light gate only — `prose-style-checker` (optional, skipped only on the user's own "Skip style check" answer in Phase 1 — `prose-style` is a declared dependency of `docs-workflows`, so the phase never skips itself for want of a plugin); no Opus review, no tests, and no deliverable branch but the `prd/` branch Phase 8's handoff cuts behind the operator's consent (`specs-preflight`, its same-run re-run after a slice key is entered included (`workflows-core:specs-repo-git` §3.5), switches `$SPECS_PATH` only between branches that already exist, and only plugin-created ones — §2.2; it creates no deliverable branch, and besides the `prd/` branch the one branch the run may create there is `session/<identity>`, in session-branch mode, where its session-file commits go — §8.2 — which holds no deliverable and which the checkout never stands on), and no commit of anything in a docs/code repo or the current working directory, where it is not the specs repository. The draft, `release-notes.md` in the resolved PRD folder, is a deliverable: it is committed by that handoff, advisory class (`workflows-core:phase-handoff` §4.0), in the specs repository and nowhere else, and never by the terminal `commit-artifacts` step, which commits ONLY `$SPECS_PATH`'s bounded session-artifact paths (`workflows-core:specs-repo-git` §2.1); under `specs_git: blocked` or `specs_git: misrooted`, or with `$SPECS_PATH` unset on an `@<path>` run, neither commits, and the draft is written and not committed — as it is where the `@<path>` leads outside `$SPECS_PATH`'s work tree, which is offered no handoff
- Diff grounding is opt-in — recommended on a dev-stage run (`run_phase: dev`, resolved in Phase 0 because it picks Phase 1's array), the PRD alone on a PM-stage one; when on, it reuses `$REPOS_PATH` resolution + `diff-summarizer`. A dev-stage run that declines it says in its plan and report how its claims were checked: only through the conformance records, as of their dates, or not against the code at all
- With diff grounding on or off, every `_conformance.md` in scope is read and its open entries shape the draft per `release-note-types.md` §8, the decision a person recorded on each followed and never asked again. `docs-workflows` cannot load `dev-workflows:conformance-format`, so the command states the fields it reads, in Phase 0 and Phase 3, and that reference's §6 names it among its readers: a change to those fields is a change to `/release-notes` too
