# dev-workflows — invariants, workflow map, agent callers

Loaded when a file under `plugins/dev-workflows/` is read. Repo-wide rules are in `CLAUDE.md`; evidence is in `docs/maintainers/rationale.md`.

The `/implement`-specific invariants are in `.claude/rules/dev-workflows-implement.md`, and `/conformance`'s map line and the readers of its record in `.claude/rules/dev-workflows-conformance.md`, both loaded with this file. The test-writing requirement for code changes is in `.claude/rules/dev-workflows-tests.md`, loaded with `/implement`, the test agents and their handoff files, and `references/code-handoff.md`.

## Authorities

`plugins/dev-workflows/references/bug-diagnosis.md` is the **single source of truth** for the bug-diagnosis discipline consulted by `/implement` (Phase 2B), followed by `risk-planner` on `task_shape: bug`, and by `code-writer` where its request carries `scratch_checkout: HEAD`: feedback-loop-first (a red-capable, deterministic repro, minimised, before hypothesizing — on a performance regression, a measurement), 3–5 ranked falsifiable hypotheses, one-variable `[DEBUG-xxxx]`-tagged probes that never write a secret's value, with a mandatory cleanup gate (stripped before the Opus-review diff), a regression test at a correct seam, which run falls on which side of the review gate, and whose it is (`risk-planner`'s first-plan repro on the working tree (a plan-approval **Revise** included); from the first edit until a non-BLOCK review nothing against the working tree, so no check — save the orchestrator's type-check of `test-writer`'s tests — and no repro or probe (a command writing the change rather than checking it is neither), and a probe or the repro only in a scratch checkout of `HEAD` — `code-writer`'s on every dispatch, its first included, and `risk-planner`'s on every re-plan — a bisect the orchestrator's, first, before any edit; after the review the orchestrator's re-run of the repro and the regression test's red-capability check — in a scratch checkout of `HEAD`, inconclusive where it fails on anything but the bug's assertion — the caller's verify the green check), and the confirmed cause named in the run's report and its pull request where step 6 says. It cites `dev-workflows:design-format` `## Seams` for seam vocabulary and pairs with `/implement`'s spec/design-conformance ("converge") check — `code-review`'s conditional 10th dimension, tracing in-scope `[Uxx]`/`[ACxx]`/`[TCxx]` against shipped code.

`plugins/dev-workflows/references/install-time-code.md` is the **single source of truth** for how this plugin installs a dependency without its install-time code; check 21 holds the install references to it.

`plugins/dev-workflows/references/code-handoff.md` is the **single source of truth** for the **code** repo's own git finish — the `finish-code-branch` entry point (§2): gate (§2.1), staging with its three carve-outs (§2.2), commit (§2.3), the consent choice asked once per run (§2.4), push (§2.5), the `gh` capability probe and its fallback (§2.6), the title and body file (§2.7), the base-branch ladder (§2.8) and the move onto that base (§2.8.1) — which each of the three callers makes first (`/implement` Phase 1.4 step 2, `/upgrade` Phase 0.5, `/vuln` Step 1.5), so the base it offers to branch from is the base its pull request targets — the not-clean-finish draft-PR rule (§2.9), and the split-call form a per-unit loop uses (§2.12). It also owns §6, how one unit's uncommitted edits are undone: the snapshot `/vuln` and `/upgrade` take before each CVE or component, and the revert `vuln-fixer` and `upgrade-executor` run from it rather than from `HEAD`, the one working-tree restore its §1 rule 3 allows. Its one structural divergence from `phase-handoff.md` is §1 rule 5: **the commit is prompt-free**, because there the deliverable is already safe on disk and here the work is not safe until it is committed — so only the push and the pull request sit behind consent; the one prompt before a commit is §2.2's secret scan, on a possible secret it cannot dismiss. **It is also the only git reference that stages at repository scope**, deliberately: `specs-repo-git.md` §1 rule 2 and `phase-handoff.md` §1 rule 2 both forbid `git add -A` because those repositories hold many runs' artifacts, whereas here the run branched off a verified-clean tree and the whole diff *is* the deliverable — §1 says so, lest a reader "correct" it either way. Its §2.3 subject is the family's own convention (`workflows-core:implementation-format` §3), not the repo's log, which is where it diverges from the edition it was ported from. Consumed by the three commands that branch a code repo and write into it: `/implement` (Phase 4.6), `/vuln` (Step 3.9, once per CVE), and `/upgrade` (step 6.5 commit per component + step 7.5 push/PR once per batch); `/vuln` and `/upgrade` also take §6.1's snapshot per unit and act on §6.3, and `vuln-fixer` and `upgrade-executor` run §6.2's revert. It never touches `$SPECS_PATH` or a docs repo. The single typed opt-out is `--no-commit` on `/implement` and `/upgrade`; `/vuln` has none.

## Workflow map

The `dev-workflows` commands' lines of the family workflow map — all but `/conformance`'s, which is in `.claude/rules/dev-workflows-conformance.md` — and the caller lines of this plugin's agents.

```
/implement           → [stopped run in the worktree: Resume on a proven tree / Start fresh / Cancel] → [keyed, in the specs repository: stop] → [require-on-main: in-scope spec/design] → [keyed: lineage check; Proceed in implementation.md] → [keyed Epic: multi-component-prereqs at implement scope — its target repository on any PRD, a mismatch an open follow-up for this repository answers is a companion run; on a multi-component PRD also prerequisites and this Epic's contract coverage; a gap asks Stop (Recommended) / continue] → [Phase 1.4, before the code is first read: the run-state file created, unless resumed; clean-tree check; keyed: fetch, then unit-branch — while the unit's PR is open, offer to continue on its branch, or switch to it on a tree with no tracked change; a fresh start moves onto the default branch; no move changing a spec input] → [Phase 1.6 input scale] → (multi-source? → [read the resolved folder → code-scanner×N (parallel, cap 4; a companion or tasks-only run's themes from its follow-up tasks alone) → §8.5 narrow round 2] → synthesis, unresolved themes named) → [risk-planner@Opus plan critique] → [Pre-Phase 3: a branch cut where Phase 1.4 left HEAD, or none on the unit's own] → [code-writer×N, one per step group in plan order, on implementation_model] → test-writer → [code-review@Opus, MODERATE and up; per piece + overall where split] → [triage: verify each finding] → review-fixer → tests (fixes by code-writer) → impl-maintenance → [handoff-to-main: escalated notes in the specs repo, unless run there] → [finish-code-branch: commit + consent-gated push/PR in the code repo] → commit-artifacts
/vuln                → [on base] → vuln-research → vuln-fixer (branch + fix, uncommitted) → [code-review@Opus] → [triage: verify each finding] → review-fixer → [vuln-fixer verify-resume: tests vs the run baseline — reviewed path; the unreviewed path tests inside the first fixer call] → [finish-code-branch: commit + push/PR, per CVE, from the base branch] ⟲ (a commit that does not land ends the loop) → impl-maintenance → commit-artifacts
/upgrade             → [on base] → upgrade-planner → [risk-planner@Opus] → upgrade-executor → [code-review@Opus] → [triage: verify each finding] → review-fixer → [upgrade-executor verify-resume: tests vs the baseline — reviewed path; the unreviewed path tests inside the first executor call] → [finish-code-branch §2.1–§2.3: commit this component] ⟲ (a commit that does not land ends the loop) → [finish-code-branch: push/PR once for the batch] → impl-maintenance → commit-artifacts
```

## Invariants

### Key invariants enforced by all three code-oriented commands

- Branch created before any file is touched (`feat/<slug>` or equivalent) — including `vuln-fixer`, whose branch step precedes its edit precisely so a CVE stopped at a failed gate still has somewhere to commit — save where `/implement` continues on the unit's own branch, which its Phase 1.4 offers and the user chooses: that branch stands before any file is touched too
- The work is COMMITTED on that branch before the run ends — prompt-free, because a commit is local and reversible and an uncommitted implementation is the one loss no later step can undo (`dev-workflows:code-handoff` §1 rule 5). The one shared exception is a secret: every commit's added lines are scanned first (`scripts/secret-scan.py`, §2.2), and a possible secret the scan cannot dismiss is put to the user — stop and leave the work uncommitted, or commit it as not secret — because a secret committed is in the history, and taking it out needs the rewrite §1 rule 3 forbids. A hit's value is never printed, only a masked preview. Pushing it and opening a pull request sit behind §2.4's single consent choice, asked once per run and reused for every later branch in it. A run that did not end clean is still committed and still *offered* for push under that same choice — which a `clean_finish` differing from the one that choice was answered under puts again, **in either direction** (§2.4's first re-ask trigger; [why](../../docs/maintainers/rationale.md#not-clean-finish-reask)), so a decline is a real answer there and not an anomaly; what the flag itself changes is only the pull request — a draft whose body leads with a DO-NOT-MERGE line, where one is opened at all, and one already open that the push updates, after either push answer, turned back into a draft with that line posted on it as a comment (`code-handoff`'s *A run that did not end clean*, **cited by heading rather than by number**) ([why](../../docs/maintainers/rationale.md#code-handoff-citation))
- Opus review gate runs **before** tests for `SIGNIFICANT` / `HIGH-RISK` tasks — and, on `/implement` alone, for `MODERATE` ones too (its Phase 3A step 6); `/vuln` and `/upgrade` review only from `SIGNIFICANT` up
- `code-review`'s findings are triaged by the orchestrator before `review-fixer` sees them (`workflows-core:finding-triage`) — each finding verified at the location it names, every dismissal recorded with a reason that disposes of that finding's own claim, a finding triage cannot settle, and that would be MAJOR or BLOCKER if true, recorded as unverified with what would settle it, and the fixer handed **survivors only**; a survivor that fails the patch gate is surfaced for a human decision instead of patched
- `review-fixer` handles surviving BLOCKER and MAJOR findings; at most one `review-fixer` cycle per reviewed artifact, and none after its re-review (`workflows-core:finding-triage` § On re-review) — save on `/implement`, whose rule `.claude/rules/dev-workflows-implement.md` states
- Every file path these commands hand to `risk-planner`, `code-review`, `code-writer`, `test-writer`, `review-fixer`, `vuln-fixer`, or `upgrade-executor` carries a read-failure tier, stated by that agent where it takes the input (`dev-workflows:context-management`) — an unreadable **evidence** input is a hard stop and is NEVER regenerated by other means (a resume that re-derives its own input is exactly the failure the contract exists to prevent); an unreadable **context** input degrades to absent and the output records the degradation
- A reviewer handed `claims_file` reads it ONLY after every other dimension is complete — the deferral is what makes the falsification independent, and it is bought structurally (a path, read late) rather than by instruction
- `workflows-core:impl-maintenance` runs post-batch and edits nothing: it returns a Lessons Learned report. Of the three, only `/implement` runs maintenance agents that edit, before `finish-code-branch`

### Multi-component PRDs (`workflows-core:components`)

- On a multi-component PRD the flat PRD-level `specification.md` is a requirements source: `/design <PRD>` and `/implement <PRD>` do not take it as one unit (Epic picker; with no specified Epic `/design` stops for `/specify` or recommends `/epics`, `/implement` recommends `/epics` at 0 Epics, and taking it whole is an override both offer only at 0 Epics), and `workflow-states.md`'s *Ready for Implementation* expects no PRD-level `design.md` — save where the override built it whole (a PRD-level `design.md` or implementation record), which reads the single-component clause
- `/design` keeps a targeted Epic's design in its target's repository; a second repository is a `Target span` risk `design-reviewer` flags. `/implement`'s Phase 1 check and `/ready`'s Phase 3(d) run one definition, `multi-component-prereqs` (§6), which writes nothing and never stops — the caller decides

### /design and /ready

- `/design` Phase 5 offers a three-take `interface-designer` fan-out (one take per constraint — minimise the interface, maximise flexibility, optimise for the most common caller) on a contested interface — any `dev-workflows:design-format` `## Seams` signal; `--design-twice` forces the fan-out itself, skipping the offer, even with no signal fired (a user who typed the flag has already answered what the offer would ask); the offer's two options carry no `(Recommended)` marker, because the list is only shown once the interface is already contested; declining costs nothing — the interview continues and `design.md`'s unconditional `### Alternatives considered` requirement is satisfied by hand
- `/ready` is **read-only about status** — it **derives the workflow phase from the artifacts present** and verifies the ARD/spec/design justify it, comparing an operator's `--claimed` status against that derivation where one is given; there is no workflow phase recorded anywhere for it to read — `prd.md`'s own `status:` is the document's authoring state, never read as one (the status peek D8 retired had no source in `$SPECS_PATH` and `ready.md` forbids reconstructing it), and it never sets one and never reads a tracker, and never stops on an unmerged artifact (`workflows-core:phase-handoff` §3.3 rows D/E, a readiness finding capping the verdict at `PARTIAL`) or a missing one (row F, delegated per §3.4, recorded as a coverage gap); it commits the deliverable or the `_readiness.md` snapshot only through `phase-handoff.md` §4.3's consent choice via `handoff-to-main` (§2), never automatically (its terminal `commit-artifacts` step commits ONLY `$SPECS_PATH`'s bounded session-artifact paths, `workflows-core:specs-repo-git` §2.1)
- `/ready` decides the PRD ladder's one optional rung, *Delivery verified (optional)* (`workflow-states.md`, *An optional rung*), from the PRD folder's `_conformance.md` and the PRD tree's `implementation.md` blocks, on a PRD- and an Epic-level run alike (Phase 1 step 2b): the record read from `<default-ref>` by `git show`, never the working tree, and gated by no `require-on-main`, so an unmerged or missing record is neither row D/E's finding nor row F's coverage gap. A record passing that step's six conditions — the last, no block later than it, by instant if both carry one, else by date, a same-day block then not counted — lifts a PRD derived at *Implementation* to the rung; any other PRD passes it over — never a straddle, never a finding, never asked about — and keeps the phase the mandatory rungs give it, with its `Delivery:` line as a note (`not verified — <reason>` where the record does not settle the rung) that never caps or lowers the verdict. Where the PRD is at *Implementation* or later and delivery is not verified, the Next step adds `PE → /dev-workflows:conformance <PRD>`, whatever the verdict. `--claimed` names the rung with or without its `(optional)` suffix at PRD altitude; at Epic altitude, whose ladder has no such rung, either spelling is re-prompted
