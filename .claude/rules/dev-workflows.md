# dev-workflows — invariants, workflow map, agent callers

Loaded when a file under `plugins/dev-workflows/` is read. Repo-wide rules are in `CLAUDE.md`; evidence is in `docs/maintainers/rationale.md`.

The test-writing requirement for code changes is in `.claude/rules/dev-workflows-tests.md`, loaded with `/implement`, the test agents and their handoff files, and `references/code-handoff.md`.

## Scope

Three extractions took content out of `dev-workflows` and none is coming back: the guideline-review commands `/api-guideline-reviewer` and `/guideline-reviewer` to `plugins/guideline-reviewers/`, the documentation commands to `plugins/docs-workflows/`, and the product-definition commands — the idea→PRD→ARD→specification ladder, `/epics`, and the six-command BRD-to-PRD route — to `plugins/product-workflows/`. The one command that did use `prose-style` (`/epics`) moved out with the rest.

## Docs tree

`dev-workflows` carries 20 pages — `docs/README.md` (the index), `getting-started.md`, `workflow.md` and `roles-and-phases.md`, 5 per-command pages under `docs/commands/`, and 11 reference pages under `docs/reference/` — with the plugin README reduced to a role-indexed pointer table. Re-derive with `find plugins/dev-workflows/docs -type f -name '*.md' | wc -l`, and the same command scoped to `plugins/dev-workflows/docs/commands` and `plugins/dev-workflows/docs/reference` for the two subtotals.

## Authorities

`plugins/dev-workflows/references/bug-diagnosis.md` is the **single source of truth** for the bug-diagnosis discipline consulted by `/implement` (Phase 2B) and followed by `risk-planner` when a task is bug-shaped (`task_shape: bug`): feedback-loop-first (a red-capable, deterministic repro, minimised, before hypothesizing — on a performance regression, a measurement), 3–5 ranked falsifiable hypotheses, one-variable `[DEBUG-xxxx]`-tagged probes with a mandatory cleanup gate (stripped before the Opus-review diff), a regression test at a correct seam, and, where there was a ranking and the fix was verified, the confirmed cause named in the run's report and its pull request. It cross-references `dev-workflows:design-format` `## Seams` for the seam vocabulary and is paired with `/implement`'s spec/design-conformance ("converge") check — `code-review`'s conditional 10th dimension that traces in-scope `[Uxx]`/`[ACxx]`/`[TCxx]` against the shipped code.

`plugins/dev-workflows/references/install-time-code.md` is the **single source of truth** for how `/vuln` and `/upgrade` install a dependency without its install-time code; check 21 holds the install references to it.

`plugins/dev-workflows/references/code-handoff.md` is the **single source of truth** for the **code** repo's own git finish — the `finish-code-branch` entry point (§2): gate (§2.1), staging with its three carve-outs (§2.2), commit (§2.3), the consent choice asked once per run (§2.4), push (§2.5), the `gh` capability probe and its fallback (§2.6), the title and body file (§2.7), the base-branch ladder (§2.8) — which each of the three callers also resolves before it cuts a branch (`/implement` Pre-Phase 3 step 4, `/upgrade` Phase 2 prep, `/vuln` Step 3), so the base it offers to branch from is the base its pull request targets — the not-clean-finish draft-PR rule (§2.9), and the split-call form a per-unit loop uses (§2.12). It also owns §6, how one unit's uncommitted edits are undone: the snapshot `/vuln` and `/upgrade` take before each CVE or component, and the revert `vuln-fixer` and `upgrade-executor` run from it rather than from `HEAD`, the one working-tree restore its §1 rule 3 allows. Its one structural divergence from `phase-handoff.md` is §1 rule 5: **the commit is prompt-free**, because there the deliverable is already safe on disk and here the work is not safe until it is committed — so only the push and the pull request sit behind consent; the one prompt before a commit is §2.2's secret scan, on a possible secret it cannot dismiss. **It is also the only git reference that stages at repository scope**, deliberately: `specs-repo-git.md` §1 rule 2 and `phase-handoff.md` §1 rule 2 both forbid `git add -A` because those repositories hold many runs' artifacts, whereas here the run branched off a verified-clean tree and the whole diff *is* the deliverable — §1 declares that divergence so a reader does not "correct" it in either direction. Its §2.3 subject is the family's own convention (`workflows-core:implementation-format` §3), not the repo's log, which is where it diverges from the edition it was ported from. Consumed by the three commands that branch a code repo and write into it: `/implement` (Phase 4.6), `/vuln` (Step 3.9, once per CVE), and `/upgrade` (step 6.5 commit per component + step 7.5 push/PR once per batch); `/vuln` and `/upgrade` also take §6.1's snapshot per unit and act on §6.3, and `vuln-fixer` and `upgrade-executor` run §6.2's revert. It never touches `$SPECS_PATH` or a docs repo. The single typed opt-out is `--no-commit` on `/implement` and `/upgrade`; `/vuln` has none.

## Workflow map

The `dev-workflows` commands' lines of the family workflow map, and the caller lines of the agents `plugins/dev-workflows/agents/` ships.

```
/implement           → [keyed run from inside the specs repository: stop] → [require-on-main: in-scope specification.md/design.md] → [keyed Epic: multi-component-prereqs at implement scope — its target repository on any PRD, a mismatch an open follow-up for this repository answers being a companion run; on a multi-component PRD also prerequisites and this Epic's contract coverage; a gap asks Stop (Recommended) / continue] → [Phase 1.6 input scale assessment] → (multi-source? → [read the resolved folder → code-scanner×N (parallel, cap 4) → §8.5 narrow round 2] → synthesis, unresolved themes named) → [risk-planner@Opus plan critique] → implementation → test-writer → [code-review@Opus] → [triage: verify each finding] → review-fixer → tests → impl-maintenance → [handoff-to-main: escalated spec/design notes in the specs repo, when any, save on a direct run inside it] → [finish-code-branch: commit + consent-gated push/PR in the code repo] → commit-artifacts
/vuln                → vuln-research → vuln-fixer (branch + fix, uncommitted) → [code-review@Opus] → [triage: verify each finding] → review-fixer → [vuln-fixer verify-resume: tests vs the run baseline — reviewed path; the unreviewed path tests inside the first fixer call] → [finish-code-branch: commit + push/PR, per CVE, from the base branch] ⟲ (a commit that does not land ends the loop) → impl-maintenance → commit-artifacts
/upgrade             → upgrade-planner → [risk-planner@Opus] → upgrade-executor → [code-review@Opus] → [triage: verify each finding] → review-fixer → [upgrade-executor verify-resume: tests vs the baseline — reviewed path; the unreviewed path tests inside the first executor call] → [finish-code-branch §2.1–§2.3: commit this component] ⟲ (a commit that does not land ends the loop) → [finish-code-branch: push/PR once for the batch] → impl-maintenance → commit-artifacts
/design              → [require-on-main: specification.md; a multi-component PRD's flat spec goes to the Epic picker, designed whole only by the 0-Epic override] → [an Epic's target: its repository alone] → [code-scanner×N (parallel, cap 4, STRICT gate)] → (embedded grilling, challenges spec) → [interface-designer×3 (offered on a contested interface; --design-twice forces the fan-out, no offer)] → [design-reviewer@Opus] → write design.md → [handoff-to-main: design.md] → impl-maintenance → commit-artifacts
/ready               → [require-on-main: spec/design paths — gates as a finding capping PARTIAL, never stops] → read the resolved folder → verify ARD/spec/design → [multi-component PRD: multi-component-prereqs at ready scope — targets + contract coverage] → [readiness-reviewer@Opus] → SUPPORTED/PARTIAL/NOT-SUPPORTED → [handoff-to-main: _readiness.md] → impl-maintenance + emit-auto → commit-artifacts
                      └── test-baseliner                        (used by /implement, and by /upgrade and /vuln both directly and via upgrade-executor / vuln-fixer)
                      └── test-writer                           (used by /implement only)
                      └── risk-planner                          (used by /implement plan critique, /upgrade)
                      └── code-review                           (used by /implement, /vuln, /upgrade)
                      └── design-reviewer                       (used by /design)
                      └── interface-designer                    (used by /design)
                      └── readiness-reviewer                    (used by /ready)
```

## Invariants

### Key invariants enforced by all three code-oriented commands

- Branch created before any file is touched (`feat/<slug>` or equivalent) — including `vuln-fixer`, whose branch step precedes its edit precisely so a CVE stopped at a failed gate still has somewhere to commit
- The work is COMMITTED on that branch before the run ends — prompt-free, because a commit is local and reversible and an uncommitted implementation is the one loss no later step can undo (`dev-workflows:code-handoff` §1 rule 5). The one exception is a secret: every commit's added lines are scanned first (`scripts/secret-scan.py`, §2.2), and a possible secret the scan cannot dismiss is put to the user — stop and leave the work uncommitted, or commit it as not secret — because a secret committed is in the history, and taking it out needs the rewrite §1 rule 3 forbids. A hit's value is never printed, only a masked preview. Pushing it and opening a pull request sit behind §2.4's single consent choice, asked once per run and reused for every later branch in it. A run that did not end clean is still committed and still *offered* for push under that same choice — which a `clean_finish` differing from the one that choice was answered under puts again, **in either direction** (§2.4's first re-ask trigger, made symmetric because the commit that wrote that trigger wrote its justification with it, and that justification named the reverse case — a decline on a blocked first unit silently withholding the clean ones behind it — as equally wrong), so a decline is a real answer there and not an anomaly; what the flag itself changes is only the pull request — a draft whose body leads with a DO-NOT-MERGE line, where one is opened at all (`code-handoff`'s *A run that did not end clean*, **cited by heading rather than by number**) ([why](../../docs/maintainers/rationale.md#code-handoff-citation))
- Opus review gate runs **before** tests for `SIGNIFICANT` / `HIGH-RISK` tasks
- `code-review`'s findings are triaged by the orchestrator before `review-fixer` sees them (`workflows-core:finding-triage`) — each finding verified at the location it names, every dismissal recorded with a reason that disposes of that finding's own claim, a finding triage cannot settle, and that would be MAJOR or BLOCKER if true, recorded as unverified with what would settle it, and the fixer handed **survivors only**; a survivor that fails the patch gate is surfaced for a human decision instead of patched
- `review-fixer` handles surviving BLOCKER and MAJOR findings (on `/implement`, only those whose fix lies in the branched repository); at most one `review-fixer` cycle per reviewed artifact, and none after its re-review (`workflows-core:finding-triage` § On re-review)
- Every file path these commands hand to `risk-planner`, `code-review`, `test-writer`, `review-fixer`, `vuln-fixer`, or `upgrade-executor` carries a read-failure tier, stated by that agent where it takes the input (`dev-workflows:context-management`) — an unreadable **evidence** input is a hard stop and is NEVER regenerated by other means (a resume that re-derives its own input is exactly the failure the contract exists to prevent); an unreadable **context** input degrades to absent and the output records the degradation
- A reviewer handed `claims_file` reads it ONLY after every other dimension is complete — the deferral is what makes the falsification independent, and it is bought structurally (a path, read late) rather than by instruction
- `workflows-core:impl-maintenance` runs post-batch to update KB, `CLAUDE.md`, and project docs

### Multi-component PRDs (`workflows-core:components`)

- On a multi-component PRD the flat PRD-level `specification.md` is a requirements source: `/design <PRD>` and `/implement <PRD>` do not take it as one unit (Epic picker; with no specified Epic `/design` stops for `/specify` or recommends `/epics`, `/implement` recommends `/epics` at 0 Epics, and taking it whole is an override both offer only at 0 Epics), and `workflow-states.md`'s *Ready for Implementation* expects no PRD-level `design.md` — save where the override built it whole (a PRD-level `design.md` or implementation record), which reads the single-component clause
- `/design` keeps a targeted Epic's design in its target's repository; a second repository is a `Target span` risk `design-reviewer` flags. `/implement`'s Phase 1 check and `/ready`'s Phase 3(d) run one definition, `multi-component-prereqs` (§6), which writes nothing and never stops — the caller decides
- A follow-up `/implement` writes for another repository asks for the same unit from there, so every keyed run reads back the open tasks naming this repository and this unit (worktree and `<default-ref>`), and on a targeted Epic whose target is another repository recommends a companion run: only the tasks' changes, no scan for, plan of or review against the Epic's own change, which the target's repository holds, and none of it named as another repository's need — where no task stands it recommends stopping, and without the read the recommended path loops between the two repositories

### Key invariants for `/implement` specifically

- A keyed run whose working directory is in the specs repository — `$SPECS_PATH` that repository's top level — stops before the preflight: the specs repository is no code repository. A direct run there runs on with a notice, its session files committed on its code branch, which `commit-artifacts` does not push unless the branch's name carries a plugin prefix (`workflows-core:specs-repo-git` §4 step 5), and a specs tree inside a larger repository is left as it was
- Phase 4.6 (`finish-code-branch`) runs **after** Phase 4, never before it — Phase 4's maintenance agents write `README.md`, `CHANGELOG.md`, `CLAUDE.md`, and in-repo memory files into the same repository, so a commit ahead of them ships a partial run. A multi-source run changes code only in the repository it branched; a change another code repository needs is a follow-up (Phase 6's, or named in the stop), never an uncommitted edit there
- Test baseline captured **before** any source edits, using `test-baseliner`
- The test-writing requirement — what `test-writer` must write, its one bound, and what a completion must name — is in `.claude/rules/dev-workflows-tests.md` § Test-writing requirement
- If no test framework is detected — or if every suite the capture actually ran aborted with no parseable pass/fail counts, the other capture that asks — surface that explicitly at Pre-Phase 3.5; test-writing is never silently skipped. **`RUN_FAILED` is about the suites that were *run*, not the ones that were *detected***, which are two different sets wherever a `command_hint` narrowed the run (`dev-workflows:test-baseliner` capture step 4), and a suite that started, finished, and printed output the parse table does not recognise is `RUN_FAILED` without having failed to start at all
- Phase 3.5 verifies against the captured baseline before the workflow is considered complete, and **names what it did not cover rather than assuming it**: a suite that could not run at either end (verify `PARTIAL`) is recorded in `### Deferred items` and the run continues; a comparison that could not be made at all (`RUN_FAILED` / `COMMAND_NOT_FOUND`) is surfaced, never read as a pass, and accepting it finishes `clean_finish: false`, so any pull request it opens carries the DO-NOT-MERGE banner; and a run whose Pre-Phase 3.5 capture returned `COMMAND_NOT_FOUND` **or `RUN_FAILED`** carries a `test_decision: skip` from that prompt, taken before any edit and while a baseline could still have been taken — **the gate being the recorded decision, never the baseline's `Framework` field**, which is why a `RUN_FAILED` capture (whose `Framework` names the suites it could not run) reaches this completion too. **That skip has two provenances and they finish differently**, stated in `.claude/rules/dev-workflows-tests.md` § Test-writing requirement (the Pre-Phase 3.5 skip bullet). Either way it is scoped to steps 4–6: the lint and build of step 3 still run, because "Skip tests for this run" is what was asked. A test the run itself wrote and that fails is in **none** of those: it is a New failure, which moves no `test-baseliner` status, and Phase 3.5 reads that list beside the status precisely so it cannot pass as one ([why](../../docs/maintainers/rationale.md#implement-phase-3-5))
- Multi-source input (more than one distinct repo, counted by top level, or any folder input — a specs folder or a spec/design folder) floors classification at SIGNIFICANT (overridable at plan approval) and triggers the Phase 1.7 fan-out scan
- The fan-out reads the resolved folder and runs per-repo `code-scanner` (single response, cap 4 concurrent); its synthesized summary feeds the planner instead of the single Explore subagent
- A theme round 1 leaves inconclusive — `partial`/`absent`/`error`, or two scanners each naming the other's repo — gets ONE narrow round 2 seeded with round 1's verified anchors (`classification.md` §8.5, cap 4, no round 3). A theme still unresolved after round 2 is named in the summary's `## Unresolved` section and carried into the plan's risks; it is NEVER flattened into an ordinary gap, because a gap asserts absence while an unresolved theme asserts only that the scan could not tell
- A referenced directory that is missing or unrecognized is surfaced, never silently skipped

### /design and /ready

- `/design` Phase 5 offers a three-take `interface-designer` fan-out (one take per constraint — minimise the interface, maximise flexibility, optimise for the most common caller) on a contested interface — any `dev-workflows:design-format` `## Seams` signal; `--design-twice` forces the fan-out itself, skipping the offer, even with no signal fired (a user who typed the flag has already answered what the offer would ask); the offer's two options carry no `(Recommended)` marker, because the list is only shown once the interface is already contested; declining costs nothing — the interview continues and `design.md`'s unconditional `### Alternatives considered` requirement is satisfied by hand as it would have been anyway
- `/ready` is **read-only about status** — it **derives the workflow phase from the artifacts present** and verifies the ARD/spec/design justify it, comparing an operator's `--claimed` status against that derivation where one is given; there is no workflow phase recorded anywhere for it to read — `prd.md`'s own `status:` is the document's authoring state, never read as one (the status peek D8 retired had no source in `$SPECS_PATH` and `ready.md` forbids reconstructing it), and it never sets one and never reads a tracker, and never stops on an unmerged artifact (`workflows-core:phase-handoff` §3.3 rows D/E, a readiness finding capping the verdict at `PARTIAL`) or a missing one (row F, delegated per §3.4, recorded as a coverage gap); it commits the deliverable or the `_readiness.md` snapshot only through `phase-handoff.md` §4.3's consent choice via `handoff-to-main` (§2), never automatically (its terminal `commit-artifacts` step commits ONLY `$SPECS_PATH`'s bounded session-artifact paths, `workflows-core:specs-repo-git` §2.1)
