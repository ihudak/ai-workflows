# dev-workflows — invariants, workflow map, agent callers

Loaded when a file under `plugins/dev-workflows/` is read. Repo-wide rules are in `CLAUDE.md`; evidence is in `docs/maintainers/rationale.md`.

The `/implement`-specific invariants are in `.claude/rules/dev-workflows-implement.md`, and the `/design` and `/ready` ones in `.claude/rules/dev-workflows-design-ready.md`, both loaded with this file. The test-writing requirement for code changes is in `.claude/rules/dev-workflows-tests.md`, loaded with `/implement`, the test agents and their handoff files, and `references/code-handoff.md`.

## Authorities

`plugins/dev-workflows/references/bug-diagnosis.md` is the **single source of truth** for the bug-diagnosis discipline consulted by `/implement` (Phases 2B to 3.6) and followed by `risk-planner` when a task is bug-shaped (`task_shape: bug`), and by `code-writer` where its request carries `scratch_checkout: HEAD`: feedback-loop-first (a red-capable, deterministic repro, minimised, before hypothesizing — on a performance regression, a measurement), 3–5 ranked falsifiable hypotheses, one-variable `[DEBUG-xxxx]`-tagged probes that never write a secret's value, with a mandatory cleanup gate (stripped before the Opus-review diff), a regression test at a correct seam, where each run falls and whose it is (before the first edit `risk-planner`'s repro on the working tree; from it every check against the working tree through the run lock, and a probe or the repro only in a scratch checkout of `HEAD` — `code-writer`'s on every dispatch, its first included, and `risk-planner`'s on a re-plan — save the orchestrator's re-run of the repro against the change at the last unit's test run; a bisect the orchestrator's, first, before any edit; the regression test `test-writer`'s, its red-capability check the orchestrator's at the unit's test run — in a scratch checkout of `HEAD`, inconclusive where it fails on anything but the bug's assertion — the caller's verify the green check), and the confirmed cause named in the run's report and its pull request where step 6 says. It cross-references `dev-workflows:design-format` `## Seams` for the seam vocabulary and is paired with `/implement`'s spec/design-conformance ("converge") check — `code-review`'s conditional 10th dimension that traces in-scope `[Uxx]`/`[ACxx]`/`[TCxx]` against the shipped code.

`plugins/dev-workflows/references/install-time-code.md` is the **single source of truth** for how this plugin installs a dependency without its install-time code; check 21 holds the install references to it.

`plugins/dev-workflows/references/code-handoff.md` is the **single source of truth** for the **code** repo's own git finish — the `finish-code-branch` entry point (§2): gate (§2.1), staging with its three carve-outs (§2.2), commit (§2.3), the consent choice asked once per run (§2.4), push (§2.5), the `gh` capability probe and its fallback (§2.6), the title and body file (§2.7), the base-branch ladder (§2.8) and the move onto that base (§2.8.1) — which each of the three callers makes before it cuts a branch (`/implement` Phase 1.4 step 2, `/upgrade` Phase 2 prep, `/vuln` Step 3), so the base it offers to branch from is the base its pull request targets — the not-clean-finish draft-PR rule (§2.9), and the split-call form a per-unit loop uses (§2.12). It also owns §6, how one unit's uncommitted edits are undone: the snapshot `/vuln` and `/upgrade` take before each CVE or component, and the revert `vuln-fixer` and `upgrade-executor` run from it rather than from `HEAD`, the one working-tree restore its §1 rule 3 allows. Its one structural divergence from `phase-handoff.md` is §1 rule 5: **the commit is prompt-free**, because there the deliverable is already safe on disk and here the work is not safe until it is committed — so only the push and the pull request sit behind consent; the one prompt before a commit is §2.2's secret scan, on a possible secret it cannot dismiss. **It is also the only git reference that stages at repository scope**, deliberately: `specs-repo-git.md` §1 rule 2 and `phase-handoff.md` §1 rule 2 both forbid `git add -A` because those repositories hold many runs' artifacts, whereas here the run branched off a verified-clean tree and the whole diff *is* the deliverable — §1 declares that divergence lest a reader "correct" it either way. Its §2.3 subject is the family's own convention (`workflows-core:implementation-format` §3), not the repo's log, which is where it diverges from the edition it was ported from. Consumed by the three commands that branch a code repo and write into it: `/implement` (Phase 4.6), `/vuln` (Step 3.9, once per CVE), and `/upgrade` (step 6.5 commit per component + step 7.5 push/PR once per batch); `/vuln` and `/upgrade` also take §6.1's snapshot per unit and act on §6.3, and `vuln-fixer` and `upgrade-executor` run §6.2's revert. It never touches `$SPECS_PATH` or a docs repo. The single typed opt-out is `--no-commit` on `/implement` and `/upgrade`; `/vuln` has none.

## Invariants

### Key invariants enforced by all three code-oriented commands

- Branch created before any file is touched (`feat/<slug>` or equivalent) — including `vuln-fixer`, whose branch step precedes its edit precisely so a CVE stopped at a failed gate still has somewhere to commit — save where `/implement` continues on the unit's own branch, which its Phase 1.4 offers and the user chooses: that branch stands before any file is touched too
- The work is COMMITTED on that branch before the run ends — prompt-free, because a commit is local and reversible and an uncommitted implementation is the one loss no later step can undo (`dev-workflows:code-handoff` §1 rule 5). The one shared exception is a secret: every commit's added lines are scanned first (`scripts/secret-scan.py`, §2.2), and a possible secret the scan cannot dismiss is put to the user — stop and leave the work uncommitted, or commit it as not secret — because a secret committed is in the history, and taking it out needs the rewrite §1 rule 3 forbids. A hit's value is never printed, only a masked preview. Pushing it and opening a pull request sit behind §2.4's single consent choice, asked once per run and reused for every later branch in it. A run that did not end clean is still committed and still *offered* for push under that same choice — which a `clean_finish` differing from the one that choice was answered under puts again, **in either direction** (§2.4's first re-ask trigger, made symmetric because the commit that wrote it named the reverse case — a decline on a blocked first unit silently withholding the clean ones behind it — as equally wrong), so a decline is a real answer there and not an anomaly; what the flag itself changes is only the pull request — a draft whose body leads with a DO-NOT-MERGE line, where one is opened at all, and one already open that the push updates, after either push answer, turned back into a draft with that line posted on it as a comment (`code-handoff`'s *A run that did not end clean*, **cited by heading rather than by number**) ([why](../../docs/maintainers/rationale.md#code-handoff-citation))
- On `/vuln` and `/upgrade` the Opus review gate runs **before** tests, for `SIGNIFICANT` / `HIGH-RISK` tasks only; `/implement` reviews from `MODERATE` up, **after** each writer unit's tests (`.claude/rules/dev-workflows-implement.md`)
- `code-review`'s findings are triaged by the orchestrator before a fixer sees them — `review-fixer` on `/vuln` and `/upgrade`, the writer owning the file on `/implement` (`workflows-core:finding-triage`) — each finding verified at the location it names, every dismissal recorded with a reason that disposes of that finding's own claim, a finding triage cannot settle, and that would be MAJOR or BLOCKER if true, recorded as unverified with what would settle it, and the fixer handed **survivors only**; a survivor that fails the patch gate is surfaced for a human decision instead of patched
- On `/vuln` and `/upgrade`, `review-fixer` handles surviving BLOCKER and MAJOR findings; at most one `review-fixer` cycle per reviewed artifact, and none after its re-review (`workflows-core:finding-triage` § On re-review). `/implement` dispatches no `review-fixer`; its fix rule is in `.claude/rules/dev-workflows-implement.md`
- Every file path these commands hand to `risk-planner`, `code-review`, `code-writer`, `test-writer`, `review-fixer`, `vuln-fixer`, or `upgrade-executor` carries a read-failure tier, stated by that agent where it takes the input (`dev-workflows:context-management`) — an unreadable **evidence** input is a hard stop and is NEVER regenerated by other means (a resume that re-derives its own input is exactly the failure the contract exists to prevent); an unreadable **context** input degrades to absent and the output records the degradation
- A reviewer handed `claims_file` reads it ONLY after every other dimension is complete — the deferral is what makes the falsification independent, and it is bought structurally (a path, read late) rather than by instruction
- `workflows-core:impl-maintenance` runs post-batch to update KB, `CLAUDE.md`, and project docs

### Multi-component PRDs (`workflows-core:components`)

- On a multi-component PRD the flat PRD-level `specification.md` is a requirements source: `/design <PRD>` and `/implement <PRD>` do not take it as one unit (Epic picker; with no specified Epic `/design` stops for `/specify` or recommends `/epics`, `/implement` recommends `/epics` at 0 Epics, and taking it whole is an override both offer only at 0 Epics), and `workflow-states.md`'s *Ready for Implementation* expects no PRD-level `design.md` — save where the override built it whole (a PRD-level `design.md` or implementation record), which reads the single-component clause
- `/design` keeps a targeted Epic's design in its target's repository; a second repository is a `Target span` risk `design-reviewer` flags. `/implement`'s Phase 1 check and `/ready`'s Phase 3(d) run one definition, `multi-component-prereqs` (§6), which writes nothing and never stops — the caller decides
- A follow-up `/implement` writes for another repository asks for the same unit from there, so every keyed run reads back the open tasks naming this repository and this unit (worktree and `<default-ref>`), and on a targeted Epic whose target is another repository recommends a companion run: only the tasks' changes, no scan for, plan of or review against the Epic's own change, which the target's repository holds, and none of it named as another repository's need — where no task stands it recommends stopping, and without the read the recommended path loops between the two repositories
