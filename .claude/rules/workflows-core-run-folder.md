# workflows-core — the run-folder authority

Loaded when any plugin's copy of `scripts/run-folder.py`, or any command, agent or reference file, is read: a command that keeps a run folder can be written in any plugin, and an agent it dispatches can be handed the path to write its result to. Kept in a file of its own so that `.claude/rules/workflows-core.md` stays under 20,000 characters; repo-wide rules are in `CLAUDE.md`; the design is `docs/superpowers/specs/2026-11-24-run-folder-design.md`.

## Authority

`plugins/workflows-core/references/run-folder.md` is the **single source of truth** for a command's run folder — where one run of one command keeps its working state, so that a run interrupted mid-way continues on the same machine: the folder and its key, the session that owns it, the saved dispatches and their fingerprints, the writers and what they wrote, the recorded answers, the guarded side effects, the changed-agents question, the stop line and the folder's removal, through its entry points `open-run`, `run-dispatch`, `run-writer`, `run-gate`, `run-effect`, `changed-agents`, `run-stop-line` and `close-run`. A command cites it — `Skill(skill: "workflows-core:reference", args: "run-folder <entry point>")` — and never restates it. Its mechanics are `scripts/run-folder.py`, called by its path, `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/run-folder.py" <subcommand> …`, so `${CLAUDE_PLUGIN_ROOT}` is the calling file's own plugin, and each plugin that calls it ships a copy equal to `workflows-core`'s, which CI checks (the copied-scripts rule, `.claude/rules/workflows-core-bounded-run.md`). Its consumers are what `grep -l 'args: "run-folder ' plugins/*/commands/*.md` lists. **`/dev-workflows:implement` is not one**: it resumes a stopped run by a different mechanism, `dev-workflows`' `scripts/run-state.py`, with its own state file in the worktree's git directory, and the two are never mixed — nor is `run-folder.py` ever named `run-state.py`.

## Invariants

1. **A run never fails because of its folder.** Where the folder cannot be made or written, `open` reports `unavailable` and exits 0, and the run goes on exactly as it would without one, after one `NOTE:`; a later call that exits 2, or with any exit the reference's §2 does not name (127 where no `python3` is found), does the same from there on. A change that lets a folder failure stop a run, or skip work the run does without a folder, breaks this.
2. **Exit 9 stops the run, writing nothing more.** A call that writes into a run, from a session other than its owner (`CLAUDE_CODE_SESSION_ID`, both non-null), or on a folder another session's *Start over* removed, exits 9 and writes nothing — save `resume` and `discard`, unchecked by design: they are how a session takes a run over and how *Start over* removes it. `discard` still waits for the write lock, as `close` does, so a write in flight lands before the folder goes and never on the new run made at its path. The command stops at once — no further call, dispatch, question, write, commit or tail, and no stop line, since the folder is the other session's.
3. **A saved result is reused only where its recorded fingerprint equals the new one and its completion was recorded** (`done`), and is read from the file its record names. A result file with no completion record is never read as a result, nor is one no record names: each `dispatch` names a result file of its own, `<area>/results/<id>.<nonce>.md`, and removes the ones the earlier records of that id named, so an agent still running for an earlier dispatch — among them one dispatched by a session another has since taken over — writes where nothing is read. A path fixed per id let such an agent overwrite the new owner's file, which `done` then recorded under the new fingerprint. The fingerprint covers the input's bytes, each attached run-folder file's bytes, the agent definition file and the model, and nothing else, so an input must name by version every external thing the agent reads — a repository by its commit, a file by its blob id or content hash; a missing version is the likeliest defect, and review looks for it first. And a later session must build the same bytes: an input built from the command's fixed text with values from files, facts or the folder, never from the conversation, never reworded or reordered — or every saved result is redone on a resume.
4. **A writer never goes through `run-dispatch`.** A dispatch that edits files in a git work tree goes through `run-writer`, whose record keeps the paths the writer changed and a hash of each one's content: a resume skips it while those still hold what the run last left there, asks where something else changed them, and meets one cut off mid-edit with the command's handling. Through `run-dispatch`, a reused result could stand beside files that no longer hold its work. A writer is matched on its input and attachments, its tree and scope, and its saved receipt — never on its agent file or model — and `stale` counts none, so a changed agent file or model never dispatches a finished writer again over its own work.
5. **The run's own edits are noted with `tree-note`.** After every edit, commit or revert a command makes itself in a writer's tree, it calls `tree-note` on that tree, so its own change never reads as `changed` on a resume, which would ask the user about the run's own work. After a revert to a unit's starting tree, the whole unit is redone from its first step — each of its writers with `--redo`, its own `put` files and copies made again, each effect the revert undid made again — never one writer alone: the unit's writers that had finished would read `intact` over the reverted files. An effect the revert leaves standing (a push, a pull request) keeps its own handling.
6. **Generated content is `put` and read back, never regenerated.** What the orchestrator generates that a later step, a dispatch's input or a recorded question's shown text reads — a plan, a brief, a requirement list — is written with `put` when it is generated — or, where a command names it, whole through a quoted here-document after an owner-checked call, with a marker (a `fact`, an `effect … done`) recorded once it is whole, without which a resumed run makes it again, since that write is not atomic — and a resumed run reads that file. Generated again, it differs in some byte, and every result and answer built from it is redone or asked again. A file the run itself rewrites later is copied with `put` at the dispatch that reads it, once, and attached. Both are made again only in a unit redone after a revert (invariant 5). Any other `scratch/` file — a capture, a listing — may be written directly.
7. **An agent's file comes from its own plugin's root, or the `agent-file` skill.** A command names its own plugin's agent as `${CLAUDE_PLUGIN_ROOT}/agents/<agent>.md`, and a `workflows-core` agent by the path `Skill(skill: "workflows-core:agent-file", args: "<agent>")` prints, since its own root names its own plugin; never by a path written across plugins. A dispatch whose file cannot be named so — a `general-purpose` one, an agent of any other plugin, or one the skill prints nothing for — runs unsaved, as before, and so do the end-of-run maintenance and defect dispatches, whose step the command guards whole as an effect.
