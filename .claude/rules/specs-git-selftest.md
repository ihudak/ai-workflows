# `specs-git.py`'s selftest — where it lives, how it runs, the mutants

Loaded when a file under `scripts/selftests/`, or `specs-git.py`, `specs_git_state.py` or `specs_git_lines.py` under `plugins/workflows-core/scripts/`, is read with the Read tool: the three scripts the mutants name. Repo-wide rules are in `CLAUDE.md`; the specs-repo git authorities the script implements are in `.claude/rules/workflows-core-git.md` and its companions; evidence is in `docs/maintainers/rationale.md`.

## Where it lives

The selftest of `plugins/workflows-core/scripts/specs-git.py` is `scripts/selftests/specs_git_selftest.py`, outside the plugin, and `python3 plugins/workflows-core/scripts/specs-git.py --selftest` is still the command that runs it and the one CI runs, every group of it. **In CI, a run with `--group` is refused:** where `GITHUB_ACTIONS` is `true`, `selftest()` prints one line on stderr, `specs-git: not run (--group is refused in CI, where GITHUB_ACTIONS is true: a partial run is never evidence that the selftest passes)`, and exits 2 before any group runs, as `s_group_refused_in_ci` checks; so a `--group` added to CI's line fails that step, whatever group it names. On a run that includes the `selftest` group, as CI's full run does, `s_ci_runs_all` also fails unless `.github/workflows/validate-catalog.yml` holds exactly one line that, stripped of the whitespace around it, starts `run:` and names `specs-git.py`, and that stripped line is `run: python3 plugins/workflows-core/scripts/specs-git.py --selftest`; so any other change to that line fails it, and a change of indentation alone does not. ([why](../../docs/maintainers/rationale.md#specs-git-selftest))

**The file is executed in the script's namespace and never imported.** `--selftest` calls the script's `_run_selftest`, which runs the file with `exec` in the script's own `globals()` and calls the `selftest()` it defines, so every name the file uses and does not define is the script's. A top-level name the file binds that the script already held would replace the script's, so `_run_selftest` compares the script's namespace after the `exec` with a copy taken before it: where a name the script held is bound to a different object, it prints one line on stderr, `specs-git: not run (the selftest file redefines a name of the script: <names>)`, and exits 2 before any test runs, as `s_selftest_redefines` checks. Define none the script has; that is why the file's header is a `#` comment block, since a module docstring would rebind the script's `__doc__`. It is never imported because its tests patch the script through `globals()` and reach the script through `__file__`, and an import would give the file a namespace and a `__file__` of its own. Run on its own, as `python3 scripts/selftests/specs_git_selftest.py`, the file exits 1 with one line naming the command that runs it, as `s_file_run_directly` checks: its first statement looks for `_run_selftest`, a name only the script defines. ([why](../../docs/maintainers/rationale.md#specs-git-selftest))

**A plugin cache holds no selftest.** Installed from a marketplace on a git remote, the plugin runs from a plugin cache, `~/.claude/plugins/cache/<marketplace>/workflows-core/<version>/`, and `SELFTEST_FILE`, `scripts/selftests/specs_git_selftest.py` under the directory three levels above the script's own, names a path that holds nothing. Run from there, `--selftest` of a release whose script defines `SELFTEST_FILE` prints one line on stderr, starting `specs-git: not run (the selftest is not shipped with the plugin`, and exits 2, as `s_selftest_not_shipped` checks; an earlier release still carries `selftest()` in the script, and runs it. Installed from a directory-source marketplace, the plugin runs from that working tree (`CLAUDE.md`, *Internal reference convention*), where `--selftest` runs the checkout's selftest. A selftest path that is there but cannot be read — a directory, say — prints `specs-git: not run (the selftest could not be read: <path>: <reason>)` instead, and exits 2, as `s_selftest_unreadable` checks. Run the selftest from a checkout of this repository.

## One group alone

`--selftest --group <name>` runs only that group, and `--group` may be repeated: the named groups run in the selftest's own order, whatever order they are named in. An unknown name is a usage error naming every group, and `--group` without `--selftest` is a usage error too. The groups are the `GROUPS` table at the end of `selftest()`; wherever `GITHUB_ACTIONS` is not `true`, `python3 plugins/workflows-core/scripts/specs-git.py --selftest --group '?'` prints their names, as that usage error on stderr (exit 2), and `mutants.py` reads them from it, running it with `GITHUB_ACTIONS` empty. A run with `--group` prints `specs-git selftest: PASS (<n> checks; partial: <groups>)`, or `specs-git selftest: FAIL (partial: <groups>)` with its failure lines under it, and **a line with `partial:` is never evidence that the selftest passes.** Only a run with no `--group` is, its PASS line carrying no `partial:`; in CI, a run with `--group` is refused (*Where it lives*).

**The `selftest` group's own runs are marked.** `scenarios_selftest` starts every run with `SPECS_GIT_SELFTEST_NESTED` set to `1`, and every run but `s_group_refused_in_ci`'s with `GITHUB_ACTIONS` empty, so that the group passes in CI too. A run with that marker that would include the `selftest` group — no `--group`, or one naming `selftest` — prints `specs-git selftest: FAIL (nested)` and one failure line, `  s_nested: a nested run was asked for every group, or for group selftest`, and exits 1 before any group runs, as `s_nested_refused` checks. Without the marker, a break in group selection that put the `selftest` group into the runs that group starts would have each of them start runs of its own, without end; with it, that break fails `s_group_alone` in seconds, as the mutant `selftest_s_group_alone` shows.

## The mutants

A mutant is a one-line edit to a script under `plugins/workflows-core/scripts/`, which a check whose failure line starts with the mutant's `fails` must catch: `fails` is at least the check's label up to and including its colon, and may go on into the message as far as tells that check from others with the same label. `scripts/selftests/specs-git-mutants.json` lists them, each with its `id`, the `group` to run, the `file`, the `old` text and the `new` text that replaces it, and `fails`; `scripts/selftests/mutants.py`'s docstring states the file's shape and every line the runner prints. `python3 scripts/selftests/mutants.py` runs every mutant, `--only <id>` (repeatable) only those named, `--list` prints each mutant's id, group and `fails` and runs nothing, and `--check` counts each mutant's `old` text in its `file` and runs nothing (below).

The runner works on a copy: it copies `plugins/workflows-core/`, `scripts/selftests/` and `.github/workflows/validate-catalog.yml` into a temporary directory, writes and runs only there, and removes the directory when it exits. No run is made in that copy: each run, a baseline's included, is in a fresh copy of it, removed after the run, so nothing one run leaves reaches another. It first runs each group a selected mutant names, unchanged, then each mutant's group with that one edit in place, and prints `killed <id>` where the run fails with a failure line that starts with the mutant's `fails`, followed by the first such line. The other outcomes are `STALE <id>`, where the `old` text is not found exactly once in `file`, so nothing runs; `TIMEOUT <id>`, where the run passes its time limit; and `SURVIVED <id>`, any other run. A group whose unchanged run does not pass prints `BASELINE RED <group>`, and its mutants are left unrun. It exits 0 where every selected mutant was killed, 1 on any other outcome, 2 where it could not run, and 128 + the signal's number where a SIGTERM, SIGHUP or SIGINT ended it; one of those it inherited as ignored, as under `nohup`, stays ignored.

**CI runs only `python3 scripts/selftests/mutants.py --check`**, in the step after the selftest's. It reads each mutant's `file` in the repository, writing nothing, counts the mutant's `old` text there as a run does, prints `STALE <id>: old text found <n> times in <file>` for each not found exactly once, then `mutants: <n> checked, <t> stale`, and exits 1 where any is stale. So it catches a mutant whose text an edit has taken away; it runs no mutant, so it cannot catch a check made to assert less, which only a run shows. A full run takes minutes (*How long it takes*), so CI makes none. Run the mutants concerned, by `--only <id>`, when you change a file a mutant's `file` names, since an edit to its `old` text leaves the mutant `STALE`; when you change a check whose failure line starts with a mutant's `fails`, since a check made to assert less can let its mutant survive; and when you change the mutants file itself.

**What none of this can see:** a check that asserts too little passes in a group run, in a full run and in CI alike, and only a mutant whose `fails` begins that check's failure line catches it, by surviving. `--list` prints each `fails`, not the checks it matches. Several checks can share one label — every check of the `branch_merged` group starts `branch-merged:` — and a `fails` that stops at the label is killed by any of them failing: a kill says that one of them caught the edit, its line shows the first that did, and it says nothing about the others. So where its label is shared, a mutant's `fails` goes on into the message as far as tells the check it targets from the others, as the `status`, `branch_merged`, `branch_key`, `push_scope` and `owner_repo` mutants' do. `grep -nF '"<label>' scripts/selftests/specs_git_selftest.py` lists the check messages written with a label, though not a label the test builds at run time, as `t_midrun_keyless` builds its label from its `name` argument. A check whose failure line starts with no mutant's `fails` has no mutant, and a group whose mutants are all killed says nothing about its other checks.

## Which rules load with the tests

Reading a file under `scripts/selftests/` loads the `gates*.md` rules, whose `paths:` take every file under `scripts/`, the rules files that load with any file, and this one; not the specs-repo git rules, which loaded with the tests while they were in the script. **Before editing a test, Read part of `plugins/workflows-core/scripts/specs-git.py` with the Read tool, giving `offset` and `limit`, since the script is over 300 KB (`wc -c`):** that loads `.claude/rules/workflows-core-git.md` and `.claude/rules/workflows-core.md`, and every rules file `CLAUDE.md`'s table lists *as* either of them, among them the specs-repo git authorities and invariants the tests check.

## How long it takes

Measured on 2026-11-13 on one 12-core machine (`nproc`), at `ee8564f3`. The selftest: the full run took 98 s; alone, `midrun` took 33 s, `end` 28 s, `start` 17 s, `land` and `mode` about 8 s, `replay` about 3 s, and each other group under 2 s. Every mutant, run once in two invocations of `--only` — the eight of `end` and `midrun`, then the other fifteen — took 546 s in all, 432 s and 114 s. The figures move with the machine and with every check added, so measure again rather than trust them. The commands below print the full run's time, then one `<group> <seconds> s` line per group, then the mutant run's time:

```bash
time python3 plugins/workflows-core/scripts/specs-git.py --selftest
(for g in $(python3 plugins/workflows-core/scripts/specs-git.py --selftest --group '?' 2>&1 | sed 's/.*one of: //; s/)$//; s/,//g'); do
  TIMEFORMAT="$g %1R s"; time python3 plugins/workflows-core/scripts/specs-git.py --selftest --group "$g" > /dev/null
done)
time python3 scripts/selftests/mutants.py
```
