# dev-workflows — `/conformance`, its mitigations and threats, the readers of its record, `/ready`'s optional rung, and `/implement`'s gate on its unit's documents

Loaded with `.claude/rules/dev-workflows.md`, whose `paths:` it shares. Split out of `.claude/rules/dev-workflows.md` to keep that file under 20,000 characters; the plugin's other rules are there, `conformance-tracer`'s caller line and `/ready`'s map line and its read-only invariant among them. `/implement`'s gate on its unit's specification and design is here rather than in `.claude/rules/dev-workflows-implement.md`, which holds its other invariants and had no room for it.

## Mitigations and threats

`/conformance` traces a threat model's mitigations — each design's `[DT#N]` Rules, and each `[AD#n]` Rule a threat's `Mitigated by` pair joins — and lists where each threat that applies to the unit stands (its Phase 1 (b) *Threat input*, Phases 2–4, and Phase 5's *Where each threat stands*). Nothing it does writes into a `threat-model.md`, a `design.md` or a findings register.

- **The default branch's copy, and no gate.** Each model is read from `<default-ref>` by `git show`, never from the working tree of a git repository — on a specs tree that is no git repository, the file itself, the only copy — and nothing gates, repairs or stops on it: it is `workflows-core:phase-handoff` §5 rule 2's consumer that executes no gate, since a reader of `<default-ref>` alone cannot read content that has not landed — an architect's uncommitted refine can neither hide a landed threat nor reopen acceptance, and no repair offer moves the checkout after Phase 0 read the records. A model only the working tree of a git repository holds binds nothing and is named in one line. A design whose gate returned `pass_amending` has its `## Threat review` read the same way, from `<default-ref>`, so an entry that has not landed decides no threat's state. The PRD folder's `design.md` is a document read, gated in Phase 0 step 4, on a PRD run only where the PRD folder's own threat model stands.
- **The fifth site.** On a PRD with no Epic folder, the one PRD-level `ard-resolution` call made for the PRD folder's model stops on no row: the model is left unused, and row C's repair is not offered (`phase-handoff` §3.7's fifth caller; `ard-resolution`'s *No-regression rule*). Every other `ard-resolution` call of the command stops as before — the map line's "an unmerged ARD stops" with that one exception.
- **No accept.** No array offers `accept` on a mitigation, a free-text accept is asked again, and an `accept` on file on one is put again; it outlasts a run only in an entry the run did not put (a `lists:` entry), and holds its threat `open` there. Only the architect accepts a risk, in the threat model.
- **An unused model withholds accept, and so does an unreadable Disposition.** A landed model the run cannot use — no ARD, no component set, the Epic's target outside it, the fifth site's stop, or threats not traced — fails closed: each `[AD#n]` Rule of its folder's ARD files, and of the PRD-level ARD it inherits, is offered no accept, with one line saying why, and is never handed `mitigation: true`. A used model holding a live threat in scope with no Disposition the run can read — none, several, or one in none of the format's three forms — does the same to the same Rules, its own line saying why. A stale threat's readable pairs join nothing, and the Rules they name keep their accept (D5's "live, non-stale"), a named limit.
- **An amended mitigation behind a stale or unreadable threat keeps an `open` line.** Rules 1 and 2 of Phase 5 read no part, so whatever stands behind such a threat stands on a line of its own, counted in the header's totals, and `/ready`'s seventh condition holds on an amended one: an in-scope design entry answering it (the maintainer's ruling on the final review's I1), and an `[AD#n]` mitigation every threat joining which took rule 1 (the controller's extension to the class's other member; a stale threat's pairs join nothing). A stand-alone ARD Rule's line is counted in the `Threats:` line, which `body_facts` carry, and not named there: G5 names threats and design entries alone.
- **The three-part join.** A pair joins the requirement of the folder it names, the ARD file's whole basename and the number — never fewer; none or several leaves that part `not checked`, never matched by number alone. An area file's decision carries its file in its id and `document:`.
- **The PRD run's full trace.** A mitigation is exempt from the PRD run's `## Satisfied` skip and traced in full every time; no `/conformance` run reads a `Threats:` line or `## Threats` back, so no record — hand-edited, carried on a Dev's branch, or written before threats were traced — makes a threat `verified`.
- **Located and re-read, not `/design`'s guarantee.** `verified` means each mitigation's lines were located by the tracer, held to `threat-model-format` §9's backstop, and re-read by the orchestrator in this run: they exist and reach the check — not that they run in production, nor that the attack fails. The tracer reads code with tools, so `/design`'s no-tool structural guarantee does not carry over, and a steered tracer can cite real code that is wired but ineffective.
- **The tracer's two copies of the backstop's test.** Item 6 of `conformance-tracer`'s handoff file and the paragraph of its agent file opening *Where the run hands any mitigation* restate `threat-model-format` §9's *An agent given a repository*: a change to any of the three is made to all three (`.claude/rules/threat-model.md` invariant 10).

## The record's readers

`plugins/dev-workflows/references/conformance-format.md` §6 names the readers of `_conformance.md` and what each reads, so a change to a field it reads, or to what a status or flag means (§4), is a change to that reader too:

- `/conformance`'s own later runs, which carry each decided entry forward — save an `accept` on what is now a mitigation, or on an `[AD#n]` Rule a landed threat model they could not use, or a threat with no readable Disposition, may rest on, which they put again — and mark it `resolved` or `requirement withdrawn` (§5), and never read back the `Threats:` line or `## Threats`, which each run writes anew (§2);
- `/implement`, which reads back the `withdraws:` lines of the PRD folder's record so that it never builds a follow-up a PRD run withdrew (§3);
- `/ready`, which reads the PRD folder's record from `<default-ref>` by `git show`, never the working tree, and tests from it, and from the `implementation.md` blocks in the PRD's tree, each ordered against the record by instant where both carry one and by date otherwise, whether the PRD reaches the optional *Delivery verified* rung (its Phase 1 step 2b): it maps no decision, so its test is its own and not `workflows-core:source-truth` §7.8's;
- `/product-workflows:create-ard`, whose refine of a threat model reads the record of the model's folder, of each Epic folder under a PRD folder that `workflows-core:threat-intake`'s guard lets it read, and of the PRD folder above an Epic folder, each from `<default-ref>` by `git show`, never the working tree — the file itself on a specs tree that is no git repository — and gated by nothing, to find a threat open on a decision — an entry on an `[AD#n]` Rule decided `amend-document` or `accept`, not `resolved`, `orphaned` or `requirement withdrawn`, and carrying no `superseded-by:`: it maps and takes no decision, so its test is that reference's own, not §7.8's, and it shows no entry's `shipped:` or `rationale:`, only nominating a threat for a question to the architect (`.claude/rules/threat-model.md` invariant 11);
- `/document` (keyed mode: Phase 3, and Phase 5.8 step 0) and `/release-notes` (Phase 0 and Phase 3), which read every record in their scope from the working tree, as data, and take the decision a person recorded in place of asking again. Which records, which entries are open (never one whose `document:` names `design.md`), which of two entries on one claim wins, what each decision maps to and how far the code has moved since are §7.8's, the one authority on them (`.claude/rules/workflows-core.md`), save that `/release-notes` keeps its own commits-read test of how far the code has moved; neither `docs-workflows` nor `workflows-core` can load `conformance-format`, so §7.8, `/document` and `/release-notes` each state the fields they read.

## /ready and the optional rung

- `/ready` decides the PRD ladder's one optional rung, *Delivery verified (optional)* (`workflow-states.md`, *An optional rung*), from the PRD folder's `_conformance.md` and the PRD tree's `implementation.md` blocks, on a PRD- and an Epic-level run alike (Phase 1 step 2b): the record read from `<default-ref>` by `git show`, never the working tree, and gated by no `require-on-main`, so an unmerged or missing record is neither row D/E's finding nor row F's coverage gap. A record passing that step's seven conditions — the sixth, no block later than it, by instant if both carry one, else by date, a same-day block then not counted; the seventh, no open threat and no threats not traced on its `Threats:` line — lifts a PRD derived at *Implementation* to the rung; any other PRD passes it over — never a straddle, never a finding, never asked about — and keeps the phase the mandatory rungs give it, with its `Delivery:` line as a note (`not verified — <reason>` where the record does not settle the rung) that never caps or lowers the verdict. Where the PRD is at *Implementation* or later and delivery is not verified, the Next step adds `PE → /dev-workflows:conformance <PRD>`, whatever the verdict. `--claimed` names the rung with or without its `(optional)` suffix at PRD altitude; at Epic altitude, whose ladder has no such rung, either spelling is re-prompted
- **The seventh condition reads the record's `Threats:` line as data, and fails closed on one it cannot read.** Only the header's lines, before the record's first `## ` heading, are read, a line opening `- **Threats:**` matched whole against `conformance-format` §2's two patterns, `[0-9]` in each, its `not read:` tail never parsed. A record with no such line passes — the line stands only where the run had threat input, so its absence is the normal case, unlike the coverage lines', and a record written before threats were traced has none — save one holding a `## Threats` section with no `Threats:` line, since the run writes the section only beside the line. `not traced — update workflows-core` fails, as does an `open` count above zero; more than one such line, one matching neither pattern, or a `## Threats` section with no `Threats:` line fails with `threats line unreadable`. No other count holds the rung — `unanswered`, `review due` and `stale` are no delivery fact — and no text of the line reaches the `Delivery:` reason but its matched `open` count

## `/implement`'s gate on its unit's specification and design

- **A fresh keyed `/implement` stops where the unit it builds has no `specification.md` or `design.md` on the default branch** — a first run for the unit, a later one for a unit already built, a companion run and a tasks-only run alike. Once the unit is settled it gates the specification and then the design, each path whether or not the file is on disk, and stops once, on the specification where both are missing — on `absent`, `IMPLEMENT_SPEC_NOT_HANDED_OFF` or `IMPLEMENT_DESIGN_NOT_HANDED_OFF` where the file is in the unit's folder, `IMPLEMENT_NEEDS_SPEC` or `IMPLEMENT_NEEDS_DESIGN` where it is not, naming what `workflows-core:phase-handoff` §4.4's *The first missing document* names and the direct run; on a specs tree that is no git repository, and on a unit folder outside the specs repository's work tree, which no gate runs on, the folder's own file decides (`/dev-workflows:implement` Phase 0, *Gate the unit's specification and design*; `phase-handoff` §3.4's `/implement` row, which records the decision). A direct run gates neither file, and a resumed run makes none of the four stops: it gates the paths its earlier run recorded (*Resuming*, step 7). `/implement <PRD>` lists only units whose specification and design are both on the default branch, naming each Epic it leaves out with what it needs first, and never auto-selects a unit that holds an implementation record, asking instead (Phase 0, *The listing test* and *Each Epic left out is counted and named*; *Epic folders, and one unit left*).
