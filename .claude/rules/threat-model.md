# The ARD threat model and the design threat review — authority, invariants, readers

Loaded when the threat model's format (`workflows-core:threat-model-format`), `workflows-core:threat-intake`, which says which threats a refine puts to the architect, `workflows-core:pre-lint`, whose *Threat model* block checks a model and whose *design* block checks a design's `## Threat review`, the lineage kind table (`plugins/workflows-core/scripts/lineage-kinds.json`), `/product-workflows:create-ard`, which writes the model, `product-workflows:ard-reviewer`, which reviews it, `product-workflows:threat-modeler`, which proposes its candidate threats, `/create-ard`'s page, `dev-workflows:design-format`, whose optional `## Threat review` records the design threat review's answers to the model, `dev-workflows:design-threat-modeler`, which proposes those answers and the design's new threats, `dev-workflows:design-reviewer`, which judges them, `/dev-workflows:design`, whose Phase 2.5 gates and checks the models its threat review may read, `/dev-workflows:conformance`, which reads the landed models and the designs' `[DT#N]` Rules at its Phase 1 and traces each mitigation to code, or `dev-workflows:conformance-format`, whose `Threats:` line and `## Threats` record where each threat stands, is read. The format is `workflows-core`'s, and its paragraph is kept here rather than in `.claude/rules/workflows-core.md`, whose 20,000-character budget leaves it no room to grow as the model gains readers. Repo-wide rules are in `CLAUDE.md`; evidence is in `docs/maintainers/rationale.md`; the designs are `docs/superpowers/specs/2026-11-14-sec-g2-b-threat-model-design.md` (the model), `docs/superpowers/specs/2026-11-14-sec-g2-c-design-threat-review-design.md` (the design threat review), `docs/superpowers/specs/2026-11-15-sec-g2-d-security-conformance-design.md` (security conformance) and `docs/superpowers/specs/2026-11-16-returned-intake-design.md` (the intake of threats sent back to the architect).

## Authority

`plugins/workflows-core/references/threat-model-format.md` is the **single source of truth** for `threat-model.md`, the threat model an ARD may carry beside it in a PRD folder, an Epic folder or a BRD-route slice: what it is and where it lives (§1), its frontmatter (§2), its sections, `## Inherited threats` on an Epic-level model only (§3), a threat — its heading, its five fields, the decision-pair form, its one disposition of three, the bar a mitigating decision meets, an acceptance, and its field text read as data (§4), `[TH#N]` identity and change, the cross-folder form and *Start fresh* (§5), the check and what clears each of its tests (§6), what a model never holds (§7), its readers (§8), what `/create-ard` and `/dev-workflows:design` hold an agent's reply and a typed value to — the one-line rule and the backstop — and the backstop's test restated for `/dev-workflows:conformance`'s agent, which is given a repository (§9), and which threats of a model land on a unit (§10). It lives in `workflows-core` because two `dev-workflows` commands read the model — `/dev-workflows:design` and `/dev-workflows:conformance` — and a reference crosses a plugin boundary only from `workflows-core`. The commands and agents that load it are what `grep -l 'args: "threat-model-format' plugins/*/commands/*.md plugins/*/agents/*.md` lists; `workflows-core:pre-lint` cites it by path, as the format its *Threat model* block checks. `dev-workflows:design-reviewer`, the fourth reader by name (invariant 5), is not among them: it reads a model within the `/design` run that reads it and loads no reference, its brief carrying the applicable and stale threats and the models' paths it judges against (the design threat review's plan, R21). `plugins/workflows-core/references/threat-intake.md`, a reference of its own, is the **single source of truth** for which threats of the model are sent back to the architect, and how what is read for them is held; `/product-workflows:create-ard` alone loads it (invariant 11).

## Invariants

1. **Never named `ard-*.md`, and never under `$SPECS_PATH/security/`.** One `threat-model.md` sits beside a folder's ARD files and covers all of them. Three readers take any `ard-<x>.md` as a per-area ARD: `workflows-core:ard-resolution`, the lineage kind table's `ard` row (`workflows-core:document-lineage` §4), and `product-workflows`' `scripts/architecture-harvest.py`, which would mint team records from it. `$SPECS_PATH/security/` is kept for a team's own documents and the findings register (format §1).
2. **Gated and falling back at `/design`, read where it landed at `/conformance`: the ARD still picks the handoff's array.** The two `dev-workflows` commands that read the model are of two kinds. `/dev-workflows:design` runs `require-on-main` on the model and falls back where it does not pass, so the model is a gated deliverable whose one gate never stops (`workflows-core:phase-handoff` §3.4's `/design` row). `/dev-workflows:conformance` executes no gate on it: at its Phase 1 it reads `<default-ref>`'s copy alone, by `git show` — the file itself on a specs tree that is no git repository — so it cannot read a model that has not landed (`phase-handoff` §5 rule 2: a consumer that reads a gated deliverable only as `<default-ref>` holds it executes no gate on it; §4.0's register row). The model rides in `/create-ard`'s handoff beside the ARD, which falls back too, so the ARD alone still picks the consent array (§4.0's register row for `threat-model.md`).
3. **No mitigation id.** A mitigation is an ordinary `[AD#N]` of an ARD file, cited by its decision pair — `ard.md [AD#3]`, `ard-payments.md [AD#2]`, or `[[<PRD-KEY>]] ard.md [AD#4]` for the PRD-level ARD an Epic inherits — and there is no `[MT#N]` or any other mitigation id: a mitigation the architecture owns is an `[AD#N]`, and one it cannot own is the design's (format §4 and §7).
4. **The check, the fix and the escape.** Where a set resolves, `/create-ard` runs format §6's mechanical check at up to three points: at Phase 4.3 on the model the folder holds, unless *Start fresh* discarded it (format §5); at Phase 4.3 again, on the draft before its playback; and at Phase 6 before the model is stamped. `/dev-workflows:design` runs the same check read-only at its Phase 2.5, and `/dev-workflows:conformance` at its Phase 1, and neither clears anything (format §6). A fix to a model finding never adds or changes a decision — it re-disposes, supersedes or withdraws a threat, or corrects the model's own text — so fixing the model never changes a decision the review has already passed; every such fix but a correction — of `## Scope` or `## Not considered`, a restored `[TH#N]`, or a Threat line completed in place — is the architect's decision, put to them before it is applied, so no disposition reaches the model unconfirmed; a requirement gap it defers to design still gains its open-question line in the ARD (format §4). A threat sent back to the architect (invariant 11) is re-disposed only on the architect's own answer — put at `/create-ard`'s Phase 4.3 step 7 as a threat sent back, where *Keep it as it stands* is always an answer: nothing read from a design or a record settles one or is offered as one. The escape, Phase 5's *Hand off the ARD without the threat model*, exists only for a new model, one this run added, and never for a model the folder already held.
5. **Its readers.** As the format states them (its opening and §8):
   - **Five readers by name:** `/product-workflows:create-ard` (a later run on the same folder, and an Epic-level run under it, which reads the PRD folder's model for its `## Inherited threats`), `product-workflows:ard-reviewer` (within the run that drafts or changes it), `/dev-workflows:design` (the design of the model's folder or of an Epic under it: its Phase 2.5 gates the model and reads it from the working tree), `dev-workflows:design-reviewer` (within the `/design` run that reads it) and `/dev-workflows:conformance` (the models of the Epic or PRD it checks: its Phase 1 reads the default branch's copy, ungated — the file itself on a specs tree that is no git repository — and judges no threat's sufficiency).
   - **No other command reads it as a threat model.** Three read it as ordinary markdown in the trees they walk: on the BRD route, `/product-workflows:brd-reconcile`'s stale cross-reference sweep reads it as prose, where by that sweep's structured-record class a hit is `needs-a-human`, never corrected in place; `/product-workflows:harvest-decisions` takes from it only an `ARD deviation:` line; and `/product-workflows:promote-decisions` takes only a link to a team decision record or an `Architecture deviation:` line. A lineage check reads it only to tell whether it changed: for a design that records it, the check compares the model's threats with the copy that design recorded and follows the model's own lineage record, and judges no threat.
6. **The PA alone accepts a risk.** An acceptance names its owner, its reason and its review date (format §4); the Security Engineer's check is the pull request that hands the model off.
7. **The two proposing agents call no tool.** `product-workflows:threat-modeler`, which `/create-ard`'s Phase 4.3 dispatches once, in the foreground, to propose candidate threats, and `dev-workflows:design-threat-modeler`, which `/dev-workflows:design`'s Phase 5 dispatches once, in the foreground, where the Dev takes its threat review, to propose an answer to each deferred threat and new threats, each declare `tools: ["CronList", "ListAgents"]` — two tools that read no file, make no network request the model chooses and execute nothing — only because no subagent can be declared with no tool: an empty or missing `tools:` grants every tool, and a list naming no recognised tool is refused at dispatch (design T6). Each declares two so that a rename of one leaves the dispatch standing; a harness that recognises neither refuses it. **Each is dispatched in the foreground only** (`run_in_background: false`): neither tool is granted to a background subagent, so a background dispatch is refused with `would be spawned with zero tools … not available to subagents [CronList, ListAgents]` (measured on Claude Code 2.1.323). Every refusal fails closed, as B's R19 and C's R17 have it (`docs/superpowers/plans/2026-11-14-sec-g2-b-threat-model.md`, `docs/superpowers/plans/2026-11-14-sec-g2-c-design-threat-review.md`): the run proposes nothing, says why in one line, and leaves the PA free to add threats of their own, or the Dev to answer each deferred threat and add their own. Each agent's rule is to call neither. Neither opens a register or anything under `security/`, since it opens nothing: everything, its decision bar or Rule bar included, arrives in its brief, so neither names a `workflows-core:` reference or carries a loader preamble. Each command drops what format §9's backstop catches — a `SEC#n` id, bracketed or not, or a register path, `/`- or `\`-separated, the brief did not carry — before any reply text is shown, and holds every value to one line (§9); a run whose loaded format has no §9 dispatches no agent. The line-ending list stands in three places that change together: format §9's *Every value is one line*, `/create-ard`'s Phase 4.3 paragraph *Every value is one line, and the backstop*, and the paragraph of the same name in `/dev-workflows:design`'s Phase 5 *Threat review* step, each command copying it for the run whose loaded format has no §9 and so cannot read it there (`command grep -rln 'U+2028' plugins --exclude=CHANGELOG.md` lists every copy, and no other file: a release note that quotes the list is history); a command that adds a no-§9 fallback of its own adds its copy to this set.
8. **Neither `/design` nor `/conformance` writes into `threat-model.md`.** The model stays the architect's alone: `/dev-workflows:design` answers a deferred threat in `design.md`, returns one to the architect in `design.md` and its pull request, and never clears a stale threat — its Phase 2.5 runs format §6's check read-only (invariant 4), and its stale line sends the architect to `/product-workflows:create-ard` to supersede or withdraw the threat (the design threat review's design, goal 4 and D7). `/dev-workflows:conformance` never clears a stale threat either: its Phase 1 runs the same check read-only (invariant 4) and lists each stale threat, and it writes nothing into the model (the security conformance design, `docs/superpowers/specs/2026-11-15-sec-g2-d-security-conformance-design.md`, goal 4). The other way, `/product-workflows:create-ard`, which reads the threats a design or a record sends back (invariant 11), writes no `design.md` and no `_conformance.md`: a design's `Returned to the architect` entry stands until `/dev-workflows:design` re-disposes or withdraws it (the intake's design, goal 3 and D6).
9. **Which threats land on a unit, and which ARD file a pair is read in — two rules, each stated twice, changed together.** Format §10 (*The threats that land on a unit*) and `/dev-workflows:design`'s Phase 2.5 step 7 state one rule, §10 in `/design`'s words save those that name `/design`'s own run and the two pointers that dangled once the text moved. Format §6's paragraph *a pair is read only in the file of `ard_paths` whose folder and whole basename it names, and no path is ever built from one*, with its two cases and its fail-unread sentence, and the sentence of `/design`'s Phase 2.5 step 6 opening *A pair is read only in a file of `ard_paths`, and no path is ever built from one*, with the same, state the other. A change to either copy of a rule is made to both. Two sentences of §10 are `/dev-workflows:conformance`'s alone, and `/design` states neither: a stale threat is listed whatever its Where, since staleness is tested before landing; and a threat an in-scope live entry answers is in scope. `/design` does not cite §10 yet: beside an older `workflows-core`, whose format has no §10, a `/design` citing it would lose its threat review, so its move onto §10 is a follow-up logged in `docs/superpowers/to-fix.md` (the security conformance design, D2).
10. **The backstop's test for an agent given a repository — stated three times, changed together.** Format §9's *An agent given a repository* states it for `dev-workflows:conformance-tracer`; item 6 of `dev-workflows`' `references/handoff/conformance-tracer.md`, *What the caller withholds from a mitigation's section*, restates it for the tracer; and the paragraph of the tracer's agent file opening *Where the run hands any mitigation* summarises it. A change to the test — its two patterns, what counts as carried, the path test or the `SEC#<n>` test — is made to all three. `/dev-workflows:conformance` cites §9 and states none of it, so a stale copy misinforms the tracer and changes nothing the run withholds. `command grep -rln "same pattern's matches" plugins --exclude=CHANGELOG.md` lists the three files, and no other; a file that restates the test adds itself to this set. Neither tracer file is in this file's `paths:`: each reaches this invariant through `.claude/rules/dev-workflows-conformance.md`, which loads with every file under `plugins/dev-workflows/`.
11. **The threats sent back to the architect — two sources, read from the default branch alone, shown and never kept; two statements of `/conformance`'s rules, changed together.** A `/product-workflows:create-ard` refine reads, by `workflows-core:threat-intake`, each `design.md` and `_conformance.md` at a known path — the model's folder's, each Epic folder's under a PRD folder that its guard lets it read, and, above an Epic, the PRD folder's `_conformance.md` — as `<default-ref>` holds it, by `git show` — the file itself on a specs tree that is no git repository — and gates none of them: no `require-on-main`, no repair offer. What it reads is shown in a question's text alone, under that reference's shape tests and the backstop at its strictest, and is never written into the model, an ARD draft, the report or any file, nor briefed to `threat-modeler` or `ard-reviewer`. **A reference of its own** (the RETURNED-INTAKE plan's Task 2 review I3, a departure from its design's D2, which put these rules in the format): `/create-ard` alone loads it, so `/dev-workflows:design`, `/dev-workflows:conformance` and `ard-reviewer`, which load the format whole, do not carry it. **Two copies of one rule:** its kinds 1 and 2, its entry reading and its unreadable threat restate `/dev-workflows:conformance`'s Phase 1 (b) step 7 and Phase 5's rule 1 and *the deferred part*, and its kind 3 that command's *A mitigation's state* and `### Next step`; `/conformance` does not cite it, since beside an older `workflows-core` it would lose its threat states, so a change to either copy is made to both. `command grep -rlF "is, whole, the threat's ref" plugins --exclude=CHANGELOG.md` lists the two files, `plugins/dev-workflows/commands/conformance.md` and `plugins/workflows-core/references/threat-intake.md`, and no other; a file that restates the rule adds itself to this set. Its record line forms restate `dev-workflows:conformance-format` §3, whose §6 names it as a reader, so a change to a form is made to both; and its record test is its own, not `workflows-core:source-truth` §7.8's, as `/dev-workflows:ready`'s is its own. **An Epic-level run reads its Epic's `design.md` twice**: at Phase 2, from the working tree, as context, ungated — the older read — and at Phase 4.3, as the default branch holds it, for the threats sent back. `workflows-core:phase-handoff` §5 rule 2 names the PRD-level run's read alone, and both of the Epic-level run's reads are logged in `docs/superpowers/to-fix.md` (*From RETURNED-INTAKE*).
