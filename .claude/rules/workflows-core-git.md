# workflows-core — git authorities and specs-repo git invariants

Loaded when a git reference (`workflows-core:specs-repo-git`, `workflows-core:phase-handoff`, `workflows-core:read-only-repos`, `workflows-core:grounding-format`, `dev-workflows:code-handoff`) or any command, reference or agent file of any plugin is read: every command that writes into `$SPECS_PATH` runs `specs-preflight` and `commit-artifacts` (`CLAUDE.md` § Hard constraints), and the references and agents those commands load invoke the same entry points or emit and consume `prep`, so these rules bind an edit to any of them. Split out of `.claude/rules/workflows-core.md` to keep that file under 20,000 characters; repo-wide rules are in `CLAUDE.md`; evidence is in `docs/maintainers/rationale.md`.

## Authorities

`plugins/workflows-core/references/specs-repo-git.md` is the **single source of truth** for the two git entry points the family runs against `$SPECS_PATH` — `specs-preflight` (run start: flush leftover artifacts, retry an unpushed artifact commit, settle the branch) and `commit-artifacts` (terminal: stage the bounded artifact paths, commit, push). It owns the bounded write authority (four directory shapes and five single files — the newest directory shape is `$SPECS_PATH/documentation/<docs-repo-slug>/…`, where a documentation run that has no PRD and never will files its cost and feedback (D19), named by what it is rather than by its position in the list, because five sites once disagreed over whether it was the second or the fourth — and `<docs-repo-slug>` is defined once, in §2.1 beside that shape (the docs repo's `OWNER_REPO`, falling back to a directory name, then flattened by one byte-wise substitution in the C locale that turns every byte outside `[A-Za-z0-9._-]`, `/` included, into `-`), because the staging classifier admits exactly one path segment there and anything else would be staged by nothing and left dirty forever — **the quoting half of that reason is retired, not the rule**: step 1 now reads `git status --porcelain -z`, whose records are never quoted, so the flattening stands on the one-segment property alone; `^(idea|prd|ard|spec|design|ready|brd|frames|kb)/` branches only — nine prefixes, fewer than there are producers because two are shared: `brd` by all six commands of the BRD-to-PRD route and by `/brd-proposal`, and `prd` by `/create-prd`, `/update-prd`, `/prd-proposal` and, on the idea route, `/prd-ground` — `phase-handoff.md`'s `prefix` input row is the authority on which producer takes which), the three guards and their four-part notice contract, the branch-disposition table with its §3.5 `branch-key` resolution (a branch's key is resolved against the run's own key set, never extracted by pattern; `phase-handoff.md` §2.2 rule 3 cites the same entry point, so a branch the preflight stayed on is the branch the handoff reuses), and the `Specs repo:` outcome line. It bounds the plugin's **bookkeeping** paths only — a phase's **deliverable** (PRD, ARD, `specification.md`, `design.md`, `idea.md`, `_readiness.md`) is `workflows-core:phase-handoff`'s to commit, push, and hand off. Consumed by the twenty-nine commands that write into `$SPECS_PATH` — every one of the family's thirty-two except `/statusline`, `/docs-profile` and `/docs-serve` (count it by ``grep -l 'commit-artifacts` entry point' plugins/*/commands/*.md``, which returns the same twenty-nine: all five of `dev-workflows`'s, all fourteen of `product-workflows`'s, five of `docs-workflows`'s seven and five of `workflows-core`'s six). ([why](../../docs/maintainers/rationale.md#recipe-returns-wrong-answer)) Hard rules: every git call is `git -C "$SPECS_PATH"` and never a `cd`; `git add -A` is never issued at repository scope; never force-push, never `branch -D`, never merge/rebase/reset, never delete an `index.lock`; never fatal.

`plugins/workflows-core/references/phase-handoff.md` is the **single source of truth** for the two phase-boundary git entry points — `handoff-to-main` (§2, producer) and `require-on-main` (§3, consumer: an eleven-state gate, rows H/I/G/A/B/C′/C″/C/D/E/F) — plus the nine-prefix branch authority (`^(idea|prd|ard|spec|design|ready|brd|frames|kb)/`, §1 rule 3), §3.4's row-F delegation table (an `absent` gated input falls back to the caller's own pre-existing behaviour, never a new prerequisite — the eight consumers that stop instead, `/design`, `/prd-ground`, `/brd-split`, `/brd-interview`, `/brd-package`, `/brd-reconcile`, `/prd-proposal`, `/brd-proposal`, each gate an input that was never optional; and on the BRD route `/create-prd`, `/create-ard` and `/specify` split row F on a slice's `decisions.md` — no register falls back, while one present in the folder and on no ref stops), the §4.1 `Phase handoff:` outcome line, and the §4.3 consent choice. It inherits four of `specs-repo-git.md`'s hard rules — **the first three unchanged and the fourth widened**, §1 rule 4 there adding `stash` and `checkout --` to the destructive-command list because a deliverable commit runs where the user's own work may be uncommitted and both of those discard it silently — and deliberately diverges on three (§1 rules 5–7: `require-on-main` is fatal by design, the deliverable commit carries a `Co-Authored-By` trailer, and `handoff-to-main` runs only behind the caller's own consent choice, never prompt-free). Eighteen producers call `handoff-to-main` — `/idea`, `/create-prd`, `/update-prd`, `/create-ard`, `/specify`, `/design`, `/implement`, `/ready`, `/frames`, `/brd-intake`, `/prd-ground`, `/brd-split`, `/brd-interview`, `/brd-package`, `/brd-reconcile`, `/prd-proposal`, `/brd-proposal`, `/harvest-decisions`; fourteen consumers call `require-on-main` — `/create-prd`, `/create-ard`, `/specify`, `/design`, `/implement`, `/epics`, `/ready`, `/prd-ground`, `/brd-split`, `/brd-interview`, `/brd-package`, `/brd-reconcile`, `/prd-proposal`, `/brd-proposal` (`/update-prd` deliberately excluded — the PRD it updates is the artifact it resolves from the tree, not a prior phase's deliverable it waits on; `/brd-intake` also excluded — it is the route's first command and consumes no prior phase's deliverable).

`plugins/workflows-core/references/read-only-repos.md` is the **single source of truth** for read-only repository mounts — the detection probe (`test -w` on the repo and `.git`, plus the `Read-only file system` error as a secondary trigger), what read-only mode skips (`fetch`/`pull`/`switch`/`remote set-head`, and the dirty-tree gate), write-free ref resolution and reading (`ls-tree`, `git grep <ref>`, `git show <ref>:<path>`), the default branch its scanner and docs-repository callers switch onto or cut a branch from (§3's **A switch takes the name**: the branch's name, `main`, never the `origin/main` ref the resolution yields, which `git switch` refuses — a caller that only reads may take the ref; `dev-workflows:code-handoff` §2.8 and `specs-repo-git.md` §3.2 keep their own ladders), the 14-day staleness / ahead-of-ref escalation trigger, and the `prep` output contract (`read_only`, `scanned_ref`, `ref_committed_at`, `head_divergence`). Consumed by `code-scanner` and `diff-summarizer`, which emit the `prep` block; `docs-grounder`, `code-grounder`, `grounding-verifier` and `docs-auditor` (which reads each repository at the `prep.scanned_ref` `code-scanner` returned) also consume it but return a digest or a finding rather than a `prep` block (`docs-grounder` reads §1–§4 only — read-only detection, what to skip, ref resolution, reading at the ref). The nine commands that dispatch the `prep`-emitting agents act on the returned `prep.read_only` via `workflows-core:escalation-rules`; `/prd-ground` cites `read-only-repos.md` directly for the read-only posture its Phase 1 holds toward every repository it resolves, and `/document`, `/docs-profile`, `/docs-brand` and `/docs-init` cite §3 for the default branch each resolves before cutting a branch in a docs repository. Nothing in it restricts a writable mount: `git switch` and `git pull --ff-only` remain sanctioned prep on a writable clone.

## Invariants

### Specs-repo git (`workflows-core:specs-repo-git`)

- Every git invocation is `git -C "$SPECS_PATH"` — the working directory is NEVER changed; fifteen of the twenty-nine callers resolve or run inside an **implementation** repository — a code clone under `$REPOS_PATH`, or the cwd's own repo for `/implement`, `/upgrade` and `/vuln` — which is the criterion, not "any repository that is not the specs repo": `$DOCS_PATH` is a read-only search base nine of the twenty-nine also resolve for docs grounding (`/brd-intake`, `/create-prd` and `/update-prd` among them), and counting it would make the number say nothing about where a stray `git` could land. Fifteen is all twenty-nine minus the fourteen that touch no implementation repository at all (`/brd-intake`, `/brd-split`, `/brd-interview`, `/brd-package`, `/brd-reconcile`, `/prd-proposal`, `/brd-proposal`, `/create-prd`, `/update-prd`, `/frames`, `/feedback`, `/prompt`, `/prompt-brainstorm`, `/prompt-grill-me`) — the two halves are equal at twenty-nine, which is arithmetic rather than a typo. **Resolving a clone read-only already counted before this was written**, which is what puts `/document` and `/release-notes` in the first half on the strength of `diff-summarizer` alone; on the same reading `/docs-init` (which lists `${REPOS_PATH:-/workspace}` clones and runs `git -C <repo> tag --list` in one), `/docs-brand` (which resolves one clone and reads it with no `git` at all) and `/docs-audit` (which dispatches one `code-scanner` per repository the profile's `source_repos[]` records) joined it. Do not re-derive this number from *write* access — that reading gives a different answer and contradicts the criterion this sentence states
- Staging is by enumeration over `git status --porcelain -z --untracked-files=all`, never by glob; `git add -A` is only ever issued as `git add -A -- <literal paths>`, and `-A` is required because cost reconciliation deletes a pending file. **`-z` is not optional in any porcelain read whose path is then matched or staged** — `--porcelain` quotes a path carrying a space, a `"`, a `\` or a non-ASCII byte, and a classifier anchored at `^` puts every such path in OTHER, silently. The same requirement binds `workflows-core:phase-handoff` §2.3, `dev-workflows:code-handoff` §2.2 with its three callers' `pre_existing_dirty` captures, and `workflows-core:grounding-format` §4 step 3. A read that only tests the output for emptiness is unaffected and keeps the plain form
- Only `^(idea|prd|ard|spec|design|ready|brd|frames|kb)/` branches are the plugin's to switch away from or delete; any other **named** branch is left alone and the artifacts are committed on it
- `workflows-core:phase-handoff` extends this reference for a phase's **deliverable** (as opposed to bookkeeping) commit: it inherits four of these hard rules — **three unchanged, and rule 4 widened there** to add `stash` and `checkout --`, which is not redundancy to strip: a deliverable commit runs where the user's own work may be uncommitted, and both of those discard it silently — but deliberately diverges on three (§1 rules 5–7) — `require-on-main` IS fatal by design, its commit DOES carry `Co-Authored-By`, and `handoff-to-main` DOES open a pull request, all gated behind the caller's own §4.3 consent choice
- **Two run-wide flags make `commit-artifacts` skip, and only one of them is a guard.** Detached HEAD is the one blocking guard: it sets `specs_git: blocked` for the whole run, `commit-artifacts` skips on that flag, and the notice fires at both ends. A misplaced `$SPECS_PATH` sets `specs_git: misrooted`, through `specs-repo-git` §3.1's notices or `workflows-core:addressing` §3 `specs-root-check`'s stop. Under that one the preflight performs no write — its fetch and §3.5's branch classification still run, and a row that would switch stays and reports — `commit-artifacts` skips, `handoff-to-main` refuses the handoff (§4.3 says so above the array), `require-on-main`'s row C offers no repair, and every emitter of the tail (cost, feedback, follow-ups, `resume.md`) falls to report-only. None of those four entry points switches a branch or commits there, though a command that changes code or documentation still branches in the repository it changed; what the command itself wrote (its deliverable, `implementation.md`, a draft) stays written and uncommitted. A dirty unrelated path (G1) does NOT block the terminal commit
- Never force-push, never `branch -D`, never merge/rebase/reset, never delete an `index.lock`, never open a PR, never call a REST API
- Never fatal — every failure is reported and the run continues
- The artifact commit carries no `Co-Authored-By` trailer; each artifact already carries its own `author:` field
- The canonical terminal order is deliverable + handoff → feedback → follow-ups → cost → `resume.md` → `commit-artifacts` → the run's last printed output. What binds every command is the **emitter tail** — feedback → follow-ups → cost → `resume.md` → `commit-artifacts`; a command's deliverable-side finish may sit anywhere relative to the tail, including between its members, at whatever point suits it (`/document`'s conditional `Phase 8.5 — Finish & handoff` sits between feedback and follow-ups). The one exception is a phase that cedes control (`/prompt-brainstorm`'s hand-off to `superpowers:brainstorming`, `/prompt-grill-me`'s long interactive grill): there `commit-artifacts` runs immediately **before** the hand-off, because a commit placed after it would never execute (`workflows-core:specs-repo-git` §4)
- Exactly one `Specs repo:` outcome line per run, wherever `commit-artifacts` ran — at the end, or immediately before a hand-off that cedes control (`/prompt-brainstorm`, `/prompt-grill-me`); a guard notice is repeated in full there, never only at the preflight
