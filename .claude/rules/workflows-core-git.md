# workflows-core — git authorities and specs-repo git invariants

Loaded when a git reference (`workflows-core:specs-repo-git`, `workflows-core:phase-handoff`, `workflows-core:read-only-repos`, `workflows-core:grounding-format`, `dev-workflows:code-handoff`), `scripts/session-branch.py` (`specs-repo-git` §8's plumbing and §4 step 6's replay), `scripts/specs-git.py` (the two references' primitives: the §2.1 status classifier, `branch-merged`, `branch-key`, `push-scope`, `owner-repo` and `mode`; `workflows-core:addressing` §3's `specs-root-check`; and `specs-repo-git`'s two entry points whole, as `start`, `end`, `replay` and `declined`) or its two modules, `scripts/specs_git_state.py` (the run's state record) and `scripts/specs_git_lines.py` (every line the script prints, as a template), the `specs-git` skill that runs it (`skills/specs-git/`), or any command, reference or agent file of any plugin is read: every command that writes into `$SPECS_PATH` runs `specs-preflight` and `commit-artifacts` (`CLAUDE.md` § Hard constraints), and the references and agents those commands load invoke the same entry points or emit and consume `prep`, so these rules bind an edit to any of them. Split out of `.claude/rules/workflows-core.md` to keep that file under 20,000 characters; repo-wide rules are in `CLAUDE.md`; evidence is in `docs/maintainers/rationale.md`.

Split out for the same budget: the `read-only-repos` authority → `.claude/rules/workflows-core-read-only.md`, which loads with that reference and with every agent, command and reference its paragraph names; the `phase-handoff` authority → `.claude/rules/workflows-core-handoff.md`, which shares this file's `paths:`.

## Authorities

`plugins/workflows-core/references/specs-repo-git.md` is the **single source of truth** for the two git entry points the family runs against `$SPECS_PATH` — `specs-preflight` (run start: print the run's `Environment:` line, fast-forward a default branch that is behind its remote, flush leftover artifacts, retry an unpushed artifact commit, settle the branch) and `commit-artifacts` (terminal: fast-forward a default branch that is behind, stage the bounded artifact paths, commit, and push only the default branch, a plugin branch or §8's session branch, and only while every commit the push would publish, measured against the branch's own remote ref (and, on the session branch, the default ref too), is a session-file commit — or, on the session branch, one of its own merges — §4 step 5's `push-scope`, which §3.4's retry applies too, to every local plugin branch — and only to `origin`, never against the user's own push configuration, to a branch the remote deleted (save §8's session branch, which §8.4 pushes again, recreating it), to a plugin branch `origin` does not have yet, or to one whose push `origin` refused, which it records ([why](../../docs/maintainers/rationale.md#specs-push-target)); where `origin` rejects that push, or one §3.4's flush or retry makes, as non-fast-forward outside §8's mode, §4 step 6 replays the commits onto `origin`'s branch with `session-branch.py replay`, touching the checkout only in one locked `update-ref` and `read-tree -m -u` move, and pushes, a security register both sides changed rebuilt by the `register.py` its caller hands over as `register_rebuild` (§7) — and where it cannot, nothing moves and §6's row names the user's `pull --rebase --no-autostash`, save where another session switched the checkout during the move, where it names none). It owns the bounded write authority (five directory shapes and five single files — the newest directory shape is `$SPECS_PATH/security/<repo-slug>/`, the security register `/security-workflows:scan` keeps per code repository, with that command's keyless cost entries beside it (`workflows-core:cost-emission` §8), its own paths only (`runs/`, `scans/`, `dev-workflows/`, `register.json` and `register.md`, one shape written with an alternation, so a team's own document under `security/` is never staged), and the newest single file a unit's `_security.md`, that command's note in the unit's folder (`workflows-core:security-register-format` §1); the documentation shape, `$SPECS_PATH/documentation/<docs-repo-slug>/…`, is where a documentation run that has no PRD and never will files its cost and feedback (D19), named by what it is rather than by its position in the list, because five sites once disagreed over whether it was the second or the fourth — and `<docs-repo-slug>` is defined once, in §2.1 beside that shape (the docs repo's `OWNER_REPO`, falling back to a directory name, then flattened by one byte-wise substitution in the C locale that turns every byte outside `[A-Za-z0-9._-]`, `/` included, into `-`), because the staging classifier admits exactly one path segment there and anything else would be staged by nothing and left dirty forever — **the quoting half of that reason is retired, not the rule**: step 1 now reads `git status --porcelain -z`, whose records are never quoted, so the flattening stands on the one-segment property alone; `^(idea|prd|ard|spec|epics|design|ready|brd|frames|kb|conformance)/` branches only — eleven prefixes, fewer than there are producers because producers share them, `conformance` by `/conformance` alone: `brd` by all six commands of the BRD-to-PRD route and by `/brd-proposal`, `prd` by `/create-prd`, `/update-prd`, `/prd-proposal`, `/docs-workflows:release-notes` and, on the idea route, `/prd-ground`, `kb` by `/harvest-decisions` and `/promote-decisions`, and `spec` and `design` by `/implement`'s conformance handoff beside `/specify` and `/design` — `phase-handoff.md`'s `prefix` input row is the authority on which producer takes which), the three guards and their four-part notice contract, the branch-disposition table with its §3.5 `branch-key` resolution (a branch's key is resolved against the run's own key set, never extracted by pattern; `phase-handoff.md` §2.2 rule 3 cites the same entry point, so a branch the preflight stayed on is the branch the handoff reuses), `branch-merged`, the merged test B2 and the handoff's branch reuse share (ancestry, then a rebase, then a squash, then the branch's content by `merge-tree`; `/harvest-decisions` keeps `architecture-kb.md`'s own for `kb/` branches; it, `branch-key`, `push-scope` and §2.1's classifier run in `scripts/specs-git.py`), and the `Specs repo:` outcome line. **Both entry points run in `scripts/specs-git.py`, through the `specs-git` skill**, which every request reaches — `workflows-core`'s own commands call it, and the `reference` loader routes `specs-repo-git specs-preflight` and `specs-repo-git commit-artifacts` there — the reference staying the rule the script follows and the text a run follows by hand where the script cannot start; what the two share across the run lives in §7's state record, `~/.claude/dev-workflows/specs-git/<session id>/<command>.json`, keyed by `CLAUDE_CODE_SESSION_ID` and the command ([why](../../docs/maintainers/rationale.md#specs-git-state-record)). §8's session-branch mode — where the default branch takes no push (the opt-in `workflows.sessionBranch`, or the refusal record) — keeps session files on `session/<identity>` through `scripts/session-branch.py`, merged with the default branch and lifted and put back around every move of the checkout ([why](../../docs/maintainers/rationale.md#session-branch)). It bounds the plugin's **bookkeeping** paths only — a phase's **deliverable** (PRD, ARD, `specification.md`, `design.md`, `idea.md`, `_readiness.md`) is `workflows-core:phase-handoff`'s to commit, push, and hand off. Consumed by the thirty-five commands that write into `$SPECS_PATH` — every one of the family's thirty-eight except `/statusline`, `/docs-profile` and `/docs-serve` (count it by ``grep -lE 'commit-artifacts` entry point|args: "specs-repo-git commit-artifacts|workflows-core:specs-git", args: "end' plugins/*/commands/*.md``, which matches the three phrasings a command executes it by and returns the same thirty-five: all six of `dev-workflows`'s, all seventeen of `product-workflows`'s, five of `docs-workflows`'s seven, six of `workflows-core`'s seven and `security-workflows`' one). ([why](../../docs/maintainers/rationale.md#recipe-returns-wrong-answer)) Hard rules: every git call is `git -C "$SPECS_PATH"` and never a `cd`; its state of its own is §4 step 6's push-refusal record — a file under the common git directory, since a hardened container mounts `.git/config` read-only, with the older `branch.<branch>.workflowsPushRefused` key still read and written where the file cannot be — §8's one marked `info/attributes` block, `session-branch.py`'s per-worktree record of the files §8.3's overlay placed, and, outside every repository, `specs-git.py`'s state record of the run (§7); `git add -A` is never issued at repository scope; never force-push, never `branch -D`, never merge/rebase/reset — §8's checkout-free merges of the default branch into the session branch, and §4 step 6's replay, §1 rule 4's named exception, which does move the checkout, aside — never delete an `index.lock`; never fatal.

## Invariants

### Specs-repo git (`workflows-core:specs-repo-git`)

- Every git invocation is `git -C "$SPECS_PATH"` — the working directory is NEVER changed; eighteen of the thirty-five callers resolve or run inside an **implementation** repository — a code clone under `$REPOS_PATH`, the cwd's own repo for `/implement`, `/upgrade` and `/vuln`, or, for `/security-workflows:scan`, the cwd's own repo on a key run and the repository a path names — which is the criterion, not "any repository that is not the specs repo": `$DOCS_PATH` is a read-only search base ten of the thirty-five also resolve for docs grounding (`/brd-intake`, `/create-prd` and `/update-prd` among them), and counting it would make the number say nothing about where a stray `git` could land. Eighteen is all thirty-five minus the seventeen that touch no implementation repository at all (`/brd-intake`, `/brd-split`, `/brd-interview`, `/brd-package`, `/brd-reconcile`, `/prd-proposal`, `/brd-proposal`, `/create-prd`, `/update-prd`, `/harvest-decisions`, `/promote-decisions` (an architecture repository is not one), `/frames`, `/feedback`, `/prompt`, `/prompt-brainstorm`, `/prompt-grill-me`, `/diagnose-session`). **Resolving a clone read-only already counted before this was written**, which is what puts `/document` and `/release-notes` in the first half on the strength of `diff-summarizer` alone; on the same reading `/docs-init` (which lists `${REPOS_PATH:-/workspace}` clones and runs `git -C <repo> tag --list` in one), `/docs-brand` (which resolves one clone and reads it with no `git` at all) and `/docs-audit` (which dispatches one `code-scanner` per repository the profile's `source_repos[]` records) joined it. Do not re-derive this number from *write* access — that reading gives a different answer and contradicts the criterion this sentence states
- Staging is by enumeration over `git status --porcelain -z --untracked-files=all`, never by glob; `git add -A` is only ever issued as `git add -A -- <literal paths>`, and `-A` is required because cost reconciliation deletes a pending file. **`-z` is not optional in any porcelain read whose path is then matched or staged** — `--porcelain` quotes a path carrying a space, a `"`, a `\` or a non-ASCII byte, and a classifier anchored at `^` puts every such path in OTHER, silently. The same requirement binds `workflows-core:phase-handoff` §2.3, `dev-workflows:code-handoff` §2.2 with its three callers' `pre_existing_dirty` captures, and `workflows-core:grounding-format` §4 step 3. A read that only tests the output for emptiness is unaffected and keeps the plain form
- Only `^(idea|prd|ard|spec|epics|design|ready|brd|frames|kb|conformance)/` branches are the plugin's to switch away from or delete; any other **named** branch save the default branch is left alone and the artifacts are committed on it, never pushed — a push would publish whatever its owner has not pushed yet, `/implement`'s own code commit on a direct run from inside the specs repository included. In session-branch mode (§8) they go to the session branch instead, whatever the checkout stands on, and it is pushed. On the default branch and a plugin branch the push still waits on `push-scope`, so the user's own unpushed commits never go out with the artifacts ([why](../../docs/maintainers/rationale.md#specs-push-scope))
- `workflows-core:phase-handoff` extends this reference for a phase's **deliverable** (as opposed to bookkeeping) commit: it inherits four of these hard rules — **three unchanged against `$SPECS_PATH`** (rule 1 there adds only §2.7.1's template reads, in the caller's repository)**, and rule 4 widened there** to add `stash` and `checkout --`, which is not redundancy to strip: a deliverable commit runs where the user's own work may be uncommitted, and both of those discard it silently; nor does it take the exception this reference's rule 4 makes for §4 step 6's replay — but deliberately diverges on three (§1 rules 5–7) — `require-on-main` IS fatal by design, its commit DOES carry `Co-Authored-By`, and `handoff-to-main` DOES open a pull request, all gated behind the caller's own §4.3 consent choice
- **Two run-wide flags make `commit-artifacts` skip, and only one of them is a guard.** Detached HEAD is the one blocking guard: it sets `specs_git: blocked` for the whole run, `commit-artifacts` skips on that flag, and the notice fires at both ends; a run that refused before its preflight has the state tested by `commit-artifacts` itself (`specs-repo-git` §4 step 1). A misplaced `$SPECS_PATH` sets `specs_git: misrooted`, through `specs-repo-git` §3.1's notices or `workflows-core:addressing` §3 `specs-root-check`'s stop — and so do `workflows-core:session-hygiene` §7's `env-check`, on any run no longer in the environment its preflight's `Environment:` line printed, and §6's *Stop*, on a `/design` or `/specify` run that finds, at any of §6's three points, its environment no longer the one its session file recorded, or, at the last two, that record unreadable or missing, and `commit-artifacts` itself, where the record the run's start made stands (`specs-repo-git` §7) and the `SPECS_PATH` half of the run's `Environment:` line no longer matches the one its preflight printed — `session-hygiene` §7's environment change, met at the end. Under that one the preflight performs no write — its fetch and §3.5's branch classification still run, and a row that would switch stays and reports — `commit-artifacts` skips, `handoff-to-main` refuses the handoff (§4.3 says so above the array), `require-on-main`'s row C offers no repair, and every emitter of the tail (cost, feedback, follow-ups, `resume.md`) falls to report-only. None of those four entry points switches a branch or commits there, though a command that changes code or documentation still branches in the repository it changed; what the command itself wrote (its deliverable, `implementation.md`, a draft) stays written and uncommitted. A dirty unrelated path (G1) does NOT block the terminal commit, save on a merged plugin branch the preflight stayed on — G1, a failed `status`, a refused switch or an early stop — where `specs-repo-git` §4 step 1's merged-branch stay commits nothing while HEAD still stands there, and a later run's preflight leaves the branch before its flush and commits the files on the default branch; in session-branch mode no such stay is kept
- Never force-push, never `branch -D`, never merge/rebase/reset (§8's checkout-free merges into the session branch, and §4 step 6's replay of the plugin's own session-file commits onto a branch `origin` moved on, aside), never delete an `index.lock`, never open a PR, never call a REST API
- Never fatal — every failure is reported and the run continues
- The artifact commit carries no `Co-Authored-By` trailer; each artifact already carries its own `author:` field
- The canonical terminal order is deliverable + handoff → feedback → follow-ups → cost → `resume.md` → `commit-artifacts` → the run's last printed output. What binds every command is the **emitter tail** — feedback → follow-ups → cost → `resume.md` → `commit-artifacts`; a command's deliverable-side finish may sit anywhere relative to the tail, including between its members, at whatever point suits it (`/document`'s conditional `Phase 8.5 — Finish & handoff` sits between feedback and follow-ups). The one exception is a phase that cedes control — one that hands the session to another skill or opens an open-ended interactive stretch, whose commands `workflows-core:specs-repo-git` §4 names: there `commit-artifacts` runs immediately **before** the hand-off, because a commit placed after it would never execute
- Exactly one `Specs repo:` outcome line per run, wherever `commit-artifacts` ran — at the end, or immediately before a hand-off that cedes control (`workflows-core:specs-repo-git` §4's exception); a guard notice is repeated in full there, never only at the preflight
