description: Run every test suite step 1's detection table covers — all of them where a repository has several, and the test command the repository declares for itself where the table covers none — and return structured results for regression comparison. Operates in two modes — "capture" (run tests, record baseline) and "verify" (run tests again, diff against a provided baseline, return a structured regression report). Run every test suite step 1's detection table covers and return a structured result for regression comparison. A stack with no row there qualifies on none of its own build files: the run then takes the test command the repository declares for itself (capture step 1's last rule), and only where it declares none does it return `Framework: not detected` with counts 0 rather than failing, leaving the caller to decide what to do about it.

Operates in two modes. The caller must specify which mode to use.

---

## Mode: capture

Run every suite and return a baseline snapshot. Use this **before** making changes.

### Steps

1. **Detect every suite** — Scan the run's scan root, settled below, for **every** marker in the table and **never stop at the first match** — first-match-wins is what made a Rails app carrying an asset-build `package.json` report a JavaScript baseline for a Ruby suite, a wrong number rather than a missing one. A marker becomes a **candidate** only where its own qualifier holds, and a **row** is one candidate per qualifying directory however many of its markers sit in that directory — three Python markers in one directory are one pytest suite, not three. **Which of them that candidate's `### Suites` row records is fixed here rather than left to whichever the scan met first**, because that column is one of the verify pairing key's two operands (verify step 2) — and the pairing is the half nothing downstream repairs, verify step 5's prefix rewrite resting on it — so two calls recording different markers move it exactly as two scan roots do — the shape measured further down this step, on a tree that did not change at all: the row records the **earliest of that row's own Marker-column entries** present in the directory — `pyproject.toml` ahead of `setup.py` ahead of `pytest.ini`, `build.gradle` ahead of `build.gradle.kts`, `*.xcodeproj` ahead of `*.xcworkspace` — and, where that entry is a glob matching more than one file there, the lexicographically first of those filenames. **This is a rule about which marker is recorded and about nothing else**: the candidate, its directory and its command are what the clause above already settled, and adding a second marker of the same row to a directory that already qualified changes none of them. Two of those three rows carry more than one marker in one directory routinely — a `pyproject.toml` beside a `pytest.ini`, an `*.xcodeproj` beside its `*.xcworkspace` — and the Gradle pair, which a project rarely writes both of, falls under the same rule rather than needing one of its own. **What settles a row whose markers sit in different directories is the containment rule below, not a count**: this clause collapses a row's markers within a directory and says nothing across directories, which is where the rule that collapsed every row to one candidate lost a real suite. **The scan is rooted, is bounded, and records a directory per candidate.** Its root is the project root the caller named, in **either** mode — the request block's `repo:`, which callers send under their own label, `Project root:` throughout this plugin — and only where a **capture** call names none at all does it fall back to the working directory; verify has no fallback, its project root path being a required input, and no shipped caller relies on the capture fallback either. **A caller that names a root on the `capture` call names the same root on every `verify` call against that baseline, or the two runs have nothing to pair** — the same requirement the Scope paragraph below places on a `command_hint`, and resting on more: `### Suites` records each marker **as a path relative to this root** (step 5), and that path is one of the verify pairing key's two operands (verify step 2) — **the half nothing downstream repairs, which is why this rule survives verify step 5's prefix rewrite rather than being made redundant by it**: that step rewrites a moved prefix onto whatever suite step 2 paired it with, and two roots move every marker path at once, which is more than step 2's one-of-each fallback can pair wherever a framework names more than one suite — so two roots read every marker as moved, and every identifier of a framework naming more than one detected suite as missing, **on a tree that did not change at all**. Measured on `frontend/package.json` beside `backend/package.json`, both Jest, byte-identical between the two calls, the capture rooted at `frontend/` and the verify at the project root: **0** of 3 identifiers matched — with step 5's rewrite and without it alike — and all **3** landed in **Missing from run** ⇒ `REGRESSIONS`, where the same two calls given one root matched **5** of 5 and returned `OK`; on the one-suite shape the divergence still pairs, but `### Notes` then records that the suite moved from `package.json` to `frontend/package.json` when nothing moved. **Where a capture fell back to the working directory, that directory is the root the verify call must be given**, verify having none to fall back to. It descends into that root's subdirectories, because a front end in its own directory is a suite of this repository and not of some other project. It does **not** descend into a dependency, build-output or VCS directory: `node_modules/`, `vendor/`, `deps/`, `target/`, `build/`, `dist/`, `out/`, `coverage/`, `.git/`, `.gradle/`, `.venv/` and `venv/` are pruned wherever they occur, and a symbolic link is not followed. That pruning is not tidiness — measured on a root `pom.xml` beside a `frontend/package.json`, an unpruned scan returned **five** markers where two were real, and one of the three false ones was `frontend/node_modules/left-pad/package.json`, whose `scripts.test` is present and is not the `npm init` placeholder and which therefore **qualifies** under this table's own Candidate-when column: a dependency would have been baselined as one of this repository's own suites. **`deps/` and the unfollowed link were measured the same way**: Mix fetches every dependency into `deps/`, each with a `mix.exs` of its own — measured, one git dependency on `jason` put `deps/jason/mix.exs` and `deps/jason/bench/mix.exs` under an application's root — and a Flutter application links each plugin it uses into its platform directories, so after one `flutter pub get` a scan that follows links reached four plugin `pubspec.yaml` files under `linux/flutter/ephemeral/.plugin_symlinks/`, two of them beside `test/` directories holding 15 and 2 `*_test.dart` files, which qualify under this table's own Dart row. **Each candidate carries the directory its qualifying marker sits in**, recorded with it, and that is the directory **the run step** issues its command from — **capture step 2 and verify step 3 alike**, each stating the rule at its own number rather than importing it by one, because a bare "step 2" read in verify mode resolves to the pairing step, which issues no command at all. Where one row's qualifying markers sit in more than one directory, **containment decides, and it is asked of those directories rather than of their depths**: each qualifying directory of that row that no other qualifying directory of that row contains is a **candidate**, and every one that another does contain is named in `### Notes`, with the marker that qualified it, instead of becoming a candidate of its own — save for a unit's own manifest where one of the two divisions below carves that unit a row — a workspace's `package.json` under the `workspaces` division, a default member's `Cargo.toml` under the Cargo one — whose marker column names it there instead. Containment is strict, so two markers of one row in the same directory stay the one candidate the clause above already made them. **Containment is what makes that note safe**, because the constructs that cover a marker below them recurse from their own directory — a Maven or Gradle reactor over its modules, `pytest`'s own discovery, a Mix umbrella over its applications, a CMake root over the directories `add_subdirectory` reaches, and the two the divisions below run one unit at a time rather than in one command, npm's own `workspaces` field and a Cargo workspace — so there the containing marker is the one that covers the others rather than the one that hides them, and taking each directory as a suite of its own would run a multi-module reactor's tests once at the root and again per module and sum them twice. **That safety is about the run and about the identifiers alike, and those six constructs buy the second half two different ways**: a reactor's identifiers are fully-qualified class names, `pytest`'s are rootdir-relative paths, a Mix umbrella's carry each test's module and a CMake root's are the names `ctest` registered, each carrying the contained unit inside the identifier, while the `workspaces` and Cargo divisions carve a row per unit and so never collapse two units into one list at all — **wherever that division runs, which the wrapper rule below is asked before**: a candidate that rule folds is not divided, so its units run under that recipe's one command rather than one apiece — which is what the clause above about running one unit at a time is scoped to — and do collapse into one list, and its note is the marked kind capture step 5 gives a fold rather than the unmarked one this clause is about. **A Cargo workspace needs the division for it and does not get it from the identifier**, which is the measurement that put it on this side rather than the reactor's: `cargo test` at the root prints each test as `<module path>::<name>` with nothing in the line naming the crate, so two members that name a test alike mint one identifier — measured on Rust 1.98.1 / cargo 1.98.1, with the figures at the division below rather than repeated here, and with the collision arriving from the toolchain's own template rather than from anything a project did. The division below is what keeps those apart, and it is available here because `cargo test -p <name>` runs one member and `cargo metadata --no-deps` enumerates them, where the wrapper rule below has a `make test` that runs once by construction and so measures and refuses three ways out instead. **Where the containing command does not recurse, the contained marker is genuinely not run, and the note is what that buys rather than a reason to run both**: a `package.json` carrying a `scripts.test` and no `workspaces` field runs its own script and nothing beneath it — `workspaces` being npm's own answer to that shape, and what the division below carves into this row's several commands; `go test ./...` matches only packages of the module it is run in, measured on Go 1.24.0, where a root module beside a `sub/go.mod` ran its own two tests and never `sub`'s three and `go list ./...` returned the root module alone; and a **Cargo workspace member outside the default set** is one `cargo test` at that root never reaches, which is why the division below carves rows for the default set and leaves the rest here — measured twice, on a root declaring `default-members = ["crates/alpha", "crates/beta"]` where a bare `cargo test` ran neither of the third member's tests, and on a root that is both a package and a workspace, where cargo makes the root package the whole default set and a bare `cargo test` there never ran the sub-crate's. **The six rows measured below add six more**: a PHPUnit configuration over a nested one — measured, the outer run reported 7 tests and never the nested configuration's 1; a plain `mix.exs` over a nested project and a `pubspec.yaml` over a nested package, each measured the same way; a build carrying `project/build.properties` inside another sbt build, which the outer `sbt test` never ran (measured); a test project whose directory holds another's, `dotnet test` naming exactly one project file; and a qualifying `CMakeLists.txt` in a directory the root's tree does not reach by `add_subdirectory`. **Where neither directory contains the other the two markers are siblings, and siblings are separate suites — the rule above already makes each a candidate, and each one runs.** Neither reason above reaches them: there is nothing above to run the other, and nothing runs twice to be summed twice. Measured on `frontend/package.json` beside `backend/package.json` with no root `package.json` — the ordinary front-end-plus-back-end repository — both qualify, neither contains the other, and run in their own directories they report **3** passing and **4**; keeping one of them and demoting the other to a note reports `OK` over half the repository, the wrong number rather than the missing one this step opens by naming as the worse of the two. **Depth settles nothing here and is not what is being asked**: those two sit at the same depth, so a shallowest-wins rule has neither a shallowest to take nor a deeper one to name, and its `### Notes` category is empty. Every candidate is a suite except where the wrapper rule below folds one into another, or where one of the two divisions below carves one into a suite per unit it runs — a workspace under the `workspaces` division, a default member under the Cargo one. **Where both of those reach one candidate the wrapper rule is asked first and the division does not run at all**, which the wrapper rule below settles with the measurement that decided it and each division below states at its own site. Detection runs whether or not a `command_hint` was supplied: the hint decides what is *run*, never what is *detected*, so the return always names the whole set a caller could narrow to. Where a tool ships a pinned entry point, that is the command: `./mvnw`, `./gradlew`, and Ruby's `bin/` binstubs ahead of `bundle exec`.

   **A JavaScript suite must be told not to watch, which is what the `CI=true` prefix is for.** `npm test` runs whatever `scripts.test` holds, and several runners watch for file changes by default outside CI: a watcher never returns, the per-suite bound truncates it, and a suite that was fine gets recorded as a failed run. `CI=true` is the one lever that is not a guess about which runner the script names — Vitest and `react-scripts` each document it as putting the run into non-interactive single-run mode. **It does not reach every watcher: the carve-out below names two runners it misses** — Karma and `ng test`. Either can be named by `scripts.test` itself or reached one level down through another npm script; Karma can additionally sit inside a `grunt` / `gulp` task, which is the third shape and the one the carve-out can only sometimes rebuild into a command of its own.

   **It is not inert for every runner that already runs once, and it is kept anyway — but what each effect does to a comparison depends on whether the runner fails a *test* or the *run*, so state it per runner rather than as one symmetry, and expect a runner it leaves alone entirely.** Both of those classes are symmetric in the sense that matters — capture and verify run under the same prefix, so nothing that was already true of the repository is read as this change's doing — and they surface in different places.

   Jest reads it as `--ci`, which is *"on by default in most popular CI environments"* and under which a snapshot with no committed file fails **the test**. A test is an identifier, so a stale committed snapshot fails at both ends and sits in the baseline's own `### Pre-existing failures`, never read as a regression, while one the run itself writes between the two calls fails at verify alone, as a **New failure** — a list the caller reads separately from the `Status` (verify step 6).

   The config `npm init playwright` writes takes `forbidOnly`, `retries` and `workers` from it, and that `only` guard fails the **run**, not a test — Playwright's own reference: *"Exits with an error if any tests or groups are marked with `test.only`"* — so no counts are produced and no identifier exists to list. A committed `.only` therefore aborts that suite at both ends: step 2 records it as a failed run, the baseline row reads `RUN_FAILED`, and verify step 6 settles it by its own ladder (`PARTIAL` where another suite produced counts, `RUN_FAILED` where none did). An `.only` the run leaves in aborts a suite the baseline recorded `OK`, so every baseline passing test of it — on a suite that was green, all of them — becomes **Missing from run** ⇒ `REGRESSIONS` (verify steps 3 and 6). It is not silent and it is not charged to the wrong run; which list it lands in is the runner's doing, not this prefix's. Playwright's built-in reporter default also becomes `dot` rather than `list` (`defaultReporter = process.env.CI ? 'dot' : 'list'`, and both print the `X passed` line step 3's table reads).

   **Mocha is in neither class, and its own documentation says otherwise.** Mocha's release notes and CLI page both state that `--forbid-only` defaults to true in CI from v12; **the shipped package does not implement it.** Measured on 12.0.0, 12.0.1 and 12.0.2, each with a committed `it.only` under `CI=true npm test`: all three exit 0 and print their counts, while `--forbid-only` passed explicitly aborts with `ERR_MOCHA_FORBIDDEN_EXCLUSIVITY` and exit 1. The package reads `process.env.CI` in exactly one place — `lib/utils.cjs`'s `isCI()` — whose one consumer appends *"(default in CI, …)"* to that error's **message**, after `forbidOnly` is already true; no rc file and no CLI default sets it. So nothing Mocha itself does changes under the prefix, and none of the tracing above is charged to it: a committed `.only` narrows what that suite reports identically at both ends and therefore moves nothing, while one the run leaves in is still caught — not as an aborted suite, but as every other baseline passing test turning up **Missing from run** (verify step 5's table), reaching the same `REGRESSIONS` by the ordinary route. **Take that as the standing rule for every runner named in this step, not merely in this paragraph: check the runner, not its documentation.** It is scoped that way on purpose — the doc-sourced assertions it exists to police are the *preceding* paragraph's, where Vitest and `react-scripts` are read out of what they document rather than out of what they do.

   Dropping the prefix costs a hang, which loses a whole suite; a per-runner flag costs the guess this prefix exists to avoid.

   **The watch carve-out — two runners the prefix does not reach, each told not to watch by its own flag.** The test is the script that actually runs — the candidate's own `scripts.test`, or, under a `workspaces` field, each workspace's own, since the division below runs those and not the candidate's — and the command is issued from the directory **that script** belongs to. For the candidate's own `scripts.test` that is the candidate's own directory, which is step 2's rule for every suite in this table rather than a carve-out of this one's; where the script examined was a **workspace's**, it is that workspace's directory, which is that row's own marker's directory rather than the candidate's, the division below giving each row it carves that workspace's own `package.json` as its marker. What does diverge from step 2's marker rule is the division's **other** rows: each runs at the candidate's directory — this rule's choice rather than npm's requirement, measured at step 2 — while its marker sits in the workspace it names, which is why step 2 names *those* among the run directories that are not a marker's own. The workspace's is where npm's own `--workspaces` runs that script, and where the relative paths written into it — a `configFile` among them — resolve:

   - **`karma start` without `--single-run`.** Karma invoked directly reads no `CI`. That script's suite is commanded `npx karma start <the script's own arguments> --single-run`.
   - **`ng test` without a `--watch` flag.** Measured against the builders `ng new` actually writes, because the CLI's documentation is not evidence about them: Angular 19 writes `@angular-devkit/build-angular:karma` and Angular 20 writes `@angular/build:karma`, and **neither derives its watch mode from `CI` at all** — each package's only `CI` reads are a build-cache toggle and a TTY helper the karma builders never consult. The 19 builder leaves Karma's `singleRun` **undefined** unless `--watch` was passed, so Karma's own `singleRun: false` default applies; the 20 builder defaults its `watch` option to `true` outright. (`@angular/build:unit-test` is the one Angular builder that derives `watch` from a TTY-and-`CI` test, and it is what neither `ng new` writes — so a project on it needs no carve-out and is unharmed by one, since `--watch=false` is what the flag would have resolved to anyway.) That script's suite is commanded `npx ng test <that invocation's own arguments> --watch=false`, an option all three of those builders' schemas declare — **rebuilt from the invocation, as the `karma` bullet rebuilds its own, and never appended to the script's text**: an append lands on the last segment, so `"test": "ng test && ng e2e"` would hand `--watch=false` to `ng e2e`, and what that does is the e2e builder's business rather than this row's. It is not reliably an error: `@cypress/schematic` 6.0.0, whose own `ng add` installs an `e2e` target, **declares** the option (`src/builders/cypress/schema.json`: `"watch": {"type": "boolean", …, "default": false}`) and its own `ng add` writes the `e2e` target with `watch: true` (`src/schematics/ng-add/index.js`), so there the flag is accepted and the append runs a whole e2e suite against a dev server under a row whose output is a unit-test count. Accepted-and-wrong is worse than rejected, which makes the rebuild more necessary than an unqualified "no schema declares it" would have. What a rebuild drops is a compound script's non-test segments — `"test": "ng lint && ng test"` no longer lints here — which is what the `karma` bullet has always done and is right for a row whose output is a test count; `/implement`, for one, runs its own lint and build in a step of its own. A browser-driven `ng test` still needs a browser; that is its own problem and not this flag's.

   **Where that script names neither runner directly, follow it one level and apply the two tests above to what you find**, as each bullet below refines them for its own shape — the same rung the `Make` wrapper rule below already carries, for the same reason, and npm-script indirection is at least as common as Make indirection. **Two shapes resolve, and nothing else does:**

   - **`npm run <name>` / `yarn <name>` / `pnpm run <name>`** → that name's own entry in the same `package.json`. `"test": "npm run test:unit"` over `"test:unit": "ng test"` is the second bullet's case, and the command is rebuilt from the **inner** script. Passing the flag through the outer one instead does nothing at all — measured: `npm test -- --watch=false` over that pair reached the inner command with `argv` identical to a bare `npm test`, npm having taken the flag as its own option at the second hop, while the same flag on `npm run test:unit` arrived.
   - **`grunt <task>` / `gulp <task>`** → that task in the `Gruntfile.js` / `gulpfile.js` beside the `package.json` **whose script this is** — the candidate's own for the candidate's `scripts.test`, that workspace's where the script examined was a workspace's — which is the directory the script runs in and so the file those tools read. This is the AngularJS shape, and it is the first bullet's case with the invocation moved inside the task — but **what decides is the task's own resolved Karma options, and a configuration file is at most one input to them**, because both tools hand those options to Karma as a CLI-level override *on top of* whatever `configFile` they name. For `grunt` that object is `karma.options` merged with the target's own data, **the target winning** — `grunt-karma` 4.0.2's `_.merge(opts, this.data)`, whose own comment reads *"Merge options onto data, with data taking precedence"*, passed on as `parseConfig(data.configFile, data, …)`; for `gulp` it is the `Server` options object, reaching the same parser the same way. So the test is **that merged object's `singleRun` where it declares one, and the named configuration file's own only where it does not** — absent at both levels watches, since Karma's own default is `false`. Measured on `grunt-karma` 4.0.2 over Karma 6.4.4 with the browser held identical across every arm: a target declaring `singleRun: true` over a file declaring `false` returned in **1s**, while the inverse — file `true`, target `false` — **never returned** and was killed at **90s**; a `gulp` `Server` given `singleRun: true` over that same false-declaring file returned in **1s**. Reading the file alone is wrong in both directions — it fires on the first, which already runs once, and misses the second, which hangs.

     **Where that merged object's `singleRun` is absent or `false`, the carve-out fires wherever the invocation names a `configFile` and every further option it writes is one the runner's own CLI declares a flag for** — the watch pair (`singleRun` / `autoWatch`) excepted, which the replacement command overrides anyway. With the `configFile` alone the suite is commanded `npx karma start <that configuration file> --single-run`, which is the first bullet's command with the task's own config file as its argument; with further options it is that same command plus one declared flag per option, carrying that option's own value and joining a list with commas — measured, `--reporters dots,progress` and `--browsers ChromeHeadlessNoSandbox,ChromeHeadless` each resolve to the two-element array the Gruntfile would have written. **The flag set is `karma start --help`'s own, read there rather than written out here**: which options matter is not this plugin's question to answer, and the runner answers it in a form that cannot go stale against the installed version. Measured on Karma 6.4.4, that help declares `--port`, `--reporters`, `--browsers`, `--log-level`, `--capture-timeout`, `--auto-watch`, `--colors`, `--detached`, `--report-slower-than`, `--fail-on-empty-test-suite`, `--fail-on-failing-test-suite` and `--format-error`, and declares nothing for `files`, `exclude`, `frameworks`, `preprocessors`, `basePath`, `customLaunchers` or `client`. **Reading that help is itself a step that can fail, and where it does the option-carrying shape does not fire**: the list comes from running `karma start --help` against the repository under test — its own installed Karma — and where that repository has none to run (nothing under its `node_modules`, and an `npx` that would have to fetch one is not it), there is no list to test the options against, so the shape is reported per the reporting rule below rather than rebuilt from a list guessed here. **The `configFile`-alone shape is unaffected**: its command carries no option flag, so it needs no list and this precondition does not reach it.

     Measured on `grunt-karma` 4.0.2 over Karma 6.4.4, with the browser failing identically in every arm so that the watch setting is the only variable. **A `configFile` alone:** `CI=true npm test` over `"test": "grunt test"` and over `"test": "gulp test"` ran to the kill at **90s** and **75s** against a config declaring `singleRun: false`, while the replacement command returned in **1s** against that same unmodified config — so what hangs is the watch setting and not the environment, and `CI=true` was in both arms. **A `configFile` plus declared-flag options**, on `grunt-karma`'s own README *Sharing Configs* shape (`options: {configFile, port: 9999, browsers: [...]}` with `dev: {reporters: ['dots']}`), which hangs like any other: `CI=true npm test` ran to a **30s** kill, while `npx karma start karma.conf.js --single-run --port 9999 --reporters dots --browsers ChromeHeadlessNoSandbox` returned in **2s** and resolved what `grunt` resolved in every field the probe read — the same two file patterns, `exclude`, `frameworks`, `basePath`, `reporters ["dots"]`, `port 9999`, `browsers ["ChromeHeadlessNoSandbox"]`, `logLevel` and `captureTimeout` — with `singleRun` and `autoWatch` the only difference, which is the whole point of the carve-out. On a second such shape (`configFile` with `logLevel: 'debug'`, `captureTimeout: 42000` and `port: 9988`) the two sides agreed on the suite, the port and the timeout and differed in one place: **`--log-level debug` normalises to `DEBUG` where the Gruntfile's own value stays `debug`** — the one field the two sides spell differently, and no field a count is read from.

     **Every other shape reports and does not fire, and the two below are ordinary configurations rather than exotic ones.** An invocation writing an option the runner's CLI declares no flag for loses that option to the rebuild, which then resolves a different suite: measured on a target adding one spec glob through `options.files`, what `grunt` hands Karma resolves to **three** file patterns where `npx karma start <that file> --single-run --reporters dots` resolves **two**; measured on a target writing `exclude: ['test/add.spec.js']` beside its `configFile`, `grunt` excludes that spec and the rebuilt command runs it. A different suite's number is the wrong-number-rather-than-a-missing-one error this step opens by naming as the worse of the two, so what declines the rebuild is the option's absence from the runner's own flag list, never a judgement here about whether that option matters. A `grunt` / `gulp` option naming no Karma setting at all is in this class by construction — `background: true` is one, and that shape needs no carve-out anyway: measured, it returned in **1s** under `CI=true npm test`, `grunt-karma` having forked the server into a background process. And a task naming **no `configFile` at all** — which `grunt-karma`'s own README calls the recommended configuration, *"You can either put your config in a [karma config file] or leave it all in your Gruntfile (recommended)"* — leaves nothing to hand `karma start`: measured, that shape ran to the **90s** kill under `CI=true npm test`, and `npx karma start --single-run` beside it found no configuration file, started a server with no files and no browser, and ran to its own **60s** kill. Neither of these is the excluded computed-path case below: both resolve perfectly well. **What they cannot do differs, and that is why they are two arms of one report rather than one rule.** The first could be rebuilt only by dropping an option the runner's CLI has no flag for, which is a different suite and therefore a different number; the second has no command to be rebuilt into at all.

   **One level, and only those two shapes.** A second level is not followed, and neither is any other indirection: a script that delegates again, a wrapper taking script names (`run-s`, `npm-run-all`), a shell script, or a task whose `configFile` is **assembled at run time** — out of a variable, a glob, or a call whose arguments are not all written out. `path.resolve(__dirname, '<literal>')` is **not** that, and the distinction is load-bearing rather than pedantic: every part of it is written out, it names exactly one file, and it is the standard `gulp` form the measurements above were taken on — an exclusion broad enough to swallow it would leave this rule refusing to fire on the very shape it cites as its evidence.

   **Wherever the carve-out does not fire on a script that does reach one of the two runners, that is reported rather than passed over** — a level or a configuration path that did not resolve, the two resolved shapes above the rule declines, and an option-carrying shape whose flag list could not be read. The suite runs the table's own command for that row — `CI=true npm test` where the script examined was the candidate's own, and that workspace's `--workspace` command from the division below where it was a workspace's — and `### Notes` names the script, what in it could not be resolved or rebuilt — the option the runner's CLI has no flag for, or the flag list that could not be read, where that is what declined it — and that the suite may therefore run to the per-suite bound — the same section the `Make` rule below names an indirection one level did not settle in, though what is named there is a different fact. A carve-out that silently fails to fire is indistinguishable from a suite that genuinely failed: the per-suite bound truncates the watcher, the row reads `RUN_FAILED`, and nothing in the return says the runner was never reached.

   **A candidate carrying a `workspaces` field is divided, and the carve-out above is not what triggers that. What does stop it is the `Make` wrapper rule below, which is asked of a candidate first and leaves nothing here to carve**: that rule settles whether a candidate is a suite of its own at all, where this one settles what kind of suite a candidate that *is* one becomes, so a candidate whose runner a `Makefile`'s `test` recipe invokes is folded and never divided — measured below, at the rule that takes the precedence, along with what the fold then owes in its place. The division is one suite, and one `### Suites` row, per workspace whose own `package.json` carries a qualifying `scripts.test` — the set `--if-present` would have run, and the same question this table's own Candidate-when already asks of them. Where the carve-out fired on one of those workspaces' scripts, that workspace's row carries the rebuilt command; every other row — a workspace whose script the carve-out never reached, and one it reached and declined, which the paragraph above makes a reachable outcome rather than an error — carries `CI=true npm test --if-present --workspace <name>`, so no workspace runs twice, and the `--if-present` those commands carry can fire only where a script vanished between the scan and the run, the division having already asked the tree for the rest. **What the division replaces is one command whose output held every workspace's tests**, and the row shape is what refuses that: a row carries exactly one command, one status and one set of counts, so several workspaces cannot share a row without losing which of them failed, what each returned, and which of them a given test belongs to. **The third of those is what reaches the identifier diff; the first two are what reach the status and the counts.** Measured on a three-workspace repository none of whose scripts reaches either runner — so the carve-out never fires and nothing but this rule divides it — the third workspace losing between the two calls a test the second also has: undivided, the baseline recorded **5** identifiers for **6** passing tests, **0** landed in **Missing from run**, and the run returned **OK** on a real regression with its own `Passing` down 6 to 5, because `PASS index.test.js > works` is one string under one prefix however many workspaces printed it; divided, the baseline recorded **6**, **1** landed in **Missing from run**, and the run returned **REGRESSIONS**. Measured on that same shape with one workspace's runner missing and the other two green: undivided, the one row reads `OK` carrying the other two's counts and nothing says that workspace never ran — a baseline covering a suite it did not run, which is what `PARTIAL` exists to say — while divided, that workspace has a row of its own reading `RUN_FAILED`, the capture is `PARTIAL`, and `### Suites` names the command that failed. And step 2's per-suite bound was one budget for every workspace of the repository: measured with a 3-second stand-in for that bound, one combined command reported **1** of three workspaces' tests and lost the third's entirely, where a bound apiece reported **2** and timed out only the workspace that was genuinely slow. **What the division costs is one npm invocation per workspace**, measured at **73**, **103** and **121** milliseconds a workspace on repositories of 3, 10 and 30 of them — 3.6 seconds added to the largest, against a bound of ten minutes a suite. **What it does not take away is the candidate's own `scripts.test`**: measured on a root carrying one beside the field, `--workspaces` never ran that script either, so the division running the workspaces' scripts and not the candidate's is npm's own behaviour rather than this rule's. **And because the division is unconditional, a candidate's row set no longer turns on whether the carve-out fires**: a workspace's script that starts watching between the two calls — the implementation's own doing — changes that row's *command*, which verify step 2 records as a `### Notes` line, and not the run's row count, which it would have to pair around. Measured on a three-workspace repository where one workspace's script became a `karma start` invocation between the calls while every test still passed: divided at both ends, all three rows paired by their own paths and **0** identifiers landed in **Missing from run**, where a candidate undivided at capture and divided at verify paired nothing at all and put all **5** of them there ⇒ `REGRESSIONS`.

   **Attributing the combined output instead was measured and refused.** npm does attribute it: each workspace's output opens with a `> <name>@<version> test` banner, the name is unique because npm refuses a repository holding two workspaces of one name (`EDUPLICATEWORKSPACE`), a workspace `--if-present` skips prints no banner at all, and the ordering held in every arm measured — a file redirect and a pipe alike, and 12,000 lines of runner output written to stderr. **What refuses it is the comparison rather than the parse**: a distinction drawn *inside* a row is invisible to verify step 5, which rewrites a baseline identifier's prefix onto the row step 2 paired it with and knows nothing of what sits after that prefix. Measured on a workspace moved from `packages/` to `apps/` with nothing else changed, attributing inside one row put **both** of that workspace's identifiers into **Missing from run** ⇒ `REGRESSIONS` on a tree that had lost nothing, where the division paired the moved row by its own marker path, rewrote its prefix and returned **OK**. A banner is also not always the workspace whose output follows it: measured, a workspace whose own test script runs a sibling's tests prints that sibling's banner in the middle of its own output, after which what follows is attributed to the sibling.

   **Each of those rows records that workspace's own `package.json` in its marker column**, as a path relative to the scan root, and never the candidate's: the candidate has one marker, its own `package.json`, so rows carrying it are rows of one framework holding one marker value, which step 3 then prefixes `[Jest/npm package.json] ` alike — **one prefix for every row the division carved**, the collision the prefix exists to prevent. **What the next measurement settles is which marker a divided row carries, the paragraph above having settled that the candidate is divided at all**, so its two arms are both divided and its tree is one the carve-out does fire on. Measured on a three-workspace repository whose carve-out fires on the first, the third losing between the two calls a test the second also has: with the candidate's marker the baseline recorded **5** identifiers for **6** passing tests, **0** landed in **Missing from run**, and the run returned **OK** on a real regression, its own `Passing` having fallen 6 to 5; with each workspace's own marker the baseline recorded **6**, **1** landed in **Missing from run**, and the run returned **REGRESSIONS**. On the same tree with the rebuilt command genuinely failing — a real `npx karma start` with no browser to drive — those figures are **3** for 4 against **4** for 4, and the candidate's marker returns `PARTIAL` rather than `OK`: the regression goes unreported under it whichever status it wears, and the marker is the one thing those two arms differ in. **The marker is that workspace's path and never its position among the workspaces**, which is the hint's own ordinal rule read from the other end: a position among this call's workspaces is a property of the call, and the workspaces are re-resolved per call, so a workspace added between the two renumbers every one after it — measured, a workspace added ahead of two untouched ones put every one of their **4** identifiers into **Missing from run** — 4 of the baseline's 6 — and returned `REGRESSIONS`, where the path paired all three rows exactly and returned `OK`. A path moves only when the workspace does, the root it is relative to being pinned by this step's own rule, and a workspace that moves is a moved suite, which verify step 2 pairs and verify step 5 rewrites exactly as it does a sibling's. **The division carves a row only where that workspace's own `package.json` carries a `scripts.test`, which is why its marker column always names a file that qualifies rather than inventing a token**: such a file qualifies on this table's own Candidate-when and is kept from candidacy only by the containment rule above — the candidate's `workspaces` field being npm's own answer to that shape — so where the division carves it into a row, its marker column is where that file is named and `### Notes` no longer carries it. Carving one for a workspace that has no `scripts.test` would invent an incompleteness instead: measured, `CI=true npm test --if-present --workspace <that one>` exits **0** with no output whatever, which step 2 records as a failed run, so the capture reads `PARTIAL` and `### Suites` names a command that could never have produced a count, on a repository where nothing failed. The rebuilt row runs in its workspace's own directory and each `--workspace` row in the candidate's — the directory the `workspaces` field naming that workspace sits in — which is a rule here rather than a necessity, npm having resolved that flag from a sibling workspace's directory and from a non-workspace subdirectory alike when it was asked to; step 2 names both, and measures what happens where the flag is issued outside the repository altogether.

   **A candidate whose `Cargo.toml` carries a `[workspace]` table is divided too, on the same grounds and with a set of its own — and is stopped by the same thing, the `Make` wrapper rule below being asked of a candidate first and leaving nothing here to carve.** A candidate whose runner a `Makefile`'s `test` recipe invokes is folded and never divided, on the measurement that rule states, which was taken on this ecosystem as well as on npm's. The division is one suite, and one `### Suites` row, per member of that workspace's **default** set — the members `cargo test` at that root would have run, which `cargo metadata --no-deps --format-version 1` reports as `workspace_default_members` beside the full `workspace_members` list — each row commanded `cargo test -p <name>` and carrying that member's own `Cargo.toml` as its marker. **That enumeration reads manifests and resolves nothing**, which is why it is safe to run at detection: measured with no `Cargo.lock`, an unresolvable external dependency and no network, `--no-deps` returned the two lists and a null `resolve` at exit 0, so no network flag is needed and none is written here. **The default set is this division's `--if-present`, and it was measured rather than preferred**: taking every member instead runs suites the repository's own entry point does not, and a member is commonly held out of the default set because it does not build — measured on a workspace declaring `default-members` over two of its three members, where the third does not compile, a bare `cargo test` exits 0 with **3** passing and the division carves those two rows and reads `OK`, while a row for every member instead runs `cargo test -p` on that third, which exits **101** with no counts — step 2 records that as a failed run, so the capture reads **`PARTIAL`** and `### Suites` names a command that could never have produced a count, on a repository where nothing failed. Measured with a third such member beside two that do carry tests, the division's three rows returned the same three identifiers and the same `OK` as the one undivided row. **What the division replaces is one command whose output held every default member's tests**, and the row shape refuses that for the reasons the paragraph above already gives: a row carries exactly one command, one status and one set of counts. Measured on a two-member workspace whose members both print `tests::works`, the second losing that test between the two calls: undivided, the baseline recorded **3** identifiers for **4** passing tests, **0** landed in **Missing from run**, and the run returned **OK** on a real regression with its own `Passing` down 4 to 3 — under a list that keeps the duplicate exactly as under one that does not, since verify step 5's table asks whether an identifier is present at all; divided, the baseline recorded **4**, **1** landed in **Missing from run**, and the run returned **REGRESSIONS**.    **Attributing the combined output instead was measured and refused here too, and cargo's channel is weaker than npm's rather than merely no better.** `cargo test` opens each test binary's output with a `Running unittests src/lib.rs (target/debug/deps/<crate>-<hash>)` banner, which is a binary header and not part of any test line — and for an integration test it names **the test target and not the crate**: measured on two members each carrying a `tests/integration.rs`, both printed `Running tests/integration.rs (target/debug/deps/integration-<hash>)`, differing only in a content hash that names no member, and the identifier under each was a bare `works` with no module path at all.    **Each of those rows records that member's own `Cargo.toml` in its marker column**, as a path relative to the scan root, and never the candidate's and never the member's position among them: a path is a tree property both calls re-derive from the same tree and the same pinned root, where a position among this call's members is a property of the call — the ordinal the `workspaces` division refuses on its own measurement, refused here for the same reason rather than re-measured. Measured on a member moved from `crates/beta` to `apps/beta` between the two calls with nothing else changed, the divided rows paired by their own marker paths, step 5 rewrote `[Cargo crates/beta/Cargo.toml] ` onto `[Cargo apps/beta/Cargo.toml] `, **0** identifiers landed in **Missing from run** and the run returned **OK**; measured on a member **added** between the calls with nothing existing touched, the same **0** and the same **OK**, the added member's tests being `new since the baseline`.    No other row's command watches — `./mvnw test`, `./gradlew test`, `bin/rspec`, `bin/rails test`, `swift test`, `xcodebuild test`, `go test`, `cargo test`, `pytest`, `dotnet test`, `vendor/bin/pest` and `vendor/bin/phpunit`, `sbt test`, `mix test`, `flutter test` and `dart test`, and `ctest` each run once and exit, the last six rows' commands measured so below. **The wrapper rule below settles *parsing*, not watching**, so `make test` does not escape this paragraph — and it does not escape it conditionally either: the `Make` row's own command in the table above **is** `CI=true make test`, whether that rule folds another candidate into it, leaves both running, or finds no runner in the recipe at all, since a recipe inherits the environment it was invoked with and hands it to every process it starts, however many levels down the runner sits. Carrying it unconditionally is the cheaper error of the two: the alternative — carrying it only where the fold happened — leaves the unfolded branch, a recipe that reaches a JS runner without naming one, starting a watcher under a bare `make test`, which the per-suite bound then truncates into a lost suite; whereas a `CI` a recipe's runner does not read costs nothing, and one it does read gets the same `CI` every other JavaScript row in this table already carries — whose effects are the per-runner ones stated above, symmetric across capture and verify, rather than the blanket non-interactivity it would be convenient to claim. **Two residuals it does create, stated rather than assumed.** `make` imports the environment into its own variable namespace — measured on GNU Make 4.3, where `CI=true make test` takes the `ifdef CI` branch a bare `make test` does not — so a recipe carrying an `ifdef CI` / `ifeq ($(CI),true)` can select a different command, commonly a quieter or machine-readable reporter whose output the `Make` parse row may not recognise at all; that is symmetric, so it manufactures no regression, but the suite's counts can be silently lost, which is the harm this paragraph is otherwise avoiding. And a `test` recipe that also runs a **non-test** step whose tool reads `CI` can fail where it passed.    - **No candidate at all, and no `command_hint`** → **take the test command the repository declares for itself before concluding it has none**, which is what a stack this table has no row for still carries. Read these files at the scan root, in this order, and stop at the first that yields a command: `.github/workflows/*.yml` and `*.yaml` in lexicographic order, `.gitlab-ci.yml`, `.circleci/config.yml`, `azure-pipelines.yml`, `bitbucket-pipelines.yml`, `Jenkinsfile`, `CONTRIBUTING.md`, `README.md`. From a CI file take the one line of each step that runs the project's tests — never the step's checkout, install, cache, build-only or publish lines — issued as `CI=true <line>`, the environment every hosted CI gives it, preceded by `cd <dir> && ` where the step names a working directory; from a document take a command in a fenced block or a code span under a heading or sentence about running the tests. **Refuse a line** that carries a CI expression (`${{ … }}`) or a variable the file sets outside the line, runs `sudo`, or installs, deploys or publishes anything: it could not run here as written, or it should not. A line repeated across jobs is taken once. **Each line taken is a declared suite**, in the order taken: its framework the runner its command names where step 3 has a row for that runner, parsed with that row, and `declared` where it names none, parsed with the `Make` row and step 3's exit-status rule; its `### Suites` marker `declared#<n>`, `<n>` being its 1-based position among the lines taken; its run directory the scan root. `### Notes` names the file and the step or heading each came from, marked (step 5): nothing in this table detected that suite, and what its command covers is the repository's word rather than this table's. **This rule fires only where the table matched nothing**, because a command read beside a suite the table did find is the guess first-match-wins was — a detected suite is never replaced by one read out of a CI file, nor run beside one. **Where no file yields a line** → run nothing and return the structure below with Framework = "not detected", all counts = 0, and a note saying no runner was found and naming the files read. Do not fail.

   **Scope — what is run.** With no `command_hint`, **every** detected suite runs, in the table's own row order — and, **within a row that yielded sibling candidates, or a candidate either of the two divisions carved, in their marker paths' own lexicographic order** — so that the same repository yields the same order on every run (verify mode pairs the two lists suite by suite, and row order alone stopped fixing an order the moment one row could yield more than one candidate). **On a divided `workspaces` candidate that order is this rule's and not npm's**, which the division changed and is worth saying rather than leaving to be found: measured, `npm test --workspaces` runs the workspaces in the `workspaces` field's **own declaration order**, expanding a glob's members in sorted order within it — `packages/zed` ahead of `packages/alpha` where the field declares them that way — so a repository whose workspaces' tests depend on each other's order is reordered by the division. **The Cargo division reorders in its own way and by less**: measured, `cargo test` at a workspace root runs the members in **package-name** order and not in the `members` field's declaration order — `crates/zed`, `crates/alpha`, `crates/mid` declared in that order ran alpha, mid, zed — so the two orders agree wherever a member's directory sorts as its package name does and differ where they do not, measured on a workspace holding a package named `zed` at `crates/aaa` and one named `alp` at `crates/zzz`, which cargo ran `alp` first and this rule runs `crates/aaa` first. All three orders are tree properties and so hold still across the two calls alike, which is all this rule asks of one; the fidelity is what it gives up. A repository holding a Rails suite and a JavaScript one, or a Java suite and an Angular one, has two real test suites, and a baseline taken from one of them cannot detect a regression in the other — which is why a second suite is never a reason to run nothing. A `command_hint` is one or more commands and becomes the run set instead: each is a suite, parsed with the row of the detected suite whose command it matches, with the row of the runner it names where it matches none, and with the `Make` row and step 3's exit-status rule where it names no runner this table has a row for; every detected suite the hint leaves out is still reported, marked `not run`. **A hinted command matching no detected suite is a suite of its own** — its framework the runner its command names, or `hinted` where the command names none, and its `### Suites` marker column reads `command_hint#<n>`, `<n>` being that command's **1-based position in the hint as sent**. **The ordinal is what keeps two of them apart, and a bare `command_hint` did not**: where two such commands resolve to one framework — two naming no runner, so both read `hinted`, or two naming the same runner — step 3 reads that framework as naming more than one of `### Suites`' rows and prefixes both `[<Framework> <marker>] `, which with one marker between them is **one prefix for two suites**, the collision the prefix exists to prevent. Measured on a two-command hint whose suites share a test name, the second losing that shared test between the calls: with a bare `command_hint` the baseline recorded **4** identifiers for **5** passing tests, **0** landed in **Missing from run**, and the run returned **OK** on a real regression — its counts falling 5 to 4 and moving nothing, since the `REGRESSIONS` arm is computed from the identifier diff and not from them; with the ordinal the baseline recorded **5**, **1** landed in **Missing from run**, and the run returned **REGRESSIONS**. **The command itself is the obvious discriminator and is not the one, on two shapes a hint can take.** A hint may carry the same command twice, which the command cannot tell apart at all — measured, **3** identifiers for **6** passing tests under the command exactly as under the bare marker, against **6** under the ordinal. And a test invocation ordinarily carries a path pattern, a flag list or a quoted expression, so the command puts a command line in front of every identifier of that suite and the `]` it carries inside the prefix — measured, one identifier ran to **109** characters against the ordinal's **34**, its first `]` falling at **50**, inside the prefix `[hinted command_hint:./scripts/run.sh --only '[a-z]+/spec' …] `, where the ordinal's closes its own; and a command carrying a newline rendered **5** identifiers as **8** lines, which step 5's one-identifier-per-line list cannot be read back from. The command is already in that row's own command column, so the ordinal names the row without repeating it. **The ordinal counts the hint, never the suites this call made of it**: whether a command matches a detected suite is a property of the tree, which moves between the two calls, so numbering the unmatched commands alone renumbers every command after one of them the moment that one starts matching, and an ordinal is not re-packed when a command matches — measured on a three-command hint whose first matched no detected suite at capture and matched one at verify, numbering the unmatched returned **REGRESSIONS** with **3** of 3 **Missing from run** on two suites nothing had touched, where numbering the hint as sent returned **OK** with **0**. A position in the hint moves only when the hint does, and the hint is resent. **Having no marker, it has no marker's directory either**, so step 2 needs one named here: a hinted command that matched a detected suite runs in **that** suite's directory, and one that matched none runs at the scan root, which is the frame a caller types a command in. A caller that sends a hint on the `capture` call sends the same hint on every `verify` call against that baseline — **the same commands in the same order**, the position being what tells one unmatched hinted suite from another — or the two runs have nothing to pair. Never ask the user which suites to run — the caller owns that question, and a subagent that prompts breaks the rule that commands orchestrate and agents execute.

2. **Run the suites** — Execute each suite's command in turn **from that suite's own run directory**, which step 1 recorded with it and which is one of four things: **the directory its qualifying marker sits in**, for every ordinary suite and for the rebuilt row of a workspaces division, whose marker is that workspace's own `package.json` (step 1); **the `Makefile`'s directory**, for a suite the `Make` wrapper rule folded, since `make test` is that suite's command now — and where that fold yielded a row per framework (step 1), those rows share the one `make test` invocation rather than issuing it apiece, its output parsed with each of their rows; **the candidate's own directory**, for a `--workspace` row of that division and for every row of the Cargo one, that being the directory the `workspaces` field or the `[workspace]` table naming that unit sits in while the row's marker sits in the unit itself; and **the scan root**, for a hinted command that matched no candidate and for a declared suite (step 1's last rule), neither having a marker of its own. The last three are the ones `### Suites`' marker column cannot name — the folded suite's and the two divisions' unit rows' because that column names each suite's own marker, the hinted and declared ones' because they have none and the column reads `command_hint#<n>` or `declared#<n>` — so the first two are named in `### Notes` with their directories and the third is read off that column. Capture stdout and stderr combined **per suite**, and read each suite's exit status from **its own command, never from a pipe after it**: a pipeline's exit status is its last command's, so a failing suite run through `| tail`, `| head`, `| grep` or `| tee` exits with the filter's status — 0 wherever the filter itself succeeds — and a suite recorded by its exit status alone (step 3's *Exit status is the result where the output yields no other*) is then recorded passing. Where the output is too long to read whole, redirect it to a temp file **outside the repository** and take the status in the same call — `f=$(command mktemp -t dw-suite-XXXXXX); <command> > "$f" 2>&1; echo "exit=$? file=$f"` — then read the file at the path it printed and remove it (`command rm -f -- <that path>`): a file written inside the tree is swept into the run's commit, which stages the whole working tree. **The project root is that directory only for a suite whose run directory resolves to it** — a marker at the root, or one of the three cases above that lands there — and on a monorepo the difference is the whole run. Measured on a root `pom.xml` beside a `frontend/package.json` carrying its own `scripts.test`: `CI=true npm test` issued from the project root exits **254** on `ENOENT … Could not read package.json` and produces no counts, so a perfectly runnable suite is recorded `RUN_FAILED` — a runner failure that never happened — while the same command issued in `frontend/` exits 0 and prints its counts; and `./mvnw test -q` issued from `frontend/` exits **127** on `No such file or directory`, the pinned entry points (`./mvnw`, `./gradlew`, `bin/rspec`, `bin/rails`) being relative paths that resolve in one directory and nowhere else. **The loud half is not the dangerous half**, which is why this is a rule rather than a convenience: measured on the same tree, `CI=true make test` issued where a second `Makefile` happens to sit runs *that* file's `test` target, exiting 0 with counts of its own — a number, and the wrong one, which is the error this step opens by naming as the worse of the two. **A `--workspace` row of step 1's division does not fail that way, and that is measured rather than assumed**: `CI=true npm test --if-present --workspace <name>` resolved and ran that workspace from a sibling workspace's directory and from a non-workspace subdirectory alike, and issued outside the repository altogether exited **254** on `ENOENT … Could not read package.json` with no counts at all — loud where it is wrong, which is why its run directory is step 1's choice rather than npm's requirement. **A row of the Cargo division behaves the same way and was measured the same way**: `cargo test -p <name>` resolved and ran that member from a sibling member's directory, cargo walking up to the workspace root the same way npm resolves a `--workspace` flag, and issued where no `Cargo.toml` stands above it at all exited on `error: could not find Cargo.toml in <dir> or any parent directory` with no counts — so its run directory is step 1's choice too. **The 10-minute bound is per suite, not per run**: one budget shared across suites lets a slow first suite truncate a later one, and a truncated run returns a short passing list that the verify diff reads as *missing from run* — a regression-severity finding manufactured by the clock. A per-suite bound cannot starve anything; its cost is that *n* suites take up to *n* × 10 minutes, and *n* is in the return. **Step 1's two divisions are that same rule reaching inside a monorepo**, where one command over every workspace, or over every default member, was one budget over all of them — measured there for each, the Cargo one on three members whose 20-second sleeper cost a third member its whole run under a shared bound. **Where step 1's wrapper rule folded that candidate neither division runs, so its units are back under one budget**, `make test` being one command — part of what the fold costs, and stated there with the rest of it. If a suite aborts (non-zero exit, truncated output, or unrecognized runner output) with no parseable pass/fail counts, record it as a failed run for **that** suite and **continue with the remaining suites** — one suite's failure never suppresses another's result. Step 4 computes one **Status** from the set (do not fail the tool call — still return the structure).

3. **Parse** — Extract from the output:

   | Framework | Passing count | Failing count | Skipped count |
   |-----------|--------------|---------------|---------------|
   | Maven | `Tests run: X` minus failures+errors per module, summed | `Failures: Y, Errors: Z` summed | `Skipped: N` summed |
   | Gradle | `X tests completed` minus failed | `, Y failed` | `, Z skipped` |
   | RSpec | `X examples` minus failures and pending | `Y failure` / `Y failures` | `N pending` |
   | minitest | `X runs` minus failures, errors and skips | `Y failures` plus `Z errors` | `N skips` |
   | SwiftPM / Xcode | `Executed X tests` minus failures, summed over suites | `with Y failures` summed | count of `skipped` test-case lines |
   | Go | count of `--- PASS:` lines | count of `--- FAIL:` lines | count of `--- SKIP:` lines |

## Mode: verify

Re-run every suite and diff against a previously captured baseline. Use this **after** making changes to detect regressions.

### Inputs

The caller must provide:
- The full baseline block from a prior `capture` run (the `## Test Baseline` markdown block)
- The project root path — the request block's `repo:`, the same field a capture call takes; **required here**, because verify has no working-directory fallback, and **required to be the root that capture scanned**, because `### Suites`' marker paths are relative to it and this is the end at which two roots manufacture a regression (capture step 1, measured there)

### Steps

**Before anything runs, test what the supplied baseline actually covers.** A baseline covers exactly the suites its `### Suites` marks `OK` or `NO_TESTS` (capture step 4). Where it marks **none** of them so, it holds no passing test and no clean zero — a `RUN_FAILED` or `COMMAND_NOT_FOUND` capture, or one every row of which aborted — and there is nothing to diff against: run nothing and return the step-7 structure with `Status: RUN_FAILED`, `Comparison status: invalid` and every count 0, saying so in `### Notes` (step 7's definition of that section admits this refusal by name). **Step 6's ladder cannot settle this state and must not be asked to.** With no baseline passing test nothing can go **Missing from run**, so `REGRESSIONS` cannot fire; and where this run's suites *do* produce counts — a runner the change itself repaired, which is the reachable case for a dependency bump — `RUN_FAILED` and `PARTIAL` are both skipped in turn and the ladder falls through to a green `OK` for a comparison that never happened. Every test failing under it would sit in `### New failures`, which no `Status` value carries. The refusal belongs here, ahead of the run, because from the return alone a caller cannot tell that `OK` from any other.

1. **Detect every suite** — Same detection logic as capture mode, `command_hint` included. Where **no candidate matched and no `command_hint` supplied one**, and the baseline holds no declared suite — capture step 4's own test for this state, because a hint that matches no detected suite is a suite of its own (step 1's Scope paragraph) and so is something to run rather than nothing, and so is a declared suite — run nothing and return the step-7 structure with `Status: COMMAND_NOT_FOUND`, `Comparison status: invalid` and every count 0. **A declared suite is read once, at capture**: where the supplied baseline's `### Suites` carries `declared#<n>` rows, this call runs those rows' own commands, in their own order, at the scan root, and reads no file for a command a second time — a workflow file this run's own change edited would otherwise hand the verify a command the capture never ran — and a candidate that qualifies now runs beside them as a suite new since the baseline (step 2) rather than replacing them.

2. **Pair each suite this run has a row for with the baseline** — every detected suite, every hinted command that matched none and every declared suite, which is `### Suites`' own set at both ends (capture step 5) — matching on framework **and marker value**, against the baseline's `### Suites` rows. Framework alone stopped identifying a suite when siblings of one row became separate suites (capture step 1), which is the ordinary front-end-plus-back-end repository: two `Jest/npm` rows there pair with two `Jest/npm` suites and nothing says which with which. A repository whose workspaces division carved a row per workspace it runs is another shape in which one framework names more than one row, and there the marker value is that workspace's own `package.json` path, so those rows pair by the workspace each names and one that moves is a moved suite like any other. A Cargo workspace whose division carved a row per default member is a third, on the same terms with that member's own `Cargo.toml` path as the marker value — measured on a member moved from `crates/beta` to `apps/beta`, which paired by that path and rewrote its prefix for **0** in **Missing from run**, and on one added, which paired the standing rows exactly and made the newcomer's tests `new since the baseline`. A hint carrying more than one command that matched nothing is a fourth, and there the marker value is the `command_hint#<n>` capture step 1 mints, so two of them pair by the position they hold in the hint — which is why a marker value is what this matches on rather than a marker path. Where that leaves, for one framework, exactly **one** baseline row and exactly **one** detected suite unpaired — a **detected** suite on this call's side, narrower than what this step pairs because the fallback is for a suite whose marker moved, and a hinted row's marker is a position in the hint rather than a place on disk — those two pair and `### Notes` records that the suite moved — a suite captured at `frontend/package.json` and detected now at `apps/web/package.json` is the same suite, and step 3 runs it where its marker sits **now**. **Where that leaves more than one of each for a framework, none of them pairs**: nothing here can say which moved to which, so they fall to the `new` and `gone` bullets below, which is the conservative answer rather than a guessed one, and `### Notes` carries both halves. Then:
   - **matched** — compared normally in step 5. A differing **command** is a `### Notes` line, not a refusal: the identifiers still come from the same runner, so they remain comparable.
   - **new since the baseline** — a row this run has that remains unpaired with the baseline. Run it. It has no baseline, so nothing in it can be a regression and a failure in it is a **New failure**; `### Notes` records that it is new. This is the ordinary result when the run's own `test-writer` created the repository's first suite of that kind, so it is never a reason to refuse the comparison.
   - **gone since the baseline** — a baseline row left unpaired after the exact matches and moved-marker fallback. Whatever baseline tests it holds fall out of step 5 as **Missing from run**, which is already regression-severity; a row the baseline marked `RUN_FAILED`, `not run` or `NO_TESTS` holds none, so nothing falls out and the status comes from the other suites, exactly as in step 3. `### Notes` records that the suite is gone either way.
   - **left out by this call's `command_hint`** — where the baseline's own row for it reads `not run` as well, it has no baseline tests and contributes `PARTIAL`. Where the baseline **ran** it, the hint has narrowed the scope between the two calls: that is not like-for-like, so its baseline tests are **Missing from run** and `### Notes` says the hint narrowed the run.

   Only where **no suite row** matches any baseline suite is there nothing to compare. Count every pair from this step — detected, hinted and declared rows alike. A matched `command_hint#<n>` or `declared#<n>` row is sufficient even when detection found no candidate; the detected-only restriction belongs to the moved-marker fallback, not this guard. With zero pairs, run nothing and return the step-7 structure with `Status: RUN_FAILED`, every count 0, and:
   ```
   Comparison status: invalid
   Reason: no suite row matches the baseline — [baseline frameworks] became [current frameworks]. Manual comparison required.
   ```
   A baseline reading `Framework: not detected` names no suite at all, so nothing can pair with it and every verify call against it returns `invalid`. That baseline is what a `command_hint` on the **capture** call can prevent; a hint supplied here for the first time cannot repair it.

3. **Run** — Execute each matched or new suite's command **from that suite's own run directory**, settled by capture step 2's four sources — its marker's directory, a folded suite's `Makefile` directory, the candidate's own directory for a `--workspace` row of a workspaces division or a member row of a Cargo one, or the scan root for a hinted command that matched no candidate and for a declared suite — **stated here rather than imported by number**, because a bare "capture step 2" read in this mode resolves to step 2 above, which pairs and issues no command. Then the same **per-suite** 10-minute bound as capture and the same run order. Capture stdout and stderr combined per suite, and take each suite's exit status from its own command, never from a pipe after it — the capture mode's step 2 says why, and how to trim long output without losing the status.

   **The directory is re-derived by this call's own detection, never read off the baseline row's marker path.** Re-derivation is also what makes it resolve: every run directory here is one this call's own step 1 resolved — a directory its scan found a marker in, a workspace it read out of one, or the scan root the caller named — so none of them is a path this call has not just seen. The baseline's path is exactly that: measured, a suite captured in `frontend/` and moved to `apps/web/` before this call is detected there, runs there and returns its three identifiers — **unchanged where its framework names it alone, the prefix carrying no marker path then; where a second suite of that framework is detected beside it the path is in the prefix and all three move with it, which is step 4's imported prefix rule rather than anything this rule decides, and step 5 rewrites them onto that suite's current prefix before comparing — measured at 5 of the run's 5 and `OK`, where comparing them as captured matched 2** — while the baseline's own `frontend/` cannot be entered at all, which would abort a suite the baseline recorded `OK` for a reason the change did not cause, and lose its every passing test to **Missing from run** whichever prefix those tests carry. Where a paired suite's re-derived directory differs from its baseline row's marker path, that is a `### Notes` line saying the suite moved — never a refusal, exactly as step 2's differing **command** is.

   **Issuing a command anywhere else manufactures a regression, which is why this rule is stated at both ends rather than at one.** Measured on a root `pom.xml` beside a `frontend/package.json` carrying its own `scripts.test`: a baseline captured in `frontend/` reads `OK` with three passing tests, and the same `CI=true npm test` issued at the project root for the verify call exits **254** on `ENOENT … Could not read package.json` with no counts, so all three fall out of step 5 as **Missing from run** and step 6 returns `REGRESSIONS` on a change that broke nothing — routing `/implement` into its Phase 3.5 fix loop and `vuln-fixer` into regression handling. Issued in `frontend/`, the same call returns the same three identifiers and step 6 returns `OK`. That is the manufactured regression the per-suite bound this step imports exists to prevent, arriving by the other door.

   If any suite aborts (non-zero exit, truncated output, or unrecognized runner output), set `Comparison status: best-effort`, record it in `### Suites` and `### Notes`, and still run the rest. **What that abort means is settled by the suite's own baseline row.** `OK` — it ran and produced tests before this change and does not now, so every baseline **passing** test of it falls out of step 5 as **Missing from run**; where it contributed any, the run is a regression and the change is the only thing that moved, and where it contributed none (a suite whose every test was already failing) nothing falls out, which is the third abort step 6's `OK` names. `RUN_FAILED` or `not run` — it could not run at either end, so it contributed no baseline tests, nothing falls out, and step 6 settles the status by its own first-that-applies ladder: `PARTIAL` where some suite produced counts, `RUN_FAILED` where none did. Either way it is a fact about the environment, never evidence about the change. `NO_TESTS`, **or no baseline row at all** (a suite new since the baseline, step 2) — it holds no baseline test that could go missing, so there is nothing to lose either way; record the abort and let the rest of the run settle the status, which step 6's `OK` and `RUN_FAILED` each say how.

4. **Parse** — Same patterns as capture mode, and the same identifier prefixing, read over **this** call's own `### Suites` rows and never copied off the baseline — a prefix copied from there would name a suite this call has no row for, which is the same re-derivation rule step 3 holds for the run directory. So a framework naming one row here prefixes by framework where a capture whose own rows held two prefixed by framework and marker, and the two calls' lists do not line up on their own; **step 5 reconciles that before it compares**, and this step mints nothing with the comparison in mind.

5. **Diff against baseline** — **Rewrite first, then compare.** Step 2 has already settled which baseline `### Suites` row is which suite of this call, and this step makes the comparison agree with that pairing rather than with the two calls' raw prefixes, which each call mints from its own `### Suites` rows (step 4, capture step 3) and which therefore differ wherever that set moved between them. **For every pair, rewrite each baseline identifier's prefix onto its paired suite's current one**: the baseline's prefix for its row is capture step 3's rule read over the **baseline block's own** `### Suites` — `[<Framework>] ` where that framework names exactly one row there, `[<Framework> <that row's marker value>] ` where it names more — and the replacement is that same rule read over **this** call's own rows; every identifier of that row in the baseline's `### Passing tests` **and** in its `### Pre-existing failures` is rewritten, both lists because the table below reads both, and `### Notes` records each rewrite. **The prefixes it reads off the baseline come from that block's `### Suites` rows and nothing else** — the rows step 2 already pairs on, the two test lists being what it rewrites rather than what it reads a prefix from; no run directory is taken from there (step 3) and no path here resolves anything on disk. **A baseline row step 2 left unpaired is not rewritten at all**: `gone since the baseline` is already its disposition and its tests are **Missing from run** whatever prefix they carry, so step 2's *"more than one of each for a framework, none of them pairs"* case stands exactly as it is — measured with this rule and without it alike, **0** of 5 matched either way on two suites that both moved. **It can invent no match**: step 2 pairs one baseline row to one suite, and an unpaired row cannot collide with any of them, since a row of this call carrying that row's own framework and marker would have paired with it exactly. Two rows of one framework carry different markers, and capture step 1 settles that at each of the five shapes in which it mints two: siblings of a row differ by the directory their paths name, the rows a workspaces division carves differ by their own workspaces' `package.json` paths, the rows a Cargo division carves differ by their own members' `Cargo.toml` paths, and two hinted commands that matched nothing, or two declared suites, differ by the ordinal theirs carries — a row's own markers in one directory being the case that mints no second row at all, since they collapse to a single candidate. Two of those five are the shapes that used to mint one prefix for several suites — the workspaces carve-out's rows and the hinted commands — each measured returning a status that reported no regression on a tree that had lost a test, and each closed where that marker is minted rather than here. **A third shape did it without minting a second row at all, and two constructs take it** — one `workspaces` candidate whose single command ran every workspace of the repository, and one `Cargo.toml` whose single `cargo test` ran every default member of the workspace, so that in each no marker could have told two units apart — and capture step 1 closes both by dividing the candidate into a row per unit it runs, which is what puts them within reach of this step: a distinction between rows is one the pairing above can carry and this rewrite can follow, where a distinction drawn inside a row is one neither ever sees. **Where a `Makefile`'s `test` recipe drives that candidate's runner, neither division runs at all** — the wrapper rule is asked first (capture step 1) — and the shape is the fourth below rather than this one. **A fourth does it and stays that way**: capture step 1's `Make` wrapper rule folds the candidates one recipe drives into one suite per framework among them, so where more than one of them shares a framework, or where one of them is a candidate a division would otherwise have carved, their tests — or that candidate's units' — print into one output under that row's prefix — and `make test` running once leaves no per-candidate command to divide into, which is why that step settles the row's marker and its counts, names its folded candidates — and a folded divided candidate's units — in `### Notes`, and says outright that its identifier list does not attribute them, rather than dividing. **That shape is reported there, not closed**, and nothing here is asked to make up the difference: such a row pairs above and is rewritten here exactly as any other, and what one of its candidates or units printed and another stopped printing is a distinction inside it. **What it buys, and the trade it makes, is that the comparison now believes step 2's pairing** — the moved-suite fallback included, so where that fallback pairs two suites that are not the same suite the comparison follows it, which capture step 3's prefix already did on a single-suite repository (measured: one suite deleted and another created carrying the same three test names returns `OK` under the prefix as written) and now does on every shape. Measured over capture step 3's three states, each mutated on one tree between the two calls: **1→2** matched **3** of 3 and returned `OK` where comparing as captured matched **0**; **2→1** matched **3** of 5, the two missing being the two that genuinely went away, where comparing as captured matched **0**; and the count staying at two while one suite moves `frontend/` → `apps/web/` matched **5** of 5 and returned `OK` where comparing as captured matched **2**. Every identifier list step 7 returns prints its identifiers **as compared** — one drawn from the baseline rewritten where its suite paired and as captured where it did not, one drawn from this run exactly as step 4 minted it — that being the string the comparison used; `### New failures` and `### Current passing tests` are drawn from this run alone and so are never rewritten. **`Comparison status` is untouched by this**: a rewrite is neither an abort nor a failure to pair, so a run whose only irregularity is a rewritten prefix is still `exact`. Then compare, using the baseline's `### Passing tests` and `### Pre-existing failures` as rewritten:

   | Category | Definition |
   |----------|-----------|
   | **Regressions** | Was in baseline `### Passing tests` AND is now failing |
   | **Missing from run** | Was in baseline `### Passing tests` AND is not present in the current run at all (treat as regression-severity — test may have been silently dropped or suite aborted early) |
   | **Newly fixed** | Was in baseline `### Pre-existing failures` AND is now passing |
   | **New failures** | Is failing now AND was not in baseline `### Pre-existing failures` AND was not in baseline `### Passing tests` (new test added and already failing) |

6. **Compute Status** — before returning, set the first that applies:
   - `REGRESSIONS` — **Regressions** count > 0 OR **Missing from run** count > 0 (both are regression-severity per the table above). This is where a suite the baseline recorded `OK` **with at least one passing test** and that aborted here lands, since those tests are then unaccounted for. **It is tested first**, so a run in which every suite aborted is a regression where the baseline had run them, rather than being written off as a run that did not happen
   - `RUN_FAILED` — no suite produced counts in this run at all, so nothing was verified. Reached only where the baseline held **no passing test that could go missing**: any suite it recorded `OK` with passing tests would have put them into **Missing from run** above, so what is left here is a baseline of rows reading `RUN_FAILED`, `not run` or `NO_TESTS`, rows recorded `OK` that contributed no passing test, and suites that had no row at all — **at least one of which is `OK` or `NO_TESTS`**, since a baseline marking none of them so never reaches this step, the pre-step gate having refused it
   - `PARTIAL` — some suite produced counts, and at least one produced none here **and no counts in the baseline either** — its baseline row reads `RUN_FAILED` or `not run`, so it aborted at both ends or the `command_hint` left it out at both. The comparison is sound as far as it reaches and says nothing at all about that suite
   - `OK` — otherwise: the comparison was possible and found no regressions. **The aborts this value tolerates are the ones that could lose no baseline *passing* test** — a suite whose baseline row is `NO_TESTS`, one with no row at all, and one whose baseline row is `OK` but whose contribution to `### Passing tests` was empty because its every test was already failing — each recorded by step 3 in `### Notes` and `### Suites`, and each moving nothing here; every abort that did lose a baseline passing test has already been taken by a value above

   Three returns come before this one — the pre-step gate above, `RUN_FAILED` where the supplied baseline covers no suite; step 1, `COMMAND_NOT_FOUND` where no candidate matched and no `command_hint` supplied one; and step 2, `RUN_FAILED` where nothing pairs with the baseline — so none of them is computed here.

   **The `Status` carries regressions; it does not carry new failures.** A test failing now that was in neither baseline list is a **New failure** by step 5's table, and no value above counts one — so `OK` and `PARTIAL` are both reachable with `### New failures` non-empty. A caller whose own run wrote tests between the capture and this call reads that list as well as the `Status`, or it reads its own broken test as a pass.
