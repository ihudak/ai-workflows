# Test suite detection

`test-baseliner` is the agent `/implement`, `/upgrade` and `/vuln` run — directly, or through `upgrade-executor` and `vuln-fixer` — before a change to record what already passes, and again afterwards to diff against that record. It finds your test suites by scanning for **markers** — a file whose presence names a build system — and the set of markers it knows is a table in the agent's own `capture` step 1. **That table is the coverage**: a suite runs because its marker is a row, and a build file the table does not list detects nothing on its own. Where nothing in the table qualifies at all, the agent falls back to the test command your repository declares for itself — in its CI configuration, or failing that its contributing guide or README. This page publishes the table so you can answer "is my technology covered?" without opening an agent file, and says what happens when the answer is no — which is a reported outcome rather than a failure.

## The detection table

Seventeen rows, over twenty-four distinct markers (five of them globs). `Gemfile` is the one marker that appears in two rows, one per Ruby test framework; the other rows take a marker each, several of them with alternative names. A marker becomes a **candidate** only where its own qualifier holds.

| Marker | Framework | Qualifies when | Command |
|---|---|---|---|
| `pom.xml` | Maven | always | `./mvnw test -q` (falls back to `mvn test -q` with no wrapper) |
| `build.gradle` or `build.gradle.kts` | Gradle | always | `./gradlew test` (falls back to `gradle test` with no wrapper) |
| `Gemfile` | RSpec | `spec/` exists | `bin/rspec --format documentation` (falls back to `bundle exec rspec --format documentation` with no binstub) |
| `Gemfile` | minitest | `test/` holds a `*_test.rb` or `test_*.rb` file other than `test_helper.rb`, or `Rakefile` declares a `test` task | `bin/rails test -v` where `bin/rails` exists, else `bundle exec rake test TESTOPTS=-v` |
| `Package.swift` | SwiftPM | always | `swift test` |
| `*.xcodeproj` or `*.xcworkspace` | Xcode | no `Package.swift` beside it — a package with a checked-in or generated project is one body of tests, and `swift test` is its pinned entry point | `xcodebuild test -scheme <scheme>`, the scheme read from `xcodebuild -list` |
| `go.mod` | Go | always | `go test ./... -v` |
| `Cargo.toml` | Cargo | always | `cargo test`; with a `[workspace]` table, one `cargo test -p <name>` per default member |
| `package.json` | Jest/npm | `scripts.test` is present and is not the `npm init` placeholder (`no test specified`), or a `workspaces` field is present and some workspace's own `package.json` has one | `CI=true npm test`; with a `workspaces` field, one `CI=true npm test --if-present --workspace <name>` per qualifying workspace |
| `pyproject.toml`, `setup.py`, or `pytest.ini` | pytest | always | `pytest -v` |
| `*.csproj`, `*.fsproj` or `*.vbproj` | .NET | the project file names a test package (`Microsoft.NET.Test.Sdk`, `xunit`, `NUnit`, `MSTest` or `TUnit`) or sets `IsTestProject` to `true` | `dotnet test <project file> --logger "console;verbosity=normal"`; under a `global.json` selecting Microsoft.Testing.Platform, `dotnet test --project <project file> --output Detailed` |
| `phpunit.xml`, `phpunit.dist.xml` or `phpunit.xml.dist` | PHPUnit | always | `vendor/bin/pest` where it exists, else `vendor/bin/phpunit --testdox` (falls back to `phpunit --testdox`) |
| `build.sbt` | sbt | it is the outermost `build.sbt`, or has a `project/build.properties` beside it | `NO_COLOR=1 sbt test` |
| `mix.exs` | Mix | always | `mix test --trace` |
| `pubspec.yaml` | Dart | `test/` holds a `*_test.dart` file | `flutter test --reporter github` for a Flutter package, else `dart test --reporter github` |
| `CMakeLists.txt` | CTest | it calls `enable_testing()` or `include(CTest)` | `cmake --build build && ctest --test-dir build --output-on-failure` (`.` instead of `build` for an in-source build) |
| `Makefile` | Make | a `test` target exists, and CMake did not generate the file | `CI=true make test` |

Where a tool ships a pinned entry point, that is the command: `./mvnw`, `./gradlew`, and Ruby's `bin/` binstubs ahead of `bundle exec`. A JavaScript command carries `CI=true` because several runners watch for file changes outside CI, and a watcher never returns; two runners do not read `CI` and are given their own single-run flag instead (`karma start … --single-run`, `ng test … --watch=false`), rebuilt from the invocation rather than appended to the script's text.

The six rows from .NET to CTest were measured against current toolchains before they were written — .NET SDK 10.0.401, PHPUnit 13.3.6 and Pest 5.2.1, sbt 1.11.7 with ScalaTest and MUnit, Elixir 1.20.4 and 1.18.4, Dart 3.13.5 and Flutter 3.47.5, and CMake 4.4.3 — and several of their commands differ from what each tool's documentation suggests because of it:

- **.NET runs one suite per test project, not one per solution.** NUnit and MSTest print a test as its bare method name, so a whole solution's tests in one list collide; a project file as the marker gives each project its own suite. The qualifier reads the project file because the MSTest template references `MSTest` alone, and a project that gets its test packages only from a `Directory.Build.props` is not detected. A `global.json` selecting Microsoft.Testing.Platform switches the command, because that runner rejects the VSTest `--logger` flag and exits having run nothing.
- **PHP runs Pest wherever Pest is installed** — PHPUnit over a Pest suite exits with a fatal error — and `--testdox` is what names each test.
- **sbt carries `NO_COLOR=1`** because MUnit colours its output even when piped and ignores sbt's own `-no-colors`. Its counts come from sbt's summary line for MUnit and from ScalaTest's own line, which replaces it. A nested `build.sbt` is a separate build only where `project/build.properties` sits beside it; otherwise it is a subproject's settings, which the build above runs.
- **Mix carries `--trace`** because nothing else names the passing tests, and it costs something — see the known limits. Both summary formats are read: Elixir 1.20's `Result:` line and the older `N tests, N failures` one.
- **Dart asks for the `github` reporter**, the one that prints a line per finished test with its outcome; a Flutter package must run under `flutter test`. A package qualifies only with a `*_test.dart` file, because without one the runner exits non-zero instead of reporting zero tests.
- **CTest builds the configured tree first and never configures one.** `ctest` alone runs whatever was last built — measured, a stale tree reported every test passing where a rebuild showed it failing — and the generator, toolchain and options that switch a project's tests on are the project's. With no configured tree the suite fails loudly and says so. The same measurement is why a `Makefile` CMake generated is not a `Make` suite: its `test` target runs `ctest` without building anything.

## How the scan reads that table

The scan reads **every** marker and never stops at the first — first-match-wins is what once made a Rails application carrying an asset-build `package.json` report a JavaScript baseline for a Ruby suite. It is rooted at the project root the caller names, descends into that root's subdirectories so that a front end in its own directory is a suite of this repository, and prunes `node_modules/`, `vendor/`, `deps/`, `target/`, `build/`, `dist/`, `out/`, `coverage/`, `.git/`, `.gradle/`, `.venv/` and `venv/` wherever they occur — measured, an unpruned scan returned five markers where two were real, one of them a dependency's own `package.json` that qualifies under the table's rule. It does not follow symbolic links either: a Flutter application links each plugin it uses into its platform directories, and following those links reached four plugin `pubspec.yaml` files, two of them qualifying.

Where two qualifying directories of one row sit side by side, neither containing the other, they are two suites and **both run**. Where one contains another of the same row, only the outer is a candidate and the inner is named in the return's `### Notes`, because the containing command usually recurses over it — a Maven or Gradle reactor, `pytest`'s own discovery — and running both would sum the same tests twice; where it does not recurse, that note is marked `CAVEAT: `, because there a qualifying suite genuinely went unrun. Two kinds of candidate are split further rather than run as one: a `package.json` carrying a `workspaces` field becomes one suite per workspace with its own test script, and a `Cargo.toml` carrying a `[workspace]` table becomes one suite per default member. A `Makefile` whose `test` recipe drives another candidate's runner is a wrapper and not a rival — that candidate runs through `CI=true make test`, the project's own pinned entry point, and is parsed with its own framework's patterns.

## More than one suite

A repository holding a Rails suite and a JavaScript one, or a Java suite and an Angular one, has two real test suites, and a baseline taken from one of them cannot detect a regression in the other. So **every candidate the scan resolves to a suite is baselined**, each from **its own run directory** — the directory its qualifying marker sits in, for an ordinary suite — and each under **its own copy of the ten-minute bound**, so a slow suite cannot truncate a later one. With no test command supplied they run in the table's own row order, and within one row in their marker paths' lexicographic order, so the same repository yields the same order on every run.

The return reports **per suite**. `Framework` and `Command` are comma-separated lists in run order, a name repeating where the run holds more than one suite of it, and a `### Suites` section carries one line per detected suite: the framework, the marker that qualified it as a path relative to the scan root, the command, that suite's own status (`OK`, `RUN_FAILED`, `NO_TESTS` or `not run`) and its own counts. The run-level `Status` is one value computed from the set — `PARTIAL` where at least one suite produced counts and at least one did not, which is incompleteness rather than a verdict on your code. Every test identifier carries a prefix naming its suite — the framework alone where that framework names one suite, the framework plus that suite's marker path where it names several — so two suites cannot mint the same identifier and mask each other's loss. What the prefix does not separate is what a `Make` fold puts *inside* one suite: several candidates print into one output under one prefix, which is the first of the known limits below.

## A stack the table does not list

A stack with no row — Haskell, Zig, Bazel, Deno, Bun, Node's built-in runner, Julia and the rest — qualifies on none of its own build files. Three things can still give it a suite. A `Makefile` with a `test` target qualifies regardless of what the recipe drives, which is the table's one stack-agnostic row. Any other marker the repository happens to carry, such as a `package.json` with a real test script, qualifies on its own terms. And where **nothing** qualifies, the agent takes **the test command the repository declares for itself**:

1. It reads these files at the scan root, in this order, and stops at the first that yields a command: `.github/workflows/*.yml` and `*.yaml` (in lexicographic order), `.gitlab-ci.yml`, `.circleci/config.yml`, `azure-pipelines.yml`, `bitbucket-pipelines.yml`, `Jenkinsfile`, `CONTRIBUTING.md`, `README.md`.
2. From a CI file it takes the one line of each step that runs the tests — never the checkout, install, cache, build-only or publish lines — and runs it as `CI=true <line>`, in the step's working directory where the step names one; a line repeated across jobs is taken once. From a document it takes a command in a code block under a heading about running the tests.
3. It refuses a line that carries a CI expression (`${{ … }}`) or a variable set elsewhere in the file, runs `sudo`, or installs, deploys or publishes anything.

Each line taken is a **declared suite**, listed in `### Suites` as `declared#1`, `declared#2` and so on. Where its command names a runner the table has a row for — a Python repository with no `pyproject.toml` whose CI runs `pytest`, say — it is parsed with that row, and its test names are exact. Where it names none, it is parsed best-effort like the `Make` row, for `X passed` / `X failed` / `X pass` / `X fail`, and where that finds no count or no test name the suite is recorded **by its exit status**: one test, `exit status 0`, passing when the command exits 0. That catches a change that breaks the suite; it cannot say which test broke. The same exit-status rule applies to a `Make` suite and to a test command you supply that names no runner in the table.

The fallback is narrow on purpose:

- It fires **only when the table matched nothing.** A command read out of a CI file never runs beside, or instead of, a suite the table did find — that would be the guess the table exists to avoid.
- A verify runs **the command the capture ran**, read back from the baseline and never re-read from the CI file, so a change that edits the workflow cannot change what is compared.
- Every declared suite carries a `CAVEAT: ` note naming the file and the step it came from, and every caller surfaces those notes whatever the status.

Where nothing qualifies and the repository declares nothing either, **that is not a failure and it is not silent.** With no candidate, no declared command and no supplied one, the agent runs nothing and returns its normal structure with `Status: COMMAND_NOT_FOUND`, `Framework: not detected`, every count 0, and a `### Notes` line saying no runner was found and naming the files it read. It does not fail the call.

`/implement` acts on that status at Pre-Phase 3.5 — after the branch is cut and **before any file is edited**, which is the last point at which the answer can still be a baseline rather than a test run. It surfaces the block's `### Notes` and `### Suites` first, then asks: *Specify test command to use*, *Skip tests for this run*, or *Cancel*. A command you supply is recorded, the capture is re-dispatched immediately with it, and that same command is carried on every later `test-baseliner` call in the run, because a verify over a different set of suites is not a comparison. A skip is written into the Phase 5 report's `### Deferred items` with its reason. `/upgrade` and `/vuln` reach the same question at the same point — after the capture and before anything is edited — and each asks it once for the whole run, because each captures once for the whole run. A command you supply is carried forward the same way in all three, onto every later call — including the verify each of these two runs inside its own agent. Their middle option differs from `/implement`'s in what it commits you to: there is no work to skip in a dependency bump, so it applies the change unverified and every pull request the run opens is a draft carrying a DO-NOT-MERGE line. [`/vuln`'s page](../commands/vuln.md) records what its two paths did before they were made to agree.

A supplied command is the coverage a repository has until its stack is a row. It becomes the run set, one suite per command; a command that matches no detected suite is a suite of its own, its framework the runner the command names or `hinted` where it names none, and its `### Suites` marker reads `command_hint#<n>` for its position in what you sent. Detection still runs underneath — a supplied command narrows what is **run**, never what is **detected** — so any suite it leaves out still gets a `### Suites` line, marked `not run`. Read that section after supplying a command: that is what it is there for.

## What adding a technology takes

The coverage is a table, and the machinery around it is general. Adding a technology is **two rows**:

1. A row in `capture` step 1's detection table — the marker, the framework it selects, the qualifier that turns the marker into a candidate, and the command. The command carries whatever verbosity flag that runner needs, because the parse also collects each passing and failing test's identifier out of the same output.
2. A row in `capture` step 3's parse table — the patterns that runner's output prints its passing, failing and skipped counts in. That table has sixteen rows today, SwiftPM and Xcode sharing one.

Measure both rows against the runner rather than writing them from its documentation. Two of the six rows added together would have been wrong otherwise: Elixir 1.20 prints its summary in a new format, and sbt prints its own count line for MUnit but not for ScalaTest.

Everything between those two tables is written against a row rather than against a framework, and a new row inherits all of it: the rooted, pruned scan; the containment rule; the per-suite run directory and the per-suite bound; the suite prefix on every identifier; the one `Status` computed from the set; and the pairing a `verify` call does against the baseline's `### Suites` rows.

What is **not** general is worth knowing before writing a row, because each of these was written for one ecosystem's shape: the `CI=true` prefix and the two-runner watch carve-out are JavaScript's, the `workspaces` and `[workspace]` divisions are npm's and Cargo's, and the wrapper rule is `Make`'s. A runner that watches for file changes by default needs a lever of its own — no other row's command watches, the fifteen non-JavaScript ones each running once and exiting, and `make test` carrying `CI=true` unconditionally because a recipe hands its environment to whatever runner it reaches — and a build system that runs its units under one command needs the question the two divisions answer: whether one row can carry them all, or whether each unit needs its own.

## Known limits

Six limits ship with the current behaviour. Every one but Mix's is disclosed in the return: the agent opens a note whose harm the `Status` and the counts cannot show with the literal `CAVEAT: `, and every caller surfaces marked lines whatever the status was — including `OK`. Mix's is a property of the row, stated here instead, since a note on every Elixir run would teach you to skip the section.

**A `make test` recipe driving two or more suites of the same framework reports correct counts and unattributed test names.** The wrapper rule is asked of a candidate before either division, so a candidate a `Makefile` drives is folded and never divided — which also brings the `workspaces` or `[workspace]` units of a folded candidate under this limit. `make test` runs once by construction, so a test identifier printed by more than one of them is recorded once and a loss in one is masked by another's copy: measured, the baseline recorded 3 identifiers for 4 passing tests, nothing landed in *Missing from run*, and the run returned `OK` on a real regression. The counts, the status and the per-suite marker stay correct, and a unit that goes away entirely is not masked at all. `### Notes` names every candidate the row folded and every unit of a divided one it took, says the identifiers are not attributed to them, and carries the mark.

**A `grunt` or `gulp` task that configures Karma inline, naming no `configFile`, still runs to the per-suite bound.** `grunt-karma`'s own README calls that the recommended configuration, and it leaves nothing to hand `karma start`, so there is no single-run command to rebuild the suite into. It runs the table's own `CI=true npm test`, the watcher runs to the ten-minute bound, and the row reads `RUN_FAILED` — a suite that was fine, recorded as a runner failure. It is reported rather than rescued: `### Notes` names the script and what could not be rebuilt. If a suite of yours stalls for the full ten minutes, this is the shape to look for first.

**Two or more suites of one framework that relocate between the capture and the verify call pair with nothing.** A verify pairs each suite to its baseline row on framework **and** marker value, and falls back to a move only where exactly one baseline row and exactly one detected suite of that framework are left unpaired. Where more than one of each is left, nothing can say which moved to which, so none of them pairs: the baseline rows count as gone and their tests land in *Missing from run*, which is regression-severity, while the suites found at the new paths count as new — on a tree that may have lost nothing. A divided candidate reaches this with a single move, because moving a `workspaces` or `[workspace]` root moves every one of its rows' marker paths at once. `### Notes` carries both halves. One suite that relocates on its own is unaffected: it pairs by the fallback, and the verify rewrites its prefix before comparing.

**A suite recorded by its exit status says that something broke, not what.** That is every declared suite and every `Make` suite or supplied command whose output yields no count or no test name. Any failing test turns its one identifier, and a test already failing when the baseline is taken hides every later failure in that suite. The note on it is marked.

**Mix's `--trace` lifts every per-test timeout.** Measured, a test tagged `timeout: 200` that sleeps a second fails under `mix test` and passes under `mix test --trace`. The effect is the same at both calls, so it invents no regression, but a change that makes a test overrun its own timeout is not caught. `--trace` is still carried, because it is the only way to have the passing tests named at all.

**A test name printed twice in one suite is recorded once.** NUnit and MSTest print a test as its bare method name, so two classes in one .NET project naming a method alike print one name twice, and losing one of them is masked by the other. `### Notes` names every such duplicate with the mark.
