description: Delivery conformance check. Given an Epic (run by its Dev, before its pull request merges) or a PRD (run by the PE, once every Epic has merged), traces every requirement against the Epic's branch, or each repository's default branch, has a person settle each discrepancy — fix the code, amend the document, or accept, never on a threat mitigation or on an ARD Rule an unused threat model, or an unreadable threat, may rest on — and records the decisions in _conformance.md. Changes no code and rewrites no requirement.

Check what was built against what was specified: $ARGUMENTS

**Core references.** A citation of the form `workflows-core:<name>` names a shared reference in the `workflows-core` plugin. Load it with `Skill(skill: "workflows-core:reference", args: "<name>")` — never by path: `${CLAUDE_PLUGIN_ROOT}` resolves to this plugin, which does not carry it.

These shared references load by part — `escalation-rules`, `finding-triage`, `next-phase-offer` and `session-hygiene`. A citation of one names a rule: before applying it, load the part that holds it, `Skill(skill: "workflows-core:reference", args: "<name> <part>")`, the part its rule index names, unless that part is already in this conversation word for word; never guess a part's name — until you hold the index (every part carries it), load it with `args: "<name> index"`. A citation that names no rule the index holds loads the whole reference, `args: "<name>"`. Never apply a rule of these references from memory.

`/conformance` closes an implementation by checking it against what was specified. Given an Epic or a
PRD address, it traces every requirement of that unit against the code — on an Epic run the Epic's
own branch, before its pull request merges or where the branch has gone on since, and otherwise each
repository's default branch, once the work has merged — puts each discrepancy to a person, and records
the decision in `_conformance.md`, in the format
`${CLAUDE_PLUGIN_ROOT}/references/conformance-format.md` fixes. It changes no code and rewrites no
requirement: *fix the code* becomes a follow-up, and *amend the document* a note and a recommended
command — on a design's Rule, the command alone.

**An Epic run is the Dev's**: the Dev runs it on their Epic after `/dev-workflows:implement`, before
its pull request merges, on the branch `workflows-core:implementation-format` §5's `unit-branch`
finds — in each repository, the one its latest block in `implementation.md` records — and its
decisions are `proposed`. After the merge, it reads the default branch — save where the branch has
gone on since (`after_merge`), when it traces the branch's tip, the merged work and what followed it
(Phase 1 (c)).
**A PRD run is the PE's**: the PE runs it
once every Epic is done and merged, its decisions are `final`, and it rules on every decision a Dev
recorded — none is carried silently.

Usage: `/conformance <EPIC-KEY | PRD-KEY | @<path>> [--skip-costs] [--skip-feedback] [--enforce-model=<model>]`

was traced, and the report's *Not traced* names those repositories. An `own_part` requirement's

**A mitigation's verdict** is composed after that merge, from every section any repository returned for it, since a check one repository holds may be called, or tested, only from another:
- **Its shape** is the run's to judge, from what the Rule requires — never from the Rule's words about itself or a tracer's `not owed`: a Rule carried out by code that must be reached to act — a check, a filter, a handler — **owes a call site**; any other owes none.
- **A merged `not-checkable`** is the run's to judge as well — save, on an Epic run, an `[AD#n]` Rule that binds only components other than this Epic's (the handoff file's rule 3): where code can show the Rule — it owes a call site, or states what code does, as a storage format does — it is *unverified*, settled by `a re-run that traces it`; only one no code can show — a policy, a configuration held outside the repository — stays `not-checkable`.
- **Where it owes one**, it is *unverified* where any of its sections holds no `reached by:` line, whatever that section's verdict, or a `satisfied` one reads `not owed`; otherwise, merged `satisfied` with no `reached by:` location in any section, it is `partial`, its `shipped:` ending `the check is not called`.
- **A `[DT#N]`** merged `satisfied` with no `test:` location in any section is `partial`, its `shipped:` ending `the test is missing` — after `the check is not called; ` where both hold.

Each *unverified* here is listed as Phase 3 lists one.

## Phase 3 — Re-check before asking

Verify each `partial`, `missing` and `contradicts` verdict at the location it cites, in the manner of
`workflows-core:finding-triage`'s *verification step*
(`Skill(skill: "workflows-core:reference", args: "finding-triage verify")`): read the evidence
yourself, at the `commit` handed to its repository's tracer.
- **Rests on a sibling Epic's part** — on an Epic run, an `own_part` requirement's `partial`, `missing`
  or `contradicts` whose evidence lies on a component of `components.siblings`, or whose shortfall is a
  part the requirement places on one (Phase 2, *A sibling Epic's part*) → taken before the outcomes
  below: it is no discrepancy of this Epic's, whatever the code at that location shows. Judge the
  requirement again without that part — read the rest yourself, at the `commit` handed to its repository's tracer — and record the verdict
  the rest bears: `satisfied` with the evidence of every part but the sibling's; a discrepancy on the
  rest, confirmed by that reading; `not-checkable` where it is an `[AD#n]` Rule that binds only
  components other than this Epic's (the handoff file's rule 3); or *unverified*, as below, where
  that reading settles neither.
  The sibling Epic's part is named as a tracer names it. The report's *Dropped at the re-check*
  names the tracer's verdict and the sibling Epic it rested on.
- **Confirmed** → a discrepancy, numbered `[DD#n]` when the record is written (`conformance-format.md` §5).
- **Could not be settled either way** → *unverified*: neither a discrepancy nor satisfied. It is never
  asked about — no decision can rest on a verdict nobody could confirm — and takes no `[DD#n]`: the
  report and the record's `## Unverified` list it with what would settle it, and a later run, of
  either kind, traces it in full.
- **Does not hold** → dropped; the report names it and why.
- **A `satisfied` verdict that cites no `file:line`** is not taken as satisfied: it is *unverified*,
  since a tracer that misses a discrepancy is the one error this re-check would otherwise never see.
  A `missing` verdict's evidence is the search it ran — `evidence: none — searched …` — which is what
  absence rests on.

**Every mitigation that would be taken as satisfied is composed and re-read first, whatever its tracer returned.** One this re-check takes as satisfied by any route — its discrepancy dropped, or judged again without a sibling Epic's part — is first composed as Phase 2 composes one merged `satisfied`, the section of each repository holding the evidence that settled it read as a `satisfied` one. Each mitigation still `satisfied`, the compose's or this re-check's, is then read, in the verification step's manner, at **its evidence** — each `satisfied` section's, or what settled it here — every `test:` location of its sections and, where its Rule owes a call site, every `reached by:` location. A location is read at the `commit` handed to its repository's tracer — one a tracer cited only where its `@` is that commit, whole or its first seven or more characters — by `git -C <repo_path> show <commit>:'<path>' --`, never where its path holds a `'`; every search this read runs is the handoff file's call-site search, held to its name class, at the searched repository's `commit`: `git -C <repo_path> grep -n -F -e '<name>' <commit>`. It stays `satisfied` only where the read confirms each of these, and is otherwise *unverified*:
- **the evidence** does what the Rule states;
- **the test** asserts the behaviour the Rule states, and is not skipped.

**A `reached by:` location counts only where the read confirms it**, in whichever repository it lies, to be a call site as the handoff file's *A requirement marked `mitigation: true`* defines one — code that runs in production — of the code at its evidence, and not unreachable on its face: under a condition that is always false, after an unconditional return, or in a file nothing loads — no import of it found, and no entry point, configuration or framework convention of the product's own build or start-up that runs it, which an example, a script, a tool or a fixture never is. In a repository that does not hold its evidence, it calls the symbol, package or endpoint that code defines, and one that matches only a name the Rule's text gives does not count. A location that does not count makes nothing *unverified*. Where the mitigation's Rule owes a call site and no location counts, the mitigation is demoted as the compose demotes one: `partial`, *the check is not called*. **Before *the check is not called* is a discrepancy**, search every repository this run traced, by that call-site search of the check's name as the code at its evidence defines it: a found line the read confirms as this paragraph confirms a location drops that demotion — the report's *Dropped at the re-check* names it — and, where no other demotion stands, the mitigation is re-read as above. The read confirms that the lines exist and reach the check; it does not confirm that they run in production, or that anything reaches a call site in turn.

**On a re-run, and on a PRD run for each Epic record, re-check each entry on file** against the code at
the evidence it recorded, reading its requirement's current text in its document, and flag it per
`conformance-format.md` §4 — on a re-run, an entry the code now satisfies is `resolved`, and one whose
requirement is gone or withdrawn is `orphaned` or `requirement withdrawn`; on a PRD run, for Epic entries: `stale` — an `amend-document` or `accept` entry whose requirement the merged
code now satisfies; `fixed` or `still open` — a `fix-code` entry, as the merged code stands; `orphaned` —
an entry whose requirement text is no longer in its document; `requirement withdrawn` — one whose id is
now superseded or withdrawn. Where the run folder is open, each entry is read from the inventory's copy of its record (Phase 2, *The inventory*).

**The verdicts — where the run folder is open** (Phase 0 step 3a). End this phase by writing what Phases 2 and 3 settled, `put <folder> 'scratch/p3/verdicts.md' --from -`, in this form, each bracket replaced by its value, each path under the specs repository relative to `$SPECS_PATH`:

```
trace_model: [the --model of Phase 2's dispatch calls, each tracer's where they differ]
## Requirements
### r<n> [its key] [its id]
- outcome: [satisfied | discrepancy | unverified — what would settle it | dropped — why | not-checkable — its reason | not traced — why]
- verdict: [the verdict the merge composed and this re-check kept: satisfied, partial, missing, contradicts or not-checkable]
- shipped: [what shipped, as the section the merge kept says it]
- evidence: [each repository's evidence, as the merge kept it — or the search a missing verdict rests on]
- test: [a mitigation's, as its sections give it — omit this line otherwise]
- reached by: [a mitigation's call sites this re-check counted — omit this line otherwise]
- sibling parts: [each sibling Epic's part, as a tracer named it — omit this line where none]
- repository: [the repo_slug whose verdict the merge kept, which Phase 5's follow-up names — omit this line where none]
## Entries on file
[each entry this re-check flagged: <its record key>/[DD#k], its flag, and the r<n> of the requirement its heading names, or none — one per line]
## Notices
[each distinct Untrusted-content notice line a tracer added, verbatim — one per line]
```

One block per requirement of `requirements.md`, in its order. Every later step that names a verdict, an outcome, a section's text, an entry's flag or a tracer's notice reads it from this file. Where the run folder is unavailable, nothing is written here.

## Phase 4 — The walk

An entry the record on file already decided is not asked again while its discrepancy persists
(`conformance-format.md` §5) — save an `accept` on a mitigation, put again (*Put again*, below): each such entry is listed, with its decision — on a PRD run, a Dev entry its ruling
names included, where that Dev entry's heading names the same requirement as the ruling entry's, with
the same `document:`. A Dev entry whose `[DD#k]` now names another requirement — its numbers reused
after a record that never merged was discarded — is asked as any other. On a PRD run, `requirement withdrawn` and
`orphaned` entries are listed, never asked — their decision no longer bears on a requirement — and a
`fixed` entry is listed and recorded `resolved`, never asked: the fix it asked for happened.

**Group the discrepancies that share a cause.** Two items asked with the plain decision array below — an Epic run's, or a PRD item with no Dev entry — share a cause where each has an evidence location in **one shared location**: the same `file:line` at the same commit, or ranges of lines in one file at the same commit that overlap. A **cluster** is the items whose evidence holds one such location, never a chain of pairwise overlaps: in the order of Phase 1 (b)'s list — never the order the walk asks in, so every session forms the same clusters — each item not yet in a cluster starts one at the first of its evidence locations that another item not yet in a cluster also holds, and every later item not yet in a cluster holding that location joins it. An item joins at most one cluster, the first in that order; a cluster of two or more is asked once, and every other item is asked on its own. The cluster's location is that one shared location, as the starting item's evidence gives it (its `file:line`, or its whole range where ranges overlap) — the question names it, each entry's `shared-cause:` records it and Phase 5's follow-up names it — so one fix there settles every item of it. An item whose evidence is `evidence: none — searched …` names no location and joins no cluster; an item with a Dev entry, or a `stale` one, is always asked on its own, since each carries a decision of its own to confirm, and so is a mitigation (below), which joins no cluster.

**The cadence — stated, so a run neither guesses it nor spends a round trip per item.** Above the first question, say how many questions follow, how many of them are clusters and how many items those cover, and that *Cancel* ends the run before anything is written — on a cluster's question by typing `Cancel`, since its array has no room for it. Then put the questions to the person **up to four in one `AskUserQuestion` call**, an item or a cluster per question, and a further call for each four after, as Phase 1 (c) does — none once an answer has ended the run, and where one answer in a call is *Cancel*, the other answers in that same call do not count as decided — each with **no `(Recommended)` marker** — which answer is right is the question itself (`workflows-core:escalation-rules`, *The `(Recommended)` marker is unconditional*). **The rationale rides on the answer**: the person gives it in the answer's notes, or as free text beside the choice, and nothing asks for it separately — save the one follow-up prompt below. Each question states: the requirement, its document and its key; the verdict; what
shipped, with `file:line@commit`; any design note bearing on it; on an Epic run, each sibling Epic's
part the requirement places, named as that Epic's and not judged here; and on a PRD run, Dev's
decision, rationale and flag.

**The order on a PRD run:** Dev's implementation-wins entries first (`amend-document`, `accept`, the
`stale` ones among them), then Dev's `still open` `fix-code` entries, then discrepancies no Epic recorded.
Within each of those groups, and on an Epic run throughout, items are asked in the order of Phase 1 (b)'s list, a cluster at the place of its first item.

Each form below, the cluster's included, is for an item that is no mitigation; a mitigation takes the forms of *A mitigation*, after them.

**An Epic run, and a PRD item with no Dev entry:**
```
choices: ["Fix the code", "Amend the document", "Accept as shipped", "Cancel"]
```
**A cluster** — its question names the shared evidence location, `file:line@commit`, and then each item as an item's question would, one line each:
```
choices: ["Fix the code — all <n>", "Amend the document — all <n>", "Accept as shipped — all <n>", "Split — ask about each of the <n>"]
```
One decision for a cluster is that decision for each of its items, with the one rationale. **Split** puts each of its items as a question of its own, in the next call or calls, at the plain array above, so a cluster is never decided whole against the person's wish.
**A PRD item with a Dev entry** — the two options after the first are the other two labels of the array
above, in its order:
```
choices: ["Confirm Dev's decision — <decision>", "<other decision 1>", "<other decision 2>", "Cancel"]
```
**A Dev entry flagged `stale`:**
```
choices: ["Mark it resolved — the code now matches", "Keep Dev's decision — <decision>", "Cancel"]
```

**A mitigation** — in this phase and Phase 5, any of Phase 1 (b)'s mitigations, its walk-only ones included — is asked on its own and is offered an accept on no form: only the architect accepts a risk, in the threat model. On a mitigation, a decision on file that is not, whole, `fix-code` or `amend-document` is read as `accept`, so that it fails closed. Its question says, besides what an item's says, that it is a mitigation — for a walk-only one, that a threat model the run could not use, or a threat whose Disposition it could not read, may rest on it, whichever made it walk-only, the first where both did. Where walk-only mitigations exist, the walk opens with one line for each of the two that made any walk-only, each printed once whether or not the walk asks anything, `<n>` the number of Rules it made walk-only, a Rule both made walk-only counted in the first line alone:
`Threats: no accept is offered on <n> architecture Rule(s) — a threat model the run could not use may rest on them`
`Threats: no accept is offered on <n> architecture Rule(s) — a threat whose Disposition the run could not read may rest on them`
Its forms:
- **decide** — an Epic run's, and a PRD item with no Dev entry:
  ```
  choices: ["Fix the code", "Amend the document", "Cancel"]
  ```
- **confirm** — a PRD item whose Dev entry decided `fix-code` or `amend-document`, `<decision>` that decision and `<the other of the two>` the decide form's label of the other:
  ```
  choices: ["Confirm Dev's decision — <decision>", "<the other of the two>", "Cancel"]
  ```
- **overrule** — a PRD item whose Dev entry decided anything else, `accept` as read above, which either answer overrules:
  ```
  choices: ["Overrule — fix the code", "Overrule — amend the document", "Cancel"]
  ```
- **stale** — a Dev entry flagged `stale` that decided `amend-document`:
  ```
  choices: ["Mark it resolved — the code now matches", "Keep Dev's decision — amend the document", "Cancel"]
  ```
- **stale accept** — a Dev entry flagged `stale` that decided anything else, `accept` as read above:
  ```
  choices: ["Mark it resolved — the code now matches", "Cancel"]
  ```

**Put again** (`conformance-format.md` §5): an entry of the unit's own record decided `accept`, as *A mitigation* reads it, whose discrepancy persists and whose requirement is a mitigation, is asked again, on its own, its earlier decision and rationale shown, and keeps its `[DD#n]`. An Epic entry is *of its requirement* where this run read it and its heading names that requirement, with the same `document:`:
- one whose `lists:` names an Epic entry of its requirement is not put again: that Epic entry is listed, or ruled on, as `conformance-format.md` §3 says;
- one whose `ruling:` or `lists:`, if any, names none → the decide form;
- on a PRD run, one whose `ruling:` names one → that Epic entry, at the form its own decision takes, as if no ruling stood: the confirm form where it decided `fix-code` or `amend-document`, *Confirm Dev's decision* writing `ruling: confirms <EPIC-KEY>/[DD#k]` and the other option `ruling: overrules <EPIC-KEY>/[DD#k]`; otherwise the overrule form, so a `confirms` is answered as an overrule. Phase 5, *An overrule held back* included, reads the ruling this answer writes.

A free-text answer is normalised into one of the three decisions or the question is asked again — on the stale-entry form, into marking it resolved or keeping Dev's decision; on a cluster's, into one of the three decisions for all its items, *Split* or *Cancel*; on a mitigation's, into one of its own array's options, never an accept: an answer that would accept, keeping or confirming Dev's `accept` included, is normalised into no option and asked again, the question then saying that only the architect accepts a risk, in the threat model — and it is never written through as a new value (`workflows-core:escalation-rules` *Closed-vocabulary pickers must normalise the free-text answer*, the `/conformance` decision picker); what the answer says beyond the decision is its rationale. Record the rationale in the person's own words from the answer's notes or free text. **A decision that needs a rationale and got none gets one follow-up prompt**, in plain text, after the call that carried it returns: *Accept as shipped*, and on a PRD run an answer that overrules Dev's decision — each a departure someone later has to understand; where the person gives none there either, record `—`. *Fix the code* and *Amend the document* need none, and an answer without one records `—` with no prompt. *Cancel* ends the run there: no record, note or follow-up is written, and the report says how many items were decided before it.

**On a PRD run, *Fix the code* on a PRD-level requirement — every requirement keyed `<PRD>`: `prd.md`'s, the PRD-level spec's, a `source: prd` Rule, a mitigation or not, and a `[DT#N]` of the PRD folder's `design.md` — also names the Epic that carries the fix**, where the PRD has Epic folders: `/dev-workflows:implement` reads a follow-up back only on a run of the unit it names, and on a PRD with Epics that unit is an Epic, save a broad slice, which it offers only where the PRD folder holds its own `specification.md` and `design.md` on the default branch. An Epic **covers** a PRD-level requirement where its `epic.md` lists that requirement's id under `## Covers` — a PRD-level spec's `[Uxx]/[ACxx]` listed there as `[Uxx/ACxx]`, or as its story's `[Uxx]`; and a `prd.md` `[AC#n]` listed there itself, or as the `[US#n]` it sits under, where the PRD places each story's criteria under it (`workflows-core:prd-format`). A `source: prd` Rule and a `[DT#N]` are covered by no Epic: `## Covers` holds the PRD's ids and the PRD-level specification's alone, as `product-workflows:epic-writer` writes it and `workflows-core:pre-lint` checks it, so no `[AD#n]` read there names the Epic a Rule's fix goes to — the PRD's only Epic carries it, and otherwise the PE is asked. Where the PRD has one Epic, or exactly one Epic covers the requirement, name that Epic in a one-line notice. Otherwise — no Epic covers it, or several do — print every Epic — key and title, marking each one that covers it — and ask, with no `(Recommended)` marker, one row per Epic where there are four or fewer and otherwise `choices: ["<key> <title>", "<key> <title>", "<key> <title>", "Another Epic (you'll be prompted for its key)"]` — each Epic row's label its bare `key` and its title, as `workflows-core:epic-picker` reads them, never the folder's `EPIC-` prefix, and the row of an Epic that covers the requirement saying so in its `description` — the last carrying in its `description` every Epic the array leaves out — key and title each, in the printed order, marked where it covers the requirement — and asking for the key in plain text, and a typed key resolved only against the keys the array and that description listed (`workflows-core:epic-picker` *The cap*). A PRD with no Epic folder has none to name, and its follow-up names the PRD. **For a cluster decided *Fix the code* whole**, the Epic is settled once for the cluster: its Epic-level items each name their own Epic, and its PRD-level items take the one Epic the rule above names, or the one the person picks, asked once for the cluster's PRD-level items together. Where the Epics so named differ, the cluster stays decided whole and its follow-up is queued once per Epic: each Epic's items share one follow-up, the cluster's location named on each.

**The walk's questions — where the run folder is open** (Phase 0 step 3a). Every question the walk can ask is composed once, before the first is asked, from the verdicts, `requirements.md`, `threats.md`, the inventory's copies of the records and its `epics:`, and written with `put <folder> 'scratch/p4/walk.md' --from -`. From then on each is read from that file, never composed again, so a resumed run asks the same questions, shown the same, and reuses each answer recorded. The file holds, in this form, each bracket replaced by its value:

```
## opening
[the lines printed above the first question: the walk-only Threats: lines *A mitigation* gives, then the line *The cadence* states]
## [gate id]
[the question as asked — its text, then its choices: array]
```

— one `## [gate id]` block per question, in the order the walk asks them: `walk-c<n>` for a cluster, `<n>` its place in the order clusters are formed (*Group the discrepancies that share a cause*), and `walk-r<n>` for an item asked on its own, `<n>` the number its requirement carries in `requirements.md`. After a cluster's block comes one block for each of its items, `walk-r<n>`, the question *Split* puts of it; and after the block of each question whose *Fix the code* names an Epic (above), a block `<that question's gate id>-epic`, the one-line notice or the question that names it, as the paragraph above words them. Where two blocks would share an id, the later takes `-2`, then `-3`, in the order they stand. The cadence line is the one a new run prints; a resumed run prints it with `, <k> of them answered earlier in this run, reused` added, `<k>` the questions `run-gate` finds answered.

**Each question is a recorded gate**, its gate id its block's, its shown text the block's text as it stands, asked through `run-gate` up to four in a call as Phase 0 step 3a's *Recorded questions* says — the questions a *Split* puts, and an `-epic` question, only once the answer that asks them is in. Two follow-ups take an answer typed after an option, so each is a recorded question of its own (`workflows-core:run-folder`, `run-gate`, *An answer in two parts*): the rationale *A decision that needs a rationale and got none* asks for, gate `<the question's gate id>-why`, its shown text `Why <the option chosen>? — <the first line of the question's block>`; and the key *Another Epic* asks for, gate `<the -epic block's gate id>-key`, its shown text `The key of the Epic that carries the fix — <the first line of the -epic block>`. A *Cancel*, and every answer of the call that carries one, is never recorded. An answer this phase asks again — a free-text answer it cannot normalise, or one that would accept a mitigation — records nothing, and the question asked again is recorded under the same gate id, its shown text as asked — on a mitigation, with the sentence saying that only the architect accepts a risk. Phase 5 takes each decision, and its rationale, from the answers so recorded or reused. Where the run folder is unavailable, the walk is asked as above and nothing is recorded.

## Invariants (always enforced)

- NEVER change code, and NEVER switch, pull or write a code repository's working tree — read it at a ref (`workflows-core:read-only-repos` §3–§4); the writes are Phase 1's `fetch` of remote refs, on a writable clone only — with (c)'s removal of a tracking ref whose branch `origin` no longer has — and, on either run, the unreferenced objects the merged test's `merge-tree --write-tree` adds to a clone's object store — through `unit-branch` on an Epic run (`workflows-core:implementation-format` §5), which change no ref and no file
- NEVER rewrite, renumber or delete a requirement; a document changes only by an `## Engineering review` note
- NEVER decide for the person: every open discrepancy is put to them, and a free-text answer is normalised or re-asked
- NEVER accept a mitigation's discrepancy, a walk-only one's included, on any array or from free text, nor carry an `accept` on file forward on one (Phase 4, *A mitigation*)
- NEVER write into a `threat-model.md`, a `design.md` or a findings register; NEVER gate, repair or stop on a threat model, or on the PRD-level `ard-resolution` call made for one (Phase 1 (b), *Threat input*) — the PRD folder's `design.md` a model brings into Phase 0 step 4's gate is gated as any document read
- A threat reads `verified` only on a trace and a re-read made in this run (Phase 5, *Where each threat stands*): no record, read back or carried, makes one so
- NEVER hide a Dev entry from the PE: a PRD run lists every Epic entry with its ruling or its flag, `stale`, `orphaned` and `requirement withdrawn` ones included
- A `[DD#n]` is permanent: never renumbered or reused (`conformance-format.md` §5)
- ALWAYS run `specs-preflight`, the document gate and the record check at Phase 0, and `commit-artifacts` as the run's last action (per `workflows-core:specs-repo-git`) — save as Phase 0 step 3a's *Where a resumed run goes on* says
- An Epic run traces the Epic's branch by `unit-branch`, before or after its merge — and the default branch in three cases: where `unit-branch` finds the work merged (`merged`), where no block names the repository (`none`), and where the Dev answered that a `missing` branch's pull request merged; a PRD run stops where no `implementation.md` in its scope holds a block (`CONFORMANCE_PRD_NOT_IMPLEMENTED`), and otherwise traces merged code, and asks before tracing an Epic, or the work of a PRD with no Epic folder, not shown merged
