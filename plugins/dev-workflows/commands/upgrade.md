Upgrade components: $ARGUMENTS

Usage: `/upgrade <component[:exact|:minor|:latest|:lts]> [<component…>] [--no-commit] [--allow-install-scripts <name>[,<name>…]] [--skip-feedback] [--enforce-model=<model>]`

**Core references.** A citation of the form `workflows-core:<name>` names a shared reference in the `workflows-core` plugin. Load it with `Skill(skill: "workflows-core:reference", args: "<name>")` — never by path: `${CLAUDE_PLUGIN_ROOT}` resolves to this plugin, which does not carry it.

These shared references load by part — `escalation-rules`, `finding-triage`, `next-phase-offer` and `session-hygiene`. A citation of one names a rule: before applying it, load the part that holds it, `Skill(skill: "workflows-core:reference", args: "<name> <part>")`, the part its rule index names, unless that part is already in this conversation word for word; never guess a part's name — until you hold the index (every part carries it), load it with `args: "<name> index"`. A citation that names no rule the index holds loads the whole reference, `args: "<name>"`. Never apply a rule of these references from memory.

**Strip the run flags first.** Execute `strip-run-flags` (`Skill(skill: "workflows-core:reference", args: "run-flags strip-run-flags")`) on `$ARGUMENTS` before anything else reads a token: it removes `--skip-costs`, `--skip-feedback` and `--enforce-model` (with any `=value`), resolves each against its environment default, and returns the `run_flags` record this run carries to its maintenance and routing steps — or stops with `RUN_FLAGS_BAD_MODEL` / `RUN_FLAGS_MODEL_UNAVAILABLE` before any write. Every later step parses only what it leaves.

**Load the question rules.** Load `escalation-rules core` now, with `Skill(skill: "workflows-core:reference", args: "escalation-rules core")`, before this run asks the user anything: every question it asks follows them — two to four options, presented verbatim with the `(Recommended)` marker where one is recommended, and a selection that carries no text.

**Strip `--no-commit` next**, before parsing any component token: an unstripped flag is read as a component name and the run fails resolving it. Take `--allow-install-scripts <name>[,<name>…]` (or `--allow-install-scripts=<name>[,<name>…]`) out of the tokens with it, where given ("Install scripts" below), so a run that resumes past Phase 1 still has it. When `--no-commit` is present, steps 6.5 and 7.5 are both skipped and the changes are left in the working tree. It is the one opt-out from a commit that is otherwise prompt-free (`${CLAUDE_PLUGIN_ROOT}/references/code-handoff.md` §1 rule 5) — typed rather than clicked, which is the difference — and a run under it says once what it costs: the work is recoverable only on this machine.

Each token is one of: `component:1.2.3` (exact), `component:minor` (latest patch on current minor), `component:latest` (latest stable), `component:lts` (latest LTS), or bare `component` (latest compatible with everything else). `--allow-install-scripts <name>[,<name>…]` is an option, not a token ("Install scripts" below).

`component` can be a library, framework, language runtime, build tool, or path like `.github/workflows`.

Each component is committed on its own as soon as its gates pass — see Phase 2's step 6.5 and step 7.5 (`${CLAUDE_PLUGIN_ROOT}/references/code-handoff.md`); the branch is pushed once for the batch where §2.4's consent choice, an `origin` and §2.5's push itself all allowed it, and a pull request opened where **§2.4's consent choice**, §2.8's base-branch ladder and §2.6's `gh` capability probe allowed one as well — §3.1's rows rather than any list written out here are the authority on which line the run emitted. **§2.4 is named in both halves rather than carried forward from the first**, because its second option (*"Push the branch only — no pull request"*) allows the push and refuses the pull request: a clause that let the push's own §2.4 term stand for the pull request's would assert one in a state §3.1 has its own row for. The commit is prompt-free save for a possible secret its scan cannot dismiss (§2.2); only the push and the pull request sit behind a consent choice, asked once for the batch. `--no-commit` skips both steps.

**Ending early.** Every stop this command takes once Phase 0's specs-repo preflight has run — Phase 0.5's (a stash git refuses, the dirty tree's *cancel*, a tree read that fails twice, the branch-start question's *Cancel*, a move git refuses), Phase 1's (a plan declined at step 7, every component `NOT_FOUND` or skipped, a conflict left unresolved), Phase 2 prep step 2's *Cancel this run*, Phase 0.5's `pre_existing_dirty could not be written`, a resumed run's (HEAD off the run's branch at Phase 2 prep step 1, *Stop the run* at *Edits made between sessions* or at a `${CLAUDE_PLUGIN_ROOT}/references/code-handoff.md` §7.4 question), and a halt on a plugin gap — takes `workflows-core:specs-repo-git` §4's refusal tail, which for this command, emitting no cost entry, is step 10's `commit-artifacts` alone: it prints the run's `Specs repo:` line as the stop's last output, after the stop message has said where HEAD and any stash stand and, where the run keeps no run folder, the run's handoff and tree-read files are removed (step 7.6). Once the run folder is open (Phase 0, *Open the run folder*), each such stop runs `run-stop-line` (`Skill(skill: "workflows-core:reference", args: "run-folder run-stop-line")`) right after its own message, `<command>` there being `/dev-workflows:upgrade` and the arguments as given; every component `NOT_FOUND` is the one a resume meets again, its saved plans unchanged, and takes that entry point's start-over form. `UPGRADE_RUN_TAKEN_OVER` takes no tail at all. No maintenance or feedback (steps 8–9) runs, and no `resume.md` is written, as on every run. A run-flag stop before the preflight takes the same commit, skipping only the preflight (that reference's §3). `emit-block` still fires at a plugin-gap halt, before it escalates, as the Invariants say. What ends a component and not the run is none of these — Phase 1 step 6's *cancel the component*, an executor's `BLOCKED`, `NEEDS HUMAN`, a review that stayed blocked — and neither is a step 6.5 commit that does not land, which ends the loop and goes on through step 7.5 to steps 8–10.

## Phase 0 — Specs-repo preflight

**The run is keyless.** `/upgrade` takes component tokens only: it reads no address and resolves no folder, so its run key set (`workflows-core:specs-repo-git` §3.2) is empty, and no step below has a key, a `workitem_key` or a resolved folder to use — never one derived from a branch name or anything else in the tree.

Invoke `Skill(skill: "workflows-core:reference", args: "specs-repo-git specs-preflight")` and execute its `specs-preflight` entry point (§3) inline: flush any leftover session artifacts from an earlier run, retry an artifact commit that failed to push, and settle the branch. This runs against `$SPECS_PATH` only — `git -C "$SPECS_PATH"`, never a `cd`, so the code repo this run is about to upgrade is untouched (§1 rule 1). Prompt-free; it prints its `Environment:` line, and is otherwise silent unless it acts, a guard fires, or §3.1 reports a misconfigured `$SPECS_PATH`. If a guard fires, emit its §5 notice; if it returns `specs_git: blocked` (§3.3 G0) or `specs_git: misrooted` (§3.1), carry that flag for the whole run — the terminal `commit-artifacts` step skips on it.

**Open the run folder** — right after the preflight, before Phase 0.5. No refusal before it depends on what this run writes: the run-flag stops and the preflight's own. Execute `open-run` (`Skill(skill: "workflows-core:reference", args: "run-folder open-run")`) with `--command dev-workflows.upgrade`; no `--key`, the run being keyless; `--specs "$SPECS_PATH"`; `--workdir` the repository's top level, `git rev-parse --show-toplevel`, the code this run upgrades; and `--args '<the arguments>'` — every token of `$ARGUMENTS` as typed, run flags and `--no-commit` included, in their order, joined by single spaces. A keyless run's key holds them, so the same components in another order, or with other flags, are another run, which `open-run`'s step 6 offers; where it resumes one, the strips at the top of this command are made again over that run's arguments. The run carries `run_folder` from here on, and `run_resumed` where it resumed; each call below is `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/run-folder.py" <subcommand> …`, met as `workflows-core:run-folder` §2 says. Where `run_folder` is `unavailable`, every step that names the folder acts as it did before this command kept one.

**Taken over.** Wherever a call of the script exits 9 from here on, or a call that only reads exits 2 with `run folder no longer exists` (`workflows-core:run-folder` §2), stop at once — save in `close-run`, where step 10 says what the run does:
`UPGRADE_RUN_TAKEN_OVER: another session (<id>) took this run over — stopping without writing.`
`<id>` is the session the script's stderr line names (`owned by session <id>`); where that line says the folder was removed, or no longer exists, print instead
`UPGRADE_RUN_TAKEN_OVER: another session started this run over or finished it — stopping without writing.`
This stop takes no tail at all — no `emit-block`, no table, no terminal commit.

**Phases.** As the run reaches each, log it first: `phase <folder> <name>`, `<name>` being `0.5`, `1`, `2-prep`, `comp-<slug>` as each component begins, `7.5` and `8`. A phase a resumed run skips is not logged, nor are the steps a stop runs.

**What stands after it**, each named by heading, with what a resumed run reads in its place: *Phase 0.5 — Settle the tree and the base*, its dirty-tree question, stash, base move and branch-start question being effects `p05-tree` and `p05-base`, whose facts stand in once they are done; *Phase 2 prep* step 1's branch cut, effect `p2-branch`, and its check that HEAD is on that branch; and, in the per-component loop, *Edits made between sessions* and `${CLAUDE_PLUGIN_ROOT}/references/code-handoff.md` §7.4's meeting of a component found `started`, before which no step reads the tree. Those effects are the run's, not a component's, so `--no-commit` work left between two components is never stashed or branched from again.

**Saved dispatches**, each through `run-dispatch` (`Skill(skill: "workflows-core:reference", args: "run-folder run-dispatch")`): area `main`; `--agent-file` `${CLAUDE_PLUGIN_ROOT}/agents/<agent>.md`, every agent here being this plugin's; `--model` the Agent call's `model:`; and an inline return, no agent here taking `result_path`. Each input is its step's prompt, filled from what that step names: `upgrade-planner`'s `comp-<slug>-plan`, step 3's planners one batch as `run-dispatch`'s *A batch* says, and `risk-planner`'s `comp-<slug>-risk` (Phase 1), `test-baseliner`'s captures (Phase 2 prep step 2), and `code-review`'s `comp-<slug>-a<n>-review-<k>` (step 4). The web the planners read is versioned only where Phase 1 records it (a `latest` or `lts` version); `impl-maintenance` and `defect-reporter` run unsaved, their step guarded whole (step 8).

**Writers.** `upgrade-executor`, every phase, and `review-fixer` go through `run-writer` as code-handoff §7.2 says: ids `comp-<slug>-a<n>-full`, `-verify` and `-regress` for the executor's `full`, `verify-resume` and `regression-resume`, and `comp-<slug>-a<n>-fix` for the fixer; each input built as §7.2 says from its step's template, the baseline taken from and attached as `scratch/p2/baseline.md`; tree the top level, no scope. `tree-note` comes where §7.9 says: after step 6.5's and step 7.5's calls, and after each revert the run runs itself (step 3's *After a revert*, §7.4's step 3) and the `node_modules` restore after it.

**Recorded questions**, each through `run-gate` (`Skill(skill: "workflows-core:reference", args: "run-folder run-gate")`), its shown text its own text then its `choices:` array, as asked: Phase 2 prep step 2's capture question, gate `p2-baseline-q<k>`, `<k>` counting the captures from `1`, and the command its first option asks for, gate `p2-baseline-q<k>-text` (*An answer in two parts*), *Cancel this run* never recorded; each `workflows-core:finding-triage` settle prompt on a component's `<k>`-th review, gate `comp-<slug>-settle-<k>`; and *Handling Test Failures*' decision, gate `comp-<slug>-regression`, *Investigate further* never recorded. §2.4's choice is a fact (code-handoff §7.6). Every other question is asked again by a session that reaches it — Phase 0.5's and Phase 1's, the secret scan's, §7.4's, and *Edits made between sessions*'.

**Guarded effects** (`Skill(skill: "workflows-core:reference", args: "run-folder run-effect")`), each named where it is made: `p05-tree`, `p05-base`, `p2-branch`, each component's `comp-<slug>` with its `comp-<slug>-a<m>-revert`, `comp-<slug>-a<n>-own-revert` and `comp-<slug>-commit`, `handoff` and `tail-maintenance`, beside `tail-emit-auto` (step 9). No path into the specs repository and no plugin path is written into a fact or a `put` file.

**On a run that resumed, check its saved results against today's agents and models**, once, before its first dispatch in this session, where it resolves its models — at Phase 1 step 3 where Phase 1 runs, otherwise as Phase 2 prep begins. Execute `changed-agents` (`Skill(skill: "workflows-core:reference", args: "run-folder changed-agents")`) with an `--agent <name>=${CLAUDE_PLUGIN_ROOT}/agents/<name>.md` and a `--model` pair for `upgrade-planner` and `test-baseliner` on `detection_model`, `risk-planner` on `planning_model` and `code-review` on `review_model`, each `run_flags.enforced_model` under §10. A result the run will not dispatch again is left out of `stale`'s list before anything is counted, printed or asked — Phase 1's once the plan is approved, the captures' once a component has begun, each review whose triage stands (step 4), and so every result of a component found `done`: `total` is the count left, and `keep`'s `--ids` take those left. No result is always redone. A capture left out because a component has begun is named in the Upgrade Summary instead: `Baseline: kept from earlier test-baseliner instructions or model (<its id>) — a capture now would measure this run's own edits.`

## Phase 0.5 — Settle the tree and the base (before Phase 1 reads the code)

Phase 1's inventory and every plan read versions off the tree, and Phase 2 applies them to the tree its branch is cut from, so the two must be one tree: a plan made on a local `<base>` behind `origin/<base>`, or on a feature branch the run then leaves, names `from:` versions the executor would not find (`upgrade-executor` step 1 refuses such a plan), and its "never silently downgrade" check is made against the wrong versions. So the tree is settled here, before anything reads it, as `/implement` settles its branch before its first read of the code. Nothing here cuts a branch or edits a file, save the stash a dirty tree's **stash** answer makes; Phase 2 prep step 1 cuts the branch from wherever this leaves HEAD.

1. **Settle the tree.**
   Run `git status --porcelain -z --untracked-files=all`. If dirty, show `git status --short --untracked-files=normal` and say, before asking, that a file of theirs the run then changes is committed whole, their earlier changes in it included (`${CLAUDE_PLUGIN_ROOT}/references/code-handoff.md` §2.2), and ask whether to stash, proceed anyway, or cancel. On **stash**, read `refs/stash` first (`git rev-parse -q --verify refs/stash`, empty where there is none), then run `git stash push -m "pre-upgrade stash"` (tracked changes only), record the resulting stash as `stash_ref` where git made one, and record every path it leaves dirty as `pre_existing_dirty`, from a tree read taken after it (below); where git refuses the stash, show its error and stop as cancel does, nothing branched yet — but read `refs/stash` again, and where it differs from the value read before the push, a stash was still made: record it as `stash_ref` and name it in the stop; on **proceed anyway**, record every dirty path as `pre_existing_dirty`, from a tree read taken now. A **tree read** is `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/tree-snapshot.py" snapshot --dir "<top level>" > "<file>"`, `<top level>` the repository's top level (`git rev-parse --show-toplevel`) and `<file>` a fresh temp file, `command mktemp -t dw-upgrade-snapshot-XXXXXX` (never inside a repo tree: `${CLAUDE_PLUGIN_ROOT}/references/context-management.md`, **Hand off by file, not paste**) — no snapshot of Phase 2 step 3's kind, which records a git tree for a revert (`${CLAUDE_PLUGIN_ROOT}/references/code-handoff.md` §6.1). On either answer, record from it each path a record names, a rename or copy record's two both, with the record's status columns and the read's fingerprint for the path, which the script takes as `${CLAUDE_PLUGIN_ROOT}/references/code-handoff.md` §2.2 defines one, byte for byte — taken here, before the first edit, so a path whose content then changes is told apart from one left as it was. The tree read's paths are raw, as `-z` gives them, because §2.2 enumerates in that form and subtracts this set from it, and a path carrying a space or a non-ASCII byte recorded quoted would subtract against nothing. Never write this read out by hand: a run that once did dropped a record's leading space and corrupted its path. A tree read that exits 2 read nothing — never take its empty file for a clean tree: correct the call and make it once more, and where it exits 2 again, show its error and stop as cancel does. Phase 2's steps 6.5 and 7.5 need `pre_existing_dirty` and `stash_ref` (`${CLAUDE_PLUGIN_ROOT}/references/code-handoff.md` §2.2 carve-outs 1–2); a clean tree records `null` for each. **Once a stash is pushed, every stop that does not reach step 7.5 names `stash_ref` in its own message** — the branch-start question's Cancel and a refused move below, a plan declined at Phase 1 step 7, Phase 2 prep step 2's *Cancel this run*, and every stop between — because no exit of this run may end without saying where the user's stashed work went; under `--no-commit` the `--no-commit` row carries it (`${CLAUDE_PLUGIN_ROOT}/references/code-handoff.md` §3.1).

2. **Settle the base.**
   **Where the branch starts.** Resolve `<base>`, the default branch's name, by `${CLAUDE_PLUGIN_ROOT}/references/code-handoff.md` §2.8 — the ladder Phase 2's steps 6.5 and 7.5 resolve it with, so the base it offers to branch from is the base its pull request targets. Never judge by a list of names: a local `develop` in a repository whose default is `main` is a branch like any other. Once it resolves, refresh `origin`'s refs as `${CLAUDE_PLUGIN_ROOT}/references/code-handoff.md` §2.8.1 step 1 says — this run's one fetch — and print each line §2.8.1 prints again with the Upgrade Summary beside step 7.5's `Code repo:` line.
     - **§2.8's ladder is exhausted** — no `origin`, or an `origin/HEAD` that is unset or names a ref that does not exist, and none of the branches it probes → there is no base to measure against or to branch from: ask nothing, print `Base branch unresolved (<reason>) — branching from the current position.`, print it again with the Upgrade Summary beside step 7.5's `Code repo:` line, and leave HEAD where it is: Phase 2 prep cuts the branch from it.
     - **HEAD is on `<base>`** (`git branch --show-current` prints it) → nothing to ask: make §2.8.1's move, which leaves HEAD on `<base>` save where the local `<base>` is strictly behind `origin/<base>` outside the specs repository; a move git refuses stops the run as **Branch from `<base>`**'s does, below.
     - **HEAD is not on `<base>`** (it prints another name, or nothing on a detached HEAD) → list the commits HEAD carries that the base does not: `git log origin/<base>..HEAD --oneline` (§2.8 yields a `<base>` only where `origin/<base>` exists). Non-empty output → ask, naming `<base>` and listing those commits, whether to branch from current position, branch from `<base>`, or cancel. Empty output with exit 0 → nothing to ask: HEAD holds no work of its own, so make §2.8.1's move for it (its step 5), which detaches it at `origin/<base>`'s commit where it is strictly behind it, outside the specs repository, and leaves it where it is otherwise; a move git refuses stops the run as **Branch from `<base>`**'s does, below. A non-zero exit is a failed read, never "no ahead commits": keep its error rather than redirecting it away, show it, and ask the same question.
     - **Branch from current position** leaves HEAD where it is, and Phase 2 prep cuts the branch from it. **Branch from `<base>`** makes §2.8.1's move now, before Phase 1 reads the tree, which branches from `origin/<base>`'s commit where the local `<base>` is strictly behind it, never moving the local branch, and runs no pull. Where git refuses the move (an uncommitted change it would overwrite), report its error and the paths it named, and stop as cancel does: no branch exists yet, and none is cut from the HEAD the move was to leave. Where the move detached HEAD, a stop before Phase 2 prep cuts the branch names it as `detached at origin/<base> <its short commit>`.

**Guarded, where the run folder is open** (Phase 0, *Open the run folder*). First read `fact <folder> start-branch`, and where its `value` is `null`, record what names HEAD as this phase begins — the branch `git branch --show-current` prints, `detached at <its short commit>` where it prints nothing, `a branch whose name is outside the safe class` for one outside it — which every stop that names the branch the run started on reads.

- **Step 1 is effect `p05-tree`.** `done` — skip step 1: `stash_ref` is fact `stash-ref`, none where it is empty, and `pre_existing_dirty` is read from `scratch/pre-existing-dirty.json` where that stands, else from `scratch/p05/tree-read.json`, else `null`. `none` — once **stash** or **proceed anyway** is answered, or at once on a clean tree, `effect <folder> p05-tree start`; on **stash**, `fact <folder> stash-before --set '<what refs/stash read before the push>'` before the push; then the step, its tree read made and kept in one command, as code-handoff §7.7 says, at `scratch/p05/tree-read.json` in place of the `dw-upgrade-snapshot-` file; `fact <folder> stash-ref --set '<stash_ref, or empty>'`; `effect <folder> p05-tree done`. A stash git refused but still made is recorded as `stash-ref` before the stop step 1 takes on it. `started` — where fact `stash-before` is not `null` and `refs/stash` now reads other than it, a stash was made, pushed or refused: record what it reads as `stash-ref`, take and keep the tree read, and `done`, asking nothing; otherwise step 1 again from its first line.
- **The set as it changes.** Each time the run changes `pre_existing_dirty`, it writes the set as it then stands to `scratch/pre-existing-dirty.json`, and the set it passes on is that file's: `retire` drops each path step 6.5's call carried — the commit's paths, which step 7 drops; `refingerprint` re-takes a fingerprint a revert put back (step 3's *After a revert*, code-handoff §7.4's step 3) — each path the revert touched that holds what the snapshot holds again, so a path a `REVERT-FAILED: ` line left is still the unit's, for its commit (§6.3). Each runs the command below, never by hand and never with a path typed on a command line (code-handoff §6.2), over the set as it stood — that file, else `scratch/p05/tree-read.json`, else `-` — its `<now>` the tree id §6.1's command prints just before it. Exit `5` is the lists', the read's or the filter's, and nothing was kept — a `<now>` §6.1's command could not print fails the same way: make it once more, and where it fails again, stop — `pre_existing_dirty could not be written: <the error>` — never going on, since the next commit would take what the set leaves out. Any other exit but `0` is the `put`'s (`workflows-core:run-folder` §2). *Edits made between sessions* writes its read whole instead.
- **Step 2 is effect `p05-base`**, its facts `base`, the `<base>` it resolved or empty where §2.8's ladder is exhausted, and `base-lines`, each line it printed to print again with the Upgrade Summary. `done` — skip step 2, reading both. `started` — step 2 again whole: each part re-tests what it would change, and nothing of this run's is in the tree yet.

```
( l=$(command mktemp -t dw-paths-XXXXXX) && m=$(command mktemp -t dw-paths-XXXXXX) && r=$(command mktemp -t dw-upgrade-snapshot-XXXXXX) && t=$(command mktemp -t dw-capture-XXXXXX) || exit 5
  trap 'command rm -f -- "$l" "$m" "$r" "$t"' EXIT
  # retire, one of these two lines:
  git -C "<repo>" diff-tree --no-commit-id --name-only -r -z --root --no-renames <the commit's sha> > "$l" || exit 5; read=-
  # refingerprint:
  git -C "<repo>" diff-tree --name-only -r -z --no-renames <its first reverted_from:> <the pre_edit_tree> > "$l" && git -C "<repo>" diff-tree --name-only -r -z --no-renames <now> <the pre_edit_tree> > "$m" && python3 "${CLAUDE_PLUGIN_ROOT}/scripts/tree-snapshot.py" snapshot --dir "<repo>" > "$r" || exit 5; read=$r
  python3 -I -c 'import json,sys
a=sys.argv;L=lambda f:json.load(open(f,encoding="utf-8")) if f!="-" else {"records":[],"fingerprints":{}};R=lambda f:set(open(f,"rb").read().decode("utf-8","surrogateescape").split("\0"))-{""}
s,n,op,ps=L(a[1]),L(a[2]),a[3],R(a[4])-R(a[5]);fp=s.setdefault("fingerprints",{})
old=[r for r in s["records"] if ps&set(r["paths"])] if op=="retire" else [];[fp.pop(p,None) for r in old for p in r["paths"]]
s["records"]=[r for r in s["records"] if r not in old];fp.update({p:n["fingerprints"].get(p,"-") for p in ps if p in fp} if op=="refingerprint" else {})
json.dump(s,sys.stdout,indent=1)' '<the set, or ->' "$read" <retire|refingerprint> "$l" "$m" > "$t" || exit 5
  python3 "${CLAUDE_PLUGIN_ROOT}/scripts/run-folder.py" put <folder> 'scratch/pre-existing-dirty.json' --from "$t" )
```

## Phase 1 — Compatibility Planning (no files changed)

**Where the run folder is open** (Phase 0, *Open the run folder*). Once the plan is approved — `scratch/p1/components.md` stands (below) — a resumed run runs none of this phase: it reads its plan from the folder, and resolves the models step 3's block names as Phase 2 prep begins. Until then a resumed run runs it again from step 1, each value below read back, each dispatch reused while its input matches, and each question asked again save one whose answer a value below holds. A component's `<slug>` is its name lowercased, each run of characters other than `a`–`z` and `0`–`9` written `-`, a `-` at either end dropped, and `-2`, `-3`, … added in requested order where two components give one slug.

- **The tree it plans on**: the id §6.1's command prints, taken as step 1 begins, which each planner's and risk planner's input names on a line `Tree: <id>` after its first, and which fact `p1-tree` records, set again wherever it differs. Where it held another id, the tree has changed since an earlier session planned on it, and step 1's inventory is made again, not read back; step 6's `Current state:` line is built at each dispatch, from the branch and the lines `git -C <top level> status --short --untracked-files=normal` prints, as printed.

**`Caveats:` is the batch-level slot for a different thing, and the two are not merged**: `Not verified:` names a suite the baseline could not cover, which its `### Suites` rows already show, while a `CAVEAT: ` line names something those rows and the counts do **not** show — a suite nothing ran though nothing failed, counts that may be summed twice, a `Make` fold's unattributed identifiers. Fill it from the Phase 2 prep baseline's `### Notes`, verbatim, one marked line per entry, whatever that baseline's `Status` was; write `none` where it marked nothing, which is every batch whose repository has none of the shapes that mint one (`dev-workflows:test-baseliner` capture step 5). A marked line an `upgrade-executor` returned in its own `notes` is that **component's** and goes in its `Notes` cell instead, since only the baseline is captured once for the batch. **Every `NEW-FAILURE: ` line goes in that cell too, named test by test**, and belongs on neither batch line: it is the one entry here that is not about coverage — the suite ran and something in it is red — it is that component's own verify that met it, and it is what moved the batch's `clean_finish` to `false`.

Append a `### Review triage` section with one line per review pass of each SIGNIFICANT/HIGH-RISK component that went through Opus review (`workflows-core:finding-triage` § Reporting): - **Review triage:** [N findings reviewed: M survived, U unverified, X dismissed (C carried, on a re-review)] — survivors: [on a re-review, `finding — severity` per survivor, or "none"; "N/A (first review)" otherwise] — dismissals: [`finding — reason`, or "none"] — unverified: [`finding — if-true severity — what would settle it`, or "none"] — raised: [`finding — from → to — effect`, or "none"] — set aside by the reviewer: [`behaviour — ruling`, or "none"] — settled: [the answer given at a settle prompt, or "not asked"] — or "N/A (SIMPLE / MODERATE, no Opus review)" for components that never reached review.

Under `run_flags.enforced_model` (`workflows-core:model-routing/classification` §10), add one line below the table, `Model routing: bypassed — enforced <id> (flag|env)`, in place of any §2 / §2.1 fallback or degradation the per-component `model_routing` blocks' `notes` would otherwise report; their `opus_available` stays what the environment resolved, never rewritten to match the enforced id.

Include the `impl-maintenance` lessons-learned report after the summary table — or, under `run_flags.skip_feedback`, the `Session feedback: …` line in its place.

On a run that resumed (Phase 0, *Open the run folder*), the Upgrade Summary — under `--no-commit` too — carries the `Resumed:` line (`workflows-core:run-folder`, `run-dispatch`), the `Baseline: kept …` line where `changed-agents` named one, and, where `kept <folder>` returns any id, `Kept from earlier agent instructions or models: <the ids>`.

Also repeat the `Run flags: …` line whenever the run-flags strip at the top of this command printed one during this run (`workflows-core:run-flags` §6).

## Handling Test Failures

`upgrade-executor` cannot prompt the user directly — dispatched subagents have no access to
interactive tools, even when one is listed in their `tools:`. When it returns
`status: TEST_REGRESSION` (previously-green tests now failing, not auto-fixable or still failing after one auto-fix), the
**orchestrator** (this command, running in the interactive session) handles the decision:

- **Name what the run has left unbuilt first.** The baseline was captured with the user's packages built. Every entry marked `restored unbuilt` that any return in this run has listed so far, and every entry this component's own list holds, is a package now on disk without its build, so a failing test that needs one may fail for that reason and not because of this change. List them above the failing tests, each with its rebuild command, and say so; the user can run those commands before answering.
- Present the failing tests clearly (from the executor's `failing_tests` / `diagnosis`), and, where its `notes` explain an auto-fix it made before the second verify, that fix too, saying it is in the tree, unreviewed, and goes into the commit on *Keep the upgrade*.
- Ask, the question's own text naming each failing test and each package `restored unbuilt`, since *Keep the upgrade* turns on them (`workflows-core:epic-picker` *The cap*):
  ```
  choices: ["Keep the upgrade and leave the failing tests for you to fix", "Revert this upgrade and skip it", "Investigate further before deciding"]
  ```
- **"Investigate further"** → show more detail (the diff, full failure output) and re-ask
  the same choices — this loops here at the orchestrator until the user picks keep or revert.
- Map the final choice to `regression_decision: keep-anyway | revert` and re-invoke
  `upgrade-executor` with `phase: regression-resume` (see Phase 2 step 6).

**`status: TESTS_NOT_RUN` is a different return and takes no `regression_decision`.** It means the
verify call compared nothing — no failing tests to show, and nothing about this component's tests known
either way. The changes stay applied. Report the reason the executor recorded, carry the component into
the Upgrade Summary as unverified, and set `clean_finish: false` for the batch (step 7). Never map it
onto `revert`: rolling an upgrade back because a suite could not be started is a decision taken on no
evidence at all.

## Install scripts

`upgrade-executor` installs a new dependency version without its install-time code (`${CLAUDE_PLUGIN_ROOT}/references/install-time-code.md`) and names every package it skipped in `skipped_install_scripts:`, each entry with the command that would run. **This component's list is the union of that field across every return of the component** — on the SIGNIFICANT / HIGH-RISK path the install happens on the call that returns `AWAITING_REVIEW`. The run never runs that code itself and never asks about it mid-run: the Upgrade Summary's `Notes` names every entry, whatever the component's status, each with what runs it later. Where step 6.5 committed the component's change — whatever its status: `OK`, `TESTS_NOT_RUN` and `TEST_REGRESSION_KEPT`, and a `BLOCKED` component step 6.5 still committed — that is the entry's own allow command (that file's last table), run on the component's branch: a rerun would upgrade it again on a branch of its own. Where it did not — `BUILD_FAILED`, `TEST_REGRESSION_REVERTED`, or any component whose change was not committed — it is a rerun of `/upgrade` with `--allow-install-scripts <names>`, which runs exactly those packages' install code after the install (`project:<hook>`, or `project:<member path>:<hook>`, for a project script) — except in a yarn berry project whose linker is not `node-modules`, where each entry carries `yarn rebuild` and everything it would build, and for a uv project install or a Composer plugin, where each entry carries the command the agent's `notes` named — uv's without `--no-build`, Composer's install without `--no-plugins` — for the user to run by hand or not, whatever the status: a rerun allows nothing there. An entry marked `restored unbuilt` — a package an install put back at the version the lockfile pinned before this unit's change, without its build: after a revert, after an earlier unit moved it, or in a clone that never built it — carries its own rebuild command instead, which the user runs in the repository whatever the component's status.

`--allow-install-scripts <name>[,<name>…]`, taken out of the arguments with `--no-commit` at the top of this command, is passed to every `phase: full` `upgrade-executor` dispatch — the calls that install — as `allow_install_scripts: [<names>]`.

- NEVER touch files before the upgrade branch exists
- ALWAYS capture the baseline once before executing any component — and where that capture returns `RUN_FAILED` or `COMMAND_NOT_FOUND`, **ask the operator rather than deciding it** (Phase 2 prep step 2), before the first component executes and while a baseline can still be taken.
