## Phase 0 — Load and classify inputs

**Strip the run flags first.** Execute `strip-run-flags` (`Skill(skill: "workflows-core:reference", args: "run-flags strip-run-flags")`) on `$ARGUMENTS` before anything else reads a token: it removes `--skip-costs`, `--skip-feedback` and `--enforce-model` (with any `=value`), resolves each against its environment default, and returns the `run_flags` record this run carries to its maintenance, cost and routing steps (into run-state `run_flags` at Phase 1.4, read from there after it) — or stops with `RUN_FLAGS_BAD_MODEL` / `RUN_FLAGS_MODEL_UNAVAILABLE` before any write. Every later step parses only what it leaves. Because a direct run's `<prompt>` is free prose kept verbatim, that prose is protected per `workflows-core:run-flags` §3 step 1: a run-flag token before the prompt begins, or in a trailing run at the very end of `$ARGUMENTS`, is stripped, but one written inside the prompt itself is kept as prompt text, even where it looks like a flag.

**Load the question rules.** Load `escalation-rules core` now, with `Skill(skill: "workflows-core:reference", args: "escalation-rules core")`, before this run asks the user anything: every question it asks follows them — two to four options, presented verbatim with the `(Recommended)` marker where one is recommended, and a selection that carries no text.

**The session-model gate runs next.** It comes after `strip-run-flags`, whose `run_flags.enforced_model` it reads, and straight after the question-rules load, whose rules its question follows; and before `--no-commit` is stripped, the working directory is classified, an address is resolved, the specs-repo preflight runs or any repository is read or written — so a run that stops here has written, stashed and switched nothing. It runs on every run, whatever its class: the class is Phase 1.5's, which the session itself decides, so a gate that waited for it would let a session below Opus classify its way past the review gate. This command's orchestration — the classification, the routing of every dispatch, the review gate and the phase order — runs on the session model, which nothing inside a running command can change (`workflows-core:model-routing/classification` §9.1).
- **`run_flags.enforced_model` set → no gate fires**, as `workflows-core:model-routing/classification` §10's *Opus-session gates do not fire* says: the user has already chosen the model, and `strip-run-flags`' step 7 advisory is the one notice of a session/enforced mismatch.
- **`current_model` — the model this orchestrator runs under — is an Opus or Fable model**, a `claude-opus-*` or `claude-fable-*` id, the test `workflows-core:model-routing/classification` §4's coding-model rule applies → proceed, saying nothing.
- **Otherwise ask at once, before any later step**, the question saying why: "/implement's orchestration — the classification, the routing of every dispatch, the review gate and the phase order — runs on this session's model, `<current_model>`, and a session below Opus has been seen to skip them."
  `choices: ["Stop — relaunch on Opus with `claude --model opus` (Recommended)", "Go on anyway on <current_model> — not recommended, recorded in the report"]`
  **Stop** stops at once, with nothing written and nothing switched, printing the relaunch command, `claude --model opus`, and the command to run in that session, `/dev-workflows:implement` with this run's arguments as typed. **Go on anyway** proceeds, recording `Session-model gate: went on anyway on <current_model>, below Opus — the classification, the routing of every dispatch, the review gate and the phase order ran on it` for the Phase 5 report's `### Assumptions & limitations` (into run-state `assumptions` at Phase 1.4, read from there after it), which Phase 4.6's `body_facts` names under the pull request's *Merge danger*.
  **Where no Opus model is available either** — `opus_available: false`, no §2 Opus row available by §2's own test, which reads the `task` tool's `model` parameter and counts a listed `opus` family for its rows (`workflows-core:model-routing/classification` §2) — there is nothing to relaunch onto, so, per §9.3, the relaunch option is dropped and the array is `choices: ["Proceed on the Sonnet floor — the degradation is recorded in `notes` and the final report (Recommended)", "Cancel"]`. **Cancel** stops as **Stop** does, printing no relaunch command; **Proceed** goes on as **Go on anyway** does, recording `Session-model gate: no Opus model is available — proceeded on <current_model>, the reasoning and review roles on the Sonnet floor` the same way.

**Strip `--no-commit` next**, before any other parsing: it is the only command-specific flag this command takes, and an unstripped flag is read as free-text prose and lands in the task description. When present (into run-state `run_flags.no_commit` at Phase 1.4, read from there after it), Phase 4.6 is skipped entirely and the changes are left in the working tree. It is the one opt-out from a commit that is otherwise prompt-free (`${CLAUDE_PLUGIN_ROOT}/references/code-handoff.md` §1 rule 5) — typed rather than clicked, which is the difference — and a run under it says once what it costs: the work is recoverable only on this machine, and `/document` and `/release-notes` will not find it later.

**The working directory is classified next**, straight after the run flags and the session-model gate — before address resolution and before any `@path` token is read, so a run that stops here has resolved no address, run no specs-repo preflight and shown no Epic picker. Run `git rev-parse --is-inside-work-tree` there. Unless it prints `true`, stop: `/implement` branches the repository it runs from, so it runs only from inside a work tree. It prints `false` inside a `.git` directory or a bare repository; where it fails instead, show git's error beside that, since the error names the cause — no repository around the directory, or one git refuses to use, as its ownership check does. Where it prints `true`, the working directory is the Code repo row's (the table below) whatever it holds, and its repository, at its top level, is the one this run branches and changes. It is not an `@path` token: no other row is tested against it and no notice below is printed for it, so a `prompt.md` or `*-design.md` file in it is read only where a token names it.

`$ARGUMENTS` may contain free-text prose plus **zero or more `@path` tokens** (today's single-`@file` form is a subset). Resolve each `@path` relative to the current working directory. Classify each `@path` **by inspection, not by matching the path string**:

| Detected as | Recognition rule | Handling |
|---|---|---|
| **Spec file** | a single `.md` file | read fully; use as the description/spec |
| **Spec folder** | a directory containing `prompt.md` and/or a `*-design.md` | read all `.md` specs within; fold into the description |
| **Specs folder** | a directory under `specifications/` that `resolve-address` resolves — its `kind:` and `key:` read off the folder's carrier (`workflows-core:addressing` §4) | hand to the folder read in Phase 1.7 |
| **Code repo** | a directory where `git -C <path> rev-parse --is-inside-work-tree` prints `true` (includes the cwd) | scan target in Phase 1.7 — or, where its top level (`git -C <path> rev-parse --show-toplevel`) is that of a code repository already classified here (the working directory's included), a search hint for that repository's scan and for Phase 2A/2B's exploration |

Test the rows top to bottom for each `@path` token: the first that matches classifies it, so a spec or specs folder below a repository's top level is that folder, never a code repo. A token naming the working directory (`@.`, or any other path that resolves to it) is classified the same way, so below the top level a spec folder there is read as one; the repository it lies in is still the run's, by the working-directory rule above. An `@path` that is its own work tree's top level (`git -C <path> rev-parse --is-inside-work-tree` prints `true` and `git -C <path> rev-parse --show-prefix` prints nothing) is always the Code repo row's whatever else it holds. Where such an `@path` also matches the Spec folder row, print `<path> is a repository's top level and is read as a code repository — its prompt.md and *-design.md files are not read into the description; name each by file (@<path>/<file>) to read it`.

**Each token's own checks run as it is classified**, before the no-description stop below and before the specs-repo preflight. A token naming nothing on disk, or one no row matches (a directory that is neither a recognized folder type nor a git repo, or a file that is not a `.md` file), is surfaced by name — never silently skipped — and the run asks whether to continue without it or stop (`workflows-core:model-routing/classification` §8.4); where `git -C <path> rev-parse --is-inside-work-tree` failed rather than printing `false`, show git's error beside it, since a repository git refuses to use (its ownership check) is not one of no kind. A single `@file` that exists but cannot be read stops the run, reporting the error. A spec file or spec folder token under `$SPECS_PATH` is no exception: it is read where it sits, out-of-contract, as the gate below says of a lone spec or design `@path`. **A direct run with no description** — no prose, and no Spec file or Spec folder token left — then stops, still before the preflight: `/implement needs a description — prose; an @<file>.md; an @<folder> that is not a repository's top level, holding prompt.md or a *-design.md; or a <KEY> or @<specs-folder> address`, followed by the notice's remedy where a token above printed it and, where the working directory holds a `prompt.md` or `*-design.md` file that no such notice named, a line naming each by file (`@prompt.md`) — listed, not read. The design-doc open-question guard (Rules, below) runs next, on either mode and still before the preflight: its input is always a token, read where it sits.

**Address resolution.** After the working directory and before the per-`@path` classification above, look for a **single positional
address** in what the run flags left of `$ARGUMENTS` — a `<KEY>` that `workflows-core:addressing` §1's `read-key` reads (a bare key, one behind its folder's kind prefix, or its folder's whole name, carried as the bare key from then on; with `$SPECS_PATH` unset a whole name cannot be looked up, and reads as prose), or an `@<path>` naming a folder in the specs tree. Present →
resolve it, as typed, with `resolve-address` (`Skill(skill: "workflows-core:reference", args: "addressing resolve-address")`, §3) and the run
is **keyed**; absent → the run is **direct** (free-text / `@file`, this command's existing flow).
That is the whole mode test, and it unifies the input grammar with `/document`. **On a `<KEY>`,
`$SPECS_PATH` comes first:** if it is unset, stop naming it before resolving anything
(`choices: ["Set SPECS_PATH (you'll be prompted for the path)", "Cancel"]`, `workflows-core:escalation-rules`
*Required path environment variable unset*) — a key is found only by searching the specs tree, so
with no tree the `absent` stop below would name the wrong cause and offer a re-enter that cannot
succeed. An `@<path>` address needs no specs tree: it is resolved without the variable and runs on,
its record written into the folder it names, and a direct run is unaffected. `ambiguous` and
`misrooted` are §3's two hard stops, the first naming every match and the second, on either address form,
a `$SPECS_PATH` set inside the specs tree. **`status: absent` is a stop, never a fall-through to direct mode**
— the `key dir not found` rule in `workflows-core:escalation-rules` (`["Re-enter key (you'll be prompted)", "Cancel"]`),
naming what creates a folder this command reads: a `PRD-` folder comes from
`/product-workflows:idea <KEY>` or `/product-workflows:create-prd <KEY>` on the idea route and from
`/product-workflows:brd-split` on its parent BRD on the BRD route; an `EPIC-` folder from
`/product-workflows:epics <PRD-ADDRESS>`. A keyed run with no folder has nowhere for Phase 4.7's
record to go.

The classification table above still applies to every other `@path` token: a spec folder contributes
to `specs`, a code repo is an `/implement`-only scan target (or, sharing the top level of one already classified here, a search hint, as the table says). Carry `mode` (`keyed | direct`), the
resolved `path`, `kind` and `key`, and `specs` forward (into run-state `mode`, `key` and `spec_context.spec_paths` at Phase 1.4, read from there after it). On a keyed run `specs` is
read out of the resolved folder only once the specs-repo preflight below has run.

**The specs repository is not a code repository.** Straight after address resolution — once its stops have passed and the mode is set, before any `@path` token is classified and before the specs-repo preflight — test whether the working directory's repository is the specs repository: `$SPECS_PATH` is set and is a directory, `git -C "$SPECS_PATH" rev-parse --show-toplevel` prints the working directory's top level, and `git -C "$SPECS_PATH" rev-parse --show-prefix` prints nothing, so `$SPECS_PATH` is that repository's top level. **On a keyed run, stop**: `IMPLEMENT_IN_SPECS_REPO: <top level> is the specs repository ($SPECS_PATH) — /implement changes code in the repository it runs from, and the code for <ADDRESS> lives in a code repository. Run '/dev-workflows:implement <ADDRESS>' from that repository — an `@<path>` address written as its absolute path.` It is a check of the directory the run starts from, needing no specs-repo state, so the run stops with no preflight (`workflows-core:specs-repo-git` §3). **On a direct run, print one line and run on** — `<top level> is the specs repository ($SPECS_PATH) — this direct run branches and changes it, as it would any repository it runs from, and the session files it writes into the specs tree are committed on its branch: those the code commit takes go out with it if you push it at the push choice, and the rest stay local until you push the branch, since the run's closing specs-repository commit pushes only the default branch and branches carrying the specs commands' prefixes; a run that stops before it cuts its branch commits them on the branch it then stands on, which is the default branch after a fresh start, and that commit pushes them there.`, or under `--no-commit`, which asks no push choice, the same line ending `… and the session files it writes into the specs tree are committed on its branch by the run's closing specs-repository commit, and stay local until you push the branch, since that commit pushes only the default branch and branches carrying the specs commands' prefixes; a run that stops before it cuts its branch commits them on the branch it then stands on, which is the default branch after a fresh start, and that commit pushes them there.` — since a direct run names no unit whose code lives elsewhere. In session-branch mode (`workflows-core:specs-repo-git` §8; its §8.1 `mode` call only reads, so it runs here, ahead of the preflight) either form instead ends `… and the session files it writes into the specs tree go to session/<identity>, as this specs repository's default branch takes no push, never onto this run's branch.` — or, where that call names no identity, `… and the session files it writes into the specs tree stay uncommitted until GIT_USER_INITIALS names a session branch, as this specs repository's default branch takes no push.`, and Phase 1.4's clean-tree check then sees them as it sees any dirty file. A `$SPECS_PATH` below its repository's top level — a specs tree inside a larger repository, which the preflight reports as unsupported (§3.1) — takes neither: that repository holds code too, and the run goes on as it did.

and before the Epic-unit resolution below reads anything, with the run key set fixed from carrier frontmatter alone

§4.1 places the resolved folder at Epic level — an `EPIC-` prefix, or with no prefix a resolved
`kind: epic` — also the key its parent's carrier asserts (§4); on a direct run none, a keyless run.
A stale plugin branch the preflight switches away from would otherwise hide a slice's `brd-link.md`

artifacts from an earlier run, retry an artifact commit that failed to push,
and settle the branch. This runs against `$SPECS_PATH` only — `git -C
"$SPECS_PATH"`, never a `cd`, so the code/docs repo this run is working
in is untouched (§1 rule 1). Prompt-free, and silent unless it acts, a guard fires, or §3.1 reports a misconfigured `$SPECS_PATH`. If a guard fires, emit its §5 notice;

Where its §3.5 B2 found the plugin branch the checkout stood on merged and left it, carry that branch's

**Epic-unit resolution (keyed runs).** `/implement` implements one Epic at a time. When
`mode: keyed`, place the resolved folder as `workflows-core:addressing` §4.1 does — by its prefix,
never by the kind it asserts, which on a BRD-route slice is `brd` — taking its container test first.
**A BRD container** — a `BRD-` folder, or a folder with no prefix holding `coverage-ledger.md` or
`brd/brd-inventory.md` and no `brd-link.md` naming a `parent:` — holds no Epic to implement, because
a BRD's work is authored in its slices; stop, before any artifact is read:
`IMPLEMENT_BRD_NOT_SLICED: <KEY> resolves to a BRD container at <path> — a BRD's Epics belong to its PRD- slices. <the remedy>`
`<the remedy>` lists the slices under it, found by the positive test §4.1 names — `Implement within a slice instead: '/dev-workflows:implement <SLICE-KEY>' — <each slice's key>.` — and, where it finds none:
`It has no slice yet: '/product-workflows:brd-split <KEY> "<how to cut it>"' carves one — the instruction is required there, and that run carves nothing where this BRD's ledger leaves no row unallocated. Where it leaves none, coverage-ledger-format.md §5 names two repairs, the narrow one first: hand-edit the one row to be built back to unallocated in coverage-ledger.md, leaving every other row as it stands; or, to re-take the whole inventory, re-run '/product-workflows:brd-intake <KEY> @<brd-file>', which reopens every row wherever its read finds a requirement and discards every deferred-to, rejected and superseded-by the ledger records.`
It is a user halt. A folder with no prefix — one §5's legacy fallback resolved, or an unprefixed
folder an `@<path>` names, a name beginning with a kind token being prefixed only where it begins
`<KIND>-<the resolved key>-` — is otherwise placed by positive evidence: a resolved `kind: epic`
counts as an `EPIC-` folder below, and a resolved `kind: prd`, or a `brd-link.md` naming a
`parent:`, as a `PRD-` folder. A folder none of these places is not guessed at — stop, naming the
folder and what it carries — and, where it holds an `idea.md` and no `prd.md`, name `/product-workflows:create-prd <KEY>` too, whose `prd.md` places it (`workflows-core:addressing` §4.1). Then:

  Phase 1.7 scan and specs resolution both scope to it.
- **The address named a `PRD-` folder** → `focus_key` is null; enumerate the `EPIC-` folders
  directly under it — a directory listing, which is what the linked-item hierarchy has become — and
  run the progress-aware picker below. **There is no third case.** A top-level `EPIC-` folder with no
  PRD above it used to have a branch of its own here, nested — unreachably — inside this one;

  - **On a multi-component PRD** — `multi-component-test` (`Skill(skill: "workflows-core:reference", args: "components multi-component-test")`, §3) run on the PRD folder returns `multi_component: true` — a flat `specification.md` is a requirements source, not a unit implemented whole save by the 0-Epic override below (`${CLAUDE_PLUGIN_ROOT}/references/workflow-states.md`, *Ready for Implementation*). So every branch below reads as though the PRD folder held no flat `specification.md` — exactly 1 Epic is auto-selected, and ≥2 Epics show the picker without the broad-slice choice — save **0 Epics**, which asks `choices: ["Split into Epics first — /product-workflows:epics <PRD> (Recommended)", "Implement one broad PRD-level slice anyway"]` — the *Split* option only where the PRD folder holds an authored `prd.md`, which `/epics` needs; without one, it becomes what `Skill(skill: "workflows-core:reference", args: "next-phase-offer epics-precondition")`'s *`/epics` precondition* names in its place — `/product-workflows:create-prd <PRD>`, or, on a BRD-route slice, whatever its ledger tests resolve that to — `/product-workflows:create-prd <SLICE>` where both clear, a `/product-workflows:brd-split` where one fails — still marked `(Recommended)` — and only where that rule names nothing is the array `["Implement one broad PRD-level slice anyway", "Cancel"]`; *anyway* is an override, carried as Phase 1's are to the Phase 5 report's `### Assumptions & limitations` and to `body_facts`. On `multi_component: false`, nothing here applies.
  - **PRD with exactly 1 Epic** → no picker; set `focus_key` to that Epic and proceed, with the
    one-line notice `workflows-core:epic-picker` requires of an auto-selection — **unless the PRD
    folder also holds a flat `specification.md`**, a broad PRD-level slice: the shape
    `/dev-workflows:design` designs as one unit and then offers to this command by the PRD's key.
    Auto-selecting the Epic there would never offer that slice, so ask, the Epic's row carrying its
    marker by the done-predicate in the next bullet:
    `choices: ["<marker> <EPIC-KEY> <title>", "Implement one broad PRD-level slice instead"]`
    The first sets `focus_key` to that Epic; the second leaves it null (specs resolve PRD-level). No
    `(Recommended)` marker: a flat specification beside an Epic means two units were specified, and
    which one this run implements is the operator's to say — the silent choice is the one this
    prompt replaces.
  - **PRD with ≥2 Epics** → render the picker per `Skill(skill: "workflows-core:reference", args: "epic-picker")`,
    honouring that file's *The cap*, which counts this command's own option against the four. **The
    broad-slice choice is offered here on the same condition as the one-Epic path's above — only
    where the PRD folder also holds a flat `specification.md`** — because the two paths ask one
    question, which of the specified units this run implements, and without that file the slice is a

    choice and *"Another Epic from the list above (you'll be prompted for its key)"* where the flat `specification.md`

    **at most three** Epic rows plus that same remainder option, which is *The cap*'s own shape for
    a picker appending nothing of its own. **`/implement`'s
    done-predicate is now the artifacts present in each Epic folder**, which is the mechanism
    `/design`'s own Epic picker already uses:
    `specification.md` but no `design.md` → ○; `design.md` present, no record → ◐; a record → ●
    (greyed, not default-selectable; selecting offers "implement anyway") — a record being an

    than a status field is
    strictly better than what it replaces: a declared status is a human's claim about the work and

    **"Implement one broad PRD-level slice instead"** (`focus_key` stays null → specs
    resolve PRD-level) **only where the PRD folder holds a flat `specification.md`**, per the
    condition above. Selecting an Epic sets `focus_key` and proceeds for **that Epic
    only** — there is **no "Next Epic?" loop** (code-writing is heavy and branchy;
    each `/implement` run targets one Epic).
  - **PRD with 0 Epics** → offer: split with `/product-workflows:epics` first, or implement one broad

    unit to confuse the slice with, so this is not a choice between two units but a choice whether
    to partition at all, and withholding the slice would leave one option where the harness needs
    two (`workflows-core:escalation-rules` §0).

When the picker, or the one-Epic path or its choice, sets `focus_key` that was initially null,
**re-resolve `specs`** now that `focus_key` is set. A keyed run's in-scope `specs` are the
`specification.md` and `design.md` present in the unit's own folder — the focus Epic's `EPIC-`

No shared reference defines this set; it is this command's own rule.

**`unit_key` — the key the branch and the commit carry** (into run-state `unit_key`, `workitem_key` and `unit_folder` at Phase 1.4, read from there after it). It is the key of the unit this run
implements, whose folder Phase 4.7's record goes in: `focus_key` wherever it is set, however it was
set, and the resolved folder's `key` on a broad PRD-level slice; `null` in direct mode. Its

## Phase 1.4 — Settle the working tree and the branch

**This phase opens by creating the run-state file**, `$(git rev-parse --git-path dev-workflows/implement-run.json)` — a file inside this repository's git directory, one per worktree and never staged, which holds every fact a later phase, a stop or the Phase 5 report reads, from here to the run's end, so that a compaction of the session loses none of it. One `/implement` run per worktree at a time is its precondition, as it is the working tree's: two runs in one working tree already collide on its files. It lies outside the working tree, so, like this run's temp files, it is no file the rules on writing only after the branch and the baseline speak of (Pre-Phase 3, Pre-Phase 3.5, the invariants), and neither a stop that says nothing was written nor a step said never to write into the code repository counts it. Every call on it is `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/run-state.py" <subcommand>`, written `run-state.py <subcommand>` below, run from the working directory, which no step of this run leaves; the script is this plugin's own, and each call runs inside one Bash call — its own, or the one a write is chained into (*A write never takes a turn of its own*, below). A command that needs another directory takes it as `git -C <dir>`, `npm --prefix <dir>` (or the tool's own equivalent) or an absolute path, or changes directory only inside a `( … )` subshell, its parentheses included — `(builtin cd <dir> && …)`: neither `cd` nor `builtin cd` is ever used outside one, since either moves the directory of every later call.

First write the full task description — the primary description with every change Phase 1's read-back joined to it, or, on a companion run, the tasks it answers — to a temp file (`command mktemp -t dw-impl-task-XXXXXX`, never inside a repo tree). Then create the file, handing `init` on stdin, as JSON, the facts the run holds by now and nothing else: `mode`, `key`, `source`, `focus_key`, `unit_key`, `workitem_key` and `unit_folder`; `run_flags`; `specs_git`, where the preflight set one; `specs_merged_branch`, where its B2 found one; `spec_context`'s `spec_paths`, `applicable_ard`, `ard_paths`, `companion_run` and `tasks_only`, each where Phase 0 or Phase 1 resolved it; `branch`; `files.task_description_file`; `patches`; `assumptions`; and `report`'s `phase1_tasks` and `notices` — each as *What it holds* below says. Every other key takes its default, which `run-state.py` defines beside the key, so the object leaves out each key the run holds no fact for:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/run-state.py" init <<'RUN_STATE'
<those facts, as one JSON object>
RUN_STATE
```

Before its first write, `init` moves aside any file an earlier run left there, unread — it is not this run's state — as `implement-run.json.stale-<UTC compact stamp>`, removing an older such file first, so at most one is kept; it prints the name and appends `Run-state file an earlier run left, moved aside unread: <that path>` to `assumptions`, which names it once. Where `init` exits `2` or `3` — a slip in the object, which its error names — correct the object as the error says and call it once more: it checks the object before it moves anything aside, so that call meets the tree the first one did. Where it exits `4`, or fails a second time, show its error and stop: nothing is stashed or switched yet, and there is no file to read; remove the task description's temp file, and each patch temp file Phase 1 wrote (*A task that names a patch*).

**What it holds** — one JSON object, each key holding what `init` gave it — for a key the object above carries, the fact the run handed it, and for every other, its default — until one of the calls below changes it:

The file holds exactly these keys, which `run-state.py`'s `KEYS` defines, and no other: `format phase mode key source focus_key unit_key workitem_key unit_folder run_flags specs_git specs_merged_branch spec_context{spec_paths in_scope_ids applicable_spec applicable_ard ard_paths companion_run tasks_only} task_shape clarifications{settled answers} routing{block history} class coding_model branch_answer{answer moves lines} branch stash_ref pre_existing_dirty session_branch_lift test_decision clean_finish files{task_description_file plan_file pending_plan_file summary_file baseline_file review_diff_file partial_diff_file review_file claims_file failure_file} pieces writer_units writers test_runs reviews patches triage conformance{summary annotated gaps handoff_line} other_repo_changes assumptions deferred report{commands_run maintenance notices phase1_tasks confirmed_cause} code_repo_outcome replans_used` — braces naming the members a call may write into. `KEYS` gives each key and member its default, and its type with it: `init` gives the default to every key or member the object leaves out, and refuses, before it moves anything aside, an object holding a key or member the list lacks, or one of the wrong type; its selftest holds this list equal to the script's. `set` holds every value it is given to the same list and types (*The calls*, below).

**Write each key the moment the run learns it, through the file**, never holding it to write later: wherever this command records a value a key holds, that record is the key's write. **A write never takes a turn of its own**, save a phase's `open`, whose printed file the phase then acts on. Every other write goes in the same message as the run's next tool call — chained before it in the one Bash command (`python3 "${CLAUDE_PLUGIN_ROOT}/scripts/run-state.py" set … && <the next command>`) where that call is Bash, and sent first in the message where it is another tool — and keys the run learns together go in one `set`. So no turn of the model's falls between learning a key and acting on it, and a compaction cannot land between them. A site that writes one says so — `(writes run-state <key>)` — and makes the write with `set`, several keys in one call, or `append`; a site that reads one after its phase's opening says `(reads run-state <key>)`, and reads it with `read`. A dispatch's brief that names a value so is handed the value itself — a path as the path, never the key, a placeholder or a command that would print it: a brief is text, and nothing expands one in it. **Each path a brief names is copied from what a command printed in the call just before the dispatch, never retyped.** A path the run-state file holds is printed by a `run-state.py read` of its key (a list entry by its index, as `spec_context.spec_paths.0`), the read apart from its decode, so that a failed read ends the call with the read's own exit code: `j=$(python3 "${CLAUDE_PLUGIN_ROOT}/scripts/run-state.py" read <key>) && p=$(printf '%s' "$j" | python3 -c 'import json, sys; print(json.load(sys.stdin))') && printf '%s\n' "$p"`, one `&&` link per path. Any other path is printed in that same call by the command that yields it — the top level a `Project root:`, `repo_root:` or `Constraints:` line names by `git rev-parse --show-toplevel`, a repository a Phase 1.7 `code-scanner` brief names by `git -C <path> rev-parse --show-toplevel`, and the `Security register:` path as `"$SPECS_PATH/security/<repo-slug>/register.json"`, `<repo-slug>` printed there by `workflows-core:components` §1's derivation. **That call tests with `test -e "$p"` each path a brief hands an agent to read** — each `files` key's, each report a `writers` entry lists, each `spec_context.spec_paths` and `spec_context.ard_paths` entry, a patch's absolute `path` while the run has not removed it, and the `Security register:` path, last and in a link whose own failure cannot end the call — `{ test -e "$r" && printf '%s\n' "$r" || printf 'absent\n'; }`, `r` holding that path, the whole alternative inside the braces so that an earlier link's failure still skips it and fails the call — since a repository with no register is the usual case: an `absent` register leaves the brief's `Security register:` line out, as that line's *where that file exists* says (Phase 1, *A security finding named outside its task*), and the agent, handed none, names another finding with no status, as its own rule says. A path a brief carries as data — a patch's `patch`, relative to `$SPECS_PATH`, and its `files`, and each `pre_existing_dirty` path, the re-plan brief's `Work so far:` line included — is copied from the read and never tested, since it can be relative or name a deletion. Any other tested path is printed before it is tested, in its own link (`j=$(… read <key>) && p=$(printf '%s' "$j" | …) && printf '%s\n' "$p" && { test -e "$p" || (exit 6); }`), and one that does not exist fails the call — it exits `6`, the last path it printed being the missing one, and prints no `absent` — and is read again, never sent, and one still missing then stops the run, naming its key and the path — through Phase 4.6 once Pre-Phase 3 has cut the branch or this phase continued on the unit's own (its `"Every run"` list), and otherwise as *Every stop from here to Phase 4.6* says, below: a brief is never sent without it. A `6` means a tested path is missing and nothing else: no `run-state.py` call exits with it, where a bare `test -e` exits `1`, which *What a failed call's exit code says*, below, reads as no file.

The calls:

- `run-state.py open "<phase>"` — sets `phase` and prints the file: every phase's opening.
- `run-state.py read [<key>]` — prints the file, or one key, changing nothing.
- `run-state.py set <key> '<json>' [<key> '<json>' …]` — sets each key to the value after it, several in one replace, the key written again before each value; with no pairs it reads a JSON object of key: value on stdin, through a quoted heredoc (`<<'RUN_STATE'`), which needs no shell quoting. It removes each temp file the write stops naming (`files`, above).
- `run-state.py append <key> '<json>' [<key> '<json>' …]` — the same two forms, adding each value to its key's list, the key written again before each value — `append assumptions '"a"' assumptions '"b"'` adds two lines, where `append assumptions '"a"' '"b"'` is refused; a key that is `null` becomes a one-element list.
- `run-state.py remove [--keep <path>]` — the end-of-run removal, below.

A key is a top-level name or a dotted path into one (`files.plan_file`), a list entry named by its index (`triage.-1.followed_by`, the last entry's). `set`, `append` and `read` refuse a key the file does not hold, so a misspelt key is never written as a new one; `set` also refuses a path through a `null` value: write that key whole. `set` holds each value to `KEYS` as `init` does: a key or member the list lacks, or a top-level key or an object key's `<key>.<member>` given a value of another type than its default fixes — a boolean never standing for an integer — exits `3`, every such slip in the call named at once and nothing written; and a top-level key whose default is an object, given an object, takes its members over the ones the file holds, so a member the object leaves out keeps its value — `set files '{"baseline_file": "<path>"}'` changes `baseline_file` alone. A deeper path or a list entry (`writers.0.status`, `triage.-1.followed_by`) is not checked. A `set` or `append` with a value written where a key belongs — an argument there opening with `"`, `[` or `{` — or with an odd count of arguments exits `2`, naming the pairs form. Each write holds a lock for its read-modify-write and replaces the file whole, so it is never half done and two calls lose nothing between them; a call that fails changes nothing. Input is read as UTF-8 whatever the locale, and the file is UTF-8, non-ASCII written as itself, so a `pre_existing_dirty` path comes back as its `-z` record gave it; JSON escapes `"`, `\` and control characters — `\t`, `\n`, `\r` and the like — in what `open` and `read` print, and each escape reads back as one character.

**Every phase from Phase 1.5 to Phase 7 opens with `run-state.py open`** — the phase heading is the trigger, so the run never has to judge whether its context was compacted — and acts on the keys it prints, never on what the run remembers. What a failed call's exit code says, and what the run does:

- `1`, no file, or `5`, a file that does not parse: say so beside the phase's first output, and write the file again with `run-state.py init --recover`, its object every fact the run still holds — every other key taking its default, as at Phase 1.4; `--recover` appends to `assumptions` that this run's own file was written again, never as one an earlier run left, naming the file it moved aside, or that there was none to move.
- `2`, a bad call — its arguments, a value where a key belongs among them, a value that does not parse, input that is not UTF-8, a path through `null` — or `3`, a key the file does not hold, or, from `init` or `set`, a key or member `KEYS` lacks or one of the wrong type, which its error names — a slip, corrected and retried once, as at Phase 1.4: nothing was written. Correct the call and make it again; where an `init` fails a second time, stop as `4` below does. A `3` from `set`, `append` or `read` saying the file holds no key the schema names is a defect of this command, so say so; one naming a wrong type is a slip like any other.
- `4`, the file could not be reached — an `OSError` reading or writing it, an unreadable directory on its path included, or git failing to name it: stop, naming the error and — since the file cannot be read — `stash_ref` and the branch from what the run holds. Once the run has edited the working tree — a patch applied or a writer dispatched — this stop is in Phase 4.6's *"Every run"* list as the one stop there that runs no part of that phase, for the reason it gives, so the work stays uncommitted: name beside the error every path `git status --porcelain -z --untracked-files=all` lists, this run's and the user's own alike, which without the file the run cannot tell apart. Its end-of-run removal is made as every stop's is; where that call exits `4` too, it removes nothing, and the stop says this run's `dw-impl-` temp files stay.

**The end-of-run removal is `run-state.py remove`, once**: as the run's last action before Phase 7's terminal `commit-artifacts`, and in every stop from here on once the stop's message is out — never at Phase 4.6, after which Phases 4.7 to 7 still read the file. It removes every temp file `files` names, each `writers` report, each `reviews` diff and return file and each `patches` path marked `temp` — only a regular file whose name begins `dw-impl-`, as every `mktemp -t` template of this run's does — save a path passed as `--keep`, as a stop passes a file it named as unreadable, which stays for the operator to look at; then the file itself, only at its git path. A `.stale-` file stays until a later `init` replaces it, and the zero-byte `.implement-run.lock` beside the file stays too; a call other than `init` that finds no file creates no directory and no lock.

## Phase 3.5 — Test run (each writer unit's, at stage `unit`; once more at stage `post-review`, after the review's edits)

**Read the run-state file first.** Its keys are the run's state, never memory: open this phase with `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/run-state.py" open "Phase 3.5"`, which sets `phase` and prints the file, and write through to it every key this phase learns (Phase 1.4).

Runs at stage `unit` for each writer unit once its test writer has returned (Phase 3 step 4), and at stage `post-review` once, after Phase 3.6's review where an edit followed the units' test runs (Phase 3.6 step 5), the same steps at both. This orchestrator runs its checks and edits nothing: every fix is a writer's — the failing file's owner, reached again with `SendMessage` in `mode: fix` (step 6). A test run ends **green** — every check passing, or failing only with pre-existing lint failures, and the verify report passing with no new failure — or **settled** by the user's answer at step 5 or step 6.

**Every build or test command this phase runs goes through the run lock**, from inside the code repository, as `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/run-lock.py" -- <command> [args…]` — a lint, a build, a check a writer left to the caller, the red-capability check and the repro's re-run — so none of them shares the working tree with a writer's run or `test-baseliner`'s. The lock runs its command directly, never through a shell: a command that opens with an environment assignment (`CI=true …`) runs as `env CI=true …` after the `--`, and one that needs `&&`, a pipe or a redirection as `sh -c '<command>'`. One run from a directory below the top level runs in a subshell, so the session's own directory never moves: `(builtin cd "<top level>/<dir>" >/dev/null && python3 "${CLAUDE_PLUGIN_ROOT}/scripts/run-lock.py" -- <command> [args…])`. A run in a scratch checkout of `HEAD` goes through the lock whole, from the top level — `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/run-lock.py" -- bash -c '<the recipe>'`, each single quote inside the recipe written `'\''` — since it links the working tree's dependency directory and so shares its state. **Read each run's stderr for a `run-lock:` line before its exit code**: every exit the lock script makes itself prints one — the lock not taken, the command not found or not runnable, a signal passed on — and its exit codes overlap a build's or a test runner's own. `run-lock: waiting for …` says only that it waited, and `run-lock: fcntl is not available here; running the command unlocked` that the command ran unlocked; any other `run-lock:` line means the script ended the run itself, and what that says turns on which line it is:
- **`run-lock: command not found: …` (exit 127) or `run-lock: cannot run …` (exit 126)** — the tool the check names is missing or cannot run: that check's own failure, which step 3 reads as it reads any failing check, through its pre-existing comparison or the fix rounds — save step 2's own checks, where a red-capability check or a repro's re-run that cannot find or run its tool is inconclusive, recorded with that line as step 2 records an inconclusive check (writes run-state `assumptions`).
- **`run-lock: usage: …` (exit 2)** — a slip in this orchestrator's call: correct it and run the check again, once; where that line comes back, treat it as the next bullet treats a check the lock ended twice.
- **Any other — the lock not taken (exit 4) or a signal (exit 128 + N)** — says nothing about the change: record the run with that line (writes run-state `report.commands_run`) and make it once more. Where the lock ends it again, that check was not made, and no fix round takes it: a red-capability check or a repro's re-run is then inconclusive, recorded with that line as step 2 records an inconclusive check (writes run-state `assumptions`); for any other check, say so, with that line, and ask `choices: ["Investigate further", "Accept an unverified run and proceed (document in Phase 5 report)", "Cancel"]`. **Investigate further** → investigate with the user, reading and never editing, and run that check again when ready. **Accept** → record in the Phase 5 `### Deferred items` section that check alone as not run, with its `run-lock:` line, set `clean_finish: false` for Phase 4.6 (writes run-state `deferred`, `clean_finish`), and go on with the test run's remaining checks and its verify; that check is not run again in this test run, a later round's re-run of step 3 included, and the test run ends `accepted` (step 1). **Cancel** → stop and summarize.

## Phase 3.6 — Review (MODERATE, SIGNIFICANT and HIGH-RISK)

**Read the run-state file first.** Its keys are the run's state, never memory: open this phase with `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/run-state.py" open "Phase 3.6"`, which sets `phase` and prints the file, and write through to it every key this phase learns (Phase 1.4).

Runs where Phase 3 step 4 sends the run, once every writer unit's test run is green or settled, at MODERATE, SIGNIFICANT and HIGH-RISK — never at SIMPLE, which goes from Phase 3.5 to Phase 3 step 8 and Phase 4. This command reviews MODERATE work with the Opus `code-review` gate SIGNIFICANT work passes (`workflows-core:model-routing/classification` §3.1), dispatching no `risk-planner` at MODERATE. The code was written by `code-writer` and `test-writer` on `implementation_model` (`workflows-core:model-routing/classification` §4) and is reviewed by `code-review` on Opus — one review per piece of the design, then, on a run of two or more pieces, one overall review — each fix a review leads to made by the writer owning the file it lands in, reached again in `mode: review` (`fixes_model`, its `implementation_model`) — unless §10 enforces a model, in which case every dispatched step, the coding and the review included, runs on `run_flags.enforced_model`. 'Opus review' throughout this command names this review gate, whatever model it runs on. **No review is told a test result** — no brief carries a test, build or lint outcome, a writer's checks or a verify report — so a green run softens none. An edit the review leads to is followed by the test run again, Phase 3.5's `post-review` stage (step 5). A **review round** is the reviews dispatched together: the first round, the one re-review round step 3 allows, and step 5's review of the post-review delta.

1. **Strip the probes and capture the review diffs.** When `task_shape: bug` (reads run-state `task_shape`), first **strip every `[DEBUG-xxxx]` probe** that reached the working tree (per `${CLAUDE_PLUGIN_ROOT}/references/bug-diagnosis.md`, under which `code-writer` places and reads them in the scratch checkout on every dispatch, its first included); no review diff may contain debug instrumentation. **The change's files** are every tracked path the working tree changed against `HEAD` — `git -c diff.relative=false diff --no-ext-diff --no-renames --name-only -z "$(git rev-parse -q --verify HEAD || git hash-object -t tree /dev/null)"` — and every untracked path a writer reported: under a code writer's `### Files changed`, a test writer's **Files touched** or a Fix Report's `### Files changed`, or in an applied patch's `files` (reads run-state `writers`, `patches`). An untracked path `git ls-files --others --exclude-standard -z` lists that none of those names — a build or code-generation output no writer reported — enters no diff; save one `pre_existing_dirty` names, it is named in `### Assumptions & limitations`, each once, as in no review, which Phase 4.6 commits unreviewed (writes run-state `assumptions`). Where the change's files are none, nothing changed to review: record it (writes run-state `triage`, appending `{"pass": "first round", "verdict": "nothing reviewed — no file changed", "rulings": [], "settled": null, "offered": null, "followed_by": null}`) and go on to step 4. Each round writes a diff only for a review it dispatches (step 2), with the diff-so-far command (Phase 3, *The diff so far*), ` -- ` and each of its paths as `':(top,literal)<path>'` (a `'` inside written `'\''`) added after its last argument, so a file created or deleted is in it, each to a fresh temp file (`command mktemp -t dw-impl-diff-XXXXXX`, never inside a repo tree):
   - **the whole diff**, over every path of the change's files, recorded as `review_diff_file` (writes run-state `files.review_diff_file`, a `set` that removes the one it replaces unless a `reviews` entry names it, Phase 1.4): the one review's diff on a run whose one piece is `all` (reads run-state `pieces`), and the overall review's on any other;
   - on a run of two or more pieces, **each piece's diff**, over **its piece paths**, which each round computes for every piece, dispatched or not: each path of the change's files its `files` hold — named outright or matched by a glob resolved from the top level, a path a piece names outright deciding over another piece's glob — each test file a test writer's `### Tests added` entry marks `— piece <its name>`, and each one the reports of the test writer of a unit whose only piece is this one name under `### Tests added` or `### Tests updated`; and each path no piece's `files` hold that a plan Step of this piece names (its `Piece:` line; reads run-state `files.plan_file`).
