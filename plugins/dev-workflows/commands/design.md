Author an engineering design for the resolved item: $ARGUMENTS

**Core references.** A citation of the form `workflows-core:<name>` names a shared reference in the `workflows-core` plugin. Load it with `Skill(skill: "workflows-core:reference", args: "<name>")` — never by path: `${CLAUDE_PLUGIN_ROOT}` resolves to this plugin, which does not carry it.

These shared references load by part — `escalation-rules`, `finding-triage`, `next-phase-offer` and `session-hygiene`. A citation of one names a rule: before applying it, load the part that holds it, `Skill(skill: "workflows-core:reference", args: "<name> <part>")`, the part its rule index names, unless that part is already in this conversation word for word; never guess a part's name — until you hold the index (every part carries it), load it with `args: "<name> index"`. A citation that names no rule the index holds loads the whole reference, `args: "<name>"`. Never apply a rule of these references from memory.

`/design` is the **Dev-phase engineering-design** workflow — the design step of the PM→PA→PE→Dev pipeline
(`/specify` → `specification.md`; then `/design` → `design.md`). The developer *takes over* a merged
`specification.md`, grounds in the **fully-mounted** implementation code, and authors a reviewed
engineering `design.md` through a relentless one-question-at-a-time grill that **challenges** the spec
and **designs** the implementation. It gates on the Opus `design-reviewer` and offers to land
`design.md` + the spec's engineering-review edits on the specs repo's main branch (via branch + PR) so
`/implement` can plan and build from it.

Key distinction from `/specify`: `/specify` (PE) *authors* the requirements spec and grounds lightly
(soft repo gate); `/design` (Dev) *challenges* that spec and *designs* the implementation, and must see
**all** implementation repos — its repo gate is **strict** (hard-stop on any unmounted repo).

Flags: `--design-twice` forces the Phase 5 interface fan-out on the run's load-bearing interface, even when no contested-interface signal fired (`references/design-format.md` `## Seams`); `--no-arch` turns off, for the run, all three sources architecture grounding reads — the architecture repository, the team decision records and the security registers — see Phase 1.

Usage: `/design <ADDRESS> [--design-twice] [--no-arch] [--skip-costs] [--skip-feedback] [--enforce-model=<model>]`

**Ending early.** Every stop in this run takes `workflows-core:specs-repo-git` §4's refusal tail: Phase 9's session cost (unless `--skip-costs`) and its terminal `commit-artifacts`, which prints the run's `Specs repo:` line after the stop message — with no Phase 8 maintenance or feedback, no `resume.md` and no Final report — save that, where this run created or resumed `_design-session.md`, Phase 8's opening run-environment comparison (`workflows-core:session-hygiene` §6 point 3) runs first, as that phase says, and a *Stop* there makes the tail's cost entry report-only and skips its commit. That is every named `DESIGN_*` stop (`DESIGN_BRD_NOT_SLICED`, `DESIGN_NO_SPEC`, which is step 3's row F turned into a stop, `DESIGN_LINEAGE_FAILED`, `DESIGN_UPSTREAM_STALE`); Phase 0's stop on a folder it cannot place, and step 4's stops on a PRD with nothing to design; every stop a shared reference's return leads the run to — `branch-check`'s, `require-on-main`'s stopping states, step 3's `ambiguous` or `misrooted` PRD dir, Phase 2.5's `unmerged` ARD and the lineage check's *Stop*; every *Cancel* that ends the run, an escalation rule's at Phase 3 or 4 included, and Phase 6's *Cancel the whole run*; and every other answer or refusal that ends it — Phase 0 step 4's *Split*, Phase 1.5's relaunch on Opus, Phase 3's re-split or add-the-component-first option, the strict gate's *I've remounted — re-scan* wherever Phase 3, 4 or 5 reaches that gate, and Phase 7's refusal of a `design.md` holding an unresolved `- [ ]`. A stop before the specs-repo preflight — on the address (none given, `invalid`, `ambiguous`, `misrooted`, `absent`) or on a run flag — takes the same tail, skipping only the preflight (`workflows-core:addressing` §3, that reference's §3). `emit-block` still fires at a plugin-gap halt, before it escalates, as Phase 8's capture-at-block invariant says. A run-environment *Stop* — at Phase 1's comparison on a resume (`workflows-core:session-hygiene` §6 point 1) or at Phase 7's (point 2) — keeps its own route, on through Phases 8–9 under `specs_git: misrooted`, as §6 says. Phase 7's handoff *Cancel* is not a stop: on the handoff's consent choice it declines the handoff, the files stay written, and the run goes on through Phases 8–9 — as it does after *Stop here* at the Next-Epic offer, which ends only the loop. A stop on an Epic the *Next Epic* loop took — its `branch-check` among them — comes after each earlier Epic's handoff offer, and no Final report follows to carry their lines, so the stop message is followed by each earlier Epic's labelled `Phase handoff (<EPIC>):` line (Phase 7), before the `Specs repo:` line.

**Every stop taken once Phase 0 has settled the run folder** — `open-run` done and its question answered (*Open the run folder*) — runs `run-stop-line` (`Skill(skill: "workflows-core:reference", args: "run-folder run-stop-line")`) right after its own message and the earlier Epics' lines, `<command>` there being `/dev-workflows:design <the address as typed>`. None is one a resume meets again on the run's own state alone. A run-environment *Stop* is one of them, though it goes on through Phases 8–9, unguarded, so a run resumed from the recorded environment goes on with what it saved. A stop's tail is never guarded, and `close-run` runs on a finished run alone (Phase 9); `DESIGN_RUN_TAKEN_OVER` takes no tail (*Open the run folder*).

Read `effect <folder> design-<u> state`:

**Saved dispatches.** A dispatch a phase below marks *saved* goes through `run-dispatch` (`Skill(skill: "workflows-core:reference", args: "run-folder run-dispatch")`), area `main`, which says when its saved result is reused instead of dispatched:

## Phase 5 — Grill: challenge + design

**Interview technique (grilling — embedded; no runtime dependency).** Conduct the design as a **relentless** interview per `Skill(skill: "workflows-core:reference", args: "grilling-technique")` — one question at a time, recommend each answer where one exists, explore the Phase 4 code scan / spec to self-answer (fact-vs-decision), ask from the frontier, and clear the confirmation gate before writing — before each section where the run writes `design.md` section by section, or once over the whole design where it writes it after the grill, as below.

**A premise about the existing system is read before a question states it.** A question, an option or the rationale for a recommendation that states how the system already behaves — a precedent (*as X does*, *like every service*), what a script, a build or a job produces, a count, how an existing endpoint answers, what a deploy step changes in the running processes, what a running job does to data — states a fact, and finding it is this run's job, not the user's: read it in the repository that holds it, at the commit id Phase 4 recorded for that repository, never its mark (the working tree where HEAD still stands at that commit and, on a read-only mount or after a read by ref, the tree is clean; else `git -C "<path>" show <commit>:<file>` to read and `git -C "<path>" grep -n <pattern> <commit>` to search), and across every instance it generalises over, since a citation proves the line it names, never the class. Where the read falsifies the premise, rewrite the option or drop it. At a gate's play-back such a statement is played back with the `file:line` it was read at, or marked *unverified* with what would settle it — never left as an inference for the user to confirm (`workflows-core:grilling-technique`). `design.md` cites each one a decision, a step or a `validated` note rests on (`${CLAUDE_PLUGIN_ROOT}/references/design-format.md` § Principle).

**The grill settles the decisions; the run then writes `design.md` behind the confirmation gates** — a gate before each section where it writes section by section, or the whole-design play-back below where it writes the design once after the grill — against `${CLAUDE_PLUGIN_ROOT}/references/design-format.md`, applying the no-hard-wrap prose convention in `Skill(skill: "workflows-core:reference", args: "prose-formatting")`, sections scaled by the Phase 1.5 classification. A change or addition the writing makes to anything a gate confirmed — a decision, a test, a criterion, a number — goes to the whole-artifact gate (`workflows-core:grilling-technique`, *The confirmation gate*) before Phase 5.5, its play-back naming each one, never to narration alone. A sentence the writing adds that states a fact about the existing system — a premise, a provenance line, what changed between two scanned commits — is such an addition. A confirmed fix applied to every occurrence its own wording reaches is not a change; where the play-back miscounted the occurrences, the session file corrects the count.

Run **two intertwined tracks**:

- **Challenge the spec.** Interrogate testability, seams, scope realism, missing cases, and feasibility
  against the real code. Record every substantive challenge **into `specification.md`**: add/extend an
  `## Engineering review` section and new `- [ ]` open questions on the spec. Raise substantive changes
  to ACs/TCs as **proposals** — do not unilaterally rewrite them; when the spec is `Published: yes`,
  **annotate only, never mutate `[Uxx]` / `[ACxx]` / `[TCxx]` IDs** (those route through the specs
  repo's human change-management). **A spec open question the design answers stays open where the
  answer is a product decision:** tick it, with the answer recorded under it, only where the answer
  changes no requirement text; an answer that adds or changes a criterion, a scope line, a target or
  a limit is written under the question as the design's proposal, the `- [ ]` stays for the
  specification's owner, the design proceeds on its proposal, and the coverage row of the
  requirement it bears on, where it bears on one, reads `proposed-change` (`${CLAUDE_PLUGIN_ROOT}/references/design-format.md` § Engineering-review
  edits to the specification). That is not a residual engineering unknown pushed onto the spec, which
  the design cannot settle and waits on (*Resolve `design.md` open questions to zero*, after these
  tracks): here the design has an answer, and only its adoption is the owner's.
- **Design the implementation.** Author each `design.md` section: Context & problem, Requirements
  coverage (with the challenge notes cross-referencing the spec's `## Engineering review`), Architecture
  & components, Interfaces / contracts, Seams, Data flow, Error handling & edge cases, Test strategy,

Where the design must change files outside the target's paths that no ride-along covers and that are not its repository's shared ground (`workflows-core:components` §2) — another module of the same repository — record each under `## Risks & mitigations` as `- Target span: <component> — <why>`, the line Phase 3's *Add anyway* writes for a repository, which `design-reviewer` flags rather than blocks. What it does to the running pods and their data — which workloads it restarts or recreates, the image each then pulls and what builds and publishes it, and what a restart or the rollout wipes, re-seeds or rewrites — is fact: read it from Phase 4's deploy-surface themes and play it back as the question's premises, each cited at the `file:line` it was read at or marked *unverified*, as a premise is above. **The rollout's reach is every workload a tag the release moves reaches, not the changed workload's alone**: each workload in the deploy manifests that pulls an image the release builds, publishes or retags is a premise of its own, with the tag it pulls and its pull policy, or that it sets none, each at its `file:line` — a live run's release also republished two database images' `:latest`, which the database workloads pulled with no pull policy, so a later restart of a database pod could start a new upstream major version on its volume, and only the review found it.
