# Changelog

All notable changes to the **security-workflows** plugin are recorded here.
Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
Versions follow semver at the plugin level.

## [0.1.0] — 2026-10-16

Install it with `claude plugin install security-workflows@shipwright`. Needs `workflows-core` 1.42.0, which carries the register format, `unit-branch` and the `/scan` cost row this plugin loads. The plugin hands its fixes to `dev-workflows` 4.28.0's `/implement`, which continues on the Epic's branch.

### Added — the family's security audit, built on Claude Security

- **`/security-workflows:scan <KEY | repo-path> [--import <dir> | --triage | --verify-fixes] [--effort medium|high]`**, one typed-only command that records Claude Security's scans in the specs repository. It never scans by itself: Claude Security's own skill reads the code, puts each finding to its verification panel and writes the report, and the command records, triages and routes what that skill reports. It never runs anything against a deployed system and never writes exploit code.
- **Its modes.** A key alone is a **change scan** of the Epic's branch before its pull request merges — the branch `workflows-core:implementation-format` §5's `unit-branch` finds, scanned in place over the block's base, at `high` effort by default; it is the only mode that runs `unit-branch`, and a checkout standing on another branch is switched only on the user's answer. A repository path is a **codebase scan** of the whole repository, at `medium`. `--verify-fixes` scans the changed files of the findings being fixed, in a temporary worktree at the default branch's head, removed on every path. `--triage` scans nothing and puts the open findings, the accepted risks past their review-by date and the decisions awaiting security review to a person. `--import <dir>` records a Claude Security report a run did not record. The command never asks for a `low`-effort scan, which keeps no coverage account and so could never close a fix.
- **Two roles, and a Dev is never blocked.** A key run without `--triage` or `--verify-fixes` is the Dev's (`dev`); every other run is the Security Engineer's (`sec`). The findings are triaged in one batch — fix, decide later, a false positive with the `file:line` of the guard that defeats it, or an accepted risk with an owner and a review-by date — and a possibly-same match is always asked. A Dev's false positive or accepted risk takes effect at once, recorded *awaiting security review*; a `sec` run confirms or overrules it, and nothing the Dev does waits on that review.
- **Fixes go to `/dev-workflows:implement`.** A `fix` decision becomes a follow-up line on a key run, or an `/implement` prompt line on a path, built from structured fields only — the `[SEC#n]`, a CWE, a plain `path:line` and the patch path — never from a finding's text, which is scan output and is quoted under its own heading wherever it is shown. Where the scan ran in the session's own repository over a clean stamp at its HEAD, the run asks Claude Security to suggest patches and copies them into the register; it never applies one. Follow-ups are previewed and written after the report, and a line the preview cancels returns its finding to `fix` with a second, small run record.
- **Closure on evidence only.** A change scan never closes a finding. A covering codebase scan, later than a finding's last sighting and over a changed file, closes a `fixing` finding by itself; one the scan reaches only through a squash merge, which names the unit and not the fix, is proposed fixed and closes on a person's confirmation, as an `open`, `fix`, `reopened` or `accepted-risk` one does.
- **The session model is the scan's model.** Claude Security's agents inherit it. On Opus nothing is asked; on Sonnet or below the run asks before scanning, recommending a re-run after `/model opus`; on Fable nothing is asked, and the confirmation says Fable's filters re-run some of the scan's requests on Opus. `--enforce-model` reaches only the run's own maintenance agents, and under it the Sonnet question does not fire. One confirmation precedes every scan and states that it may take a while and use a significant number of tokens.
- **Twelve stops, all `SECURITY_*`:** `SECURITY_USAGE`, `SECURITY_SPECS_MISROOTED`, `SECURITY_NO_IMPLEMENTATION`, `SECURITY_PREREQ_PYTHON` (a `python3` older than 3.9), `SECURITY_PREREQ_WORKFLOWS` (no `Workflow` tool: turn on *Dynamic workflows* in `/config`), `SECURITY_TREE_DIRTY`, `SECURITY_EPIC_MERGED`, `SECURITY_BRANCH_MISSING`, `SECURITY_NOTHING_TO_VERIFY`, `SECURITY_NOTHING_TO_TRIAGE`, `SECURITY_ALL_SKIPPED` and `SECURITY_NO_REPORT`. A stop writes no run record, unit note or follow-up.
- **A report that may still hold a credential is not copied without asking.** Where Claude Security says the report's files may still hold a credential value, the run asks before copying anything into the specs repository: *Stop to clean the files, then record them with --import (Recommended)*, which names the files to check and the command that records them once clean, or *Record as they are*, after which the report says they were recorded unchecked. On `--import`, which cannot see whether Claude Security reported a redaction failure, the run says instead that the redaction is best effort.
- **The register is bookkeeping, and nothing waits.** `$SPECS_PATH/security/<repo-slug>/` and the unit's `_security.md` note are committed and pushed by `commit-artifacts` with the run's session files, never handed off by pull request, and no run stops because another run's register changes are unmerged. The run records that other `session/*` branches hold are reserved before numbering, and a temporary worktree a crashed run left is offered for removal once nothing under it has changed for six hours.
- **`scripts/register.py`, the register's one writer** — `plan`, `ids`, `commit`, `rebuild`, `verify-scope` and `--selftest`, Python standard library only — implementing `workflows-core:security-register-format`. A finding is named by a permanent origin, `<scan_id>:<plugin_id>`, so a renumbering never points a record's decisions at another finding; a number is never reused, and a renumbering is reported by each run that meets it until one records it: that run writes the move into its own record, so no later run reports it again. A changed `ID_VERSION` is judged per finding, never as a mass event. `plan --default-ref` anchors each sighting's base on the default branch, and `plan` lists as unverifiable each finding whose last sighting this clone cannot place. A squash merge counts as "later" only through a `[<key>]` commit dated no earlier than the last sighting and outside the base the sighting shares with the default branch, and "changed" compares the file's blob at the scan's commit with the one last seen. CI runs its self-test.
- **Packaging.** `plugin.json` declares `workflows-core` and `claude-security@claude-plugins-official`, neither pinned to a version, and the marketplace allowlists `claude-plugins-official` (`allowCrossMarketplaceDependenciesOn`), so installing this plugin installs Claude Security too. It ships no agent, hook, skill or reference file; a docs tree of eight pages; and the family's `scripts/bounded.py`, which CI holds identical to `workflows-core`'s.
- **Not built yet.** This release is sub-project A of the security roadmap in `docs/superpowers/specs/2026-10-15-security-workflows-scan-design.md`. Not in it: E, the architecture feedback loop, which would carry what the registers record into `/create-ard`, `/specify` and `/design`; the threat models, B in the ARD and C in the design; and D, security conformance, which would trace each threat model's mitigations to merged code.
