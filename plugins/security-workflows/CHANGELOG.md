All notable changes to the **security-workflows** plugin are recorded here.
Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

A section headed `— Unreleased` has not been published yet; where more than one of them stands, they all ship together in the next release.

## [0.1.0] — 2026-10-17

Install it with `claude plugin install security-workflows@shipwright` — in a script that runs before any interactive Claude Code session has registered Anthropic's official marketplace, such as a container launcher or CI, after `claude plugin marketplace add anthropics/claude-plugins-official`, without which Claude Security is not installed and the plugin cannot load. Needs `workflows-core` 1.42.0, which carries the register format, `unit-branch`, the `/scan` cost row and the `[SEC#n]` match of `followup-emission` §5 this plugin relies on. The plugin hands its fixes to `dev-workflows` 4.28.0's `/implement`, which continues on the Epic's branch and starts from the scan's patch.

### Added — the family's security audit, built on Claude Security

- **`/security-workflows:scan <KEY | repo-path> [--import <dir> | --triage | --verify-fixes] [--effort medium|high]`**, one typed-only command that records Claude Security's scans in the specs repository. It never scans by itself: Claude Security's own skill reads the code, puts each finding to its verification panel and writes the report, and the command records, triages and routes what that skill reports. It never runs anything against a deployed system and never writes exploit code.
- **Its modes.** A key alone is a **change scan** of the Epic's branch before its pull request merges — the branch `workflows-core:implementation-format` §5's `unit-branch` finds, scanned in place over the block's base, at `high` effort by default; it is the only mode that runs `unit-branch`, and a checkout standing on another branch is switched only on the user's answer — tracking `origin`'s branch where only the remote has it — while a switch or fast-forward git refuses stops the run as a *Cancel* does. A repository path is a **codebase scan** of the whole repository, at `medium`. `--verify-fixes` scans the changed files of the findings being fixed, in a temporary worktree at the default branch's head, removed on every path, and names each finding whose last sighting the default branch's head is not later than — stopping before the scan where no file is left to read, and saying so where the run's fetch of the repository failed or timed out. `--triage` scans nothing and puts the open findings, the findings to fix whose follow-up is unwritten, the accepted risks past their review-by date and the decisions awaiting security review to a person. `--import <dir>` records a Claude Security report a run did not record. The command never asks for a `low`-effort scan, which keeps no coverage account and so could never close a fix.
- **Two roles, and a Dev is never blocked.** A key run without `--triage` or `--verify-fixes` is the Dev's (`dev`); every other run is the Security Engineer's (`sec`). The findings are triaged in one batch — fix, decide later, a false positive with the `file:line` of the guard that defeats it, or an accepted risk with an owner and a review-by date — and a possibly-same match is always asked; where no row's suggestion would record a decision, the batch asks only *Decide each row* or *Decide all later*. A false positive's cited line must be a line of the scanned commit's tree: the run shows it and records the evidence as given, judging nothing, and a Security Engineer reviewing the decision sees that line beside it. The batch also offers each fixed finding the scan reports again, which it reopens, and each finding to fix whose follow-up was never written — its line cancelled at a preview, or its run cut off before the write — unless the scan closes it or proposes it fixed, and an accepted risk past its date that also awaits security review is one row, which one *Accept the risk* re-dates and, in a `sec` run, confirms. A Dev's false positive or accepted risk takes effect at once, recorded *awaiting security review*; a `sec` run confirms or overrules it, and nothing the Dev does waits on that review.
- **Fixes go to `/dev-workflows:implement`.** A `fix` decision becomes a follow-up line on a key run, or an `/implement` prompt line on a path, built from structured fields only — the `[SEC#n]`, a CWE, a plain `path:line` and the patch path — never from a finding's text, which is scan output and is quoted under its own heading wherever it is shown. Where the scan ran in the session's own repository over a clean stamp at its HEAD, the run asks Claude Security to suggest patches and copies them into the register; it never applies one. On a key run `/dev-workflows:implement` reads each patch a follow-up names under `$SPECS_PATH` and starts from it where it still applies; on a path the report prints each patch's absolute path beside its prompt line; and a finding marked fix again names the patch an earlier run recorded for it, where this scan made none — never one this run reopens, whose recorded patch is the fix that regressed, so its line says it has no patch. Follow-ups are previewed and written after the report, and a line the preview cancels returns its finding to `fix` with a second, small run record, which clears its follow-up link, so the next run offers it again. `followup-emission` §5 skips a `[SEC#n]` line only for an open line carrying the same `[SEC#n]`, so a finding reopened after its fix is queued again.
- **Closure on evidence only.** A change scan never closes a finding. A covering codebase scan, later than a finding's last sighting and over a changed file, closes a `fixing` finding by itself; one the scan reaches only through a squash merge, which names the unit and not the fix, is proposed fixed and closes on a person's confirmation, as an `open`, `fix`, `reopened` or `accepted-risk` one does. A finding raised for no unit — a scan of a repository path records one — has no key a squash's subject could carry, so, where it was last seen off the default branch, a later commit of the default branch outside its sighting's base stands in for the squash: once the default branch has moved on past the sighting, the finding can be proposed fixed rather than staying open for good. That commit says nothing about whether the fix merged, so such a proposal is marked `via: moved`, its row suggests *decide later* — which *Accept the suggestions* records nothing for — and it closes only on a Security Engineer's explicit *Confirm fixed*: a Dev's run offers no row for it. A finding whose file is gone is proposed fixed only by a scan later than its last sighting, never by a parallel Epic's or by the default branch's before its work merged, save that, for a finding raised for no unit and last seen off the default branch, any scan holding a later commit of the default branch proposes it the same marked way.
- **The session model is the scan's model.** Claude Security's agents inherit it. On Opus nothing is asked; on Sonnet or below the run asks before scanning, recommending a re-run after `/model opus`; on Fable nothing is asked, and the confirmation says Fable's filters re-run some of the scan's requests on Opus. `--enforce-model` reaches only the run's own maintenance agents, and under it the Sonnet question does not fire. One confirmation precedes every scan and states that it may take a while and use a significant number of tokens. Whether a scan is verified is read from its revision stamp, never from the workflow's journal, whose *empty result* for a researcher that found nothing is a clean answer, and the report says how many researchers did not return where some did not.
- **Twelve stops, all `SECURITY_*`:** `SECURITY_USAGE`, `SECURITY_SPECS_MISROOTED`, `SECURITY_NO_IMPLEMENTATION`, `SECURITY_PREREQ_PYTHON` (a `python3` older than 3.9), `SECURITY_PREREQ_WORKFLOWS` (no `Workflow` tool: turn on *Dynamic workflows* in `/config`), `SECURITY_TREE_DIRTY`, `SECURITY_EPIC_MERGED`, `SECURITY_BRANCH_MISSING`, `SECURITY_NOTHING_TO_VERIFY`, `SECURITY_NOTHING_TO_TRIAGE`, `SECURITY_ALL_SKIPPED` and `SECURITY_NO_REPORT`. A stop writes no run record, unit note or follow-up, and a stop after the scan's report directory was found names it and the `--import` line that records it without scanning again — by the repository's path on a `sec` run, so the import keeps that role.
- **A report that may still hold a credential is not copied without asking.** Where Claude Security says the report's files may still hold a credential value, the run asks before copying anything into the specs repository: *Stop to clean the files, then record them with --import (Recommended)*, which names the files to check and the command that records them once clean, or *Record as they are*, after which the report says they were recorded unchecked. On `--import`, which cannot see whether Claude Security reported a redaction failure, the run says instead that the redaction is best effort. The command page and the getting-started page say what that leaves: a credential the redaction missed without saying so is copied into the specs repository and pushed with the run's session files, unreviewed, so keep that repository's access no wider than the code repository's and rotate any credential found in a scan folder.
- **The register is bookkeeping, and nothing waits.** The register's own paths in `$SPECS_PATH/security/<repo-slug>/` — `runs/`, `scans/`, `dev-workflows/`, `register.json` and `register.md`, so never a team's own document under `security/` — and the unit's `_security.md` note are committed and pushed by `commit-artifacts` with the run's session files, never handed off by pull request, and no run stops because another run's register changes are unmerged. A scan that another branch's run record holds already records nothing, and the run deletes the scan folder it copied; one a run on the same checkout recorded meanwhile records nothing either and keeps its folder, which that run's record names, and either way the run lists its decisions for a `--triage`. A report imported again copies nothing where its files are identical to the scan folder's, and where they differ keeps the recorded copy, naming the files that differ; only a folder no record names, left by a run that broke off, takes the new files — at once, without planning first, where it lacks the stamp or the JSONL, which no record can name — and a folder a record names is never rewritten. The run records that other `session/*` branches hold are reserved before numbering, and a temporary worktree a crashed run left is offered for removal once nothing under it has changed for six hours. Where the terminal push is rejected because another clone pushed first, and the rejected commit holds a file of the register — on a run that recorded, or one whose rebuild rewrote a stale `register.json` or `register.md` — the run, one that ends early included, prints after its `Specs repo:` line how to settle the conflicts the advised `git pull --rebase` stops on: `register.json` and `register.md` by `register.py rebuild` and `git add`; a unit's `_security.md`, which is append-only, by keeping both sides' blocks; its `follow-ups.md`, whose lines are ticked in place, by keeping both sides' new lines and, where both sides hold one line, its ticked form; then `git rebase --continue`. A run that recorded nothing dispatches only the session-maintenance agent. The run's scratch directory is removed on every path.
- **`scripts/register.py`, the register's one writer** — `plan`, `ids`, `commit`, `rebuild`, `verify-scope` and `--selftest`, Python standard library only — implementing `workflows-core:security-register-format`. A finding is named by a permanent origin, `<scan_id>:<plugin_id>`, so a renumbering never points a record's decisions at another finding. A number is never reused, and a published one stays: where two records published one number, the earlier-sorting one keeps it and the other finding moves — onto the number another of its own allocations was last published under, where that number is its own, and otherwise to the lowest number above it nobody published — never back to one it held, and a new finding numbers past every published number, a move's target included. A move is reported from every number the finding was published under until a record holds it: the recording run writes it into its own record and names the follow-up lines to correct: the moved finding's own line under the old number, and those whose CWE and file, as far as a line names them, match the moved finding, a line naming neither only where it is that own line; `plan` and `rebuild`, which record nothing, mark it provisional. Ancestry is judged finding by finding — a sighting at a commit that comes before a finding's last one moves nothing and reopens nothing — and each record says so per sighting, so the replay needs no git. A changed `ID_VERSION` is judged per finding, never as a mass event. `plan --default-ref` anchors each sighting's base on the default branch, and an empty one stops as an unresolvable ref does. `plan` reads the revision stamp's `scan_prefix`, so a scan run from a subdirectory records paths and scope relative to the repository's top level, and refuses a finding whose file lies outside it. `plan` and `verify-scope` list as unverifiable each finding whose last sighting this clone cannot place, and propose a gone file's finding fixed only at a later commit; `verify-scope` lists a file only at a head later than its finding's last sighting, and as unreachable each finding whose last sighting that head is not later than. `plan` marks `via: moved` each closure and each gone file that only the default branch moving on past a sighting raised for no unit, made off it, reaches, and `verify-scope` each such gone file; without `--default-ref`, `plan` counts no commit for that leg. `plan` offers every `fix` finding again as `pending_fix`, and, given `--followups <the unit's follow-ups.md>`, every `fixing` one no line there carries under a number held for it or as its own line, as its run wrote it, so a finding a collision moved is not offered again while its own uncorrected line stands, save a finding the scan closes or proposes fixed; a `fix` decision clears the finding's follow-up link. A squash merge counts as "later" only through a `[<key>]` commit dated no earlier than the last sighting and outside the base the sighting shares with the default branch, and "changed" compares the file's blob at the scan's commit with the one last seen. `register.md` opens with each count in its own number — one scan, one accepted risk, one false positive. CI runs its self-test.
- **Packaging.** `plugin.json` declares `workflows-core` and `claude-security@claude-plugins-official`, neither pinned to a version, and the marketplace allowlists `claude-plugins-official` (`allowCrossMarketplaceDependenciesOn`), so installing this plugin installs Claude Security too. It ships no agent, hook, skill or reference file; a docs tree of eight pages; and the family's `scripts/bounded.py`, which CI holds identical to `workflows-core`'s.
