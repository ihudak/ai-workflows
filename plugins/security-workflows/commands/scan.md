name: scan
description: Security audit with the Claude Security plugin — before an Epic's pull request merges, or across a repository. Records the findings in the specs repository's per-repository register, triages each new finding in one batch (fix, decide later, false positive with evidence, accepted risk with owner and review date), and hands fixes to /dev-workflows:implement, which continues on the Epic's branch. A Dev is never blocked; the Security Engineer reviews in --triage. --verify-fixes closes fixes on evidence.

Check a codebase for security vulnerabilities with Claude Security: $ARGUMENTS

**Core references.** A citation of the form `workflows-core:<name>` names a shared reference in the `workflows-core` plugin. Load it with `Skill(skill: "workflows-core:reference", args: "<name>")` — never by path: `${CLAUDE_PLUGIN_ROOT}` resolves to this plugin, which does not carry it.

These shared references load by part — `escalation-rules`, `finding-triage`, `next-phase-offer` and `session-hygiene`. A citation of one names a rule: before applying it, load the part that holds it, `Skill(skill: "workflows-core:reference", args: "<name> <part>")`, the part its rule index names, unless that part is already in this conversation word for word; never guess a part's name — until you hold the index (every part carries it), load it with `args: "<name> index"`. A citation that names no rule the index holds loads the whole reference, `args: "<name>"`. Never apply a rule of these references from memory.

`/security-workflows:scan` wraps Claude Security and never scans by itself: Claude Security's own
skill reads the code, puts each finding to its verification panel and writes the report, and this
command runs that skill on an Epic's branch before the merge, or on a whole repository, and records
what it reports in the specs repository's findings register for that code repository. The register
is `workflows-core:security-register-format`'s (`Skill(skill: "workflows-core:reference", args: "security-register-format")`)
— its layout, statuses, roles and rules — and is written only through
`python3 "${CLAUDE_PLUGIN_ROOT}/scripts/register.py"`, its one writer. **The Dev** runs the command on
their Epic, before its pull request merges; **the Security Engineer** runs it across a repository,
closes fixes with `--verify-fixes`, and reviews decisions in `--triage`. **A Dev is never blocked**: a
`dev` run's decisions take effect at once — a false positive or an accepted risk it records is
*awaiting security review* until a `sec` run confirms or overrules it — and no run waits on another.
The command reasons about source code: it never runs anything against a deployed system, and never
writes exploit code.

Usage: `/security-workflows:scan <KEY | @<path> | repo-path> [--import <dir> | --triage | --verify-fixes] [--effort medium|high] [--skip-costs] [--skip-feedback] [--enforce-model=<model>]`

**Rule: Ask, don't guess.** Use `choices` arrays: 2–4 options, each array presented verbatim, and
never an authored "Other" — the harness supplies the free-text escape itself
(`Skill(skill: "workflows-core:reference", args: "escalation-rules core")` §0). A free-text answer to one of
this command's pickers is normalised into that picker's own options, or the question is asked again;
it is never written through as a value of its own.

**No shell variable survives from one Bash call to the next.** A value the run carries — `run_dir`,
`wt` and `run_role`, and a `$SPECS_PATH` the run was given at Phase 0 step 3 rather than inherited — is
set at the head of each Bash call that names it (`run_dir=<the path>; …`). Every other placeholder
below (`<repo root>`, `<repo-slug>`, `<default ref>`, `<KEY>`, `<unit folder>`, the unit's folder Phase 0
step 4 resolved, and `<run folder>`, the run folder step 5b opened) is written out in the command, and a
`<repo-path>` in a stop or an offer is written as this run's `<repo root>` where the run has one.

**`register.py` exits 2 when it cannot run**, its stderr led by its stop code. Save where a step below
handles a code itself, the run stops there with that message.

**Ending early.** Every stop — each `SECURITY_*` line, the `$SPECS_PATH` *Cancel*, Phase 0 step 4's
address stops, a stop `branch-check` makes at Phase 0 step 4, a switch or a fast-forward git refuses at Phase 1, and a `register.py` exit 2 before
Phase 7.2 has written the run's record — and every
run-ending answer — Phase 0 step 8's *Cancel*, Phase 1's switch *Cancel*, Phase 3's *Cancel* and

7.4's worktree removal where Phase 2 added one, the cost entry (unless `--skip-costs`), the removal of
`$run_dir` where it is a `mktemp` directory (Phase 0 step 5b: made there, or afresh where the run folder was lost) — `run_dir=<the path>; case "$run_dir" in */security-workflows-run.*) rm -rf -- "$run_dir" ;; esac`,
which removes nothing else, and nothing in a run folder, which a stop keeps — immediately before `commit-artifacts`, and `commit-artifacts`, with the
`register_rebuild` Phase 7.6 passes, its outcome line followed by Phase 7.6's settle line wherever 7.6 says that line applies, with no `resume.md` and no
maintenance phase. A stop taken before Phase 0 step 4's
preflight — step 2's and step 4's `SECURITY_USAGE`, the `$SPECS_PATH` *Cancel*, step 4's address
stops — skips the preflight too (§3 there). A stop writes no run record, unit note or follow-up, and
says what was decided before it; a scan folder in the register that no record names, and that Phase 4
created or copied files into, is deleted — save where the run folder is kept, since effect `p4-copy` stands for it and the session that resumes the run records it. A folder a record names is never deleted, and one Phase 4
found in place and copied nothing into stays as it was found (Phase 4 step 2). A stop on a run that scanned, once Phase 3 step 3 has found the report directory
and before 7.2 has written the run's record, names that `CLAUDE-SECURITY-…` directory — on
`--verify-fixes`, the copy 7.4 makes of it out of the worktree — and the line that records it without
scanning again, `/security-workflows:scan <KEY | @<path> | repo-path> --import <report dir>`. Its address, where the
run's role is `dev`, is the `@<path>` as typed where the run was given one — the key may match more
than one folder — else its `<KEY>`; where the role is `sec`, it is the run's `<repo root>`, whatever
address the run was given: an `--import` with a key is a `dev` run (Phase 0 step 2), so only the path
keeps a `sec` run's role. Where the run folder is kept, running the same command again resumes the run and records that report too, keeping the answers given; the `--import` line starts a run of its own.

**Every stop taken once Phase 0 step 5b has opened the run folder** — step 6's, step 8's, and every one of Phases 1 to 7 — runs `run-stop-line` (`Skill(skill: "workflows-core:reference", args: "run-folder run-stop-line")`) right after its own message, `<command>` there being `/security-workflows:scan` and the arguments as given; save step 8's *Cancel* on a run that did not resume, which discards the folder instead (step 8). A stop before step 5b prints no `Run folder kept:` line. No stop here but one is one a resume meets again: each re-tests what caused it, and no answer that ends the run is recorded. The one is `SECURITY_RESUME_REPORT_GONE` (step 6), in either of its forms, whose `Run folder kept:` line is `run-stop-line`'s start-over form. These tails are not guarded: the session that resumes and finishes the run runs its own. `SECURITY_RUN_TAKEN_OVER` (Phase 0 step 5b) takes no tail at all, and no stop takes the tail a finished run takes, so `close-run` runs on a finished run alone (7.6).

## Phase 0 — Setup

1. **Run flags.** **Strip the run flags first.** Execute `strip-run-flags` (`Skill(skill: "workflows-core:reference", args: "run-flags strip-run-flags")`) on `$ARGUMENTS` before anything else reads a token: it removes `--skip-costs`, `--skip-feedback` and `--enforce-model` (with any `=value`), resolves each against its environment default, and returns the `run_flags` record this run carries to its maintenance, cost and routing steps — or stops with `RUN_FLAGS_BAD_MODEL` / `RUN_FLAGS_MODEL_UNAVAILABLE` before any write. Every later step parses only what it leaves.

   **Load the question rules.** Load `escalation-rules core` now, with `Skill(skill: "workflows-core:reference", args: "escalation-rules core")`, before this run asks the user anything: every question it asks follows them — two to four options, presented verbatim with the `(Recommended)` marker where one is recommended, and a selection that carries no text.

2. **Arguments.** What step 1 leaves is one positional address and the command's own flags.
   - **An `@` token whose path — absolute, or relative to the working directory — names an existing directory under `$SPECS_PATH/specifications/` is a unit's folder**, and the run is a key run in every respect: step 4 reads the key its carrier asserts. With `$SPECS_PATH` unset, or naming no existing directory, such a token cannot be placed yet: take step 3's stop first, and classify the address again once it is answered. **Any other address that does not begin with `@` and names an existing directory is a repository path**: step 5 takes its repository. **Any other address is a key**, which step 4 reads with `read-key` — an `@` token naming no such folder among them, which `read-key` finds `invalid`.
   - `--import <dir>`, `--triage` and `--verify-fixes` exclude one another, and `--import` takes an existing directory.
   - `--effort` takes `medium` or `high`. This command never asks Claude Security for a `low`-effort scan, which reads the target with one researcher, keeps no coverage account, and so can never close a fix (`workflows-core:security-register-format` §5 rule 2). On `--import` and `--triage`, which scan nothing, `--effort` has no effect, and the run says so.
   - Anything else stops — no address or two, an unknown flag, a flag without its value, two of `--import`, `--triage` and `--verify-fixes`, an `--import` naming no existing directory, or an `--effort` other than `medium` or `high`:

     `SECURITY_USAGE: /security-workflows:scan needs one address — a key (^[A-Z][A-Z0-9_]*(-\d+)+$, e.g. ACME-7-01), an @<path> to its folder, or a repository path — at most one of --import <dir>, --triage and --verify-fixes, and --effort medium or high. Re-run '/security-workflows:scan <KEY | @<path> | repo-path> [--import <dir> | --triage | --verify-fixes] [--effort medium|high]' — <what was wrong>.`

   **A run that scans** is every run but `--import` and `--triage`: a key with none of `--import`, `--triage` and `--verify-fixes` (a **change scan** of the Epic's branch), a path with none of them (a **codebase scan** of the whole repository), and `--verify-fixes` with either address (a codebase scan scoped to the files of the findings being fixed). The effort defaults to `high` for a change scan — Claude Security's own advice for a feature-sized change — and to `medium` for a whole-repository scan or `--verify-fixes`.

   **The run's role, `run_role`** (spec D3): `dev` for a key run without `--triage` or `--verify-fixes` — the Dev's pre-merge scan, or an `--import` with a key — and `sec` for every other run. It is recorded as `register.py`'s `--role`, and passed to cost as `run_role`.

3. **Require `$SPECS_PATH`.** Take this test before step 4 resolves anything: the register lives under it, on every run. Where it is unset, or names no existing directory, stop naming it: `choices: ["Set SPECS_PATH (you'll be prompted for the path)", "Cancel"]` — *Set SPECS_PATH* asks for the path in plain text, carries it as `$SPECS_PATH` for the run once it names an existing directory, and asks again where it does not (`workflows-core:escalation-rules` *Required path environment variable unset*); *Cancel* ends the run.

4. **Resolve the address.** A repository path needs no resolution: its run key set is empty, and the run is keyless. A unit's folder given as an `@<path>` is never read with `read-key`, which reads no path: read the key its carrier asserts now (`workflows-core:addressing` §4) — the run's key from here on, its run key set's and every stop's — and hand `resolve-address` the token as typed, through its `@<path>` branch (§3 step 1); a folder with no carrier asserts no key, and a key run needs one, so it stops as §3 step 1 says. This is the way through `resolve-address`'s `ambiguous` stop, which names `@<path>`. A key is read with `read-key` (`workflows-core:addressing` §1) and resolved with `resolve-address` (`Skill(skill: "workflows-core:reference", args: "addressing resolve-address")`, §3). `status: found` → carry its `path` (the unit's folder), `kind` and `key`; `ambiguous` → stop, naming every match; `misrooted` → stop with §3's `SPECS_PATH_INSIDE_TREE` message; `absent` → stop with the `key dir not found` rule of `workflows-core:escalation-rules` — this command creates no folder. A token `read-key` finds `invalid` stops with `SECURITY_USAGE`, its `<what was wrong>` reading `'<token>' is not a key (workflows-core:addressing §1)`.

   **Specs-repo preflight** — once the run key set is fixed (`workflows-core:specs-repo-git` §3.2: the resolved `key`, and on an Epic folder its parent PRD's key too; empty for a path). Invoke `Skill(skill: "workflows-core:reference", args: "specs-repo-git specs-preflight")` and execute its `specs-preflight` entry point (§3) inline, with `register_rebuild: ${CLAUDE_PLUGIN_ROOT}/scripts/register.py` (its §7), so that a leftover push its §3.4 retries, which `origin` rejects because its branch moved on, can rebuild a register both sides changed. Where it returns `specs_git: blocked` (§3.3 G0), carry that flag for the whole run: the register is still written, and `commit-artifacts` leaves it uncommitted and says why. Where it returns `specs_git: misrooted` (§3.1), stop: the register lives under `$SPECS_PATH`, and nothing is written under a misplaced one — no scan folder, run record, unit note or follow-up:

   `SECURITY_SPECS_MISROOTED: $SPECS_PATH is misplaced — the notice above says how, and names the value to set where it can tell. The register can be read there but not written, so this run would record nothing; point SPECS_PATH at the root of a dedicated specs repository, then re-run '/security-workflows:scan <the arguments as given>'.`

   **Check the branch the run stands on.** Where step 4 resolved a unit's folder — a key, or an `@<path>` to one — execute `branch-check` (`Skill(skill: "workflows-core:reference", args: "phase-handoff branch-check")`, §6) on it, with no `prefix`: this command hands nothing off in the specs repository. A stop it makes ends the run here. A repository path resolves no folder, and skips this.

5. **The repository** (spec D5). Each run reads one code repository, `<repo root>`:
   - **A key run without `--import`** — a change scan (a key with none of `--import`, `--triage` and `--verify-fixes`), or `--triage` or `--verify-fixes` with a key — takes the repository this session is open in: `git rev-parse --show-toplevel` from the working directory. It is the one repository Claude Security's change job scans, and, for `--triage` and `--verify-fixes`, the repository whose register the key narrows. Where that fails, stop with `SECURITY_USAGE`, its `<what was wrong>` saying that this session is open in no git repository.
   - **A path** takes `git -C <path> rev-parse --show-toplevel`. Where that fails, stop with `SECURITY_USAGE`, naming the path as no git repository.
   - **`--import <dir>`** takes the repository whose root holds `<dir>`: `git -C <dir> rev-parse --show-toplevel`. With a key, that repository must be one the unit's `implementation.md` names in a block's `repo:`; with a path, it must be that path's repository. Otherwise — or where `<dir>` is in no repository — stop with `SECURITY_USAGE`, saying which.

   **`<repo-slug>`** is `workflows-core:components` §1's: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/bounded.py" 5 git -c safe.bareRepository=explicit -C '<repo root>' remote get-url origin 2>/dev/null`, `<repo root>` single-quoted, each `'` it holds written `'\''` — a top level `git rev-parse --show-toplevel` printed, which holds the `.git` §1's precondition asks of a directory (`workflows-core:read-only-repos` §0) — any trailing `/` stripped and then a trailing `.git`, and the URL's last path segment taken. A repository with no `origin` has no slug (`workflows-core:components` §1), and so no register: stop with `SECURITY_USAGE`, naming `<repo root>` as having no `origin`. (On `--import` with a key, the slug is what the `repo:` test above compares.)

   **Refresh its remote refs**, best effort, on a writable clone (`workflows-core:read-only-repos` §1): `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/bounded.py" 30 git -C <repo root> fetch --quiet origin` — refs only, never a switch, a pull or a working-tree write. A fetch that fails or times out is named in the report's `### Scope`, and the clone is read as last fetched. On a read-only mount, fetch nothing, and the report says so. Where `git -C <repo root> rev-parse --is-shallow-repository` prints `true`, the report's `### Scope` says the merge state may read as open in a shallow clone (`workflows-core:implementation-format` §5), and the run never deepens it.

   **`<default ref>`** is the repository's default ref by `workflows-core:read-only-repos` §3's chain, read after that fetch — `origin/<default>`, with `<default>` its branch name. `register.py` anchors a scan's base on it, and a change scan's `unit-branch` reads it. Where the chain resolves none, every run but `--triage` skips the repository, its reason that it has no default branch (`git -C <repo root> remote set-head origin --auto` sets one), and stops at once with Phase 2's `SECURITY_ALL_SKIPPED`; `--triage` reads no commit, and plans without one.

   **A change scan (a key with none of `--import`, `--triage` and `--verify-fixes`) then finds the Epic's branch**, with `workflows-core:implementation-format` §5's `unit-branch`, which reads local refs only. First take `<branch>` from the latest block of the unit's `implementation.md` whose `repo:` is `<repo-slug>` (§5's *Latest, earlier and earliest*), where there is one, and fetch it by its explicit refspec — a single-branch clone's plain fetch never creates `origin/<branch>` (§5 there) — on a writable clone, best effort: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/bounded.py" 30 git -C <repo root> fetch --quiet origin +<branch>:refs/remotes/origin/<branch>`. Its `couldn't find remote ref` says only that `origin` lacks the branch, and is no failure. Where that fetch found the branch not on origin and `refs/remotes/origin/<branch>` still resolves (`git -C <repo root> rev-parse --verify --quiet refs/remotes/origin/<branch>`), remove that one stale tracking ref, `git -C <repo root> update-ref -d refs/remotes/origin/<branch>`, and the report says it was removed. Any other failure or a timeout is named in the report. On a read-only mount this fetch is skipped too, and the report says so. Then run `unit-branch` (`Skill(skill: "workflows-core:reference", args: "implementation-format unit-branch")`) with `<repo root>`, `<repo-slug>`, `<KEY>`, the unit's `implementation.md` and `<default ref>` as `<ref>`, and carry its `state`, `branch`, `base`, `commit`, `tip` and `after_merge` to Phase 1. Where `unit-branch` could not compare the tip — a git whose `merge-tree` lacks `--write-tree`, or a call that compared nothing — the report's `### Scope` says the tip was not compared; where its merged test passed in the subject leg's left-behind case (`workflows-core:implementation-format` §5), it says instead that the tip conflicts and `origin/<branch>` is gone, so the merge state rests on the commit subject alone.

   Where a change scan's state is `none`, stop:

   `SECURITY_NO_IMPLEMENTATION: <KEY>'s implementation.md names no block for <repo-slug>, the repository this session is open in — it names <slugs, or 'nothing'>. Run '/security-workflows:scan <KEY>' from one of those repositories, or '/security-workflows:scan <repo-path>' for a whole-repository scan.`

5a. **Prerequisites.** Skip both checks under `--triage`.
   - Where `python3 -c 'import sys; sys.exit(sys.version_info < (3, 9))'` fails, stop, `<version>` being what `python3 --version` prints:

     `SECURITY_PREREQ_PYTHON: Claude Security needs python3 3.9 or newer on PATH, and this one is <version> — put a newer python3 first on PATH, start a new session, then re-run.`
   - For a run that scans, where the `Workflow` tool is not among the tools this session can call right now — the tools given with their parameters, not a name in a recipe or a grant — stop:

     `SECURITY_PREREQ_WORKFLOWS: Claude Security runs its scan as a dynamic workflow, and the Workflow tool is not available in this session — turn on the Dynamic workflows row in /config (on Pro it is off by default), then re-run.`

5b. **Open the run folder — once step 5 has resolved `<repo root>` and steps 5 and 5a have taken their stops, and before the run's scratch directory is made.** No refusal before it depends on what this run writes: `branch-check` runs with no `prefix`, so only its §6.1 applies, which reads `specifications/` and leaves out the session files, while this run writes its register under `security/` and its unit note and follow-ups as session files. Step 8, the session-model question, comes after it, since it reads the folder (*Where a resumed run goes on*, below). Execute `open-run` (`Skill(skill: "workflows-core:reference", args: "run-folder open-run")`) with:
   - `--command` naming the mode, since a keyed run's key leaves its arguments out (`workflows-core:run-folder` §1) and two modes under one key are two runs: `security-workflows.scan` for a change scan or a codebase scan, `security-workflows.scan-verify-fixes`, `security-workflows.scan-triage` and `security-workflows.scan-import`;
   - `--key <KEY>` on a key run, the key step 4 read, and none on a repository path;
   - `--specs "$SPECS_PATH"`;
   - `--workdir <repo root>`, the repository the run reads, so one key scanned from two repositories is two runs;
   - `--args '<the arguments>'` — every token steps 1 and 2 read, run flags included, in their order, joined by single spaces, a repository path written as `<repo root>` and `--import`'s `<dir>` as `cd <dir> && pwd -P` prints it. A keyless run's key holds them, so one started with other flags is another run, which `open-run`'s step 6 offers.

   The run carries `run_folder` from here on, and `run_resumed` where it resumed (`workflows-core:run-folder` §2). Where `open-run`'s step 6 resumes another run, steps 1 and 2 are taken again from its arguments; its repository is `<repo root>`, since `others` lists only runs on it. Then read `fact <run folder> today`, and where its `value` is `null`, record `date -u +%Y-%m-%d`'s output with `fact <run folder> today --set '<it>'`: the run's UTC date — the `--today '<it>'` every `register.py plan` call adds, the day Phase 5 step 5 counts a review-by date from, and 7.3's heading.

   **Then make the run's scratch directory, `run_dir`**, outside every repository; its files — the reservations, the plans, the decisions — are the run's own and are never committed. Where the run folder is open, it is `<run folder>/scratch` (`workflows-core:run-folder` §5). Otherwise `run_dir=$(mktemp -d -t security-workflows-run.XXXXXX)`, carrying the path it prints, removed on every path from here on: immediately before the terminal `commit-artifacts` (Phase 7.6), and in *Ending early*'s tail. **Where the run folder is lost later** — the run goes on without it after a call's exit 2, or a write into the folder that failed (`workflows-core:run-folder` §2) — `run_dir` leaves it at once, before the step that lost it goes on: make one afresh the same way, `run_dir=$(mktemp -d -t security-workflows-run.XXXXXX)`, copy the folder's scratch files into it, `run_dir=<the new path>; cp -R -- "<lost_folder>/scratch/." "$run_dir/"` — a copy that fails stops nothing — and carry the new path from then on, removed as the one made without a folder is. Where that step was writing with `put` a file a run with no folder writes into `run_dir` itself — a plan, `decisions.json`, `decisions-cancel.json` or `answered-plan.json` — it writes that file into the new `run_dir` instead, under its own name: copied from its `--from` file — the copy, or where the copy failed, the folder's own file — or its here-document written again.

   **Its files, where the run folder is open.** Each `register.py plan` call below writes `"$run_dir/plan.out"` in place of the file it names; once it exits 0, and no stop its step takes on that output is taken, `put <run folder> 'scratch/<the file it names>' --from "$run_dir/plan.out"` writes that file. `rebase` reaches `decisions.json` the same way, through `"$run_dir/decisions.out"`, and `verify-scope` reaches `scratch/p1/verify-scope.json` through `"$run_dir/verify-scope.out"`; `answered-plan.json` is `put` `--from "$run_dir/plan.json"`; and `decisions.json` and `decisions-cancel.json`, which the run writes itself, are `put` from a quoted here-document (`workflows-core:run-folder` §5). The reservations are a capture step 6 makes again in each session. `commit.json` is the output of effect `p72-commit`, written whole by its call and read only once that effect is done (7.2).

   **Taken over.** Wherever a call of the script exits 9 from here on, or a call that only reads exits 2 with `run folder no longer exists` (`workflows-core:run-folder` §2), stop at once — save in `close-run`, where 7.6 says what the run does:
   `SECURITY_RUN_TAKEN_OVER: another session (<id>) took this run over — stopping without writing.`
   `<id>` is the session the script's stderr line names (`owned by session <id>`); where that line says the folder was removed, or no longer exists, print instead
   `SECURITY_RUN_TAKEN_OVER: another session started this run over or finished it — stopping without writing.`
   This stop takes no tail at all (`workflows-core:run-folder` §2).

   **Phases.** As the run reaches each phase, log it first: `phase <run folder> <n>`, `<n>` being `1` to `6`, then `7.1` to `7.6` for Phase 7's steps. A phase a resumed run skips is not logged, nor are the steps a stop runs.

   **On `unfinished`, before its question**, the question takes this command's lines, read with `effect <run folder> <id> state`, `fact <run folder> <name>` and the run's files, writing nothing, since the run is not yet this session's. On every such run: `Resuming reuses each triage answer and maintenance-proposal choice this run recorded while its question is unchanged; to answer one again, start over.` Then the first of these that applies:
   - effect `p72-commit` done, fact `p72-record` naming a record: `The register holds this run's record, <it>: resuming goes on from there — the unit note, the report and the end of the run, each skipped where an earlier session finished it.` Where that fact is empty: `An earlier session of this run reached the register's commit and recorded nothing there: resuming goes on to the report and the end of the run.`
   - step 6's *A report gone* ending in its stop: `The report this run records is gone, and no whole copy of it stands in the register: resuming stops on that; start over to <scan afresh | import it again>.`

## Phase 1 — Scope

Phase 1 fixes what the run reads: the **commit** a scan must read, its **kind**, and its **scope**.

**A run that scans needs a writable clone.** Claude Security writes its report directory into the scan
root, and a switch or a temporary worktree writes too. On a read-only mount
(`workflows-core:read-only-repos` §1), a run that scans skips the repository, with that reason, and
stops on Phase 2's `SECURITY_ALL_SKIPPED`.

**A change scan (a key with none of `--import`, `--triage` and `--verify-fixes`)**, by `unit-branch`'s state — `--verify-fixes` and `--triage` with a key never run `unit-branch`, and never meet these states:
- **`checked-out`:** scan the branch's tip in place. A dirty tree — `git -C <repo root> status --porcelain` prints anything — stops for the user to commit or stash, because a change scan reads committed changes only, and a report stamped dirty yields no patch:

  `SECURITY_TREE_DIRTY: <repo-slug>'s checkout has uncommitted or untracked changes, and a change scan of <branch> reads committed changes only — commit them, stash them with 'git stash -u', or delete or ignore the untracked files, then re-run '/security-workflows:scan <KEY>'.`

  Where the tip is `origin/<branch>`'s — `<branch>` resolves to another commit, which is behind it — run `git -C <repo root> merge --ff-only origin/<branch>` first and say so; where git refuses it, report its error and stop as the switch question's *Cancel* below does. The commit is then `git -C <repo root> rev-parse HEAD`. Where it differs from the block's recorded `commit`, the Phase 3 confirmation says so: review commits move a branch past it, which is no error. Where `after_merge` is true, the confirmation says that the pull request has merged and the branch has gone on since, so the change scan reads what the branch adds over `<base>`: the work that followed the merge, and, where the pull request merged by a squash or a rebase, the merged work too.
- **`local` or `remote`**, on a clean tree — a dirty one stops with `SECURITY_TREE_DIRTY` as above, since no switch is offered over it: name `<branch>` and its tip, and ask `choices: ["Switch to <branch> (Recommended)", "Cancel"]`. *Switch* runs `git -C <repo root> switch <branch>` where the state is `local`, and `git -C <repo root> switch --no-track -c <branch> origin/<branch>` where it is `remote`, which creates the local branch from `origin/<branch>` with no configuration write, then `git -C <repo root> branch --set-upstream-to=origin/<branch> <branch>`, best-effort, whose failure — a `.git/config` that cannot be written — moves nothing and stops nothing. Never `--track`: its upstream write, where `.git/config` cannot be written, comes after git has created the branch and moved the index and the working tree onto it, and exits 1 with HEAD where it was, which the refusal below would report over a staged reversal of HEAD's branch. Then, where the tip is `origin/<branch>`'s and the local branch is behind it, `git -C <repo root> merge --ff-only origin/<branch>`, saying so. The commit is then HEAD, and `after_merge` is said as above. *Cancel* ends the run with the checkout where it was. Where git refuses the switch or the fast-forward — `<branch>` checked out in another worktree of the clone, say — report its error and stop as *Cancel* does, naming the branch the checkout stands on — `a branch whose name is outside the safe class` for one outside `workflows-core:read-only-repos` §3's *Branch names* class. A read-only mount takes no switch: the repository is skipped, with that reason.
- **`merged`:** stop:

  `SECURITY_EPIC_MERGED: <KEY>'s work in <repo-slug> has merged into <default> — a change scan has nothing left to diff. Scan the repository with '/security-workflows:scan <repo-path>', or close fixes with '/security-workflows:scan <repo-path> --verify-fixes'.`
- **`missing`:** stop:

  `SECURITY_BRANCH_MISSING: <KEY>'s latest block in <repo-slug> records <branch>, which is neither shown merged nor found in this clone — where its pull request closed without merging, re-run '/dev-workflows:implement <KEY>', which needs <KEY>'s specification.md and design.md on the specs repository's default branch, then '/security-workflows:scan <KEY>'; where it merged under a subject without [<KEY>] and its branch is gone, scan the repository with '/security-workflows:scan <repo-path>'.`

  After `records <branch>`, add each clause that applies: for a block that says `pushed: false`, ` (never pushed — push it from the clone that committed it, or scan there)`; where Phase 0 step 5's branch fetch reached `origin` and found no branch, ` (not on origin)`; and where that fetch failed or timed out, ` (the run's fetch of it failed — fetch it with 'git -C <repo root> fetch origin +<branch>:refs/remotes/origin/<branch>', then re-run)` — the only case that offers a fetch.

The kind is a **change scan**, with `--base <base>`: the block's `base`, written `origin/<base>` where
that ref resolves after Phase 0's fetch, so that a stale local `<base>` cannot move the merge base
back and widen the diff past the Epic's own work.

**A path:** a codebase scan of `<repo root>` as it stands, at `git -C <repo root> rev-parse HEAD`. A
dirty tree is scanned anyway, and its confirmation says that a dirty scan closes nothing and yields
no patch (`workflows-core:security-register-format` §5 rule 5).

**`--verify-fixes`:** a codebase scan at the default branch's head, `git -C <repo root> rev-parse <default ref>`,
scoped to the files of the findings being fixed:

```
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/register.py" verify-scope --specs "$SPECS_PATH" --slug <repo-slug> --repo <repo root> --ref <default ref> [--unit <KEY>]
```

`--ref` is the repository's default ref (`workflows-core:read-only-repos` §3), and `--unit` is given
with a key. It prints `{files, gone, unverifiable, unreachable}`, each `fixing` finding in at most one
of them. Its `files` — each `fixing` finding's file that changed on `<default>` since the finding was
last seen, at a head later than that sighting — become the scan's scope, and its `gone` — an entry
for each `[SEC#n]` whose file `<default>` no longer holds, at a head later than its last sighting,
marked `via: moved` as Phase 4's plan marks one — carry to Phase 5 as gone rows. Its `unverifiable`
— the `[SEC#n]` whose last sighting this clone cannot place, their file on `<default>` or not — carry to the report's `### Register`, as Phase 4's do. Its
`unreachable` — the `[SEC#n]` whose last sighting this clone holds but `<default>`'s head is not later
than, so a scan there can close nothing yet: a sighting on a branch whose fix `<default>`'s head does not
show merged, or, for a finding raised for no unit, one that head has not moved on past
(`workflows-core:security-register-format` §5 rule 2) — carry to the report's `### Register` too. On exit 2, stop with its message. Where the run folder is open, it prints into `"$run_dir/verify-scope.out"`, which Phase 0 step 5b's rule writes to `scratch/p1/verify-scope.json`, whence Phase 5 and the report read these lists.
Where `files` is empty, stop before the scan:

`SECURITY_NOTHING_TO_VERIFY: no finding being fixed in <repo-slug><, for KEY> has a file that changed on <default> after its last sighting — nothing to verify yet.`

Where `unreachable` names findings, the message goes on: ` <default>'s head is not later than the commit <each [SEC#n]> was last seen at, so a scan of it can close nothing yet — where a fix is not on <default>, push it and merge it, then re-run '/security-workflows:scan <the arguments as given>'.` Where `gone` names findings, it goes on: ` <default> holds no file for <each [SEC#n]>; a scan of the repository ('/security-workflows:scan <repo-path>') proposes them fixed.` — and, where any is marked `via: moved`: ` For <each such [SEC#n]>, nothing records that its fix merged: where it is not on <default>, push it and merge it first, then confirm or keep open what that scan proposes.` Where `unverifiable` names findings, it goes on: ` This clone cannot place the last sighting of <each [SEC#n]> — fetch the branch that holds it, then re-run.` And where Phase 0 step 5's fetch of `origin` failed or timed out, it ends, whichever lists name findings: ` This run's fetch of origin <failed: <git's error> | timed out>, so <default> was read as this clone last fetched it — fetch origin, then re-run.`

Where `files` is not empty, scan them as below, and the report's `### Register` names every
`unreachable` finding, which this scan leaves as it stands.

**`--triage`:** no scan. Plan the triage:

```
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/register.py" plan --specs "$SPECS_PATH" --slug <repo-slug> --repo <repo root> [--unit <KEY> --followups "<unit folder>/follow-ups.md"] --reserve-dir "$run_dir/reserve-<repo-slug>" --default-ref <default ref> > "$run_dir/plan.json"
```

`--unit` and `--followups` are given with a key — `--followups` names the unit's `follow-ups.md`,
whether or not it exists, so a `fixing` finding whose line it lacks comes back as `pending_fix` — and
`--default-ref` is left out where Phase 0 step 5 resolved no default ref. On exit 2, stop with its
message. Where the plan's `open`, `pending_fix`, `review_due` and `unconfirmed` are all empty, stop:

`SECURITY_NOTHING_TO_TRIAGE: <repo-slug>'s register holds no open finding, no finding to fix whose follow-up is unwritten, no accepted risk past its review-by date, and no decision awaiting security review<, for KEY>.`

Otherwise go to Phase 5.

**`--import`:** no scan. Go to Phase 4.

## Phase 2 — Checkout

- **A change scan** scans `<repo root>` in place, on the branch Phase 1 left checked out: the scan root is `<repo root>`.
- **A path** scans `<repo root>` in place too.
- **`--verify-fixes`** scans a temporary worktree at the default branch's head, so the user's checkout is never switched. Run `wt=$(mktemp -d -t security-workflows.<repo-slug>-<commit7>.XXXXXX)`, `<commit7>` the first seven characters of Phase 1's commit, then `git -C <repo root> worktree add --detach "$wt" <commit>`, and carry the path as `wt`. The scan root is `$wt`. Its fixed name prefix is what Phase 0 step 7 finds after a crash. While it stands, run `touch "$wt"` before each question this run asks — Phase 3's confirmation, Phase 4's redaction question and every Phase 5 question — so that another session's Phase 0 step 7 never takes a worktree whose run is waiting on an answer for idle; `touch` changes only the directory's time, and nothing `git status` reads. Phase 7.4 runs `git -C <repo root> worktree remove --force "$wt"` on every path, failure included. A read-only mount skips it, with its reason (Phase 1); where `worktree add` fails, the repository is skipped with git's message. Where the run folder is open, a worktree fact `wt` already names that `git -C <repo root> worktree list --porcelain` lists — an earlier session's, holding no report this run records (Phase 0 step 5b) — is removed before the `worktree add`, with `git -C <repo root> worktree remove --force <it>`, and the new path is recorded once that add succeeds, `fact <run folder> wt --set '<it>'`.

Where the repository was skipped — here, in Phase 1, or for want of a default ref (Phase 0 step 5) —
stop:

`SECURITY_ALL_SKIPPED: every repository in scope was skipped — <each: repo-slug, reason>.`
