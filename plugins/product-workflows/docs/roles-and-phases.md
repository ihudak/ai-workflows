# Roles and phases

[Workflow overview](workflow.md) shows where each command sits in the pipeline. This page says what each role is accountable for, and — in its second half — what each cost-attribution phase means when you see it on a cost report or a run's output.

## The handover model

Every phase ends the same way: a producing command lands its deliverable on the specs repo's default branch — not merely written to disk, and not merely committed to a branch of its own. What the next command in the chain does when that hasn't happened yet depends on which state it finds, and two states show up often enough that you will actually hit them.

- **The artifact exists but sits on an unmerged branch the commands cut** (`idea/`, `prd/`, `ard/`, `spec/`, `design/` and the rest) — a pull request open, or one that never got opened. The next command stops cold and names the branch (and the open PR, if there is one) rather than guessing at content that might still change underneath it.
- **No such branch carries it** — it was never committed, or sits only on a branch of your own. The next command treats it as absent and falls back to whatever it already did before this artifact existed — an absent optional input is never promoted into a new prerequisite. Several of this plugin's own commands are the exception: each whose gated input was never optional stops on its absence, and `workflows-core:phase-handoff` §3.4 lists them.

The companion `dev-workflows` plugin's `/dev-workflows:ready` is the one caller whose own gate never stops it: because its whole job is to report on readiness, an artifact it can't verify becomes a finding that caps its verdict at `PARTIAL` rather than a reason to halt. It ships outside this plugin, but it is the exception worth knowing, since it consumes the ARD and the specification this plugin's own PA and PE roles produce. This plugin's `/brd-reconcile` also reads a stopping row without stopping, at three sites — its cross-BRD write guard, a `--sent` run's redundancy check at Phase 0 step 6, which reads the gate inverted, and its ordinary Phase 0 gate on the most recent prompt while the package the review answers is undetermined, which tries each older prompt, newest first, and stops only where none passes; and `/brd-interview` at one, its Phase 0 step 8a gate on its parent's defect log, where a stopping row withholds only its offer to close an `unsourced` defect and the round goes on (`workflows-core:phase-handoff` §3.7).

## PM — product management

- **Owns:** turning a raw prompt, community post, RFE, or existing PRD into a refined idea, then into a well-formed Product Requirements Document, and keeping an existing PRD current.
- **Runs:** `/idea`, `/create-prd`, `/update-prd`; also `/prd-proposal` and `/brd-proposal`, the two optional effort proposals — one for a slice, one for the programme over it — which gate nothing on the build ladder and which nothing on it waits on; each does gate its own input — `/prd-proposal` the folder's `prd.md`, `/brd-proposal` each included slice's `proposal.md` — and that is the whole of what either **gates** on, and each command's only hard refusal on readiness (see [proposal](#proposal) below); both refuse on other things, an unresolvable address and an uncapturable profile among them; also the early run of the companion plugin's `/docs-workflows:release-notes`, before any specification or design exists yet.
- **Consumes:** a prompt, file, community post, RFE, or existing PRD as its source; then a refined `idea.md` plus a user-supplied address.
- **Produces:** `idea.md` in the PRD folder the address names, then **prd.md** written to that same folder under `$SPECS_PATH/specifications/`; an early release-notes draft; and, optionally, **proposal.md** and its rationale brief in that same folder, or in the `BRD-` container above a set of priced slices.
- **Hands over at the seam:** `/idea` writes `idea.md` in its final folder and lands it, and `/create-prd` / `/update-prd` land the PRD, each onto the specs repo's default branch. `/create-ard` and `/specify` each gate on the PRD there — an absent PRD falls back to reading the resolved folder directly instead of stopping (reported, not silent), and the hard stop is an unmerged PRD, never a missing one. `/epics` reads the PRD unconditionally through the folder read, with no PRD gate at all — see PE below for the input it does gate.
- **Cost phase(s):** `prd-creation` (`/idea`, `/create-prd`), `prd-update` (`/update-prd`), `brd-to-prd` (`/brd-intake`, `/brd-split`, `/prd-ground` on either route, `/brd-interview`, `/brd-package`, `/brd-reconcile`), `proposal` (`/prd-proposal`, `/brd-proposal`) — all role `pm`.
- **Grounds (`/prd-ground`, either route):** consumes the resolved folder's own claim list — a BRD slice's `[BR#n]` inventory, which `/brd-split` copied from the parent's, on the BRD route; a PRD's own `[AC#n]`/`[FR#n]` rows on the idea route, where it gates `/create-prd`'s `prd.md` — and the mounted implementation and design repos, pinned to a verified commit; produces `[CG#n]`/`[DG#n]` findings in that folder, landed by the same handoff as every other deliverable. On the BRD route the same `/brd-split`, run again on that slice, refuses to allocate a row until every finding carries a verifier verdict.
- **Also owns the BRD-to-PRD route** ([BRD workflow](brd-workflow.md)): turning a customer-supplied BRD into a requirement inventory that is grounded, fully allocated, decided, and reviewed by the customer who supplied it. This route is PM-owned end to end — every command on it runs as PM, `/prd-ground` included; a PA or PE runs it instead where the PM cannot clone the code repositories — both have them cloned for their own work, and teams have fewer PAs than PEs, so either may (PA and PE below).
- **Hands over at the BRD route's own seams:** each command of the route lands its deliverable on the specs repo's default branch, and a later one gates on it there — `/brd-split`, run on the root, reads the intake ledger from the worktree, ungated, and carves each slice's own inventory and ledger; `/prd-ground`, run on a slice, on that ledger and inventory; `/brd-split` again, run on the same slice in `allocate-only` mode, on those grounding findings; `/brd-interview` on the findings, reading that second `/brd-split` run's fully-allocated ledger from the worktree (it refuses a single row still `unallocated`), and on the parent's defect log before the one resolution it may write there, for an `unsourced` defect a verified finding settles; `/brd-package` on the decision register; `/brd-reconcile` on the sent package, and on the parent's defect log the intake wrote, which it writes its defect resolutions into. Between `/brd-package` and `/brd-reconcile` the route leaves the plugin entirely: the customer reviews the bundle off-platform, with a vanilla agent and nothing installed, and the route resumes only when an operator hands `/brd-reconcile` the file that came back. The BRD route on `/create-prd`, `/create-ard` and `/specify` ships, so `/brd-reconcile` is where this route hands over rather than where it ends. **All three refuse a `BRD-` container** (D5), so the route never offers them against a root key: `/brd-reconcile` refuses a root at its own Phase 0 (`BRD_RECONCILE_ROOT_LEVEL`), and its next-step phase, on a run that left nothing to re-enter for, offers the three against the key of the **slice** it stands on — `/create-prd` only where, among the ledger rows the slice claims, none is still `unallocated` and at least one is `covered-here`, and `/create-ard` and `/specify` on the level test alone, since neither reads the ledger as an authoring input, and the PRD gate both of them run on every route reports an absent PRD rather than stopping on it. A slice whose questions were all settled from the findings needs no customer review, and `/brd-interview` hands it over on the same conditions.

## PA — product architecture

- **Owns:** architecture decisions for a PRD, or for one Epic inside it — an optional role in the pipeline; and, optionally, reviewing a grounding pull request `/prd-ground` opened.
- **Runs:** `/create-ard`, then `/harvest-decisions` once ARDs have merged, and `/promote-decisions` inside the architecture repository to propose organisation ADRs; and `/prd-ground`, a PM command, where the PM cannot clone the code repositories — the PA has them cloned (see PM above; a PE may run it too).
- **Consumes:** the PRD (and the Epic, when scoped), grounded on the mounted implementation repos it discovers under `$REPOS_PATH` — architect-driven discovery, never a pull-request read.
- **Produces:** **ard.md**, or **ard-\<area\>.md** for a big Epic split by area, written into the same specs feature folder as the PRD. `/harvest-decisions` keeps the team knowledge base under `$SPECS_PATH/architecture/` — one record per merged `[AD#N]`, which the next `/create-ard`, `/specify` and `/dev-workflows:design` ground on; and `/promote-decisions` proposes organisation ADRs in the architecture repository, recording the outcome on each record it promotes.
- **Hands over at the seam:** `/create-ard` gates on the PRD — an absent PRD falls back to reading the resolved folder directly instead of stopping (reported, not silent), and the hard stop is an unmerged PRD, never a missing one; `/create-ard` then lands the ARD the same way, and `/epics`, `/specify`, and the companion plugin's `/dev-workflows:design`, `/dev-workflows:implement`, and `/dev-workflows:ready` each consult it once it's there.
- **Cost phase(s):** `architecture` (`/create-ard`), role `pa`. A `/prd-ground` a PA runs for a PM is still role `pm`.

## PE — product engineering

- **Owns:** breaking a PRD into Epics, and writing an org-standard specification for one item — an Epic, or, for a small PRD, the whole PRD.
- **Runs:** `/epics`, `/specify`, `/update-spec` — which revises a merged specification in place, keeping its IDs — and, once every Epic has merged, `/dev-workflows:conformance <PRD-KEY>`, which closes the implementation phase those two opened — a `dev-workflows` command, so a PE installs that plugin too; and `/prd-ground`, a PM command, where the PM cannot clone the code repositories — the PE has them cloned, and with fewer PAs than PEs on most teams, a PE is often the one at hand (see PM above).
- **Consumes:** the PRD, plus the ARD when one exists and any Epics already drafted.
- **Produces:** one `EPIC-<PRD-KEY>-NN-<eslug>/epic.md` per Epic under the PRD folder, plus a PRD-holistic `_coverage.md` beside `prd.md`, landed on the specs repo's default branch; `specification.md`, landed the same way; and, from `/dev-workflows:conformance` on the PRD, `_conformance.md` with the PE's final decision on every discrepancy, the Dev's proposals included.
- **Hands over at the seam:** `/specify` gates on the PRD the same way `/create-ard` does — an absent PRD falls back to the resolved folder, and is reported rather than silent, and the hard stop is an unmerged PRD, never a missing one. `/epics` has no PRD gate at all, but it does gate two other inputs: an optional PRD-level `specification.md`, whose absence is a silent skip (`vi_spec_present: false`) — save on a multi-component PRD, where `/epics` asks for it — and the applicable ARD, where `status: unmerged` stops the run. `/epics` lands its Epic drafts on an `epics/` branch with a pull request, and `/specify` — like `/create-ard` at Epic altitude — stops while an Epic it reads sits there unmerged; an Epic on no branch is read from the folder as it stands, and reported. `/specify` lands `specification.md` onto the specs repo's default branch, and the companion plugin's `/dev-workflows:design` refuses to start until it finds that specification there.
- **Cost phase(s):** `epic-refinement` (`/epics`), `specification` (`/specify`, `/update-spec`) and `conformance` (`/dev-workflows:conformance` on a PRD) — all role `pe`.

## Where Dev picks up

This plugin's spine ends at `specification.md`, landed on the specs repo's default branch. The companion `dev-workflows` plugin's Dev role — `/dev-workflows:design`, `/dev-workflows:implement`, and `/dev-workflows:ready` — reads it from there, along with any ARD this plugin's PA role produced, and takes the pipeline the rest of the way to shipped code and product documentation. That role, its own cost phases (`planning`, `implementation`, `readiness` and `conformance` — the last on an Epic, since `/dev-workflows:conformance` on a PRD is the PE's — plus `documenting`, `docs-scaffold` and `docs-audit` for the companion `docs-workflows` plugin's `/docs-workflows:document`, `/docs-workflows:docs-init` and standalone `/docs-workflows:docs-brand`, and `/docs-workflows:docs-audit`, and `security-audit` for the companion `security-workflows` plugin's `/security-workflows:scan` of the Dev's own Epic), and why there is no separate verification role are documented on `dev-workflows`'s own Roles and phases page — this one covers only the three roles whose commands ship here.

## Cost-attribution phases

Every cost-emitting command tags its cost line with a `phase` and a `role`. Seven phases are reached by this plugin's fifteen cost-emitting commands; each entry below names the command that emits it and what being in that phase means. Eight more lifecycle phases exist for the companion `dev-workflows`, `docs-workflows` and `security-workflows` plugins' own commands — four, three and one respectively — and are documented on those plugins' own pages, not restated here; `workflows-core:cost-emission` §7 is the table that fixes every command's pair. Each of the seven below can also be reached **by inheritance**: the companion `workflows-core` plugin's `/workflows-core:prompt`, `/workflows-core:feedback`, `/workflows-core:prompt-brainstorm` and `/workflows-core:prompt-grill-me` adopt the phase and role of whatever they are correcting, so a correction to a `/specify` output is a second entry in `specification`.

### prd-creation

Emitted by `/idea` and `/create-prd`, role `pm`. From either, being in this phase means the PRD does not yet have a merged specification or design — the work underway is idea refinement or PRD authoring, and Epics may or may not exist yet. The companion `docs-workflows` plugin's `/docs-workflows:release-notes` also lands here, by inference, on a run where neither `specification.md` nor `design.md` exists under the PRD's specs directory. So does the companion `workflows-core` plugin's `/workflows-core:frames`, on a run whose resolved folder asserts `kind: prd` or `kind: epic` — an idea-route PRD folder, or any Epic folder, one under a BRD-route slice included — and there the phase marks product-definition spend and nothing about the folder's progress: a folder it indexes may already hold a merged specification or design.

### prd-update

Emitted by `/update-prd`, role `pm`. Being in this phase means an existing PRD is being refreshed or re-done, never created from scratch — the distinction cost aggregation needs between a first PRD write and a later revision.

### brd-to-prd

Emitted by `/brd-intake`, `/brd-split`, `/brd-interview`, `/brd-package` and `/brd-reconcile`, role `pm`, and by `/prd-ground`, role `pm` too, on either route it runs — whoever runs it; an entry written before product-workflows 3.31.0 reads `pa` and stays as recorded. On the BRD route, being in this phase means a customer-supplied BRD is somewhere on the BRD-to-PRD route — its requirement inventory is being extracted, split into slices, grounded against code and design, allocated, decided, packaged for customer review, or reconciled against the review that came back — whether or not a slice of it already holds its PRD, since a later round, package or reconciliation runs on such a slice all the same; every command on that route runs as PM, `/prd-ground` included, which a PA or PE runs instead where the PM cannot clone the code. `/prd-ground` tags this same phase on the idea route too, where there is no BRD in the folder's ancestry at all: an existing PRD's own `[AC#n]`/`[FR#n]` rows are being ground against code and design instead, optionally and ungated, after `/create-prd`. `/workflows-core:frames` also lands here, by inference, on a run whose resolved folder asserts `kind: brd` — a BRD container, or a BRD-route slice, though the slice is a `PRD-` folder — and there too the phase marks spend on that route and nothing about the folder's progress: a slice it indexes may already hold its PRD.

### architecture

Emitted by `/create-ard`, role `pa`. Being in this phase means architecture decisions are being recorded for a PRD or one of its Epics — an optional phase.

### specification

Emitted by `/specify` and `/update-spec`, role `pe`. Being in this phase means an org-standard `specification.md` is being authored for one item, lightly grounded in code, or a merged one revised in place.

### proposal

Emitted by `/prd-proposal` and `/brd-proposal`, role `pm`. Being in this phase means a requirement set is being **priced** rather than advanced — work packages, hours by role, and a range with its evidence — for a document a vendor sends a customer. It is the one phase here that no other phase waits on, and nothing it gates lies downstream of it: both commands gate their own input and nothing else — `/prd-proposal` waits on the folder's `prd.md`, which is the `prd-creation` phase behind it, and `/brd-proposal` waits on each included slice's `proposal.md`, which is this same phase gating its own earlier run. A proposal is optional at every readiness tier, and no command of the build ladder reads one. The one command that reads **another folder's** proposal as a proposal is `/brd-proposal`, which gates on each included slice's `proposal.md` in order to roll it into the programme umbrella — a second proposal rather than a phase of the build. Every other read is an own-folder one: a later run of `/brd-proposal` reads the umbrella it wrote last time to say whether it is still current and anchors its re-estimate on it, a later run of `/prd-proposal` does the same with the slice proposal it wrote, and `proposal-reviewer` opens the proposal it is handed inside the run that wrote it — reads, never gates. One read is neither, and is not a proposal read at all: `/brd-reconcile`'s stale-cross-reference sweep scans every markdown file under a parent BRD as prose, a proposal among them, and never edits one it hits — the hit goes to *what still needs a human*, because re-running `/prd-proposal` or `/brd-proposal` is the correction, and that run archives the prior revision and classifies each change it records as a correction or a re-estimate. One more is of the record alone: a sibling slice's run of `/prd-proposal` reads a proposal's `priced-against` record, and nothing else of it, at its next-step offer. It is its own phase rather than part of `brd-to-prd` because `/prd-proposal` runs on the idea route as readily as on the BRD route.

### epic-refinement

Emitted by `/epics`, role `pe`. Being in this phase means a PRD is being broken down into child Epic drafts.

---

**Plugin feedback** (`plugin-feedback`, role `n/a`) is the fallback phase for a `/workflows-core:prompt`/`/workflows-core:feedback`/`/workflows-core:prompt-brainstorm`/`/workflows-core:prompt-grill-me` run with no target command to inherit from, and the phase every `/workflows-core:diagnose-session` run is charged to — documented in full on the companion `workflows-core` plugin's own Roles and phases page, since none of this plugin's seventeen commands emits it directly.
