# Environment reference

[Getting started](../getting-started.md) says what each variable is *for* and what to export before your first run. This page says what each variable **is** — its default, where that default comes from, what happens when it is unset, and what happens when it points somewhere the plugin cannot read or write. The plugin reads four user-settable variables. A fifth, `GIT_USER_INITIALS`, is read on its behalf by the companion `workflows-core` plugin's branch-naming rules — for the branch `/promote-decisions` cuts in the architecture repository, and for your session branch where the specs repository takes no direct push — and is described in [Getting started](../getting-started.md) and on `workflows-core`'s own environment page. Claude Code also sets variables of its own for every plugin run; you never set those, and they are not listed here.

## `$SPECS_PATH`

- **`$SPECS_PATH`** — the shared, team-visible repository holding every PRD, ARD, specification, idea, and BRD folder these seventeen commands read and write, and the one place any of them commits its own session bookkeeping; required for every keyed run, with no built-in default.

**Resolution.** Read straight from the shell environment — there is no config file, CLI flag, or derived fallback that feeds it. Every git call against it is `git -C "$SPECS_PATH"`, never a `cd`, so your current working directory is untouched.

**When unset.** Every command that needs it stops naming `SPECS_PATH` explicitly — there is no fallback and no silent default, because a PM/PA/PE artifact has nowhere else to live. All but two then offer to enter a path or cancel, and take the path you type once it names an existing directory, asking again where it does not. `/harvest-decisions` and `/promote-decisions` stop and name the variable with no question: set it and run the command again.

**When it points somewhere unreadable.** The bookkeeping entry point, `specs-preflight`, requires an existing directory, a resolvable git dir, and a **writable** `.git`; a gate that fails on **writability** is a silent no-op (a read-only specs mount is a normal state here, and there is nothing to fix), while a gate that fails because `$SPECS_PATH` is not a directory or not a git repository at all emits a notice, one line naming the variable and the path — and, where the path is a `specifications/` directory mounted on its own, which of the two signals under *When it points inside the specs tree* below it matches, plus the stop's second line where it has one — because that state is never supported, and the notice keeps it from passing for the read-only one; and because the terminal `commit-artifacts` step applies the same writability gate, nothing gets committed either. The deliverable-verification gate, `require-on-main`, needs only a readable git dir, and where even that fails it verifies nothing. Most commands then go on without the check; two stop instead, because there is no default branch to read: `/update-spec`, which revises only a merged specification (`UPDATE_SPEC_NO_BASE`), and `/brd-reconcile` run with no `@<review-file>`, which has no merged state to find the customer's committed review in (`BRD_RECONCILE_NEEDS_REVIEW`).

**When it points inside the specs tree.** `$SPECS_PATH` must name the root of a dedicated specs repository — the directory that holds `specifications/` — never `specifications/` itself, nor a folder inside it. Two layouts are unsupported: a specs tree inside a larger repository, and a specs root that is itself a subdirectory named `specifications`. Pointed inside the tree, a run that resolves an address stops with `SPECS_PATH_INSIDE_TREE`, and any other run prints a `specs-preflight` notice and goes on — save on a checkout whose `.git` is read-only, where the preflight does nothing and prints none; a specs tree inside a larger repository draws a notice too, and either way the run commits nothing to the specs repository. To fix it, point `SPECS_PATH` at the root of a dedicated specs repository where the variable is set — the stop names the value to set, or the folders to move — and re-run.

- **A specs tree inside a larger repository** is unsupported because the plugin switches branches and commits in the repository `$SPECS_PATH` belongs to, which there would move the checkout of everything else that repository holds. A `$SPECS_PATH` below its repository's top level that the inside-tree check (below) does not stop draws a `specs-preflight` notice naming the top level, and the run goes on, treated as misplaced (below).
- **A specs root that is itself a subdirectory named `specifications`**, holding its tree at `specifications/specifications/`, is unsupported for detection rather than git: it cannot be told from the damage a misrooted run leaves (below), so it stops on every run. Set `SPECS_PATH` to the repository root and move the tree up a level, as the stop says.
- **The check.** Where `$SPECS_PATH` is set, every command that resolves an address — every command here but `/harvest-decisions` and `/promote-decisions` — first tests two signals, on a `<KEY>` and an `@<path>` address alike. An `@<path>` address is tested too, because a run that passed its own resolution on one would otherwise meet the same stop at a later lookup by key, of an ARD or a specification, after its expensive work.
- **The two signals.** `$SPECS_PATH` is, or is inside, a `specifications/` directory rather than a repository root; or it is, or directly holds, a specs folder — one whose artifacts assert a `key:` and a folder kind and whose name begins with that kind and key (for `$SPECS_PATH` itself, its physical name; a subfolder that is a link back into its own `specifications/` is skipped). So a root's templates, `README.md` or `docs/` never count, fresh or populated, and a specs repository nothing has been written into yet matches neither signal and is not stopped.
- **What neither signal sees** is a `$SPECS_PATH` outside any repository's top-level `specifications/` that is, or holds only, folders not named `<KIND>-<key>-`, such as a mount of a legacy unprefixed folder.
- **The stop.** Either signal stops the run with `SPECS_PATH_INSIDE_TREE` where it resolves its address, naming the variable, its value, the signal and the value to set: the directory that physically holds that `specifications/`, symlinks resolved, where it lies in the same git work tree, and otherwise *the directory that holds `specifications/`*. Where that directory is not its repository's top level, the stop adds that the layout is unsupported. It stops before any folder is searched or created, since every key would otherwise resolve to nothing, every command would report its folder not found, and `/idea`, `/create-prd` or `/brd-intake` would create theirs at `specifications/specifications/…`. There is no option to enter a path for the one run: fix the variable where it is set.
- **Stray specs folders.** Where `$SPECS_PATH` names the right directory — a repository's top level, or a directory in a repository holding `specifications/` — but holds stray specs folders beside `specifications/`, the stop says so, names every stray folder and `specifications/` as where they belong, and adds the unsupported-layout clause where that directory is below its repository's top level.
- **When nothing on disk can tell.** Where nothing on disk says whether `$SPECS_PATH` is a specs root or a specs tree under another name — a path that is no repository, or one below its repository's top level holding no `specifications/` — the stop states both readings and what each needs, and you choose. Under the specs-tree reading, the folders belong in a directory named `specifications/`, and the stop names that directory and tells you to set `SPECS_PATH` to its parent.
- **Damage an earlier run left.** Where `$SPECS_PATH` is the `specifications/` directory directly under a repository root or anything inside it, or is itself a specs folder, or holds specs folders directly, the run stops whether or not a nested `specifications/` exists. Where one does, or where misrooted runs left bookkeeping under `$SPECS_PATH`, the stop adds one more line naming each, where it belongs, and which of these applies to it. Move them yourself, commit the move, then re-run: the plugin moves nothing and gives no commands.
  - Feedback and pending cost under `dev-workflows-feedback/` and `dev-workflows-cost/` there are never committed.
  - A `documentation/<slug>/dev-workflows/` there, and the bookkeeping and any `implementation.md` in a nested `specifications/`, are not committed while the variable stays wrong, but the first run after it is fixed commits them in the wrong place unless they are moved first.
  - A nested `specifications/` left in place is also searched for keys once the variable is fixed, so a key whose folder only it holds resolves there.
- **A run that resolves no address** is not stopped: `specs-preflight` tests the same signals at run start — on a checkout whose `.git` is writable, and on a path that is not a git repository at all, such as a `specifications/` directory mounted on its own — and prints a notice naming the variable, its value, the signal and the value to set, with every addition the stop would make, then runs on. On a checkout whose `.git` is read-only the preflight does nothing, so no notice is printed there. `/idea` runs its preflight before it resolves its address, so it prints that notice first and then stops, both naming the same cause.
- **What a stopped or noticed run does.** A stopped run and a noticed one alike — the notice for a specs tree inside a larger repository included — treat `$SPECS_PATH` as misplaced for the rest of the run: cost, feedback and follow-ups stay in the printed output, no `resume.md` is written, and the specs-repository steps commit nothing, hand nothing off and switch no branch. Where `$SPECS_PATH` is a git repository with a writable `.git`, the preflight still fetches, and names any branch it stayed on where it would otherwise have switched. A stopped run writes nothing under `$SPECS_PATH`. A noticed run that goes on writes what the command itself writes — its deliverable, and any draft or record it keeps beside it, such as `implementation.md` — where the command puts it, and leaves it there uncommitted. That bound is the specs-repository steps' alone: a command that changes code or documentation still branches and commits in the repository it changed, and where that repository also holds the specs tree, its branch moves the specs checkout too, which is one more reason that layout is unsupported.

**When it changes under a resumed conversation.** Each run of `specs-preflight` first prints one line, `Environment: SPECS_PATH=<real path> (origin <url|none>), REPOS_PATH=<value|unset>`, and the conversation carries it wherever it is resumed. Before the run hands its deliverable off, and before each write of its tail — feedback, cost, follow-ups, `resume.md` — it compares the environment it now stands in with that line, and once more at its terminal commit where the record the run's start made stands — the file that start keeps under `~/.claude/dev-workflows/specs-git/`, which a run whose session id changed before its end does not find — comparing there only `$SPECS_PATH`'s real path and its `origin`, the one check a run that hands nothing off and writes nothing in its tail meets. Where they differ — a conversation resumed in another container, with `claude --resume` or a continuation — it prints `Environment changed: …` once, naming both, and from there commits, hands off and records nothing more in the specs repository, without asking: its bookkeeping stays in the printed output, and what it already wrote stays where it is. Re-run in the container the run started in. A deliverable a command writes before its handoff is not covered — it lands where `$SPECS_PATH` names at that moment — save on `/specify`, whose session file records the environment and is compared before that write too ([Resume and checkpoints](resume-and-checkpoints.md#resuming-from-a-session-file)).

## `$REPOS_PATH`

- **`$REPOS_PATH`** — where your mounted implementation and code clones live; defaults to `/workspace` when unset.

**Resolution.** `${REPOS_PATH:-/workspace}`, read fresh by each run that grounds against code — `/create-ard`'s mandatory repo discovery, `/idea`'s optional `--ground-code`, `/specify`'s light feasibility scan, `/update-spec`'s scan of the items it revises, `/epics`'s optional code scan, and `/prd-ground`'s pinned-commit grounding — and by `/brd-split`'s *Ground now*, which lists the clones once for the `/prd-ground` runs it starts. A `/prd-ground` run given `--repos-path` uses that value in its place. It may be a single directory or a colon-separated list; a repo is a top-level directory carrying a `.git` entry directly under it. `/create-ard`, `/specify` and `/epics` never ask for it while it resolves: each prints the value it resolved as `Repos: <value> (from REPOS_PATH | REPOS_PATH unset — the default)`, adding that another base is set through `REPOS_PATH` — or, for `/epics`, named at its plan's approval.

**When unset.** The `/workspace` default takes over without a question — safe, because this is only ever a read/scan base, so a wrong default never writes anywhere unexpected: one that is missing is asked about (next paragraph), and one that is empty finds nothing to scan.

**When it points somewhere unreadable or empty.** An unresolved repo slug or theme is escalated to the user rather than invented or silently dropped; a repo the user then declines is carried forward by name with its themes left unverified, never disappearing from the record. Where no entry of the resolved value is an existing directory, `/create-ard`, `/specify`, `/update-spec`, `/epics` (with code examination on) and `/prd-ground` ask you to set it, and take the path you then type once an entry of it is an existing directory. The first three also offer their own way on without code — `/create-ard` *Ground only the confirmed-mounted set (record the rest as open questions)*, `/specify` *Proceed without code scan*, `/epics` *Turn code scan off — produce Epic drafts from PRD content alone*; `/prd-ground`, which grounds nothing without a repository, offers only *Set REPOS_PATH* or *Cancel*, and `/brd-split`'s *Ground now* asks the same, its *Cancel* dropping that continuation rather than ending the run, and passes the path you type to each `/prd-ground` run it starts as `--repos-path`, so none of them asks again. `/create-ard`'s discovery is mandatory rather than opt-in, so a `$REPOS_PATH` that exists but is empty surfaces there as zero candidate directories to confirm, not as a stop.

## `$ARCHITECTURE_REPO_PATH`

- **`$ARCHITECTURE_REPO_PATH`** — a local clone of your organisation's architecture repository (technology radar, standards, principles, patterns, ADRs), read-only to grounding; no default.

**Resolution.** Resolved by the architecture-grounding gate the family shares, in `/create-ard`, `/specify` and `/update-spec` on both routes (and in `/dev-workflows:design`); `--no-arch` turns off, for a run, this repository and the two other sources architecture grounding reads: the team knowledge base and the security findings registers under `$SPECS_PATH/security/`. `/promote-decisions` uses it where the session's own repository is not the architecture repository, and writes there only when the clone is writable.

**When unset.** Architecture grounding reports `OFF` with a line naming the variable, and the run continues exactly as without it; the team knowledge base under `$SPECS_PATH/architecture/` is resolved separately, and still read where it exists.

**When it points somewhere invalid.** `OFF` with a reason naming the variable and what failed — never an error, never a gate or reviewer BLOCKER. Grounding never writes, fetches or pulls the clone; `/promote-decisions` is the one command that writes an architecture repository, proposing ADRs on a branch of their own.

**Directory layout.** Whatever the agent recognises: a catalog, a radar file, ADR folders, and standards, principles, patterns and reference-architecture folders.

## `$DOCS_PATH`

- **`$DOCS_PATH`** — your shipped product documentation's clone, read-only in its role as a docs-grounding root, which is the only role this plugin gives it; defaults to `/workspace/docs` when unset. (`docs-workflows`' docs commands also use it as a write target for a docs repository — a different role, not a contradiction.)

**Resolution.** Resolved by the docs-grounding gate the family shares, in every command here except `/brd-split`, `/brd-interview`, `/brd-package`, `/brd-reconcile`, `/prd-proposal`, `/brd-proposal`, `/harvest-decisions` and `/promote-decisions` (each of which resolves no docs grounding at all — for `/brd-split`, because it allocates requirements to a recorded fate, which documentation does not inform; for `/brd-interview`, `/brd-package` and `/brd-reconcile`, because they work on decisions already taken, on which a documentation page settles nothing; for `/prd-proposal` and `/brd-proposal`, because an estimate's inputs are the specs tree and the profile, while a documentation page bears on how a feature is described rather than on what it costs to build; for `/harvest-decisions`, because it runs a bundled script over the ARDs already on the default branch, with no authoring step for documentation to inform; for `/promote-decisions`, because it drafts organisation ADRs from team records and the architecture repository, which shipped documentation does not bear on). What it finds is used three ways: `/idea`, `/create-prd`, `/update-prd`, `/create-ard`, `/specify`, `/update-spec` and `/brd-intake` order what they ask you by it, `/epics` hands it to the agent writing its Epics, and `/prd-ground` uses it only to steer where to look and to record where a page diverges from what the code shows, never as evidence. Overridable with `--docs <path>`, which every one of the nine consumers here parses and strips together with its value before the address is read; turned off with `--no-docs` everywhere, and additionally by `--no-code` in `/prd-ground`.

**When unset.** The `/workspace/docs` default is probed; on a host where that path does not exist, the resolution simply reports `OFF` and the run continues.

**When it points somewhere unreadable.** Every miss — unset, missing, unreadable, or no markdown file found — is a **silent, non-blocking skip**, never an error and never a gate or reviewer BLOCKER. `product-workflows` never writes into `$DOCS_PATH` under any circumstance.

**Directory layout.** No expected substructure — whatever markdown sits under the root (for example, a full documentation-site checkout).
