# Resume and checkpoints

A long-running command ends by doing two separate things: it flushes a small pointer file to disk recording exactly where things stand, then it suggests — never performs — the right context action for what comes next, `/compact`, `/clear`, or a session `/rename`. Both are guidance only; the plugin never invokes any of those three itself. The point is to stop relying on you to remember to ask "am I ready to compact or clear" — the pipeline does the disk-flush itself and hands you the choice already framed. The mechanism itself is shared across the whole family; this page describes what `product-workflows`'s own commands do with it — fourteen of its sixteen, since `/harvest-decisions` and `/promote-decisions` use none of it: they write no pointer file and suggest no context action.

## What `resume.md` is for

`resume.md` exists so you can pick a run back up in a fresh session without re-deriving what the last one already established — what command ran last, what it produced, and what to run next — instead of scrolling back through a compacted or cleared transcript, or worse, re-reading every artifact from scratch to reconstruct where you left off. It is a **"last known position" pointer, overwritten every run, not an append log** — there is exactly one current answer to "where am I," not a history of every past one. It stays intentionally tiny:

```markdown
# Resume — <KEY>[ / <EPIC-KEY>] (<role>)

- **Last completed:** <command> <args> — <phase or 'command complete'> (<ISO datetime with its UTC offset>)
- **Artifact:** <relative path to the deliverable just written/committed, or 'none (read-only)'>
- **Next step:** <the exact next command from ### Next step, or 'PRD fully processed'>
- **Suggested session name:** <KEY>-<slug>-<role>   (omit this line on a run whose own `### Context hygiene` block carries no `/rename` suggestion — e.g. /create-prd, which writes the file and omits the line for its phase length and not for want of a key: it takes one as a mandatory argument)
- **Carry-forward decisions:** <0–N one-line items: the decisions the next phase needs that are NOT already in the artifact, and every item the pointer being overwritten carried that is not settled, by the one test the paragraph after this template gives — each of its carry-forward items, and each open item of its Next step that this run's Next step does not name, each such item that asks for a command to run ending `(waiting since <ISO datetime>)`, its waiting datetime; 'none' if none>
```

**Overwritten, but nothing open is dropped.** Before it writes, the run reads the pointer it is about to replace. There is one per PRD or BRD folder, written by every run of every Epic and every role under it — a slice keeps its own, as the PRD folder it is — so the old one can hold another Epic's or another role's open work — a pending ARD refine, a PRD update, a re-run, a push, the order pull requests should merge in — that this run's own next step does not need. Each such item is carried into the new pointer's `Carry-forward decisions` line, one line each, unless it is settled — and the test for that is one, `workflows-core`'s `session-hygiene` §1: the run settled it itself, or the check for what the item waits on, a read that fetches and writes nothing, shows every branch, command, question or path it names settled. An item that waits on more than one of these — a push and then its pull request's merge, say — is settled only once each of its checks shows it settled, and one naming a pull request waits on that pull request's merge. An item waiting on a merge — of a branch, or of the pull request it names — is settled by the merged check alone, never by a push: in the specs repository, by the same merge test the run-start preflight uses, which sees a merge, a rebase and a squash, asked of the branch's remote ref where it still has one and its local ref otherwise, or by that preflight having found the branch merged; in a code repository, by ancestry in the refs the run holds, or by a merged test the run already made on it. An item asking for a push is settled once the branch is pushed; one asking for a follow-up, once its line is ticked; one asking for a command to run, once a record that command writes as the item asks it to run — in the item's own mode and role, and in or for the repository the item names where it names one — is later than the item's waiting datetime (the datetime it waits from: the one its line ends with as `(waiting since <ISO datetime>)`, or, for an item of the old pointer's *Next step* or one whose line ends with none — an older pointer's, say — the old pointer's *Last completed* datetime): in the folder the item names, an `implementation.md` block, a `_conformance.md` entry or a `_security.md` block whose `kind` and role are the item's and whose `repo` is the item's where it names one; for `/product-workflows:prd-ground`, a run's dated heading in `grounding/baselines.md` or `grounding/design-grounding.md`, files only that command writes a heading into — `/product-workflows:update-prd`, `/product-workflows:create-ard` and `/product-workflows:specify` write only `consumed_by`, inside a finding's block, never a heading — a `baselines.md` one, which every run but `--no-code` writes, for an item asking for a run that grounds code, and a `design-grounding.md` one, which every run writes, for an item asking for `--no-code`, neither settling an item asking for `--rebaseline`, a run they do not tell from another, nor, while `design-grounding.md`'s `## Frame sets covered` section, which each run rewrites, records a set `skipped: --no-design`, one that does not ask for `--no-design`; for `/dev-workflows:ready`, `_readiness.md`'s heading, `# Readiness check — <run timestamp, ISO 8601 UTC>`, which only that command writes, overwriting the file on each run; and, for `/security-workflows:scan`, a run record under `security/<repo-slug>/runs/`, written where the run changed the register, whose `kind` and `role` are those `security-register-format` §2 gives the run the item asks for — `kind` `verify` for `--verify-fixes`, `triage` for `--triage`, `import` for `--import` and `scan` for a scan, and `role` `dev` for a key run without `--triage` or `--verify-fixes` and `sec` otherwise — so no run of another mode or role settles it, with, on a repository path, `<repo-slug>` the register's slug the item names beside the path, kept with it by every run that carries it, read from the item and never derived from the path on a machine where the path is not that repository, and, on a key, a record whose `unit` is that key, in the register of the repository the item names or, where it names none, in any — the only record a `--triage` on a key leaves, since a run appends to `_security.md` only where it recorded a scan — a record that holds no mode or role of its own being of the mode and role its command and its folder fix, and each record dated by the datetime it records, `_readiness.md`'s compared with the waiting datetime directly — a waiting datetime written with no UTC offset, an older pointer's, read as UTC, and one with no time as the end of its UTC day, either reading erring to carrying wherever it is no earlier than the pointer was written — save that a block of an append-only record — `implementation.md`'s or `_security.md`'s, or a run's in `grounding/baselines.md` or `grounding/design-grounding.md` — records a day alone, and is dated by its heading's own day first (one whose day is earlier than the waiting datetime's day, in UTC, is never later, and one whose day is later always is, whatever commit carried it; only a block of that same day is dated by the commit that added its heading line, the commit `git -C "$SPECS_PATH" blame -L <n>,<n> --porcelain -- <file>` names for heading line `<n>`, at that commit's `author-time`, which a rebase keeps where it moves the committer time, never the file's last commit, which a later block of another repository, mode or role moves too, and a same-day block whose heading line blame names no commit for, or the all-zero commit, dates nothing — one in a file the branch the checkout stands on does not track, one not yet committed, or, in `specs-repo-git` §8's session-branch mode, one committed on the session branch and not yet on the branch the checkout stands on), a `_conformance.md` is dated as a block of an append-only record is, its `Run:` line standing for the heading line (by that line's day first and, on that same day, by the commit blame names for it), and a same-day block or `Run:` line whose blamed commit's `author-time` falls on a later UTC day than the line's own day dates nothing either, since a run commits the record it writes on the day it writes it, so a later day's commit is a re-write or a late one — a squash, a later run's flush — and a run that spans midnight UTC, committing its record on the next day, or one whose heading or `Run:` line carries a local date behind UTC, dates nothing by the same rule, which errs to carrying, the command check settling nothing wherever it cannot tell who wrote what it reads, or when, so the item is carried, never dropped; a decision, a fact or an open question, once a deliverable the next phase reads at the folder's top level records it (`prd.md`, `ard.md`, `epic.md`, `specification.md`, `design.md`, a `decisions.md` register or a `_*.md` record — never the pointer itself or a session file); and one asking for a path inside a repository the item names with it to be removed, or to be written or committed, once the path is absent from, or present at, that repository's default branch — the same answer on every machine. A path an item names for any other reason — a command's argument (the `<repo-path>` of `/security-workflows:scan`'s Security Engineer offers among them), the deliverable a merge carries, a file a decision is about — is settled with its item, by the check for what the item waits on, and an item naming a worktree that `/security-workflows:scan` 0.2.0 or older failed to remove, the line that version's resume-pointer step wrote into *Carry-forward decisions*, is settled at once, as one the pointer never carries. A settled item is dropped; the run that settled one may keep a line saying so, which the next run drops. An item not settled — by the run or by the check for what it waits on — is carried, and one a file the next run reads already records, such as `follow-ups.md`, stays as one line naming that file. An item that waits on a pull request names its branch and repository, so a later run can make the merged check, and an item that asks for a path to be removed, written or committed names the repository it lies in. An item that asks for a command to run is carried with its line ending `(waiting since <ISO datetime>)`, its waiting datetime copied as the old pointer writes it, and every run that carries the item keeps that datetime, never replacing it with the run's own *Last completed* datetime, so a record that reaches the checkout only after a later run wrote its pointer — pushed from another clone while a run that carried the item was under way, held on another session branch until its pull request merged, or kept local by a rejected push until it was pushed — still settles the item; the datetime is all the marker adds to the item's one line, naming no path and nothing the redaction below removes. A path outside every repository the pointer's readers share — a scratch worktree, a temporary directory — is never written into the pointer, since the pointer is shared while such a path belongs to one machine, so its absence on one cannot be told from its removal on another; a run that leaves one names it in its final report and its feedback instead. These stay longer than they need: a code repository's branch merged by a squash or a rebase, until a run applies `implementation-format` §5's merged test to it — a run of the Epic the branch belongs to, or `/dev-workflows:conformance <PRD>`; a branch or a path in a repository the run holds no ref for, or only refs older than the merge, the removal or the write — a code repository the run did not open or did not fetch, or a branch never fetched here — until a run holding current refs settles it; a specs-repository branch with neither its local nor its `origin/` ref left — deleted and pruned before any run that wrote a pointer here saw it merged — which, without a fetch, cannot be told from a branch never fetched here, so it stays carried; an item asking for `/security-workflows:scan` whose run changed nothing in the register, and so wrote no run record, or whose scan a run of another mode recorded — an `--import` of its report, say — until a run of the item's own mode and role records and so settles it, for good where none can, as no change scan records once `unit-branch` reads its Epic's branch merged with no work after it; an item only a block of `implementation.md` or `_security.md` of its waiting datetime's own day can settle, in `specs-repo-git` §8's session-branch mode, until the session branch's pull request merges — by a merge or a rebase, or by a squash on the block's own day — and the block reaches the branch the checkout stands on; an item only a day-dated block or `Run:` line can settle whose commit falls on a later UTC day than the line's own day — a pull request a squash merged on a later day, a later run's flush, a run past midnight UTC, a heading written in a local date behind UTC — until a record of a later day settles it, or a run of the item's command writing this pointer settles it itself, and for good where that command writes another folder's pointer and nothing runs it again: `/product-workflows:prd-ground <CHILD-KEY>` in a root BRD's pointer after a *Ground now* whose pull request a squash merged on a later day; an item asking for a command that leaves none of the records this check reads — one whose only record is its deliverable, a whole file the check does not read: most name no date of their own, and other commands commit into several — or asking for one in a mode those records do not tell — `/product-workflows:prd-ground`'s `--rebaseline`, or a run of it that grounds design while `design-grounding.md`'s `## Frame sets covered` records a set `skipped: --no-design` — until a run of that command writing this pointer settles it itself, so one whose command ran on another clone without this pointer in front of it stays until then, and for good where that command writes another folder's pointer or none: `/product-workflows:brd-proposal` in a slice's pointer and `/product-workflows:prd-proposal` in its root's or a sibling's, whose `priced-against` record names each input's content and no time, and `/workflows-core:frames`, which writes none; an item asking for `/security-workflows:scan` on a repository path with no register slug beside it — a Security Engineer offer an older `/security-workflows:scan` wrote, say — until a run on a machine where that path is that repository, a repository with an `origin` that `git -C <path> rev-parse --show-toplevel` names, settles it by the command check, with the slug it derives there as `/security-workflows:scan` does (`workflows-core`'s `components` §1), every other run carrying it; and an item an older pointer wrote naming a pull request by its number alone, until a run settles it. One can leave sooner than it should: blame names the commit that put a line on the branch the checkout stands on, so a block or a `_conformance.md` of an item's waiting datetime's own day that a later commit of that same day carried — a squash merge, a hand commit of a handoff its run declined, a later run's flush — is dated by that commit and can settle the item though it was written before that datetime; and so can a block whose heading, or a `_conformance.md` whose `Run:` line, carries a local date ahead of UTC, written between local midnight and UTC midnight: its day is later than the UTC day it was written on, so the day-first rule reads it as later than a waiting datetime of that UTC day that came after it; and an item whose waiting datetime an older pointer wrote in a local time behind UTC with no offset, or as a date alone written behind UTC after UTC midnight, can leave sooner too, since that datetime is read as UTC, or as the end of its UTC day, and so as earlier than it was. That, and one line per item, is what keeps the file tiny.

Any secret, credential, token, or other sensitive value that might otherwise land in the `Carry-forward decisions` line is redacted before writing — a resume pointer records what to do next, never a value worth protecting.

**When it's written.** The write is unconditional for any PRD-scoped run, save one carrying `specs_git: misrooted` (a `$SPECS_PATH` the run found misplaced), and it happens first — before the terminal `commit-artifacts` step, but only after the deliverable artifact is already saved or committed, and after the feedback, follow-ups and cost phases have all run. The canonical terminal order is deliverable and handoff, then feedback, then follow-ups, then cost, then `resume.md`, then `commit-artifacts`. Whether the suggestion (below) actually fires or not, the write itself always happens — **prepare always, suggest adaptively.**

**Where it lands.** Three tiers, walked in order: `$SPECS_PATH` writable with the PRD directory matched → `<PRD-dir>/dev-workflows/resume.md` — a fixed, family-wide folder name shared with the cost and feedback files described elsewhere in this reference section, not a `product-workflows`-specific path — the primary case; `$SPECS_PATH` writable but **no PRD directory matched** → the file is skipped outright and the run relies on the printed `### Next step` instead; and `$SPECS_PATH` not writable → skipped, with a one-line warning that no resume pointer could be persisted and you should set it.

**Which runs skip it entirely.** `/idea` does resolve a PRD folder, but its brief is handed off in the same run rather than resumed later, so a pointer would only go stale.

## The suggestion: `/compact` or `/clear`

Every next-step option a command offers already carries a role label — see [Roles and phases](../roles-and-phases.md) for what PM, PA, and PE each own. The context-hygiene suggestion reads those same labels rather than hardcoding a per-command verdict:

- **Staying in the same role** for the next step (`/create-prd` → PM `/update-prd`, or `/brd-intake` → `/brd-split`, both PM) → **`/compact`** — the context is still relevant, so keep the thread going.
- **Moving to a different role** (`/epics` PE → `/create-ard` PA, or `/create-prd` PM → the companion plugin's `/dev-workflows:design` Dev) → **`/clear`** is the better default when one person is wearing both hats, since the prior role's reasoning becomes noise for the next one; `/compact` still works fine if you're continuing right away yourself.
- **The next step could go either way** (`/create-prd` → PM `/docs-workflows:release-notes`, or handing off to PA/PE) → both branches are named explicitly: continuing as the same role suggests `/compact`, handing off — even to yourself — suggests `/clear`.
- **You're done, or ending the session** → no suggestion at all.

`/prd-ground` runs as PM like every other command on this route, even where a PA or PE runs it for a PM who cannot clone the code: the suggestion follows the *next* command's role, exactly as every other transition does. So `/brd-split` on a root → `/prd-ground` on a child, and `/prd-ground` → `/brd-split` on that slice, are both PM to PM → **`/compact`**; only a PA or PE who grounded for a PM hands the next step to someone else's fresh session.

## The `/rename` aid

The commands that print a suggested `/rename <KEY>-<slug>-<role>` line are the PA/PE/Dev ladder — `/create-ard`, `/epics`, `/specify` here, and the companion plugins' `/dev-workflows:design`, `/dev-workflows:ready`, `/dev-workflows:implement`, `/docs-workflows:document`, and `/docs-workflows:release-notes` — plus this plugin's two PM effort-proposal commands, `/prd-proposal` and `/brd-proposal`, whose suggested name is keyed on the folder they priced. The line lets you find this session again later in `claude --resume` by name instead of by scrolling. `<KEY>` is the key that named the folder the run resolved — a PRD key on the ladder, the root BRD key for `/brd-proposal` — and `<role>` is the lane tag of the command that just finished: pm, pa, or pe here. **That set is not "every command that takes a `<PRD>` or `<EPIC>`"**: `/dev-workflows:implement` in direct mode takes no address and `/docs-workflows:document` in doc-edit mode takes none either, and neither of those modes writes a pointer at all. `/idea` and `/create-prd` are excluded, and the reason is the phase rather than the key: each takes a mandatory key as its first argument and refuses without one, so a PM run always has a key it could name the session after — but the ideation phase is short enough that naming the session isn't worth automatically suggesting. `/update-prd` and every command of the BRD-to-PRD route print none either, `/brd-reconcile` included: a BRD key exists from the first command, so this is never a want of a key, and no route command states a reason of its own — the resume pointer's omit-condition reads each run's own context-hygiene block rather than a list, so none is needed.

## Mid-phase checkpoints

None of `product-workflows`'s sixteen commands carries a mid-phase checkpoint — each authoring or grounding run finishes in one pass and reaches the end-of-run write described above.

## The contract

Five rules bound everything above: it is **guidance-only** — `/compact`, `/clear`, and `/rename` are always suggested, never invoked by the plugin itself; the disk flush is **prepare-first** — unconditional for a PRD-scoped run, save one carrying `specs_git: misrooted`, and always ahead of the suggestion it accompanies, so acting on the printed suggestion is always safe; the compact-versus-clear split is **role-aware through a single graph**, reading role labels from the next-step offer rather than duplicating that graph here; the whole mechanism is **mode-aware**, degrading to a plain optional `/compact` note (or nothing at all) on a run that writes no pointer — for one of two reasons: either there is no PRD anchor to write one against, or there is one and the run is not a phase a later run resumes, which is `/idea`'s case; and it **never blocks** — the guidance is a nudge appended to the end of the Final Report, exactly like the next-phase offer it sits beside.

The full mechanics — the exact `resume.md` write procedure, the redaction rule, and the `### Context hygiene` block's own shape — live in `workflows-core:session-hygiene`, which this page describes from `product-workflows`'s side rather than restates.
