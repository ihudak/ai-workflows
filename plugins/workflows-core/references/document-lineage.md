# Document lineage (shared reference)

Single source of truth for the **lineage record** — which version of each upstream document a document in the specs repository was built from — and for the check a consumer runs on it before it builds on that document. A PRD is built from its idea, or on the BRD route from its slice's decision register; the register from the slice's grounding files and inventory; a grounding file from the slice inventory on the BRD route and from the PRD on the idea route; an ARD from its PRD (and, on an Epic, the Epic's `epic.md` and the PRD's ARD); a specification from a PRD, its ARDs, its grounding files, on the BRD route its decision register and, on an Epic, its `epic.md`; a design from a specification. When an upstream is revised after a downstream was built from it, the next command that reads the downstream would build on a stale chain without a word. The record and the check close that gap: the record names the exact bytes each upstream had when the downstream's run read it, and the check walks the chain and **asks** when one of them moved. It never stops a run on its own account.

`scripts/lineage.py` does every read, write and comparison, called as `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/lineage.py" <subcommand> …` — `${CLAUDE_PLUGIN_ROOT}` being `workflows-core`, whose file this is, as for `scripts/session-branch.py` in `workflows-core:specs-repo-git`. Its kind table is `scripts/lineage-kinds.json` beside it (§4). Each subcommand prints one JSON object and exits `0`; any other exit is a failure, reported with the first line of its stderr (§5, §6). It is tested in CI by `python3 plugins/workflows-core/scripts/lineage.py --selftest`.

Callers: `/product-workflows:create-prd`, `/product-workflows:update-prd`, `/product-workflows:prd-ground`, `/product-workflows:brd-interview`, `/product-workflows:brd-reconcile`, `/product-workflows:create-ard`, `/product-workflows:specify`, `/product-workflows:epics`, `/product-workflows:update-spec`, `/dev-workflows:design`, `/dev-workflows:implement`, `/dev-workflows:conformance`, `/dev-workflows:ready`, `/docs-workflows:document` (keyed mode) and `/docs-workflows:release-notes` — `grep -l 'document-lineage' plugins/*/commands/*.md` lists them. `/update-prd` records (§5) and never asks; `/create-prd` records, and checks and asks on the BRD route only, where it builds on the decision register; `/prd-ground` records, and checks and asks on the idea route only, where it builds on `prd.md`; `/ready`, `/document` and `/release-notes` check, never ask and record nothing (§6 step 6); the rest check and ask (§6), and those among them that write a document of a covered kind record it too — save `/brd-reconcile`, which keeps the decision register's record as `/brd-interview` wrote it, and `/brd-interview` itself on a run that only resumes or re-opens a round.

## 1. The record

Two frontmatter keys on the downstream document, written only by the script:

```yaml
upstreams:
  - path: specifications/PRD-0042-checkout/prd.md   # relative to $SPECS_PATH
    blob: <40-hex git blob id of the bytes the run read>
    version: null                                    # the upstream's Version, or null where its kind has none
accepted:                                            # written only by a "Proceed" answer (§6)
  - path: specifications/PRD-0042-checkout/prd.md
    blob: <the blob the operator accepted>
```

- **`upstreams:`** lists every input the producing run read, save one below its own output in the chain (§4), each by the path it was read at. The blob is captured **when the run reads the input**, never when it writes its output, so an input that moved mid-run reads as moved. It is the git blob id **of the bytes the run actually read**: the default branch's blob for an input gated on it, and `git hash-object` of the working-tree bytes for one read from disk — a grounding file, which nothing gates; an `epic.md` `require-on-main` reported `absent`; a copy the run went on with as `pass_amending` or `unmanaged`. A blob id rather than a `Version` because a hand edit that forgets to bump `Version` still changes the bytes, as `/product-workflows:prd-proposal`'s `priced-against` record hashes them.
- **An empty record is a record.** A producer that read no input under `$SPECS_PATH` — `/product-workflows:create-prd` with no idea, or with one read from outside the specs repository — writes `upstreams: []`: the document has a record, with nothing above it, and is never reported as missing one (§3).
- **`accepted:`** lists what the operator accepted on this document's behalf (§6): an upstream at its then-current blob, or an unrecorded document at its blob. A later move of that upstream — a different blob — asks again.
- **A consumer whose output is not a document of a covered kind keeps `accepted:` alone.** `_conformance.md` carries it in its frontmatter, with no `upstreams:`. `implementation.md` carries it **inside the run's own block** (`workflows-core:implementation-format` §1), never in a frontmatter, because `workflows-core:specs-repo-git` settles that file as a set of blocks and refuses a header the two sides changed differently; a check reads the acceptances of every block, so an earlier run's stay honoured without being copied forward.
- **A document with no frontmatter** — the decision register, a grounding file — gets one holding these blocks alone, put above its first line; the rest of the file is kept byte for byte.
- **Every other frontmatter key is kept**, in place and byte for byte: the script rewrites these two blocks and nothing else, where the first of them stood and in the frontmatter's own line ending (CRLF or LF). A comment line inside either block, or after a value, is read past and not kept: the blocks are the script's.
- **A rewrite of the document by its own command re-stamps `upstreams:`** and carries forward each `accepted:` entry whose blob is still that path's blob on the default branch, dropping the rest.

## 2. When an upstream counts as moved

The current copy of an upstream is read from the default branch (`<default-ref>`, as `specs-preflight` resolved it).

1. **Same blob as recorded** → not moved.
2. **A different blob** → the script reads the recorded copy by its blob id (`git cat-file -p`) and compares **live items** by key, per the upstream's row in the kind table (§4). No live item added, changed or withdrawn → **not moved**: a note another command wrote (`/dev-workflows:design`'s `## Engineering review`, an open question ticked, an `Engineering proposal (/design):` answer), a header count or whitespace never asks. Otherwise it moved, and the keys that changed are what the operator sees.
3. **Item keys** are an item's full ID path where its IDs restart under a parent — a specification's `[U02]/[AC01]/[TC03]`, since AC and TC numbers restart per story and per criterion (`product-workflows:specification-format`) — and its own ID where they do not (`[US#2]`, `[AD#3]`). Text outside every item is compared per `## ` section, keyed `§<heading>`; a kind with no item IDs is compared that way alone. A section the kind row drops — a grounding file's `## Documentation divergences` and `## Frame sets covered` — has its own text left out, though a finding written inside one is still read as a finding; a field the row ignores — a finding's `outcome` and `notes`, the verifier's bookkeeping — is left out of its item, with its continuation lines.
4. **A superseded or withdrawn item whose marker sits on its own heading** — a specification's (` — Superseded by`, ` — Withdrawn`) — is reported once, as withdrawn, and the items nested under it are not reported again. A kind that marks it on a line of its own under the heading — a PRD's or an ARD's `**Superseded by:**` — has that item reported as changed.
5. **The recorded blob is not in the clone** — a shallow clone, rewritten history, or working-tree bytes that were never committed → reported as moved, with *recorded copy unavailable — cannot list items*.
6. **The upstream is absent from `<default-ref>`** → reported as absent, never as moved: the gate that reads that upstream owns that state, and a caller with no such gate reports it as a note (§6 step 6).

**A grounding re-run is not a move.** Every `/product-workflows:prd-ground` run that grounds code mints a fresh baseline finding per repository and supersedes the last (`workflows-core:grounding-format` §4.1), re-verifies every finding and writes that run's `outcome` onto it, and rewrites `## Frame sets covered`. None of that asks: the comparison leaves out every item `grounding/baselines.md` beside the file names by its `finding:` id — read at `<default-ref>`; missing or unreadable, it names none, and a legacy entry carrying no id adds nothing — the two dropped sections and the two ignored fields (step 3). Nothing downstream draws from a baseline finding (§4.1 rule 3). What a finding asserts — its claim, verdict, evidence, altitude, horizon, commit — still counts, and a contradiction counts through the finding it retires and the successor appended after it.

**The altitude filter, per link.** Where the downstream's kind consumes one altitude (§4 — a `prd.md` `product`, an ARD `architecture`, a `specification.md` `implementation`) and the upstream's records carry an `altitude:` field (the decision register, a grounding file), step 2 compares only the records at the downstream's altitude: a record whose every live copy carries another altitude is left out, and a record carrying none, a record whose altitude moved into or out of the downstream's, and text outside every record still count — save a section the kind row gives an altitude: a grounding file's `## Derivation matrix` is `implementation` (`workflows-core:grounding-format` §7), so a specification sees a change in it and an ARD does not. A decision taken at another altitude never asks. The filter applies to one link at a time and never along the walk: the register and the grounding consume no single altitude, so their own links compare every record, and a register behind its grounding is reported to every consumer that walks through it — a product decision can rest on an implementation finding through its `evidence`, and that is a fact about the register, settled by revising it. A product decision's change still reaches a specification, through its PRD reading as stale.

## 3. A missing record, and the coverage boundary

- **A document of a covered kind (§4) with no `upstreams:` key** is reported as having no lineage record: whether its upstreams moved cannot be told. It asks once (§6); *Proceed* records an `accepted:` entry for that document at its current blob, so the same consumer is not asked again until it changes. This is the path every document written before its producer recorded one takes — a decision register, grounding file or BRD-route `prd.md` written before product-workflows 3.72.0 among them.
- **The walk follows a document's record only where its kind is covered.** A document of an uncovered kind is a **top** of the walk: it is compared as an upstream — blob and items — but its own record is never looked for, and its lack of one never asks.

## 4. The kind table

`scripts/lineage-kinds.json` is the table, and the script reads nothing else to tell kinds apart: a new kind is one row there. Each row names its files (by basename), whether it is **covered**, the command that **revises** it when it is the stale downstream, whether its header carries a `Version`, its item patterns, the sections excluded as notes, the lines ignored, the item fields ignored, the sections dropped or given an altitude, a file beside the document naming items to skip, and where each was measured (`_source`). Summarised:

| Kind | Files | Items | Excluded | Reviser | Covered | Altitude |
|---|---|---|---|---|---|---|
| specification | `specification.md` | `[Uxx]` › `[ACxx]` › `[TCxx]` | `## Engineering review`, every `Open questions` heading's section, `- [ ]`/`- [x]` lines, `Engineering proposal (/design):` lines, the `Version` and `Open questions` header lines | `/product-workflows:update-spec` | yes | consumes `implementation` |
| epic | `epic.md` | none — per section | `## Engineering review`, `- [ ]`/`- [x]` lines | `/product-workflows:epics` | yes | — |
| design | `design.md` | none — per section | `## Engineering review`, `- [ ]`/`- [x]` lines, the `Version` and `Open questions` header lines | `/dev-workflows:design` | yes | — |
| prd | `prd.md` | `[US#n]`, `[AC#n]`, `[SM#n]`, `[SMC#n]`, `[UC#n]`, `[FR#n]` | `## Engineering review`, `- [ ]`/`- [x]` lines | `/product-workflows:update-prd` | yes | consumes `product` |
| ard | `ard.md`, `ard-<area>.md` | `[AD#n]` | `## Engineering review`, `- [ ]`/`- [x]` lines | `/product-workflows:create-ard` | yes | consumes `architecture` |
| grounding | `code-grounding.md`, `design-grounding.md` | `[CG#n]`, `[DG#n]` | `consumed_by:` lines; `outcome` and `notes` fields; `## Documentation divergences` and `## Frame sets covered` text; baseline findings, by `baselines.md` | `/product-workflows:prd-ground` | yes | each record's `altitude:`; `## Derivation matrix` `implementation` |
| decisions | `decisions.md` | `[VD#n]`, `[CD#n]`, `[AS#n]` | `consumed_by:` lines | `/product-workflows:brd-interview` | yes | each record's `altitude:` |
| inventory | `brd-inventory.md` | `[BR#n]` rows | — | — | no | — |
| idea | `idea.md` | none — per section | — | — | no | — |

**The chain, top to bottom, depends on the route.** On the BRD route: the slice inventory → the grounding files → the decision register → `prd.md` → the PRD's ARDs → the PRD-level `specification.md` → `epic.md` → the Epic's ARDs → the Epic's `specification.md` → `design.md`. On the idea route: the idea → `prd.md` → the grounding files → the PRD's ARDs → and on as above. A grounding file sits above the register on the BRD route, where `/product-workflows:prd-ground` grounds the inventory's `[BR#n]` rows, and below `prd.md` on the idea route, where it grounds the PRD's own requirements. **A producer never records a document below its own output**, even one it reads: `/product-workflows:update-prd` reading the ARD, the specification or a grounding file as secondary grounding, `/product-workflows:create-ard` reading an Epic's `specification.md` or `design.md`. That document already records this one, and a record each way would make every revision of either leave the other stale — a chain that never settles. It is read as context, and nothing more. (`/update-prd` records no grounding file on the BRD route either: there the PRD is built from the register, which records the grounding itself.)

**A producer records only what belongs to the document it writes**: its own folder's documents, the PRD folder's above an Epic folder, and a seed `--sort-existing` left in a slice's parent for its slices (`prd-seed.md`, `ard-seed.md`), which is the slice's input wherever it was read and an uncovered top at which the walk stops. A BRD-route command reads more — a prerequisite BRD's register, the parent's inventory and defect log, its siblings' coverage ledgers — as context, and records none of them: a record into another BRD's tree would carry the walk there, and every prerequisite decision or sibling re-cut would read as a move of this slice.

A file matching no row is compared as plain text, whitespace collapsed. Only `specification.md` and `design.md` carry a `Version`; every other kind is shown by its short blob id (§6). **Altitude** is §2's filter: a downstream row's `altitude` is the one it consumes, and an upstream row's `item_altitude` reads a record's `altitude:` field — only at the column of that record's own `id:` key, so a line inside a block value is never taken for it.

## 5. `record` — the producer entry point

Executed by a command that writes a document of a covered kind, in two steps.

1. **When the run reads its inputs**, capture them, before reading any of them:
   `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/lineage.py" capture --specs "$SPECS_PATH" --ref <default-ref> --from-ref <path>… --from-disk <path>… --out <capture-file>`
   — every path relative to `$SPECS_PATH`; `--from-disk` for each input the run reads from the working tree, which is how the family's commands read their inputs, and `--from-ref` only for one it reads from `<default-ref>` itself (`git show <default-ref>:<path>`). Either way the blob is that of the bytes read (§1): a working-tree copy equal to the default branch's has the default branch's blob. `<capture-file>` is a file the run creates where `workflows-core:run-flags` puts its temporary files. **A run that writes into one of its own inputs** before it writes its output — `/product-workflows:create-prd` on the BRD route appending a roundless `[AS#n]` to the decision register — takes its capture after its last write there instead, so the output never reads as stale against its own run's write.
2. **After the run writes each document**, and before its handoff stages it, stamp it:
   `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/lineage.py" stamp --specs "$SPECS_PATH" --ref <default-ref> --doc <the document's absolute path> --capture <capture-file>`
   — then, wherever the run executed `upstream-check` (§6) and went on past it, accept into it:
   `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/lineage.py" accept --doc <the document's absolute path> --check <check-file>`
   — which writes each link the operator accepted this run and each one an earlier run had accepted (the check JSON's `accepted`), so a document its command rewrote from scratch keeps them.

**Any non-zero exit stops the run** with `<COMMAND>_LINEAGE_FAILED: <the first line of the script's stderr>`, `<COMMAND>` being the calling command's error prefix, before it writes anything further: a document stamped wrongly or not at all would hide a stale chain from every later run.

## 6. `upstream-check` — the consumer entry point

Executed by a command after its own gates have passed the documents it reads (`workflows-core:phase-handoff` `require-on-main`, §3) — a caller with no such gate is step 6's — before its first agent dispatch or other expensive work. The caller supplies `docs` — the documents of a covered kind it is about to build on, relative to `$SPECS_PATH` — and `output`, its own existing output document where one is on disk (the one a re-run rewrites), else none.

1. **Check:** `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/lineage.py" check --specs "$SPECS_PATH" --ref <default-ref> [--output <output's absolute path>] [--accepted-from <absolute path>]… --out <check-file> <docs…>`. A non-zero exit stops the run with `<COMMAND>_LINEAGE_FAILED`, as in §5. The check walks from each document up its recorded `upstreams:` and on through every covered upstream's own record, to the top of the covered chain (§3), and reports every stale link it meets — not only the documents' direct ones.
2. **Nothing stale and nothing missing** — the JSON's `stale` and `missing` are both empty → say nothing more; the Final report carries `Lineage: current` (§7). An `accepted` entry is a link `output` already accepted: it is not asked again, and `record` step 2 writes it into the new output.
3. **Otherwise show one block**, then ask. One line per stale link: `<downstream> ← <upstream> <recorded> → <current>: changed <keys>; new <keys>; withdrawn <keys>` — `<recorded>` and `<current>` being the `Version` where the upstream's kind carries one, else the first seven characters of each blob, and an empty kind of change left out; *recorded copy unavailable — cannot list items* in place of the keys where the JSON's `unavailable` is true. One line per missing record: `<doc>: no lineage record — cannot tell whether its upstreams moved`. One line per absent upstream is not shown here: its gate owns it. Then ask, with `escalation-rules` loaded as the caller's **Load the question rules.** step loaded them:

   - **Where `stale` is not empty:** `choices: ["Stop — revise <highest> first with <reviser> (Recommended)", "Proceed — record that I accepted these upstreams"]` — `<highest>` and `<reviser>` from the JSON's `highest`: the stale downstream nearest the top of the chain, and the command that revises it, its `<KEY>` filled with that document's folder key. Fixing the top link first is the only order that settles the chain, since revising a lower document against a stale higher one leaves it stale.
   - **Where only `missing` is:** nothing is known to have moved — the documents only predate the record — so proceeding is recommended: `choices: ["Proceed — record that I accepted these unrecorded documents (Recommended)", "Stop — revise <top_missing> first with <reviser>"]`, `<top_missing>` and `<reviser>` from the JSON's `top_missing`, filled as above.
4. ***Stop*** → the run stops, writing nothing further, its Final report naming each stale link and missing record: with `<COMMAND>_UPSTREAM_STALE: <highest> is behind its upstreams — revise it first with <reviser>`, or, where only `missing` was, `<COMMAND>_UPSTREAM_STALE: <top_missing> carries no lineage record — revise it first with <reviser>, or re-run and proceed`.
5. ***Proceed*** → keep `<check-file>`; after the run writes each document, `record` step 2 accepts into it (§5). A run that stops before writing records nothing, and the next run asks again: nothing was built on the acceptance. The Final report names each accepted link.
6. **A caller that never asks** — `/dev-workflows:ready`, whose defining trait is that it neither asks nor stops, and `/docs-workflows:document` (keyed mode) and `/docs-workflows:release-notes`, which describe work already built and report a stale link beside the discrepancies they report, never as a reason to revise first — runs step 1 **once per unit**: for each Epic it reads, with `docs` and each `--accepted-from` that Epic's `specification.md` and `design.md` where present, and no `--output`; on a PRD-level run, once more for the PRD folder's own `specification.md` and `design.md`. On a `/document` or `/release-notes` run addressed to an Epic, that Epic is the one unit. **Where no unit in scope holds either document** — nothing specified yet, as on a `/release-notes` run at the PM stage — `/document` and `/release-notes` take one check, with the PRD folder's `prd.md` as `docs` and as `--accepted-from`, so a PRD behind its idea or decision register is still named and an acceptance its own run recorded is honoured. A link accepted by a document of the same unit — `design.md` recording that its run went on past a moved PRD — is a decision taken there, and is shown as *accepted in this unit* — the JSON names no accepting document; one accepted only in another Epic's documents is not, since nobody on this unit accepted it. Step 3's lines become the caller's own findings, worded as step 3 words them — `changed <keys>; new <keys>; withdrawn <keys>`, so a requirement the upstream gained is named; step 3's question, and steps 4 and 5, do not apply, and the caller never runs `accept`. **Across its units, the caller lists and counts each (downstream, upstream) pair once**: a link above the units — `prd.md` ← the decision register — comes back from every unit's check; it is listed as stale where any unit reports it stale, and as *accepted in this unit* only where every unit that met it accepted it. A non-zero exit is reported as a finding too, never a stop — a `<default-ref>` that does not resolve among them, which the script refuses rather than reporting every document absent (§7).

   **A caller with no gate** — `/document` and `/release-notes` run no `require-on-main`, so nothing has settled that what they check is on `<default-ref>` — also shows each `absent` entry, as a note line: where its `downstream` is null, the checked document itself is missing there, `<upstream>: not on <default-ref> — its chain was not checked`; otherwise an upstream it records is, `<downstream> ← <upstream>: not on <default-ref> — not checked`. **It also tests what it reads against what was checked**: the check reads every document at `<default-ref>`, while the caller writes from the checkout's copies, so a PRD revised on an open `prd/` branch would otherwise pass as current against the default branch's `prd.md`, which every specification recorded. It runs `git -C "$SPECS_PATH" diff --name-only <default-ref> -- <the PRD folder>`, keeps each path whose file name a kind of §4 matches (`lineage-kinds.json`'s `match`) — on an Epic-addressed run, none inside another `EPIC-` folder — and shows each as a note line, `<doc>: this checkout's copy differs from <default-ref> — the lineage shown is the default branch's, not the copy this run reads`. Step 2's `current` then also needs `absent` and those notes empty: while one is listed the report never says `current`, and where every document the run checked was absent it says so instead (§7). A run with no specs repository to read — an `@<path>` run with `$SPECS_PATH` unset, or one whose folder lies outside its work tree — runs no check. `/ready` keeps step 3's rule, since its `require-on-main` gate already reports a document that is not on `<default-ref>`.

## 7. Report line

Every caller's Final report carries one `Lineage:` line: `Lineage: current`; `Lineage: <n> stale link(s), <m> unrecorded — accepted` with each named; `Lineage: stopped — <highest> is behind its upstreams`; `Lineage: <n> stale link(s), <m> unrecorded — reported` from a caller that never asks (§6 step 6), with `, <k> not on <default-ref>` and `, <j> changed on this checkout` before the dash where a caller with no gate listed `absent` entries or checkout notes; `Lineage: not checked — <doc…> not on <default-ref>` from such a caller where every document it checked was absent, and `Lineage: not checked — no specs repository` where it had none to read; `Lineage: not checked — lineage.py failed: <the script's first stderr line>` from a caller that never asks, whose run did reach `upstream-check`; or `Lineage: not checked — <reason>` where the run never reached `upstream-check`.
