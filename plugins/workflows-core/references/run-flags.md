# Run Flags — Shared Reference

Single source of truth for the three run flags every applicable command accepts, their environment defaults, the model aliases, the `run_flags` record, and the skipped-cost path. Read through the loader; commands execute `strip-run-flags` in Phase 0 and `skip-cost` in their cost phase.

## 1. The flags

| Flag | Env default | Values |
|---|---|---|
| `--skip-costs` | `$WORKFLOWS_SKIP_COSTS` | bare = `true`; `--skip-costs=true\|false` |
| `--skip-feedback` | `$WORKFLOWS_SKIP_FEEDBACK` | bare = `true`; `--skip-feedback=true\|false` |
| `--enforce-model=<m>` | `$WORKFLOWS_ENFORCE_MODEL` | alias, full model id, or `routing` |

**Precedence: flag > env > off.** A flag given on the command line always wins over the corresponding environment variable, and an unset flag with an unset environment variable resolves to off (`skip_costs: false`, `skip_feedback: false`, `enforced_model: null`).

**Boolean flags (`--skip-costs`, `--skip-feedback`), stated explicitly because nothing elsewhere in the family parses a flag this way:** the bare form (`--skip-costs`, no `=`) resolves to `true`; `--skip-costs=false` resolves to `false`, with `false` matched case-insensitively (`--skip-costs=False` and `--skip-costs=FALSE` are `false` too); any other `=value` (`--skip-costs=1`, `--skip-costs=yes`, `--skip-costs=anything-else`) resolves to `true`. The same three cases apply to `--skip-feedback`.

**Env booleans** (`$WORKFLOWS_SKIP_COSTS`, `$WORKFLOWS_SKIP_FEEDBACK`): `1`, `true` or `yes`, matched case-insensitively, resolve to on; every other value, and an unset variable, resolves to off.

**A set-but-empty environment variable is unset.** `WORKFLOWS_ENFORCE_MODEL=""` (or `export WORKFLOWS_ENFORCE_MODEL=`) is treated exactly as if the variable were not set at all — source `default`, no enforcement, never a missing-value `RUN_FLAGS_BAD_MODEL` — and the same holds for an empty `$WORKFLOWS_SKIP_COSTS` or `$WORKFLOWS_SKIP_FEEDBACK`, which would have resolved off anyway.

**`--enforce-model` takes two equivalent forms:** `--enforce-model=<value>`, and the two-token pair `--enforce-model <value>` (a plain space, not `=`) — §3 strips either and resolves them identically. **The pair form always consumes the very next token as its value, whatever that token looks like** — so `/implement --enforce-model PROJ-12` treats `PROJ-12` as the requested model, never as a positional argument, and the run stops `RUN_FLAGS_BAD_MODEL` once `PROJ-12` fails every form in §2's table. A bare trailing `--enforce-model` with no token after it, and `--enforce-model=` with nothing after the `=`, are both a missing value; each stops `RUN_FLAGS_BAD_MODEL` — but, per §3's applicability step, only once `--enforce-model` is confirmed to apply to the running command, exactly like every other malformed or unreachable value. `--enforce-model=routing`, `$WORKFLOWS_ENFORCE_MODEL=routing`, and an unset flag with an unset environment variable all resolve to no enforcement (`enforced_model: null`); `routing` is matched case-insensitively (`Routing`, `ROUTING`).

**Flags may appear anywhere in the argument list** — before, after, or interleaved with a command's own positional arguments and other flags — except inside the prose of a free-text command (§3 step 1).

## 2. Model aliases

| Alias form | Resolves to |
|---|---|
| `opus` | the highest reachable model in `classification.md` §2 (the Opus rows only), where the model parameter accepts ids; see Reachability below |
| `sonnet` | the highest reachable model in `classification.md` §2.1, where the model parameter accepts ids; see Reachability below |
| `haiku` | the highest reachable model in the Haiku rows below, where the model parameter accepts ids; see Reachability below |
| `fable` | the reachable `claude-fable-…` id highest by version number — no `classification.md` chain names one — where the model parameter accepts ids; see Reachability below |
| `<family><major>` | `claude-<family>-<major>` |
| `<family><major>.<minor>` | `claude-<family>-<major>-<minor>` |
| `claude-…` | itself, unchanged |

`family` ∈ `opus | sonnet | haiku | fable`. The six alias rows (every row but `claude-…`) are matched case-insensitively — `Opus`, `SONNET`, `Opus4.6` resolve exactly as their lowercase forms — and a `claude-…` id is taken as written. Anything else given to `--enforce-model` or `$WORKFLOWS_ENFORCE_MODEL` — a form matching none of the seven rows above — stops the run with `RUN_FLAGS_BAD_MODEL`, naming the rejected value verbatim (or `(missing)` where there was none) together with its source — `(from --enforce-model)` for an explicit flag, `(from WORKFLOWS_ENFORCE_MODEL)` for the environment default (§3 step 2) — and listing these seven accepted forms. **Where the rejected value is itself a run-flag token the pair form consumed (§1)** — `--skip-costs`, `--skip-feedback` or `--enforce-model`, with or without an `=value` — the message also says so, in these words: `--enforce-model took '<token>' as its value; write --enforce-model=<model>, or put <token> before it`, so a user who wrote `--enforce-model --skip-costs` sees why the run stopped.

**The Haiku rows**, newest first — what the `haiku` alias resolves against, and what Reachability below reads for a Haiku value. No `classification.md` chain names Haiku (`defect-reporter` runs on `classification.md` §2.1), so these rows serve an enforced Haiku value only, and wherever this file speaks of a family's chain or its newest chain row, these rows are Haiku's:

1. `claude-haiku-5-5`
2. `claude-haiku-4-5`

**Reachability** is read exactly the way `classification.md` §2 already reads it — from the Agent tool's `model` parameter documentation, never assumed — and what it can prove depends on what that parameter enumerates.

- **Where the parameter accepts model ids**, a resolved id that is not reachable in the current environment stops the run with `RUN_FLAGS_MODEL_UNAVAILABLE`, naming the resolved id with the same source tag — `(from --enforce-model)` or `(from WORKFLOWS_ENFORCE_MODEL)` — and the models of that family that are reachable. For a bare `fable`, which has no chain to resolve against, a parameter listing no `claude-fable-…` id stops it the same way, naming `fable` with the source tag and saying no Fable model is reachable.
- **Where the parameter enumerates only family names** (`opus`, `sonnet`, `haiku`, `fable` — `classification.md` §2's *family-only harness*, which Claude Code's Agent tool is today), no id is ever listed, so reachability is decided per family and the harness picks the version:
  - **A bare family alias** (`opus`, `sonnet`, `haiku`, `fable`) is reachable iff its family is listed, and resolves to the family itself — `run_flags.enforced_model` records `opus`, not an id — and every dispatch passes it unchanged. A family the parameter does not list stops `RUN_FLAGS_MODEL_UNAVAILABLE`, naming the family with the source tag and listing the families the parameter does enumerate.
  - **A version-specific form** (`opus5.5`, `claude-opus-5-5`, …) is honoured only where the harness can select exactly it, which a family-only harness can do only for the version its family name most plausibly selects: the value is accepted **iff its resolved id is the first (newest) row of its family's chain** — `classification.md` §2's Opus rows for `opus`, §2.1 for `sonnet`, the Haiku rows above for `haiku` — and its family is listed. `run_flags.enforced_model` then records the resolved id (the record of intent), and every dispatch passes the family name (`classification.md` §5's dispatch form). `fable` has no chain, here or in `classification.md`, so no version-specific Fable form is accepted in a family-only harness.
  - **Any other version-specific form** — an older row (`opus5` → `claude-opus-5`), an id on no chain, or a Fable id — stops `RUN_FLAGS_MODEL_UNAVAILABLE`, not because the model is unreachable but because it cannot be selected exactly in this harness: the message names the resolved id with the same source tag and says, in these words, `this harness selects models by family only; use --enforce-model=<family>` (the resolved id's own family; for a `claude-…` id naming none of the four families, the message lists the families the parameter enumerates instead), since only the bare family can be honoured there.

What each dispatch was actually passed, and where it differs from the value requested, is what §6's `Model routing:` line reports.

**Both stops — and every validation in this section — apply only to an `--enforce-model` (or `$WORKFLOWS_ENFORCE_MODEL`) that §3's applicability step has already found applicable to the running command.** An inapplicable one — an explicit flag on a command outside its set, or an env default anywhere outside its set — is never parsed against this table, never reachability-checked, and never stopped on; §3 disposes of it first, before this section is ever reached for it.

**Both stops happen in Phase 0, before `specs-preflight` and before any write, and emit no feedback entry** — a bad or unreachable model name is a defect in the user's own invocation, not a gap in the plugin.

**Unpriced reachable id.** The price table is the first of `$DEV_WORKFLOWS_COST_PRICES` (a path), a repo-local `cost-prices.yaml`, and the bundled `${CLAUDE_PLUGIN_ROOT}/references/cost-prices.yaml` that exists, and an id is priced when its `models:` map carries a key equal to the id or, failing that, a key the id starts with (the longest such key wins) — stated here so Phase 0 never loads `cost-emission.md` to make this check. A reachable id that resolves but carries no such key does not stop the run: print one warning line, `⚠ <id> is unpriced in cost-prices.yaml — its cost will be recorded as null`, and continue. The check prices the resolved id; for a bare family alias resolved in a family-only harness, which records no id, it prices that family's newest chain row (`claude-opus-5-5`, `claude-sonnet-5-5`, and `claude-haiku-5-5`, the first of the Haiku rows above) — and `fable`, which no chain names, counts as priced when the table carries any key beginning `claude-fable-`, the warning naming `<id>` as `fable` where it carries none. Like the two stops above, this warning is reached only for an applicable, enforced model — an inapplicable `--enforce-model` never resolves far enough to trigger it.

## 3. `strip-run-flags` entry point

1. **Strip the tokens, capturing whatever raw value each carries without judging it yet.** Remove every token matching `^--skip-costs(=.*)?$` or `^--skip-feedback(=.*)?$` (§1's boolean grammar reads whatever followed the `=`, if anything, once the later steps reach it). For `--enforce-model`, remove whichever of these is present: a token matching `^--enforce-model=(.*)$` (the captured group is the raw value, possibly empty), or the bare token `--enforce-model` together with the single token immediately following it, consumed as a pair regardless of what that following token looks like (§1) — and where a bare trailing `--enforce-model` has no token after it at all, remove just that one token, carrying no value forward. None of this — including a missing or empty value — is judged yet; that is step 4's job, and only for a flag step 3 has found applicable.

   **Free-text commands strip run flags only outside the prose span.** A **free-text command** is one whose own body says (part of) its argument is prose kept verbatim rather than parsed into further positional arguments — tested exactly as step 3 below tests applicability: against the *running command's own body*, already in the executing agent's context, never by grep. Today's members are `/feedback`, `/prompt`, `/prompt-brainstorm`, `/prompt-grill-me`, `/implement`, `/idea`, `/brd-split`, `/diagnose-session`, `/document` (direct mode only — its keyed mode is an ordinary address command and carries no prose span at all) — stated here as today's members, never as the definition. A maintainer re-deriving the set from outside a live run greps for the tell instead — `grep -ln "verbatim" plugins/*/commands/*.md`, then reads each hit's own argument-parsing step, since a "verbatim" mention elsewhere in a command's body (a quotation preserved for a report, a customer's or a reviewer's own words recorded as such) does not make that command a member — kept here as that recipe and nothing more, never as the runtime test.

   For a free-text command, the **prose span** begins at the first token the command's own parse does not recognize as one of: a run flag (with its value), this command's own flag (with its value), its key/address, or — for `/implement` only — an `@path` token. For `/implement`, `/feedback`, `/prompt`, `/prompt-brainstorm`, `/prompt-grill-me`, this test runs from the very start of `$ARGUMENTS`, consuming any mix of run flags and, **for `/implement` only**, all three of its own `--no-commit`, an address/key, or an `@path` token — none of those three apply to the other four commands, so a note or corrective request that happens to start with a key-shaped word is still ordinary prose for `/feedback`, `/prompt`, `/prompt-brainstorm` and `/prompt-grill-me` — in whatever order the recognized tokens appear, until the first token matching none of them (for the running command) is reached; that token, and everything from it onward, is the candidate prose. For `/idea` and `/brd-split`, the leading region runs **up to and including the key/address**: any flag found before the key (a run flag or one of the command's own) is part of this region; the run flags among them are stripped, the command's own are left for its own parse — and the region ends at the key; nothing *after* the key extends it further, so a flag-shaped token — a run flag, or, for `/idea`, one of its own (`--deep`, `--no-docs`, `--docs <value>`, `--ground-code`) — sitting immediately after the key is candidate prose too, unless the trailing rule below reaches back far enough to claim it. For `/document`, this test is what decides which of its two modes' rules apply, rather than waiting on the command's own Mode detection to decide first: after the leading run of run-flag tokens is consumed, the next token is tested against `workflows-core:addressing` §1's key grammar and against `@<path>` naming a folder in the specs tree. A hit is this command's key/address — its keyed mode is not free-text at all, so an ordinary strip applies: run flags removed wherever they appear, the address left untouched. A miss puts the run on the free-text rule, exactly as for `/feedback`: the leading region is a single `@<path>` token where the stripped argument opens with one and it is not such a folder — direct mode's own file argument (its Phase 0 step 1) — otherwise nothing of the command's own, and the prose span begins there. The command's own Mode detection then re-reads the stripped result to make its own, authoritative keyed/direct call; it never runs before this test, and this test never waits on it — the order removes the circularity a reader could otherwise construct between the two. For `/diagnose-session`, the leading region is the leading run of run-flag tokens and then, where the next token is its session — an existing `.jsonl` path, or a token shaped like a session id (its Phase 0 step 1) — that one token; the prose span begins after it.

   Separately, for every free-text command, the **trailing run** is the longest suffix of `$ARGUMENTS` that parses **left to right** as complete tokens of the running command's own recognized grammar — its own flags (with value) and run flags (with value) alike, plus, **for `/implement` only**, an `@path` token. The pair form (`--enforce-model <value>`, and `/idea`'s `--docs <value>`) consumes its very next token as one unit, whatever that token looks like (§1) — so a trailing `--enforce-model opus` counts as one unit inside the run, and a trailing `… --enforce-model --skip-costs` takes `--skip-costs` as `--enforce-model`'s value, not as a second flag, exactly as the leading strip already reads it. For `/implement`, an `@path` token found in the trailing run is left in place there exactly like its own flags are, symmetric with the leading region: `/implement fix x --skip-costs @a.md` strips `--skip-costs` out of the 2-token trailing run `--skip-costs @a.md`, leaving `@a.md` for implement's own `@path` classification and `fix x` as the prompt. Where the candidate prose found above is itself all trailing run — nothing separating the end of the leading region from a run of complete flag/`@path` tokens — the trailing run consumes the whole of it, and no prose remains.

   Strip only the **run-flag** tokens found before the prose span begins, or inside the trailing run; the command's own flags found in either place are left untouched, for that command's own later parse to remove. Every token inside the prose span that is not part of the trailing run is prose, kept verbatim even where it is a flag name — because it is neither before the prose span begins nor part of the trailing run, nothing in this step strips it.

   **The costs, stated plainly:** prose that genuinely ends in a flag name loses it to the trailing-run strip — and where that flag is `--enforce-model`, the word before it is lost too, consumed as its value before either word is judged. Because the trailing run is the *longest* parsing suffix, this can reach much further back than the prose's last word or two: a flag name written anywhere in the prose, followed by exactly one plain word and then a genuine trailing flag, pulls the whole tail from that flag name onward into the run — `/implement fix the --enforce-model flag --skip-costs` reads `flag` as `--enforce-model`'s value and `--skip-costs` as a second flag inside that same trailing run, stopping the run with `RUN_FLAGS_BAD_MODEL` with only `fix the` surviving as prompt, well short of the prose's actual last word. This happens even where the trailing flag does not apply to the running command at all: step 1 strips by pattern alone, before step 3 ever tests applicability, so an inapplicable trailing token is still removed from the text and reported `Run flags: --<flag> does not apply to /<command> — ignored`, rather than surviving as prose. There is no placement that fully avoids this; keeping a flag name away from the prose's end, and never followed there by a single word and then a real flag, avoids the cases above.
2. **Determine each flag's raw source, per §1's precedence, resolving nothing yet.** For each of the three flags: `flag` when step 1 found an explicit token for it (whatever raw value it carried, including none/empty for `--enforce-model`); else `env` when the corresponding environment variable (§1's table) is set to a non-empty value (whatever that value is — an empty one counts as unset, §1); else `default` (neither present). This step only records *where* a value would come from.
3. **Applicability — resolved before anything is validated.** Test each flag against the *running command's own body*, already in the executing agent's context, never by shelling out: a `grep -l … plugins/*/commands/*.md` does not resolve at runtime, since the agent's cwd is the user's project and the installed plugin tree lives under `~/.claude/plugins/cache/`, not under a repo-relative `plugins/` path. The runtime test, per flag: `--skip-feedback` applies iff the running command's own body cites `workflows-core:impl-maintenance`; `--skip-costs` applies iff the running command's own body calls `emit-cost`, or the running command is `/prompt-brainstorm` or `/prompt-grill-me`; `--enforce-model` applies iff the running command's own body invokes `workflows-core:model-routing`. A maintainer re-deriving these three sets from outside a live run — never the running command itself, which already has its own body in context — uses the three `grep` recipes instead, kept here as **that recipe and nothing more**, never as the runtime test: `--skip-feedback`'s set is `grep -l 'workflows-core:impl-maintenance' plugins/*/commands/*.md`; `--skip-costs`'s set is `grep -l 'emit-cost' plugins/*/commands/*.md` plus `prompt-brainstorm.md` and `prompt-grill-me.md`; `--enforce-model`'s set is `grep -l 'workflows-core:model-routing' plugins/*/commands/*.md`. A flag given **explicitly** to a command whose own body fails its test prints `Run flags: --<flag> does not apply to /<command> — ignored` and resolves to that flag's default for this run, **unvalidated** — step 4 never looks at its raw value at all, so a malformed or unreachable one on an inapplicable command stops nothing. An env default whose flag fails its test is silently treated as unset — no notice, same unvalidated default resolution — so an environment default never stops, warns on or alters a command it does not apply to: `$WORKFLOWS_ENFORCE_MODEL` set to a value that would stop an applicable command is ignored by a command outside the `--enforce-model` set, and `/docs-serve` and `/statusline`, which are in none of the three sets, run exactly as if no run-flag variable were set. `/harvest-decisions`, in none of them either, runs no `strip-run-flags` at all: it never reads a run-flag variable, and an explicit run flag reaches its own argument parse, which refuses any argument but `--dry-run`. Only a flag that passes its test proceeds to step 4 at all.
4. **Resolve every flag step 3 found applicable, and only those.** `skip_costs` and `skip_feedback` resolve per §1's boolean grammar. `enforce_model` resolves per §2's alias table and reachability check: a missing or empty value (step 1) or a value matching none of §2's seven forms stops `RUN_FLAGS_BAD_MODEL`; a resolved-but-unreachable id — or, in a family-only harness, an unlisted family, or a version-specific form that is not its family's newest chain row and so cannot be selected exactly in this harness (§2) — stops `RUN_FLAGS_MODEL_UNAVAILABLE`; a resolved, reachable value that §2's price check finds absent from `cost-prices.yaml` prints §2's unpriced-model warning and continues. A flag step 3 found inapplicable never reaches this step — its record value (step 5) is simply the default, whatever step 2 found.
5. **Build the record:**
   ```yaml
   run_flags:
     skip_costs: <bool>
     skip_feedback: <bool>
     enforced_model: <id|family>|null   # a family only for a bare alias in a family-only harness (§2)
     requested: <raw --enforce-model value as written>|null   # null where enforced_model is null
     source:
       skip_costs: flag|env|default
       skip_feedback: flag|env|default
       enforce_model: flag|env|default
   ```
   For a flag step 3 found inapplicable, its `source` here is always `default`, whatever step 2 determined — the explicit-vs-env distinction only matters for a flag that actually applied, since an inapplicable one never produced a resolved, non-default value to attribute.
6. **Report when non-default.** When any of `skip_costs`, `skip_feedback` or `enforced_model` is non-default, print one line: `Run flags: skip-costs=<on|off>(<source>) skip-feedback=<on|off>(<source>) enforce-model=<id|routing>(<source>)`, where `<id>` is rendered exactly as §6 renders the `Model routing: bypassed` line's `<id>` — from `enforced_model` and `requested` — so the two lines never show different values for one flag. When all three are default, print nothing here.
7. **Report an orchestrator/session-model mismatch.** When `enforced_model` is set and differs from the model the orchestrator is itself running under, print `Run flags: orchestrator runs on <session-model>; relaunch after /model <alias> to enforce it there too`, and continue the run unchanged. `<alias>` is the family alias `opus`, `sonnet` or `haiku` **only when the enforced id is exactly what that alias resolves to** in §2's table here (the highest reachable model of that family), since `/model <family>` selects the newest model of the family and not an older one; for any other enforced id — an older version such as `claude-opus-4-6`, or any `fable` id, which is not a verified `/model` alias — print the full id instead, as `relaunch with <full id> selected via /model to enforce it there too`. **In a family-only harness (§2)** the enforced value is a family, or a version-specific id §2 accepted only because it is its family's newest chain row — so it "differs" from the session model exactly when the session model is not of that family, and `<alias>` is that family's name; a `fable` value, which is not a verified `/model` alias, prints `relaunch with a Fable model selected via /model to enforce it there too` instead.

Return `run_flags` and the stripped argument string — every later parsing step in the command reads only what this entry point leaves behind.

## 4. Skip-feedback

Under `run_flags.skip_feedback`, the command's maintenance phase dispatches `workflows-core:defect-reporter` in place of `impl-maintenance`, with the same compact session handoff `impl-maintenance` would have received, plus `Plugin root:` (the dispatching command's own `${CLAUDE_PLUGIN_ROOT}`, which `defect-reporter` searches for the command's, reference's, or agent's file a candidate names — its own `${CLAUDE_PLUGIN_ROOT}` reaches only `workflows-core`'s own installed files, never a sibling plugin's), on `model: run_flags.enforced_model` when it is set, else the `classification.md` §2.1 Sonnet chain, the tier `impl-maintenance` runs on — either passed in `classification.md` §5's dispatch form. When `defect-reporter` returns at least one defect, persist them with `feedback-emission`'s `emit-bugs` entry point (`Skill(skill: "workflows-core:reference", args: "feedback-emission emit-bugs")`) in place of `emit-auto`; when it returns none, load `feedback-emission` not at all. `emit-block` (capture-at-block) is unaffected by the flag and fires exactly as it would without it. **What the user loses under this flag: the in-session Lessons Learned report** — `defect-reporter` returns defects only, never workflow advice, agent/skill suggestions, or target-project tooling notes.

## 5. `skip-cost` entry point

1. **Resolve session artifacts** exactly as `cost-emission.md` §1 names them — restated here, in full, because this path must never load `cost-emission.md`:
   - **`<cwd-slug>`** — the absolute `cwd` with every `/` and `.` replaced by `-`.
   - **Main transcript** — the newest `*.jsonl` directly under `~/.claude/projects/<cwd-slug>/`; its basename minus `.jsonl` is `session_id`.
   - **Subagents dir** — `~/.claude/projects/<cwd-slug>/<session_id>/subagents/`.
2. **Advance the checkpoint, and nothing else:**
   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/session-cost.py" \
     --transcript <main transcript> --subagents-dir <subagents dir> \
     --checkpoint ~/.claude/dev-workflows/cost-state/<session_id>.json \
     --snapshot ~/.claude/dev-workflows/cost-snapshots/<session_id>.json \
     --now-ts <current UTC ISO8601> --advance-only
   ```
   `${CLAUDE_PLUGIN_ROOT}` here resolves to `workflows-core`, which ships `session-cost.py` — correct, since this reference is read through the loader skill regardless of which plugin's command is running.
3. **Drop any deferred claim.** If `~/.claude/dev-workflows/cost-state/deferred-<session_id>.json` exists, print `cost attribution for <command> dropped (--skip-costs)` once per record it holds, then delete the file — a checkpoint that has already advanced past those records' boundaries could never match them anyway. Where the file cannot be read or does not parse as the §13.1 record list, print one line, `deferred cost records unreadable — dropped (--skip-costs)`, delete the file if it can be deleted, and continue; like step 5, this never fails the run.
4. **Write nothing into `$SPECS_PATH`.** No cost entry, no pending file, no §9-style reconciliation offer — none of `cost-emission.md`'s persistence ladder runs.
5. **Never fail the run.** A `session-cost.py` failure of any kind prints one line naming the failure and the run continues unaffected.

**`/prompt-brainstorm` and `/prompt-grill-me` never run `skip-cost`**, because both cede the session at their own Phase 3, before any cost phase could run at all. Under `--skip-costs` (or `$WORKFLOWS_SKIP_COSTS`) each instead writes its `cost-emission.md` §13.1 deferred record with `"skip": true`, so the replaying run's `emit-cost` still carves the ceded segment out of its own window — attribution stays correct — but then discards that segment instead of writing an entry for it.

## 6. Reporting

Four report lines, each printed only where the step that produces it fires:

- `Run flags: …` — §3 step 6 (non-default flags) and/or §3 step 7 (orchestrator/session-model mismatch).
- `Session cost: skipped (--skip-costs)` or `Session cost: skipped (WORKFLOWS_SKIP_COSTS)` — the command's cost phase, under `run_flags.skip_costs`, naming the source that set it.
- `Session feedback: bugs-only (--skip-feedback) — N defect(s) persisted` or `— no defects` — the command's maintenance phase, under `run_flags.skip_feedback` (§4).
- `Model routing: bypassed — enforced <id> (flag|env)` — wherever a command's final report would otherwise state its model-routing degradation, under `run_flags.enforced_model`. `<id>` is rendered as **what the dispatches were actually passed** (`classification.md` §5's dispatch form), followed — where that differs from `run_flags.requested`, the value as written, or where the harness picks the version — by a parenthesis saying so. Where the parameter accepts ids: `enforced claude-opus-5-5 (flag)` when `claude-opus-5-5` was requested as written, and `enforced claude-opus-5-5 (from opus) (flag)` when the alias `opus` resolved to it; `enforced opus (the harness picks the version) (flag)` for a bare `opus` in a family-only harness; `enforced opus (from opus5.5; the harness picks the version) (env)` for an accepted version-specific form there, naming the value as the user wrote it.

**The final report repeats the `Run flags:` line** whenever §3 printed one during the run, so a reader of the report alone — without having watched the run live — still sees which flags were non-default and why.
