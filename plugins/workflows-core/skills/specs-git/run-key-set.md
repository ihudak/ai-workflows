# The run key set — what `specs-git start --key` takes

`workflows-core:specs-repo-git` §3.2's *Run key set*, for a run that calls the `specs-git` skill. A citation of that rule is served by this file.

The run key set is every key the run is scoped to — the identity each of this run's own branches is named for — taking each key already resolved where the call is made. It exists only to recognise this run's branches. A PRD-scoped run contributes its PRD key. An Epic-scoped run — one whose single address resolved an `EPIC-` folder, on any command that takes an Epic address — contributes both the Epic's key and its parent PRD's, the key the parent folder's carrier asserts, because the Epic's key carries its ancestry, whether or not the run reads the PRD. A command whose keys come off its arguments (`read-key`) contributes each such key — for a token typed as a folder's whole name, the key that folder's carrier asserts — and one given an `@<path>`, the key the carrier of the folder it names asserts; `/vuln` contributes one per token that carries one. Where no key is resolved when the call is made, the set is empty and the run is keyless; never defer the call to obtain a key a later phase would mint.

`/create-prd` always contributes its folder's key, on both routes — the key it copies into the PRD's `key` frontmatter, which nothing mints — and no route is ever treated as keyless: an empty set would send a resumed run off its own unmerged branch, and its handoff to a duplicate branch ending `-2`. What stays keyless is a run that resolved no key where the call is made, never a route. A key is a folder's identity, and contributing it widens no tracker identity; §3.5's `branch-key` matches a key of any depth by one rule, a three-segment slice key as a two-segment one. The commit's key is a different input, resolved at the end of the run and passed as the skill's `--commit-key`: a run keyless here may hold one by then, and is not thereby committing under `NOISSUE`.
