# Hooks reference

`workflows-core` bundles three hooks, declared in `hooks/hooks.json` and installed automatically with the plugin — there is nothing to opt into separately. All three are advisory: **a hook never blocks Claude.** Each script ends in an unconditional `exit 0` regardless of what it detects or whether its own logic errors out, by contract — a hook exists to notify, remind or keep an installed file current, never to gate a tool call.

| Hook | Event | Matcher | What it does |
|---|---|---|---|
| `notify-done` | `Stop` | — | Raises a cross-platform desktop notification, "Claude Code finished", at the end of every turn. |
| `test-notify` | `PostToolUse` | `Bash` | Detects a test-runner invocation, parses its pass/fail counts, and raises a desktop notification summarizing the result. |
| `statusline-refresh` | `SessionStart` | — | Replaces the status line `/workflows-core:statusline` installed with the script this plugin version ships, where the installed copy is unedited. |

**All three are session-wide, and that is why they live here.** None is scoped to a command: `notify-done` fires on every `Stop` event, `test-notify` on every `Bash` tool call, whatever ran, and `statusline-refresh` on every session start. Every plugin in the family declares `workflows-core` as a dependency, so shipping them here gives every user exactly one copy — the alternative, duplicating them per plugin, would double-notify anyone holding two. `statusline-refresh` belongs with the script it installs, which is this plugin's.

The `dev-workflows`, `product-workflows` and `docs-workflows` plugins each ship a `preload-context` hook of their own instead, matched to their own commands. This plugin ships none. Six of its seven commands take no address at all — `/feedback` and the three `/prompt*` commands resolve the target they are correcting from the session rather than from an argument, `/statusline` sets a configuration value, and `/diagnose-session` takes a session id or a transcript path, never a specs-tree address — so there is nothing for a hook to surface ahead of them. `/frames` is the exception: it takes a **mandatory** address, which its own Phase 0 parses and resolves with `resolve-address`, and it gets no injection.

## What each hook does, in detail

### `notify-done` (`hooks/notify-done.sh`)

Runs on every `Stop` event with no matcher, so it fires at the end of every turn regardless of what happened during it. It builds one fixed message, `"Claude Code finished"`, and dispatches it through the first notification mechanism available for the host: `osascript` when `$OSTYPE` starts with `darwin`, `wsl-notify-send` or a PowerShell balloon-tip fallback when `/proc/version` mentions Microsoft (WSL), and `notify-send` — falling back to a plain terminal bell (`echo -e '\a'`) if that binary is missing — everywhere else. Every branch degrades to a fallback rather than propagating a failure: the darwin branch is explicitly suffixed `|| true`, while the WSL and default branches fall through to the terminal bell when their own notifier command fails. The actual never-fails guarantee comes from the unconditional `exit 0` on the script's last line, regardless of which branch ran.

### `test-notify` (`hooks/test-notify.sh`)

Runs on every `PostToolUse` event matched to the `Bash` tool. It reads the tool-call payload from stdin, extracting the executed command and its captured output — the Bash result's `stdout`, which carries the command's error output too, and `stderr` in case a harness keeps the two apart (checking both the nested `tool_input`/`tool_response` shape and top-level fallback keys for older payload versions). If the command **contains** none of `mvnw test`, `mvn test`, `gradlew test`, `gradle test`, `gradlew cleanTest test`, `gradle cleanTest test`, a Gradle task path ending in `:test` (`./gradlew :api:test`, `./gradlew -q clean api:test`, the root project's `./gradlew :test`), `npm test`, `yarn test`, `pytest`, or `make test`, it exits immediately. **The test is a substring one, which is why each wrapper needs an entry of its own** — `mvnw test` no more contains `mvn test` than `gradlew test` contains `gradle test`. The same substring rule is what lets a flagged or prefixed form through on an existing entry — `./gradlew test --info`, `mvn test -q`, `python -m pytest` and `pnpm test` all match — and what leaves a goal or script name in front of the word out: `mvn clean test`, `./gradlew clean test`, `npm run test` and `py.test` do not match, and notify nothing. `cleanTest test` and the single-module `./gradlew :<module>:test` are the two such forms with entries of their own: `dev-workflows`' `test-baseliner` runs a Gradle suite as `./gradlew cleanTest test --no-build-cache`, which the `gradlew cleanTest test` entry matches, and its `/vuln` and `/upgrade` references prescribe the single-module form. That one entry is a pattern rather than a substring — a whole argument ending in `:test`, after any flags or other tasks — so `./gradlew -q :api:test` matches and `./gradlew :api:testClasses` does not. For a match, a small embedded Python script parses tool-specific pass/fail counts out of the output — `Tests run:`/`Failures:`/`Errors:` for Maven, `N tests completed, N failed` for Gradle, `N passed, N failed` for pytest, and a `Tests: … passed … failed` line for npm/yarn/pnpm — and raises a desktop notification (the same cross-platform dispatch as `notify-done`) reading `"Test run: <summary>"`. **Where none of a family's own patterns match its output, the summary is the literal `"tests completed"` rather than a count** — the same literal `make test`, the one matched command outside those four families, always gets. That is not a cosmetic default: most of what people put behind `npm test` is not jest and prints no `Tests:` line at all, and a green Gradle run prints no `N tests completed` line, because filling an unmatched count with a zero would report a genuinely red suite as `"0 failed"` — indistinguishable from a green one. A count that was read is reported; a count that was not is not invented. A miss *beside* a hit is still reported as `0`, because a runner omits the clause for a zero from a summary it did print.

### `statusline-refresh` (`hooks/statusline-refresh.sh`)

Runs on every `SessionStart` event with no matcher — a new session, a resume, a `/clear` or a compaction. It does nothing unless `/workflows-core:statusline` has installed `~/.claude/dev-workflows/statusline-command.sh`; it never installs one. Where the installed script equals `${CLAUDE_PLUGIN_ROOT}/scripts/statusline-command.sh` — the copy the running plugin version ships — it only makes sure `statusline-command.sh.sha256` beside it records that script's SHA-256. Where they differ, it replaces the installed script only if the script's SHA-256 matches that record, which the install wrote: it copies the old script to `statusline-command.sh.prev`, moves the new one into place, executable, and records the new SHA-256. A copy edited by hand, or one installed with no record, is left as it is. It prints nothing and needs `shasum` or `sha256sum`; without either it does nothing. The [statusline page](../commands/statusline.md#updates) says what this means for an install.

## Why none of this blocks you

All three scripts end `exit 0` unconditionally — the exit code is never derived from what the hook found, so a missing notifier binary or an unparsed test-output format never stops a tool call, a turn, or the run itself. `test-notify` also guards on `command -v python3` up front and exits 0 immediately when it is absent, degrading to silence rather than failing; `notify-done` carries no such guard because it never calls `python3` at all, and neither does `statusline-refresh`, which returns without a write wherever a file it needs or a hash tool is missing.
