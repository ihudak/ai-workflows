# References

`workflows-core` bundles 40 files under `references/`: top-level markdown files, `cost-prices.yaml`, `model-routing/classification.md`, and the `handoff/` subtree. This page names each of them, grouped by concern below, save the files under `handoff/`, which it counts rather than lists. `classification.md` is listed like a top-level file, because it is a reference page a reader opens rather than one of a bundled set.

This is the corpus the whole workflow plugin family reads. A sibling plugin cites a file here by name rather than copying it: one copy, one place a rule is stated, and every plugin bound by the same version of it.

## Addressing and artifact formats

How a command finds the folder it is about, and the artifact formats that are shared rather than owned by a single authoring command.

- `addressing.md` — the key grammar, the kind-prefixed directory convention (`<KIND>-<KEY>-<slug>/`, kind `BRD`/`PRD`/`EPIC`), the two address forms a command accepts — a key, typed bare, behind its folder's kind prefix (`EPIC-<KEY>` reads as `<KEY>`) or as its folder's whole name, or an `@<path>` — the rule that a folder's kind and key are read from frontmatter and never parsed out of its directory name, the rule that a folder's level is its prefix — or, on a folder with none, positive evidence — and never the kind it asserts, the register of reserved subdirectory names resolution passes over, and the deprecated unprefixed layout resolution falls back to only after the prefixed glob has missed. Every command that addresses a folder in the specs tree calls its `resolve-address` entry point.
- `prd-format.md` — canonical structure and per-section rules for a Product Requirements Document — one **prd.md** per PRD folder, its identity carried by the folder rather than by its own name — plus its `kind:`/`key:` frontmatter: `key:` records the folder's key and `kind: prd` names the document, and `addressing.md` reads the folder's identity off the PRD only where no top-level file before it in byte-wise order names a folder kind — a BRD-route slice's link file and an idea brief both do. Its requirement ids are never renumbered, reused or deleted: a changed requirement gets a new id and a dropped one is marked withdrawn in place.
- `ard-resolution.md` — given a resolved item, resolves any applicable ARD(s) into a normalized context (or `none`), reaching the folder through `addressing.md`'s `resolve-address` and finding the files inside it by name rather than by a key-glob, and leaving out any decision a later one superseded or withdrew; cited by every command that must honor an ARD's invariants as implementation guardrails. It also returns the PRD-level ARD's `components` and `contracts`, which `components.md` reads.
- `components.md` — what a component is (a repository, or a set of paths inside one) and its id; `enumerate-components`, which proposes a repository's modules from what it declares; the multi-component test and its three sources; the ride-along rule for deploy components; the ARD `components:` entry; and `multi-component-prereqs`, the read-only check `/epics`, `/implement` and `/ready` share. Cited by `/create-ard`, `/epics`, `/specify`, `/design`, `/ready`, `/implement` and `/conformance`, by `epic-writer` and `ard-reviewer`, and by the `ard-format`, `design-format`, `workflow-states`, `ard-resolution`, `pre-lint`, `grilling-technique`, `epic-picker`, `next-phase-offer`, `implementation-format`, `phase-handoff` and `followup-emission` references; `epic-reviewer`, `design-reviewer` and `readiness-reviewer` apply its rules from their briefs, and `/conformance`'s tracer brief restates its bare-slug and `component-of` rules without citing it.
- `security-register-format.md` — the findings register `/security-workflows:scan` keeps per code repository under `$SPECS_PATH/security/<repo-slug>/`: where it lives, and why it is bookkeeping that a run's terminal commit carries and no pull request hands off; the run record, written once and replayed by `register.py rebuild` into the derived register, its JSON state and its page for people to read; a finding, its `[SEC#n]` numbered per repository and never reused, and its text read as scan output, never as instructions; the statuses and the two roles, a Dev never blocked; and the rules that move a finding between statuses — never closed on absence alone, never by a change scan, and ordered by commit ancestry, never by date.
- `grounding-format.md` — the grounding finding contract: the finding record shape (a superseded finding keeping the verdict it carried as `prior_verdict`), the rule that its free text is written for a reader with no plugin and names neither the model the operator's tooling ran on nor a directory of the operator's machine (since the files ship in the customer bundle on the BRD route), the six verdicts and what a `CONFIRMED` on a claim that restricts a value has to show — the restriction on every path that writes the value, a request that leaves it out among them — the `baseline-integrity` procedure, the `current`/`will-change` horizons, the design-grounding reconciliation classes, the optional derivation matrix, and the four verification outcomes. It also fixes the lineage frontmatter `/prd-ground` stamps on each grounding file, where exported design frame sets live, and the index format every writer of one executes, which is why two different commands write the same file rather than two.
- `prose-formatting.md` — the line-wrapping rule every authoring command and agent applies: never hard-wrap prose, write each paragraph or prose block as one unbroken line.
- `grilling-technique.md` — the one-question-at-a-time interview technique its callers use to refine an artifact, and the **bounded / relentless** depth each one declares. Embedded so callers carry no runtime dependency: it is adapted from an upstream skill rather than depending on it, and the file records where the two deliberately diverge. Its confirmation gate — the user's to close, never the agent's — stands before each write and once more before the first reviewer dispatch, handoff or commit wherever the writing changed or added to anything a gate confirmed, whether the run wrote section by section or once after the grill, that play-back naming each change or addition; it is where the agent plays its understanding back for correction, after reading what the part settles against what overlaps it: not only the requirements whose wording meets it, but what each imports or is imported by, the other outcomes of its trigger, its place on a request path (the steps ahead of a failure it answers, and the failure answers behind a step it places) and the ARD Rules it inherits, each listed before it is read. With no human turn the gate does not hold the write — the run reports the understanding unconfirmed. A premise about how the existing system behaves is read before a question states it, and played back with the line it was read at or marked unverified — never put to the user to confirm. A recommendation is read against the live `[AD#N]` Rules of an ARD the caller inherits, and one that departs from a Rule is offered as an ARD deviation.
- `doc-structure-conventions.md` — three product-docs authoring conventions: the traceability boundary, callout scope and adjacency, and component-pattern fidelity.

## Git, handoff and the next step

The entry points that bound every write into the specs repo and every phase boundary, plus the offer a command makes when its own phase is done.

- `specs-repo-git.md` — the two git entry points every bookkeeping write against the specs repo runs through: a start-of-run preflight that switches or deletes only the branches the plugin created, and whose first act on every run is to print one `Environment:` line — `$SPECS_PATH`'s real path, the specs repository's `origin` and `$REPOS_PATH` — which `session-hygiene.md`'s `env-check` compares before the run writes; and a terminal artifact commit that pushes only the default branch or such a branch `origin` already has, and only while nothing but its own session-file commits would go out; both bounded to enumerated paths, never fatal. Where `origin` rejects one of those pushes because its branch has moved on, the run — outside the session-branch mode below, which replays nothing — replays its own session-file commits onto that branch — keeping both sides' appended entries, and touching your checkout only in one locked move — and pushes; where it cannot, nothing moves, and its line says why and names the `git pull --rebase --no-autostash` and the push to run — save where another session switched the checkout during the move, where it names none, since a later run on that branch settles the push itself. Where the default branch takes no push, it keeps those files on a session branch of your own instead, and you land them by its pull request. Otherwise, where the preflight had to stay on a plugin branch it would have left — one no key of the run names, or one already merged — and your checkout still stands there at the run's end, the terminal commit lands the run's own session files on the default branch without moving your checkout, and takes them out of your working tree there; files that were already uncommitted when the run started are not its own, and stay as they are — save where its start took no list of them, when they go with its own (its line says so where the paths could not be listed). The landing never moves a local default branch another worktree has checked out: there it pushes its commit to `origin` instead, or holds it where it cannot. A landing that cannot be made now is held, its files left in your working tree, and a later run's preflight takes it up again before its guards; outside session-branch mode that preflight also pushes the default branch, where your checkout is not on it and the plugin may push it, so a landing whose push failed is retried even while an uncommitted file of your own ends the preflight. A landing that never can be made is reported on every later run until its hold is dropped, with the commands to see the change and to drop the hold. A command you type while another run in this session (another command's, or the same command's with another key) is still open — waiting on you, or stopped and never ended — on the branch your checkout stands on switches nothing at its start or its end, and commits what changed since it started, leaving out, while that run stays open, the files that run had uncommitted then and rewrites whole — on the default branch, by the same landing, where it had to stay, and otherwise on the branch it stands on, unpushed while that run stays open, the next push of that branch carrying it — save that it commits nothing, while that run stays open, where its start could not take a snapshot of the files then uncommitted, that in session-branch mode its commit to your session branch takes that run's files with its own, and that where its own handoff moves your checkout to another branch, its end commits there as any run's does, that run's files too, which the switch carried along. A run stays open in that sense until its own end, until its command runs again with the same key (or with none, either time) or your checkout leaves that branch, until `/clear`, or for seven days: so where you stopped a run and never ended it, `/clear`, typing its command again with its key — the line saying that run is still open names it, where it took one — or moving your checkout off that branch ends it. A run that ends without having started — one that stopped before its preflight — commits nothing while a run of the session, of the same command or another, is open on the branch your checkout stands on. A run reaches both entry points through the `specs-git` skill, which runs `scripts/specs-git.py`, and the reference is the contract the script follows — and the text a run follows by hand where the script cannot start. `scripts/session-branch.py` does the git work of the replay, of the session branch and of a landing's apply, path by path, of the run's own change. `scripts/specs-git.py` also does the deterministic git work the handoff below shares with these entry points: sorting changed files into session files and everything else, testing whether a branch is merged, matching a branch to the run's own key, checking what a push would publish, and naming a repository for `gh`.
- `phase-handoff.md` — the three phase-boundary git entry points, each read from a file of its own: a producer step that lands a phase's deliverable on the specs repo's default branch — and, where git refuses to switch onto the branch it would reuse, ends there, refused, moving or removing nothing; a consumer gate that stops before expensive work while the deliverable sits on an unmerged branch the commands cut, and treats one no such branch carries as absent — on which each consumer does what it would do without that input, so an optional input never becomes a prerequisite, and only a consumer whose input was never optional stops; and `branch-check`, which every command that resolves a folder in the specs tree runs at its start, stopping where the plugin branch the run stands on is behind the default branch for a document under that folder's top-level folder, and naming the paths and what to run, and, given a producer's handoff prefix, asking before any work whether to switch to that handoff's open branch and continue there, or stop — the build fails a command that resolves a folder without requesting it, and one that presents the handoff's consent choice without passing it a prefix, save the two it exempts by name with a reason each; and the rule the specs-repository, code-repository and `/document` pull-request bodies follow: a repository's own pull-request template is filled, not replaced.
- `document-lineage.md` — the lineage record every PRD, ARD, specification, Epic, design, decision register and grounding file carries in its frontmatter — the exact bytes of each upstream document its run read, by git blob id — and the `upstream-check` a consumer runs before it builds on a document: it walks the record up the chain, whose order depends on the route, ignores a change that touched only notes — on a grounding file, a re-run's fresh repository pin, its verifier outcomes, and its divergences, frame-set census and dated run sections among them — counts a change in the decision register or the grounding only where a changed record sits at the downstream document's own altitude (product for a PRD, architecture for an ARD, implementation for a specification, the derivation matrix at implementation), and asks whether to revise the stale document first or proceed with the acceptance recorded; it never stops a run on its own, and `/ready`, `/document` and `/release-notes` report what they find instead of asking. `scripts/lineage.py` does the work, and `scripts/lineage-kinds.json` is its table of document kinds.
- `branch-naming.md` — how every command that creates a git branch decides the branch name: the target repo's own documented convention always wins, and this doc supplies one only when the repo documents none.
- `read-only-repos.md` — how to detect a read-only repository mount, what to skip when one is found, and how to resolve a ref and read from it without ever attempting a write. Its resolution also names the default branch that the scanners and the docs-repository commands switch onto or cut a branch from — by its name (`main`) rather than the `origin/main` ref, since `git switch` refuses a remote-tracking ref — and where your clone has no local copy of that branch, makes one before the switch with no write to `.git/config`, since git's own guess at it writes an upstream there, and where a container mounts that file read-only moves your working tree onto the branch's files while leaving you on the branch you were on. Its ref reading also serves a writable clone, where a `code-scanner` brief asks it to read the default branch's tip by ref: one capped fetch, then every read at that ref, the checkout left on whatever branch it was on.
- `scan-refresh.md` — when a scanning command's `code-scanner` dispatches refresh a clone, and when they read the session's own repository at its default branch by ref instead, its checkout left where it stands: the refresh question and its three-option and four-option forms, the question a command asks again when that repository joins its list late, the by-ref read a command with a fixed policy makes, the `refresh:` lines each repository's brief carries, a by-ref read that fails, and the line the run's report gives each read by ref. How such a read is done stays `read-only-repos.md`'s.
- `implementation-format.md` — the append-only implementation record a keyed run writes: one block per run that committed, with one entry — the code repository the run branched — holding refs and never a summary, kept in the folder of the unit implemented — an Epic's, or the PRD folder's for a broad slice. It owns the commit convention, and the two-source read a documenting run performs over that record plus a commit-message scan matching each key whole, with the boundary each consumer takes over both; that read also has the optional pull-request layer, through which a merged GitHub pull request naming a key adds the commits it landed. Its `unit-branch` entry point names the branch that carries a unit's work in one repository and the state it is in, and holds the merged test that says whether a block's work has merged.
- `next-phase-offer.md` — the family-wide contract for the next-phase offer every pipeline command surfaces at the end of its run, naming the natural next command(s), including the `<merge-clause>` placeholder and its overflow rule.

## Review, triage and escalation

The shared discipline between a reviewer's findings and a fixer's edits, and the shape every stop-and-ask prompt takes.

- `finding-triage.md` — the step between a reviewer's findings and a fixer's edits: verify each finding at the location it names; keep it, mark it unverified with what would settle it, or dismiss it with a reason; triage a re-review against the run's earlier rulings over the same artifact; and hand the fixer survivors only.
- `escalation-rules.md` — the canonical `choices:` arrays for escalation decision points. It owns the shape every array in the family must have: **2–4 options, and never an authored "Other"**, because the question tool renders at most four and supplies the free-text escape itself — and **a selection carries no text**: choosing an option returns its label and nothing else, so an option that needs your text (a name, a path, a key, a reason) is labelled `… (you'll be prompted)` and is followed by one plain-text question asking for it (save *Provide manual fix notes*, which first shows the notes the run drafted, where it can draft them, to apply or replace with your own), and a question whose whole answer is text with no default is asked in plain text rather than as a picker. It also owns the rule that **a recorded review verdict names the version it was taken against** — the one-fix-cycle cap assumes a fix only removes defects, and a fix can introduce something the re-review then finds with the budget already spent, which would leave a `PASS` on record beside a file the `PASS` never saw. Every command that records a verdict says what it covers, and names any edit that followed it, in its final report and in its pull request, where every finding left open is listed too. It owns **the offer to apply what a review leaves open**: after each review whose verdict is not `BLOCK`, or a `BLOCK` a settle prompt's **Proceed** settled as not one, a command that fixes its findings inline — and `/dev-workflows:implement`, through `review-fixer` — offers once to apply the ones whose fix is only an edit, so a known defect never reaches a pull request without the user deciding it should; the question lists them in its own text, one line per finding, never pointing at a list printed elsewhere. In `/product-workflows:create-prd`, `/product-workflows:update-prd`, `/product-workflows:create-ard`, `/product-workflows:specify`, `/product-workflows:update-spec` and `/dev-workflows:design`, each finding whose fix needs a decision is then put to you in a question of its own — after the offer, whatever you answered, or alone where no finding whose fix is only an edit is open: the reviewer's options for it, or answers the run drafts where the reviewer gives none, at most three, and *Leave it open*, which records it as the artifact keeps its open questions or, in `/design`, leaves it in the final report and the pull request. Before a `BLOCK`'s fix cycle in a command that fixes inline, it owns **a `BLOCK` review's other findings**: where findings whose fix is only an edit stand beside the BLOCKERs (or, in those six, findings that need a decision — on *Fold*, each then asked on its own in the fix cycle; on *Fix the BLOCKERs only*, left to the questions after the re-review), the run asks once whether to fold them into that fix cycle, so the one re-review covers them. It owns **manual fix notes**, one answer to a BLOCKER escalated as unresolved: one BLOCKER at a time, the run drafts the notes from the BLOCKER's suggested fix and asks whether to apply them or to write your own, or, where the fix needs a decision, drafts nothing and asks for your notes, naming the decision; and every request for your notes says that the run waits for them. And it owns **the unspent re-review**: a `PASS`, a `PASS WITH RECOMMENDATIONS`, or a `BLOCK` the first settle prompt's **Proceed** settled before any fixer ran spends neither the fix cycle nor the re-review, so a run that then edits the reviewed artifact in answer to its findings offers that one re-review before going on — never a second one after a `BLOCK`'s fix cycle. It owns **the read after the last review**: once the cap is spent, a command that dispatches `overlap-reader` — `/dev-workflows:design`, `/product-workflows:specify` and `/product-workflows:update-spec` — has that agent read once more, before the handoff, each edit answering the last review's findings and each decision settled at its questions; each conflict it returns is put to you as a question, and the verdict's record names the read and the number of conflicts it returned. It is not a review and raises no cap, and where you declined the re-review the cap still held, no such read follows. It owns a rule for the commands that fix their own reviewer's findings inline: **an inline fix is read against what it overlaps** — every requirement it adds or changes against everything that overlaps it, as `grilling-technique.md` lists it, and an operational step against everything its selector reaches, before the re-review, so the one re-review is not spent on a contradiction the fix itself wrote. And for the six commands whose artifact keeps open questions — `/create-prd`, `/update-prd`, `/create-ard`, `/specify`, `/update-spec`, and `/epics`, whose Epics keep theirs as `[NEEDS CLARIFICATION]` markers — it owns **a finding left open that needs a decision is recorded in the artifact** as an open question — in the five of them that ask such a decision first, one you chose to leave open, or one no question was put for — because the next phase reads the artifact and never the final report. Every command in the family that presents a choice list loads the `core` part — that shape and the rules for presenting a list — as a step of its own, **Load the question rules.**, before its first question: a citation of it inside a rule statement is read as a source note, not as a step, and the build fails a command whose first question comes before that step.
- `pre-lint.md` — deterministic, grep-expressible structural checks a reviewer-gated command runs against a just-authored artifact before spending an Opus review pass on mechanical structure.
- `source-truth.md` — the Implementation-vs-Description discrepancy-escalation protocol: how to verify a user-visible claim against shipped source, and what to do when the written description and the source disagree. It is also the one authority on how `/docs-workflows:document` and `/docs-workflows:release-notes` take a decision `/dev-workflows:conformance` recorded instead of asking again: which conformance records, and which of their entries, count; which of two entries on one claim wins; and what each decision becomes in the documentation — and, for `/docs-workflows:document`, how far the code has moved since the record was written.
- `epic-picker.md` — the progress-aware Epic picker the Epic-unit commands share: enumerate the child folders under a resolved PRD folder, mark each from the artifacts present rather than from a declared status, and never pick silently. *The cap* is the half no static check can reach, because the array is built from a directory listing.
- `instruction-file-maintenance.md` — the verification discipline for changes to agent-instruction files: verify every command claim against what actually runs it, itemise a narrowed rule as a deletion, and never retire a rule on "it looks derivable."

- `session-diagnosis.md` — the rules `/diagnose-session` and its `session-analyst` agents follow to read a session's transcripts on disk: context safety, locating a session, the case file, the seven dimensions, the findings shape, the report, and the family-involvement statement that names a location and proposes no fix.
- `session-hygiene.md` — the family-wide contract for session-hygiene suggestions: flush resume-critical state to disk, then suggest the right context action, after a big command finishes or a long run checkpoints; and the environment a command that resumes from a session file records there and compares on a resume, before its handoff and before its terminal writes, stopping on a mismatch; and `env-check`, its counterpart for every run: before the handoff and before each write of the run's tail, and at its terminal commit where the record the run's start made stands — there for `$SPECS_PATH`'s real path and its `origin` alone — the run compares the environment it stands in with the `Environment:` line its preflight printed, and where they differ — a conversation resumed in another container — it says so once and commits, hands off and records nothing more in the specs repository there, asking nothing.

## Environment and routing

What the family needs configured around it, and how a command chooses the model it runs on.

- `run-flags.md` — the three run flags every applicable command accepts (`--skip-costs`, `--skip-feedback`, `--enforce-model`), their `$WORKFLOWS_SKIP_COSTS` / `$WORKFLOWS_SKIP_FEEDBACK` / `$WORKFLOWS_ENFORCE_MODEL` environment defaults, the model-alias table, the record of the run's flags built at its start, the `strip-run-flags` / `skip-cost` entry points, and the rule that every `mktemp` a run executes runs with `TMPDIR` set to the session's scratchpad, where the session names one that exists — save for a file a process outliving the session goes on writing, such as a server's log.
- `dependencies.md` — the two kinds of relationship a plugin here can have with another: a declared, host-resolved `dependencies` entry inside this family (an unsatisfied one disables the plugin), and an optional companion outside it resolved at runtime with graceful fallback.
- `bounded-run.md` — the one portable way to cap a call's run time: the bundled `scripts/bounded.py <seconds> <command…>`, which needs only `python3`, so a host with no `timeout` binary — macOS ships none — takes the same branch as any other instead of failing every capped call with `command not found` and reading it as a skip; exit 124 means the call timed out. Every slug→clone map in the family, `components.md`'s among them, the documentation-grounding index check in `docs-grounding.md`, and `docs-grounder` run their capped calls through it.
- `classification.md` — lives under `model-routing/`, not the top level; the single source of truth for task-complexity classification, the model fallback chain, the mandatory Opus code-review checklist, and the model-routing record every pipeline command keeps from its own classification step.

## Bundled reference sets

One subtree carries per-agent document-format contracts, counted here rather than enumerated file-by-file.

- `handoff/` (2) — one input/output document-format contract per agent this plugin ships that needs one, read by the agent itself rather than by the dispatching command.

Every file in `references/` is markdown except `cost-prices.yaml`, which is a data file rather than a reference page and is named above for exactly that reason: it is user-overridable, so a reader has cause to open it.

## References that load by part

`escalation-rules.md`, `finding-triage.md`, `next-phase-offer.md` and `session-hygiene.md` are long rulebooks of which a run seldom needs every rule at once, so each also loads by part. The reference stays the one file above, the only one anyone edits. Each of its parts is assembled from that file into a generated file under `reference-parts/<name>/`, together with the reference's always part, the other parts that part needs and the reference's rule index, under a line naming every part the file holds; a generated file is never edited by hand. A caller names the part after the reference, `Skill(skill: "workflows-core:reference", args: "session-hygiene resume-pointer")`; `args: "<name> index"` loads the rule index alone, which names the part holding each rule; and a request with no second argument reads the whole reference, as it does on any other reference, save where an entry point below serves it from a file of its own, or where it is a citation of `specs-repo-git.md` that the `specs-git` skill's text serves, which reads nothing more — the loader hands that reference's two entry points to that skill, reading no reference for them ([Skills](#skills)). A second argument that names no part of one of these does not stop the run: the loader reports it, reads the reference's rule index, and then reads the part the index names for the rule the step applies — or the whole reference, where the index names no part for it — never reading anything else in its place, and never applying a rule it has not read. Every command, agent and reference in a dependent plugin that cites one of these carries a paragraph telling a run to load the part that holds a rule before applying it, unless that part is already in the conversation word for word, and never to guess a part's name: until the run holds the index, which every part carries, it loads the index first.

## Entry points with a file of their own

`phase-handoff.md` does not load by part, and it is too large for one read, but three of its entry points read a file of their own: `require-on-main`, the gate a command runs before it reads a prior phase's artifact; `branch-check`, the check every command that resolves a folder in the specs tree runs on the branch it stands on; and `handoff-to-main`, the handoff a producer offers at its end. The first two run early — in most commands in Phase 0 — and a read made early is carried by every later step of the run. Each needs only part of the reference: the gate about half of it — the check, its state table, its stop contract, the rules it applies from elsewhere in the file; `branch-check` its own section, the hard rules, the branch-resolution rules and the one remedy it shares with the gate's state table; and `handoff-to-main` the hard rules, its own section, the outcome lines, the consent choice and the rules of the downstream classes that choice is picked by, but not the classes' register of artifacts. Their files, under `reference-parts/phase-handoff/`, are generated from that one source like the parts above, each carrying the sections it needs whether or not another carries them too, never edited by hand, and each names in the line under its title every section it holds. A request naming an entry point — `args: "phase-handoff require-on-main"`, `args: "phase-handoff branch-check"` or `args: "phase-handoff handoff-to-main"` — reads that entry point's file and runs it from there; a producer makes the last at its consent step, presents the consent choice from that file, and runs the handoff only on its first option. A citation of a section one of these files holds — of one a file holds in part, only for the text that file's line names — is a lookup the file serves: wherever the run has already read that file, or the whole reference, in any phase, the citation works from that copy and reads nothing, so the phases between the gate and the handoff cite those sections at no cost; where no copy is in front of the run, it reads the file in a phase that requests its entry point, before the request or after it — that phase reads the file at most once — and the whole reference anywhere else. Every other request reads the whole reference, as on any other reference — a lookup in the classes' register among them, which a pre-handoff maintenance step makes — and so does a citation of a section no file in front of the run holds, of one held in part for any other text, or of the reference by no section, which is why a command names that contract in words where it only explains it, ahead of its first load of the whole reference. One reference is the exception to that: on `specs-repo-git.md`, the two entry points the loader hands to the `specs-git` skill read no reference, and neither do the citations that skill's text serves ([Skills](#skills)). A read of the whole of `phase-handoff.md` covers every one of these files. The loader keeps these rules for the entry points' files in its entry-point rules, a file beside it, which a request on `phase-handoff` reads with or before its other reads, unless the run already holds it word for word; the loader's own text, which comes with every request, names only the entry points, where their files are and where the rules are.

## Skills

Three skills ship under `skills/` — reusable guidance packaged for the `Skill` tool, distinct from a `references/` file that a command or agent reads directly by path. The two that read a reference, `reference` and `model-routing`, exist for the same reason: `${CLAUDE_PLUGIN_ROOT}` resolves to the *reading* plugin, so a command or agent in a sibling plugin cannot expand it into this plugin's tree — its own plugin root names the sibling, and the shared corpus is not there to open. A skill invoked by its namespaced name resolves the path on the caller's behalf instead. Neither reading skill reads a file again while the text a request needs is in front of the run: where that text is already in the conversation word for word, from a read made in the same run, the caller works from it and nothing is read — save that an entry point is executed, and a task classified, only from a read made in the current phase (the section of the command running — a phase, a step or any other, the text before its first heading counting as one — or an agent's whole dispatch), while a rule is looked up from any read of the run. The text a request needs is the whole file, except for a request with a second argument on a reference that loads by part, a request the file of an entry point above serves, and, on `specs-repo-git.md`, the two entry points the loader hands to the `specs-git` skill, which read no reference, and the citations that skill's text serves (below); and a read short of every line — a section, a range, a search — covers no request that needs the whole file; consecutive ranges from the first line to the last, taken where one read cannot hold the file, are one read of every line. The file is read whenever that text is not in front of the run, whatever removed it — it was never read in the run, only a different part of it was read, or an earlier read has since been replaced by a summary or cleared, since a summary of a reference is never its text — and wherever the run cannot tell. On a reference that does not load by part, a second argument that names none of its entry points — an entry point is the first word of a code span in one of its headings, such as `resolve-address` — fails the request: the loader reports the argument that named nothing, and the run stops as its command, or its agent, stops. A run that already holds the loader's text from an earlier request knows the paths it names, so it makes a request's `Skill` call and that request's reads in one turn — a file's line count where a whole read needs it, and each file's first read — and any further ranges together in one more; no rule of the loader's is skipped for a read made before its text arrives: where that text names a different read, the run makes that read too, since a read it does not call for serves no request.

The third skill, `specs-git`, reads no reference while its script can run. It resolves the path of `scripts/specs-git.py` the same way and runs it for a run's specs-repository start and end — the preflight and the terminal commit `specs-repo-git.md` describes — keeping the state the two share in a file of its own under `~/.claude/dev-workflows/specs-git/`, outside every repository, which the end removes once it has finished and a start in a later session removes after seven days where the end did not. The script asks nothing, and the skill says which of its lines to print and where. A request naming either entry point — `args: "specs-repo-git specs-preflight"` or `args: "specs-repo-git commit-artifacts"` — reaches it through the loader, which hands the request on and reads no reference for it; this plugin's own commands call it directly. A citation of `specs-repo-git.md` in a command's own start or end step, and one of its run key set, its notices or its outcome lines anywhere in a command's own text, is served by the skill's text and the script's output and reads nothing more. Every other request on `specs-repo-git.md` reads the whole reference, as a request on any other reference does, and so does a run whose script cannot start, which runs that entry point by hand from the reference.

| Skill | Invocable | What it's for |
|---|---|---|
| `model-routing` | No — loaded internally, at the classification step, by every pipeline command in the family; all but `/frames` ship from a plugin that cannot reach this one's `references/` by path | Resolves the classification reference and hands the caller the task-complexity classification rules and the model fallback chain. |
| `reference` | No — loaded internally, wherever a command or agent must read a shared reference or run one of its entry points | Hands the caller a reference, or its entry point or part, to follow as written; a `specs-repo-git` start or end request goes to `specs-git`. Every dependent plugin reads the corpus through it. |
| `specs-git` | No — loaded internally, at the start and the end of every command that writes into the specs repository | Runs `scripts/specs-git.py` for a run's specs-repository start and end, keeps their shared state across the run, and says which lines to print. |
