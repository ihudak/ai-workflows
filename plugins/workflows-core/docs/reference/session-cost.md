# Session cost

Cost attribution is one of the subsystems this plugin exists to hold: the shared cost-emission reference and the `cost-prices.yaml` price table beside it are what every plugin in the family reads, and `scripts/session-cost.py` is what does the arithmetic. This page documents the subsystem from the side that invokes it — what a command has to declare, what it gets back, and what the commands *in this plugin* charge to.

## What a command declares

Every cost-emitting command passes a `phase` and a `role` label at the point it calls the shared entry point, and the shared cost-emission reference carries one attribution row per command. A command that cannot label itself in advance marks both labels *inferred* and lets the cost phase resolve the real values from the run's own context.

Six commands emit a cost entry here, unless `--skip-costs` ([below](#skipping-cost---skip-costs)): `/diagnose-session`, `/feedback`, `/frames`, `/prompt`, `/prompt-brainstorm` and `/prompt-grill-me`. None of the six carries a fixed pair — each infers, from the folder it resolved (`/frames`), from the target command it is correcting (the four feedback commands), or, for `/diagnose-session`, from a target that is always `n/a`, which lands it on `plugin-feedback`. [Roles and phases](../roles-and-phases.md) says what those resolved labels mean. `/statusline` is the one command in this plugin that emits nothing: it sets a configuration value rather than running a task.

## How cost is computed

`scripts/session-cost.py` reads the assistant-turn `usage` and `model` fields already present in the session's main transcript, plus every subagent transcript dispatched during the window being measured, sums token counts per model — each API message once within the window, though Claude Code writes one response as several records that repeat its usage — and multiplies by the price table in effect for that run. Claude Code's own running dollar total reaches the transcript only now and then — a `cost-state` record between sessions, never at a command's edges — so cost is always **computed** from token usage against a price table. That makes it an estimate that drifts from Claude Code's own accounting by the accuracy of that table, and by every compaction in the window: Claude Code bills the call that summarises a context, on `/compact` or when the context fills, but records no token usage for it, so the computed figure leaves it out and the entry's `compactions:` field counts what it left out.

The session's main transcript is the one in Claude Code's project folder for the working directory **whose newest record of the command now running** — typed, or started through the Skill tool by another command — **is the newest such record of any transcript there**, not simply the newest file: two sessions open in the same directory would otherwise charge each other's spend. Where no transcript records the command, the run prints `cost not measured — …` and writes no entry.

The price table lives at `${CLAUDE_PLUGIN_ROOT}/references/cost-prices.yaml`, keyed by model id. Override it with `$DEV_WORKFLOWS_COST_PRICES`; see [Environment](environment.md) for the resolution order. An unknown model is still recorded with its token counts, priced `cost_usd: null` and tagged `note: unpriced-model` — the run never fails on it.

**Fast mode and US-only inference are priced, because they change the rate rather than the token count.** Claude Code records `usage.speed` and `usage.inference_geo` on every assistant message, and the engine buckets each model's tokens by that pair before pricing. A turn run under `/fast` prices from the model's own `fast:` block in the table — `$8`/`$40` on Opus 5.5, `$10`/`$50` on Opus 5 and Opus 4.8, twice their standard rates — and US-only inference multiplies every category by 1.1, stacking on fast mode. A row priced this way says so: it carries `modifiers: [speed:fast]` (or `inference-geo:us`, or both), so a cost per token that looks high explains itself instead of looking like a bad price table. Its token counts are still the plain totals — only the cost is a sum over variants. Where the table cannot price a variant — a fast turn on a model with no fast-mode rates, or a residency with no multiplier — the row's cost is **null** with a `note:` naming which, never the standard rate: that figure would be confident and known to be low by half.

**Prompt length is priced on the one model that bills by it.** Haiku 5.5 charges `$0.10`/`$0.50` per million tokens while a request's prompt is 100,000 tokens or fewer, and `$0.50`/`$2.50` above that. Its table entry carries a `long_context:` block holding that threshold and the higher rates, and the engine checks each message's own prompt (input, cache reads and cache writes together). A message over the threshold bills all its tokens at the higher rates, and a row with any such message carries `modifiers: [long-context]`. A `long_context:` block with no threshold prices the row **null** with `note: unpriced-long-context`.

The window a figure covers is **chained, not fixed**: a small local checkpoint file, keyed by session id and never committed, records where the last cost phase left off, and the next one picks up exactly there. Three commands run back to back produce three entries whose windows are contiguous.

## Spend a command cannot measure itself

### Ceded runs

A **ceded** run is a `/prompt-brainstorm` or `/prompt-grill-me` run, which hands the session over at its Phase 3 — to a brainstorming skill, or to a long interactive grill — and never gets it back, so it cannot write its own cost entry. A `/prompt-brainstorm` run that finds the brainstorming skill not installed hands nothing over and ends at Phase 3, but defers its entry in the same way, so it counts as ceded here too.

Neither command can run a cost phase after its own expensive work, because there is no "after" that it controls, and one placed before the hand-off would price the logging prologue alone. So the run that cedes records the labels it would have claimed into a local, transient, never-committed file beside the checkpoint, and **the next cost-emitting run in the session writes the entry on its behalf**. **`--skip-costs` stops that entry from either side**: a ceding run under the flag marks its record `skip`, so the replaying run still carves the segment out of its own window and then writes nothing for it, and a replaying run under the flag drops every pending record unreplayed, naming each in its output.

The boundary between the two runs is not guessed. A transcript already records every slash-command invocation, so the replaying run splits its own measurement window: the ceded run gets the segment from its own invocation to the next command of any kind, and everything else stays with the replaying run. The slices are disjoint and sum to what that run would otherwise have claimed whole.

Two details there are doing real work. The ceded run is found **by name**, not by counting invocations — a window often contains commands that emit no cost entry at all, and an interrupted run leaves a mark too, so counting positions would shift every attribution by one. And a command invocation is recognised by its whole envelope rather than by one tag, because Claude Code writes built-in and plugin commands in two different tag orders. If a recorded intent matches no invocation, nothing is written for it — its spend stays with the replaying run, and the run says so rather than attaching it to a neighbour.

The replaying run may be in **another plugin**, and usually is: the deferred claim is resolved from whichever cost-emitting command runs next in the session, wherever it ships from.

**But only from a command of this family, and that boundary is the point.** A claim is matched against a manifest of the family's own `<plugin>:<command>` names, and a command from any other marketplace matches nothing in it. Such a command still **ends** the open window — its spend is its own and is never absorbed into somebody else's figure — while remaining unclaimable, so a deferred claim it interrupts is reported as unmatched and dropped rather than attached to it. The discipline errs the safe way in both directions: the worst outcome is a claim you can see was not resolved, never one command's spend quietly filed under another's phase.

## Status-line cross-check

Installing the status line with [`/workflows-core:statusline`](../commands/statusline.md) adds a second cost figure to a cost entry. On every render, given `jq` on the `PATH` the status line runs with, it writes Claude Code's own running cost for the session, `total_cost_usd`, to one small snapshot file per session, `~/.claude/dev-workflows/cost-snapshots/<session_id>.json`, overwritten each time. A cost phase subtracts the figure the checkpoint recorded at the session's previous cost phase from the current snapshot and writes the difference into the entry as `cost_statusline_usd`, beside the computed `cost_computed_usd`.

The field is there only when a snapshot exists and an earlier cost phase in the same session has recorded a baseline, so a session's first cost phase never carries it, even with the status line installed. It is also left out of a window that a ceded run's deferred record splits, since a whole-window figure cannot be divided between two entries, and wherever Claude Code's status-line input carries no cost.

Read the two figures against each other. The status-line figure is Claude Code's own price and the computed one is the price table's, so over a window with no compaction they differ by cents, and a larger gap means the price table needs refreshing. Over a window that held a compaction the status-line figure is higher by roughly what the compaction cost, which the computed figure leaves out — dollars on a large context — and the entry's `compactions:` field says when that is so. The status-line figure also lags slightly at the end of a window, because the status line renders after the final turn.

## Skipping cost (`--skip-costs`)

Under `--skip-costs` (or `$WORKFLOWS_SKIP_COSTS`), the cost phase never calls `emit-cost` and never loads the shared cost-emission reference — it runs the `skip-cost` entry point of the shared run-flags reference instead. The checkpoint (see above) still advances exactly as a full run would, so the next command's window is still measured from the right place; nothing else happens. No cost entry is written, no pending file, and no reconciliation offer. Any deferred record left by a prior `/prompt-brainstorm` or `/prompt-grill-me` run — waiting to be replayed into this run's entry — is dropped instead: the skipping run prints `cost attribution for <command> dropped (--skip-costs)` once per record, then deletes the file, since a checkpoint that has already advanced past those records' boundaries could never match them anyway. `/prompt-brainstorm` and `/prompt-grill-me` never run `skip-cost` themselves — both cede the session before a cost phase could run at all — so under this flag each instead writes its own deferred record with `"skip": true`; the replaying run still carves the ceded segment out of its own window for correct attribution, then discards it rather than writing an entry for it.

The run reports `Session cost: skipped (--skip-costs)` or `Session cost: skipped (WORKFLOWS_SKIP_COSTS)`, naming whichever set it, in place of the usual persisted-path line.

## Where cost files land

Cost writes to a `cost/` subdirectory with one file per session — `<PRD-dir>/dev-workflows/cost/<sid8>.md`, named after the first eight characters of the session id — so no two engineers' commands can collide in one file. Where no folder resolves, the entry goes to a pending file under `$SPECS_PATH` and is offered for relocation once a real key is known; where nothing resolves at all, it stays in the run's printed output. On a run that found `$SPECS_PATH` misplaced in any of the cases [Environment](environment.md) describes, or found its environment changed since its preflight printed it, as the same page says, the entry stays in the run's printed output instead, whatever else resolves, so nothing is written under a path the run found wrong. That is the whole ladder for **these** commands; the shared ladder carries a further rung, ahead of pending, that only the documentation plugin's runs it names, and a `/security-workflows:scan` with no key, can reach, so none of the six above ever takes it. The plugin never writes into your current working directory, where it is not the specs repository, since it may be a code repository.

The full mechanics — the resolution ladder, the entry format, the status-line cross-check [above](#status-line-cross-check), and the attribution table itself — live in the shared cost-emission reference ([References](references.md)), which this page describes rather than restates.
