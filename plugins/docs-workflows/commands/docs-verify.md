Verify a drafted documentation backlog unit: $ARGUMENTS

`/docs-verify` takes one `drafted` unit of the documentation backlog — its page drafted as `/docs-workflows:docs-write` drafts one — and resolves the page's claims by its audience's method. **A user page is walked**: `walkthrough-composer`, an agent that reads the page and never the code, composes the walkthrough that observes every claim, or extends the one the unit has, and the operator walks it in this session, one question per step, each answer written into the walkthrough as it is given — or, under `--prepare`, the run stamps the walkthrough for the page as it stands, commits it and prints a checklist, from which somebody walks it outside the session and records each result in the file by hand, for a later run to take behind its question. **An engineering page is read**: `claim-reader`, an agent that holds no shell, reads its claims in an export of the code at today's commit and in the page's ARD at the specs default branch, and one question shows the readings. Outside a prepare, the run has `doc-writer` apply the answers — the walk's, or the readings the operator took — removes the page-level marker, holds the page to the style, build and review gates, and commits the page — with a user page's walkthrough and images — and the unit's move from `drafted` to `verified` in **one commit** on a branch of the documentation repository. A unit that cannot move stays `drafted`, and the run commits the record of why: a claim it could not resolve, or a walk that did not finish, whose answers the next run takes; a prepare, which moves no unit, commits the stamped walkthrough instead. **A backlog run** is a run of a command that takes the backlog's units one at a time and moves each one it finishes;
