Serve the documentation site for a profiled docs repo: $ARGUMENTS

`/docs-serve` runs a profiled documentation repository's own dev server and reports a URL that actually opens from the host — on any profiled repo, not only one `/docs-workflows:docs-init` scaffolded. It reads the `dev_servers` block `/docs-workflows:docs-profile` already wrote; it never picks a generator, a port, or a start command of its own. **It writes no documentation and no artefact** — no branch, no commit, no pull request, and (see Phase 0) no `specs-preflight`. **It also runs no review gate**: D17 — the docs-workflow family design's rule that every artefact-writing command of the family its §4 table lists (`/docs-init`, `/docs-brand`, `/docs-audit`, this command, and the commands that design plans after them — not every command in this plugin) passes a high-tier review before it is trusted — names `/docs-serve` as that family's sole exemption, precisely because there is no artefact here for a reviewer to check.

**Signature:** `/docs-serve [<docs-repo-path>] [--internal] [--stop] [--status] [--build] [--port <n>]`

## Phase 0 — Resolve

**Strip the run flags first.** Execute `strip-run-flags` (`Skill(skill: "workflows-core:reference", args: "run-flags strip-run-flags")`) on `$ARGUMENTS` before anything else reads a token: it removes `--skip-costs`, `--skip-feedback` and `--enforce-model` (with any `=value`) and resolves each against its environment default. No run flag applies to this command — it dispatches no `impl-maintenance`, calls no cost-emission entry point, and invokes no model-routing skill, since starting a process and reporting a URL is not a task to classify — so `strip-run-flags` reports an explicit one as ignored. It takes its own flags (`--internal`, `--stop`, `--status`, `--build`, `--port <n>`) and an optional `<docs-repo-path>` to protect, but a stray run-flag token must not be misread as one of them.

Strip every recognized flag from `$ARGUMENTS` wherever it appears — `--internal`, `--stop`, `--status`, `--build`, and `--port <n>` (consumes the token immediately following it as its numeric argument) — before reading a positional token; the flags themselves are handled in **Mode dispatch**, below. What remains is the optional `<docs-repo-path>`.

Execute **`resolve-docs-repo`** from `${CLAUDE_PLUGIN_ROOT}/references/docs-workflow/repo-resolution.md` §1 — the signal-positive form, since this command needs a docs repo that already exists, never one to create. Do not restate its ladder here; the entry point owns it. Report which rung answered, per its own hard rule — a command that quietly works in an unexpected directory is expensive to unpick afterwards.

Record the resolved absolute path as `<repo>`, and its git work-tree top level as `<repo-root>` — `git -C <repo> rev-parse --show-toplevel`, or, where `<repo>` is in no git work tree, `<repo>` itself as `builtin cd "<repo>" >/dev/null && builtin pwd -P` prints it — `builtin cd`, its output discarded, wherever a `cd` runs in the Bash tool's own shell and this command reads what follows it, and `builtin pwd` wherever it reads what a `pwd` prints: that shell carries the user's aliases and shell functions (`${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/render-verification.md` §2, **Portability**), and a `cd` or a `pwd` of theirs would otherwise run in its place and could print into the path read. `<repo-root>` is the profile's one home (`${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/docs-profile-schema.md`, **Where the profile lives**): wherever a mode below reads the profile, runs a command it records or reads and writes the state file, it does so at `<repo-root>`, the state file sitting beside the profile — also where `<repo>` is a site below that top level, such as a monorepo's `docs/`.

**No `specs-preflight`.** This is deliberate, not an omission: `/docs-serve` writes nothing into `$SPECS_PATH` — it starts a process in the resolved docs repo and reports a URL — so opening a branch discipline for a run with no artefact behind it would be ceremony. Its closest sibling is `/workflows-core:statusline`, not `/docs-workflows:document`: like that command, this one runs no `specs-preflight` and no terminal `commit-artifacts`. What the commands it runs write is theirs — a server's own caches, and in `--build` mode the site output of the profile's build command, wherever that command puts it. The only things it writes itself are three: Phase 7's pid/port record, under `<repo-root>/.dev-workflows/`, beside the profile; where no rule ignores that record yet, the one line naming it in the repository's local, never-committed exclude file, which keeps it out of `git status` unless someone committed a copy (Phase 7); and the log each start writes (Phase 4), a `dw-serve-*` file under the system's temporary directory, which Phase 7 records and which is removed as its **A log goes with its entry** says — never anything under `$SPECS_PATH`.

## Mode dispatch

Exactly one of `--status`, `--stop`, or `--build` drives this run; where more than one appears in `$ARGUMENTS`, the first encountered (left to right) wins, and the run says which of the others it ignored.

- `--status` → **`--status` mode**, below. Reports recorded state; starts nothing.
- `--stop` → **`--stop` mode**, below. Stops a recorded server; starts nothing.
- `--build` → **`--build` mode**, below. Runs the profile's build command; starts no server.
- None of the three → the default serve flow, **Phase 1** onward.

**Its tools must be present.** Every mode but `--build` judges ports with Phase 2's tests, and those need `curl` for the reachability probe and four reads besides: the socket table, to name the process that holds a port and, on a port nothing answers on, to say whether anything is listening there, which is what makes that port taken rather than free (`render-verification.md` §2, **Portability**, defines free); that process's working directory, to place it in a checkout (Phase 2's **Checkout first**); and its parents and command lines, to match it to a server. Following a process group this command started — which Phase 2's living-entry test, Phase 5 and `--stop` all do — takes three reads more: a process's group, its start time (Phase 7), and the states of the group's members (the gone-group test, `render-verification.md` §2 step 5). `${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/render-verification.md` §2, **Portability**, defines every one of those reads, with one source per operating system: on Linux — wherever `test -r /proc/net/tcp` succeeds — the kernel's own tables under `/proc`, which need nothing installed and no root for this user's processes; anywhere else, `lsof` for the socket table and a working directory, and `ps` for the rest. They need `bash` too: every call this command makes on a process group — Phase 4's start, the gone-group test Phase 5 polls and Phase 7's own-group test asks, and `--stop`'s signals — is an explicit `command bash -c`, whatever shell the Bash tool itself uses (`render-verification.md` §2 step 2 says why). So before `--status`, `--stop` or the serve flow does anything else, confirm that `curl` and `bash` are present and, where `test -r /proc/net/tcp` fails, that `lsof` and `ps` are too — each tested as `${CLAUDE_PLUGIN_ROOT}/references/toolchain-preflight.md` §3 tests a tool run through `bash -c` or as `command <name>`, never by a bare `command -v`, which an alias or a shell function of that name passes. None of them has a degraded mode. A probe that cannot run is never read as a port that answers, nor as a free one, and a group call that cannot run is never read as a gone group: `command bash -c 'kill -0 -- -<pgid>'` exits 1 both where the group is gone and where this user may signal no member of it — two answers §2 step 5 tells apart by the process table, which is what decides a group gone — and 127 only where `bash` itself could not run, so a 127 from any group call is no answer at all. Without a socket table nothing establishes which process holds a port — a page can say which site answers there, but never whose checkout serves it or which process `--stop` would have to end — so every identity this command gave it would be a guess. Without `ps` off Linux, no process the socket table names can be matched to a server, and no group this command started told from one that reuses its id. **Test `bash` first, and where it is absent stop with `DOCS_SERVE_NO_BASH` alone**: §3's test runs *through* `bash`, so with none installed every other tool here exits 127 and reads missing though it is installed — none of them was tested, so none of them is reported. Otherwise, where one of them is missing, stop with its message; where several are, print each of their messages, in the order below, and stop:

`DOCS_SERVE_NO_BASH: bash is not installed here (or not on PATH), and /docs-serve starts, tests and signals every process group it follows through an explicit bash -c — without it a group that still runs and one that is gone look the same, so nothing was probed, started, stopped or recorded. Install bash and re-run.`

`DOCS_SERVE_NO_PROBE: curl is not installed here (or not on PATH), and /docs-serve judges every port with it — without it a port that answers and a free one look the same, so nothing was probed, started, stopped or recorded. Install curl and re-run.`

`DOCS_SERVE_NO_SOCKET_TOOL: this host has no /proc/net/tcp to read and no lsof on PATH, and /docs-serve reads which process holds a port from one of them — without either, nothing can say whose server answers on a port, or which process --stop would end, so nothing was probed, started, stopped or recorded. Install lsof and re-run.`

`DOCS_SERVE_NO_PS: ps is not installed here (or not on PATH), and on a host with no /proc/net/tcp to read /docs-serve reads the parents and command lines of the process holding a port with it — without it no process can be matched to a server, so nothing was probed, started, stopped or recorded. Install ps and re-run.`

A tool that exits 127 later in the run — it could not run after all — stops the same way at that point, with that tool's message, and the stop names what the run had already done: a server it started and could not poll, test or identify, left running and unrecorded, its log removed (Phase 7, **A log goes with its entry**), or an entry it signalled but could not re-probe. On Linux no read needs `lsof` or `ps`, so of these only `curl` and `bash` can stop a run this way there. `--build` needs none of these: it runs the build command and reads its exit code.

## `--status` mode

Read `<repo-root>/.dev-workflows/docs-serve.state.json` (Phase 7 writes it). Absent, or holding no entries → report `No /docs-serve state recorded for <repo>. Nothing appears to be running (a server started outside this command is invisible to --status).` and stop cleanly — an idle repo is the ordinary state, not an error.

Otherwise, for each recorded entry — one per port, the key Phase 7 writes: test whether it is living (Phase 7), and re-probe the port and URL with the same reachability check Phase 2 uses. Report, per entry: port, space (and visibility, where recorded), pid, URL, and one of *running*, *starting* (below) or *stale*, decided by what follows — a probe that cannot run gives no status at all, and stops the mode with `DOCS_SERVE_NO_PROBE`, as a group call whose `bash` cannot run stops it with `DOCS_SERVE_NO_BASH` (Mode dispatch). **A living entry's page is not asked**: where the socket table names the entry's pid on its port, that is Phase 2's process evidence, and Phase 2's site test never gates it — a server whose page names no site, such as a VitePress dev server's client-rendered shell, is *running* while its process holds the port. An entry that is not living — one recording no pid, which Phase 5 wrote when its readiness poll timed out or where the socket table named no process on the port that answered, **and one whose recorded pid no longer holds its port** — is judged by its group first, then by the identity of whatever now holds its port, with Phase 2's tests, for the server the entry recorded. The recorded pid changes nothing in what follows:

- **Its port's listener is a member of the entry's own group** (Phase 7) — it descends from the command Phase 4 started for the entry, whatever its command line says: it is *running*, and the entry takes that listener's pid, as in the next case.
- **Phase 2 would re-adopt it there as that server** — its listener is established as this checkout's, and the evidence names the entry's server, or nothing names a server and it is the sole server of a one-server profile, answering as this docs site: it is *running*, and the entry takes that listener's pid — Phase 7's record at that port, rewritten with it — so from then on it is an ordinary living entry.
- **Nothing answers there, and the entry's group is its own** — a **starting** entry (Phase 7): the server Phase 4 started is still coming up, as a readiness timeout leaves it, or it is between one listener and the next, as a server that re-spawns its child leaves it. It is *starting*, and `--stop` ends it through that group; a serve run counts it as running, too (Phase 2 step 1, Phase 4). This is the one bullet that holds for an entry which recorded a pid as squarely as for one that did not — the group is the evidence, and a `--status` that reported such an entry *stale* would disagree with the `--stop` that signals it.
- **The evidence gives the port to something else** — another checkout, another of this repo's servers, or a process that does not answer as this docs site — or **nothing answers there, and the entry has no group of its own**: it is *stale*, whatever its page says, since the server it recorded does not hold that port.
- **Anything else** — nothing names a server there, the port answers as this docs site, and Phase 2 would not re-adopt it: the socket table shows no process on the port, or shows one it cannot place, or the profile has more than one server — it is *running*, and it says it has no pid.

A selector narrows the report to the entries **Phase 7's lookup** returns for it: `--internal` is Phase 1's own server selection for `--internal`, looked up as that server — so only entries recorded for it are reported, which on the two-server profile `/docs-workflows:docs-init` writes means those that recorded `internal` — and a bare `--port <n>` names the **bound port**: it reports the entry keyed at `<n>`, the server on that port, and never one matched by its `requested_port`. With neither given, every recorded entry is reported.

## `--stop` mode

Read the same state file. Select the entry to stop through **Phase 7's lookup**, always — never by space alone:

- A bare `--port <n>` argument names the **bound port**: the entry keyed at `<n>` is the one stopped, and no entry is ever matched by its `requested_port`. An operator naming a port means the server on it — not a server a collision moved off it, which is keyed where it now runs — and a key admits one entry, so there is no prompt.
- An `--internal` flag is Phase 1's own selection (steps 1–3, `--port` override included) for `--internal` — the same selection a serve run makes, looked up as that server and at its port. The lookup takes only the entries recorded for the selected server — on a profile that tags its servers, the ones that recorded `internal` — and among them the one bound to the port that selection resolves or moved off it by a collision. So `--stop --internal` stops the server a `--internal` serve run started, given the same `--port` where that run carried one. On the two-server profile `/docs-workflows:docs-init` writes, that is the `internal`-tagged server and never its public twin of the same space — not even a public server an earlier collision moved onto the internal server's configured port, which a lookup by port alone would have returned.
- With neither given and exactly one entry recorded, stop that one — no prompt.
- With neither given and more than one entry recorded, resolve it the same way Phase 1 step 3 resolves an ambiguous server: the state file holds one entry per running server, as many as there are ports in use, with no count fixed anywhere, so the same cap applies. Print every recorded entry as prose above the prompt — its port, its space, and its visibility where recorded — then:
  - **Three or fewer entries** — `choices: ["port <port-1> — <space-1> (Recommended)", "port <port-2> — <space-2>", "port <port-3> — <space-3>"]` (2 or 3 options, matching however many are recorded; a recorded visibility is appended to its option, e.g. `port 8001 — docs (internal)`).
  - **Four or more entries** — `choices: ["port <port-1> — <space-1> (Recommended)", "port <port-2> — <space-2>", "port <port-3> — <space-3>", "Another entry from the list above — name its port"]`.

  The typed answer is resolved against the ports just printed — never parsed out of the free text.

For the selected entry: **where it records a `pgid` whose group is its own** (Phase 7) — a server this command started, whether or not it has bound its port — stop that group as `${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/render-verification.md` §2 step 5 stops one: `command bash -c 'kill -TERM -- -<pgid>'`, wait up to 5 seconds for the group to be gone by that step's test, and where it is not, `command bash -c 'kill -KILL -- -<pgid>'` and wait up to 5 seconds more. A group that is still not gone then is reported as `process group <pgid> still runs`, and the server is never reported stopped. **That entry is kept**, and the report says so, so a second `--stop` can signal the group again: a process that outlives `SIGKILL` is in uninterruptible sleep, which it may yet leave, or is a member of the group this user may not signal — one that became another user, as a command run through `sudo` does — which only that user, or root, can end. **The second cause reaches this branch because the test reads the process table rather than the signal**: `kill -0` on such a group fails with `EPERM`, which §2 step 5 refuses to read as gone, while the table names its live members whoever owns them. Read the other way, that group would have been called gone, this entry dropped, and a running server reported as one whose process has ended. **Otherwise, where it is living** (Phase 7) — a server this command re-adopted, which it did not start and so records no group of, or one whose group is no longer its own — send `SIGTERM` to its pid; wait up to 5 seconds for it to exit; `SIGKILL` if it has not, and wait up to 5 seconds more. Where the entry is still living then — its pid still holding its port — report `process <pid> still holds port <port>`, and never report the server stopped. **That entry is kept too**, as for a group, and the report says so, so a second `--stop` can signal it again. **An entry `--stop` keeps is not re-probed** — one whose group, or whose pid, outlives `SIGKILL`, or one recording no pid that it cannot stop (below): its report already says what still runs or holds the port, so it is never reported stopped, and its process is never said to have ended or to hold the port no longer. **An entry recording no pid with no group of its own is judged before this sentence applies** (**An entry recording no pid**, below): where Phase 2 re-adopts its listener it takes that pid and is stopped as a living entry, and otherwise it is removed or kept as that paragraph says. **Every other entry that is neither is never signalled** — its process has exited, or its pid or its group id now names some other process — and goes straight to the re-probe; where its port no longer answers, report it as already stopped. **Then re-probe the port of every entry not kept before reporting**, with Phase 2's tests: stopped means Phase 2's evidence names none of this repo's servers there — the process first, whether or not its page names this docs site — and, where nothing names a server there at all, that the port no longer answers as this docs site; nothing short of that does. The site test decides only in that last case, as in Phase 2: a port the evidence gives to another checkout no longer holds this repo's server, whatever its page says, so report the server stopped and name that checkout as what now holds its port. Where the evidence still names one of this repo's servers on it — a pid recorded by an earlier version that took a wrapper for the server, or a server something restarted — or nothing names a server there and it still answers as this docs site, say that the port still answers although the recorded process has ended or no longer holds it, name its listener's pid where the socket table names one, and **never report the server stopped**. Remove the entry from the state file either way — what it recorded no longer holds the port, and leaving a stale entry behind is what breaks the next `--status` — save an entry whose group still runs after `SIGKILL`, or whose pid still holds its port after it, which is kept, as above. Report what was stopped, or `Nothing recorded to stop for <repo>` when the file holds no matching entry. **An entry recording no pid** — one Phase 5 wrote when its readiness poll timed out, or where the socket table named no process on the port that answered — is stopped through its group wherever that group is its own, as above, and then kept, or re-probed and reported, like any other entry: so a server whose readiness poll timed out is stopped before it binds its port, and never comes up unrecorded after `--stop`, whatever its command line carries — its group stays its own while its leader lives (Phase 7). One with no group of its own is judged first, exactly as `--status` judges it, by the identity of whatever now holds its port. Where Phase 2 would re-adopt it there as the server the entry recorded, the entry takes that listener's pid, as in `--status`, and is stopped as above, a living entry like any other. Where `--status` would call it stale — the evidence gives its port to another checkout, to another of this repo's servers or to a process that does not answer as this docs site, or nothing answers there — it is removed **without signalling anything**, since what holds its port is not the server it recorded. Only where `--status` would call it running with no pid is it a live server this command cannot stop, and then `--stop` says so, with its port, and keeps the entry. **Every entry `--stop` removes takes its `log` with it**, removed as Phase 7 removes one, and every entry it keeps keeps its log (Phase 7, **A log goes with its entry**).

## `--build` mode

Run the profile's build command and exit without starting a server — this is the flag `/docs-serve` carries instead of a separate `/docs-build` command: the pipeline already gates on the profile's build (`${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/docs-profile-schema.md`'s field rules — an absent build command already disables `/docs-workflows:document`'s own gating build check), and a flag is cheaper than a whole command.

Resolve the command to run, most specific first:

1. The profile's `builds[]` list (the two-build MkDocs shape `/docs-init` scaffolds): `--internal` selects the entry whose `id` (or `visibility`) is `internal`; its absence selects `public`. Where the list records the other one but not the one asked for — a `--public-only` scaffold's lone `public` build under `--internal` — stop, never building the other visibility in its place. The IDs are Phase 1's, and the messages speak of `builds[]`, which is what is missing here:

   `DOCS_SERVE_NO_INTERNAL_BUILD: <repo>'s profile records no internal build — no builds[] entry has id or visibility internal, so --build --internal has nothing to run. A /docs-init --public-only scaffold has none by design; adding one takes an mkdocs.internal.yml build config and a builds[] entry that builds it. Drop --internal to build the public site.`

   `DOCS_SERVE_NO_PUBLIC_BUILD: <repo>'s profile records no public build — no builds[] entry has id or visibility public, so --build has nothing to run without --internal. Pass --internal to build the internal one.`

   Neither id present → fall through.
2. `commands.per_space.<space>.build`, where `<space>` is Phase 1's own selection logic, applied here even though this mode starts no server — the same space still identifies which build to run.
3. `commands.build` (flat).

No candidate resolves at any of the three → stop:

`DOCS_SERVE_NO_BUILD_COMMAND: <repo>'s profile records no build command (checked builds[], commands.per_space.<space>.build, commands.build). Run /docs-workflows:docs-profile <repo> to record one, or build by hand.`

Run the resolved command via Bash, in the foreground (this mode waits for it, unlike Phase 4's server start), from `<repo-root>` (Phase 0). Report its exit code and output; a non-zero exit is reported as a failed build, never swallowed.

## Phase 1 — Read `dev_servers` and select the server

Read `<repo-root>/.dev-workflows/docs-profile.yml` (`${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/docs-profile-schema.md`). The file absent, or present but carrying no `dev_servers` block, stops the run:

`DOCS_SERVE_NO_DEV_SERVER: <repo> has no dev_servers block recorded. Run /docs-workflows:docs-profile <repo> first — it detects a repo's *:start scripts and writes this block.`

`dev_servers.servers[]` is a list, one entry per server — `space`, `command`, `port`, and optionally `base_path`, `public_base_url`, and `visibility` (`docs-profile-schema.md`'s field rules). Usually that is one per servable space, but not always: the two-build profile `/docs-init` writes records **two** servers for its **one** space, a public and an internal one, told apart by `visibility` alone — which is why the state Phase 7 records is keyed by port and never by space. A space id still labels a row of step 3's picker, beside that server's port, since the servers step 3 offers carry no `visibility` to tell them apart. Select the entry this run serves:

1. Where an entry carries the declared `visibility` field (`public | internal` — it pairs a server with the `builds[]` entry of the same visibility, and the two-build MkDocs shape `/docs-init` scaffolds records one server per build, tagged to match), `--internal` selects the `internal`-tagged entry and its absence selects the `public`-tagged one. **Where the tag asked for is on no entry, stop — never serve the other visibility in its place.** Under `--internal` with no `internal`-tagged server — the profile `/docs-init --public-only` writes records exactly one server, tagged `public` — stop: `DOCS_SERVE_NO_INTERNAL_BUILD: <repo>'s profile records no internal build — no dev_servers.servers[] entry is tagged internal. A /docs-init --public-only scaffold has none by design; adding one takes an mkdocs.internal.yml build config and a dev_servers.servers[] entry tagged visibility: internal that serves it. Drop --internal to serve the public build.` Without `--internal`, on a profile whose tagged servers are all `internal`, stop the same way: `DOCS_SERVE_NO_PUBLIC_BUILD: <repo>'s profile records no public build — no dev_servers.servers[] entry is tagged public. Pass --internal to serve the internal one.` `--status --internal` and `--stop --internal`, which make this same selection, stop the same way.
2. Where no entry carries `visibility` and the list holds exactly one entry — the ordinary case for a repo with nothing to split, including a single-space profile with no two-build scaffold behind it — use it regardless of `--internal`, and say plainly that the profile records no public/internal split for this command to honour, rather than pretending `--internal` changed anything.
3. Where the list holds more than one entry and none carries `visibility`, ask — never guess, and never render an array sized to the list: `docs-profile-schema.md` fixes no upper bound on `dev_servers.servers[]` — it states the length of neither that list nor `spaces[]`, which is "required and non-empty" and nothing more — so a naive one-row-per-server array is a tool call `AskUserQuestion` rejects the moment a profile records five servers, not a long menu. This is the same shape `workflows-core:epic-picker` *The cap* exists for — a picker built from a directory listing, with no literal options for a static check to count — so resolve it the same way. Load the reference with `Skill(skill: "workflows-core:reference", args: "epic-picker")`; cited here as the authority rather than restated.

   Print every candidate `dev_servers.servers[]` entry as prose above the prompt, one line each — its `space` id and `port` — then:

   - **Three or fewer entries** — the array carries them all: `choices: ["<space-1> — port <port-1> (Recommended)", "<space-2> — port <port-2>", "<space-3> — port <port-3>"]` (2 or 3 options, matching however many are recorded; a one-entry list never reaches this rung — it resolves at step 2).
   - **Four or more entries** — the array carries the first three plus the overflow option: `choices: ["<space-1> — port <port-1> (Recommended)", "<space-2> — port <port-2>", "<space-3> — port <port-3>", "Another server from the list above — name its space and port"]`.

   The port is on every row because nothing in `docs-profile-schema.md` stops two untagged entries sharing a space id, and two rows reading the same id would be a choice the operator cannot make. The typed answer is resolved against the `space` ids and ports just printed — never parsed out of the free text (`workflows-core:epic-picker`'s closing paragraph states the same rule for its own picker). The worked two-space profile (`cloud`, `self-hosted`) reaches the three-or-fewer case: its two servers differ by space, not by visibility, so step 1 never resolves them and step 3 prints both and asks.

**The port reaches the command only through its `{port}` token.** The selected entry's `command` may carry the literal token `{port}` (`docs-profile-schema.md`'s field rule for `dev_servers.servers[].command`), and Phase 4 replaces it with the port this run serves on — the configured `port`, `--port <n>`, or Phase 3's shift. Nothing else in a command is ever rewritten. A command without the token is **fixed-port**: it binds a port of its own wherever it starts — a baked-in `-a 0.0.0.0:8000`, or a script such as the schema's `pnpm cloud:start` that names its port inside — so nothing this command does can move it. Phase 2 runs no pre-scan for it, Phase 3 never walks it (each says why), and `--port` cannot move it either.

`--port <n>`, when given, overrides the selected entry's configured `port` for this run: Phases 2 and 3 test `<n>` rather than the profile's recorded port, Phase 2 runs no pre-scan from it, and Phase 4 substitutes it for `{port}`. **On a fixed-port command, `--port <n>` stops the serve flow here**, before anything is probed, rather than start a server that binds somewhere other than `<n>`:

`DOCS_SERVE_FIXED_PORT: <repo>'s <server> server runs "<command>", which carries no {port} token — it binds its own port, so --port <n> cannot move it, and nothing was started. Drop --port to serve it on its configured port <port>, or add {port} to the command where its tool takes a port argument (docs-profile-schema.md, dev_servers.servers[].command).`

`<server>` is the selected entry's space, followed by its visibility in parentheses where the profile tags one — `docs (internal)`. `--status` and `--stop` read `--port` as a port to look up and start nothing, so this stop is the serve flow's alone.

## Phase 2 — Already-running detection

Before starting anything, test whether the selected server is already up. **A server's identity comes from evidence, never from the port it answers on.** Every port this command judges — the configured port here, each port step 2's pre-scan probes, each other server's configured port step 3 takes on a `concurrent: false` profile, and each port Phase 3 walks — is judged the same way, in this order:

- **Does it answer?** The reachability probe, `command curl -s -o /dev/null --noproxy '*' --max-time 2 http://localhost:<port>/`, read by its exit code as `${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/render-verification.md` §2 defines a port that answers: exit 7, a refused connection, is a port that does not answer on `localhost`; any other code but 127 is a port that answers; 127 means curl could not run, which is no answer at all and stops the run (Mode dispatch). Every request this command makes to a port — this probe and the home-page fetch below — carries `--noproxy '*'`, for the reason that section gives: a proxy in the environment would otherwise answer for `localhost`, so a free port would read as answering, and the proxy's page as the site's.
- **Is anything listening on it?** Asked only of a port that does not answer. Where the listening read (`${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/render-verification.md` §2, **Portability**) finds a socket in `LISTEN` on the port, the port is **taken** though nothing answers there: a listener bound to an address `localhost` does not reach, which that section defines free against, for this command and for `/document`'s render check alike. **It names no server**, and the evidence below is never asked about it: this command reports a URL the operator can open, and the probe is what establishes that one does — so a listener the probe cannot reach is never re-adopted as the selected server, whatever its command line says. The report names it by its listener's pid where the read names one, and as an unnamed process where it does not.
- **Is another server still starting on it?** Asked only of a port that does not answer. Where the state file records at that port a **starting** entry (Phase 7) of a server other than the selected one — an entry step 1 of Phase 7's lookup would not keep for the selection, its group still its own and the command Phase 4 started for it still coming up, whatever pid it recorded — the port is **taken**, though nothing answers there yet: that server will bind it, and a server started there meanwhile would take the port from under it. A port that does not answer is **free** only where no such entry is recorded at it and nothing is listening on it.
- **Is a living recorded entry of another server bound to it?** One the state file records at that port for a server other than the selected one — an entry step 1 of Phase 7's lookup would not keep for the selection — that is living (Phase 7). That makes it another of this repo's servers, whatever its page says — typically one an earlier run's Phase 3 moved onto the selected server's configured port: the public twin of an internal server, or another space's server.
- **Which server is it?** Decided by the evidence below, and by nothing else — **the process before the page**. A listener established as another checkout's is never this run's server by this evidence; a member of a process group this command started is identified by that group before any of it is asked (Phase 5, and Phase 7's living entry). A listener established as this checkout's whose command line carries a server's recorded command — exactly one, or the longest of several that nest (below) — names that server **whether or not its page names this docs site**: what a process was started with is evidence, and a page can name nothing at all — a VitePress dev server's client-rendered shell carries an empty `<title>` and no site name, at `/` and under its base path alike. The page's site name is read only for a listener in this checkout whose command line names no server, and it never overrides one that does (below).
- **Does it answer as this docs site?** It decides what the run does only where the evidence names no server, and wherever else it is asked it only names what holds a port — **the site test never gates the evidence**. Fetch its home page — `command curl -sL --noproxy '*' --max-time 10 http://localhost:<port>/`, which prints the page, `-L` following the redirect `mkdocs serve` gives `/` for a site served under a path — and test it for something that actually names this docs site (the profile's `repo.name`, or the generator's own `site_name`, whichever the repo exposes). An answer carrying no such marker is not this docs site. A marker establishes the *site* and nothing more: every server of a multi-server profile renders a page naming it, and so does the same server run from another checkout of this repo.

**The evidence.** Two kinds count, and each names at most one of `dev_servers.servers[]`: the listening process, and, for a listener in this checkout whose command line names no server, the page's site name.

1. **The listening process.** The *listener* on a port is the process the socket table names for it — the processes holding a listening socket on that port, read as `${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/render-verification.md` §2, **Portability**, reads them: from `/proc/net/tcp`, `/proc/net/tcp6` and each process's `/proc/<pid>/fd` on Linux, with `command lsof -t -iTCP:<port> -sTCP:LISTEN` elsewhere. Where it names several processes, the listener is the one the others descend from (walk each one's parents, read as that paragraph reads a parent); where none is, or the table names none, or it cannot be read at all — off Linux, with no `lsof` installed — **no listener is named**. This command always reads the table (Mode dispatch), so for it no listener is named only where the table shows no process for a port that answers — one another user runs, say, whose socket the table lists but whose `fd` links cannot be read, or one reached through a container's published port, neither of which names a process — or shows several, none of which the others descend from. Nothing then establishes which process holds that port or whose checkout it is in, and no server is named there, by its process or by its page.
   - **Checkout first.** A named listener's checkout is the git top level of its working directory — `git -C <its working directory> rev-parse --show-toplevel`, the directory read as that same paragraph reads one: `/proc/<pid>/cwd` as it stands on Linux, the path on the `n` line of `command lsof -a -p <pid> -d cwd -Fn` elsewhere — and this run's checkout is `git -C <repo-root> rev-parse --show-toplevel`: the top level Phase 0 recorded, computed by the same command as the listener's so the two compare like with like — never the resolved `<repo>` itself, since a docs repo resolved at a subdirectory of a work tree (a monorepo's `docs/`) runs its servers inside that same top level. Git resolves symlinks in both paths; where a directory is in no git work tree, its top level is the directory itself, as `builtin cd "<dir>" >/dev/null && builtin pwd -P` prints it. **Compare the two as whole paths, never as a prefix**: a `git worktree` can sit inside another checkout's tree — nesting them under `.worktrees/` in the main checkout is a common layout — and a prefix test calls that worktree's server the main checkout's. Equal paths establish the listener as **this checkout's**; different ones establish it as **another checkout's**, whether a sibling worktree, another clone or another project — with one exception, **outside git**: where `<repo-root>` is in no git work tree, a listener is this checkout's where its working directory, as `builtin cd "<dir>" >/dev/null && builtin pwd -P` prints it, is `<repo-root>` or lies below it, its path continuing `<repo-root>/` — whether or not that directory is itself in a git work tree. **The docs directory is the unit there**: outside git there is no nested worktree to take for it, and a command's leading `cd <dir> &&` leaves its server standing in `<repo-root>/<dir>`, a plain subdirectory or a git repository kept below the docs directory, whose own top level is never `<repo-root>`. Inside a work tree the whole-path comparison stands, unchanged; where no listener is named, or its working directory cannot be read, the checkout is **not established**.
   - **Then which server** — only for a listener established as this checkout's. Walk from the listener up through the processes it descends from, up to pid 1, reading each one's command line and its parent as `render-verification.md` §2, **Portability**, reads them — `/proc/<pid>/cmdline` and `/proc/<pid>/stat` on Linux, `command ps -o args= -p <pid>` and `command ps -o ppid= -p <pid>` elsewhere: a wrapper — `pnpm …:start`, an npm script, the `sh -c` or `bash -c` the Bash tool itself starts — puts the listener in a child and the recorded command on a parent. The first command line on that walk carrying any server's recorded `dev_servers.servers[].command` — with its `{port}` replaced by the port being judged, since that is the command line a server serving that port was started with; a fixed-port command is compared as recorded; and a recorded command beginning `npx <rest>` is carried, too, by a command line carrying `npm exec <rest>`, since `npx` rewrites its own command line to that as it runs — names that server. A launcher that rewrites its command line otherwise leaves the recorded command on no process — npm drops its own options and the `--` before the script's, so `npm run docs:start -- -a 0.0.0.0:8001` runs as `npm run docs:start -a 0.0.0.0:8001` — so a server this command started is identified by its process group instead (Phase 5, and Phase 7's living entry), and one started by hand by its page or not at all. **Both sides are normalised before that test**, after the `{port}` substitution. From the recorded command, first set aside a leading `cd <dir> &&` and every leading `VAR=value` word, in whatever order they lead — exactly the words `${CLAUDE_PLUGIN_ROOT}/references/toolchain-preflight.md` §2 sets aside to find a command's tool. The shell consumes them, so a server started with `cd website && pnpm docs:start` or `NODE_ENV=development pnpm docs:start` — typed by hand, or started by Phase 4, whose shell runs its subshell's last command in the subshell's own process — carries `pnpm docs:start` on its command line and neither of the others. Then every `'` and `"` character is removed from the command line and from what remains of the recorded command, and each run of whitespace in either is collapsed to one space. A recorded command that carries a quote is otherwise carried by no process at all: the shell removes the quotes before the server sees its arguments (`mkdocs serve -f 'cloud.yml'` runs as `mkdocs serve -f cloud.yml`), and the Bash tool's wrapper writes each `'` as `'"'"'`. Where it carries more than one server's recorded command, the walk stops there too, and what it names depends on whether those commands are **nested** — tested on the normalised commands, with `{port}` replaced as above. They are nested where one of them is longer than every other and each other one is a substring of it, as `pnpm start` is of `pnpm start:internal`, or `mkdocs serve -a 0.0.0.0:<port>` of the same command followed by `-f other.yml`: then that longest command names its server, since a process started with a shorter one never carries the longer one's text. Where they are not nested — two unrelated commands on one command line, as a wrapper that starts two servers carries both, or two servers recording the same command — it names none: **never pick one of two unrelated commands**. A walk that reaches pid 1 without a match names none.
2. **The page's site name** — only for a listener established as this checkout's whose command line names no server, and only on a profile where it tells the servers apart: more than one server, each pairing by `visibility` with a `builds[]` entry whose `config` is an MkDocs config that sets a `site_name` (its own key, or the one its `INHERIT` parent sets), and no two of those names the same. The two-build profile `/docs-workflows:docs-init` writes is one: `<product>` and `<product> (internal)` (`${CLAUDE_PLUGIN_ROOT}/references/docs-workflow/scaffold-tree.md` §5 and §6). Take the port's home page, fetched as the site test above fetches it — `/`, with the redirect `mkdocs serve` gives it for a site served under a path followed — and the text of its `<title>` element, with any HTML character references decoded. A MkDocs theme titles its home page with the site name, or with `<page title> - <site name>` where the page sets its own title, as the scaffold's does; so the page names the server whose build's site name the title equals, or ends with after ` - `. **Compare the whole name, never a substring**: one scaffold name contains the other. Where two servers' names fit, or none does, the page names none. A profile whose servers do not pair with builds — the schema's two-space `cloud`/`self-hosted` example — or whose build configs are not MkDocs configs gets nothing from this: its servers are identified by process or not at all.

**The page never overrides the process.** Where the listener's command line names a server, that is the answer, and the page is not asked which server it is; where the listener is another checkout's, or none is named, or its checkout is not established, the page names no server either.

**What the evidence decides**, at the configured port, at each pre-scan port and at each port Phase 3 walks — wherever the port answers and no living recorded entry of another server is bound to it:

- **The selected server, in this checkout** — the listener is established as this checkout's, and its command line names the selected server, whether or not its page names this docs site, or, naming none, its page's site name does. **Re-adopt it, on every profile**: report its URL, and whether it sits off the configured port; record an entry at that port in Phase 7's shape — `requested_port` the port Phase 1 resolved and `pid` the listener's — and stop. **Never start a second copy.**
- **Another checkout, or another of this repo's servers** — the listener is established as another checkout's, or it is this checkout's and its command line or its page names a server other than the selected one; either way, whether or not its page names this docs site. Leave it running and record nothing, and name what holds the port in the Phase 6 report — another checkout by its top level, or, where its page does not name this docs site either, a process that is not this docs site, with that top level beside its pid: here the site test only names what holds the port, and decides nothing, since the run does the same with it either way. At the port being served it is a collision, which step 2 below handles; in the pre-scan and in Phase 3's walk, pass over it.
- **Nothing names a server** — no listener is named, or the listener's checkout is not established, or it is this checkout's and neither its command line nor its page names a server. Only here does the site test decide:
  - where the port does not answer as this docs site, something that is not this docs site holds it — a collision at the port being served, which step 2 below handles, and a port to pass over in the pre-scan and in Phase 3's walk;
  - where it does, the listener is established as this checkout's, and `dev_servers.servers[]` holds **one** server, re-adopt it by the page, since it is the only candidate — exactly as for the selected server above, with the listener's pid;
  - where it does otherwise — the list holds **more than one** server, or no listener is named, or its checkout is not established — report the port as answering as this docs site with its server **unconfirmed**, together with the listener's pid where the socket table named one; start nothing and record nothing — a guessed identity is exactly the entry a later `--stop` would act on — and name the way forward: stop what holds that port by hand (its listener's pid, where the socket table named one), then re-run. Only where the selected entry's `command` carries the `{port}` token, name a second way: re-run with `--port <n>` to serve the selected server on another port. A fixed-port command has no second way, since `--port` cannot move it (Phase 1).

So every re-adoption records the pid of a listener established as this checkout's: a port whose holder cannot be shown to be this checkout's is never re-adopted, whatever its page says.

1. Read `<repo-root>/.dev-workflows/docs-serve.state.json` (Phase 7 writes it) and look this run's selection up by Phase 7's lookup — the server Phase 1 selected, at the port Phase 1 resolved, as overridden by `--port`. A returned entry that is living (Phase 7) is the running server — including one an earlier run's Phase 3 moved to a later port, which the lookup finds by its `requested_port`, and one whose port's listener is a member of its own group, whatever pid it recorded, which takes that listener's pid here, as `--status` gives it one. Report its recorded URL and stop. A returned entry that is **starting** (Phase 7) — nothing answers on its port and the group Phase 4 started for it is still its own, whatever pid it recorded: a server whose readiness poll timed out and that is still coming up, or one between one listener and the next — counts as running too: report that the selected server is still starting, with its port, its command and its `log`'s path, that `/docs-workflows:docs-serve --status` follows it and `--stop` ends it through its group, and stop. **Never start a second server.**
2. No living or starting entry returned (a different session started it, the state was lost, or nothing has ever run) — probe the port directly, and judge it as above. Where the evidence finds the selected server there, or names no server while the port answers as this docs site, what it decides governs. Otherwise the port is free, or it is a **collision** — a living recorded entry of another server is bound to it, another server is still starting on it, something is listening on it though nothing answers there, the evidence names another checkout or another of this repo's servers, or nothing names a server and it does not answer as this docs site — and, for a command carrying the `{port}` token, neither is proof the server is down: an earlier run's Phase 3 may have moved it further up and its record may be gone. That holds whether or not the configured port has come free since, because the walk takes the first free port it meets, so a copy moved past a port that was busy then can sit beyond one that is free now. So, on every profile, pre-scan the ports Phase 3 would walk (`port + 1` … `port + 20`) for such a command, judging each one that answers exactly as above. Where the evidence finds the selected server, re-adopt it (the lowest such port); failing that, where a port answers as this docs site and nothing names its server, that outcome governs at the lowest such port — re-adopted or reported unconfirmed, as **Nothing names a server** says; pass over every other port. Only where the pre-scan does neither, proceed: to Phase 4 at the configured port where it is free, to Phase 3 where it is a collision. A multi-server profile's common case — another of its servers on its own configured port, its record lost — is identified as that server and passed over, so only a site nothing can name still stops the run.

   **A fixed-port command gets no pre-scan.** The pre-scan looks for a copy a collision moved, and only a command carrying `{port}` can be moved: a fixed-port one binds its own port wherever it starts, so no run of this command left a copy of it above that port, and what answers there is some other server — on the schema's own two-space profile, the next space's. Pre-scanning anyway could only mislead. Where the evidence names that server's process, it is passed over, which changes nothing; where nothing names it — as where a launcher other than `npx` rewrote the command line it was started with, on a two-space profile, which has no page to tell its servers apart — it is reported as the selected server unconfirmed, the run stops, and the operator is told to stop the process holding that port, which is the other space's server. So a fixed-port command goes straight on: to Phase 4 where its port is free, and to Phase 3, which reports the collision, where it is one.

   **An explicit `--port <n>` runs no pre-scan.** The pre-scan infers a history — that an earlier collision moved a copy off this port — and an operator who names the port has overridden that inference. It is also what makes the unconfirmed report's `--port <n>` remedy work: a pre-scan from `<n>` would meet the same site nothing can name, and stop again. Beyond skipping the pre-scan, `--port` changes only which port is judged and served: this step and Phase 3 judge `<n>` and walk from it exactly as they judge a configured port, so a collision at `<n>` goes straight to Phase 3, and Phase 4 substitutes whichever port the run ends up serving on. `--port` on a fixed-port command never reaches this step (Phase 1).
3. **On a profile that sets `dev_servers.concurrent: false`, and on no other**, judge each other server's configured port too, wherever step 2 proceeds — to Phase 3 or to Phase 4. Take the `port` of every other `dev_servers.servers[]` entry that this run has not judged already, and judge it by the tests above. Where the evidence finds the selected server there, what it decides governs, as at any port. Where it names another of this repo's servers, that server is known to be running, and Phase 4's one-at-a-time rule counts it. Whatever else answers there — another checkout, or a site nothing names — changes nothing: the port is not the one being served, so it is no collision, nothing walks past it and nothing is reported unconfirmed there. Without this step, a server of this repo running unrecorded on its own configured port — below the selected server's, or more than twenty above it — would go unjudged, and Phase 4 would start beside it.

## Phase 3 — Port collision

The selected port is taken, but not by the selected server — another of this repo's servers or another checkout holds it, something nothing names that is not this docs site answers there, another of this repo's servers is still starting on it, or something is listening on it though nothing answers there (Phase 2 step 2).

**A fixed-port command is never walked.** Its `command` carries no `{port}` token, so it binds its own port wherever it starts: run while that port is held, it fails to bind and never answers on the port a walk chose. Report the collision instead, start nothing and record nothing:

`DOCS_SERVE_PORT_HELD: port <port> is held by <what holds it>, so <repo>'s <server> server cannot start there — its command "<command>" carries no {port} token, which means it binds that port wherever it starts and cannot be moved. Nothing is running for it and nothing was recorded. Stop what holds the port and re-run, or add {port} to the command where its tool takes a port argument (docs-profile-schema.md, dev_servers.servers[].command).`

`<what holds it>` is what Phase 2's tests established there, named as Phase 2 names it — another checkout by its top level, another of this repo's servers by its space and visibility, a process that does not answer as this docs site, with its top level where its checkout was established, or, where nothing answers on the port at all, a listener the probe could not reach — followed by the listener's pid wherever the socket table named one, since that pid is what the operator stops; or, where another of this repo's servers is still starting there, that server by its space and visibility, still starting, which `/docs-workflows:docs-serve --stop --port <port>` ends. **Where Phase 5 reached this stop instead, `<what holds it>` is what Phase 5 names there**, since no test of Phase 2's saw that port taken. `<server>` is named as in Phase 1's stop.

A command carrying `{port}` is walked. Never fail on this and never reuse the port silently: walk forward from it (`port + 1`, `port + 2`, …, capped at 20 attempts) with the same probe and listening read Phase 2 used, judging each candidate the way Phase 2 judges the configured port:

- **It is free** — it does not answer at all, no other server is still starting on it, and nothing is listening on it (Phase 2) — take it. Use that port for Phase 4, and **say so explicitly in the Phase 6 report** — a port-shifted stack (a project's ancillary services moved off their standard ports to coexist with another project's containers) is the normal case here, not the exotic one, and a silently shifted port is a URL the operator will not find.
- **A living recorded entry of another server is bound to it, or Phase 2's evidence finds another checkout or another of this repo's servers there** — whatever its page says, as in Phase 2 — **or nothing names a server there and it does not answer as this docs site, or another server is still starting on it, or something is listening on it** — walk on, naming what holds it in the Phase 6 report as Phase 2 names it.
- **Phase 2's evidence finds the selected server there, whether or not its page names this docs site, or names no server while it answers as this docs site** — the selected server may already be running here, moved by an earlier run's Phase 3 whose record is gone. Phase 2's pre-scan has already re-adopted or reported such a port, unless `--port` skipped it. **Never walk past it to start a second copy**: what the evidence decides governs here exactly as at the configured port. Re-adopted, the report says it sits off the configured port, and its entry is keyed at this port with `requested_port` the port Phase 1 resolved; where nothing names a server and Phase 2 does not re-adopt it, it is unconfirmed, and nothing is started or recorded.

Exhausting the 20 attempts without serving on one of them is reported, never guessed past.

## Phase 4 — Start

**One server at a time, where the profile says so.** Before anything starts: where `dev_servers.concurrent` is `false` — the profile's servers cannot run at once (`docs-profile-schema.md`'s field rule) — and another of this repo's servers is **known to be running**, start nothing. Known to be running means one of two things: a living or starting entry (Phase 7) anywhere in the state file for a server other than the selected one — an entry step 1 of Phase 7's lookup would not keep for the selection, a starting one being a server Phase 4 started whose readiness poll timed out while it was still coming up — or a port this run judged, at the configured port, in the pre-scan, on the walk or at another server's configured port (Phase 2 step 3), where the evidence named another of this repo's servers. Stop:

`DOCS_SERVE_NOT_CONCURRENT: <repo>'s profile sets dev_servers.concurrent: false — its servers cannot run at once — and <other> is already running or still starting, so the <server> server was not started and nothing was recorded. Stop <other> and re-run: <how>.`

`<other>` names each such server as Phase 1 names `<server>` — its space, with its visibility in parentheses where the profile tags one — followed by its port. `<how>` is `/docs-workflows:docs-serve --stop --port <its port>` for one a living or starting entry records, since a bare `--port` names the server bound to that port (Phase 7's lookup); one only the evidence found has no entry for `--stop` to act on, so `<how>` is its listener's pid, stopped by hand — the evidence names another of this repo's servers only for a listener the socket table names. The second kind is only what this run's own judging identified. On this profile the run judges the port Phase 1 resolved and, for a command carrying `{port}`, the twenty above it, and every other server's configured port (Phase 2 step 3), so a server of this repo with no living or starting entry is not known to it where it holds none of the ports the run judges — a collision or `--port` moved it off its configured port and past them — or where it holds one but the evidence does not name it there: as where it was started through a launcher other than `npx` that rewrites its own command line, so that no command line on its listener's walk carries its recorded command and no page tells the servers apart, or where the socket table does not show its process at all, as for one another user runs. The stop cannot fire on any of these. A profile that sets `concurrent: true`, or no `concurrent` at all — `/docs-workflows:docs-init` writes none, its public and internal servers running side by side on their own ports — skips this paragraph.

**The command's tool must be present.** Before anything starts, check the selected entry's `command` for its tool — the tool `${CLAUDE_PLUGIN_ROOT}/references/toolchain-preflight.md` §2 defines for a command, checked as its §3 checks a tool the run starts inside `bash -c`, asked from the directory the command runs from — `<repo-root>` (Phase 0), or the directory a leading `cd <dir>` names under it, which is what resolves a path-valued tool such as `node_modules/.bin/vitepress` — and, where that tool is `pnpm`, `npm` or `yarn`, for its installed dependencies: a package manager whose lockfile has neither a `node_modules/` beside it nor, for Yarn, a `.pnp.cjs` counts as missing (`${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/render-verification.md` §2 step 1 states the rule and how to tell). Where it is missing, stop: a server that could never start is never started, so the run does not wait out Phase 5's readiness poll for it.

`DOCS_SERVE_NO_SERVER_TOOL: <repo>'s <server> server runs "<command>", whose tool <tool> <why>, so nothing was started or recorded. Install <what>, or record a command whose tool is present (/docs-workflows:docs-profile <repo>), and re-run.`

`<server>` is named as in Phase 1's stop. `<why>` is `cannot be found here`, with `<what>` `it`; or, where its dependencies are what is missing, `has no dependencies installed — <lockfile> has none beside it`, with `<what>` `them`.

Start the selected entry's `command`, with every `{port}` in it replaced by the port this run serves on — the configured `port`, `--port <n>`, or Phase 3's shift — **in a process group of its own**, from `<repo-root>` — the top level every command the profile records runs from (Phase 0), never `<repo>` where that is a site below it, and never the plugin's own directory. **A log goes with its entry, and a run leaves no log that no entry names** — save a run interrupted between its start and its record, whose log nothing that follows can name. **The key is the port because a port holds exactly one server, and a space id does not identify one.** The two-build profile `/docs-workflows:docs-init` writes — every run but a `--public-only` one — records **one** space served **twice** — a public server and an internal one, tagged by `visibility` — so a record keyed by space made the second server started overwrite the first one's entry: the process it described kept running past `--stop`, and `--status` could no longer see it.

**The lookup** — the one rule Phase 2, `--status` and `--stop` all apply, in two steps.

1. **Filter to the selected server.** A selection made through Phase 1 — every serve run, and `--internal` in `--status` or `--stop` — names one `dev_servers.servers[]` entry. Only state entries that recorded that entry's `space` and its `visibility` (or recorded none, where it has none) are candidates — `internal` for `--internal` and `public` for its absence on a profile that tags its servers — and an entry recorded for any other server is never returned, whatever port it holds. Where two of the profile's servers share a space and neither is tagged, those fields cannot tell them apart, so a candidate must also have been started for the selection's port: its `requested_port` is *P*. A bare `--port <n>` in `--status` or `--stop` names a port, not a server, and filters nothing.
2. **Match on port.** Among the candidates, the entries for the selection's port *P* are the one keyed at *P* and any whose `requested_port` is *P* — a server Phase 3 moved off *P* because something else held it. **A bare `--port <n>` matches the key alone**: it names the bound port, so it returns the entry keyed at `<n>` — the server on that port — and never one whose `requested_port` is `<n>`, which is a server a collision moved off `<n>` and which is keyed where it runs.

**A living entry is one whose pid still holds its port** — the socket table names that pid as the port's listener, as Phase 2 names one — **or, where it records a group, one whose port a member of that group holds, whatever pid it recorded.** A pid that merely answers `kill -0` is never enough: pid numbers are reused — a container restart starts them again from 1 — so the pid of a server long gone can belong to a live, unrelated process, which Phase 2 would then report as the running server and `--stop` would signal. Membership is different: where its port's listener is a member of the entry's own group (below), that listener is the entry's server whatever its command line says — the process it recorded, or one its server re-spawned under a new pid in the same group — so the entry counts as living wherever it is met, and `--status`, `--stop` and Phase 2 step 1 give it that listener's pid where it recorded another or none. Anything else is not living — an entry recording no pid, and one whose recorded pid no longer holds its port: `--status` and `--stop` judge it by its group first and then by what holds its port, and give it that listener's pid where Phase 2 would re-adopt it there, after which it is. **Not living is not the same as stale**: an entry whose group is still its own with nothing answering yet is *starting*, whatever pid it recorded (below).

**An entry's group is its own** while its `pgid` still names the process group Phase 4 started: the group is not gone, by `render-verification.md` §2 step 5's test, and its leader — process `pgid` itself — still leads it and started at the entry's `pgid_start`, its process group and its start time each read as that section's **Portability** paragraph reads one. A recorded `pgid` whose group is not its own — gone, led by another process, or recorded without a `pgid_start` — is never signalled, and the entry is then treated as one that records no `pgid`.

**A member of an entry's own group is the entry's server.** A listener whose process group, read as that paragraph reads one, is the `pgid` of an entry whose group is its own descends from the command Phase 4 started for that entry, so it is the server the entry recorded, whatever its command line says and wherever it stands — Phase 5's own test, applied to a group already on record.

**A starting entry** is one whose group is its own and whose port nothing answers on, **whatever pid it recorded**: the command Phase 4 started for it is still running, and nothing of it holds the port yet — the state a readiness timeout leaves while the server is still coming up, and the state a server that re-spawns its listener leaves between one listener and the next, or after its child has crashed and it is waiting to start another. Once a member of that group answers on its port it is living (above); once its group is gone, it is neither.

Nothing here looks a server up by its space alone.

**The bound port stays the key; the filter exists because the requested port is not exclusive.** Only one live server can hold a port, so the key never has to tell two live servers apart. But a server Phase 3 moved onto another server's configured port is keyed there: a public server moved onto the internal server's port — say 8001 — or one space's server moved onto the next space's. The same reasoning the reference gives for `/product-workflows:brd-proposal` applies here: an offer that names no gate its own run feeds carries no clause. `scripts/check-docs.sh` check 11 only asserts the placeholder across the `/product-workflows:brd-*` and `/product-workflows:prd-*` families — no `/docs-*` glob is in its scope — so nothing enforces this for `/docs-serve`; it is stated here by discipline, for the next maintainer who adds a `/docs-*` offer that *does* name a fed gate, to hold it to the same rule the check does not check.
