# Hooks reference

`docs-workflows` bundles two hooks, declared in `hooks/hooks.json` and installed automatically with the plugin — there is nothing to opt into separately. Every hook is advisory: **a hook never blocks Claude.** Both scripts end in an unconditional `exit 0` regardless of what they detect or whether their own logic errors out, by contract — a hook exists to notify or remind, never to gate a tool call.

| Hook | Event | Matcher | What it does |
|---|---|---|---|
| `preload-context` | `UserPromptSubmit` | — | On a `/document <address>` or `/docs-workflows:release-notes` prompt, injects the specs-tree context those runs resolve against; a near-instant no-op otherwise. |
| `changelog-owners-reminder` | `PostToolUse` | `Edit\|Write\|MultiEdit` | On a docs page under a profile-declared content root, warns if a changelog entry dated today (tracked-and-modified pages only) or a required page owner is missing. |

The companion `dev-workflows` plugin ships a `preload-context` of its own, covering the pipeline commands it owns (`/implement`, `/vuln`, `/dev-workflows:upgrade` — qualified-only for exactly the reason `/docs-workflows:release-notes` is below, a Claude Code built-in of the same bare name winning it); the companion `product-workflows` plugin ships another, covering `/epics`, which moved there. A `UserPromptSubmit` hook fires whichever plugin ships it, so on a machine carrying any of these plugins together all their scripts run on every prompt — but the three plugins' regexes are pairwise disjoint, so at most one of them ever emits. Installing this plugin without `dev-workflows` or `product-workflows` is a supported configuration, and it is the reason these two hooks live here: `${CLAUDE_PLUGIN_ROOT}` resolves to the plugin that *ships* a hook, and `changelog-owners-reminder` reads two bundled files through it.

## What each hook does, in detail

### `preload-context` (`hooks/preload-context.sh`)

Runs on every `UserPromptSubmit` event. It reads the submitted prompt from stdin JSON (trying the `prompt`, `user_prompt`, and `message` keys in turn for compatibility across Claude Code versions) and matches it in two branches: `^/(docs-workflows:)?(document)([[:space:]]+|$)` accepts either form, and `^/(docs-workflows:)(release-notes)([[:space:]]+|$)` accepts the **qualified form only**. That asymmetry is deliberate: Claude Code ships its own built-in `/release-notes` and the built-in wins, so a bare `/release-notes` never reaches this plugin and preloading for it would inject specs context into a run that is not ours. `/document` has no built-in of the same name. It then skips the leading flags — every token opening with `-`, and a bare `--enforce-model` together with the token after it, since that run flag's value may follow it as a word of its own (`workflows-core:run-flags` §1) — because the command strips a run flag that stands before its argument: `/document --skip-costs ACME-77` preloads exactly as `/document ACME-77` does. Anything else, including a bare command with no argument and one followed by nothing but flags (`/document --help`), exits immediately with no output. For a match, it routes by command: `/document` gets specs context (`$REPOS_PATH`, `$SPECS_PATH`, and the current branch when the cwd is inside a git repository) **only** when its first argument after those flags looks like an address, since its free-text/`@file` direct-edit mode owns its own git hygiene and never invokes Opus — an address being an argument opening with an uppercase token that reaches a hyphen and a digit (`[A-Z][A-Z0-9_-]*-[0-9]`), a deliberately loose superset of the key grammar `workflows-core:addressing` §1 defines that also takes a typed folder name such as `EPIC-ACME-77-01-alerts`, because a hook cannot load that reference and the command validates the address itself; `/docs-workflows:release-notes` gets that same specs context unconditionally, since it is keyed and accepts either an address or a folder in the specs tree. `/docs-profile` is not matched at all — it resolves a documentation repository rather than the specs tree — so no context is injected for it. For `/document`, whose prefix is optional, the qualified form works identically to the bare one — `/docs-workflows:document ACME-77` preloads specs context exactly as `/document ACME-77` does, which previously matched neither hook.

### `changelog-owners-reminder` (`hooks/changelog-owners-reminder.sh` + `changelog-owners-reminder.py`)

Runs on every `PostToolUse` event matched to `Edit|Write|MultiEdit`. The shell script is a thin dispatcher: it first guards on `command -v python3`, exiting immediately when python3 is absent (line 7 — the same guard `preload-context` uses); otherwise it resolves `$CLAUDE_PLUGIN_ROOT` (falling back to the script's own parent directory if the variable is unset, which happens outside a normal plugin invocation) and hands the tool payload straight through, on stdin, to `changelog-owners-reminder.py`.

The Python script does the actual check. It reads the edited file's path from the payload, returns immediately unless the path ends `.md`, then resolves the **applicable docs profile** — the nearest `.dev-workflows/docs-profile.yml` walking up from the edited file, else this plugin's built-in default at `references/docs-profiles/docs-profile.default.yml` — and returns unless the path sits under one of that profile's `spaces[].content_root` values. **No content root is hardcoded**: a repo supplying its own profile gets its own roots, which is what lets the hook work against any docs repo rather than only the bundled example. The profile is read by a tolerant line scan rather than a YAML parser, so the hook never depends on PyYAML being installed and never raises on a malformed profile.

For a matching page it re-reads the file's own frontmatter and checks two things independently. A changelog gap is only flagged when `git status --porcelain` also reports the file as tracked-and-modified (so a brand-new untracked file is not yet expected to carry a changelog entry) and the frontmatter's `changelog:` block has no entry dated today. A page whose space id appears in the profile's `frontmatter.owners_spaces` list is additionally checked, regardless of its git status, for whether its `owners:` block names everyone in `references/docs-profiles/default-owners.txt` — that path is fixed, read from this plugin's own bundle rather than from the profile's `frontmatter.default_owners` pointer, which the hook never reads. When `owners_spaces` is absent or empty — or the bundled owners list is empty or unreadable — the owners check never fires. Any gap becomes one line in a `{"systemMessage": ...}` reminder naming the file, the specific issues found, and pointing at the `docs-frontmatter` skill to fix them; a page with no gaps prints nothing at all.

## Why none of this blocks you

Both scripts end `exit 0` unconditionally — the exit code is never derived from what the hook found, so a prompt payload that will not parse, or a page failing the changelog/owners check, never stops a tool call, a turn, or the run itself. Both also guard on `command -v python3` up front and exit 0 immediately when it is absent, degrading to silence rather than failing — `preload-context.sh` and `changelog-owners-reminder.sh:7`. The frontmatter conventions `changelog-owners-reminder` checks are covered in full, including how to satisfy them, by the plugin's [`docs-frontmatter` skill](references.md#skills); this page only describes what the hook itself does.
