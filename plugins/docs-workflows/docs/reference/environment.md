# Environment reference

[Getting started](../getting-started.md) says what each variable is *for* and what to export before your first run. This page says what each variable **is** — its default, where that default comes from, what happens when it is unset, and what happens when it points somewhere the plugin cannot read or write. The plugin reads four user-settable variables. Two other names appear in its files, `CLAUDE_PLUGIN_ROOT` and `ARGUMENTS`; Claude Code sets both itself for every plugin invocation, and neither is yours to set.

## `$SPECS_PATH`

- **`$SPECS_PATH`** — the shared, team-visible repository holding the PRD folder `/document` and `/release-notes` read, and the one place either of them commits its own session bookkeeping; required to resolve a `<KEY>` address, with no built-in default.

**Resolution.** Read straight from the shell environment — there is no config file, CLI flag, or derived fallback that feeds it. Every git call against it is `git -C "$SPECS_PATH"`, never a `cd`, so the docs or code repository the run is working in is untouched.

**When unset.** What happens turns on the address form. A `<KEY>` is resolved by searching `$SPECS_PATH/specifications/`, so with the variable unset there is nothing to search, and both commands stop before doing anything, on the same ground: each checks the variable before it resolves a `<KEY>` — `/document` keyed mode in Mode detection, `/release-notes` in Phase 0 step 1 — and stops naming it, offering *Set SPECS_PATH* — which asks you for the path, and asks again until it names an existing directory — or *Cancel*, rather than on a folder it could not find. Elsewhere in the family the same variable stops every `product-workflows` command, `/design`, `/ready`, `/conformance`, `/frames` and `/security-workflows:scan` on every run, `/implement` on a `<KEY>` address, and `/vuln` on an `@<path>` one. An `@<path>` names its folder directly and is resolved without the variable, so it gets past address resolution in `/document` and `/release-notes` alike; `/release-notes` then degrades rather than stopping — it falls back to treating the run as the PM's early run, which only suppresses the inference that would otherwise read the PRD folder for a `specification.md` or `design.md`, and offers no handoff of its draft, there being no specs repository to hand it to. `/document`'s direct mode resolves no address and never needed one. `/docs-profile` never reads the variable at all. `/docs-audit` degrades: two of its seven surface kinds come from the specs tree, so with the variable unset it enumerates the other five, reports the two it did not, and stops only where no code repository resolved either.

**When it points somewhere unreadable.** The bookkeeping entry point, `specs-preflight`, requires an existing directory, a resolvable git dir, and a **writable** `.git`; a gate that fails on **writability** is a silent no-op (a read-only specs mount is a normal state here, and there is nothing to fix), while a gate that fails because `$SPECS_PATH` is not a directory or not a git repository at all emits a notice, one line naming the variable and the path — and, where the path is a `specifications/` directory mounted on its own, which of the two signals under *When it points inside the specs tree* below it matches, plus the stop's second line where it has one — that state is never supported, and the notice is what tells it apart from the read-only one — and because the terminal `commit-artifacts` step applies the same writability gate, nothing gets committed either. The deliverable-verification gate, `require-on-main`, needs only a readable git dir, and a failure there returns `unmanaged`, on which the caller proceeds as it would with no gate at all.

**When it points inside the specs tree.** `$SPECS_PATH` must name the root of a dedicated specs repository — the directory that holds `specifications/` — never `specifications/` itself, nor a folder inside it. Two layouts are unsupported: a specs tree inside a larger repository, and a specs root that is itself a subdirectory named `specifications`. Pointed inside the tree, a run that resolves an address stops with `SPECS_PATH_INSIDE_TREE`, and any other run prints a `specs-preflight` notice and goes on — save on a checkout whose `.git` is read-only, where the preflight does nothing and prints none; a specs tree inside a larger repository draws a notice too, and either way the run commits nothing to the specs repository. To fix it, point `SPECS_PATH` at the root of a dedicated specs repository where the variable is set — the stop names the value to set, or the folders to move — and re-run.

- **A specs tree inside a larger repository** is unsupported because the plugin switches branches and commits in the repository `$SPECS_PATH` belongs to, which there would move the checkout of everything else that repository holds. A `$SPECS_PATH` below its repository's top level that the inside-tree check (below) does not stop draws a `specs-preflight` notice naming the top level, and the run goes on, treated as misplaced (below).
- **A specs root that is itself a subdirectory named `specifications`**, holding its tree at `specifications/specifications/`, is unsupported for detection rather than git: it cannot be told from the damage a misrooted run leaves (below), so it stops on every run. Set `SPECS_PATH` to the repository root and move the tree up a level, as the stop says.
- **The check.** Where `$SPECS_PATH` is set, `/document` in keyed mode and `/release-notes` first test two signals, on a `<KEY>` and an `@<path>` address alike. An `@<path>` address is tested too, because a run that passed its own resolution on one would otherwise meet the same stop at a later lookup by key, of an ARD or a specification, after its expensive work.
- **The two signals.** `$SPECS_PATH` is, or is inside, a `specifications/` directory rather than a repository root; or it is, or directly holds, a specs folder — one whose artifacts assert a `key:` and a folder kind and whose name begins with that kind and key (for `$SPECS_PATH` itself, its physical name; a subfolder that is a link back into its own `specifications/` is skipped). So a root's templates, `README.md` or `docs/` never count, fresh or populated, and a specs repository nothing has been written into yet matches neither signal and is not stopped.
- **What neither signal sees** is a `$SPECS_PATH` outside any repository's top-level `specifications/` that is, or holds only, folders not named `<KIND>-<key>-`, such as a mount of a legacy unprefixed folder.
- **The stop.** Either signal stops the run with `SPECS_PATH_INSIDE_TREE` where it resolves its address, naming the variable, its value, the signal and the value to set: the directory that physically holds that `specifications/`, symlinks resolved, where it lies in the same git work tree, and otherwise *the directory that holds `specifications/`*. Where that directory is not its repository's top level, the stop adds that the layout is unsupported. It stops rather than reporting the key's folder as not found. There is no option to enter a path for the one run: fix the variable where it is set.
- **Stray specs folders.** Where `$SPECS_PATH` names the right directory — a repository's top level, or a directory in a repository holding `specifications/` — but holds stray specs folders beside `specifications/`, the stop says so, names every stray folder and `specifications/` as where they belong, and adds the unsupported-layout clause where that directory is below its repository's top level.
- **When nothing on disk can tell.** Where nothing on disk says whether `$SPECS_PATH` is a specs root or a specs tree under another name — a path that is no repository, or one below its repository's top level holding no `specifications/` — the stop states both readings and what each needs, and you choose. Under the specs-tree reading, the folders belong in a directory named `specifications/`, and the stop names that directory and tells you to set `SPECS_PATH` to its parent.
- **Damage an earlier run left.** Where `$SPECS_PATH` is the `specifications/` directory directly under a repository root or anything inside it, or is itself a specs folder, or holds specs folders directly, the run stops whether or not a nested `specifications/` exists. Where one does, or where misrooted runs left bookkeeping under `$SPECS_PATH`, the stop adds one more line naming each, where it belongs, and which of these applies to it. Move them yourself, commit the move, then re-run: the plugin moves nothing and gives no commands.
  - Feedback and pending cost under `dev-workflows-feedback/` and `dev-workflows-cost/` there are never committed.
  - A `documentation/<slug>/dev-workflows/` there, and the bookkeeping and any `implementation.md` in a nested `specifications/`, are not committed while the variable stays wrong, but the first run after it is fixed commits them in the wrong place unless they are moved first.
  - A nested `specifications/` left in place is also searched for keys once the variable is fixed, so a key whose folder only it holds resolves there.
- **A run that resolves no address** is not stopped: `specs-preflight` tests the same signals at run start — on a checkout whose `.git` is writable, and on a path that is not a git repository at all, such as a `specifications/` directory mounted on its own — and prints a notice naming the variable, its value, the signal and the value to set, with every addition the stop would make, then runs on. On a checkout whose `.git` is read-only the preflight does nothing, so no notice is printed there.
- **What a stopped or noticed run does.** A stopped run and a noticed one alike — the notice for a specs tree inside a larger repository included — treat `$SPECS_PATH` as misplaced for the rest of the run: cost, feedback and follow-ups stay in the printed output, no `resume.md` is written, and the specs-repository steps commit nothing, hand nothing off and switch no branch. Where `$SPECS_PATH` is a git repository with a writable `.git`, the preflight still fetches, and names any branch it stayed on where it would otherwise have switched. A stopped run writes nothing under `$SPECS_PATH`. A noticed run that goes on writes what the command itself writes — its deliverable, and any draft or record it keeps beside it, such as `implementation.md` — where the command puts it, and leaves it there uncommitted. That bound is the specs-repository steps' alone: a command that changes code or documentation still branches and commits in the repository it changed, and where that repository also holds the specs tree, its branch moves the specs checkout too, which is one more reason that layout is unsupported.

**When it changes under a resumed conversation.** Each run of `specs-preflight` first prints one line, `Environment: SPECS_PATH=<real path> (origin <url|none>), REPOS_PATH=<value|unset>`, and the conversation carries it wherever it is resumed. Before `/release-notes` hands its draft off, and before each write of any run's tail — feedback, cost, follow-ups, `resume.md` — the run compares the environment it now stands in with that line, and once more at its terminal commit, which compares only `$SPECS_PATH`'s real path and its `origin` — the one check a run that hands nothing off and writes nothing in its tail meets. Where they differ — a conversation resumed in another container, with `claude --resume` or a continuation — it prints `Environment changed: …` once, naming both, and from there commits, hands off and records nothing more in the specs repository, without asking: its bookkeeping stays in the printed output, and what it already wrote stays where it is. Re-run in the container the run started in. A draft `/release-notes` appends before its handoff is not covered — it lands where `$SPECS_PATH` names at that moment — and neither is anything a run writes into a docs repository, which this check never reads.

## `$REPOS_PATH`

- **`$REPOS_PATH`** — where your code clones live; defaults to `/workspace` when unset.

**Resolution.** `${REPOS_PATH:-/workspace}`, read fresh by each run that resolves a code clone — there is no persisted override once a run ends. It may be a single directory or a colon-separated list. A keyed `/document` run, and `/release-notes` under diff grounding, never ask for it while it resolves: each prints the value it resolved as `Repos: <value> (from REPOS_PATH | REPOS_PATH unset — the default)`, adding that another base is set through `REPOS_PATH` or named at the plan's approval. Where a run resolves a repo it was handed the slug of — a keyed `/document` run's clones, and `/release-notes`' under diff grounding, each built into a slug→clone map — the match is by `git remote get-url origin` slug, **never by directory name**, so a clone renamed on disk is still found as long as its `origin` remote is intact. `/docs-init` and `/docs-brand` instead discover repos to offer you — `/docs-brand` only where neither its `--from` nor the docs profile's recorded `source_repos[]` settles the repository: each lists the directories one level under `$REPOS_PATH` and resolves your answer against that listing, so a rename changes the name a clone is offered under, never whether it is offered. `/docs-audit` does both: it resolves each `source_repos[]` entry the docs profile records — by its recorded path, else by its `origin` slug matched against the clones one level under `$REPOS_PATH` — and, where the profile records no such set, falls back to that same listing and confirms one with you.

**When unset.** The `/workspace` default takes over without a question — safe, because this is only ever a read/scan base, so a wrong default never writes anywhere unexpected: one that is missing is asked about (next paragraph), and one that is empty finds nothing to scan.

**When it points somewhere unreadable or empty.** Where no entry of the resolved value is an existing directory, `/document` and `/release-notes` ask you to set it, and take the path you then type once an entry of it is an existing directory, asking again where none is — or go on without code: `/document` as *Proceed without the repos — PRD-only for every repo*, `/release-notes` as *PRD content only*, its diff grounding turned off. An unresolvable slug escalates to the user rather than being silently dropped. A base that exists but is empty is not stopped on — it simply yields zero matched repos, which downstream turns into a diff-summary gap the run reports.

## `$DOCS_PATH`

- **`$DOCS_PATH`** — where your product documentation's clone lives; defaults to `/workspace/docs` when unset. It plays **two roles, and "read-only" belongs to only one of them**: as a docs-**grounding** root (`/release-notes`) it is read-only, and nothing ever writes into it; as a **write target** — `/docs-init` scaffolds a docs repository there, `/document` keyed mode, `/docs-profile`, a standalone `/docs-brand` and `/docs-audit` write into the docs repository they resolve there, and `/docs-serve` writes its uncommitted state file, `.dev-workflows/docs-serve.state.json`, into the one it resolves (and, under `--build`, whatever the profile's build command writes) — it is written to like any other docs repository. That is a different role for the same variable, not a contradiction.

**Resolution.** The commands that resolve a docs repository test `${DOCS_PATH:-/workspace/docs}` in two opposite ways. The **signal-positive** form tries it as one rung among several — after the working directory, before a search under `$REPOS_PATH` — and takes it only when it carries at least one docs signal; `/docs-profile`, `/docs-brand`, `/docs-serve` and `/docs-audit` all resolve their target repo this way. The **inverted** form is `/docs-init`'s alone: it takes the same expression only when it is **absent, or exists and carries no docs signal**, because that command is looking for a place to create a docs repository rather than adopt one; a `$DOCS_PATH` that does carry a signal there is never skipped in silence — it is reported, together with the redirect to `/docs-profile`, since it is almost certainly the repository the operator meant. `/document` Phase 0 resolves `${DOCS_PATH:-/workspace/docs}` separately, through its own **docs-repo discovery hint** — rung (a.5) of its resolution ladder, which is neither of those two forms — and takes it as the write target when it carries at least one docs signal or an in-repo `.dev-workflows/docs-profile.yml`. `/release-notes` resolves it for docs grounding instead, off `--no-docs` and overridable with `--docs <path>`.

**When unset.** The `/workspace/docs` default is probed. On a host where that path does not exist, the signal-positive rung simply does not fire — `/document`, `/docs-profile`, `/docs-brand`, `/docs-serve` and `/docs-audit` continue down their ladders — and grounding turns off. For `/docs-init` the same absence is the opposite outcome: its inverted ladder **accepts** an absent path as the place to create the repository, offers to create it, and reports that rung 2 answered.

**When it points somewhere unreadable.** For **grounding**, every miss — unset, missing, unreadable, or no markdown file found — is a **silent, non-blocking skip**, never an error, and the grounding path never writes into `$DOCS_PATH` under any circumstance. As a **write target**, the two forms above are never silent: each reports which rung answered on every run, `/docs-init` never passes over a `$DOCS_PATH` that carries a docs signal without reporting it and pointing at `/docs-profile`, and a directory resolved there is written to as any other docs repository would be. `/document`'s own Phase 0 ladder is the exception, and it names no rung: it takes a working directory that carries a signal silently, and shows the docs repository it resolved — whichever rung supplied it — in keyed mode's readiness table, ahead of its clarification phase. The `/document` discovery hint is a write-target *candidate* only in that same sense.

**Directory layout.** No expected substructure — whatever markdown sits under the root (for example, a full documentation-site checkout).

## `$GIT_USER_INITIALS`

- **`$GIT_USER_INITIALS`** — your branch identifier; optional, and rung 1 of the family's shared branch-naming identity ladder.

**Resolution.** It is rung 1 of the identity ladder every command here that creates a branch in a code or docs repository applies (`/release-notes`' `prd/` branch in the specs repository is named by the specs-repository handoff instead) — `/document` in keyed mode (direct mode creates no branch and no commit), `/docs-profile`, `/docs-init`, and a standalone `/docs-brand`. The rungs run in order, stopping at the first non-empty result: `$GIT_USER_INITIALS` (used verbatim, never with a trailing `/`) → `git config user.initials` → inference from existing branch names → a mandatory prompt if none of the three yields anything. What that prompt offers turns on which placeholder is being filled: where the repository documents no convention and the whole prefix is being supplied, it offers this command's fallback prefix — `docs/` for all four — as its default; where the repository's own convention has a name-or-initials segment, it omits the fallback choice and asks for a real identity outright, because `docs/` is not a name.

**When unset.** The ladder falls through to the rungs below it — there is no error, only degradation to a less certain source. Branch naming is repo-rule-first: where the target repo's documented convention has no name-or-initials segment at all, the variable is simply unused for that repo regardless of whether it is set.

**Session branch.** Where your specs repository is in session-branch mode — it protects its default branch, so the session files a run commits there go to a branch of your own and a pull request — the same ladder names that branch, `session/<identity>`, but stops before its prompt: with no identity, the run leaves its session files uncommitted and its `Specs repo:` line says to set this variable.
