# Environment reference

[Getting started](../getting-started.md) says what each variable is *for* and what to export before your first run. This page says what each variable **is** — its default, where that default comes from, what happens when it is unset, and what happens when it points somewhere the plugin cannot read or write. The plugin reads four user-settable variables. The rest of the names its own inventory check encounters while scanning for `$VAR` reads are never user-settable and stay out of scope here: `CLAUDE_PLUGIN_ROOT` and `ARGUMENTS` are runtime plumbing Claude Code itself sets for every plugin invocation.

## `$SPECS_PATH`

- **`$SPECS_PATH`** — the shared, team-visible repository holding the PRD folder `/document` and `/release-notes` read, and the one place either of them commits its own session bookkeeping; required to resolve a `<KEY>` address, with no built-in default.

**Resolution.** Read straight from the shell environment — there is no config file, CLI flag, or derived fallback that feeds it. Every git call against it is `git -C "$SPECS_PATH"`, never a `cd`, so the docs or code repository the run is working in is untouched.

**When unset.** What happens turns on the address form. A `<KEY>` is resolved by searching `$SPECS_PATH/specifications/`, so with the variable unset there is nothing to search, and both commands stop before doing anything, on the same ground: each checks the variable before it resolves a `<KEY>` — `/document` keyed mode in Mode detection, `/release-notes` in Phase 0 step 1 — and stops naming it with `choices: ["Set SPECS_PATH (enter the path)", "Cancel"]` (`workflows-core:escalation-rules` *Required path environment variable unset*), rather than on a folder it could not find. `grep -lE 'Set SPECS_PATH|Required path environment variable unset' plugins/*/commands/*.md`, run from the repository root, names every command in the family that stops on the variable itself. An `@<path>` names its folder directly and is resolved without the variable (`workflows-core:addressing`, `resolve-address`'s path branch), so it gets past address resolution in both; `/release-notes` then degrades rather than stopping — it falls back to `run_phase: pm`, which only suppresses the inference that would otherwise read the PRD folder for a `specification.md` or `design.md`. `/document`'s direct mode resolves no address and never needed one. `/docs-profile` never reads the variable at all. `/docs-audit` degrades: two of its seven surface kinds come from the specs tree, so with the variable unset it enumerates the other five, reports the two it did not, and stops only where no code repository resolved either.

**When it points somewhere unreadable.** The bookkeeping entry point, `specs-preflight`, requires an existing directory, a resolvable git dir, and a **writable** `.git`; a gate that fails on **writability** is a silent no-op (a read-only specs mount is a normal state here, and there is nothing to fix), while a gate that fails because `$SPECS_PATH` is not a directory or not a git repository at all emits a notice, one line naming the variable and the path — and, where the path is a `specifications/` directory mounted on its own, which of the two signals under *When it points inside the specs tree* below it matches, plus the stop's second line where it has one — that state is never supported, and it used to be indistinguishable from the read-only one, and because the terminal `commit-artifacts` step applies the same writability gate, nothing gets committed either. The deliverable-verification gate, `require-on-main`, needs only a readable git dir, and a failure there returns `unmanaged` — the caller proceeds exactly as it did before that machinery existed.

**When it points inside the specs tree.** `$SPECS_PATH` is the root of a dedicated specs repository, the directory that holds `specifications/`. It is never `specifications/` itself, nor a folder inside it. **Two layouts are unsupported, each for its own reason.** The first is **a specs tree inside a larger repository**, because the plugin switches branches and commits in the repository `$SPECS_PATH` belongs to, which there would move the checkout of everything else that repository holds. The second is given below. A `$SPECS_PATH` below its repository's top level that the check below does not stop draws a `specs-preflight` notice naming the top level, and the run goes on. Where `$SPECS_PATH` is set, `/document` in keyed mode and `/release-notes` first test two signals (`workflows-core:addressing` §3, `specs-root-check`), on a `<KEY>` and an `@<path>` address alike: `$SPECS_PATH` is itself a `specifications/` directory rather than a repository root, or it is, or directly holds, a specs folder — one whose artifacts assert a `key:` and a folder kind and, where `$SPECS_PATH/specifications/` exists, whose name begins with that kind and key, so a correct root's templates, `README.md` or `docs/` never count. Either one stops the run with `SPECS_PATH_INSIDE_TREE` where it resolves its address, naming the variable, its value, the signal and the value to set: the directory that physically holds that `specifications/`, symlinks resolved, where it lies in the same git work tree, and otherwise *the directory that holds `specifications/`*. Where that directory is not its repository's top level, the stop adds that the layout is unsupported. It stops rather than reporting the key's folder as not found. An `@<path>` address is tested too, because a run that passed its own resolution on one would otherwise meet the same stop at a later lookup by key, of an ARD or a specification, after its expensive work. **An earlier run's damage is caught too.** Where `$SPECS_PATH` is the `specifications/` directory directly under a repository root, or is itself a specs folder, or holds specs folders directly, the run stops whether or not a nested `specifications/` exists. Where one does, or where misrooted runs left bookkeeping under `$SPECS_PATH` (`dev-workflows-feedback/`, `dev-workflows-cost/`, `documentation/<slug>/dev-workflows/`) that nothing commits there, the stop adds one more line naming each and where it belongs. Move them yourself, commit the move, then re-run: the plugin moves nothing and gives no commands. A run that resolves no address is not stopped: `specs-preflight` tests the same signals at run start, on an ordinary checkout as well as on a mount, and prints a notice naming the variable, its value, the signal and the value to set, with every addition the stop would make, then runs on. There is no option to enter a path for the one run: fix the variable where it is set. A specs repository nothing has been written into yet matches neither signal and runs as before. **The second unsupported layout is a specs root that is itself a subdirectory named `specifications`**, holding its tree at `specifications/specifications/`. Its reason is detection rather than git: it cannot be told from that damage, so it stops on every run. Set `SPECS_PATH` to the repository root and move the tree up a level, as the stop says.

## `$REPOS_PATH`

- **`$REPOS_PATH`** — where your code clones live; defaults to `/workspace` when unset.

**Resolution.** `${REPOS_PATH:-/workspace}`, read fresh by each run that resolves a code clone — there is no persisted override once a run ends. It may be a single directory or a colon-separated list. Where a run resolves a repo it was handed the slug of — a keyed `/document` run's clones, and `/release-notes`' under diff grounding, each built into a slug→clone map — the match is by `git remote get-url origin` slug, **never by directory name**, so a clone renamed on disk is still found as long as its `origin` remote is intact. `/docs-init` and `/docs-brand` instead discover repos to offer you — `/docs-brand` only where neither its `--from` nor the docs profile's recorded `source_repos[]` settles the repository: each lists the directories one level under `$REPOS_PATH` and resolves your answer against that listing, so a rename changes the name a clone is offered under, never whether it is offered. `/docs-audit` does both: it resolves each `source_repos[]` entry the docs profile records — by its recorded path, else by its `origin` slug matched against the clones one level under `$REPOS_PATH` — and, where the profile records no such set, falls back to that same listing and confirms one with you.

**When unset.** The `/workspace` default takes over silently — safe, because this is only ever a read/scan base, so a wrong or empty default finds nothing to scan rather than writing anywhere unexpected.

**When it points somewhere unreadable or empty.** A user-supplied path is validated to contain at least one directory before it is accepted; `grep -rn 'at least one directory' plugins/*/commands/`, run from the repository root, is the authority on which commands document that step. An unresolvable slug escalates to the user rather than being silently dropped. The default itself is never validated this strictly — an empty `/workspace` simply yields zero matched repos, which downstream turns into a diff-summary gap the run reports.

## `$DOCS_PATH`

- **`$DOCS_PATH`** — where your product documentation's clone lives; defaults to `/workspace/docs` when unset. It plays **two roles, and "read-only" belongs to only one of them**: as a docs-**grounding** root (`/release-notes`) it is read-only, and nothing ever writes into it; as a **write target** — `/docs-init` scaffolds a docs repository there, `/document` keyed mode, `/docs-profile`, a standalone `/docs-brand` and `/docs-audit` write into the docs repository they resolve there, and `/docs-serve` writes its uncommitted state file, `.dev-workflows/docs-serve.state.json`, into the one it resolves (and, under `--build`, whatever the profile's build command writes) — it is written to like any other docs repository. That is a different role for the same variable, not a contradiction.

**Resolution.** Two entry points in `docs-workflow/repo-resolution.md` test the same expression and read it oppositely (D23). The **signal-positive** form, `resolve-docs-repo` (§1), tries `${DOCS_PATH:-/workspace/docs}` as one rung among several — after the working directory, before a search under `$REPOS_PATH` — and takes it only when it carries at least one docs signal (§3); `/docs-profile`, `/docs-brand`, `/docs-serve` and `/docs-audit` all resolve their target repo this way. The **inverted** form, `resolve-scaffold-target` (§2), is `/docs-init`'s alone: it takes the same expression only when it is **absent, or exists and carries no docs signal**, because that command is looking for a place to create a docs repository rather than adopt one; a `$DOCS_PATH` that does carry a signal there is never skipped in silence — it is reported, together with the redirect to `/docs-profile`, since it is almost certainly the repository the operator meant. `/document` Phase 0 resolves `${DOCS_PATH:-/workspace/docs}` separately, through its own **docs-repo discovery hint** — rung (a.5) of its resolution ladder, not either shared entry point — and takes it as the write target when it carries at least one docs signal or an in-repo `.dev-workflows/docs-profile.yml`. `/release-notes` resolves it for docs grounding instead, off `--no-docs` and overridable with `--docs <path>`.

**When unset.** The `/workspace/docs` default is probed. On a host where that path does not exist, the signal-positive rung simply does not fire — `/document`, `/docs-profile`, `/docs-brand`, `/docs-serve` and `/docs-audit` continue down their ladders — and grounding turns off. For `/docs-init` the same absence is the opposite outcome: its inverted ladder **accepts** an absent path as the place to create the repository, offers to create it, and reports that rung 2 answered.

**When it points somewhere unreadable.** For **grounding**, every miss — unset, missing, unreadable, or no markdown file found — is a **silent, non-blocking skip**, never an error, and the grounding path never writes into `$DOCS_PATH` under any circumstance. As a **write target**, the two shared entry points are never silent: `resolve-docs-repo` and `resolve-scaffold-target` report which rung answered on every run, `/docs-init` never passes over a `$DOCS_PATH` that carries a docs signal without reporting it and pointing at `/docs-profile`, and a directory resolved there is written to as any other docs repository would be. `/document`'s own Phase 0 ladder is the exception, and it names no rung: it takes a working directory that carries a signal silently, and shows the docs repository it resolved — whichever rung supplied it — in keyed mode's readiness table, ahead of its clarification phase. The `/document` discovery hint is a write-target *candidate* only in that same sense.

**Directory layout.** No expected substructure — whatever markdown sits under the root (for example, a full documentation-site checkout).

## `$GIT_USER_INITIALS`

- **`$GIT_USER_INITIALS`** — your branch identifier; optional, and rung 1 of the identity ladder `workflows-core:branch-naming` §2 fixes.

**Resolution.** It is rung 1 of the identity ladder every branch-creating command here applies — `/document` in keyed mode (direct mode creates no branch and no commit), `/docs-profile`, `/docs-init`, and a standalone `/docs-brand`. The rungs run in order, stopping at the first non-empty result: `$GIT_USER_INITIALS` (used verbatim, never with a trailing `/`) → `git config user.initials` → inference from existing branch names → a mandatory prompt if none of the three yields anything. What that prompt offers turns on which placeholder is being filled: where the repository documents no convention and the whole prefix is being supplied (§1.4), it offers this command's fallback prefix (§2.4, `docs/` for all four) as its default; where the repository's own convention has a name-or-initials segment, §2.5 omits the fallback choice and asks for a real identity outright, because `feat/` is not a name.

**When unset.** The ladder falls through to the rungs below it — there is no error, only degradation to a less certain source. Branch naming is repo-rule-first: where the target repo's documented convention has no name-or-initials segment at all, the variable is simply unused for that repo regardless of whether it is set.
