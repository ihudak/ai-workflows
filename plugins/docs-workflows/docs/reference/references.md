# References reference

`docs-workflows` bundles 26 files under `references/` — six top-level markdown files and five bundled subtrees. This page enumerates the six top-level files, the four in `docs-workflow/`, the three in `docs-audit/` and the two in `docs-iteration/`, which are enumerated as well as counted because each is a distinct entry point a command names — grouped by concern below — then counts the other two subtrees rather than listing each file inside them, although commands and agents cite files in both of those by name too. The arithmetic: six named individually, plus 5 + 4 + 4 + 3 + 2 = 18 markdown pages across the five subtrees — 6 + 18 = 24 accounted for, against 26 files on disk. The remaining two are non-markdown data or templates inside the `docs-profiles/` subtree, deliberately not listed as reference pages: a defaults file and an owners list, neither of them prose a reader would open. The subtree figures below are markdown-page counts specifically; the two data files already sit inside that same subtree and are not part of that count, so nobody should later "correct" a subtree figure by adding them back in.

The shared corpus every plugin in this family reads — the addressing grammar, the git and phase-handoff entry points, model routing, escalation and triage, cost/feedback/follow-up emission, the docs-grounding and doc-structure conventions, and the PRD format — ships in the companion `workflows-core` plugin and is enumerated on its own references page, reached through the loader skill rather than by path. Some of those references load by part, as that page says: where a command here cites one rule of such a reference, it loads only the part holding that rule, and it loads the whole reference where it cites no particular rule or asks for all of it. What is listed here is what `docs-workflows` itself carries.

## Verification gates

The accounting a documentation run keeps about what it actually verified, and the two extractors that decide what there was to verify.

- `gate-ledger.md` — the six verification-gate outcomes (`RAN` / `DEGRADED` / `FAILED` / `UNAVAILABLE` / `SKIPPED_BY_USER` / `NOT_APPLICABLE`), the rule that no outcome is orchestrator-assignable to mean "I decided not to run this", `/document`'s per-mode gate registry and [`/docs-write`](../commands/docs-write.md)'s own — the toolchain check, the repository's checklist, the style check and the build, which must pass for a unit to move wherever the profile records one for the page's space — the `UNAVAILABLE` conversion prompt, and the reviewer contract; consumed by `/document`, by `/docs-write` and by the agents whose gates it registers, and cited by `/docs-init`, which borrows its distinction between an unrun gate and a passed one for its own verification.
- `repo-verification-gates.md` — how to extract a docs repo's own pre-PR checklist into the `repo_verification_gates` block a reviewer can check the written files against, augmenting the plugin's own gates rather than overriding them; `doc-planner` extracts it for keyed `/document`, and the orchestrator itself for direct mode and for `/docs-write`, which checks each unit's page against it.
- `toolchain-preflight.md` — the environment check `/document` runs at Phase 0, deriving the required tool set from the resolved profile, the repo's config signals and the repo's own documented prerequisites; the tool→gate map; and the prompt that fires only when a required tool is missing. `/docs-write` runs it at its Phase 0 too, deriving the set from the profile's build and lint commands and the repository's own files, never from its dev servers. `/docs-init` runs the same check at its Phase 2 but derives nothing — there is no profile yet — and hands it a fixed set of its own. The file says which test each tool takes, by asking the shell — and the directory — that will run it: a tool the plugin runs through `bash -c` or as `command <name>` — `bash`, `curl`, `lsof`, `ps`, `vale` and every dev server's tool — is asked of that same child shell, which runs no alias of yours and no shell function of yours that you have not exported, while a build or lint command's tool, which runs in the Bash tool's own shell, is asked of that shell, where your aliases and functions apply exactly as they will when the command runs. Either test runs from the directory the command runs from, so a tool a profile records as a path — `node_modules/.bin/vitepress` — resolves as it will at run time, and an alias pointing somewhere that is not there passes, to fail at the gate like any other environmental failure. Each tool and directory the check takes from the profile or the repository's files is held to a fixed set of characters first and written single-quoted, so nothing in a profile runs while the check runs: one outside that set reads missing, named by the field it came from. `/docs-serve` runs no preflight, but tests its own tools with the first of those tests — not a bare `command -v` in your shell, which an alias or a shell function named after the tool passes; `/document`'s render check uses it too — and takes the file's definition of a command's tool, with that test, before it starts a server, and its set-aside of a leading `cd <dir> &&` and `VAR=value` words when it matches a recorded command to a process's command line. The file also defines, once, the five names Vale reads its configuration from and how the plugin runs Vale over one — a lint and `vale sync` alike, on the repository's configuration with no global Vale configuration and no `VALE_CONFIG_PATH`, as a clean CI runner has neither, and with the limit it states for a configuration that sets no `StylesPath`, which keeps the machine's shared default styles directory — which `docs-style-checker`, `docs-scaffold-reviewer` and `/docs-init` cite.

## Git and handoff

The handoff mechanics this plugin's documentation-writing commands run against a **docs** repository, rather than ones the family shares.

- `finish-and-handoff.md` — the mechanics `/document` (keyed mode) uses for its inline-profiling-branch handling and its finish-and-handoff step: squash, opt-in push, copy-paste PR draft. And a backlog run's finish, which `/docs-write` runs: the check that the backlog and the profile are committed, the branch it continues or cuts, one commit per unit, what becomes of a unit that does not commit — its files moved under `.dev-workflows/unfinished/`, its edits restored — one push offer and the pull-request draft it prints. The specs repo's own git entry points, and the code repo's, are elsewhere — the `specs-repo-git` and `phase-handoff` references in `workflows-core` for the first, the pipeline plugin's `code-handoff` reference in `dev-workflows` for the second.

## Finding the work

How the two documentation commands find the code a feature changed, beyond the implementation record.

- `key-discovery.md` — how `/document` (keyed mode) and `/release-notes` run the whole-key commit scan, its probe and the optional GitHub pull-request search through `scripts/key-discovery.py`; how the repository that holds the documentation is read by path — a commit touching only its documentation set, which `key-discovery.md` defines, is never counted as work — and, where no content path is known there, or one is the whole repository, how the repository is left out whole, or read whole where the implementation record names it; how a merged pull request's landed commits join the scan's result — in that repository, where it is read by path, only those touching another path — while every other pull request found is listed, never read; and the check `/document` runs on its own commit against the same set.

## Authoring formats

- `release-note-types.md` — the release-note section map (`## Breaking changes` / `## Feature updates` / `## Fixes`, all three in one **release-notes.md** under a release-version heading, each draft under a scope comment naming the PRD or Epic it was drafted for, the stage its run drafted at — `stage: pm` or `stage: dev` — and the moment its run started, where the run still held that moment when it wrote the draft, neither of which bounds anything and both of which `/dev-workflows:ready` reads for its *Release Preparation* stage, and every commit its run read, which is what bounds a later run rather than any date), the per-section draft shape and prose rules, the deprecation-note rule, the effective-version rule, the rule for a state the release starts from, Change Type sourcing, and how a claim a `/dev-workflows:conformance` entry settled is worded in the draft — which entries count, which of two entries on one claim wins and what each decision maps to being the `source-truth` reference's, which this file cites rather than copies; consulted by `release-notes-writer`, cited by `/release-notes` for its own invariants, and named by `docs-workflow/scaffold-tree.md`, by the companion `dev-workflows` plugin's `/ready` command and its conformance-record format, and by three shared references on the companion `workflows-core` plugin's References page, the PRD format, the implementation record and `source-truth`.

## The documentation-portal scaffold

`docs-workflow/` (4) — the bulky, stable content the portal-scaffolding commands write, held here so the command bodies stay orchestration. Each file is enumerated rather than merely counted, because each is a named entry point a command cites when it says which part it is executing.

- `docs-workflow/scaffold-tree.md` — what a scaffolded documentation portal contains: the directory tree and why each section is standard, the per-directory stubs with their frontmatter and their "what does not belong here" half, the `nav:` generation rule and the regeneration `/docs-write` runs over configs that carry the generated block, the two MkDocs configs, and the Vale config with its vocabulary-seeding rule.
- `docs-workflow/visibility.md` — the two-build public/internal model, the two traps that make the obvious checks useless (the dev server is not the build; snippets cross the boundary invisibly), the two output-level CI gates and the conditional third, the marker convention both halves of gate 2 depend on, and the CI workflow the scaffold writes.
- `docs-workflow/repo-resolution.md` — the shared docs-repo resolution ladder, in its two opposite forms (`/document` resolves its repository by a ladder of its own, whose differences from this one the file records): `resolve-docs-repo` for a command that needs a docs repository that already exists, and `resolve-scaffold-target` for the one command that needs a place to make one, plus the shared signal set both test against.
- `docs-workflow/contrast.md` — the WCAG 2.2 contrast thresholds a derived brand palette is held to, the relative-luminance formula with a worked example, and what a failing colour does (reported with its measured ratio, applied only on the operator's confirmation).

## The documentation audit

`docs-audit/` (3) — the vocabulary a documentation audit is written in and the two contracts that vocabulary produces, held here so that one file defines each name and no command or agent re-derives it. Enumerated rather than merely counted, for the same reason as `docs-workflow/` above: each file is a named entry point a command cites when it says which part it is executing.

- `docs-audit/coverage-model.md` — what a documentation **surface** is and where each of the seven kinds is derived from — a part of a code repository for five, the specs tree for `decision` and `release` — the page-**type** vocabulary and the `(surface, audience, type)` coverage grid it is the second axis of, why tutorials are the one quadrant a human picks rather than the audit generating it, the four prioritisation signals and the guard that stops volatility excluding a surface instead of merely ranking it, the five paths a backlog **unit** enters by with the consequence of the hand-written one, and the definition of done.
- `docs-audit/backlog-format.md` — `.dev-workflows/docs-backlog.yml` in full: the schema with its `sources[]`, `surfaces[]`, `units[]`, `tutorial_candidates[]`, `coverage` and `threshold` blocks, why surfaces and units are two tables rather than one, the unit status lifecycle with the three transitions a command writes today — the mint to `missing`; `missing` → `drafted`, by `/docs-write` in the commit that writes the page and by a refresh; and a refresh's `missing` → `published` — and the one edge that deliberately does not exist, what `blocked_by` carries, what a `coverage` fraction counts, the file's one home at the docs repo's git top level, and the invariant tying `visibility` to `page_path`.
- `docs-audit/evidence-contract.md` — what a documentation claim may rest on: the one interface with its user and engineering implementations, the three evidence kinds (`code`, `walkthrough`, `artifact`) and what each records, the rule that a marked claim never becomes prose fact by default, the walkthrough file with its closed action vocabulary, how a walkthrough is executed as a checklist today and by a driver later without the format changing, and the page-level marker every page `/docs-write` drafts carries until the page is walked.

## The documentation backlog runs

`docs-iteration/` (2) — what a backlog run — a command that takes one documentation backlog unit at a time and moves its status — changes in the agents it shares with `/document`, and the steps every backlog run shares. Enumerated rather than merely counted, for the same reason as `docs-workflow/` and `docs-audit/` above.

- `docs-iteration/unit-brief.md` — the unit brief: the one list of the sections of `doc-writer` and `doc-reviewer` that a backlog run's brief replaces, the brief's fields and how the run composes each, and the text that replaces each listed section. A dispatch whose brief does not say it is a unit brief reads both agents as they stand, so `/document` reads them unchanged.
- `docs-iteration/backlog-run.md` — the steps every backlog run shares, written once, with the values each command fills in for itself — the prefix of its stop codes and of its temporary files, the phase that scans the code, the question that asks consent and the files a writing agent may change among them: what the run treats as data and how it quotes a value; the value classes and the two tests that hold a value to them; the base branch; the unit's sources, and the test that admits a code repository; the read of the pages already carrying a unit's id; a walkthrough's admission; the read of an ARD at the specs default branch; the copy a run takes of a file before it first edits it, and the two tree tests around each writing agent; and the two programs that read the page-level marker and test a page for it. [`/docs-write`](../commands/docs-write.md) reads it whole before it starts and cites each step from its own phases, which keep its stop lines and what it does with each step's result.

## Bundled reference sets

Two further subtrees carry bundled guidance too large or too domain-specific to enumerate file-by-file; each is counted here instead.

- `docs-profiles/` (5) — docs-profile authoring conventions for the built-in `example-docs` worked example (frontmatter, changelog, anchors, render verification, the docs-profile schema). Every command here reads a file in it — `/release-notes` only the built-in profile, `docs-profile.default.yml`, for its commit scan under diff grounding, where the repository holding the documentation has no profile of its own — and so do the `doc-planner`, `doc-writer` and `doc-reviewer` agents, the `docs-frontmatter` skill and the `changelog-owners-reminder` hook.
- `handoff/` (4) — one input/output document-format contract per agent, read by the agent itself — and, for `docs-auditor` and `ia-planner`, also by `/docs-audit`, which builds each dispatch's brief from the file: one each for `diff-summarizer`, `release-notes-writer`, `docs-auditor` and `ia-planner`. The last two are a matched pair — `ia-planner`'s input block is `docs-auditor`'s output block, verbatim — so a field added to one is added to the other in the same edit, and the volatility window and its buckets are written once, in `docs-auditor`'s, for both of them to read.

One of these subtrees (`docs-profiles/`) also holds the data and template files named in the introduction above, so its markdown-page count here is smaller than its file count; `handoff/`, `docs-workflow/`, `docs-audit/` and `docs-iteration/` are markdown only, and for them the two counts agree.
