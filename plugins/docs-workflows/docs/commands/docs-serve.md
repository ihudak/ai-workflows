# /docs-serve

Starts, stops, or checks a profiled documentation repository's dev server, and reports a URL that actually opens from the host.

## Who runs it

`/docs-serve` runs outside the role pipeline, the same way `/docs-profile` does — no role, no cost-attribution phase (it is one of the commands [Session cost](../reference/session-cost.md) names as emitting nothing), and no `workflows-core:model-routing` classification: it starts a process and reports a URL rather than reasoning about anything. [Workflow overview](../workflow.md) draws it beside `/docs-profile` in the setup-utility row, reached at any point rather than as a pipeline stage. It writes no documentation and no artefact, which is also why it carries no review gate — D17, the docs-workflow family design's rule that every artefact-writing command of that family passes a high-tier review, names `/docs-serve` as the family's sole exemption. That family is the one the design's §4 table lists — `/docs-init`, `/docs-brand`, `/docs-audit`, this command, and the commands that design plans after them — not every command in this plugin. Of the four that ship, this is the only one without a gate: `/docs-audit` passes `docs-audit-reviewer` at Opus, and the other two `docs-scaffold-reviewer`.

## Synopsis

```
/docs-serve [<docs-repo-path>] [--internal] [--stop] [--status] [--build] [--port <n>]
```

None of the three run flags apply to this command — it dispatches no `impl-maintenance`, calls no `emit-cost`, and invokes no `workflows-core:model-routing` — but `strip-run-flags` still runs first in Phase 0, so an explicit `--skip-costs`, `--skip-feedback` or `--enforce-model` is recognized and reported ignored rather than misread as the docs-repo path or one of this command's own flags.

Every recognized flag is stripped from `$ARGUMENTS` before the remaining token is read as the optional docs-repo path (Phase 0). `--status`, `--stop`, and `--build` each select a short-circuit mode (Mode dispatch); with none of the three, the command resolves the repo's `dev_servers` profile and serves it. `--internal` selects the internal build's server where the profile distinguishes one, and stops where the profile tags a public server but no internal one — a `--public-only` scaffold — rather than serving the public build in its place; `--port <n>` serves on `<n>`: the port reaches the server only through the `{port}` token in the profile's recorded command, which every run replaces with the port it serves on and which is the only part of a command ever rewritten. On a command without the token — a fixed-port one — `--port` stops rather than start a server that binds elsewhere.

## What it needs

- **A profiled docs repository** — resolved by `resolve-docs-repo` (`docs-workflow/repo-resolution.md` §1), the same signal-positive ladder `/docs-profile`, `/docs-brand` and `/docs-audit` use: the given path, else the working directory, else `$DOCS_PATH`, else a search under `$REPOS_PATH`, else a question — only two of these rungs can hand back a directory carrying no docs signal, an explicit path (taken as given) and the final generic question; every other rung tests against a docs-repo signal before it can answer, and the rung that did is reported.
- **A written `dev_servers` block** — `.dev-workflows/docs-profile.yml` at the resolved repo's git top level (not in the plugin, and not in a site directory below that top level), specifically its `dev_servers.servers[]` list, whose commands run from that top level, keep their server in the foreground — a command that detaches it (`setsid`, `nohup … &`, a trailing `&`, `docker run -d`) is a profile defect, since this command follows the server it starts through the process group it starts it in, and a server detached out of that group is out of its reach; a foreground `docker run -p` or `docker compose up` keeps to the rule, but Docker's forwarding holds its port, not the command's process, so this command cannot identify its server, and you stop it with Docker — and bind the port they are given or fail: a command that moves to another port when its own is busy is a profile defect too, so VitePress's command passes `--strictPort`, and an Astro site, whose command line cannot pin its port, sets `vite: { server: { strictPort: true } }` in its configuration. An `astro dev` command also sets `ASTRO_DEV_BACKGROUND=0` ahead of the tool: Astro 7 detaches its server wherever it detects an agent, Claude Code among them, unless that variable is set; and an `astro preview` command sets `ASTRO_PREVIEW_BACKGROUND=0`, since Astro 7.2 detaches the preview server the same way. A repo that has never been profiled, or whose profile predates `dev_servers`, stops with `DOCS_SERVE_NO_DEV_SERVER` and points at `/docs-workflows:docs-profile` to write one.
- **`curl` and `bash` — and, off Linux, `lsof` and `ps`** — every mode but `--build` judges ports with `curl`, starts, tests and signals the process group it follows each server through with an explicit `bash`, and reads which process holds a port, and that process's working directory, parents and command line, from the socket and process tables. On Linux it reads them from the kernel's own tables under `/proc`, which need nothing installed and no root for your own processes, so it runs in a slim container that ships neither `lsof` nor `ss` nor `ps`, and in one that drops root before you can install anything; elsewhere it reads them with `lsof` and `ps`, both of which macOS ships. Where one it needs is missing, it stops before it probes, starts or stops anything (`DOCS_SERVE_NO_PROBE`, `DOCS_SERVE_NO_BASH`, `DOCS_SERVE_NO_SOCKET_TOOL`, `DOCS_SERVE_NO_PS`). Each is tested by asking the child shell that runs it, rather than by a bare `command -v` in your own, which an alias or a shell function of its name passes (`toolchain-preflight.md` §3). `bash` is tested first and reported alone when it is missing, since that test runs through it and every other tool would otherwise read missing with it. None has a fallback: without a socket table nothing can say which process holds a port, so every identity the command gave it would be a guess. The server's own tool — `mkdocs`, `pnpm`, `node_modules/.bin/vitepress`, whatever its command runs — is checked before it is started, and so are a package manager's installed dependencies (`DOCS_SERVE_NO_SERVER_TOOL`).
- **Nothing from `$SPECS_PATH`** — this command runs no `specs-preflight` and no `commit-artifacts`. The only state it records lives beside the profile, under the resolved repo's git top level's `.dev-workflows/` — plus, where no rule ignores that file yet, one line naming it in the repository's local `.git/info/exclude`.

## What it produces

The default flow (Phase 1 onward) selects the server to run — by a profile's own `visibility` tag when one is recorded, by being the only server on offer, or by asking when several exist and neither applies — then checks whether it is already running (never starting a second copy of a server that is already up), works around a port already held by something else by moving forward to the next free one and saying so — where the command carries the `{port}` token; a fixed-port command binds its own port wherever it starts, so a collision on it is reported with what holds the port, and nothing is left running for it — starts the chosen command in a process group of its own — its `{port}` token replaced by the port it serves on — bound to `0.0.0.0` so a container-mapped port stays reachable from the host, polls it for readiness — and stops polling the moment that group is gone, reporting that the command exited, with the last lines of its log, and recording nothing, rather than waiting out the timeout for a server that has already exited — and reports the URL to open: the profile's own `public_base_url` when set, or the in-container address with an explicit caveat when not. It then records the pid of the process actually holding the port — read from the socket table, never a wrapper's — and, beside it, the id of the process group it started, so a later `--stop` ends a server started through `npm run` or `pnpm` together with its wrappers, and the path of the log its start wrote, outside the repository, which `--stop` deletes with the record — only ever a regular file named `dw-serve-…`, whatever the record says — and a run leaves no log that no record names, save one interrupted between starting a server and recording it: a run that records nothing for what it started deletes its log itself, after quoting the last lines of one whose command exited, and a record that replaces another takes over that record's log where the replaced record's process group is still its own and holds the listener the new record names, and deletes it otherwise; the records go under `.dev-workflows/`, **keyed by the port the server is bound to** and naming the server it started — its space, and its visibility where the profile tags one — so a later `--status` or `--stop` — in the same session or a new one — can act on what this run started. A port holds one server and a space name does not identify one: the profile `/docs-init` writes serves one content space twice, a public site and an internal one, and a record per port is what keeps the two from overwriting each other. Every lookup made through the server selection — a serve run checking whether its server is already up, and `--status --internal` or `--stop --internal` — looks only at records of the selected server before it matches a port, so a server a port collision moved onto another server's port is never mistaken for that one: not the public site moved onto the internal site's port, and not one space's server moved onto the next space's. **A port counts as free only where nothing answers on it and nothing is listening on it** — a listener bound to an address `localhost` does not reach answers nothing, so a port held that way is a collision like any other: walked past where the command carries `{port}`, and reported with what holds it where it does not. Whether any other socket standing on a port refuses a bind is in no table, so it is not predicted: a server that exits before its port answers is a collision at that port too wherever something is listening there, or its log names an address-in-use failure. Both are asked, because neither sees the other's case: a connection's local end standing on the port is no listener, and each tool words the failure its own way. **Where no record survives, a server is identified by evidence, never by the port it answers on.** A port that answers — the configured one, one the collision walk reaches, or one a collision would have moved the server to — is asked which process holds it before its page is asked anything. A process established as another checkout's — the socket table names it, and its working directory lies in another checkout of the same repository, such as a sibling `git worktree` (nested inside this one or not) — is left running, named in the report and never recorded, so one checkout's `--stop` never ends it. Outside git, where there are no worktrees to confuse it with, a process standing in the docs directory or any directory below it is this checkout's, a git repository kept below the docs directory included: the docs directory is the unit there. A process in this checkout is matched to a server by the command line it was started with, whether or not its page names the site — so a client-rendered site whose page names nothing, such as a VitePress dev server's, is still found rather than walked past and started twice. A command started through `npx` is matched by the `npm exec` command line it becomes as it runs; a recorded command that begins `cd <dir> &&` or with a `VAR=value` assignment is matched by what follows them, which is all a server's own command line carries, since the shell consumes both; and a recorded command carrying quotes is matched with every quote removed from both sides and its spacing collapsed, since the shell strips the quotes before the server sees its arguments. Where one recorded command is contained in another — `pnpm start` in `pnpm start:internal` — a command line carrying both names the longer one's server, since a process started with the shorter command never carries the longer one's text; a command line carrying two unrelated recorded commands names neither. On the two-build profile `/docs-init` writes, a process in this checkout whose command line names no server is matched by the site name in its page's title instead, which never overrides a server the command line names. Whether the page names this docs site at all decides what the run does only where neither says which server it is; anywhere else it only helps name what holds the port. A port whose process the socket table does not show — one another user runs, say — names no server at all, whatever its page says. The selected server is re-adopted and recorded wherever it is found, on any profile, and another of this repository's servers is passed over. For a command carrying `{port}`, the only kind a collision can move, the ports a collision would have moved it to are searched before anything starts unless `--port` names the port — and searched whether the configured port has come free since or is still held, because a copy moved past a port that was busy then can sit beyond one that is free now. Once the server it started answers, the run asks the socket table which process won the port. A process in the process group the run started is that server, whatever its command line says — npm rewrites its own as it runs, dropping its options and the `--` before the script's, and two servers whose commands differ only by a leading `cd <dir> &&` leave the same command line behind — so the run records it without asking anything else. Otherwise it records what won only where that is this checkout's server as the checks above identify it — the same server another run in this checkout started a moment earlier, say. Where another checkout of the repository started at the same moment and won, or another of the repository's servers or some other process took the port first, this run records nothing and names what holds the port. Where the socket table shows no process on the port at all — another user's, or a container's published port — nothing can say whose server answers, and it may be the one just started, so the run records it without a pid and says so, naming `--stop --port <n>` to clear the entry if what answers is not this docs site. Only where nothing says which server answered, and its page names this docs site, does a profile with one server re-adopt it anyway — and then only where the socket table places that process in this checkout — since the profile has no other server it could be. Anywhere else — a profile with more than one server, or a process the socket table does not show or cannot place — it says it cannot tell and starts nothing, naming the process to stop by hand — or, where the command carries `{port}`, `--port <n>` to serve elsewhere. Every server it re-adopts is recorded with the pid of the process holding its port. It records an entry without a pid in two cases only: a server that had not answered when the readiness wait ran out, and a port whose process the socket table does not show. Each keeps the id of the process group the run started and the start time of that group's leader, and while that group is still the one it started — its leader still leads it, with the recorded start time — `--status` reports a server that has not bound its port yet as *starting*, a serve run reports it still starting and starts no second copy, another server's serve run counts its port as taken though nothing answers there yet — at its configured port and on its collision walk alike, so it never starts on that port from under the server coming up there — `--status` gives the entry its pid once a process in that group holds the port, whatever its command line says, and `--stop` ends it through the group, before it binds as well, so a slow server never comes up unrecorded after a `--stop`. Without that group, `--status` and `--stop` judge such an entry by whatever now holds its port. Where that is the server the entry recorded, identified in this checkout as a serve run would re-adopt it, the entry takes its listener's pid, and `--stop` then ends it like any other. Where it is another checkout's server, another of the repository's servers or a process that is not this docs site, or nothing answers there, the entry is stale, and `--stop` removes it without signalling anything. Only where nothing identifies what answers and it answers as this docs site does the entry stay without a pid, and then `--stop` cannot end it and leaves it in place. `--stop` reports a server stopped only once no process on its port is identified as one of the repository's servers and, where nothing there is identified at all, the port no longer answers as this docs site — a port another checkout's server now holds counts as stopped, whatever its page says. Where the process group it signals still runs after `SIGKILL` — or, for an entry that records no group of its own, the process it signals still holds the port after `SIGKILL` — it says so, never reports the server stopped, and keeps its record, so a second `--stop` can signal it again. A recorded pid counts only while the socket table still names it on its port, and a recorded group only while its leader is still the process the run started — the start time it recorded for it — so a pid or group number reused after a container restart is never taken for the server, and never signalled. While that group counts, any member of it holding the port is the server, whatever pid the record names — one re-spawned under a new pid included — and the record takes that member's pid; and while that group counts with nothing holding the port, the record is *starting* whatever pid it names, so a server caught between one listener and the next is reported as still coming up, counted as running by a serve run, and ended through its group by `--stop`, rather than read as stale by three of the four and signalled by the fourth. On a profile whose `dev_servers.concurrent` is `false`, it starts nothing while another of the repository's servers is known to be running — recorded and alive, recorded and still starting, or identified by this run's own port checks, which on such a profile take in every other server's configured port — and names that server and how to stop it. The command never commits the state file, and keeps it out of `git status`: where no rule ignores it, the command adds that one path to the repository's local `.git/info/exclude`, which is never committed either, so a clean-tree check — `/docs-profile`'s, `/docs-brand`'s, `/document`'s — does not meet it as an untracked file, whether `/docs-init` scaffolded the repository or not. That does not cover a copy someone committed by hand: git reports a tracked file's changes whatever ignores it, so that copy shows in `git status` until `git rm --cached` takes it out of the index. A `.gitignore` line, where you want one, ignores that one file, not the `.dev-workflows/` directory, which also holds the committed profile.

`--build` runs the profile's build command (from `builds[]`, `commands.per_space.<space>.build`, or `commands.build`, in that order) in the foreground and exits without serving — the flag exists instead of a separate `/docs-build` command, since the pipeline already gates on the profile's build. `--status` reports every server this command has a live record of for the resolved repo. `--stop` ends one. With either, `--port <n>` names the server bound to port `<n>` — the one recorded there, never one a collision moved off it — so `--stop --port <n>` stops exactly that server, without asking.

## Gates

**No review gate, by design (D17).** This command writes no documentation and no other artefact — a start/stop/status/build run against a repo's own dev-server process — so there is nothing for a reviewer to check before it is trusted. Its closing report carries a `### Next step` line rather than a `choices` next-phase offer, and that offer states explicitly that it carries no `<merge-clause>`: nothing downstream ever waits on a pull request this run might have opened, because this run opens none.

## Failure modes

- `DOCS_SERVE_NO_DEV_SERVER` — the resolved repo's profile is absent, or present but records no `dev_servers` block. Run `/docs-workflows:docs-profile` against the repo first.
- `DOCS_SERVE_NO_PROBE` — `curl` is not installed (or not on `PATH`). Every mode but `--build` judges ports with it, and without it a port that answers and a free one look the same, so the run stops before it probes, starts or stops anything.
- `DOCS_SERVE_NO_BASH` — `bash` is not installed (or not on `PATH`). Every mode but `--build` starts, tests and signals a process group with an explicit `bash`, and a group call that cannot run would read a group that still runs as gone, so the run stops before it probes, starts or stops anything. A group call whose `bash` could not run later in a run stops it the same way.
- `DOCS_SERVE_NO_SOCKET_TOOL` — off Linux only: the host has no `/proc/net/tcp` to read and no `lsof` installed. Every mode but `--build` reads which process holds a port from one of them, and without either nothing can say whose server answers there or which process `--stop` would end, so the run stops before it probes, starts or stops anything. Install `lsof`.
- `DOCS_SERVE_NO_PS` — off Linux only: `ps` is not installed. Every mode but `--build` can need to match the process holding a port to a server, which on a host with no `/proc/net/tcp` means reading its parents and command lines with `ps`, so the run stops the same way. Where more than one of these is missing, the run prints each of their messages at once — except a missing `bash`, which is reported on its own, since the test for every other tool here runs through `bash` and would report each of them missing too.
- `DOCS_SERVE_NO_BUILD_COMMAND` (`--build` only) — none of `builds[]`, `commands.per_space.<space>.build`, or `commands.build` resolves a command to run.
- `DOCS_SERVE_NO_INTERNAL_BUILD` — `--internal` on a profile that tags its servers or builds but records no internal one, which is what a `/docs-init --public-only` scaffold writes. Drop `--internal` to serve the public build; an internal build needs its own build config and a server entry tagged `internal`. Under `--build` the message names the missing `builds[]` entry instead, since that is what `--build` reads. `DOCS_SERVE_NO_PUBLIC_BUILD` is the same stop the other way round.
- `DOCS_SERVE_NO_SERVER_TOOL` — the tool the selected server's command runs cannot be found: `pnpm` not installed, say, or a `node_modules/.bin/…` path with no `node_modules` behind it — or it is a `pnpm`, `npm` or `yarn` whose dependencies are not installed: its lockfile has no `node_modules/` beside it, nor, for Yarn, the `.pnp.cjs` a Plug'n'Play install keeps instead. Nothing starts, so the run does not wait out the readiness timeout for a server that could never start; install the tool, or record a command whose tool is present.
- `DOCS_SERVE_NOT_CONCURRENT` — the profile sets `dev_servers.concurrent: false` and another of its servers is already running or still starting, recorded and alive, recorded and still starting, or identified on a port this run checked — every other server's configured port among them. Nothing starts; the message names that server and how to stop it — `--stop --port <its port>` where it is recorded, its process by hand where it is not.
- `DOCS_SERVE_FIXED_PORT` — `--port <n>` on a server whose command carries no `{port}` token. Such a command binds its own port, so nothing starts; drop `--port`, or add the token where the command's tool takes a port argument.
- `DOCS_SERVE_PORT_HELD` — the configured port of a server whose command carries no `{port}` token is held by something else: another checkout, another of the repository's servers — one still starting on that port included — a process that is not this site, or a listener the probe cannot reach. Nothing is left running for it, and the report names what holds the port, with its pid where the socket table names one, so you can stop it and re-run. A start that exits before its port answers reports the same way wherever something is listening on that port; where nothing is listening and only its log names an address-in-use failure, the report quotes the line of the log that matched in place of a holder, since that line names none. Whether a socket standing on a port refuses a bind is in no table, so it is not predicted.
- A port collision on a command that carries `{port}`, or a `dev_servers.readiness_timeout_seconds` timeout, is reported rather than treated as a stop — the collision moves the server to the next free port and says so, and after a timeout the server may still come up or the operator may need to look at what else is bound to the expected port, which a hard stop would foreclose. A command that exits before its port answers is reported as soon as its process group is gone, with the last lines of its log, and nothing is recorded — save an exit at a port something is listening on, or whose log names an address-in-use failure, which is the collision above.

## Example

```
/docs-workflows:docs-serve ~/repos/example-docs
```

Resolves the repo, reads its `dev_servers` block, starts (or finds already running) the public server, and prints the host-visible URL — `public_base_url` when the profile records one, otherwise the in-container address with a caveat.

```
/docs-workflows:docs-serve --stop
```

Resolves the repo the same way, then stops the server this command has a record of running for it — or, where it has records for several ports, lists them and asks which.
