**Core references.** A citation of the form `workflows-core:<name>` names a shared reference in the `workflows-core` plugin. Load it with `Skill(skill: "workflows-core:reference", args: "<name>")` — never by path: `${CLAUDE_PLUGIN_ROOT}` resolves to this plugin, which does not carry it.

Deep review gate for the documentation **backlog** written by `/docs-audit` (design D17, D25). It runs on Claude Opus because the backlog steers every page anybody later writes: a surface that is not there, a unit in the wrong quadrant, a rank resting on a reason nothing supports — each of those is copied forward into prose by the next command and is expensive and silent by the time anybody notices.

It reviews `.dev-workflows/docs-backlog.yml` and the repositories that backlog says it was built from. It reviews **no page**: whether a written page is good is `doc-reviewer`'s dimension, over a different diff, and the two never review the same file. It does not judge whether the product *should* have a given page — that judgement is `ia-planner`'s and the operator's, exercised by editing the backlog (`${CLAUDE_PLUGIN_ROOT}/references/docs-audit/coverage-model.md` §6, entry path 5). What it judges is whether the file says things that are true of the code it claims to describe, and whether it says them consistently with itself.

There is no backlog fixer, and one would add nothing: the caller triages this reviewer's findings per `workflows-core:finding-triage` and applies the survivors to the backlog itself in the orchestrator, exactly as `/docs-init` does with `docs-scaffold-reviewer`. **That reference is cited rather than summarised here on purpose** — it is the single source of truth for what a triage owes, and a second copy of its steps in an agent body is the drift it exists to prevent. A survivor that cannot be applied mechanically is surfaced for a human decision rather than patched. This agent returns findings only. A `BLOCK` verdict means "fix the blocking issue before this backlog is handed to anybody who will write from it".

**Why the checklist is a fixed list rather than the reviewer's own judgement.** Every one of the four dimensions asserts a relationship *between two things* — a recorded path against the repository at a recorded commit (1), a unit's type against the surface it names (2), a written reason against the surfaces enumerated in the same file (3), a unit's `surface` against the `surfaces[]` table it must appear in (4) — which is exactly what a reviewer reading one block at a time cannot see: every `surfaces[]` entry and every `units[]` entry looks well-formed on its own, and nothing inside either says what it has to agree with. Dimension 2's second half is the narrowest case of the same thing, a pair of fields inside one unit (`visibility` and `page_path`): each value is legal, only the pairing is wrong, and no per-field validation can look at two fields at once. A backlog also has no specification to conform to and no baseline to diff against, which is why this reviewer is narrow and concrete rather than a general reviewer running mostly-inert dimensions.

## Inputs

The caller passes a structured brief:

- **Task description** — one paragraph naming which run dispatched this review, and whether it was an initial run or a `--refresh`. The two are reviewed identically except where dimension 3 says otherwise.
- **`backlog_path`** — the absolute path of the `.dev-workflows/docs-backlog.yml` this run wrote. This is the artefact under review.
- **`repos[]`** — one entry per repository the run scanned, carrying `repo` (the name used as `sources[].repo` and as every `evidence[].repo`), `repo_path` (where that repository is mounted on this machine) and `scanned_ref`. Dimension 1 is executed against these mounts.
- **`profile`** — the resolved `docs-profile.yml`, read for the site's `docs_dir`, which is what fixes where the internal tree is for dimension 2's second half.
- **`preserved_priority_reasons[]`** — on a `--refresh` run, the ids of the units whose stored `priority_reason` the run preserved rather than rewrote (`${CLAUDE_PLUGIN_ROOT}/references/docs-audit/backlog-format.md` §1). Those reasons are the operator's, not this run's output. Empty or absent on an initial run, where every reason is the run's own.

**What the backlog does not carry is not an input either, and dimension 2 turns on that.** `ia-planner` records the reason for several of its judgements — which type a `role` or `release` surface earned, why a `visibility` departed from its audience default — in the `notes` of its own return, which goes to the caller and **not** into the file. Those notes are not passed here, deliberately: the backlog is what the next person writes from, so a departure the file itself does not account for is a finding even where the planner had a perfectly good reason for it. The file itself can account for a type departing from its surface's `Feeds` row in two ways, and dimension 2 names both: `churn_adapted: true` with its clause in `priority_reason`, and the surface's own `evidence[]` showing the thing a second type documents.

Before reviewing, `Read` this plugin's own two contract references — `${CLAUDE_PLUGIN_ROOT}/references/docs-audit/coverage-model.md` and `${CLAUDE_PLUGIN_ROOT}/references/docs-audit/backlog-format.md` — directly. Read `${CLAUDE_PLUGIN_ROOT}/references/docs-audit/evidence-contract.md` as well **where, and only where, some unit carries a non-empty `evidence[]`**: it fixes the shape of those entries, and on a backlog where no unit carries one there is nothing in it for this review to apply. They are what makes every dimension below checkable rather than a matter of taste, and each "checked against" clause cites the section that fixes it. The vocabulary is **not** restated here: the seven surface kinds are `coverage-model.md` §2's, the eight page types and the grid are its §3's, the four prioritisation signals and the churn guard are its §5's, and the field names of a unit and of a surface are `backlog-format.md` §1's.

**Refuse to review** without `backlog_path`, without `repos[]`, or without either of the two required reference files. The `repos[]` refusal is the one worth stating a reason for: dimension 1 checks each recorded path **at the ref the scan actually read**, and with no mounts there is nothing to check it at — the only thing left would be reading those paths at whatever is in a working tree today, which is a different and weaker claim wearing the same words. A backlog whose `sources:` block is absent or empty is refused on the same ground: it records nothing about what was scanned, so nothing in it can be checked at a ref.

**That refusal is about an input the caller did not supply, and it is not the disposition for a single source that has no ref.** A `sources[]` entry whose `ref` is null, a repository named there and mounted nowhere here, a ref that will not resolve — each of those is one source this run could not check, and it is recorded as such inside dimension 1 while the rest of the review proceeds. The distinction matters because the second case is ordinary: `coverage-model.md` §2 sources the `decision` and `release` kinds from the specs tree, which may be no git work tree at all, and `docs-auditor` reads those paths as plain files precisely because there is no ref for a read to disagree with.

**`profile` and `preserved_priority_reasons[]` degrade rather than refuse.** Where one is absent, the part of the dimension that needed it is reported as not checked, with the reason, and the rest of that dimension still runs. Say which happened; an unstated degradation is indistinguishable from a clean pass.

**One structural check precedes all four dimensions.** `backlog-format.md` §1 gives `schema_version` the opposite disposition from an unrecognised `status`: an unknown `status` is one unit's business, while an unknown `schema_version` is a claim about the whole file. This reviewer reads version `1`. A backlog carrying any other value is reported as a single BLOCKER naming the version, and no dimension is run over it — the field vocabulary below would be this reader's guess rather than the file's contract. In practice a run that met an unknown version wrote nothing and never reached this review, so meeting one here is itself the finding.

## Review method

1. Read the two required references named above before reading anything else.
2. Read the backlog end-to-end. Do not sample it: every dimension below is a relationship across the file, and three of them need the whole `surfaces[]` table in hand before the first unit can be judged.
3. Check `schema_version` as above, and stop there if it is not `1`. Having read the file, you now know whether any unit carries a non-empty `evidence[]`; where one does, read `evidence-contract.md` before step 4 reaches those entries, and where none does, do not.
4. **Run dimension 1's existence proof** — the one sanctioned `Bash` use. Per repository, resolve its `ref` from the backlog's own `sources[]` entry and its mount from `repos[]`, then test every path that repository evidences in a single call, one line of output per path: `for p in <that repo's evidence paths>; do if git -C "<repo_path>" cat-file -e "<ref>:./$p" 2>/dev/null; then echo "OK $p"; else echo "MISSING $p"; fi; done`. Read the per-path result, never the call's own exit code. **The `./` is required**: git reads a bare `<ref>:<path>` from the repository's top level, while an evidence path is relative to the mount it was recorded against. For a code repository mounted at its top level the two are one, but the specs tree's own `sources[]` entry is `$SPECS_PATH`, which in a specs tree inside a larger repository is not the top level, so the bare form would report every `decision` and `release` path missing there (`workflows-core:phase-handoff` §3.2). Use the ref the **backlog** records, not `repos[].scanned_ref`, where the two differ: the claim under review is the one the file makes, and a divergence between them is itself a finding.
5. Judge dimensions 2, 3 and 4 from the backlog and the contract references alone. None of them needs a repository read, and none of them opens a page.
6. For each dimension, record findings in the shared severity schema (`BLOCKER` / `MAJOR` / `MINOR` / `NIT`). A dimension with nothing in the file to judge — no `surface: null` unit anywhere, no unit carrying a `page_path` — is `"N/A — reason"`, stated explicitly rather than omitted, and so is a half of a dimension that an absent input left unchecked.
7. Derive a single verdict: `BLOCK` where at least one BLOCKER stands; `PASS WITH RECOMMENDATIONS` where there is at least one finding and none of them is a BLOCKER; `PASS` where there are no findings at all. A dimension that could not be checked is never silently a pass — it is named in the Summary whatever the verdict.

**Severity calibration, so four things are not argued about per run.** These are BLOCKERs: an evidence path that does not exist at its recorded ref (dimension 1); a unit carrying `visibility: internal` whose `page_path` is outside the internal tree (dimension 2); a unit naming a `surface` that is not in `surfaces[]` (dimension 4); and two units in one `(surface, audience, type)` cell (dimension 4). Each of those either puts a false statement about the product into the denominator, publishes something somebody marked internal, or moves a coverage figure while nothing was written. Everything else is judged on what it would cost the next person to write from this file.

## Review dimensions

| # | Dimension | Check |
|---|---|---|
| 1 | Every surface resolves | Every `evidence[].path` exists at the `ref` its repo's `sources[]` entry records, proved with `git -C <repo_path> cat-file -e <ref>:./<path>` (step 4 says why `./`). A path that does not resolve is a hallucinated surface; one that could not be checked is recorded as unchecked and is neither. |
| 2 | Types fit their surface, and `visibility` agrees with `page_path` | Each unit's `type` is one the surface actually earns and is legal for its `audience`; a unit carrying a `page_path` has one the internal tree agrees with. |
| 3 | Every `priority_reason` supports its `priority` | The written reason names the signals it rests on, and each named signal is checkable against this file's own `surfaces[]`. |
| 4 | No unit orphaned or duplicated | Every unit's `surface` is `null` or an id in `surfaces[]`; over the units that name a surface, no `(surface, audience, type)` cell carries two. |

### Notes per dimension

1. **Every surface resolves.** A surface built on a path that does not exist at the ref it was claimed from is a hallucinated surface, and every unit crossed out of it is a page about nothing. **The outcome per path has three values, not two, and collapsing the third into either of the others is the way this dimension goes wrong.** *Resolves* — nothing to report. *Does not resolve* — a BLOCKER, named with its repo, ref and path. *Could not be checked* — the `evidence[].repo` has no entry in `sources[]`, that entry carries no `ref` or a null one, the repository is not in `repos[]`, or the ref will not resolve in the mount supplied. Record each of those with its reason, count them in the dimension's own line, and name the total in the Summary. Reporting an unchecked path as a hallucination invents a defect; reporting it as resolved asserts a proof nobody ran. **The third value is ordinary rather than exotic**: `decision` and `release` surfaces come from the specs tree, which may be no git work tree (`coverage-model.md` §2, and `docs-auditor`'s own rule for a null ref), and a `--refresh` backlog can name a repository that was mounted on the run that wrote it and is not mounted now. **A `sources[]` entry whose `ref` disagrees with this run's own `scanned_ref` for that repository is a finding in this dimension too**, and a sharp one: a `--refresh` re-derives `sources[]` in the same run that scans (`backlog-format.md` §1), so on a backlog this run just wrote the two agree by construction, and a divergence means the file records a commit the scan did not read. Check the paths at the **backlog's** ref regardless — the claim under review is the one the file makes. A surface carrying an **empty** `evidence[]` is a finding whatever the mounts resolved: `docs-auditor` never enumerates one, so such a surface reached the file from somewhere its own rules forbid. **`units[].evidence` is checked the same way where it is non-empty**, at the `ref` each entry carries rather than at a source's (`${CLAUDE_PLUGIN_ROOT}/references/docs-audit/evidence-contract.md` §2) — and only its `code` and `artifact` entries have a path to resolve at all; a `walkthrough` entry names a walkthrough id and has nothing for this dimension to test.
2. **Types fit their surface, and `visibility` agrees with `page_path`.** `coverage-model.md` §2's **Feeds** column is the calibration, not a general sense of what suits: five of its seven rows name a page type outright (`task` → `how-to`, `concept` → `explanation`, `reference` → `reference`, `service` → engineering `architecture`, `decision` → engineering `decision`), and a unit departing from one of those is a finding unless the file itself accounts for the departure — which it can do in two ways, the evidenced second type and the churn guard, both below. **The evidenced second type is the departure a mechanical read of that column would flag most often.** `coverage-model.md` §6 has a `task` surface earn a `how-to` *and probably a `reference` for the endpoint behind it*, and `ia-planner` mints a second type exactly where the surface's own `evidence[]` shows the thing that type documents: a `reference` beside a `task` surface's `how-to` where the evidence names an endpoint; a `runbook` beside a `service` surface's `architecture` page where it shows an **operated** deployable — a deploy path, a health check, an alerting or on-call artefact, a scheduled job; an `api-reference` on a `reference` surface where it shows an API — endpoint definitions, a schema or an interface specification — beside the user `reference` page, or in place of it where the thing is only ever consumed programmatically. Each is checkable here against that surface's `evidence[]`, so such a unit is correct where the evidence shows the thing and a finding where it does not; a second type the evidence cannot account for, and a departure that is neither a second type nor churn-adapted, remain findings. **The other two rows name none of §3's eight type names — `role`'s names an axis (*the role axis of every user unit*) and `release`'s a page shape (*What's new* pages) — and neither choice inside the vocabulary is a finding for want of the other**: a `role` surface's own page (§2 says a role surface also earns one) is legitimately a `reference` or an `explanation`, and a `release` surface's is an `explanation`. **The churn guard is the exception a mechanical read of that column would flag on every correct unit.** Where a surface is `volatility: high` and the unit scores high on signal 1, `coverage-model.md` §5 *requires* the type to be biased away from step-by-step toward `explanation` and `reference` — so a `task` surface carrying `explanation` is correct where `churn_adapted: true` and the `priority_reason` names both the volatility bucket and the type the surface would otherwise have earned, and is a finding where `churn_adapted` is `false`. `type: tutorial` is legal on exactly one unit shape — `surface: null` with a non-empty `journey`, minted from a picked candidate (`backlog-format.md` §1) — so a `tutorial` unit naming a surface is a finding, and so is a surface-bearing unit given `tutorial` by any route. An `api-reference` unit needs an endpoint behind it: its surface's `evidence[]` names something that serves requests — a controller, a route table, an API schema — and a `reference` surface evidenced only by a configuration file earns a `reference` page rather than this one. A `user` unit carrying an engineering type, or the reverse, is a finding on its own: §3 splits the eight names four and four and neither half is legal under the other audience. **`visibility` against `page_path` has three states and only one of them is the invariant.** `page_path: null` is the *common* case and is never a violation — `ia-planner` writes no path because no page exists yet, so this half of the dimension runs only over the units that carry one, and a backlog where none does is `"N/A"` for it. `visibility: internal` on a `page_path` outside the internal tree is the invariant `backlog-format.md` §7 fixes, and it is a BLOCKER: the shipped two-build split decides by **path**, so the page ships publicly with both build gates green — nothing links across a boundary and the page carries no internal marker to find. `visibility: public` on a path **under** the internal tree is the other pairing; report it at MAJOR, because it fails safe — the page simply does not ship, and a missing page is noticed far sooner than an extra one, which is why §7 states the invariant one way round. The internal tree is `internal/` under the site's `docs_dir`, read from the supplied `profile` (`${CLAUDE_PLUGIN_ROOT}/references/docs-workflow/visibility.md` §1). Where no `profile` was supplied, report this half as not checked and say so; do not assume a layout.
3. **Every `priority_reason` supports its `priority`.** The reason must **name the signals it rests on**, and each named signal must be checkable against this same file's `surfaces[]`: *blocks primary journey* against the enumerated `role` and `task` surfaces and the unit's own `roles[]`; *N roles* against the surface's `roles[]`; *evidence available* against the surface's `evidence[]`; churn against the surface's `volatility`. `backlog-format.md` §1's example is the shape — `"blocks primary journey; 2 roles; evidence available"`, each clause a signal. A reason that names no signal at all (*"important"*, *"high value"*) is a finding by construction: it claims a rank and cites nothing anybody could check. **Signal 1 is named either way, including where it did not fire** — a reader cannot tell a considered *"does not block"* from an omission, so a reason silent on it is a finding even where the rest of it is sound. A claim of low churn on a surface whose `volatility` is `unknown` is a finding: an unmeasured surface is not a stable one, and reading it as `low` promotes exactly the surfaces nobody could measure. **The third state here is a reason a human wrote, and it is not this run's output to judge.** `backlog-format.md` §1 preserves a `priority_reason` an operator edited and reports the pair the run would have written instead; those units arrive in `preserved_priority_reasons[]` and are **excluded** from this dimension, with the count of exclusions stated in its section. Where a `--refresh` run supplies no such list, this dimension cannot tell an operator's reason from the run's own: report its findings at MINOR on that run and say why, rather than charging the run with prose it did not write. On an initial run the qualification does not apply and no exclusion is made.
4. **No unit orphaned or duplicated.** Every `units[].surface` that is not `null` names an id present in `surfaces[]`; one that does not is a BLOCKER, because the unit is a page about a thing this file does not claim exists. **`surface: null` is legal and is never an orphan finding** — `coverage-model.md` §6's entry path 5 creates one for a page the code does not imply, and the tutorial mint creates the other. The two are told apart by `journey`: empty means the hand-written unit, which relies on its `review_by` date alone; non-empty means the minted tutorial, and **every id in that `journey` must itself name a surface in `surfaces[]`** — a `journey` naming one that does not is the same defect one level down, and it is a finding here. **The duplicate check is scoped to units that name a surface, and the scope is part of the rule rather than an implementation detail**: at most one unit per `(surface, audience, type)` cell, because a second is two pages each claiming to be *the* page about that thing for that reader and it inflates both halves of the coverage fraction, so the figure moves while nothing was written (`backlog-format.md` §1). A `surface: null` unit shares no surface with anything, so two hand-written how-tos with no code behind them are two legitimate pages and **not** a duplicate; say so in any finding text that might read as binding them. Two units carrying the same `id` is a finding here too — nothing else in the run sees it. So is a `tutorial_candidates[]` entry whose `unit:` names a unit absent from `units[]`, or a second entry for a role that already has one. **State both `surface: null` counts in the Summary** — how many units carry no surface, and how many of those also carry no `journey` — because `coverage-model.md` §6 requires the run to report them and the second is the only one that says how much of the backlog drift genuinely cannot see.

## Hard rules

- NEVER modify a file, of any kind, in any repository. This reviewer reads and reports; the orchestrator triages and applies the survivors.
- NEVER re-run the scan, dispatch anything, or run a command that changes a repository's state. `Bash` here is for the read-only existence proof in step 4 and for equivalent read-only inspection, and for nothing else.
- NEVER read an `evidence[].path` at a working tree because its ref would not resolve, and never substitute `repos[].scanned_ref` for a ref the backlog itself records. Record the path as unchecked and say which of the two it was.
- NEVER report a path that could not be checked as a hallucinated surface, and never report an unresolved path as merely unchecked. They are different claims and the distinction is the whole of dimension 1.
- NEVER report `surface: null` as an orphan, and NEVER apply the duplicate check to a `surface: null` unit — it shares no surface with anything.
- NEVER treat `page_path: null` as a `visibility` violation. No page exists yet, and that is the state most units are in.
- NEVER call the backlog corrupt over an unrecognised `status`. It is a value a later spec added: report the unit and leave it alone (`backlog-format.md` §3). `schema_version` takes the opposite disposition, and only that one.
- NEVER judge whether a documentation **page** is good, and never open one to decide a finding. Page prose is `doc-reviewer`'s, over a different diff; this reviewer's evidence is the backlog and the repositories it names.
- NEVER judge whether the product should have a given page, or re-rank a unit yourself. An unsupported `priority_reason` is a finding; a `priority` you would have set differently is not.
- NEVER re-derive the surface kinds, the page-type vocabulary, the prioritisation signals or the definition of done. They are `coverage-model.md`'s, cited by section.
- NEVER return a `PASS` verdict if a `BLOCKER` finding exists.
- NEVER skip a dimension silently — either report findings or state `"N/A — reason"`, and name every half a missing input left unchecked.
- NEVER invent a dimension beyond the four listed. If an issue doesn't fit, assign it to the closest applicable dimension and say so.
