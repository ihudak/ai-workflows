# Key discovery

**Core references.** A citation of the form `workflows-core:<name>` names a shared reference in the `workflows-core` plugin. Load it with `Skill(skill: "workflows-core:reference", args: "<name>")` — never by path: `${CLAUDE_PLUGIN_ROOT}` resolves to this plugin, which does not carry it.

How `/document` (keyed mode) and `/release-notes` (with diff grounding on) run the commit scan `workflows-core:implementation-format` §4 defines, and the optional pull-request layer beside it, through one script: `${CLAUDE_PLUGIN_ROOT}/scripts/key-discovery.py`. That §4 stays the authority on what the scan means; this file says how it runs and what the two commands do with what it returns, and, in §6, how `/document` checks its own commit against the same documentation set.

## 1. Run it

In Phase 3's diff-source step, or, on a `/document` run whose implementation record holds no block in its scope, in that command's Phase 0 step 3a, before it asks whether to document at all, its Phase 3 then taking that result — save where a base named at its Phase 2 *Revise plan* replaces the `$REPOS_PATH` step 3a resolved, or undoes *Proceed without the repos* there (*A clone mounted mid-run*, below): once the slug→clone map is built and the tokens are known — §4's tokens for this run's scope, each read off a folder the run resolved or listed — in one shell block, with the Bash tool's timeout set to 600000 ms, since it reads every clone and asks GitHub once per pull request it keeps:

```bash
kd=$(command mktemp) && python3 "${CLAUDE_PLUGIN_ROOT}/scripts/key-discovery.py" scan --scope head --probe \
  --key <token> --key <token> … --repo <clone> --repo <clone> … \
  --exclude <specs repository> --docs-root <the documentation root> --docs-content <content path> … \
  --owner-of <clone not picked> … > "$kd"; echo "exit=$? out=$kd"
```

Each token is its own `--key`. Each repository the scan covers — those `implementation.md` names, resolved through the map, or, when it names none, every clone in the map, one per slug — the clone the user chose for the slug, where `/document` Phase 4 step 5 recorded one, else by Phase 4's preference (a basename ending `-repo`, then `_repo` or `_fast`, then the alphabetically last) — is its own `--repo`; every other clone the map holds goes as `--owner-of`, so every GitHub owner a clone under `$REPOS_PATH` belongs to is searched, although only the scanned clones are read.

**No clone to scan: do not run it.** Where the scan covers no repository — the map holds no clone, as on a `/document` run whose implementation record holds a block and whose repositories question, put in its Phase 1, took *Proceed without the repos*, or every repository `implementation.md` names resolved to none — the script cannot run (it requires a `--repo`) and there is nothing to scan. Do not call it, and report the scan as not run, *no clone resolved*, with no `--no-github` retry and no script failure. On a `/document` run whose implementation record holds no block, the repositories question is put in its Phase 0 step 3a, and where it takes *Proceed without the repos* there no map is built and the script is not called either: that step reports the scan as not run because of that answer.

The JSON goes to a file of the run's own, never to the tool's output, which a large result would overflow: read the file the printed line names — the script indents it, so it reads line by line however large — and remove it with `rm -f` once the phase that ran it has taken what it needs — save the file of `/document`'s Phase 0 scan, which is kept until that run's Phase 3 takes its result, or removes it unread to run the scan again over a base named at that run's Phase 2 *Revise plan*, and which a run ending before then removes as it ends (that command's *Ending early*).

**Never code: the specs repository.** Pass `--exclude <the specs repository>` — the top level of the PRD folder's repository, `git -C <PRD folder> rev-parse --show-toplevel`, where that prints one — unless it is a repository `implementation.md` names. The script leaves out every clone whose `origin` slug is its, a second clone included, and drops every pull request in a repository of that name: the specs repository's artifact commits and handoff pull-request titles carry the run's tokens by the family's own conventions, and read as code they would verify a requirement by its own text. `--exclude` leaves out nothing for a path inside a repository, or outside any. **Its limit:** where `implementation.md` does not name it, code committed inside the specs tree's repository is never scanned — a specs tree inside a larger repository is a layout the family does not support (`workflows-core:specs-repo-git` §3.1, *A `$SPECS_PATH` below its repository's top level*).

**The documentation-holding repository: read by path.** The repository that holds the documentation — the documentation root's git top level — is scanned like any other, save that a commit there counts only where its message names a token **and** it touches at least one path outside the documentation set: the content paths below and the family's own paths together. A commit touching only paths in the set is a documentation-only commit and is never a commit found, so `/document`'s own commits there, which carry the run's tokens by the family's own conventions, are not taken for the work they describe wherever the set covers what it wrote (§6 checks that it does). A commit touching a documentation path and a path outside the set is kept: a person changed code and named the key. Pass `--docs-root <the documentation root>` and one `--docs-content <content path>` for each content path, **whether or not `implementation.md` names that repository**; the script works out the rest:

- **The documentation root.** `/document`: `docs_repo_resolved`, the directory its Phase 0 step 2 rung answered with. `/release-notes`: `--docs <path>`, else `${DOCS_PATH:-/workspace/docs}` — **whether documentation grounding is on or off**, `--no-docs` included. Where that directory does not exist, pass neither `--docs-root` nor `--docs-content`: the script refuses a `--docs-root` that is not a directory, and a `--docs-content` without one. Where it lies in no git work tree, the script changes nothing (`docs` is null, §2).
- **The content paths.** Each path the docs profile readable when the scan runs records, relative to the documentation-holding repository's top level — each `spaces[].content_root` and `snippet_root`, `images.root` where `images.policy` is `in-repo`, each `builds[].config`, and each `announcement_pages[].path` — as the profile records it, each its own `--docs-content`, quoted for the shell, and passed as `--docs-content=<content path>` where it begins with `-`. The profile: for `/document`'s Phase 0 step 3a, `<docs_repo_path>/.dev-workflows/docs-profile.yml` where it exists, else the built-in profile, `${CLAUDE_PLUGIN_ROOT}/references/docs-profiles/docs-profile.default.yml`, where `is_known_docs_repo` (its step 3), else none, its step 4 not having resolved one yet; for a scan its Phase 3 or Phase 4 runs, the profile its Phase 0 step 4 loaded or generated; for `/release-notes`, `<top>/.dev-workflows/docs-profile.yml` where it exists, `<top>` being `git -C <the documentation root> rev-parse --show-toplevel`, else none. A profile that exists and cannot be read is none. The content paths are worked out at each scan the run makes, never carried from an earlier one. Pass only the profile's: where the documentation root lies below the top level, the script adds the site's own directory itself, first among `docs.content_paths` (§2), and it lists in `docs.rejected`, and does not use, a content path that is absolute or holds a `..` segment.
- **The family's own paths**, stated here once and cited everywhere else: what the family itself writes into a documentation repository, and the configuration and navigation files of the generators its docs signals name. A path outside them and outside the content paths is code — a markdown file below the top level among them, since a product's code can be markdown. Each line is `literal <path>` — that path from the top level, a directory with everything below it — or `glob <pattern>` — a pattern from the top level whose `*` stops at `/`, so `*.md` is the top level's markdown and nothing deeper, whose `[jt]` or `[cm]` is one of the two characters it lists, whose leading `**/` is any depth, the top level included, and whose trailing `/**` is everything below:

<!-- family-doc-paths -->
```text
literal .dev-workflows
literal .claude
literal docs
literal .docstack
glob    *.md
glob    **/_snippets/**
glob    **/mkdocs.yml
glob    **/mkdocs.*.yml
glob    **/docusaurus.config.[jt]s
glob    **/docusaurus.config.[cm]js
glob    **/sidebars.[jt]s
glob    **/sidebars.[cm]js
glob    **/_category_.json
glob    **/_category_.yml
glob    **/antora.yml
glob    **/nav.adoc
glob    **/.pages
glob    **/SUMMARY.md
literal .vale
literal _vale
literal vale.ini
literal .vale.ini
literal _vale.ini
```

**Which clones the rule reads, and what it leaves alone.** Every `--repo` that is the documentation-holding repository — by its path, or by its `origin` slug, so a second clone of it is read by the same rule — is read under it and listed in `docs.clones`, and §3 and §4 say how. The rule changes how that repository is read, never whether it is covered: where no `--repo` is that repository — a record naming other repositories, say — nothing is added to the scan, and its pull requests are dropped by name, as an `--exclude`'s are, since the commits each one landed can be tested by path only in a clone the scan holds.

**Where no content path is known, the repository is left out whole.** Where neither the site's own directory nor the profile names a content path — a site at the repository's top level with no profile, as on a first `/document` run there, whose Phase 0 step 4(c) generates the profile after the scan — the script leaves the documentation-holding repository out whole, as an `--exclude` of its top level would, with `docs.reason` `no content path`, and the run says why in its `Left out as never code:` line (§5). No generator's default content folder is guessed: `/docs-workflows:docs-profile` writes the profile that makes the scan possible. The script leaves it out whole too where a content path is the whole repository (`the content path is the whole repository`), and where `--exclude` names it as well (`--exclude names it too`) — the specs repository's exclusion being the one `--exclude` the two commands pass.

`exit=0` with one JSON document in the file (§2) is the only success. Any other exit, a file that is not JSON, or a call the tool's timeout ended, means it could not run: run it once more with `--no-github` — the scan alone — and report the pull-request search as not run, with the first call's reason (its stderr line, or that it timed out). Only where that fails too, report it as the scan's result for every repository, and continue on the record alone.

**A clone mounted mid-run.** Where Phase 4 waits for a missing repository — "Mount the missing repo(s) now", "I'll clone it — wait" — takes a path the user specifies for one, or takes another of a slug's clones (`/document` Phase 4 step 5), rebuild the map and run the script again over the new set, the new or chosen clone among the scanned ones; its result replaces the earlier one. It is cheap, and it is the only way the new clone's commits are scanned, and its pull requests given a `clone`. **So too for a base named at `/document`'s Phase 2 *Revise plan*** on a run whose implementation record holds no block, where that base replaces the `$REPOS_PATH` its Phase 0 step 3a resolved or undoes *Proceed without the repos* there: its Phase 3 builds the map over the named base and runs the script once over it, in place of taking step 3a's outcome. A commit that run finds is read as any other; where it finds none, or does not look, nothing is asked — the nothing-built question is put in Phase 0 step 3a or not at all — and where the result it replaced had found a commit, that command prints one line and records that its pages were written from the PRD alone, as it does where one of its Phase 4 re-runs above finds none, or does not look, on such a run (its Phase 3, *A later scan that finds none*).

The script fetches nothing and writes nothing: it reads each clone as it stands.

## 2. What it returns

- `excluded` — the slugs of the repositories left out whole: each `--exclude` that is a repository's own top level, and the documentation-holding repository where the rule leaves it out whole (`docs.rule` `left-out`).
- `repos[]` — per clone: `path`, the `ref` scanned (`HEAD`), `scanned` (its non-merge commits — on a clone read under the documentation rule, only those touching a path outside the documentation set), `matched`, `github` (`<owner>/<repo>`, or null where the clone is not on github.com), `error` (where it could not be read; `scanned` is then null), `probe` — §4's unanchored probe, by SHA, date and subject, on a clone where `matched` is 0 — `probe_error`, where that probe failed on a clone the scan read: the scan's own reach stands, and only the report-only probe is missing — and `docs_rule`, true on a clone read under the documentation rule.
- `commits[]` — each non-merge commit on `HEAD` whose message names a token whole (`via: message`), and each commit a found pull request landed whose own message names none (`via: pull-request`) — on a clone read under the documentation rule, only one touching a path outside the documentation set: `repo` (the clone), `sha`, `date` (local time), `subject`, `keys` — the tokens its message names and those of every found pull request that landed it — and `prs`, the URLs of the found pull requests that landed it.
- `docs` — null where no `--docs-root` was passed, or where the documentation root lies in no git work tree; otherwise the documentation rule as the script applied it: `root` (the documentation root as given), `top` (the documentation-holding repository's top level), `repo` (its `origin` slug, else the top level's directory name), `rule` (`paths`, read by path, or `left-out`, left out whole), `reason` (null under `paths`; under `left-out`, one of `no content path`, `the content path is the whole repository` and `--exclude names it too`), `content_paths` (the site's own directory first, where the root lies below the top level, then each `--docs-content` taken, a leading `./` and a trailing `/` dropped and a repeat taken once, `.` standing for the whole repository), `rejected` (each `--docs-content` not used, by `path` and `why`: absolute, or holding a `..` segment), `clones` (the `--repo` clones read under the rule; empty under `left-out`, and where no `--repo` is that repository) and `docs_only` (each commit in those clones whose message names a token whole and that touches no path outside the documentation set, by `repo`, `sha`, `date`, `subject` and `keys`; none is in `commits[]`).
- `github` — `status` (`ok`; `partial` where a search failed, reached its 1000-hit limit, returned what the script cannot use, or ran out of its time budget — one budget over every GitHub call, the auth check, the searches and the views alike, each search batch it left unrun counted in `detail`, with its tokens; `rate-limited`; `not-installed`; `not-authenticated`; or `no-github-clones`), `detail` (each failure, or why `gh` cannot search), the `owners` searched, `queries`, `dropped_loose`, and `prs[]`: `url`, `owner`, `repo`, `number`, `title`, `state` (`MERGED`, `OPEN` or `CLOSED`), `keys`, `clone` (null where no scanned clone holds the repository), `head_ref`, `base_ref`, `head_oid`, `merge_commit`, `cross_repository`, `landed_as` (`merge`, `squash`, `rebase` or null), `landed`, `reason`, and `landed_docs_only` — in a clone read under the documentation rule, the commits it landed that touch no path outside the documentation set, which are never read; `[]` everywhere else.

## 3. The scan's result

- `commits[]` with `via: message` are exactly the scan §4 describes.
- **A documentation-only commit is never a commit found.** A commit in `docs.docs_only` names a token and touches no path outside the documentation set: it is not in `commits[]` and not counted in `matched`, it is never reported as unrecorded work or handed to `diff-summarizer`, and it never stands as work found where a command asks whether anything is built. §5 lists it.
- `repos[].scanned` and `matched` are the scan's reach; a repository with an `error` was not read, and is reported as such, never as zero matches. **On a clone read under the documentation rule (`docs_rule`), `scanned` counts only the non-merge commits on `HEAD` that touch a path outside the documentation set**, never the clone's whole history: it is the one walk taken with the set as exclude pathspecs, with `--full-history`, so a side branch whose changes cancel out is still counted. The scan and the probe read the clone's log as they read any other, then test each commit they matched there on its own against the set — a merge against its first parent — which walks no history.
- A repository whose `probe_error` is set was read: report its reach as above, and name the probe as failed with that reason, never the repository as unread.
- `repos[].probe` is §4's report-only probe, less any commit a found pull request accounts for — its merge commit, or a commit it landed — which the run reads or lists under §4 below instead; on a clone read under the documentation rule, less too each commit that touches, and each merge that brought in over its first parent, no path outside the documentation set.

## 4. Pull requests — optional

Where a scanned clone's `origin` is on github.com — an SSH host alias resolved as `workflows-core:phase-handoff` §2.6.1's `owner-repo` resolves it — and `gh` is installed and logged in, the script also searches the GitHub pull requests of every owner a clone under `$REPOS_PATH` belongs to for the tokens, and keeps one only where its title or body names a token whole: GitHub's own search matches loosely, even with each token quoted as a phrase, and `dropped_loose` counts the pull requests it dropped. Where `gh` is absent or logged out, `github.status` says so and nothing else changes.

- **A merged pull request that shipped and is its own** — its merge commit in the clone and on `HEAD`, its range bringing in no other branch's merges — contributes its `landed` commits: the branch's own commits for a merge commit, the one commit for a squash, the rebased run for a rebase. One the scan already found is that same commit, tagged with the pull request in `prs`. One whose own message names no token comes back `via: pull-request` and joins the scan's commits as a commit only the scan found — reported as unrecorded work like any other, and handed to `diff-summarizer` as `{branch_from: <sha>, branch_to: <sha>^}`. **In a clone read under the documentation rule**, each commit it landed is tested on its own against the documentation set — a merge against its first parent — and only those touching a path outside the set stay in `landed`; the rest move to `landed_docs_only` and are never read.
- **A commit's tokens are its `keys`** wherever a rule reads them — `/release-notes`' note boundary among them: those its message names and those of every found pull request that landed it. A commit two pull requests landed carries the tokens of both.
- **Every other found pull request is listed, never read**: an open one; a closed unmerged one; a merged one whose merge commit the clone does not hold, or is not on `HEAD` (a pull request merged into a branch that never shipped); a release or promotion pull request that merges other branches onward (`reason: lands other branches' merges -- read by hand`); one the time budget left unviewed; one in a repository no scanned clone holds (`clone: null`); and, in a clone read under the documentation rule, a merged one that landed only documentation (`reason: landed documentation only`, its commits in `landed_docs_only`) and one whose landed commits' paths could not be read (`landed: []`, the git failure as its `reason`) — each by URL and its `reason`, or its `state` where it has none.
- **The documentation-holding repository's pull requests are listed wherever a clone of it is scanned.** They are not dropped there: an open or closed unmerged one is listed, never read, like any other — **an earlier `/document` run's own documentation pull request, still open, among them** — and a merged one is read only through the landed commits touching a path outside the documentation set. A pull request listed is never work found. Where no scanned clone is that repository, or the rule leaves it out whole, its pull requests are dropped by name, as an `--exclude`'s are.

## 5. What the report says

- One `GitHub PR search:` line: `ok — <owners>, <queries> queries, <n> kept, <dropped_loose> loose matches dropped`, or the `status` and its `detail` — or "not run", with the first call's reason, where the `--no-github` retry ran.
- The merged pull requests read through their landed commits, each by URL with its commits' SHAs, followed, where its `landed_docs_only` is not empty, by `; left out as documentation only: <those SHAs>`.
- The pull requests found but not read, each by URL and why — in the documentation-holding repository, an open or closed unmerged one among them, an earlier `/document` run's own documentation pull request still open included, and a merged one that landed only documentation. Each is listed as found and not read, never as work found.
- For each clone in `docs.clones`, one line: `<slug>: read by path — <the content paths> and the family's own paths (key-discovery.md §1) are taken as documentation; a commit counts as scanned there only where it touches a path outside them.` — `<the content paths>` being `docs.content_paths`, comma-separated. In this line and the next two, `<slug>` is `docs.repo`, the documentation-holding repository's slug, which every clone in `docs.clones` shares.
- Where `docs.docs_only` is not empty, one line, `Left out as documentation only: <n> commit(s) in <slug> name a token but touch only the paths taken as documentation — none is work found:`, `<n>` its length, then each commit on a line of its own, `<sha> <date> <subject>`.
- Where `docs.rejected` is not empty, one line, `Not taken as content paths in <slug>: <path> (<why>)[, <path> (<why>)]…`, each entry's `path` and `why` as the script gives them.
- `Left out as never code: <the excluded slugs>` — the repositories left out whole, and only those. Where `docs.repo` is among them, its slug carries the reason in parentheses: for `no content path`, `<slug> (no profile yet says where its documentation lives — /docs-workflows:docs-profile makes the scan possible)`, or, printed after `/document`'s Phase 0 step 4(c) for a result its step 3a's scan returned, where that step 4(c) then generated a profile recording a content path other than the whole repository, `<slug> (no profile said where its documentation lives when the scan ran — the profile this run wrote, once merged, makes the scan possible)`; for `the content path is the whole repository`, `<slug> (its profile takes the whole repository as documentation)`; for `--exclude names it too`, `<slug> (the specs repository's exclusion names it too)`.
- Each repository the script could not read, by path and its `error`; a failed probe on a repository it did read, by path and its `probe_error`, as a probe failure.
- Where the script could not run at all, its stderr line, or that it timed out; where it was not run because there was no clone to scan, *not run — no clone resolved*.

## 6. The documentation paths check

The documentation set cannot be proved complete: an image directory a writer chose, or a navigation file of a generator §1's list does not know, is recorded nowhere, and a commit of `/document`'s that touches such a path is read by every later run's scan as built work for the key its message names, silently. So `/document`'s Phase 8.5 tests its own commit against the set with the script's `docs-check`, after its Step 1 commit is made and before its Step 2 offers the push, and goes on whatever it finds:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/key-discovery.py" docs-check --docs-root <the documentation root> \
  --docs-content <content path> … --base <base>; echo "exit=$?"
```

- `--docs-root` — `docs_repo_resolved`, as §1 passes it.
- `--docs-content` — the content paths §1 passes for a scan its Phase 3 or Phase 4 runs: those of the profile its Phase 0 step 4 loaded or generated, each quoted, and passed as `--docs-content=<content path>` where it begins with `-`.
- `--base` — the merge-base of `base_branch` and `HEAD`, `git -C <docs_repo_path> merge-base <base_branch> HEAD`: the base its Step 1 item 2 computes where Phase 0 recorded no `profile_commit`, taken here in every case, so that on an inline-profiling run the profile commit is checked with the squash. `--head` stays at its default, `HEAD`, the commit Step 1 made.

`exit=0` with one JSON document on standard output is the only success: `docs`, as §2 gives it less `clones` and `docs_only`; `base` and `head`, as passed; and `outside`, each path `git diff --name-only --no-renames <base> <head>` lists that lies outside the documentation set — added, changed or deleted, a renamed file as the deletion of its old path and the addition of its new one. `outside` is `[]` where `docs` is null or `docs.rule` is `left-out`: a later scan reads no commit there by path. Any other exit — the script prints the cause on standard error — means the check did not run.

What the run prints, one line:

- `outside` not empty: `Documentation paths check: this commit touches <n> path(s) outside the documentation paths — <path>, <path>, … — so a later run's commit scan will read this commit as built work unless the docs profile names those paths.`
- `outside` empty under `docs.rule` `paths`: `Documentation paths check: every path this commit touches is a documentation path.`
- `docs.rule` `left-out`: `Documentation paths check: not applied — <docs.repo> is left out of the commit scan whole (<reason>).`, `<reason>` the text §5's `Left out as never code:` line puts in parentheses for that `docs.reason` — for `no content path`, its first form.
- The check did not run: `Documentation paths check: not run — <why>.`, `<why>` what the script printed on standard error, or that git refused Step 1's commit, which leaves no commit to check.
