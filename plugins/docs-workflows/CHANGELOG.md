All notable changes to the **docs-workflows** plugin are recorded here.
Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
Versions follow semver at the plugin level.
A section headed `— Unreleased` has not been published yet; where more than one of them stands, they all ship together in the next release.

## [1.7.0] — 2026-10-05

### Added

## [1.6.0] — 2026-10-05

### Changed
- **Every breaking release note carries an Action plan.** `release-note-types.md` §4 said to omit the remediation "only when no action is needed", which contradicts §2's own definition of a breaking change as one that forces the customer to act. The remediation now sits in its own paragraph that opens with a literal `**Action plan:**` label, so a reader scanning the section finds what to do; where the PRD states none, the draft carries `<!-- TODO: action plan -->` there and the writer raises a gap. The steps are never invented.
- **A breaking note that takes effect in a later release says so.** §6 banned every release version from the prose, because the `#` heading a note is filed under already names its release. That holds for a change that takes effect in the release it is filed under, and it still names none. But a note announcing a break in a later release sits under the heading of the release that announces it, so the ban hid the one date the customer needs. Such a note now opens `Starting with <release>, …` when the PRD's body names a release later than the one the note is filed under; under `# Unreleased`, only when the PRD says that release comes after the one that ships the change. A break that is itself a deprecation, far enough out that only its end-of-life date is known, gives that date. A PRD that says the break comes later without saying when gets a placeholder and a new `effective_version` gap the command asks about. Where that break is a deprecation whose end-of-life date is also open, the date the command collects settles both. The release is never invented, never copied from the heading, and never read from the PRD's `release_versions` frontmatter. `release-notes-writer` takes a new `filed_version` input so it can tell the cases apart.
- **Release-note prose rules.** Titles aim for 80 characters or fewer instead of 5–10 words, a range real headlines often fall outside. A titled note's first paragraph runs to about two sentences, and a second paragraph does one job: compatibility, scope or a required action. A fix may run to two sentences and opens with a past-tense verb. Link text names its target. No note carries a codename, a feature-flag name, an internal component or team name, a person's name, or a marketing superlative. Another component's versions the PRD states are allowed in any note.
- **The Phase 8 report** gives the title's character count and the first paragraph's sentence count, and for a breaking note says when it takes effect and where its Action plan came from.

### Fixed
- **Choosing another route at the Phase 6 Change Type prompt re-shaped the draft in the command**, not in `release-notes-writer`, which applies `release-note-types.md` §4. Choosing Fix on a draft that announced a deprecation dropped its required deprecation note, since `## Fixes` has no room for one, and a deprecation never routes there. A switch now re-dispatches the writer with the chosen type and takes its draft and gaps, so a note that becomes breaking gets its Action plan and any takes-effect clause from the writer. A draft carrying a deprecation note is offered a second array with no Fix route.
- **`release-notes-writer`'s deprecation trigger fired on the word.** It scanned for "deprecat*" wording, so a deprecation the PRD put out of scope, left to later work or mentioned only as background gave the note a deprecation note and an end-of-life question it should never have had. §5 now says what is not a trigger: the test is what this change deprecates.
- **`release-notes-writer` step 1 read "Otherwise, `change_type` → infer"** right after the authoritative case, which garbled the routing rule. It now says that a null `change_type` is inferred as well.

## [1.4.6] — 2026-10-02

**Update `workflows-core` to 1.10.0 with this release**: `/document` and `/release-notes` rely on its commit scan taking no merge commit.

### Fixed
- **`diff-summarizer` returned an empty diff for work that had already been merged.** It took `<branch_to>...<branch_from>`; once the branch lands by a merge commit or a fast-forward it is an ancestor of the base, the range's merge base is the branch itself, and the element came back `OK` with zero files — so `/document` and `/release-notes`, which usually run after the merge, wrote without the code. The agent now tests whether the ref has landed and reads it from the merge that landed it (`<landing>^1...<branch_from>`); a fast-forwarded single commit is read as its own change, and a fast-forwarded branch name, which leaves no fork point to read, goes to the key-commit fallback; and a range that changes no file is never reported as resolved, save a single commit whose own change is empty. It also reads `branch_to` as `origin/<branch_to>` wherever the local branch is absent or an ancestor of it, and a `branch_from` the clone holds only as a remote-tracking branch as that: a stale local base read a merged ref as not landed and carried other work into the range. Prompted by upstream superpowers' review-package fix for the same class (5bf4e780).
- **`/document` and `/release-notes` label their branch-name probe** *"may name this key inside a branch name or in a merge commit"*, in Phase 3 and in their reports, since the scan now skips merge commits the probe keeps, and **define the scanned count** as the non-merge commits walked (`git rev-list --no-merges --count HEAD`). `/document`'s Phase 5 dispatch now says the elements are the ones Phase 3 built, where it said Phase 4.
- **Neither `/document` nor `/release-notes` said how a `refs[]` element is built.** A record entry is now `{branch_from: <its commit — its branch only where none is recorded>, branch_to: <its base>}`, handed whether or not the clone holds the commit yet — the agent's fetch brings it wherever a remote branch still reaches it — and a commit only the scan found is `{<sha>, <sha>^}`, its own change: `workflows-core` 1.10.0's scan takes no merge commit, so every commit it returns has at most one parent, and the agent reads a root commit against the empty tree (in a shallow clone, where a parentless commit may be the clone's boundary, it comes back unresolved). A squash of a recorded commit is read beside that commit, the same change summarised twice.
- **`/release-notes` said the key-commit fallback is reached only for a ref absent from the clone**, and that route is unreachable there: the command has never passed `diff-summarizer` a `keys_hierarchy`. Its dispatch now says so and why — the fallback's whole-history search is not bound by the note boundary — and the read-set rules and docs page say that an element the agent cannot read on its own ref, a squash-merged branch deleted with its commits the common case, comes back under **Not read**.

**Update `workflows-core` to 1.8.2 with this release**: it adds `claude-sonnet-5-5` to the §2.1 chain, which the references below now name.

### Fixed — behaviour

- **Acceptance-criteria discrepancies no longer masquerade as code discrepancies.** The writer returns separate gap kinds and evidence fields; the command offers criterion-based corrections without creating an implementation-gap report. ### Added — `/docs-audit`: what documentation this product is missing, and which of it to write first

A documentation portal that builds is not a documentation portal that is finished, and until now nothing in this family would say what was still absent. `/docs-audit` builds a denominator from the product's own code and from the committed documents in the specs tree, crosses it with the page types each thing actually earns, ranks the result on four signals with a written reason on every one, and writes `.dev-workflows/docs-backlog.yml` into the resolved documentation repository along with a coverage grid. **It writes no documentation content, and it creates no branch and no commit in the docs repository** — the backlog is left in the working tree for you to review and commit with the rest of your work. `--refresh` re-derives surfaces against today's code, reconciles pages already carrying a unit's id in their `unit:` frontmatter key, and preserves every field a human owns; a unit whose surface has vanished is marked `blocked_by: [surface-removed]` and reported rather than deleted, because a surface disappearing from a scan is as likely to be a scan failure as a real removal. `--audience` narrows what is minted and never what the coverage grid counts. Three new agents do the work — `docs-auditor` enumerates surfaces with volatility from `git log` density, `ia-planner` crosses and ranks them and proposes tutorial candidates, and `docs-audit-reviewer` reviews the assembled backlog at Opus on four dimensions — and their findings are triaged by the orchestrator, which applies survivors itself, there being no fixer agent here (D25). The tutorial quadrant does not automate: candidates are written into the file as a marked section and a human picks by editing it, which is a sanctioned act rather than a workaround. ### Added — the route page, which documents the manual half as carefully as the automated one

### Added — the cold-start scaffold: `/docs-init`, `/docs-brand`, `/docs-serve`

Three commands answer the question the plugin previously could not: *there are no docs and no docs repo — what should exist?* Every existing command assumed documentation already existed, and documented a delta against it.

- **`/docs-init`** scaffolds a documentation repository from nothing: a product-shaped Material for MkDocs page skeleton with a stub in every section, **two builds over one content root** (public and internal), a nav generated from frontmatter `order`, Vale with a project vocabulary seeded with the product name and the scaffold's own stub vocabulary, a CI workflow that runs both builds and the two output-level visibility gates, a `.gitignore` for the build outputs, the synced Vale packages and `/docs-serve`'s state file — **created, or merged into**: an existing `.gitignore`, such as a hosting template's, gains only the lines it lacks and never loses, reorders or rewrites one of its own, and, immediately before the commit, every path the run wrote — the branding phase's logo and stylesheet included — is tested against it: a path a project line ignores is left uncommitted, never force-added, every config reference to it is removed so the committed `mkdocs.yml` names no missing file, and both are reported — and the `.dev-workflows/docs-profile.yml` that `/document`, `/docs-brand` and `/docs-serve` read (`/release-notes` reads none). It refuses to scaffold over a repository that already carries a docs signal — an in-repo `docs-profile.yml` among them, so a profiled repository built with any generator is refused — and points at `/docs-profile` instead; it also refuses a target below a git work tree's top level — an absent one included, tested through the nearest directory up its path that exists, since a `git init` there would nest a second repository inside the first — because the profile it writes lives at a work tree's top level. It branches before it writes, verifies the scaffold builds and lints, and finishes on a **drafted** pull request it never pushes. Its lint applies **the same Vale exit criterion its CI workflow applies, over the same configuration** — it runs Vale on the repository's configuration alone, with the machine's global configuration and any `VALE_CONFIG_PATH` set aside, which is what CI's bare `vale docs/` reads on a GitHub-hosted runner, and its `vale sync` runs the same way, so the packages it installs into the repository's `styles/` are the ones the repository's `.vale.ini` names — so a local pass on the scaffold's files is the verdict CI's first run reaches on them, and the stubs pass: they raise no error-level alert against the seeded vocabulary. What can still make the two differ `scaffold-tree.md` §7 names: a scaffold path a project `.gitignore` line keeps out of the commit, a newer Vale release or synced package on the runner, and a runner of the project's own that carries a Vale configuration of its own. The source-repo set it confirms was, in this release, used for that run only — 1.3.0 records it in the profile as `source_repos[]`. *(Corrected in 1.3.2: `/docs-audit`, from 1.3.0, reads it too, and `/docs-profile` reads the existing one when it refreshes it; `docs-profile-schema.md`'s opening paragraph names every command that writes the profile and every other command that reads it.)*
- **`/docs-brand`** extracts a logo and a rough primary/accent colour pair from the product's own code — a fixed precedence over a Tailwind config, CSS custom properties, a MUI theme, a web-app manifest and SCSS/LESS variables — prints every extracted value with its file and line before applying anything, checks the pair against the WCAG 2.2 threshold pair, and copies assets into the site's `docs_dir` (`docs/assets/` on the scaffold's layout) rather than linking back into the code repo. It runs standalone, or `--inline` from `/docs-init`, which folds its diff and its contrast finding into that command's own review and pull request: a rebrand never requires re-scaffolding the site. **`--inline` never aborts the scaffold**: any stop or Cancel returns `no branding applied: <reason>` with an empty diff, and `/docs-init` continues as if `--no-brand`, recording the reason — an API or CLI product with no frontend reaches `DOCS_BRAND_NOTHING_TO_APPLY` routinely. It validates the **effective** theme, following `INHERIT`, so the inheriting `mkdocs.internal.yml` the scaffold writes is accepted rather than refused, and it writes `theme` and `extra_css` only into the config that inherits nothing — never a second theme block into the inheriting one — and the `logo`/`favicon` keys only when it applies a logo. A standalone run runs the same commit-time ignore test before it commits, so a docs repository whose `.gitignore` keeps `*.svg` or `*.css` out never receives a config naming a file its commit lacks. It brands a Material site where it sits, a monorepo's `site/` below its repository's top level included: it finds the configs through the profile's `builds[]`, whose `config` paths are relative to the top level, or, where the profile records none, in the resolved directory; follows each `INHERIT` from the directory of the config that names it; and writes the stylesheet and copies the assets under each config's own `docs_dir`, resolved against that config's directory as MkDocs resolves it, while git runs at the top level.
- **`/docs-serve`** starts, stops or checks the docs site's dev server for any profiled repo and reports a URL that actually opens from the host. It never starts a second server on a port that already answers, falls forward to the next free port on a collision and says so, and `--build` runs the profile's build command and exits. **A port counts as free only where nothing answers on it and nothing is listening on it** — a listener bound to an address `localhost` does not reach answers nothing — read as `render-verification.md` §2 defines free, for the render check's pre-boot probe too; whether any other socket standing on a port refuses a bind is in no table, so a start that exits before its port answers is read as a collision wherever something is listening on that port, or its log names an address-in-use failure — both asked, since a connection's local end standing on the port is no listener and each tool words that failure its own way, some of them naming no port (`EADDRINUSE`, *Address already in use*, *Port &lt;n&gt; is already in use*). **The port reaches a server only through the `{port}` token in its recorded command**, which every run replaces with the port it serves on — the configured one, `--port <n>`, or the one a collision moved it to — and which is the only part of a command ever rewritten; the same substitution identifies a moved server by its command line. A command without the token is **fixed-port**: it binds its own port, so a collision on it is reported with what holds the port (`DOCS_SERVE_PORT_HELD`) instead of falling forward, `--port` on it stops (`DOCS_SERVE_FIXED_PORT`), and no pre-scan looks above its port for a copy nothing could have moved there. Before it starts a server it checks the command's tool, as `toolchain-preflight.md` §2 defines one. For `pnpm`, `npm` or `yarn` it also checks the dependencies installed beside the lockfile: `node_modules/`, or the `.pnp.cjs` a Yarn Plug'n'Play install keeps instead. Where either is missing it stops with `DOCS_SERVE_NO_SERVER_TOOL`, rather than wait out the readiness timeout for a server that could never start. It starts a server in a process group of its own, as `/document`'s render check boots one, and a command that exits before its port answers — `mkdocs` with a theme that is not installed, a script its package does not have — ends the readiness wait as soon as that group is gone: the exit is reported with the last lines of the command's log, and nothing is recorded, rather than the timeout being waited out and the server recorded as one that might still come up. Its pid record is **keyed by port**, because a port holds one server and the profile `/docs-init` writes serves one space twice (public and internal), and each entry names the server it started — its space, and its **visibility** where the profile tags one. A lookup made through the server selection — every serve run's already-running check, and `--status`/`--stop` with `--internal` — **filters on the recorded server before matching a port**, so a server a collision moved onto another server's configured port is never reported as that one: a public server on the internal server's port is never taken for the internal one, `--stop --internal` never stops it, and one space's server is never taken for the next space's. With no record to consult, **a server is identified by evidence, never by the port it answers on**: the process the socket table names for the port — first its checkout, the git top level of its working directory compared as a whole path, so the checkout test never takes a `git worktree` nested inside the main checkout for it (outside any git work tree, where no worktree can nest, the docs directory or any directory below it, each path read as `builtin cd "<dir>" >/dev/null && builtin pwd -P` prints it, so a `cd` or a `pwd` of the user's cannot print into it), then the command line it or a process it descends from was started with — or, for a process in this checkout whose command line names no server, where the profile's builds carry different site names, the home page's whole site name, which never overrides a server the command line names. **The process is asked before the page**: a process in this checkout started with one of the profile's commands is that server whether or not its page names the site, so a client-rendered site whose page names nothing — a VitePress dev server's shell carries an empty `<title>` — is re-adopted rather than walked past and started a second time, and whether a page names the site decides anything only where the evidence names no server; anywhere else it only helps name what holds the port. A command started through `npx` is matched by the `npm exec` command line `npx` rewrites itself to. A recorded command carrying quotes is matched too: the comparison removes every `'` and `"` from both sides and collapses each run of whitespace, since the shell strips the quotes before the server sees its arguments and the Bash tool's wrapper writes each `'` as `'"'"'`. Where one command line carries several recorded commands and they nest (`pnpm start` inside `pnpm start:internal`), the longest names the server, since a process started with a shorter one never carries the longer one's text; two unrelated commands on one command line name none. A recorded command that begins `cd <dir> &&` or with a `VAR=value` assignment is matched by what follows them, as `toolchain-preflight.md` §2 finds a command's tool: the shell consumes both, so a server's own command line carries neither, whether it was typed by hand or started by this command. **It reads which process holds a port, and that process's working directory, parents and command line, from the socket and process tables, and never guesses without them.** On Linux it reads the kernel's own tables under `/proc`: `/proc/net/tcp` and `tcp6`, and each process's `fd` links, `stat`, `cmdline` and `cwd`. They need nothing installed and no root for the user's own processes, so it runs as it is in a slim container that ships neither `lsof` nor `ss` and drops root before anything could be installed. Elsewhere it reads them with `lsof` and `ps`, which macOS ships. `render-verification.md` §2 defines each read once, and `/document`'s render check reads the tables the same way. Each read runs its utilities as `command <name>`, and the socket read's `ls` as `QUOTING_STYLE=literal command ls`, since the Bash tool's shell carries the user's aliases and exported environment: an `ls` alias carrying `-F`, `--color=always`, `-Q` or `-L`, or an exported `QUOTING_STYLE` that quotes, would leave the read naming no process for a port `lsof` and `ss` name a listener on. It stops before it probes, starts, stops or records anything where `curl` or `bash` is missing, or, off Linux, `lsof` or `ps` (`DOCS_SERVE_NO_PROBE`, `DOCS_SERVE_NO_BASH`, `DOCS_SERVE_NO_SOCKET_TOOL`, `DOCS_SERVE_NO_PS`), each tested as a binary rather than by a bare `command -v`, which an alias or a shell function of its name passes, and prints every missing tool's message at once — save a missing `bash`, reported on its own, since that test runs through `bash` and would report every other tool missing with it: without a socket table nothing can say which process holds a port, so every identity given to one would be a guess. `--build` needs none of them. A port whose process the socket table does not show — one another user runs, say — names no server, whatever its page says. A server established as another checkout's — its process named by the socket table, its working directory in another checkout — is never re-adopted or recorded on that evidence, so one checkout's `--stop` never ends another's server; a member of the process group this run started is the exception, recorded whatever its checkout — a command's `cd` into a repository nested below the docs directory leaves its server standing in one — because it is this run's own server, as the membership rule below says. The selected server is re-adopted wherever it is found, on every profile — at the configured port, on the collision walk, and, before anything starts, on the ports a collision would have moved a `{port}`-carrying command to, whether the configured port has come free since or is still held, since a moved copy can sit beyond the first free port — and another of the repository's servers is passed over. Once the server it started answers, a process in the process group it started is that server, whatever its command line says, and is recorded as such: npm rewrites its own command line as it runs, dropping its options and the `--` before the script's, and two servers whose commands differ only by a leading `cd <dir> &&` leave the same command line behind, so in those cases no command line could say it. Anything else that answers there is recorded only where the already-running check would re-adopt it as the selected server, its listener this checkout's — the same server another run in this checkout started a moment earlier, whose record the port key then replaces; where another checkout starting at the same moment, another of the repository's servers or a foreign process won the port instead, it records nothing and names what holds it. Only where nothing names the server and its page names the site does a one-server profile re-adopt it by that page, and then only where the socket table places its process in this checkout; anywhere else — a multi-server profile, or a process the table does not show or cannot place — it is reported unconfirmed, starting nothing and naming the process to stop by hand or, where the command carries `{port}`, `--port <n>`, which runs no such pre-scan. The recorded pid is always the listener's, never a wrapper's, so `--stop` never ends a wrapper and leaves its server serving, and it reports a server stopped only once no process on its port is identified as one of the repository's servers and, where nothing there is identified at all, the port no longer answers as this docs site. Where the process group it signals still runs after `SIGKILL` — or, for an entry that records no group of its own, the process it signals still holds the port — `--stop` says so and keeps the entry, so a second `--stop` can signal it again. Every re-adopted server is recorded with its listener's pid; an entry is recorded without one in two cases only — a server that had not answered when the readiness wait ran out, and a started server's port whose process the socket table does not show, another user's or a container's published port. A server it started is also recorded with the id of the process group it started it in and the start time of that group's leader, and `--stop` ends it through that group, wrappers and all — a timed-out server before it binds, too, so a slow server never comes up unrecorded after `--stop`, whatever its command line carries — but only while the group's leader still leads it with that start time, since a group id is reused as a pid is, and a process that takes a reused one started later; `--status` reports such a server that has not yet bound its port as starting — whatever pid its entry recorded, the group being the evidence there as it is for a living entry, so a server caught between one listener and the next is reported as coming back rather than as stale — and a serve run counts it as running, reporting it still starting and starting no second copy, while another server's serve run counts that port as taken, at its configured port and on its collision walk, rather than start there from under it; `--status` gives its entry the listener's pid once a process in that group holds the port. Its entry also records the log its start wrote under the temporary directory, which `--stop` deletes wherever it removes the entry, stopped or stale — only ever a regular file named `dw-serve-…`, whatever the state file names — so a long-running server's log is not left to grow once its record is gone. A run leaves no log that no entry names, save one interrupted between starting a server and recording it: a run that records nothing for what it started deletes its log itself, and a write that replaces an entry takes over that entry's log where the replaced entry's process group is still its own and holds the listener the new entry names, and deletes it otherwise. An entry recorded without a pid and without such a group is judged by what now holds its port: where the already-running check would re-adopt it as the entry's own server, the entry takes the listener's pid, and `--stop` ends it like any other; where another checkout's server, another of the repository's servers or a process that is not this docs site holds the port, or nothing answers there, the entry is stale, and `--stop` removes it without signalling anything; only where nothing identifies what answers, and it answers as this docs site, does the entry stay without a pid, and `--stop` cannot end it and leaves it in place. A recorded pid counts as living only while the socket table still names it on its port, so a pid number reused after a container restart is never reported as the running server and never signalled; an entry that records a process group of its own counts as living, too, while any member of that group holds its port, whatever pid it recorded — so a server that re-spawns its listener under a new pid in the same group is still found by `--status` and by a serve run, as `--stop` already found it — and it takes that member's pid. With `--status` or `--stop`, a bare `--port <n>` names the server bound to `<n>` — the entry recorded at that port, never one a collision moved off it — so `--stop --port <n>` stops that server without a prompt. On a profile that sets `dev_servers.concurrent: false`, it starts nothing while another of the repository's servers is known to be running — a living recorded entry, one recorded and still starting, or one its own port checks identified, which on such a profile take in every other server's configured port — and stops with `DOCS_SERVE_NOT_CONCURRENT`, naming that server and how to stop it. The state file stays out of `git status`, a copy someone committed excepted, which git reports until `git rm --cached`: where no rule ignores it, the command appends that one path to the repository's local `.git/info/exclude`, never committed, so a clean-tree gate in the family does not meet it as an untracked file, in a repository `/docs-init` scaffolded or any other. `--internal` on a profile that tags a public server but no internal one — a `/docs-init --public-only` scaffold — stops with `DOCS_SERVE_NO_INTERNAL_BUILD` instead of serving or building the public site — under `--build`, with a message naming the missing `builds[]` entry. It writes no documentation and no artefact — the one command in this plugin that writes neither — which is why it runs no `specs-preflight`, no `commit-artifacts`, no review gate and no maintenance phase; `/docs-profile`, which writes a profile, runs none of those four either, and its page, which called it the one command here that emits no cost entry, now names `/docs-serve` beside it.

### Changed — the docs profile records what the scaffold produces

`docs-profile-schema.md` and `docs-profile.default.yml` gain `generator` (informational only — every invocation still goes through `commands.*`, which is what keeps the generator choice reversible), `builds[]` for a repo whose one content root renders into more than one output, `dev_servers.servers[].public_base_url` (a command inside a container cannot infer the host's published port mapping, so it reports this instead of guessing) and `dev_servers.servers[].visibility`. `dev_servers.servers[].command` may carry the literal token `{port}`: every consumer that runs the command substitutes the port it serves on and never runs the token unsubstituted, nothing else in a command is rewritten, and a command without it is fixed-port — its port is its own, and no consumer can move it. A server command that binds only loopback is a profile defect, which `/docs-serve` reports rather than patches. So is one that detaches its server (`setsid`, `nohup … &`, a trailing `&`, `docker run -d`), because both consumers that start a server track it through the process group they start it in, which `setsid` or a container takes a server out of, and `/docs-serve` records a pid only for a listener in its own checkout, which a server detached into a container is not. A foreground `docker run -p …` or `docker compose up` keeps to that rule, and the schema says `/docs-serve` cannot identify the server it starts — Docker's forwarding holds its port, not the command's process — and that such a server is stopped with Docker. `/docs-init` writes the token into both of its server commands (`mkdocs serve -f <config> -a 0.0.0.0:{port}`). `/docs-profile` writes it only in place of a literal port a detected command already carries, never inventing a flag or an argument-forwarding form, and its report lists every fixed-port server it wrote; the worked example's `pnpm cloud:start` stays fixed-port. `images.policy` becomes an enum — `in-repo` (the scaffold default) / `object-store` / `cdn` — replacing a free-text sentence, with every rule that sentence carried preserved under the policy it describes, beside `images.root`, `max_bytes`, `public_prefix` and `internal_prefix`. `dev_servers.concurrent` states what its absence means — no one-at-a-time limit, which is what `/docs-init` writes by writing no key, its two servers running side by side — and `/docs-serve` honours `false`; `dev_servers.readiness_timeout_seconds` names both of its readers, `/document`'s render check and `/docs-serve`'s readiness poll. The schema also advises recording, where the operator can, a server command whose tool keeps the command line it was given — `node_modules/.bin/<tool> …` — since `/docs-serve` identifies a server by that command line. And a server command binds the port it is given, or fails: one that moves itself to another port when its own is busy is a profile defect, like a loopback-only bind, and where a tool's command line cannot pin the port, its configuration must: VitePress passes `--strictPort`, and an Astro site, whose `astro dev` takes no such flag and moves off a busy port with one, sets Vite's `server.strictPort` under `vite` in its `astro.config` — without either, Vite takes the next free port, where nothing looks for the server and `/docs-serve` can start a second copy beside it. A tool can also detach its own server: Astro 7 does wherever it detects an AI coding agent, Claude Code among them, and the schema names the opt-out Astro documents, `ASTRO_DEV_BACKGROUND=0` ahead of the command, which keeps it in the foreground — and, since Astro 7.2 detaches `astro preview` the same way, that command's own, `ASTRO_PREVIEW_BACKGROUND=0`. It also says that Astro runs one dev server per project root: a second `astro dev` for a root whose first server still runs exits at once, *Another astro dev server is already running*, so a profile that serves one Astro root twice needs `--ignore-lock` on one of its two commands, never `--force`, which stops the first. `astro preview` locks its root the same way — a second exits with *Another astro preview server is already running* — and takes the same `--ignore-lock`. `/docs-profile` records a detected command as it stands and adds no flag, so its report now lists the server commands it can tell break one of these field rules — a loopback-only bind, a detaching command, `astro dev` or `astro preview` without its variable among them, and a VitePress or Astro command that moves off a busy port unpinned — each with the rule it breaks and how to fix it, or its tool's configuration, by hand. VitePress and Astro are the two tools whose pinning it checks: whether a command running another tool moves off a busy port, and what would pin it, is that tool's own behaviour, which it has no verified form to judge, so the report neither lists nor clears such a command. Run inline from `/document`, which skips that report, it hands both lists back, the fixed-port servers and these defects, and `/document` shows them.

### Changed — `/document`'s render check stops each server by its process group

The smoke-check recorded "the process id" of each server it booted and killed it before booting the next, without saying which process. Started the way the Bash tool starts a command, that is a wrapper shell, and an `npm` or `pnpm` script adds another: signalling either leaves the server serving, so the next server booted beside it. A server that had not bound its port when the readiness poll timed out was worse: killing its wrapper left it running, and it bound after the check had moved on, outliving the run. It now boots each server **in a process group of its own** — `command bash -c 'set -m; (cd <docs_repo_path> && <command>) > <log> 2>&1 & echo $!'`, where job control makes the printed pid the id of a group the command's wrappers and children inherit — and stops it by **signalling that group**, under the same explicit `command bash -c`, so job control, `$!` and `kill -- -<pgid>` are bash's whatever shell the Bash tool uses — Claude Code runs it in bash or in zsh, zsh on a default macOS — and a `bash` function of the user's never answers for the group, `SIGTERM` and then `SIGKILL`, after its pages and after a readiness timeout alike. **The next server boots only once two things are confirmed**: the group is gone, and the port is quiet. A group counts as gone where **the process table** names no member of it or where every member it names is a zombie: a zombie runs nothing and holds no port, and under a parent that never reaps — a container whose PID 1 is `sleep infinity`, with no init — a signal test alone would find the group running for good and end the check after its first server. `kill -0` settles only the other half — exit 0, so a member is alive and signallable, so the group is not gone — because its failure has two causes that mean opposite things: no such group, and a group this user may signal no member of, which `kill(2)` refuses with `EPERM` and bash reports with the same exit 1. Reading that failure as a gone group reports a live server as ended: measured against four live root-owned groups on this host, where `kill -0` exits 1 while the table names a live, non-zombie member of each. The table names another user's processes too, on Linux from `/proc` and elsewhere from `ps`, so it answers where the signal cannot. Where the port still answers, the port's **listener** is signalled as a second stop — `/docs-serve`'s definition of one, without its checkout test (this run started the server) or its state-file test (this command keeps none). Where either still cannot be confirmed, no further server boots, the record names the port or process group left running, its command and its log, and every page not yet checked falls to the manual table; a server confirmed stopped has its log removed, so the check leaves behind no log but one its record names. A server job control gave no group of its own is stopped by its pid and its listener instead, and a readiness timeout on it ends the check, since nothing can tell whether it will bind late. Every read of the process or socket table (the group a boot made, its members' states, a listener and its parents) comes from `/proc` on Linux, which needs nothing installed, and from `ps` and `lsof` elsewhere (`render-verification.md` §2), each utility run as `command <name>` so an alias or shell function the Bash tool's shell carries cannot change what the read parses. A missing `lsof` alone never ends the check. A probe before each boot keeps the check from booting onto a port something else already holds, and that process is never signalled. **The readiness poll ends as soon as that group is gone**: at every interval at which its request gets no response it tests the group, and a server whose command exits before its port answers — a theme that is not installed, a configuration it cannot load, a script its package lacks — is reported with the last lines of its log, its pages fall to the manual table, and the check goes on at once, where 1.1.3's poll ran until HTTP 200 or the whole readiness timeout, 120 seconds by default, for a server that had already exited.

### Fixed — a style-check outcome no rule ever assigned

The same work found a **pre-existing** live defect, and it is worth separating from the deletion above because the deletion did not cause it. The style-check outcome mapping had two rules for a missing primary linter: `DEGRADED` when every detected rung *failed*, and `NOT_CONFIGURED` when no rung was detected **and** `prose-style` was absent. Those do not meet. A repository with no linter of its own and `prose-style` installed — the common case — landed in neither, so the `style_check` gate had no outcome to record at all. Removing the `NOT_CONFIGURED` branch did not expose the hole; it removed the last rule that mentioned the case at all, making it unavoidable. Both rules now name "detected and failed, or never detected" explicitly — the `DEGRADED` rule and the `ERROR` → `UNAVAILABLE` rule, in `/document` and in `docs-style-checker`'s own `status` definitions alike.

One consequence to know about if you read the agent's output: `complementary_linter: none` has **inverted** meaning. It used to say "no complementary pass ran; the primary carried the gate", which mapped to `RAN`. It now says "`prose-style-checker` *was* the primary", which maps to `DEGRADED`. Same token, opposite ledger consequence, in the field `/document` derives the outcome from. Nothing else consumes it.

Everything else is behaviour-preserving.
