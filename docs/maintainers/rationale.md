## description-budget

The limit is GitHub Copilot CLI's, and it rejects the **whole catalog** — one over-long blurb makes every plugin in the marketplace fail to install or update.

Claude Code enforces no limit, which is exactly why over-long blurbs kept shipping: the Claude editions grew unchecked and the Copilot edition inherited the overflow at port time. The blurb reached 2788 chars by appending one sentence per release, and was trimmed by hand three times in the Copilot edition before the check existed.

## mermaid-gate

The rule exists because GitHub draws each ```` ```mermaid ```` block as a diagram and shows *"Unable to render rich display"* where it does not parse.

## reference-parts

`scripts/reference-parts.py` exists so a shared reference can be split into parts without a rule going missing (lean context part 1, `docs/superpowers/specs/2026-10-20-lean-context-loader-design.md` §B–§D).

**Why generated files.** Extracting a part when it is loaded was the alternative, and it fails the callers that need parts most: `review-fixer`, which applies one rule of `finding-triage` on every dispatch, has no Bash, and a skill's `allowed-tools` grants no tool its caller lacks; `doc-fixer` has neither Bash nor the loader and reads its reference by path. A committed generated file is one `Read` for every caller, and the model never assembles the always part itself. The source stays one file, so a maintainer edits one place and checks 11, 16 and 20 keep the reference files they are keyed to. Each part file names, in the line under its title, every part it holds, because the loader's rule that a part already read covers every part it holds is otherwise decidable only from the part list in `index.md`, which a run holding the part file alone has not read: `review` holds `version-line`, `triage` holds `patch-gate` and `verify`, and each lane holds `contract`.

**Why it fails closed.** A part file is read by runs and checked by nothing else, so every way it can drift without a symptom is a failure here, never a pass: a source edited without `generate` serves an old rule; a file a removed part left behind still answers a request that names it; a request whose second argument names no part of its reference sends a run through a report and the rule index, and its recovery ends in the part the index names for the rule or, where the index names none, in the whole reference, and never in anything else; an entry-point request whose token no heading of its reference carries as the first word of a code span stops the run that makes it; a part file read by path from a dependent plugin opens nothing, since `${CLAUDE_PLUGIN_ROOT}` there is the reading plugin's root and only `workflows-core`'s holds `reference-parts/` — the defect check 16 exists to prevent, which its relation 5 cannot see, matching only `references/` paths; an explicit request whose sentence names a rule that the loads of that sentence's calls do not hold is a call converted to the wrong part, and it fails even where another call in the paragraph loads the right part — a later call comes after the run has applied the rule, and after an earlier one the rule is already in the conversation, so nothing goes missing, but the call is still the wrong part, and catching it is what the check is for; a sentence naming a rule it does not cite, in a paragraph that cites a split reference in any form, may be leaning on the paragraph's loads, so it is judged against the loads made at or before it — explicit part and whole loads, and the parts bare citations are placed on, of every split reference the paragraph cites whose index holds the name, any one of which may hold it — never a later one; a bare citation naming no rule counts as a whole load there, because the preamble sends it to `args: "<name>"`, which holds every rule, and the gate models what the run does; a citation naming a rule of a private part points the run at text no part load brings; and a scan that finds no declaration, or no citation of a declared reference, proves nothing when it passes. The calls of one sentence count as one load, in any order, because a run reads a sentence whole before it acts and command prose often names a rule before the parenthetical call that loads it; and a sentence citing a split reference is judged as that citation for that reference's names only, so a rule two references both name is never read against the one the sentence does not cite. A name matching entries in two parts fails too, though with exact matching it never reaches a citation, because the index's own uniqueness check, which `check-parts` and `check-citations` both run first, fails it. Two cases pass and are counted instead, since neither loses a rule: a bare sentence naming rules of two parts is placed on both, because the preamble has the run load the part that holds each rule before applying it; and a citation naming no rule the index holds is placed on the whole reference, which the preamble then loads — the census is how a heading renamed under its callers is found. An `index` request passes too, as a lookup: the run loads what the index names, so the request's own sentence passes whatever public rule it names, and its load holds every later sentence of the paragraph.

**Why its own script.** `scripts/check-docs.sh`'s body is byte-identical in the internal Claude and Copilot editions, so a check there ships to both, and they would receive a gate with nothing to check (the design, §D).

**Why a sentence or a paragraph, never a line.** Command files hard-wrap their prose, so a rule's name in an italic span often wraps across two lines. The gate reads each citation's own sentence and, in a paragraph that cites a split reference, its other sentences, out of the joined paragraph, never a line; the `minimal` fixture wraps both the name and the preamble to hold that.

**Why a `§` reference belongs to the citation nearest it.** A `§` number names a section of whatever reference the prose has just cited, split or not: `/conformance`'s terminal sentence writes the resume pointer per a `session-hygiene` call's §1 and then commits through `specs-repo-git`'s `commit-artifacts` entry point (§4). Read against every split reference its paragraph cites, that `§4` became `session-hygiene`'s and failed correct prose — there and in `/security-workflows:scan`'s terminal paragraph, once the trial split below converted their calls to part requests. So a `§` belongs to the nearest citation before it in its sentence. With none before it, it belongs to the first after it there, since prose names a rule before the parenthetical call that loads it. In a sentence citing nothing it belongs to the nearest citation in an earlier sentence of its paragraph, which is what "then stop as §4 says" after a call leans on — that is how a run reads it, and the citation it is given is one the paragraph actually makes, never a reference name parsed out of the words around it. With no citation anywhere before it in its paragraph, there is nothing for it to lean on, and it names nothing. Measured on the same trial split, with its calls converted or not, giving each `§` its citation this way changes no verdict and no placement against reading only the citation before it in its sentence, and every `§` of the two terminal paragraphs goes to the reference it points into. A `<plugin>:<name>` token is a citation only where that plugin holds that reference file: a `references/` directory shares its name with a command or a skill (`dev-workflows:upgrade`, `workflows-core:model-routing`), and a token naming one is no citation. ## resolve-against-a-known-set

All five sites of 3.3.0's longest-running defect family are this: four re-stated a key grammar locally instead of citing the one `workflows-core:addressing` §1 fixes, so the copies drifted apart and a valid slice key hard-stopped a command its own recommended redirect sent it to; the fifth extracted a key out of a branch name.

The worked example: `workflows-core:specs-repo-git` §3.5's `branch-key` strips the plugin prefix, then tests the remainder against the keys the run already holds — a key counting as a candidate only where the remainder is exactly it or continues with `-` or `_`, longest candidate winning.

- *`run-state.py` rejecting a `workitem_key` equal to `unit_key` (2026-10-23).* Two live `/implement` runs wrote the Epic's key into run-state as its `workitem_key`, and one committed it as a `Work-Item:` trailer. ### refinement-7

**The two measurements behind the addition-count rule disagree about whether one delimiter is enough, which is why it states a property and not a character count.** On the edit that added a wrapper alternation to the `test-notify` gate, one delimiter on each side suffices: the body `mvn test|gradlew test|…|make test` still returns 1 with `mvnw test|` inserted ahead of it, and returns 1 again on a fixture appending `|cargo test` instead — the second case being why the opening `(` is not enough on its own, since an insertion lands at either edge. On the edit that inserted five rows into `test-baseliner`'s parse table it does not, because there the delimiter bounds every row rather than the edit: the `Gradle` row alone returns 1 before and 1 after, that row with one character on each side returns 1 and 1 as well, and only the `Gradle` row *plus the `pytest` row that had followed it* falls 1 → 0.

Measured over `commands/` and `references/`, a 17-character phrase survives the wrap break about six times in seven, but an 80-character one only about one time in three — so at sentence length a line-based grep misses an occurrence more often than it finds one, and the short count it reports is plausible rather than obviously wrong, which is what makes it dangerous on exactly the files refinement 7 exists for. The reviews on this branch ran the three-step method as `scratchpad/r47/sweep.py`, a session-local script this repo does not ship and which collapses the file but not the pattern.

Reading the paragraph is not enough either, and this was bought twice in one round and once more by the round that wrote the refinement: the round that corrected `between the three` to `between the four` in `workflows-core:phase-handoff` §4.3 had read that paragraph and left the identical string standing further down the same section, in the paragraph saying the array is not reworded for a missing remote — next to a second falsified count on that same line — while scoping *"the one reader a proposal has"* on six surfaces and leaving it on two more, one of them the §1 of the very reference whose §0 it had just made the census, and the other an instruction telling the run to **print** the retired sentence; then the round that wrote refinement 7 certified it with a count of that same string taken on the parent tree, publishing **3** in a commit whose own new prose quoted it — as this rationale section still does. One wrap-insensitive count per edited string, taken after the edit rather than before it, catches every one of those; no other refinement on the list does, because each of the others tells you where to look and this one tells you when you are done.

A replacement changes text *inside* the span you counted, so the after-count falls however the query was framed, while an addition changes text only at that span's boundary and leaves the string standing inside the new form *by design*. A line-based `grep -c` over hard-wrapped files returns a number smaller than the truth with nothing to say it did. The three-step method is the rule, not any script: write your own and keep the method.

The `docs/` copies need remembering, not a wider scope: refinement 4's scope already covers those pages. The second instance above is what anchoring a sweep on a noun costs.

Refinement 8 says which strings to count; refinement 7 says when you are done counting them. **Copies vary in wording site by site, including among the ones you already hold**, which is the whole reason the query is built on the subject; and one noun across every copy is worth a little precision because a second noun is a copy the next sweep cannot see.

## sentence-context

**The risk peaks where a reader would least expect it**: of the four instances one batch's records carry, **three were introduced by fixes to earlier findings**, so the move is likeliest exactly when someone is already being careful about a rule they have just been shown to have got wrong.

**Four surfaces, one move.** A **trigger**'s extent is the worked example below. A **rationale**'s is the second. A **report condition**'s is the third: a Final Report asked for `workflows-core:phase-handoff` §4.1's outcome line *on every run*, where a producer that never offers a handoff — `/frames` having written no index, `/idea` on `status: draft`, `/implement`'s Phase 4.5 no-op, the live cases §4.1 itself lists — has no line to print and would have had to assert a decline nobody was asked about; the widened condition reached all three of §4.1's outcome states, not the two the report line was written for. And the fourth is the same move at **sentence** scale: a gloss widened to say what else an option drops asserted *save one*, a count the run cannot make where the set may be none, one or many.

**The trigger surface in full, because it is the clearest.** The array is the cheap half of such a change; the expensive half is every sentence around it that says what an option *does*, each written when only the old trigger could reach that question and free to assume whatever that trigger guaranteed. **Measured**, as an Important regression on its branch: `/brd-intake`'s same-or-new question gained a second trigger — a matched pair whose two anchors name one element without their text being the same — with no condition on the file's recorded state, while *Same requirement*'s stated effect kept the existing row whole, its anchor and its existing `text` with it. That effect was written for the unmatched-row case, where the file is recorded **unchanged** and the existing text is still what the document says; on a file Phase 2 recorded **replaced** it would have kept text the revised document no longer carries. The array was right and its options were right — the paragraph stating the effect was not, and it is the one a change that reads only the array never opens. It now turns on the file's recorded state: on a replaced file the option keeps the id, takes the returned `text` and reports the change old → new.

**The rationale surface** — `pass9a-1-report.md` counts two of that batch's last three findings as this: a **rationale** clause added for a new rule, landing beside an older sentence written when the rule was narrower, where the instruction stays correct and the reason beside it goes false. In `/brd-intake` a carve-out gained a clause saying a revised document can make the agent start returning a row it had not returned, two clauses from a standing claim that the agent is handed the same inputs on every later run; sweeping that claim found a twin one paragraph away resting a prediction on the same premise. **A third site kept the claim unqualified and was right to**, being the re-dispatch *within one run*, where nothing the agent is handed can change. On qualifying by the class: the first repair (`d2cdba1a`) named a source the customer had not revised, and it survived exactly one review round before a corrected transcription — a change to what the agent is handed with no revision behind it — falsified it; the second (`9a5599a9`) closed the class instead.

**The pointer face — one documented instance of each kind.** A `source:` ladder written from `product-workflows:brd-format` §1.1's vantage, where *this log* is the link log, was pasted into `brd/brd-figures.md`'s own layout block, where *this* re-points at the figures file — which is no log, and the opening line the instruction means is the link log's — so a writer meeting the instruction inside the block it is writing looks in the wrong file. And a clause across an em-dash read *"no later command of the route opens anything"*, where the object was the file named before the dash: read literally it is an absolute claim about every later command. **It arrived in a sentence written to repair an earlier finding** — `62c4a552`, the round-13 lead-in that gave `/brd-intake`'s one run-ending recommendation its reason where the choice is made — and the round after removed it (`19ea31f3`): the *risk peaks* claim above, counted there over the extent face alone, holds on this one too. Two instances, one check, so the pointer face stays a clause of the rule rather than a rule of its own.

**Nothing in the rule quotes `brd-intake.md` for what it says today, deliberately**: the first draft of the rule quoted it four times, and one of those quotations was falsified within a round by the batch that owns the file — the rule, in miniature, at its own expense. The instances **describe** instead, which is what that audit settled on and what keeps them checkable; the one quotation that stands is of a clause two named commits add and then remove, which `git show` settles and no later edit of that file can move.

Why the faces differ: on the extent face the sentence you wrote stays put while its neighbours go false, and it is the one you have already checked; on the pointer face the sentence you wrote is the one that goes wrong while its neighbours stay untouched, so the extent check is inert, nothing having widened and no case split existing to enumerate. The old precondition's out-of-reach paragraphs are where an assumption sits unstated precisely because nothing could once falsify it. The third-check threshold exists because three checks with their evidence will not read as one line; a face that needs a check of its own is a rule of its own.

Refinement 8 of the claim-expiry sweep fires on the same change as the extent face and covers the *other* axis — the **copies** of that claim elsewhere — so a reader who does one and not the other is half covered: the extent face is about the adjacent assumption, refinement 8 about the distant copy.

## verifier-blind-batched

**Blind by construction (#73).** Until 2026-10-01 `/prd-ground` Phase 7 handed `grounding-verifier` the whole finding — `evidence` and `cites` included — and relied on the agent's own rule not to read them before re-deriving. In one live run of eight dispatches, four reported unprompted that they could not comply: the evidence was already in their context. The anchoring risk is toward `agree` on exactly the failure that run found most often, an original citing something real but adjacent to the premise. A self-imposed discipline cannot remove text from a context window, so the answer is no longer sent: the derive dispatch carries the premise and the source, and the agent refuses one that carries more. A `[DG#n]`'s `class`, and a class-1 claim's `none — frame-only: <field>`, still reach the blind step: they are the question being re-derived, not its answer. **Blinding also removed the second look**, so a disputed `contradict` gets one back. An unblind verifier could weigh its own reading against the original's; a comparison that has seen the original must never revise the blind result, or the blindness is undone. In the final live smoke run an original `NOT-PROVABLE` ("orders are persisted to a database table", where persistence could live in another system) came back from the blind step `REWRITTEN`. The comparison's own notes said the blind verdict overreached, and the finding was rewritten anyway. So compare now flags a blind result whose own evidence does not establish its own verdict, never one merely because the original differs, and Phase 7 asks a second blind derivation. Agreement upholds the `contradict`; disagreement settles the finding `unprovable`. That restores the second look without anchoring it to the original.

**Batched, not weakened (#74).** One Opus dispatch per finding made a 138-claim, two-repository run cost 278 verifier dispatches in about 70 sequential batches, 200 of them `NOT-PROVABLE` and 117 from a frontend answering backend claims. Batching by repository or frame set, at most 25 to a batch and two dispatches each, makes that run about 24 dispatches, and each derive batch explores its repository once instead of once per finding.

**Refused, with the reason:**

- *A cheaper tier, or a sample, for `NOT-PROVABLE` findings.* A wrong `NOT-PROVABLE` where the code actually contradicts the premise sends a question to `/brd-interview`'s operator without the fact that settles it. Every finding keeps its own Opus re-derivation.
- *One repository-scope finding ("this repository holds no persistence layer") standing in for the findings under it.* The findings under it would never be individually re-derived. Inside one derive batch the agent may cite a fact it established for one finding for another, after checking it bears on that premise — each finding's evidence still stands alone.
- *Carrying an outcome forward from an earlier run at the same pin.* It needs a stamp saying which verifier contract the outcome was reached under, something must bump that stamp whenever the agent, `grounding-format` or the model changes, and no gate would check it; a missed bump carries a stale outcome forward silently. Batching shrinks a re-run's cost by the same factor as a first run's, and on unchanged code a re-verification is the only way the first verifier's error surfaces.
- *Two dispatches per finding instead of per batch.* It fixes #73 by doubling #74's dispatch count.
- *One dispatch with the originals sealed in a file the agent opens after deriving.* Blind by instruction again.
- *The comparison done inline by Phase 7.* Running controls and judging agreement would move to the session's model, which need not be Opus, and every result would land in the orchestrator's context.
- *Continuing the same agent with the withheld fields.* Agent continuation is not available in every harness these commands run in.
- *Checkpoint and resume across a Phase 7 stop.* With batching a lost pass is about 24 dispatches; an incomplete result is retried once in each verification pass and in each second opinion instead.
- *A second blind opinion on a disputed `agree` or `extend` (2026-10-23).* The dispute reaches only `contradict`. On the measured miss — a range check confirmed while a request that leaves the value out stores the type's default outside it, which the grounder and the blind derive both read and both missed — its best case is `unprovable`, which keeps the wrong `CONFIRMED`, and none of the three agents that shared the blind spot noticed it, so none would have flagged it. Fixing the verdict rule at its source, `grounding-format` §3's *A claim that restricts a value*, attacks the shared blind spot instead. The investigation is preserved in `docs/superpowers/verification/2026-10-22-lean-context-handoff-part-worse-prd-ground.md`, Item 1 and *Would not do* 5.
- *A hook or a new rule against a plain `cd` in derive mode (2026-10-23).* A run's own feedback called a blind derive's `cd "<repo_path>" && …` a break of blindness. The rule is already explicit — `grounding-verifier`'s Process opening and its hard rule against reading the session's working directory — and the dispatch that broke it carried no answer field. A plain `cd "<repo_path>" && …` inside one call reads `repo_path`, not the session's directory, so nothing under `$SPECS_PATH` was reachable. A hook cannot tell a derive dispatch's Bash calls from any other without machinery the risk does not justify. The investigation is preserved in `docs/superpowers/verification/2026-10-22-lean-context-handoff-part-worse-prd-ground.md`, Item 2b and *Would not do* 7.

## specs-push-scope

Step 5 now applies that rule as `push-scope`, and §3.4 cites it.

**The base is the branch's own remote ref, never the remote as a whole.** The first draft of `push-scope` counted the commits on no ref of the remote at all. A review showed that this passes a default branch that has been fast-forwarded locally onto a pushed `prd/` branch: that branch's commits are on the remote, so they did not count, and the push landed them on the remote's default branch — effectively merging an unreviewed pull request. The remote-wide form survives only where the branch has no remote ref: the local-only branch a failed `push -u` leaves behind, or one whose remote ref was pruned — since 2026-10-27 never a plugin branch, which step 5 no longer pushes where `origin` lacks it ([specs-push-target](#specs-push-target)). **The push names its branch**, `push -u <remote> <branch>`, because a bare `git push` under `push.default=matching` pushes every matching branch, and only this one was measured; an upstream under another branch's name, which a branch cut from the default branch can inherit, counts as none, so a plugin branch is never pushed onto the default branch. Upstream presence is read with `for-each-ref`, which prints nothing where there is none, because `@{u}` exits 128 in exactly that state.

**A default branch the run stands on is caught up at run start (2026-10-05).** §3.5's B1 did nothing, and only B2 and B4, which switch to the default branch, pulled. A checkout left on the default branch while a pull request merged on the remote, or while a teammate pushed session files, then committed on a stale base: the push was rejected as non-fast-forward, and so was every later run's retry. §3.4 now fast-forwards a default branch that is strictly behind before it flushes, and §4 step 2 again before staging, so a run whose preflight stopped at a guard also commits on the remote's tip. The pull carries `--no-rebase`: a `pull.rebase` setting, common in user configs, would otherwise make it a rebase that refuses to run beside a modified artifact. A branch that had already diverged was not rebased then: the rejected-push line named `pull --rebase --autostash` and the push for the user to run. Since 2026-10-28 (LC11) the run takes `origin`'s commits in itself outside session-branch mode, on the default branch and on a plugin branch alike, by a checkout-free replay of its own session-file commits (§4 step 6), and the line names `pull --rebase --no-autostash` only where that replay refuses or cannot run, nothing having moved; the measured reasons are in the retired bullet that closes this section.

**Refused, with the reason:**

- *Pushing a branch the plugin did not create where `push-scope` passes.* That still adds a commit to somebody else's remote branch, and to any pull request open from it. §2.2 manages only the branches the plugin created, so pushing someone else's branch is theirs to do.
- *Exempting a deliverable commit whose own push failed at handoff.* Telling it from a user's commit means parsing commit messages, a pattern over free text rather than a lookup in a known set. §6's *push-scope* line names the commit and tells the user to push the branch, `next-phase-offer`'s *Push failed* clause says the same, and §3.4's retry already refused it.
- *Passing this reference's own commits whatever a `pre-commit` hook put into them.* A hook that regenerates and stages a file puts it into the pathspec commit (step 4), so on such a repository the plugin never pushes its session files: the §6 line names the file each run, and the user pushes. Two passes were tried in review and both leaked. A pass by sha also pushed whatever a hook that stages broadly (`git add -A`) swept in: the user's pending G1 path, draft or deliverable. A pass by path (a path step 2 did not list was clean, so the hook generated it) missed the original path of a staged rename, whose deletion a `git add -u` hook commits, and it let a generated index carry the names of folders the user had not committed. Each fix exposed the next, and a stranded push that is reported is the cheaper failure.
- *Rebasing the plugin's session-file commits onto a diverged default branch.* **Retired 2026-10-28 (LC11): outside session-branch mode the run now takes `origin`'s commits in itself, on the default branch and on a plugin branch alike — by a checkout-free replay, while the in-checkout rebase stays refused.** The refusal read: "`push-scope` proves they are the plugin's own, but two writers appending to the same `implementation.md` conflict, and a rebase stopped on a conflict in a shared checkout is worse than a line naming the two commands." Both halves were measured (git 2.43.0, scratch repositories; `docs/superpowers/verification/2026-10-27-lc11-measurements/`, whose README tabulates every scenario):
  - **An in-checkout rebase is unsafe in a shared specs checkout, autostash or not.** With autostash the user's file contents come back but the index does not — a staged-then-edited file (`MM`) comes back ` M`, an `AM` comes back `A ` — and where putting the changes back conflicts it still exits 0, leaving conflict markers in the user's own file and a stash behind (s1); an abort does not restore that index either (s5). Without autostash it refuses up front on any dirty tracked path (s2), which a specs checkout often holds beside the plugin's commits (§3.3 G1). During a stop HEAD is detached, so a concurrent family run's preflight hits G0; an edit made to a tracked file during the stop is destroyed at the abort; an `index.lock` held at the abort leaves the rebase stuck; and a commit made during the stop is published unmeasured or orphaned (s6).
  - **The append conflict is real, and git's `union` driver does not settle it.** Without `union` two writers appending to one file conflict; with it, two distinct entries that share lines become one (`review-of-first-draft.md`'s t2–t3, on the family's real formats; [session-branch](#session-branch)). So the replay settles a block-shaped session file both sides changed by entry set, rebuilds a security register both sides changed from its run records with the `register.py` the caller hands over (refusing where none is), and refuses on any other path both sides changed.
  - **The checkout-free replay is safe.** Each commit is replayed with `merge-tree --write-tree --merge-base` and written with `commit-tree`, so nothing in the checkout, the index or any ref moves: on every dirty state of s1 the user's files kept their exact status letters and bytes, and a dirty or untracked path the change would overwrite refused the move with nothing changed (s8). **The move order** is the one measured never to leave the index differing from HEAD on a path the user did not touch, or a branch the working tree does not match: `update-ref --stdin` with `start`, the update and `prepare`, then `read-tree -m -u <old> <tip>`, then `commit` or `abort`; `read-tree` before the ref update, `switch -C`, `checkout -B` and `reset --keep` each failed a case (s9-1). **The push follows the move**, because pushing a tip the local branch did not hold doubled entries two runs later (s9-2). **A push race** is met by fetching, replaying and moving again, at most three attempts: two races settled on the third, and after three the branch stood consistently on the last replay for the next run's push (s9-3).
  - **The remedy names `pull --rebase --no-autostash`**, where the replay refuses or cannot run (save where another session switched the checkout during the move, where the row names none, since a pull run in a checkout another session moved could land in another branch): a `rebase.autoStash` setting turns a bare `--rebase` into s1's autostash (`review-round-2.md`, N4: exit 0, conflict markers in the user's file, a stash kept), and with `--no-autostash` the pull refuses up front, touching nothing, while anything is uncommitted.
  - **Still outside it:** the deliverable push (`phase-handoff` §2.5), reviewed through its pull request; a `[remote rejected]` refusal, which is recorded as before; and every push in session-branch mode, where the default branch is never pushed and the session branch's own rejection a later run already merges, as §8.4 says (s9-5), while a plugin branch §3.4 retries there is reported, not replayed.

## specs-push-target

**Where the session-file push goes, and what it never touches (2026-10-06).** The push-scope round filed twelve edge cases, fixed two and closed ten as outside the population it measured. At the user's request a later round reopened the ten: nine are fixed, and a protected default branch had an interim fix until the next round designed it ([session-branch](#session-branch)). These six are `workflows-core:specs-repo-git`'s:

- **`origin`, and only `origin`.** Step 5 pushed to the branch's upstream remote, else `origin`, while §3.2, §3.5 and `phase-handoff.md` read `origin` alone. On a fork whose default branch tracked the parent repository, the session files went to the parent. Now the push goes to `origin`, and where `branch.<branch>.pushRemote` or `remote.pushDefault` sends the branch elsewhere it does not push at all.
- **The session-file push never goes to a branch the remote deleted — save the session branch.** A branch whose same-name upstream on `origin` is gone (`ls-remote` exits 2) is not pushed, since a push recreated a renamed default branch or a merged, deleted pull-request branch. In session-branch mode `specs-repo-git` §8.4 pushes `session/<identity>` again after `origin` deletes it, recreating it: delete-on-merge removes that branch every time its pull request merges, and this rule would then keep every later run's files local for good ([session-branch](#session-branch), *A remote that deleted the session branch does not stop its push*). Since 2026-10-07 a branch with no upstream at all counts as pushed where its remote-tracking ref `refs/remotes/origin/<branch>` exists: a push from a container that mounts `.git/config` read-only records no upstream, and a pull request merged with *delete branch on merge* while the run was finishing then had its branch recreated by the session-file push. `phase-handoff.md`'s own deliverable push is outside this rule: it pushes a branch its §2.2 rule 3 reused, which a deliverable may need. **Since 2026-10-27 (to-fix LC2) the session-file push never creates a plugin branch on `origin` either.** A handoff whose commit a `pre-commit` hook refused left its `spec/` branch local, and `commit-artifacts` then pushed it with the session-file commit alone: a branch on `origin` with no deliverable and no pull request. Only the handoff's §2.5 push now publishes a plugin branch; the session-file commits wait on the local branch for it. Nothing needed the other way: every local-only plugin branch that holds a deliverable commit already failed `push-scope`, so the only plugin branches the session-file push ever created were ones whose handoff had committed nothing. The cost is that the session-file commits on such a branch wait until a later handoff of it pushes it or the operator does; a handoff with nothing to commit removes a branch it cut instead of leaving it empty, and re-publishes a reused branch's unpushed deliverable (`phase-handoff.md` §2.3).
- **A refusal is final until the user says otherwise.** `[remote rejected]` in the push's `--porcelain` status records the refusal, and no later run pushes that branch — whatever reason follows it, save a reason beginning with the few words git or a host gives a push a concurrent update or a server fault broke (`failed to update ref`, `unpacker error` and the like), which is retried. Before, each run retried, was refused, and left another commit on the local branch. On the default branch the record also turns session-branch mode on ([session-branch](#session-branch)).
- **Merged means merged by any of the three ways a pull request lands.** `branch-merged` adds a rebase test (`git cherry`, every line `-`) and a squash test (the branch's whole change found by patch id among the default branch's commits) to ancestry. B2 and `phase-handoff.md` §2.2 rule 3 share it. **A fourth test, by content, since 2026-10-26** (batch B01): a patch id hashes each hunk's context lines, so a squash whose commit landed after the default branch changed a line within three lines of one of the branch's hunks read unmerged by both, for good — measured on a 30-line file, the branch changing line 10 and the default branch line 12 before the squash, where a change to line 25 matched — and the next run stayed on the merged branch and its handoff recreated the branch the host had deleted. `git merge-tree --write-tree <default-ref> <ref>` printing `<default-ref>`'s own tree says merging the branch changes nothing, which drift cannot defeat; it read merged there, and unmerged on the same branch before its squash. It still reads unmerged where the default branch changed a line the branch changed again, or the merge needed a conflict settled by hand.
- **A copied file is never a session file.** §2.1's shapes matched any path under the specs tree, so a customer's `implementation.md` under `brd/source/`, or a page `/idea` vendored under `attachments/` as `release-notes.md`, went into the prompt-free bookkeeping commit. The classifier now excludes `workflows-core:addressing` §2's reserved subdirectory names, all but `dev-workflows/`.
- **A commit stranded on another plugin branch is retried** — where `origin` has that branch; since 2026-10-27 one it lacks keeps its commits until a handoff or the operator pushes it (above). §3.4 retried only the branch the run stood on, and B4 switches away right after the flush commits.

**Measured, and the reason a protected default branch was not fixed here:** git refuses to fast-forward over a working copy of a file the incoming commits add or change, even when the copy is byte-identical, untracked or tracked (git 2.43). Most session files are appended across sessions — the feedback file per PRD, `follow-ups.md`, `implementation.md`, `resume.md` — so any design that commits them somewhere other than the checked-out default branch, while their copies stay in its tree, stalls the default branch's catch-up as soon as that commit is merged. One that commits them on the local default branch and pushes them elsewhere diverges it from the remote the first time a teammate merges. The next round designed it, as an overlay in the main checkout rather than the second checkout first proposed here ([session-branch](#session-branch)); a refused push of the default branch is still recorded, and the record now turns that mode on.

**Refused, with the reason:**

- *Pushing where git itself would push (`@{push}`).* On a fork that is the user's fork, which nothing in this reference reads, so the next run's catch-up and merge tests would not see what was pushed.
- *Anchoring the §2.1 shapes to key-shaped folder names.* `workflows-core:addressing` §4 reads a folder's kind and key off its carrier, never its name, and an `@<path>` address can name a folder of any name, so a session file in an ordinary folder such as `specifications/my-feature/` would have been left dirty forever, firing G1 on every run. The reserved-name exclusion that was taken has the same cost only for a feature folder placed beneath a directory with a reserved name, a layout `addressing` §2 does not define.
- *Recording only a hook's refusal (`… hook declined`).* That is git's own wording for a refusing hook, but GitHub's rulesets refuse with `push declined due to repository rule violations` and Azure Repos' policies with a code of their own, so an allow-list retried them on every run, the defect being fixed. A deny-list of the few transient reasons errs the other way, on a host's own transient wording, and the line says how to remove the record.
- *Deleting a branch merged by squash or rebase.* `git branch -d` cannot see such a merge and `-D` is forbidden (§1 rule 4), so B2 names the command and the user runs it.

## session-branch

**Session files on a specs repository whose default branch takes no push (2026-10-06).** Before it, every run committed its session files on the local default branch and pushed them; on a protected one the push was refused, the interim recorded the refusal and stopped retrying, and the commits piled up on a local branch that diverged from `origin` the first time a teammate merged anything, after which the catch-up stopped working. Runs that open a deliverable branch were never the problem; every run that stands on the default branch when it commits was.

**Measured (git 2.43):** `pull --ff-only` and `switch` refuse to overwrite a working copy of a file the incoming commits add or change, byte-identical or not, so a session file left in the tree blocks the catch-up the moment the commit carrying it is merged. `git merge-tree --write-tree -X ours`, with `merge=union` for the appended shapes in the repository's own `info/attributes`, merges a teammate's appended entry and the user's own without a checkout and keeps the session side of an overwritten file — where the two entries share no line; *Amended by LC11* below says what `union` does to two entries that do, and what replaced it. A commit can be built on a branch nobody stands on through a temporary index, `commit-tree` and `update-ref` with the old value. `commit-tree` reads no `commit.gpgSign`.

**The user's decisions:** the files reach the default branch through a pull request from a per-user `session/<identity>` branch; an *overlay* in the main checkout, so no emitter or reader changes; the mode turns on automatically at the first refused push and by an opt-in key (`workflows.sessionBranch`) for a team that knows in advance; the user opens the pull request from a printed `gh pr create` line, the steps staying prompt-free; and the plumbing lives in one self-tested script, `workflows-core/scripts/session-branch.py`, whose selftest pins its classifier and identity exclusions to `specs-repo-git` §2.1 and `branch-naming` §4.

**Amended during planning:** `commit` builds on the tip the working copies came from and merges the default branch second, since writing working copies over a merged tip deleted the entries the merge brought; a new session branch starts at `merge-base HEAD <default-ref>`; `sync` defers while a dirty session file is not on the branch; the preflight ends with `put-back`; a branch that holds nothing of its own is fast-forwarded; and the overlay's paths include those where the branch differs from HEAD, without which a deleted overlay-only file was never committed as a deletion and came back.

**Amended during execution, each found by a test or a walk-through and fixed test-first:**

- *`sync` also merges `origin`'s copy of the session branch*, which a second fetch refreshes. The same identity on a second clone or machine otherwise built a branch that could never fast-forward onto the one it had pushed.
- *A remote that deleted the session branch does not stop its push.* Delete-on-merge is common, and §4 step 5's deleted-branch rule would have kept every later run's files local for good.
- *`push-scope` counts the default branch as published* and checks the branch's whole change (`<default-ref>...<session>`) for ARTIFACT paths only. Measured: listing against the session branch's own remote ref alone listed every teammate commit the merge brought in, and the first merge after the default branch moved blocked every later push. The line counts session files not yet landed, not commits, which a squash merge leaves counted.
- *The stranded commits are dropped with `lift` then `reset --keep`.* Measured: `reset --keep` alone aborts over the overlay, and a mixed `reset` leaves a teammate's newer deliverable stale in the tree.
- *A working copy of an appended shape that lost the branch's entries is merged with the branch's version* (base `merge-base HEAD <tip>`; by `merge-file --union` then, and since LC11 by entry set for a block-shaped file, as *Amended by LC11* below says), never written over them — a manual `lift` then a ticked follow-up did that. HEAD as the base read a stranded commit's entry as deleted on the branch; the selftest caught it.
- *`commit` and `put-back` refuse while a worktree has the session branch checked out*, and sign where the user signs.
- *A commit never takes a missing overlay for the run's own deletions.* Review round 1 found every direct `/implement` run inside the specs repository, the stranded-commit remedy and a switch back from the session branch deleting session files from it: after a `lift`, an overlay-only file is absent and a tracked one is HEAD's, which a commit read as the run's intent. A working copy that is HEAD's version, or the version this worktree was last given, is now never committed, and an absent session file is a deletion only under `dev-workflows-cost/`, the one session file a run deletes, and only where HEAD holds it or this worktree held it; any other is put back, a tracked one removed by hand included. The script records path and version per worktree. Round 2 found the record taking a stranded commit's clean file as held, a lift a lock stopped partway leaving removed files held, and a second worktree's stale copies undoing the first's relocation; round 3 found a lift stopped partway leaving present files unrecorded, so a later relocation was undone. Each path now leaves the record just before `lift` touches it, and `put-back` records a copy already in place.
- *Overwritten shapes are `-merge`.* `!merge` leaves the attribute unspecified, so `resume.md` got a line-by-line text merge that can splice two overwrites together; unset keeps the session side whole.
- *`require-on-main`'s row C′ does not count session files in the mode*, or every consumer would stop on the overlay; `/implement`'s direct run lifts again before its code commit; moves run unwrapped where no identity names the branch; a guard-ended preflight still puts back.

**Amended by LC11 (2026-10-28): `union` now merges `follow-ups.md` alone, as a line set, and every block-shaped session file is merged by entry set.** `union` matches lines, not entries, so two distinct entries that share lines become one, and git exits 0 (`docs/superpowers/verification/2026-10-27-lc11-measurements/review-of-first-draft.md`, t2–t3, on the family's real formats): two same-day `/implement` blocks on one unit, each `pushed: true`, became one block, the later run's header gone and the teammate's `pushed: true` lost; two feedback entries of one date, command and category became one, its YAML holding `id:` and `author:` twice. The defect reached every team in the mode with two same-day entries in one appended file. A block-shaped file — `implementation.md`, `_security.md`, the feedback and cost files — is a header followed by entries, each from its format's dated `## ` heading to the next, and now settles as one side's version followed by each entry of the other's that it lacks; it is refused where the headers differ, where an entry of the merge base was edited or removed on one side alone, or where the versions' line endings differ (`specs-repo-git` §8.2 step 3). A merge still runs `merge-tree -X ours`, which keeps an overwritten file whole, but every block-shaped path both sides changed is then replaced by the entry-set result, whatever `merge-tree` wrote: with `union` gone, `-X ours` alone would take the session branch's side, and the session pull request would delete the teammate's entry. Where the rule refuses, that source is not merged at all and the path is listed in `sync.conflict`; a working copy the rule cannot settle with the branch's version stays out of the commit, as it is in the working tree, and is listed in `unsettled`, since committing it would drop the branch's entries. The marked `info/attributes` block names no block-shaped file any more, and the script rewrites it on each clone's next run, so a merge the user makes by hand stops on a conflict rather than fusing two entries. `follow-ups.md` keeps `union`, since each line is a whole task: a line ticked on one side beside the other's append comes back beside its open copy, a visible duplicate, and versions in mixed line endings are refused, since `union` would keep each task in CRLF beside its copy in LF. `specs-repo-git` §4 step 6's replay, outside the mode, settles both shapes by the same two rules ([specs-push-scope](#specs-push-scope)).

**Refused, with the reason:**

- *A second checkout of the session branch.* Every reader of `implementation.md` and `follow-ups.md` would learn a second root, and the operator's drafts would sit in a hidden directory.
- *Per-session files.* It changes the format every reader depends on.
- *Opening the pull request, or asking once.* These steps are prompt-free and never open one.
- *Moving the user's default branch to drop the stranded commits.* A `reset` the plugin never runs (§1 rule 4); the line names it.
- *A session branch on every repository ("always PR").* Considered twice and declined: the machinery is the same size either way, and what it adds is a standing pull request per person on every team, `implementation.md` reaching a teammate's `/document` only after that merges, and the overlay on every repository rather than the ones that need it. A team that wants the pull-request flow sets `workflows.sessionBranch`.

## entry-descriptions

**Command, agent and skill descriptions (2026-10-06).** Every installed plugin's command and skill descriptions share one listing in each session's context, and Claude Code bounds it. **Measured in the 2.1.288 binary:** the listing gets a fraction of the context window (`skillListingBudgetFraction`, default 1%), each description is cut at `skillListingMaxDescChars` (default 1,536), and "when the listing exceeds this, descriptions are shortened to fit" — every plugin's, not only the long ones. A survey agent saw ten of this family's commands listed with no description at all and another cut mid-sentence. Before this check the family's descriptions totalled 32,355 characters over 50 commands, 22,805 over 51 agents and 6,444 over 16 skills; ten command descriptions passed 1,024 (`/brd-split`'s reached 4,310), most of them narrating the procedure the body already carries.

**The rule:** a description says what the command, agent or skill does, when to use it and what it is not for, in about 500 characters (BMAD's Toolsmith canon, `6a0a068e`: a description that explains the procedure lets the model skip the body and improvise). **The thresholds are the user's** (2026-10-06): `scripts/validate-catalog.py` fails a description above 1,024 — the Agent Skills ceiling — and warns above 600. The 28 over 600 were rewritten in the same change, bringing the totals to 18,910, 21,063 and 5,875, measured on the change itself.

**Taken later the same day:** `disable-model-invocation` on every command only ever typed. It was first set aside here as a per-command audit for a gain only to prose requests; the 600 budget then left the listing over its budget, so the gain is the listing itself ([typed-only-commands](#typed-only-commands)).

## typed-only-commands

**Typed-only commands (2026-10-06).** The 600-character budget cut the waste and left the listing over its budget. **Measured in the 2.1.288 binary:** the skill listing gets the context window's token count × 4 × `skillListingBudgetFraction` (default 0.01) characters — 8,000 at a 200,000-token window, a subagent's included, and 40,000 at 1M — overridden by the `SLASH_COMMAND_TOOL_CHAR_BUDGET` environment variable or the `skillListingBudgetFraction` setting, and each entry is `- <name>: ` followed by its description and its `when_to_use`. This family's descriptions came to 20,997 characters (22,801 with their names), every other installed plugin's on top. Splitting a plugin changes nothing: the budget is per session, over everything installed.

**The listing holds only what the model may invoke.** An entry whose frontmatter sets `disable-model-invocation` — read as Claude Code reads it: the YAML value, as `1`, `true`, `yes` or `on` in any case — is left out of it, and the Skill tool refuses it unless the user typed `/<name>` in that turn's message ("cannot be used with Skill tool due to disable-model-invocation. Ask the user to run /<name> themselves"), while the typed slash command still runs. Measured on a probe plugin, Claude Code 2.1.288 with Claude Haiku 4.5: the flagged command ran when typed, was absent from the listing the model quoted, and was refused through the Skill tool; its unflagged sibling was listed. **Where a command and a skill share a name** the listing holds one entry: the command's, and the Skill tool runs the command, while the command is unflagged; the skill's, and the Skill tool runs the skill, once it is flagged. Flagging such a command only swaps its entry for the skill's — for `obsidian-llm-wiki`, whose ten commands each wrapped a same-named skill, that would have grown its share from 2,400 characters to 4,184 — so those commands stayed unflagged until that plugin left the catalog (2026-10-26).

**The rule:** every command is typed-only unless a command, agent, skill or reference file runs it through the Skill tool, written `skill: "<plugin>:<name>"` with the Skill tool named just before it, or as `Skill(skill: …)`, outside a fenced block (a fence is printed, never executed; a bare mention of the form is no call, since a sentence forbidding the call carries it too) — on 2026-10-06, `/document` running `/docs-profile` and `/docs-init` running `/docs-brand` — or its plugin ships a skill of the same name. `scripts/validate-catalog.py` fails a command that is none of these, and a flagged command or skill some file calls; it reads a call only in that form, which is why `/docs-init`'s Phase 5 now writes it so, and it names a plugin by its manifest, as Claude Code does. A command that used to hand the run on to a flagged one now stops and names it for the user to type — `/create-prd`'s pickers for `/update-prd` — and `session-cost.py` cuts no window at a Skill call the tool refused. The family's descriptions fell from 20,997 characters to 4,975 (22,801 to 5,555 with their names), measured on the change. **The cost:** a request in prose ("implement EPIC-1") no longer starts a family command; the user types it, and each getting-started page says so.

**Where everything else still overflows it**, the user raises the budget: `skillListingBudgetFraction` in `~/.claude/settings.json`, or `SLASH_COMMAND_TOOL_CHAR_BUDGET`. Every getting-started page and the repository README say what to set and how to check it: `claude --debug` writes `Skill listing over budget: <N> skills, <X> chars > <Y> budget` to `~/.claude/debug/latest` (measured). An estimate from plugin files alone is not enough — on the maintainer's machine it gave about 34,000 characters where that log, with `0.025` set and the pre-change versions installed, read 130 skills and 48,396 characters, Claude Code's bundled skills and the user's synced and personal skills making up the difference — so the pages give the check, not a number to trust. The budget is not reserved: a session pays only for what is listed.

**Not taken:** descriptions short enough to fit as they were — about 150 characters each, which strips the "when to use" and "not for" clauses the 600 budget keeps, and still overflows beside any other plugin. The Agent tool's list of agent descriptions (21,063 characters) is a separate list with no such budget, and is not the overflow.

## ssh-alias-host

**An SSH host alias is resolved before a pull request's repository is named (2026-10-07).** `workflows-core:phase-handoff` §2.6 and `dev-workflows:code-handoff` §2.6 keep a remote's host whenever it is not `github.com`, so that a GitHub Enterprise remote is never sent to github.com. **Measured on the first end-to-end run of the family on a test project:** the specs remote `git@github-ig.com:ihudak/bookstore-specs.git` names a `~/.ssh/config` alias whose `HostName` is `github.com`; the push over it succeeded, the derivation produced `github-ig.com/ihudak/bookstore-specs`, and `gh pr list -R` failed with `error connecting to github-ig.com`, so no pull request opened and the run blamed `gh`. `gh` resolves aliases only when it reads a repository's remotes itself, never in `-R`. `ssh -G <host>` prints the configuration ssh would use without connecting, its `hostname` line the real host; it runs only for a non-`http(s)` remote and a plain hostname, so the remote's text never reaches `ssh` as an option. `github.com` itself is never resolved, because GitHub's documented port-443 setup (`Host github.com`, `Hostname ssh.github.com`) would rename it, and a resolved `ssh.github.com` reads as `github.com`. The same derivation governs `require-on-main` §3.5's pull-request probe, `/promote-decisions`' and `/harvest-decisions`' `gh` calls, and `docs-workflows:finish-and-handoff` §4's host classification, which `/document`, `/docs-profile`, `/docs-brand` and `/docs-init` use.

**Not taken:** resolving the alias inside `<docs-repo-slug>` (`workflows-core:specs-repo-git` §2.1), which reuses the same expressions. The slug names a folder earlier runs already wrote, and it must be computable from the remote's text alone; resolving it would move an alias user's documentation record to a new folder and make the name depend on the machine's ssh configuration.

## refusal-record-file

**The push-refusal record is a file, not configuration (2026-10-07).** `specs-repo-git` §4 step 6 recorded a refused push as `branch.<branch>.workflowsPushRefused` in `.git/config`, and that record is what stops a later run pushing into the same refusal and what switches a clone to session-branch mode (§8). **Measured:** the family's own container hardening mounts `.git/config` (with `.git/hooks` and `.git/commondir`) read-only, because a configuration setting can start a program, while the rest of `.git` stays writable. There the write fails, nothing is recorded, every run pushes and is refused again while commits pile up locally, and session-branch mode never switches on. The record is now `workflows/push-refused/<branch>` in the common git directory (`rev-parse --git-common-dir`, joined to the repository's path where it is relative), standing wherever the file exists and holding the date; the old key is still read, so a clone that recorded a refusal before keeps it, and still written where the file cannot be, so nothing that recorded a refusal before stops recording one. **Not `--path-format=absolute`**, which needs git 2.31: an older git echoes an option it does not know and exits 0, so the path would carry the option's text and the record could never be written, a regression for every user of git 2.23 to 2.30 (measured by the review on a simulated unknown option). The opt-in `workflows.sessionBranch` stays configuration — the user sets it, on the host where `.git/config` is read-only in the container.

**Not taken:** a file under `.git/info/`, which belongs to git; and keeping the configuration key with a reported failure, which leaves automatic detection dead in every hardened container.

## specs-git-state-record

**Why the run's state record lives under `~/.claude`, keyed by the session and the command (GIT-G1 part 2a, 2026-11-09, `docs/superpowers/plans/2026-11-09-git-g1-part2a-start-end.md`).** Part 2a runs `specs-repo-git`'s `specs-preflight` and `commit-artifacts` in `scripts/specs-git.py`, called at a run's start and at its end, and what the end needs from the start — the run key set, the flags and the notice that set `specs_git: misrooted`, the guard block it repeats, the branches it left — was carried until then only in the conversation, where a compaction can lose it. So the script keeps it in a file, `~/.claude/dev-workflows/specs-git/<session id>/<command>.json`, as `specs-repo-git` §7's *The run's state record* states.

**The design's candidate was the specs repository's git directory**, as `/dev-workflows:implement`'s `run-state.py` keeps its file in the code repository's (`git rev-parse --git-path dev-workflows/implement-run.json`). Two facts moved it. `specs-repo-git` §3.1's gate fails exactly where that directory is missing or unwritable — `$SPECS_PATH` unset, not a repository, a read-only mount — yet a not-a-repository `$SPECS_PATH` with a `specs-root-check` signal still sets `specs_git: misrooted`, whose notice `end` must repeat, so the record has to be writable where the repository is not. And nothing outside every repository is ever staged, so no staging rule has to learn to leave it alone.

**The key's session half is `CLAUDE_CODE_SESSION_ID`.** Claude Code's environment-variables page (https://code.claude.com/docs/en/env-vars) documents it as set in Bash tool subprocesses, equal to the hook input's `session_id`, and updated on `/clear`; it is also the transcript's basename, the `session_id` `cost-emission` §1 derives by scanning transcripts (both checked on 2026-11-09). The page's caveat — that `--continue` or `--resume` without an explicit id may hand an MCP subprocess the startup id — concerns MCP subprocesses, which never run the script. The id survives a compaction, which the conversation's text does not.

**The command half** keeps a different command typed in the middle of another's run — `/feedback` during a `/specify` — off the outer run's record (the plan review's finding m4): one file per session and command, so the inner run's `start` opens its own and its `end` removes only that. The same command typed twice shares that file, and is kept off the outer run's record by parking and `--started` (2026-11-10, [stay-landing](#stay-landing)): its `start` parks an open earlier record under that run's `started` stamp, and each run's `end`, `declined` and `replay`, and its `start` on a re-run or a continuation, name the run's own record by `--started` — any stamp the run's starts printed, a re-run keeping the earlier ones in `started_before` — save the skill's remake of a first `start` that returned no JSON, which names none and takes up only a record marked `call_returned: false` ([stay-landing](#stay-landing)).

**The family's precedent** is the cost subsystem's: the checkpoint `~/.claude/dev-workflows/cost-state/<session_id>.json` and `cost-emission` §13.1's deferred file beside it, both per session, both outside every repository.

**Why it is safe**, as `specs-repo-git` §7 states it: it lives outside every repository, so no staging sees it, and `run-state.py remove`, which removes files in the code repository's git directory, cannot reach it. One file per session and command keeps two sessions on one specs repository apart. A nested run is another command, and starts only after its parent's `end` (`specs-repo-git` §4's exception: `/product-workflows:brd-split`'s *Ground now*). A subagent carries its parent's session id, and no agent runs either entry point — `grep -lE 'args: "specs-repo-git (specs-preflight|commit-artifacts)|workflows-core:specs-git' plugins/*/agents/*.md | wc -l` returns 0. A run started `--inline` by another command calls neither. A run whose id changes before its end — a `/clear`, or a resume that hands it a new one — finds no record, and its `end` runs as a run with no preflight does, on the flags the run passes, and compares no `Environment:` line, since that comparison needs the record: §3.1's placement tests and the tail's `env-check` still guard it.

**Pruning.** Each `start` removes every other session's record more than seven days old, and each session directory that leaves empty; the current session's records are kept whatever their age. A record outlives its run only where no finished `end` read it — a crash, a closed session, or a session id that changed before its end — and nothing reads a record of another session.

**Where `CLAUDE_CODE_SESSION_ID` is unset**, the script runs neither entry point (exit 2, nothing done) and writes no record, and the run follows `specs-repo-git`'s prose, as every run did before 2a. The cost of a harness without the variable is the reference read the script was built to save, and the end's comparison of the `Environment:` line, which needs the record: a run that hands nothing off and writes nothing in its tail commits there even where its environment changed, which the tail's `env-check` catches for every other run. It is never a commit the pre-2a prose would not have made.

## stay-landing

**A run whose preflight stayed on a plugin branch it would have left lands its own session-file change on the default branch, without moving the checkout, because committing it on that branch puts it into a pull request it has nothing to do with, and holding it uncommitted leaves it where git refuses to carry it across a later switch (STAY-2 and MIDRUN-B4, 2026-11-10, `docs/superpowers/specs/2026-11-10-stay2-midrun-design.md`).** Landed by plumbing, the files reach the maintainer the way every session file does. `specs-repo-git` §4 step 1 states the landing, §3.2 the held stage and §3.5 the run typed mid-run. The maintainer's decisions S1–S4 (2026-11-10) are in the design, its evidence in the research memo beside it, `2026-11-10-stay2-midrun-research.md`, and the measured cases below in the plan's reviews and the build's task reviews.

**STAY-2: an unrelated pull request.** Where the preflight had to stay on an unmerged plugin branch no key of the run names — G1 fired, git refused the switch, `status` could not run, or the preflight stopped before the switch — the terminal commit put the run's session files (cost, feedback, follow-ups, `resume.md`) on that branch, and step 5 pushed them into its pull request. G1 on another key's branch is the usual state after a declined handoff, and it fires on every later run, so every later run added a commit to an unrelated pull request. Skipping the commit fixes nothing: §3.4's flush commits leftover session files on the branch HEAD stands on, so the next run's flush would have committed them there instead.

**D5's hold, which git 2.43 refuses to carry.** 2a's D5 held a merged-branch stay's files uncommitted for the next run's merged-branch leave. Measured on git 2.43: git refuses to switch over a modified file whose copy in the target commit differs from HEAD's, and over an untracked file the target commit holds, even where the working copy is byte for byte the target's. So the leave was refused whenever the default branch had changed those files since, and the next flush committed them on the merged branch, the outcome D5 existed to prevent. S2 replaced the hold with the same landing: one rule for a merged stay and an other-key stay.

**The attribution by snapshot.** Whatever was dirty when the run's start took its snapshot — an earlier run's leftover, or an open run's work in progress — is not the run's own. The landing builds `c1`, HEAD's tree with the snapshot's versions, and `c2`, `c1`'s tree with the working copies now, and lands the change from one to the other. **A three-way merge of `c2` on `c1` was replaced by a per-path apply, `session-branch.py`'s `own_change`** (the plan review's finding C1). That merge read everything `c1` holds and `onto` lacks — the snapshot's lines, and the branch's own committed content — as deleted on `onto`, and every path the run also changed as changed on both sides. Measured with the planned construction: a `follow-ups.md` whose `onto` held one line, whose snapshot added an open run's line and to which the run added its own, replayed to all three, the open run's line committed under this run's message; and a block-shaped cost file was refused outright (`conflict`), so every such landing would have been held for good. The apply starts from `onto`'s version of each path the run changed and adds only what `c2` holds and neither `c1` nor `onto` does; the plan's re-review ran the same two cases against it, and the run's line alone, and the run's entry alone, landed (its E1 and E2). Nor does it need git 2.40's `merge-tree --merge-base`.

**The drop rule: nothing of the branch's own content reaches `<default>` ahead of its pull request.** The plan's first rule let an edit of a line or entry only the stayed branch held land as a copy. The plan's re-review measured where that went: a follow-up the branch had committed, ticked by hand, landed on `<default>` ticked beside the run's new line, and the branch's pull request then conflicted on the file (E3); a hand removal of a branch-only follow-up line (E8), and a run's removal of a branch-only block entry (E9), reached no branch, and the lift wrote the removed line or entry back — the removal lost. So a change that drops a line or entry `c1` holds and `onto` lacks is refused (`dropped`, `edited`) and held alone, a cause that will not pass, while the rest lands; `follow-ups.md` gains a second copy only of a line `onto` already holds, `followup-emission`'s two-copies case. A path the run adds or changes under a feature folder `c1` holds and `onto` holds nothing under is refused too (`folder-gone`), since writing it would bring back on `<default>` a folder a teammate removed or renamed, or plant there one only the stayed branch has: Task 1's review measured a modified cost file, `follow-ups.md` and `resume.md` under such a folder landing and recreating it, while the rule still covered added paths alone. The cost is a held path in a rare case, which the user settles with the commands its line prints.

**No local branch another worktree has checked out is moved** (the plan review's finding C2). Measured: with `main` checked out in a second worktree, `git update-ref refs/heads/main <a teammate's commit> <old>` exits 0, and that worktree's `status` then shows a staged reversal of the teammate's commit, its HEAD ahead of its index and files, so a commit there reverts the teammate's work. The landing tests for such a worktree under the ref's lock; where one has `<default>` checked out, it builds on `<default-ref>` and pushes the commit by refspec, leaving the local ref for that worktree to pull — measured in the plan's re-review: local `main` unmoved, the other worktree's `status` and `diff --cached` empty, its later `pull --ff-only` exiting 0 (E7). **Where `<default-ref>` names no commit** — an `origin` without `<default>` — nothing is built or pushed on that path, and the change is held (`origin-lacks`), a cause that will not pass: Task 5's first re-review found the path building on local `<default>` there, its refspec push skipping the scope test, and confirmed by probe that it published a user's unpushed commit to `origin`.

**Why the lift is needed.** Once `<default>` holds the change, each path whose working copy is still exactly what landed is written back to the version the change started from. Without it, git refuses every later switch to the default branch over those copies, byte-identical or not (git 2.43, as above), and the next flush commits them on the stayed branch again — STAY-2 once more, a run later. It is the second discard `specs-repo-git` §1 rule 4 names, and it discards only content it has just found on `<default>`.

**The pull-request conflict a landing can cause.** A landing that appends to a file the stayed branch also changed makes that branch's pull request conflict on it, in content (E3) or add/add for a file new on both (E5, measured where the file's folder too was the branch's alone, a shape the folder rule above now refuses). The remedy is the one `phase-handoff`'s *Row B′'s remedy* gives for a file the plugin commits beside the documents: merge `<default>` into the branch and keep every line either side holds.

**Why not session-branch mode.** The research memo weighed three forms of it (its option C). Turning the real session branch on for the run puts a session branch and a session pull request on users who never opted in, commits nothing where no identity names the branch, and leaves an overlay that goes stale once the mode is off, which the next flush would then commit as leftovers. Committing onto the default branch through `session-branch.py`'s `commit` would carry the stayed branch's own unmerged entries there, since that call takes its base from `merge-base HEAD <tip>`. Turning the mode on for good at the first stay changes every such user's workflow to a session pull request. And none of the three stops B4's switch under an open run. What the landing reuses from §8 and §4 step 6 is their plumbing.

**Held commits.** A landing that cannot be made now — an `index.lock` at its start, a ref's lock, `<default>` moved twice while the run committed on it, or another worktree's checkout of `<default>` with no refspec push to make — is kept as a commit under `refs/workflows/held/`, listed in a per-worktree record, its files left in the working tree; a later preflight's held stage, which runs before the guards so that G1 holds none of it back, lands it, or, on `<default>` or in session-branch mode, drops the hold and leaves the files to that run's own commit. The held stage also pushes `<default>` where HEAD is not on it, outside session-branch mode: §3.4's retry covers only the branch HEAD stands on and the settle loop runs only past the guards, so while G1 persisted nothing would have retried a landing whose push failed. Held entries chain only on a shared path (the plan review's M2): in one strict order, an entry refused for good would have stalled every later landing, on any path, for good. A refusal is per path: the refused path is held alone, and the rest lands. A cause that will not pass is reported on every later run until its hold is dropped, with the commands to see the change and drop the hold, and never promised to land.

- **The held stage's budget.** The Task 6 review reproduced a resumed held stage retrying, and printing again, an entry already settled in the same start: at `--budget 0` the probe's six calls each named `start --resume`, and none reached the second entry. At the default 480 s budget, it reckoned, about six entries failing against a hanging `origin` — each remote retry checks a 94-second cost — would keep the stage from ever finishing. So a start remembers the entries it has tried, and spends its budget on each at most once.
- **A stuck entry holds nothing back.** Task 6's first re-review reproduced a resumed stage in which a stuck entry held back a later, transient entry on its path and lent it its own permanent refusal, so the transient one never landed. Only a transient refusal holds later entries back.
- **An `index.lock` at the end holds the landing.** A landing that met the lock used to return *Locked* with nothing held, so its files stayed dirty and unheld, and on an `unkeyed` stay the next run's flush committed them on the stayed branch — the bug this batch fixes (Task 3's fourth re-review, N16). The change is now held for `locked`, a cause that passes: `c1` and `c2` are built through a temporary index, and neither the held ref nor the held record takes the index's lock. While a lock stands the held stage lands and lifts nothing, since the process holding it may be committing on the branch HEAD stands on, which a lift would race; it still drops entries on `<default>` or in session-branch mode, since a drop touches neither the index nor a working-tree file.

**A run typed mid-run (S3).** A command typed while another run of the same session waits on the user ran its own preflight on the shared checkout: a keyless one — `/feedback` in the middle of `/specify` — flushed the open run's in-progress session files under its own message, then B4 switched the checkout to the default branch under that run, which went on from the wrong branch. Now the start reads the session's other records, and where one is open on HEAD's branch, its preflight and its end switch nothing and move nothing under that run — no flush of HEAD's dirty files, no merged-branch leave, no catch-up and no retry of HEAD's push. Its own change is told apart by the same snapshot and committed apart from that run's files: by the landing, where it holds a stay, and otherwise by **the here form** (the plan review's M1). On a branch it would not leave — the default branch, a branch of its own key, or a branch of the user's — the change is applied onto HEAD's branch, that branch is moved by `update-ref` from the tip the commit was built on, and `restore --staged` runs over exactly the paths the commit carried whose index entry nobody has staged anew, so the index follows HEAD with no file written. On the default branch that is S3's `<default>` literally; on a branch of its own key it keeps §4.1's rule that a keyed run's session files ride its own branch, a cost told to the maintainer with M1.

- **The journals.** Both of the here form's steps are journalled before the ref moves, in the held record and in the run's state record (`end_commit`), and a run by hand journals in the held record too, through the same `land` call, since a recovery made after a kill between the two steps could not otherwise know which paths to restore. `end --resume`, or the next preflight's held stage, finishes a journal only where its move is verified: a lift after a kill before the move would discard the run's change (the plan's final check, F2).
- **What it does not move.** The here form's commit is not pushed while the open run stands, since a push `origin` rejected would go to §4 step 6's replay, which moves the checkout under that run; the next push of that branch carries it. It refuses whole and holds nothing, unlike the landing: a held entry lands on `<default>`, the wrong place for the files of a branch B3 or G2 kept, and the open run's own terminal commit takes them anyway. Where the run's start took no snapshot, it commits nothing while the open run stands (Task 3's fourth re-review, N17), since nothing then tells its files from that run's. In session-branch mode it still switches nothing, but §8.2's commit takes every file the overlay holds, the open run's among them: the mode is unchanged, and keeps no snapshot apart.
- **The protection's end, and its accepted cost.** It ends when its command runs again in the session, when HEAD leaves the branch, at `/clear` (a new session id), at the open run's own `end`, or 7 days after it started (S3). An abandoned run — stopped with Esc and never ended — therefore holds the preflight and the end of every later run of the session's other commands on its branch until one of those.
- **HEAD's leave is read from HEAD's reflog**, as a `checkout: moving from <HEAD's branch> to <another branch>` entry since the open run's `started`, so a leave and a return still end the protection, with no write to another run's record: a test of where HEAD stands now would protect again on the return, and one a later command observes would depend on whether one ran in between. The entry names HEAD's current branch, not the branch the open run recorded: Task 3's first re-review verified on git 2.43 that the open run's own handoff writes `checkout: moving from <recorded branch> to <its branch>`, and reading that as a leave would end the protection of every run that handed off onto its own branch — MIDRUN-B4 again. A move from a branch to itself never counts, and where no reflog can be read the protection holds while HEAD stands on the branch.
- **A parked record protects nothing** (the plan review's M3). The same command typed twice parks the first run's open record under its `started` stamp rather than replacing it, and the parked record keeps serving that run's own end but no longer protects its branch: S3 ends the protection when its command runs again, and the park is that moment. A parked record that went on protecting would leave, after an abandoned middle run of three, the oldest run protecting a branch its command had since been typed on again; `protects: false` is written with the park.
- **A re-run carries its first start's reading** (Task 7's review, I1, reversing a ruling that had suppressed a re-run's switch back under a later-started open run). Measured: a `/document` re-run that read the open runs afresh took a `/specify` run started after its first start as its open run, and its end's here form committed that run's in-progress line as its own, under a row saying it had not, since its carried snapshot predated that run. S3 protects a run from the commands typed after it, so a re-run keeps the open run its first start read, re-tested as the end re-tests it, and never takes one started later; a run typed mid-run switched nothing, so it holds no branch to switch back to. Only a re-run that finds no record of its own reads afresh, which can only protect more.
- **The run's own handoff is left to GIT-G1 Part 3** (S4). Where it moves HEAD off the branch the run started on — measured in Task 7's review onto a branch a key of the open run names — the end commits as any run whose HEAD moved, the open run's files among them where that run stands there too. Part 3 scripts the handoff, which can then hand off and switch back.

**`end` with no start.** A run that stopped before its preflight, ran `--no-preflight`, or has only a declined handoff's record has no snapshot. The plan's re-review (N3) found such an end fast-forwarding HEAD's branch under an open run and committing that run's in-progress files under its own message — MIDRUN-B4's first harm. So it reads the session's records first, this command's own other records included, and where one is open on HEAD's branch it writes nothing and says that run's terminal commit takes the files.

**Which record a run is.** `start`'s JSON names its record's `started` stamp, and `end`, `declined` and `replay` — and `start` on a re-run or a continuation, save the one continuation `call_returned` serves (below) — take it back as `--started`, so two runs of one command each end on their own record, in either order (the plan's re-review, N1). A re-run keeps its earlier stamps in `started_before`, so a run reaches its own record by any stamp its starts printed: a re-run the harness stops before its JSON has saved its record under a stamp its run never learned, and a remake naming the earlier stamp would otherwise find nothing and start a record beside it. A re-run cut off between saving its record and removing the file it re-ran from leaves that file behind; no read takes it, and the record's next save or removal deletes it.

- **Every start-side `next` names its record by `--started`.** Before it, a `start --resume` the script handed back named no record where its run's call had been given none, so one made more than 15 minutes after the record's last save started afresh and set the run's own record aside — a replay that hangs to its 600-second timeout, then a second call, can pass that. Task 8's third re-review measured `t_midrun_open_next_aged` failing on the code before the change: `replaced` set, and the end handing over a replay under the open run.
- **`call_returned`** exists for the one continuation that names no record: the skill's remake of a first `start` whose call returned no JSON, so that its run never learned the stamp. A record is marked `call_returned: false` only from the first write of a plain start, or of a continuation given no `--started`, until that call returns its JSON, an error's included, and the remake takes up only a record so marked and made with its own arguments, meeting any other as a plain start does — parking it where it is an open run. Task 8's third re-review found the mark also left by named calls and by an error path, so another run's remake with the same arguments could have taken a named run's record over; its fourth confirmed both fixed.
- **The accepted upgrade-window edge.** A record written before the field existed loads as returned, so an unnamed remake within 15 minutes of a plugin update parks the run's own record rather than going on with it. Task 8's fourth re-review found what parking costs: it moves only the state record — the working tree, the held refs and the held record are untouched — losing the stopped start's progress and the protection of a run typed under it, never files. Going on with such a record instead could land a run on another run's record, since nothing in it tells the two apart.

**Not covered: two sessions on one checkout** (the plan's P18). Each session's records are its own, and reading every session's would make other sessions' week-old runs look open.

## skill-listing-figure

**The skill-listing figure in the repository `README.md` and the getting-started pages, and how to measure it (2026-11-09).** Those pages say how many characters every plugin of the marketplace, installed together, adds to Claude Code's skill listing ([typed-only-commands](#typed-only-commands)). No recipe was recorded with any figure the pages published: "about 5,600" at `649e8454` (2026-10-06), then, as `/prd-ground` entered the listing on 2026-10-12, "about 6,200" at `932623b7` and "about 6,100" at `8a438ead`, and "about 5,800" at `1f72f4fd`, whose message records 5,848 "with a YAML parser over the tree (19 entries)". Nothing re-measured it when `e003f181` (2026-10-26) took `obsidian-llm-wiki` out of the catalog, so it stood about 2,600 characters too high from then on.

**The recipe.** For each plugin `.claude-plugin/marketplace.json` lists, take each `skills/<name>/SKILL.md` and each `commands/<name>.md`; skip one whose frontmatter sets `disable-model-invocation` to `1`, `true`, `yes` or `on` in any case, as Claude Code reads it; where a command and a skill share a name, count one entry, the command's; and count each entry as `len("<plugin>:<name>") + len(description) + len(when_to_use) + 5`, the 5 being `- `, `: ` and the line break of the binary's format. A description written as a YAML block scalar (`>`, `|`) is read folded as YAML folds it. Run it from the repository root as `python3 -I <file> .`:

```python
import json, os, re, sys

root = sys.argv[1]

def frontmatter(path):
    text = open(path, encoding="utf-8").read()
    if not text.startswith("---\n"):
        return {}
    lines, fields, i = text[4:text.index("\n---", 4)].split("\n"), {}, 0
    while i < len(lines):
        m = re.match(r"([A-Za-z_-]+):\s*(.*)$", lines[i])
        i += 1
        if not m:
            continue
        key, value = m.group(1), m.group(2).strip()
        if value[:1] in (">", "|"):  # a block scalar: its indented lines, folded as YAML folds them
            style, body = value[0], []
            while i < len(lines) and (lines[i].startswith(" ") or not lines[i].strip()):
                body.append(lines[i].strip())
                i += 1
            value = "\n".join(body).strip()
            if style == ">":
                value = re.sub(r"\n(\n*)", lambda n: n.group(1) or " ", value)
        elif len(value) > 1 and value[0] in "'\"" and value[-1] == value[0]:
            value = value[1:-1]
        fields[key] = value
    return fields

def entry(plugin, name, path):  # "- <plugin>:<name>: <description><when_to_use>\n", or None where typed-only
    fields = frontmatter(path)
    if str(fields.get("disable-model-invocation", "")).lower() in ("1", "true", "yes", "on"):
        return None
    return len(f"{plugin}:{name}") + len(fields.get("description", "")) + len(fields.get("when_to_use", "")) + 5

total = 0
for listed in json.load(open(os.path.join(root, ".claude-plugin/marketplace.json"), encoding="utf-8"))["plugins"]:
    base = os.path.join(root, listed["source"])
    plugin = json.load(open(os.path.join(base, ".claude-plugin/plugin.json"), encoding="utf-8"))["name"]
    entries = {}
    skills, commands = os.path.join(base, "skills"), os.path.join(base, "commands")
    for name in sorted(os.listdir(skills)) if os.path.isdir(skills) else []:
        if os.path.isfile(path := os.path.join(skills, name, "SKILL.md")) and (size := entry(plugin, name, path)):
            entries[name] = size
    for file in sorted(os.listdir(commands)) if os.path.isdir(commands) else []:
        if file.endswith(".md") and (size := entry(plugin, file[:-3], os.path.join(commands, file))):
            entries[file[:-3]] = size  # after the skills: where a command and a skill share a name, the command's
    total += sum(entries.values())
print(total)
```
