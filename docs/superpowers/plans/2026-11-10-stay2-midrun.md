# STAY-2 and MIDRUN-B4 — a stayed run's session files land on the default branch; a run typed mid-run switches nothing — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A run whose preflight had to stay on a plugin branch it would have left commits its own session-file change on `<default>` without moving the checkout, and a command typed while another run of the same session is open on HEAD's branch switches nothing and commits only its own change — with D5's merged-branch hold, the record collision and D5's degraded leave fixed by the same mechanism.

**Architecture:** `specs-git.py` gains one landing primitive, `land()` — the run's own change taken against a snapshot the start records, replayed onto `<default>` with `session-branch.py`'s checkout-free plumbing, `<default>` moved by `update-ref`, then lifted out of the working tree — with a held commit under `refs/workflows/held/` where the landing is refused, retried by every later preflight. `start` records the snapshot and every stay (other-key, merged, mid-run) in the state record; `end` lands where HEAD still stands on the stayed branch; a run typed mid-run reads the session's other records, stays, and commits apart from the open run. The same command typed twice parks the open record instead of replacing it. Every new line is worded in SRG first and pinned in `specs_git_lines.py`; `land` is also a CLI primitive for SRG's prose fallback.

**Tech Stack:** Python 3 standard library; git ≥ 2.38, and ≥ 2.40 for a landing (`merge-tree --write-tree --merge-base`, as §4 step 6's replay — an older git holds every landing, with its reason); the gate chain of `.github/workflows/validate-catalog.yml`.

**Spec:** `docs/superpowers/specs/2026-11-10-stay2-midrun-design.md` (binding; the maintainer's decisions S1–S4 are settled), with its research memo `docs/superpowers/specs/2026-11-10-stay2-midrun-research.md` (evidence; the design wins where they differ). ## The maintainer's decisions (2026-11-10)

Quoted from the spec, §2; not reopened here.

- **S1** — A run whose preflight stayed on a plugin branch it would otherwise have left commits **its own** session-file change on `<default>` in the same run, **without moving the checkout**, and pushes it where §4 step 5 allows. It then takes that change out of the working tree on the stayed branch. Files already dirty when the run started are not its own and stay where they are.
- **S2** — D5's merged-branch hold is replaced by the same landing: one rule for a merged stay and an other-key stay. PR #182 merges with D5 as shipped.
- **S3** — A command typed while another run of the same session is open on HEAD's branch switches nothing, never commits the outer run's in-progress files, and lands only its own change on `<default>`. The outer run's protection ends when its command runs again, when HEAD leaves the branch, at `/clear`, at its `end`, or after 7 days.
- **S4** — A producer typed mid-run, whose handoff moves the checkout under the outer run, is filed with GIT-G1 Part 3 as owner; not fixed here.

## Review Focus

The five input classes the spec implies, no task's main tests exercise, and a person meets first; each has its test in the owning task.

1. **A session file edited by hand on the stayed branch between the run's start and its end**, including an entry only the branch holds (a follow-up the user ticked there). A person expects the edit never to be lost: it lands on `<default>` with the run's change, or the whole change is held with the files left as they are. Test: Task 4 `e_land_hand_edit`.
2. **Another worktree standing on `<default>` for a day**, so two runs in a row hold their landings, the second touching a file the first held, before that worktree leaves. A person expects both changes on `<default>` once, in order, and the file clean afterwards. Test: Task 2 `l_held_chain`.
3. **A kill between the landing's ref move and its lift, and no `end --resume` after it** — the session died and a new one starts. A person expects the files not to stay dirty for good, blocking every later switch. Test: Task 5 `t_held_journal`.
4. **An outer run abandoned with Esc, then an hour of other commands in the same session.** A person expects each of them to work, to say why it stays (naming the outer command), and `/clear` or a switch of HEAD to end it. Test: Task 6 `t_midrun_abandoned`.
5. **A git older than 2.40**, which cannot replay without a checkout. A person expects every landing held with the line naming the git version needed, nothing lost, and no later flush committing the held files on the stayed branch. Tests: Task 2 `l_land_cannot_replay`, Task 5 `t_held_flush_excludes`.

## Rulings this plan takes

The planner's calls where the spec left a choice open; each one's cost if wrong is what the final report names.

- **P1 — the noun.** SRG §7 already says "a nested run" for a run another command starts (`/brd-split`'s *Ground now*). The new case is **a run typed mid-run**, and the run it finds is **the open run**; its stay's kind is `mid-run`, and the code's names are `midrun`. Never "nested" for it, in SRG or code.
- **P2 — a run typed mid-run on a branch it would not have left** (spec silent; ambiguity 1 of the report). The spec's landing on `<default>` covers stays (§3.1 *When*: "a plugin branch it would have left"); S3's "never commits the outer run's in-progress files" also binds a run typed mid-run on the default branch (B1), on a branch a key of its own names (B3), and on a user's named branch (G2), where it stays anyway. There it commits its own change **on the branch HEAD stands on** — the same `c1`/`c2` change replayed onto HEAD, the branch moved by `update-ref` and its index entries by `restore --staged`, no file written (the *here* form). On the default branch that is S3's `<default>`; on B3 and G2 it keeps §4.1's places for the run's files. A refused here-form commits nothing (the *mid-run* row) and holds nothing: the open run's own `end` takes the files.
- **P3 — one attribution rule for every stay** (ambiguity 2). The memo proposed no snapshot subtraction on a merged stay; S1 ("Files already dirty when the run started are not its own") and S2 ("one rule") are binding, so a merged stay subtracts its snapshot too, and leftovers dirty at its start stay for §3.4's merged-branch leave.
- **P4 — the same command typed twice is not a run typed mid-run** (ambiguity 3). Spec §3.3 tests "another command's record", and S3 ends the protection "when its command runs again": a second run of one command is how a user retries an abandoned one. D-park only keeps the first run's record from being replaced.
- **P5 — `end --no-preflight` parks too.** A second run of one command that stops before its start never parks, and its `end --no-preflight` would save over and remove the first run's open record — the record collision by another road. Where the record it ignores is open on HEAD's branch (the test of P13), `end` parks it as a start would, and puts it back as it ends.
- **P6 — the held record is also the landing's journal.** `land` writes its held entry, with the replayed tip, before `<default>` moves, and removes it after the lift; a landing a kill cut off between the two is completed by `end --resume` (the spec's case) **and** by the next preflight's held stage, which lifts an entry whose tip `<default>` already holds — so a session that never resumes leaves no file dirty for good (Review Focus 3).
- **P7 — held commits land in order.** The held stage lands them oldest first; `land` first retries any held entry and, where one stays held, holds its own change behind it with that entry's reason, so `<default>` never takes a newer change before an older one. After a retry, a file is lifted to the oldest landed entry's `c1` version where its working copy is the newest landed entry's `c2` version (Review Focus 2).
- **P8 — a held file edited since it was held.** Spec: "reported and committed as today". The flush commits it where HEAD stands and prints `pre.held.changed`, and the held commit is rebuilt without that file (its `c2` tree takes `c1`'s version of it; the ref and the entry move to the new commit), so a later landing does not put the same change on `<default>` a second time. An entry left with no file is dropped.
- **P9 — where the held stage drops instead of landing.** With HEAD on the default branch, an entry is dropped, its ref with it, and its files are the flush's: git switched to the default branch with them, so each is that branch's version with the held change on it. In session-branch mode it is dropped the same way, for §8.2's `commit`. Under `specs_git: misrooted`, on a detached HEAD or where the gate did not pass, the stage does nothing.
- **P10 — the `land` CLI.** The spec's `land --branch <b> --default-ref <r> [--snapshot <file>]`, plus what a commit and the prose need: `--command /<name>` and `--commit-key K` (the message, §4 step 4's), `--register-rebuild P`, and `--here` (P2's form); and a second form, `land --default-ref <r> --retry-held`, which runs the held stage for SRG's prose.
- **P11 — the snapshot's lifetime.** `start_dirty` is taken right after a fresh, non-re-run start's first save (its blobs written with `hash-object -w`, so the content survives), then narrowed at every call's return (`_close`) to the paths still dirty, each keeping its first blob; a `--rerun` carries its first start's and only narrows it, since the run may have written its own files between the two. None is taken under `specs_git: misrooted` or where the gate did not pass (no write under the flag); `null` where `status` could not run.
- **P12 — `merged_stay` becomes `stay`**, `{branch, kind, reason, command}`, in the record and in `start`'s JSON. `state.load` maps a 1.82.0 record's `merged_stay` to `stay` with kind `merged`, so a record left by the released version still saves (`state.save` refuses unknown keys).
- **P13 — the open-run test** is spec §3.3's plus one condition: the record's `top` equals this run's, so a record of another repository in the same session never counts. Parked records are read like any other; this command's own files never are.
- **P14 — one stay line.** Where more than one reason to stay holds, §3.5 prints one line: the misrooted one, else the unlisted one, else the mid-run one.
- **P15 — the landing's reason clause** is §6's reason clause for the refusal's reason, `<branch>` in it read as `<default>` (the reason clauses are filled first, then placed in the row).
- **P16 — the landing lives in `specs-git.py`**, as 2a kept orchestration there: a new module would need its own docs entry and rules `paths:` for no gain.
- **P17 — the unsupported clause** (§6, `mode` `unsupported`) applies to a landing's row, whose `<branch>` is `<default>`, and not to the *held* or *mid-run* rows, which name no branch the files are committed on.
- **P18 — two sessions on one checkout** — spec §3.3, "Not covered, stated" — is stated in SRG §3.5 and recorded in `to-fix.md`'s *Accepted* section (MIDRUN-2S), so the next reader finds the decision and its reason.
