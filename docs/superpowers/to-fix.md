- **D18 — a producer's handoff reuses a branch whose copy of the deliverable this run never read.** Found by the Opus review of B08 for `/specify`: a `specification.md` only on an unmerged `spec/<EPIC>-…` branch, with the checkout on the default branch, is invisible to the run (it tests the working tree and `<default-ref>`), and `handoff-to-main` then reuses that branch (`workflows-core:phase-handoff` §2.2 rule 3) and commits this run's file over the branch's copy, with no question and no archive. The same holds for every producer that reuses a plugin branch for its deliverable (`/create-ard`, `/create-prd`, `/design`, …), so it belongs in `phase-handoff` §2.2, not in one command: before reusing a branch, compare its copy of each `deliverable_paths` file with what this run read, and stop or ask where they differ. Measure which producers reach it first. **Measured 2026-10-29, and decided by the maintainer.** The overwrite this entry feared cannot happen: `handoff-to-main`'s reuse is a plain `git switch`, which refuses wherever the reused branch changed a path the run changed or left untracked (tested on git 2.53.0), so nothing is committed over the branch's copy. What happens instead is a **handoff refused after the whole run**, with no instruction for it — git's own advice, *move or remove them*, does the overwrite by hand. 18 of the 23 producers can reach it (19 with `/brd-package`'s `brd-link.md`), `/ready` on every re-run while its previous pull request is open; `/update-spec` and `/conformance` already check up front, `/harvest-decisions` and `/promote-decisions` stop on any unmerged `kb/` branch. **Decision: check up front and define the refusal** — one `phase-handoff` entry point every producer runs at Phase 0, stopping or asking where an unmerged branch of the name it would reuse changed one of its deliverable paths since forking, as `/update-spec` and `/conformance` do; and a *switch refused* row in §4.1 that keeps the run's copies and never follows git's advice.

- **D32 — document lineage: every document records the upstream versions it was built on, and every consumer checks the chain.** Agreed with the maintainer in the D19 design (`docs/superpowers/specs/2026-10-28-update-spec-design.md` § Follow-up), which built only its first, coarser step, a specification's `inputs_at`. Every produced document records, in its frontmatter, each upstream's path, the git **blob id** it read and that upstream's `Version` for display — blob ids, because a hand edit that forgets to bump `Version` still changes the hash (`proposal-record.py`'s `priced-against` record is the precedent). A moved upstream **asks**, never hard-stops, naming what changed and offering to revise or proceed with the choice recorded. **Null version**: a downstream document recording no upstream version, against an upstream that has one, is treated as outdated and asks. A downstream command's own write into its upstream — `/design`'s notes in `specification.md` — must not read as a move: hash the upstream's live items only, or skip a change the downstream command made.
