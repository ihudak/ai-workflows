## From the live checks of 2026-10-26 — any machine

- **LC11 — a rejected session-file push is settled by the run, not handed back. Decided 2026-10-27: the broad form.** The user's question in run 6. **The user's decision (2026-10-27): of three options, (a) keep the hand-over, (b) settle only the security register, and (c) the broad form, the user chose (c).** Where `push-scope` shows that every commit to publish is the run's own, the run rebases those commits onto `origin/<default>`. It merges the append-type session files with the rules session-branch mode already applies, the `info/attributes` block of `specs-repo-git` §8: `union` for an appended shape, and an overwritten one kept whole. It settles `register.json` and `register.md` by `register.py rebuild`, then continues and pushes. On any other conflict it runs `git rebase --abort` and prints today's lines. (b) was set aside because most session files are append-type, so it would have helped `/security-workflows:scan` alone. Design points to settle in its spec:
  - `--autostash` and `--abort` against the user's own dirty files on the shared checkout, measured;
  - how `commit-artifacts`, a `workflows-core` reference, reaches a rebuild that `security-workflows`' `register.py` owns;
  - the amendment that retires the rationale's refusal.

  It is a design track of its own, with a spec, an Opus review and a plan, never a batch fix. The analysis behind the choice follows.

  `workflows-core:specs-repo-git` never merges or rebases. Where the closing push is rejected, it prints `pull --rebase --autostash`, the push, and, for a register, the `register.py rebuild` lines, for the user to run. `docs/maintainers/rationale.md#specs-push-scope` refuses *Rebasing the plugin's session-file commits onto a diverged default branch*: "two writers appending to the same `implementation.md` conflict, and a rebase stopped on a conflict in a shared checkout is worse than a line naming the two commands". That reason is a conflict left standing in a file people append to. A narrower rule avoids it. Where `push-scope` already shows that every commit to publish is the run's own, rebase those commits onto `origin/<default>`. Where the rebase stops only on a file the run can rebuild exactly from its records (`register.json` and `register.md`, through `register.py rebuild`), settle it, continue and push. On any other conflict, `git rebase --abort`, which leaves the checkout as it was, and print today's lines. In run 6 the only conflicts were the two register files, so the push would have gone through unaided. Population: every default-branch-mode specs repository with concurrent writers. Session-branch mode (§8) avoids the rejection for a team that turns it on, but it switches on by itself only at a *refused* push, never at one rejected because someone else pushed first. That was option (a)'s answer, and the user declined it.
