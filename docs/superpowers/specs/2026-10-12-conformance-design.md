# `/conformance`: settle what shipped against what was specified, with or without documentation

Date: 2026-10-12. Status: design approved in conversation, section by section; amended on the user's first review (the PRD run checks Dev's decisions rather than re-tracing every Epic, the run prerequisites stated, the risks' mitigations made concrete); spec awaiting review. Branch: `iv-gu/conformance`.

## Background

`/docs-workflows:document` runs a discrepancy analysis early in keyed mode (Phase 5.8, under `workflows-core:source-truth` §7). It compares the **PRD**, the **spec** (what was intended) and the **code** (what was built). It never reads documentation: the documentation repository is only where `/document` writes. But the analysis lives inside a command that needs a documentation repository, so a project without one never gets it. `/release-notes` runs a two-way version (PRD against code) inside its own run.

Three more facts shape the gap:

- **The decisions are about documentation, and they last one run.** §7.4's `discrepancy_decisions` vocabulary is `document-as-spec`, `document-as-code` and `skip-and-report`. The record is built and handed to `doc-writer` inside one run. Nothing reads a saved discrepancy record from disk: `<KEY>-implementation-gaps.md` is written and never read back.
- **The claims come from planned pages.** `doc-planner` lists the user-visible claims the pages it plans will make (source-truth §2). Requirements no page states are never checked.
- **`/implement` checks conformance per Epic, at implementation time, and keeps only the gaps.** `code-review` dimension 10 judges `[Uxx]`/`[ACxx]`/`[TCxx]` as `satisfied`, `missing`, `partial` or `contradicts` against the change. Step 7.5 writes the unresolved `missing`/`contradicts` as `- [ ]` notes under `## Engineering review` on the spec or design. No per-requirement record survives, and nothing checks the PRD as a whole after its Epics have merged.

The user wants the delivery closed by an explicit analysis that settles every discrepancy, whether or not the project has documentation, with `/document` following where documentation exists.

## Goals

1. A `dev-workflows` command, `/conformance <ADDRESS>`, that traces **every requirement** of an Epic or a PRD against the code that shipped or is about to ship, and has a person **settle** each discrepancy: fix the code, amend the document, or accept as shipped.
2. **The role follows the address.** An Epic run is the Dev's, who owns that Epic's delivery. A PRD run is the PE's, who owns the whole PRD and makes the **final** decision on every discrepancy. Every decision a Dev recorded is put to the PE, re-checked against the merged code; none is carried silently.
3. A durable record, `_conformance.md`, that `/document` and `/release-notes` read so they do not ask again, and that `/ready` reads for a new optional stage.
4. No documentation repository needed, and no `docs-workflows` dependency.

## Non-goals

- **Changing code or rewriting a requirement.** *Fix the code* becomes a follow-up; *amend the document* becomes a note and a recommended command.
- **Replacing `/implement`'s conformance review.** That review still judges the change at implementation time; this command judges the delivery afterwards and is not invoked by it.
- **Tracing test cases.** `[TCxx]` describes how a criterion is verified, not behaviour; `test-writer` and `/implement` own tests.
- **Tracing outcomes no commit can prove.** `[SM#n]`/`[SMC#n]` (success metrics) and `[UC#n]` (narrative), following `/prd-ground`'s precedent (`prd-ground.md` Phase 2).
- **A required workflow stage.** The new stage is optional (D17).
- **Checking documentation.** That stays `/document`'s and `/docs-audit`'s.

## Terms

- **Unit.** The addressed folder: an `EPIC-` folder (an **Epic run**) or a `PRD-` folder (a **PRD run**). A BRD-route slice is a `PRD-` folder and runs as a PRD.
- **Requirement.** One traced item from D4's sets.
- **Verdict.** One of `satisfied`, `partial`, `missing`, `contradicts` (dimension 10's vocabulary), or `not-checkable` with a reason.
- **Discrepancy.** A requirement whose verdict is `partial`, `missing` or `contradicts` and survived the re-check (D8). It is numbered `[DD#n]` within its record.
- **Decision.** `fix-code`, `amend-document` or `accept`, with a status of `proposed` (Epic run) or `final` (PRD run).

| D8 | Re-check before asking | The orchestrator re-checks each `partial`, `missing` and `contradicts` verdict at the location it cites, in the manner of `workflows-core:finding-triage`'s verification step. One that does not hold is dropped, and the report says why. A `satisfied` verdict with no evidence is not taken as satisfied: it is shown as *unverified*, since a tracer that misses a discrepancy is the one error this re-check would otherwise never see. |

A `[DD#n]` is cited outside its record as `<KEY>/[DD#n]`. |
| D10 | Re-runs | A `[DD#n]` is permanent: never renumbered or reused. A re-run carries each decided entry forward, without asking again, while its discrepancy persists. | D11 | The walk | One `AskUserQuestion` per discrepancy, with no `(Recommended)` marker, since the decision is the question (`workflows-core:escalation-rules`, *The `(Recommended)` marker is unconditional*). The PRD walk takes D3's order — Dev's implementation-wins entries, then Dev's `fix-code` entries, then discrepancies no Epic recorded — and each question carries its flag (*stale*, *orphaned*, *fixed*, *still open*) and Dev's rationale. A stale entry is asked as `["Mark it resolved — the code now matches", "Keep Dev's decision — <decision>", "Cancel"]`. A free-text answer is normalised into one of the three decisions or the question is asked again, never written through as a new value: these arrays together become a tenth row of `escalation-rules`' closed-vocabulary table. |

## Worked example

Take the bookstore demo, PRD `BOOK-1` (back-in-stock alerts), with Epics `BOOK-1-01` … `BOOK-1-06`.

**When each run happens.** The **Dev** runs `/conformance <EPIC-KEY>` after that Epic's `/implement`, while its pull request is still open (D5). The **PE** runs `/conformance <PRD-KEY>` once every Epic is done and every pull request is merged (D6); a run that finds an Epic not merged names it and asks before tracing.

1. A Dev finishes `/dev-workflows:implement BOOK-1-02` (storage restock notice); the pull request is open. They run `/dev-workflows:conformance BOOK-1-02`.
   - The run reads `EPIC-BOOK-1-02-…/implementation.md`, finds the branch it recorded in `bookstore` and traces the branch tip.
   - Spec `[U02]/[AC03]` says the notice fires "within one minute of the restock"; the code schedules it every five minutes, so the verdict is `contradicts`, re-checked and confirmed.
   - The Dev chooses *Fix the code*. `[DD#1]` is recorded `proposed`, and a follow-up ``Run `/dev-workflows:implement BOOK-1-02` from repository `bookstore`: [U02]/[AC03] … — schedules every 5 minutes`` goes into the Epic's `follow-ups.md`.
   - The record lands on `conformance/BOOK-1-02` after the consent choice.
2. The Dev's next `/implement BOOK-1-02` reads the follow-up back and fixes the schedule. A re-run of `/conformance BOOK-1-02` marks `[DD#1]` `resolved`.
3. Once every Epic has merged, the PE runs `/dev-workflows:conformance BOOK-1`.
   - The merged test passes for all six Epics: five by ancestry, `BOOK-1-04` by a squashed commit whose subject ends `[BOOK-1-04]`. The run prints the number of requirements and repositories it will trace.
   - Every Epic has a record, so the run traces the PRD-level requirements in full, re-checks each Epic entry against the merged code, and re-traces only the `satisfied` requirements whose evidence changed since the Epic run.
   - First come Dev's implementation-wins entries. `BOOK-1-05` had proposed *Accept* for a label difference, and the label still differs; the PE overrules it to *Fix the code*. `EPIC-BOOK-1-05`'s entry gains `superseded-by: BOOK-1/[DD#2]`, and a follow-up goes to `BOOK-1-05`. `BOOK-1-03` had proposed *Amend the document* for a retention period, but the merged code now matches the spec — the Dev fixed it later without changing the record — so the entry is flagged *stale*, and the PE marks it resolved.
   - Then the `fix-code` entries: `BOOK-1-02`'s `[DD#1]` is shown *fixed*, as its re-run already recorded.
   - Then what no Epic recorded: `[AC#4]` of `prd.md` ("alerts can be turned off per book") is `partial` — only a global switch shipped. The PE chooses *Amend the document*; `BOOK-1/[DD#1]` is `final`, and a `## Engineering review` note on `prd.md` recommends `/product-workflows:update-prd BOOK-1`.
4. `/ready BOOK-1` does not yet derive *Delivery verified*, because `BOOK-1/[DD#2]` (`fix-code`) is unresolved. Once it is fixed and `/conformance BOOK-1` is re-run, it does.
5. `/docs-workflows:document BOOK-1` later meets the per-book-switch claim, finds `BOOK-1/[DD#1]` (`amend-document`, `final`), and documents the shipped global switch without asking.

## Risks

- **Cost of a PRD run.** D3 replaces a full re-trace with a re-check of every Dev decision at its evidence plus a drift re-trace, so the full-depth work is the PRD-level requirements and any Epic without a record. The tracers run on the Sonnet tier, Opus only synthesises and re-checks, D7 prints the scale before tracing, and D10's carry-forward makes a re-run ask only about what changed.
- **A missed discrepancy.** D8's re-check sees only verdicts that found a problem, so a tracer that wrongly reports `satisfied` would hide one. Mitigation: every verdict must cite evidence, and a `satisfied` without evidence is shown as *unverified* (D7, D8); D3's drift check re-traces a `satisfied` requirement whose evidence moved.
- **A Dev decision the code has overtaken.** A Dev may rule that the implementation wins and then fix the code without updating the record. Mitigation: the PRD run re-checks every Dev entry against the merged code and flags it *stale* (D3, D11).
- **Unnumbered `epic.md` criteria.** An acceptance bullet is identified by its quoted text, so an edited bullet is a new requirement to the next run. Mitigation: a Dev decision on text no longer in `epic.md` is shown to the PE as *orphaned*, never dropped (D3).
- **Telling that an Epic merged.** D6's test is concrete: ancestry of the recorded commit, or a default-branch subject carrying `[<EPIC-KEY>]`, which a squash keeps because `/implement`'s pull-request title is its commit subject. A merge whose message an operator rewrote without the key fails both, and the run then asks rather than assuming.
- **A record the code has moved past.** Readers say how far the default branch has moved since the record's traced commit (D18), and a re-run settles it (D10).
- **A new branch prefix** touches every site that lists the ten (prose only, no gate): `phase-handoff` §1 rule 3, §2.9 and §3.2; `specs-repo-git` §2.1 and row G2; `branch-naming`'s skip list (whose "nine" is already stale); `.claude/rules/workflows-core-git.md`; and the roles pages. Mitigation: a phrase sweep and an after-edit count of `ready|brd|frames|kb)` across the sweep scope.
- **Counts that nothing gates** (`CLAUDE.md` § Editing discipline): the dev-workflows command count in `CLAUDE.md`, `plugin.json`, `marketplace.json` and the root README; and in the rules files, the model-routing callers, the run-flags consumer sets, the `impl-maintenance` callers, `commit-artifacts`, `handoff-to-main` and `require-on-main`, the implementation-repository callers, and `followup-emission`'s callers. Each is re-derived by its stated recipe, never incremented by hand.

Two signals, both in the PRD folder and both read from `<default-ref>` by `git`, as A4 reads the record, with no `require-on-main` call and no docs-repository read: **documentation** — `pr-draft.md`, which a keyed `/docs-workflows:document` run writes there, landed (`/document` itself does not change); and **a dev-stage release note** — a draft in `release-notes.md` whose scope comment carries the line `stage: dev`, which `/docs-workflows:release-notes` now writes from its `run_phase` (`stage: pm` or `stage: dev`, `docs-workflows:release-note-types` §1).
