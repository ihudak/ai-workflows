# Multi-component PRDs: one target per Epic, the contract in the ARD

Date: 2026-10-04. Status: design approved in conversation; spec awaiting review. Branch: `iv-gu/multi-component-epics` in all three editions.

## Background

`docs/superpowers/harvest/NEXT.md` § *Follow-ups from Round 3* carries **"Multi-repository features: one repository per Epic, the contract in the ARD"**, agreed on 2026-10-04. It follows from Round 3's decision that `/implement` changes code in one repository per run: a change another repository needs becomes a companion change and a follow-up. The question that raised it was a feature that spans a client and a server repository, which `/epics` splits into, say, ten Epics, six server and four client. The PRD-level ARD and `/specify` prepare the shared API between them, or a contract Epic implements it.

While brainstorming, the user widened the unit from a repository to a **component**. A single repository with several deployable modules is multi-component as soon as a PRD changes more than one module. Two examples:

- `github.com/ihudak/bookstore`: a Gradle multi-project with nine Spring Boot services (`books`, `clients`, `carts`, `storage`, `orders`, `ratings`, `payments`, `dynapay`, `ingest`). It also has `common` (JPA entities shared by the services), `exceptions` (a shared exception hierarchy), an Angular `web/`, and `k8s/` manifests. Services call each other over HTTP with RestTemplate.
- `github.com/ihudak/weekplanner`: the same shape, with `categories`, `users`, `tasks`, `workitems`, `common`, `exceptions`, `web` and `k8s`.

A PRD that adds email validation to bookstore's `clients` module stays in one component and does not split.

The three editions are as in every round. **This repository** is canonical (`workflows-core`, `dev-workflows`, `product-workflows`, `docs-workflows`). **The internal edition** has one `plugins/dev-workflows` plugin, uses "VI" for the PRD, and writes tracker-bound Epic files with no frontmatter. **The Copilot edition** (`ihudak-copilot-plugins`) has `dev-workflows/skills/<name>/SKILL.md`, `skills/_shared/` and `agents/`, the same VI vocabulary and Epic shape as the internal edition, and its own dialect.

### What is wrong today

1. **An Epic has no target.** `epic-writer`'s template names repositories only in free text under `## Dependencies`. An Epic can span two repositories, and nothing notices until `/implement` plans half of it as an out-of-scope companion change.
2. **There is no contract.** The ARD's `## Cross-repo / component approach` says which capability lands in which repository (the Capability→Architecture map), but not the interface between them. Client and server Epics are specified and designed separately, so after `/implement` the two sides may not fit.
3. **Modules are invisible.** `/create-ard` Phase 3 maps themes to repositories. A repository's modules never appear, so a bookstore PRD across `orders`, `carts` and `web` grounds as one repository and splits as one.
4. **A PRD-level spec turns into a cross-component design.** `/design <PRD>` designs a flat PRD-level `specification.md` in preference to the Epic picker (`commands/design.md` Phase 0 step 4). `workflow-states.md`'s *Ready for Implementation* row then expects that PRD-level `design.md`. On a multi-component PRD, both make one design span every component.
5. **Nothing checks that the Epics fit together.** `/ready` is optional, and `/implement` Phase 0.5 is advisory only. An interface a client Epic consumes but no Epic produces reaches code unseen.

## Goals

1. Each failure above is unreachable in every edition.
2. Every Epic of a multi-component PRD has exactly one target, and every interface it produces or consumes is named in the ARD and cited by `AD#N`.
3. On a multi-component PRD, the ARD with its contract, the PRD-level spec, and each Epic's spec and design are expected. `/epics` and `/implement` stop with a recommended way forward when one is missing, and `/ready` caps its verdict.
4. A single-component PRD gets no new question, no new section and no new stop. It gains only the one-entry `components:` in its ARD, the `target:` on its Epics, and the `Target` line in each design header.
5. Every statement of each changed claim is found and rewritten. That covers the whole population, including the `docs/` pages and the instruction tiers (`CLAUDE.md` § Editing discipline, refinements 4, 6 and 8).
6. Every check is shown red on the pre-change tree and green after it.

## Non-goals

- **A new command** (agreed in NEXT.md).
- **`/implement` enforcing modules inside one repository.** `/implement` checks the target repository and the prerequisites (D22). It gains no module-scope rule, and its one-repository machinery (Phase 3A/3B step 2, the companion-change route) is unchanged. `/design` and `design-reviewer` keep a design inside its target.
- **`/implement` running `/ready`.** That would nest `/ready`'s specs-repo writes, consent prompts, Opus review and maintenance phases inside `/implement`, and `/ready` judges the whole PRD where `/implement` works on one Epic. `/implement` runs the deterministic part instead (D21).
- **A change to `references/specification-format.md`.** It is frozen. A PRD-level spec cites an interface `AD#N` in prose the format already allows.
- **A new requirement-ID prefix.** Interfaces are `AD#N`s, so `scripts/check-id-grammar.sh` is unchanged.
- **Per-area ARDs** (`ard-<area>.md`). These are unchanged.
- **`/idea`, `/create-prd`, `/update-prd`, the BRD-route commands, and `docs-workflows`.** These are unchanged. Where `/create-ard`, `/specify`, `/epics`, `/design` or `/ready` runs on a BRD-route slice, the slice takes exactly the path a PRD folder takes.
- **Detecting components without a human confirming them.** Enumeration only proposes a set.

## Terms

- **Component.** A repository, or a set of paths inside one repository, that an Epic can target. Its **id** is `<repo-slug>` for a whole repository, or `<repo-slug>:<path>` for a module. `<path>` is relative to the repository's top level, POSIX, with no trailing slash: `bookstore:orders`, `bookstore:k8s`.
- **Known set.** The components confirmed for one PRD: the ARD's `components:` where an ARD has them, otherwise the set `/epics` confirmed for that run (D14). It is the set every target is resolved against.
- **Multi-component PRD.** A PRD whose known set has two or more components.
- **Interface row.** One row of the ARD's `## Contracts` table: an interface between components, stated by an `AD#N`.
- **Producer / consumer.** The component that implements an interface, and the components that call it or read it.
- **Ride-along.** A change to a deploy or config component's files, made by an Epic whose target is another component in the same repository, where those files exist only to deploy or configure that target (D4).
- **Contract Epic.** An Epic whose job is to produce an interface that is a code artifact (D15).

## Worked examples

These are the walkthroughs the review traces each command's text against.

**A. Client and server repositories.** `server-repo` and `client-repo`, one PRD, ten capabilities.

1. `/create-ard <PRD>`. Phase 3 enumerates nothing in either repository, so each is one component. The architect confirms `components: [{id: server-repo}, {id: client-repo}]`. Phase 4 authors `## Contracts` with seven REST interface rows (`[AD#3]`–`[AD#9]`, producer `server-repo`, consumer `client-repo`, status `new`, artifact `—`), versioning under `/api/v2`, and landing order `server-repo`, `client-repo`. `ard-reviewer` passes. Phase 7 recommends PRD-level `/specify`.
2. `/specify <PRD>`. End-to-end acceptance criteria cite the `AD#N` each crosses.
3. `/epics <PRD>`. The ARD supplies the set, and both prerequisites are present. `epic-writer` writes six Epics targeting `server-repo`, each `Produces` some of `[AD#3]`–`[AD#9]`, and four targeting `client-repo`, each `Consumes` some of them with a stub in its Independent Test and a dependency on the producing server Epic. There is no contract Epic, because no row has an artifact.
4. Per Epic: `/specify <EPIC>` (scan narrowed to the target), then `/design <EPIC>` (one repository, a `## Contract` section).
5. `/ready <PRD>` reports contract coverage complete.
6. `/implement <EPIC>`, run in `client-repo` for a client Epic: the target matches, the prerequisites are present, and coverage for this Epic holds. It runs as today.

Had the team kept an OpenAPI file in a third repository, `api-specs`, the rows would carry `Artifact: openapi/v2.yaml` with producer `api-specs`. A contract Epic targeting `api-specs` would then come first.

**B. bookstore discount codes.** One PRD: a discount code entered in the web cart, validated by `orders`, applied by `carts`, stored on a new `Discount` entity in `common`, with the orders service URL passed to carts through `k8s`.

1. `/create-ard`. `enumerate-components bookstore` proposes fourteen components (D2). The architect confirms `bookstore:common` (`paths: [common, exceptions]`), `bookstore:orders`, `bookstore:carts`, `bookstore:web`, and `bookstore:k8s` (`kind: deploy`). `## Contracts` gets three rows:

## Amended during review

Nine whole-branch review rounds in this repository (Important findings per round: 6, 3, 1, 2, 2, 2, 2, 1, 0; the user's rule after round 4 was to stop at the first round with none) changed these decisions. The ledger's `Ruling:` lines carry the full reasoning.

1. **D3 — only code components count.** A PRD is multi-component when its set has two or more `kind: code` components. A deploy component that a module only rides along on, or deploys through in another repository, needs no contract (round 2).
2. **D2 and D5 — enumeration and grouping.** A repository that declares no modules is itself a code component (round 1). A component's grouping and corrected `kind` are recorded only in the ARD (rounds 1 and 3). A module-declaring repository has **shared ground**: every path inside none of the modules and deploy directories `enumerate-components` finds. A module target's Epic or design may change it, and both reviewers receive that enumeration in their briefs (rounds 6–9).
3. **D4 — ride-along.** A ride-along names a `kind: deploy` entry of the set or, where the set lacks one, a §2 deploy directory of the target's repository, identified by its path (round 5).
4. **D14 — `/epics`.**
   - Phase 5.5 is seeded from the targets existing Epics carry, and with code scan off those targets are its proposal (rounds 1 and 2).
   - A focus run splits its Epic when the user names, at plan approval, work that moves to another component of the set, or when the Epic's scope already spans components (rounds 5 and 6).
   - A move to a component outside an ARD's set is reported, never dropped (round 7).
5. **D19 — `/design`.**
   - "Design across components anyway" is offered only with no Epic folder and a flat spec — the shape `/implement` can reach (round 2).
   - Re-split works within an ARD's set; otherwise `/create-ard` is recommended first (round 5).
   - A span into another component is recorded as a `Target span` (rounds 2 and 9).
6. **D21 — `multi-component-prereqs`.**
   - The `epic_target` row was added (round 1).
   - Each remedy is chosen by the row's state (rounds 1 and 4).
   - A non-git `$SPECS_PATH` gives `unmanaged`, which asks nothing (round 7).
   - The target-repository check runs on any targeted Epic (round 5).
7. **D20 and D23 — the override.** A multi-component PRD built whole by the 0-Epic override — its folder holds a PRD-level `design.md` or an `implementation.md` with a block — is read by `/ready` as a single-component slice. Phase 1 sets that once, as a flag (rounds 6–8).
