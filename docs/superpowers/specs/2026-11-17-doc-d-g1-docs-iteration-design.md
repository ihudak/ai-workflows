## Intent

`/docs-audit` writes a ranked backlog of documentation units into the documentation repository, and nothing turns a unit into a page. Every step of the route between the audit and the next refresh is a procedure a person follows by hand — write the unit, capture what it shows, verify its claims (ROUTE:5, :87, :89-115, :117-157, :159-194) — and the plugin's own pages say so: `/docs-write` "is planned, not shipped" (`docs/workflow.md:70`), and ROUTE carries three *Later: … No such command exists yet* lines (:115, :157, :194). The shipped references were written ahead of these commands and still name them as their future writers: BF's lifecycle assigns `missing → drafted` to "Spec 2's `/docs-write`" and `drafted → verified` to "`/docs-verify`" (BF:102-103); `unit:` "has a reader today and no automated writer" (FG:108); "nothing in this increment composes a walkthrough" (EC:99) and "no command in this increment renders that checklist" (EC:105); and the generated navigation is "to" be regenerated by `/docs-write` (ST:5, :464), until which a page is placed by hand (ST:466, ROUTE:104 — the interim fix of DOC-C-B1, `docs/superpowers/reviews/2026-10-26-bugs-review.md:2102`, which the fix-batches note at :482 says this track replaces).

This design adds the three commands that work the backlog: `/docs-write` drafts a unit's page, `/docs-verify` resolves its claims, `/docs-capture` records a process before it is written. It settles the contracts all three share — the state machine, the evidence each move rests on, where each artifact lives, the docs-repository git discipline, untrusted input, GIT-G1 — and specifies `/docs-write` in full. `/docs-verify` and `/docs-capture` are specified to the depth their contracts need, with the rest named for their own sub-project's design questions (D1).

**One noun.** *A backlog run* is a run of any of the three commands: one that reads the backlog, works one or more units, and moves each unit it finishes. Every rule below that binds all three says *a backlog run*.

## What exists today

- **The backlog** lives at `<top>/.dev-workflows/docs-backlog.yml`, `<top>` the docs repository's git work-tree top level, and is tracked and reviewed in a pull request (BF:154-158). Its status enum is five values, closed against today's writers and open to a later addition: a reader "treats an unrecognised `status` as a value a later spec added … reports the unit and leaves it alone" (BF:97). `captured` is the sixth value the family design drew and BF deliberately left out (BF:97).
- **The lifecycle table** names, per edge, the command that writes it (BF:99-107). Today `/docs-audit` is the only writer of anything: `missing` at mint, and `missing → drafted` or `missing → published` on a `--refresh` that matches a page by its `unit:` key, by whether the page carries a marker (BF:109-116). `verified → published` has no command "in any spec" (BF:104, :118); `drafted → published` is not a transition (BF:120).
- **The evidence contract** fixes one interface with two implementations: a user-audience claim is resolved by observation, an engineering one by a code read, never the other way round (EC:19-24, :135); three evidence kinds, `code` and `artifact` recording a `ref` (EC:34-38, :136); a claim that could not be grounded marked `[NEEDS CLARIFICATION]`, never becoming prose fact by default (EC:53-61); the walkthrough file at `<top>/.dev-workflows/walkthroughs/<id>.yml` with a closed verb set (EC:91, :97); and a v1 execution of `confirmed` / `differs` / `blocked`, `differs` requiring the observed text (EC:105-125).
- **`/docs-audit`** resolves the docs repository with `resolve-docs-repo` (AUD:32), runs the specs preflight (AUD:34), requires `<top>` writable (AUD:36), and leaves the backlog uncommitted in the working tree, with no branch and no commit in the docs repository (`.claude/rules/docs-workflows.md:38`). Its cost and feedback land under `$SPECS_PATH/documentation/<docs-repo-slug>/` (family D19; `plugins/workflows-core/references/cost-emission.md:604`).
- **`/document`** has two modes and neither reads a backlog. Keyed mode needs a PRD folder, an implementation record and diffs (DOC:13, :64-140) and writes its pull-request draft into the PRD folder (FH:93). Direct mode has no review gate and "no branch and no commit, ever" (`.claude/rules/docs-workflows.md:54`, :56; DOC:1848).
- **The agents `/document` uses are PRD-shaped.** `doc-writer` takes `folder_read`, `diff_summaries` and a planner checklist (`agents/doc-writer.md:14-26`); `doc-reviewer` "refuse[s] to review without the written file paths, the `doc-planner` checklist, and the diff summaries" (`agents/doc-reviewer.md:34`); `doc-planner` refuses without `folder_read` (`agents/doc-planner.md:29`). `doc-location-finder` is not: it takes a `feature_summary` and optional `diff_highlights` (`agents/doc-location-finder.md:14-20`).
- **Nav generation** is a rule in ST §4 — sort each section's pages on `order`, then `title`; both configs generated; a hand edit vanishes at the next generated write (ST:458-470) — which `/docs-init` executes by name (`commands/docs-init.md:106`). Whether a repository runs it is not in the profile: `generator` is informational and "no consumer branches on its value" (`references/docs-profiles/docs-profile-schema.md:104`).
- **The docs-repository finish** for a run with no PRD is `/docs-init`'s: branch before the first write, commit by pathspec, a drafted pull-request message printed, never pushed (`commands/docs-init.md:92-103`, :219-226). `/document` keyed squashes, offers an opt-in push and writes `pr-draft.md` to the PRD folder (FH §2-§5, :27-133). No command of the plugin opens a pull request in a docs repository (FH:8).
- **The specs repository's bounded paths** admit, for a documentation run, `documentation/*/dev-workflows/**` and nothing else (SRG:112-123, :128); a non-git write target files under the target's basename, and "three runs' command bodies lead to that last case" (SRG:132).

## Goals

1. **Route step 4 runs as a command**: `/docs-write` turns the highest-priority actionable unit into a reviewed page on a branch, writes `unit:`, `evidence:` and `review_by`, regenerates the navigation, and moves the unit `missing → drafted` in the same commit.
2. **Step 6 runs as a command**: `/docs-verify` resolves a drafted page's claims by its audience's method and moves `drafted → verified` only where nothing is left unresolved.
3. **Step 5 runs as a command**: `/docs-capture` records a process and its screenshots and moves `missing → captured`.
4. **The coverage grid moves only on evidence**: no command certifies its own prose (BF:120; family D17).
5. **No existing command changes behaviour** (D15).
6. **A minimal GIT-G1 footprint**, every edit listed for approval by name.

## Non-goals

- **`/docs-drift`** (DOC-D-G2), and so `published → stale` and `stale → drafted` as drift writes them (BF:105-106).
- **A browser driver** (family D3's v2). The walkthrough format is unchanged so that one can come later (EC:127).
- **`verified → published`**, which stays a person's act (BF:118).
- **`release`-surface units** — the What's-new pages. `/docs-write` refuses them in this track (D14).
- **Any change to `/document`**: no third mode, and no nav regeneration in keyed mode (logged, D17).
- **A `schema_version` bump**, a tracker projection, a backlog in the specs repository, or a pull request opened in the docs repository by the plugin.

## Anti-goals

- **A unit moved by a run that did not finish it** (D8).
- **A command certifying its own prose**: no `drafted → published`, and no `drafted → verified` that no human answer or code read stands behind.
- **A user-audience claim resolved by a code read**, or an engineering one by observation (EC:135).
- **A second copy of `/document`'s chain** in prose that drifts from it (D4).
- **A backlog, profile, walkthrough or capture value that steers the run**: each is resolved against a known set or tested against a class before it reaches a path, a ref or a shell (D13).
- **Any write into a source repository** (`references/docs-profiles/docs-profile-schema.md:102`), and any deliverable, deliverable branch or branch prefix in `$SPECS_PATH` — the session branch `specs-repo-git` §8 may create for a run's session files (AUD:34) is that reference's, not this design's.

## Decisions

### D1. Three sub-projects, one contract

**This design settles every rule that crosses the three commands and specifies `/docs-write` in full; it builds in three sub-projects, each with its own plan, reviews and release** (question 1):

1. **`/docs-write`**, with all three selectors (`<unit-id>`, `--next`, `--batch <n>`). It ships something usable alone: route step 4 becomes a command, and its units sit at `drafted` until step 6, still by hand, moves them — which is what `drafted` means (BF:116). Done when a `--next` run on a scaffolded repository commits one page, its regenerated navigation and its unit's move in one commit, and the strict public build passes over it.
2. **`/docs-verify`**, both backends. Second, because it is the only way a unit `/docs-write` drafted reaches `verified` without a person editing the backlog, and it closes the loop the coverage grid measures.
3. **`/docs-capture`**, and with it the `captured` status. Last, because a how-to drafted code-first still reaches `verified` through `/docs-verify`'s composed walkthrough (D11): capture improves process-shaped pages and blocks nothing.

The family design ordered capture before write for process-shaped units (family D22). That order is right for a how-to's quality and wrong for shipping: it puts the most interactive command, and the one with the most open questions, ahead of the one that unblocks every other type. **Each sub-project opens with a design-questions step** for what this document leaves to it (*What is left to the builder*), as P3 §5's batches do.

**Rejected:** a design for `/docs-write` alone, the others later — the state machine, walkthrough ownership and the git discipline bind all three, and settling them three times is the drift BF exists to prevent (BF:9).

### D2. Where each artifact lives, and which git authority applies

| Artifact | Where | Written by | Git authority |
|---|---|---|---|
| The backlog | `<top>/.dev-workflows/docs-backlog.yml` (BF §6) | `/docs-audit`; a backlog run, two keys of one unit (D8) | the backlog run's docs-repo finish (D10) |
| Pages | the content root the profile declares, in the docs repository `resolve-docs-repo` answers (D3) | `/docs-write`; `/docs-verify` edits | same |
| Walkthroughs | `<top>/.dev-workflows/walkthroughs/<id>.yml` (EC:97) | `/docs-verify` composes; `/docs-capture` records | same |
| Images | per `images.policy` (ROUTE:145-155) | `/docs-capture` | same, `in-repo` only; the others commit none |
| Cost and feedback | `$SPECS_PATH/documentation/<docs-repo-slug>/dev-workflows/` (SRG:115, :128) | the emitter tail | `workflows-core:specs-repo-git`, through the `specs-git` skill's `start` and `end` |

- **The backlog is in the docs repository alone**, where family D5 put it and BF §6 pins it. Nothing is mirrored into the specs repository.
- **Pages are written into `$DOCS_PATH` only where `resolve-docs-repo` answers there** — its rung 3 is a write-target rung (RR:28), not documentation grounding, which these commands do not resolve (D14).
- **Two authorities, one per repository.** `$SPECS_PATH` takes only the bookkeeping `specs-repo-git` already bounds: every backlog run runs `specs-preflight` in its Phase 0, keyless, and `commit-artifacts` as its last action (`CLAUDE.md` § Hard constraints). The docs repository takes FH, widened by a section for a backlog run (D10).
- **No `phase-handoff` register row changes, and no `require-on-main` caller, producer or `branch-check` caller is added.** The register classifies the specs-repository deliverables the tree's `deliverable_paths` name (PH:406); these commands declare none and call no `handoff-to-main`. `phase-handoff`'s every git call is `git -C "$SPECS_PATH"`, so it has no reach into the docs repository the backlog lives in. No branch prefix is added: SRG §2.2's set governs branches in `$SPECS_PATH`, and these commands create none there (SRG:128, last sentence).

### D3. The target, and the one stop that takes no tail

- **The selector never reaches the ladder.** RR's rung 1 takes "the first positional token … as given" (RR:26). A unit id there would resolve as a directory, the failure AUD step 1 records for a mistyped flag (AUD:30). So the docs repository is named by a flag of its own, `--docs-repo <path>`, handed to `resolve-docs-repo` as its rung-1 token; the unit id is never handed to it. With no flag the ladder starts at rung 2.
- **The target is a git work tree's top level.** A backlog run commits, so a directory outside any work tree is no target for it. **That stop is a refusal before the target is resolved**, and takes no tail, as SRG §4 lets a command state where its cost entry is filed per target (SRG:757-761) — the same reading AUD:32 takes for its ladder's Cancel. That keeps SRG:132's "three runs' command bodies lead to that last case" true, and is why it is stated here.
- **The other pre-target stops** — an unknown flag, a bad `--batch` value, a run-flag stop, the ladder's Cancel — take no tail either, as AUD:30 and :32 do.
- **After the target**, every stop takes AUD's stop route (AUD:18): the report, then the emitter tail, `commit-artifacts` last.

**Rejected:** taking the tail on a non-git target. It files the entry under the target's basename, a fourth run behind SRG:132, which is a GIT-G1 edit for a run that did nothing.

### D4. `/docs-write` against `/document`: its own phases, the same agents, one reference for the difference

`/docs-write` is the chain the family design drew (family §12.1, :771-790) — ground, write, style, review, triage, fix — but it is **not** `/document` behind a front end, because no mode of `/document` can take a backlog unit:

- **Delegation is rejected.** Keyed mode needs a PRD folder and diffs; direct mode is held by invariants to no review and no commit (`.claude/rules/docs-workflows.md:54`, :56). A third mode would change `/document`, against goal 5. And one command starting another while its own run is open is exactly what GIT-G1 Part 3 rules out: under its P4, a command typed while another run of the session is open asks before it starts (P3:24), and "no command may start a pipeline command while its own record is open" (P3:79). The only way round that is an `--inline` mode that skips the start, which the `specs-git` skill records as one command's exception (`plugins/workflows-core/skills/specs-git/SKILL.md:10`).
- **A shared reference extracted from `/document` is rejected for now.** `/document` is 328,791 bytes (`wc -c`), and its phases interleave the PRD read, the discrepancy escalation, the CDN handoff and the gate registry; extracting a chain out of it is a regression risk to the plugin's most-used command for a benefit the agents already give.
- **Own phases, the same agents.** `/docs-write` dispatches `code-scanner`, `doc-location-finder`, `doc-writer`, `docs-style-checker`, `doc-fixer` and `doc-reviewer`, and cites the references `/document` cites for the same steps: `toolchain-preflight`, `gate-ledger` (adopted by §7's rule, `references/gate-ledger.md:159-163`), `render-verification`'s build check, `repo-verification-gates` as direct mode applies it without a planner, `workflows-core:finding-triage`, `workflows-core:escalation-rules`. What drifts if it drifts is the agents' contract, and that has one copy.
- **The difference lives in one new reference, `references/docs-iteration/unit-brief.md`.** `doc-writer` and `doc-reviewer` each gain one conditional sentence: where the brief carries `brief_kind: unit`, read that file and follow it in place of the named input and refusal sections. A brief without the field — every `/document` dispatch — reads exactly today's text. The file holds the unit brief's inputs (the unit, its surface row, the scanner returns, the artifacts' text, a walkthrough where one exists, the write target, the profile), the writer's marker and frontmatter rules (D9), and the reviewer's refusal and dimension map: factual correctness against the evidence in place of the PRD and diffs; an *evidence contract* dimension (markers, reserved keys, evidence entries with their `ref`, `review_by`, the visibility-path pair and the internal marker); completeness against the unit's type in place of the planner checklist; the rest as written.
- **`doc-location-finder`, `docs-style-checker`, `doc-fixer` and `code-scanner` are unchanged.** `doc-planner` is not used: the unit and its evidence are the plan.

**Rejected:** two new agents, a unit writer and a unit reviewer. Each would copy the frontmatter, snippet, anchor, traceability and untrusted-content rules the two existing agents hold, and the copies would drift. (Question 2.)

### D5. `/docs-write`'s phases

Signature: `/docs-write <unit-id>|--next|--batch <n> [--docs-repo <path>] [--skip-costs] [--skip-feedback] [--enforce-model=<model>]`.

- **Phase 0 — Resolve.** Strip the run flags; load the question rules (`escalation-rules core`) **before the start call**, as P3 §4.3 requires of every command that will ask P4's question; parse the selector, one of the three and exactly one; resolve the target (D3); test `<top>` writable; run `specs-preflight`, keyless (no `--key`, no `--commit-key` — a unit id is not a key, D13); read the profile — absent or unreadable is a stop naming `/docs-workflows:docs-profile`, since the content roots and the build commands are the profile's; read the backlog — absent is a stop naming `/docs-workflows:docs-audit`, an unknown `schema_version` a stop that writes nothing (BF:65), and a backlog that is not committed a stop (D10); run the toolchain preflight against the profile, as DOC Phase 0 step 7 does.
- **Phase 1 — Select** (D7), **and route.** Classification is MODERATE per unit (family §12.1); `doc-writer` on the Opus chain it is pinned to, `doc-reviewer` on its Opus pin (family D20).
- **Phase 2 — Ground.** Resolve each evidence entry's `repo` against `sources[]` and then the profile's `source_repos[]` (D13); dispatch one `code-scanner` per repository in a single response, capped at four, `search_hints.paths` set to the unit's evidence paths, refreshed by `workflows-core:scan-refresh`'s fixed policy as AUD Phase 2 is; resolve each `prep.scanned_ref` to its commit, as BF:89 requires of `sources[].ref`. Read each `artifact` entry at the specs repository's `<default-ref>` alone (D14). Read the unit's walkthrough where it names one.
- **Phase 3 — Place.** `doc-location-finder`, with a `feature_summary` composed from the unit's title, type and surface and `diff_highlights` from its evidence paths. Only a new page is a legal target: one unit is one page (CM:83), so an `extend-existing` candidate is never taken. The path honours BF §7 — under the internal tree exactly where `visibility: internal`. A single unit's plan is confirmed once — unit, evidence, path, branch — `["Write it (Recommended)", "Enter another path (you'll be prompted)", "Cancel"]`; a batch is placed whole first, then confirmed once (D7).
- **Phase 4 — Branch** (D10), before the first write.
- **Phase 5 — Write.** `doc-writer`, `brief_kind: unit`.
- **Phase 6 — Style.** `docs-style-checker`, then `doc-fixer` on its findings (no triage on the style-fed dispatch, as in `/document`).
- **Phase 7 — Navigation and build.** Regenerate the navigation (D9), then run every `builds[]` command — the strict public build is gate 1 (ST:506) — gating, each result a ledger row.
- **Phase 8 — Review.** `doc-reviewer` at Opus, `brief_kind: unit`; `finding-triage`; `doc-fixer` on survivors; one fix cycle and one re-review; an unresolved BLOCK escalated as DOC Phase 7 does. Any edit after Phase 7 re-runs Phase 7 before the commit.
- **Phase 9 — Commit the unit** (D8, D10).
- **Phase 10 — Finish** (D10): the push offer and the printed pull-request draft, once per run.
- **Phase 11 — Report**, then the emitter tail as AUD's: `impl-maintenance` and feedback, follow-ups kept in the report (no PRD folder), cost, `commit-artifacts`.

`--batch` runs Phases 2 to 9 per unit after one Phase 3 placement pass and one consent; Phase 4 runs once.

### D6. The state machine

| From | To | Written by | In which commit |
|---|---|---|---|
| *(none)* | `missing` | `/docs-audit` | — (unchanged) |
| `missing` | `captured` | **`/docs-capture`** | the walkthrough and its in-repo images |
| `stale` | `captured` | **`/docs-capture`** | same |
| `missing` | `drafted` | **`/docs-write`**; `/docs-audit --refresh` (unchanged) | the page, its navigation |
| `captured` | `drafted` | **`/docs-write`** (from sub-project 3) | same, prose derived from the walkthrough |
| `stale` | `drafted` | **`/docs-write`**, by `<unit-id>` only; Spec 3's `/docs-drift` (unchanged) | the rewritten page |
| `drafted` | `verified` | **`/docs-verify`** | the resolved page, the walkthrough's results |
| `verified` | `published` | none — a person (unchanged) | — |
| `published` | `stale` | Spec 3's `/docs-drift` (unchanged) | — |
| `missing` | `published` | `/docs-audit --refresh` (unchanged) | — |

- **`captured` joins the enum with its writer, in sub-project 3**, by BF's own reasoning: "a value no writer produces is a state a reader has to handle for no benefit" (BF:97). **`schema_version` stays 1**: BF:97 makes the enum open precisely so that this addition costs no version — a reader on an older release reports a `captured` unit and leaves it alone. `captured` counts in its cell's denominator and never its numerator (BF §5).
- **`stale → drafted` by `/docs-write`** is the route's step 8 made executable: a page that "is not" right "goes back to step 4" (ROUTE:210), which a person marks by setting `stale`. Only an explicit `<unit-id>` takes it, since nothing writes `stale` today.
- **What a backlog run refuses to move**: `/docs-write` a unit whose status is `drafted`, `verified` or `published` (an edit to such a page is `/document` direct mode's or a person's); `/docs-verify` anything but `drafted`; `/docs-capture` anything but `missing` or `stale`. Each refusal names the status.
- **No edge from a run's own judgement**: `drafted → verified` needs a recorded answer or code read for every claim it resolves (D11), and there is still no `drafted → published` (BF:120).

### D7. Selection, consent and review

- **`<unit-id>`** is resolved against `units[].id`, compared whole (D13). A unit with a non-empty `blocked_by` is refused, naming the tokens, since ROUTE:91 asks a person to settle them first.
- **`--next` takes the first candidate**, where a candidate is a unit whose `status` is `missing` (and, from sub-project 3, `captured`), whose `blocked_by` is empty, whose `surface` names a row of `surfaces[]` or is `null` with evidence or a `journey` (BF:67-71), whose surface kind is not `release` (D14), whose id is in the safe class (D13), and that no unmerged branch of the docs repository already carries past that status (below). Order: `priority` ascending — the lowest number first, as BF:148 reads the threshold — then file order. No candidate is a stop that names why the nearest units were passed over.
- **The unmerged-branch read.** ROUTE:110 names the trap: a unit drafted on a branch not yet merged is still `missing` on the base, and a run from the base picks it again. So `--next` and `--batch` read, for each local branch and remote-tracking branch not merged into the base (`git -C <top> for-each-ref`, `--no-merged`), that ref's backlog by `git show`, and skip a candidate whose `status` there is past this one, naming the branch. A ref's backlog is data: only the candidate's own entry, found by its id compared whole, is read. *Assumption:* the count of such refs is small; the builder caps the read and says so where it stops early.
- **`--batch <n>`** takes `n` from 1 to 10 — the cap bounds one run's Opus spend, which family D20 controls by throughput, never by a weaker gate. It applies `--next`'s rule `n` times and excludes `tutorial` and `how-to` units, which are process-shaped (family D22) and written one at a time. It places every unit first (Phase 3), prints the list — id, title, type, priority, page path — and asks once: `["Write these <n> units (Recommended)", "Cancel"]`. Fewer candidates than `n` is said, not a stop.
- **Each unit takes its own full gate.** A batch is never reviewed as one diff. An unresolved BLOCK is escalated as in a single run, and the batch waits on the answer: the family's rule that a finding needing a decision is a person's applies inside a batch too. *Cancel the whole run* ends the batch after the units already committed.

### D8. A unit moves only in the commit that finishes it

- **The backlog is written last.** A unit's two keys — `status`, and `page_path` where it was `null` — are edited only after its review has settled and its last Phase 7 build has passed, immediately before its commit, and they go into that commit with the page and the navigation. A run that stops at any earlier point has not touched the backlog for that unit.
- **A targeted edit, never a rewrite.** The edit changes those two keys inside the one entry whose `id` is the unit's, compared whole, and nothing else in the file — every human field, comment and other unit is byte-for-byte what it was (BF:81's preservation, applied to a writer that is not `/docs-audit`). No stdlib YAML parser ships with the plugin's scripts (`grep -rln 'import yaml' plugins/*/scripts` finds none), so the run re-reads the entry after the edit and stops, unstaged, where it is not what it wrote.
- **`page_path` is written for a page that exists** (BF:184), and only together with the move.
- **What a stopped run leaves.** Its page files stay in the working tree, uncommitted, named in the report with the unit and its unchanged status; nothing is deleted. The next run's clean-tree check names them (D10).

### D9. What a drafted page carries

- **The four reserved keys** from the unit (FG:87-108): `type`, `audience`, `visibility`, and `unit: <id>` — the first automated writer of `unit:`, which retires FG:108's asymmetry.
- **`evidence:`** in EC §2's shape: `code` entries with the commit Phase 2 resolved for that repository, never the backlog's `sources[].ref` when the code has moved since the audit — the page rests on what was read, and EC:36 re-checks a page "at that `ref`, and at the current one". Where the two differ, the report says the code moved since the audit and leaves `sources[]` alone, which is `/docs-audit`'s to re-derive (BF:81). `artifact` entries with the specs commit read. A `walkthrough` entry where the unit has one.
- **`review_by`**, the calendar backstop (FG:113), from the surface's `volatility`: high 90 days, medium 180, low 365, from the run's date; a `surface: null` unit takes 180. Derived from a field the backlog already holds, so no profile key is added. *Assumption:* the three intervals; they are the builder's to confirm against a live run.
- **Markers.** Every claim the evidence does not ground is marked `[NEEDS CLARIFICATION: <why>]` (EC:57). A user-visible claim drafted from code is **not** marked for that reason alone: family D3 makes code-first drafting plus observation the user method, and `drafted` already says the page is unwalked (BF:116). - **The internal marker** as the first line after the frontmatter of a page under the internal tree (`references/docs-workflow/visibility.md:97-102`), which visibility.md:5 already says "a page it writes under `internal/` is to carry".

### D10. The docs-repository git discipline

FH gains a section, *A backlog run's finish*, cited by all three commands:

- **The backlog must be committed before a run starts.** Where `git -C <top> status --porcelain -z -- .dev-workflows/docs-backlog.yml` prints anything, or the file is untracked or ignored, the run stops before its branch step, naming the commit to make. A stash would hide the very file the run read; proceeding would fold the audit's whole uncommitted output into a page's pull request. `/docs-audit` leaves the backlog uncommitted by design and ROUTE:77 already tells the operator to commit it, so this makes step 3's last bullet a precondition. (Question 3.)
- **Adopt or cut, once per run.** On the base — or a detached HEAD — the run cuts a branch from the base, the base resolved by `workflows-core:read-only-repos` §3's chain as `/docs-init` and DOC 6.2 resolve it, named by `workflows-core:branch-naming` (§1.4's no-convention case, prefix fallback `docs/`; a profile's `branch_naming.pattern` wins) and always confirmed. On any other branch it asks `["Continue on <branch> (Recommended)", "Cut a new branch from <base>", "Cancel"]`: several units stacked on one branch make one pull request, and a run continuing there reads the backlog its earlier units moved.
- **The clean-tree check** is `/docs-init`'s (`commands/docs-init.md:98`): stash, proceed or cancel, each dirty path named. Under *Proceed anyway* a nav config somebody had edited is committed with those edits, and the report says so, as FH:31-39 does.
- **One commit per unit, by pathspec**, as FH §2 commits: ST §7's commit-time ignore test over the unit's paths, `git add -- <paths>`, `git commit -F <message file> -- ':(literal)<path>' …`, the index brought back in step. The message follows `profile.commit_convention`, else a `docs:` prefix, and names the unit id as provenance in the commit message, where `doc-structure-conventions` §1's table puts it — never as a key placeholder's value.
- **Push is opt-in, once, at the end** — FH §3's `["Push <branch> to origin now", "Skip — I'll push later", "Cancel"]`. A backlog run writes pages, like `/document`, not configuration like `/docs-init`, and runs many times; an offered push saves a step without taking the choice. Never forced.
- **The pull-request draft is printed, not filed.** FH §5 writes `pr-draft.md` into the PRD folder (FH:93), which a backlog run does not have, and `documentation/<slug>/` admits only `dev-workflows/**` (SRG:115), so filing it in the specs repository would be a GIT-G1 edit for a draft. The draft — units moved, each page path, each review verdict and triage, each build result, markers left per page, deferred items, ignored paths left uncommitted — is printed, and written to one `mktemp` file outside every repository (`workflows-core:run-flags` §7) for FH §5's host footer command to read. FH §5's last line, the `implementation records read` instant, is `/document`'s and is not written.

### D11. `/docs-verify`

- **Selector:** `<unit-id>` or `--next` (the highest-priority `drafted` unit with an empty `blocked_by`); no batch in sub-project 2, since every user unit is an interactive walk.
- **The backend is the unit's `audience`, never chosen** (EC:19-24, :135).
- **The user backend, as built without a driver, is the checklist EC §5 already defines, run by the command.** It loads the unit's walkthrough, or composes one (below); prints each step with its `expect`; and asks one question per step, `["confirmed", "differs — I'll type what I saw", "blocked — I'll say why"]`, a `differs` asking for the observed text in plain text and re-asked while empty (EC:113), a `blocked` asking for the note. It writes each answer back as `result:` (EC:115-125). **Asynchronous form**: where every step of the file already carries a valid `result`, written by a person who walked it away from the session, the run takes those answers without asking — EC:105's "the answers go back into the file by hand", now read by a command. The questions are bounded, one per step, so the run does not cede control, and `commit-artifacts` stays its last action (SRG §4's ceding exception, and its list of commands, untouched).
- **Composing a walkthrough** for a user unit with `walkthrough: null`: a new agent, provisionally `walkthrough-composer`, drafts steps from the drafted page in the closed verb set (EC:91) — a step per instruction of a how-to or tutorial, a `navigate` and an `expect` per observable claim of a reference or explanation page. A claim the five verbs cannot reach stays marked, which is EC:91's finding, not a sixth verb. The id is the next `W-<n>` free in both the walkthrough directory's listing and `units[].walkthrough`.
- **The engineering backend is a code read, not the gate ledger.** The ledger accounts for the gates a run ran and how — it confirms no claim (`references/gate-ledger.md:13-23`, :159-163); the run adopts it for its own build, style and review gates. The read is a new read-only agent, provisionally `claim-checker`, which re-reads each claim the page's evidence covers at the entry's `ref` and at today's commit, by `workflows-core:source-truth` §3's techniques, and returns per claim `confirmed`, `differs` (the code's value and `path:line`) or `unresolvable`.
- **Applying answers.** `doc-fixer` applies the dispositions: a confirmed marked claim loses its marker; a `differs` claim is rewritten to the observed text or the code's value and loses its marker; a `blocked` step's or an `unresolvable` claim's text stays or becomes marked. Then style, the build, and `doc-reviewer` at Opus with the unit brief and the recorded answers, checking that each edit says what was answered and nothing more — family §12.3's failure mode (:829-831) — triage, fixer.
- **What `verified` claims, and what it does not.** The unit moves only where, after the pass, the page carries no marker and — user — every step was answered `confirmed` or `differs`, none `blocked`, or — engineering — no claim was `unresolvable`; and its `evidence` refs are advanced to what this run read, a `walkthrough` entry added where one was walked. It asserts that each claim the page makes was observed in the environment and role the walkthrough names, or read in the code at the commit recorded. It does not assert that the page is complete beyond its unit, that the product behaves so in another environment or role, or that the page is published. Otherwise the unit stays `drafted` and the report names what is left.

### D12. `/docs-capture`

- **`/docs-capture <unit-id> [<capture-dir>]`**, for `how-to` and `tutorial` units only — fact-shaped units never run it (family §12.2, :794).
- **It starts from a skeleton, not a blank.** `code-scanner` over the unit's evidence (routes, forms, validation messages, which roles reach which screen), then `walkthrough-composer` in skeleton mode (family §12.2, :796).
- **Interactive mode** walks the skeleton step by step in the session, recording `confirmed` / `differs` / `blocked`; each capture slot asks for the path of a screenshot the person took, or none. **Folder mode** reads `capture.md` (numbered steps, images inline), or numbered images with an optional `notes.md`, and proposes an alignment of notes to images that the person confirms (family §12.2, :798-819).
- **The skeleton and the capture are reconciled and the difference is reported, never resolved** (family §12.2, :816).
- **Images** land by `images.policy`: `in-repo` under `images.root` — and under the internal tree where only internal pages may see one, ROUTE:155's trap — one path per slot, within `images.max_bytes`; `object-store` and `cdn` commit nothing, staging each file where the operator names, outside every repository, the slot keeping its placeholder until a URL is given.
- **Never automated:** performing the process; taking a screenshot; uploading to an object store or CDN; choosing a tutorial's journey (CM §4); confirming an alignment; resolving a skeleton-capture discrepancy; and judging that an image shows nothing it must not — a customer name, a host name, a token in an address bar, the deletability case family §8.4 sizes. Each image is shown to the person by path, and the run asks once per run whether every one is fit for the build it will ship in. **Video is rejected outright** (family D22).

### D13. Untrusted input: what is resolved, what is quoted, who sees what

The backlog is a tracked file any committer edits, by design (CM:97); a walkthrough, a capture folder and a profile likewise. Every value read from them is data.

- **Resolved against a known set, never parsed.** A typed `<unit-id>` against `units[].id`, whole. An evidence `repo` against `sources[].repo`, then the clone by the profile's `source_repos[]` order — `path`, then `origin` matched against each clone's own remote, then ask (`references/docs-profiles/docs-profile-schema.md:100`). A walkthrough id against the walkthrough directory's listing. A free-text picker answer is normalised into the picker's vocabulary or re-asked (`workflows-core:escalation-rules` §0).
- **A class before any value reaches a path, a ref or a branch name.** An id used in a branch slug or a file name: `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`, else the unit is reported and never selected. A ref a backlog or page records: a full hex object name, `^[0-9a-f]{40}([0-9a-f]{24})?$`, else unused. A path: relative, no `..` segment, no leading `-`, no control character, resolving inside its repository at the ref; a page path additionally inside the profile's content root, `.md`, and in BF §7's agreement with `visibility`. A capture folder: an existing directory, every file read inside it with no symlink leaving it; image destinations named by the run from the slot, never from a source file name.
- **A unit id is not a key.** It matches `workflows-core:addressing` §1's grammar (`U-001` does) and is still never added to the run key set, passed as `--commit-key`, or written into a `[<key>]` subject.
- **Shell.** Every such value reaching a command is single-quoted with each `'` written `'\''` (FH:132), placed after `--` where git takes paths, committed by `:(literal)` pathspec, and a commit message goes through `-F <file>` (FH:44-53); a branch name passes `git check-ref-format --branch` before any switch.
- **Who sees what.**

| Agent | Sees | Does not see |
|---|---|---|
| `code-scanner` | one source repository; the unit's title and type as its `context`; the evidence paths as `search_hints.paths` | the docs repository; other units; `priority_reason` |
| `doc-location-finder` | the docs repository; the composed summary | source code |
| `doc-writer` | the unit brief: the unit and its surface row, scanner returns, artifacts' text, the walkthrough, the profile, the target | other units |
| `docs-style-checker`, `doc-fixer` | the page; the triaged findings; in `/docs-verify`, the recorded answers | the backlog |
| `doc-reviewer` | the page, the unit brief, the source repositories, the ledger; in `/docs-verify`, the recorded answers | other units |
| `walkthrough-composer`, `claim-checker` | the page; the unit's evidence; in capture, `capture.md` and `notes.md` | the backlog's other entries |

  Every one of them carries the family's untrusted-content block (e.g. `agents/doc-writer.md:102-137`); a new agent carries it too. Observed text typed by a person comes off a screen that may show attacker-chosen text: it is written as a YAML string, shown quoted, handed to agents as data, and never reaches a shell. A screenshot is an image an agent can read; it is data, and an image's text that tries to steer is reported as the block says.
